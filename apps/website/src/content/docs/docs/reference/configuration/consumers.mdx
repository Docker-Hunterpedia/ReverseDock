API clients and users that requests are attributed to, with their API keys (stored hashed). The `api` provider may add consumers and keys (`rdock consumers`).

<Status maturity="beta" />

## `consumers.<name>.groups`

**Type:** list of `string`

Groups, in order of precedence: per-group limit overrides use the first listed group that has one, and `api_key.groups` admits a consumer in any of them. In the admin API's document, an entry without `groups` only adds keys to a consumer of the file.

## `consumers.<name>.keys`

**Type:** list of object

API keys, stored as their ID and the SHA-256 of their secret; never the key itself.

### `consumers.<name>.keys[].expires`

**Type:** `string`

When the key stops working: an RFC 3339 time, e.g. `2027-01-01T00:00:00Z`.

### `consumers.<name>.keys[].hash`

**Type:** `string` · **Required**

SHA-256 of the key's secret (the 32 characters after the ID's `_`, without the 6-character checksum), as 64 lower-case hex digits. `rdock keys hash` prints it.

### `consumers.<name>.keys[].id`

**Type:** `string` · **Required**

The key's public ID: the 12 characters after `rdk_`.

### `consumers.<name>.keys[].note`

**Type:** `string`

What the key is for.

## `consumers.<name>.keys_file`

**Type:** `string`

A file of `id:sha256[:expires]` lines (blank lines and `#` comments ignored), read on every reload and watched like the configuration file.

String values in `rdock.yaml` can refer to environment variables and files, and secret fields also to a Vault or OpenBao server. That keeps passwords, tokens and keys out of the configuration file, so the file can be committed to version control and shared.

## What you need

- The secret as a file, for example a Docker or Compose secret, a Kubernetes secret volume or a file readable only by the `rdock` user; or an environment variable of the ReverseDock process.

## The three forms

| Reference | Replaced by |
|---|---|
| `${NAME}` | The environment variable `NAME`. |
| `${env:NAME}` | The same, written explicitly. |
| `${file:/absolute/path}` | The contents of the file, with one trailing newline removed. |

- The path of a `file:` reference must be absolute. The file may hold at most 64 KiB of UTF-8 text.
- A variable that is not set, or a file that cannot be read, is an error that names the configuration path where the reference appears. Nothing falls back to an empty value.
- Text that a reference produced is never expanded again, so a secret that happens to contain `${` cannot pull in other values.
- `$${` writes a literal `${`.
- References work in string values, such as hosts, addresses, header values and tokens.

## The configuration

This route sends an API key to its backend in a request header. The key is read from a file:

```yaml title="rdock.yaml"
listeners:
  web:       { address: ":80" }
  websecure: { address: ":443", tls: {} }

certificates:
  example:
    cert_file: /etc/rdock/certs/example.com.pem
    key_file: /etc/rdock/certs/example.com.key
    key_password: "${file:/run/secrets/example_key_password}"

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app
    middlewares: [backend-key]

middlewares:
  backend-key:
    type: headers
    request:
      set:
        X-Api-Key: "${file:/run/secrets/backend_api_key}"

services:
  app:
    backends: [{ address: "10.0.0.5:3000" }]
```

Quote values that contain a reference. Inside YAML flow collections (`{ … }` and `[ … ]`), an unquoted `}` ends the value early.

With environment variables, for example to choose the backend per environment:

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    backends: [{ address: "${env:APP_BACKEND}" }]
```

## Secret fields

Some fields are secrets. Their reference is not replaced when the configuration is loaded; it stays in the loaded configuration and is resolved only by the component that uses the value, at the moment it uses it:

- `certificates.<name>.key_password`
- `acme.eab.hmac_key`, and the credentials of `acme.dns_providers.<name>`: `api_token`, `token`, `tsig_secret`, `access_key_id`, `secret_access_key`, `session_token`, `client_secret`, `client_certificate`
- `middlewares.<name>.hmac_secret` (`jwt`), and `client_secret`, `session.key` and `session.keys` (`oidc`)
- `services.<name>.sticky.cookie.secret` and `previous_secrets`
- `observability.alerts.webhook.token`, and the `url`, `secret`, `token` and `password` of `observability.alerts.channels.<name>`
- `observability.metering.webhook.secret` and `token`, `observability.metering.otlp.token`
- `secrets.vault.auth.token`

Only these fields accept [`${vault:…}`](#vault-and-openbao).

Objects from providers never make ReverseDock read a secret <Status since="v0.8" />: a secret
field of a Docker or Swarm label, a Kubernetes object or another provider's object cannot hold a
`${…}` reference, and such an object is left out with an error. Objects written through the
[configuration API](/docs/guides/config-api/) may name `${file:…}` and `${env:…}` in secret
fields, since only operators write them, but not `${vault:…}`: Vault is read only for the
configuration file. Elsewhere, provider and API objects are taken as written: a `${…}` there
is never replaced.

When a secret field holds a literal value instead of a reference, `rdock validate` warns:

```text
warning: certificates.example.key_password: a secret is written in the configuration file
    store it as a file and reference it: "${file:/run/secrets/key_password}"
```

For every field, the configuration history and the last-known-good copy under `$RDOCK_DATA_DIR/state` store the document as you wrote it, with references unresolved. When a value from a reference fails to parse, the error message does not quote it.

## Regular-expression replacements are literal

The `replacement` field of the `redirect` and `rewrite` middlewares is never interpolated, because `$1` and `${name}` there refer to capture groups of the regular expression:

```yaml title="rdock.yaml (excerpt)"
middlewares:
  to-www:
    type: redirect
    regex: "^https://example\\.com/(.*)"
    replacement: "https://www.example.com/${1}"
    permanent: true
```

## Secrets with Docker Compose

Compose mounts each secret as a file at `/run/secrets/<secret_name>` in the container ([Docker documentation](https://docs.docker.com/compose/how-tos/use-secrets/), checked 2026-10-27):

```yaml title="compose.yaml"
services:
  rdock:
    image: ghcr.io/docker-hunterpedia/rdock:0.8.0-alpha.1
    secrets: [example_key_password, backend_api_key]
    volumes:
      - ./config:/etc/rdock:ro
secrets:
  example_key_password:
    file: ./secrets/example_key_password.txt
  backend_api_key:
    file: ./secrets/backend_api_key.txt
```

## Changing a secret

ReverseDock reloads on its own when `rdock.yaml`, certificate and key files, `users_file` of `basic_auth` and the page files of `errors` and `maintenance` change. Files read through `${file:…}` are not watched. After changing a secret file or an environment value, reload (a few secret fields are read again without a reload; see [External secret stores](#external-secret-stores)):

```sh
rdock reload
```

A changed environment variable only reaches ReverseDock when the process is restarted, because the environment of a running process cannot be changed from outside. See [Reload the configuration](/docs/guides/reloads/).

## External secret stores

Secret managers such as [External Secrets Operator](https://external-secrets.io/), the [Secrets Store CSI driver](https://secrets-store-csi-driver.sigs.k8s.io/), and Vault or OpenBao with their agents and operators all end in the same two things: **a file** or **a native Kubernetes Secret**. ReverseDock already reads both, so it needs no code for them:

- A file (a Secret mounted as a volume, a CSI volume, a file an agent renders) is read with `${file:/absolute/path}`.
- A `kubernetes.io/tls` Secret is read by the [Kubernetes provider](/docs/guides/kubernetes-gateway-api/) for a Gateway listener. A changed Secret changes the file in ReverseDock's data directory and reloads.

Manifests for each tool are in [`examples/kubernetes/secrets`](https://github.com/Docker-Hunterpedia/ReverseDock/tree/main/examples/kubernetes/secrets), and a Compose example with an OpenBao Agent is in [`examples/secrets`](https://github.com/Docker-Hunterpedia/ReverseDock/tree/main/examples/secrets). **They are not run by the project's CI**; treat them as starting points and check them against the tool's current documentation. The store, its roles and the operator are yours to set up.

ReverseDock can also read a Vault or OpenBao server itself: see [Vault and OpenBao](#vault-and-openbao).

### When a rotated value is picked up

What happens after the store changes the file depends on who reads it:

| Where the reference is | When the new value is used |
|---|---|
| `acme.dns_providers.<name>` credentials (API tokens, TSIG secrets, access keys, client secrets) | At the next call to the DNS provider. They are read again for every call, so no reload is needed. |
| `observability.alerts.channels.<name>` URLs, secrets, tokens and passwords | At the next delivery of an alert. No reload is needed. |
| `certificates.<name>.key_password`, `middlewares.<name>.hmac_secret`, `services.<name>.sticky.cookie.secret` and `previous_secrets` | When the configuration is next applied (loaded). They are read when the configuration is built, so a reload is needed. |
| `acme.eab.hmac_key` | Not re-read on its own; reload after changing it. |
| Every other string value (header values, addresses and so on) | When the configuration is next loaded; a reload is needed. |

A **reload** re-reads every `${file:…}` and `${env:…}` reference. It happens when you run `rdock reload`, on `SIGHUP`, and when a watched file changes: `rdock.yaml` and its includes, certificate and key files, the `users_file` of `basic_auth`, and the page files of `errors` and `maintenance`. Changes are debounced for 250 ms, and ReverseDock reloads only when the content of a watched file really changed. **A file that is only read through `${file:…}` is not watched**, so changing it alone triggers nothing: a value that is read at load keeps its old value until a reload. A reload that cannot read a file is rejected and the running configuration stays in place.

Two delays come before ReverseDock sees a new file on Kubernetes:

- The store tool must write the new value. External Secrets Operator reads the store every `refreshInterval` under its default refresh policy `Periodic`, the CSI driver only with its rotation feature (alpha, off by default), and a Vault Agent every `static_secret_render_interval` for non-leased secrets (default 5 minutes).
- Kubernetes updates the files of a Secret volume eventually: the delay "can be as long as the kubelet sync period + cache propagation delay", and a container that mounts a Secret as a `subPath` "does not receive automated Secret updates" ([Kubernetes, Secrets](https://kubernetes.io/docs/concepts/configuration/secret/#using-secrets-as-files-from-a-pod), checked 2026-11-11). Mount the volume as a whole, and do not use an environment variable for a value that rotates: an environment is fixed when the container starts.

Sources for the tools, checked 2026-11-11: [ExternalSecret API](https://external-secrets.io/latest/api/externalsecret/), [Secret auto rotation](https://secrets-store-csi-driver.sigs.k8s.io/topics/secret-auto-rotation), [Vault Agent templates](https://developer.hashicorp.com/vault/docs/agent-and-proxy/agent/template). Vault is licensed under the Business Source License; OpenBao, its fork, under MPL-2.0 ([research note](https://github.com/Docker-Hunterpedia/ReverseDock/blob/main/docs/research/v0.8-cache-extensibility.md), section 5).

## Vault and OpenBao

<Status since="v0.8" /> A secret field can read a field of a KV version 2 secret from a [HashiCorp Vault](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2) or [OpenBao](https://openbao.org/docs/api/secret/kv/kv-v2/) server, without an agent or operator in between:

```yaml title="rdock.yaml (excerpt)"
secrets:
  vault:
    address: https://vault.internal:8200
    ca_file: /etc/rdock/vault-ca.pem        # optional: the CA that signed the server's certificate
    auth:
      token: "${file:/run/secrets/vault-token}"

middlewares:
  auth:
    type: jwt
    hmac_secret: "${vault:secret/rdock/jwt#key}"
    algorithms: [HS256]
    issuer: https://idp.example.com
    audiences: [api]
```

`${vault:<mount>/<path>#<field>}` names the KV version 2 mount (`secret`), the secret's path below it (`rdock/jwt`) and a field of its data (`key`). ReverseDock reads it with `GET /v1/<mount>/data/<path>`, the latest version. A field that holds a number or a boolean is used as text; an object, an array or `null` is an error.

| Setting | Default | Meaning |
|---|---|---|
| `address` | (required) | The server's root. `https://`, or `http://` only to a loopback address (a dev server, a local agent). |
| `ca_file` | the system's roots | PEM certificates that sign the server's certificate. |
| `namespace` | none | Sent as `X-Vault-Namespace` (Vault Enterprise, OpenBao namespaces). |
| `auth.token` | | A `${file:…}` or `${env:…}` reference to a token, read again for every request, so a token file an agent renews is picked up. A literal token is refused. |
| `auth.kubernetes` | | `{ role, mount: kubernetes, token_file: /var/run/secrets/kubernetes.io/serviceaccount/token }`: logs in with the pod's service-account token (`POST /v1/auth/<mount>/login`). The token Vault returns is replaced by logging in again after two thirds of its lease, and after a `403`. |
| `refresh` | `5m` | How often every reference is read again; at least `1s`, and `rdock validate` warns below `10s`. |
| `timeout` | `5s` | Time for one request; shorter than `refresh`. |
| `allow_private_targets` | `true` | Allow a server on a private address. Vault usually runs inside the network. |
| `insecure_http` | `false` | **Unsafe.** Allow `http://` to a server that is not on loopback: the token and every secret cross the network unencrypted. `rdock validate` warns. |

### When values are read

- **At every load** (start, reload, a change of a watched file) every reference is read before the configuration is built. A reference that has never been read and cannot be read now rejects the configuration, like a missing `${file:…}`: at start, ReverseDock does not start; on a reload, the running configuration stays. `rdock validate` reads Vault the same way, so it needs the server and a token.
- **Every `refresh`**, the references of the running configuration are read again. A changed value reloads the configuration, so fields that are read when the configuration is built (a JWT key, a sticky-cookie secret) get the new value; fields that are read at use (alert and metering tokens) use it at once.
- **A failed read keeps the last value.** ReverseDock marks Vault degraded: `rdock status` and `GET /api/v1/status` show `secrets.vault.state: degraded` with the reason, the log has a warning, and `rdock_vault_refresh_failures_total` counts it. The next successful read clears it.

### Where values never appear

Values are kept in the process's memory only. The configuration as served by `GET /api/v1/config`, its history, the last-known-good copy and provider snapshots in the data directory keep the `${vault:…}` reference; errors, diagnostics and log lines name the reference and Vault's status code, never the value or the token. A test checks every file in the data directory, the admin answers and the log after a rotation.

`${vault:…}` is accepted **only in [secret fields](#secret-fields)**. In any other field (a header value, an address) the value would become part of the loaded configuration, which the admin API serves; `rdock validate` refuses it. To send a Vault value as a header, let a Vault Agent render it to a file and use `${file:…}`. References are read only from the configuration file and its includes, at a load and at every refresh; objects from providers (Docker labels, Kubernetes) and the API cannot add any.

### What is supported

- KV version 2 only; token and Kubernetes login. AppRole, other auth methods, dynamic secrets (database credentials, PKI) and KV version 1 are not.
- Tested in CI against **OpenBao 2.7.2** in dev mode with token login; the Kubernetes login is tested against a fake server. Vault uses the same API ([KV v2](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2), [Kubernetes auth](https://developer.hashicorp.com/vault/api-docs/auth/kubernetes), checked 2026-11-11) and is not tested by the project.
- Vault is licensed under the Business Source License 1.1 since its releases after 2023-08-10; OpenBao, the Linux Foundation fork of its last MPL release, under MPL-2.0 ([HashiCorp announcement](https://www.hashicorp.com/en/blog/hashicorp-adopts-business-source-license), checked 2026-11-11; [OpenBao](https://github.com/openbao/openbao), checked 2026-11-11; the OpenBao API pages, checked 2026-11-12).

A Vault policy for ReverseDock needs only `read` on the secrets it references:

```hcl title="rdock-policy.hcl"
path "secret/data/rdock/*" {
  capabilities = ["read"]
}
```

## Validating in CI

`rdock validate` resolves references, so it needs the same variables and files as `rdock run`, and the Vault server when the configuration has `${vault:…}` references. In CI, provide placeholder values:

```sh
APP_BACKEND=app:3000 rdock validate --strict rdock.yaml
```

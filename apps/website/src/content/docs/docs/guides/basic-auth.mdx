The `basic_auth` middleware <Status since="v0.1" /> asks for a user name and password before a
request reaches the backend. Use it for small internal tools. For single sign-on, use
[forward authentication](/docs/guides/forward-auth/) instead.

## Before you start

- Serve the route over HTTPS. Basic authentication sends the password with every request,
  encoded but not encrypted. See [TLS certificates](/docs/guides/tls-certificates/).
- Have the `rdock` binary at hand to create password hashes. Plain-text passwords are never
  accepted.

## Create a password hash

`rdock hash` reads the password from the first line of standard input, so it does not end up in
your shell history or the process list, and prints an argon2id hash. With `--user` it prints a
complete `user:hash` entry.

```sh
rdock hash --user alice
```

Type the password and press Enter. To hide it while you type, pipe it in, for example from a
password manager's command-line tool. The output looks like this:

```text
alice:$argon2id$v=19$m=19456,t=2,p=1$Mk1XX0F08SxdcsXb41BuJw$Opsu4ymnvQTr81nzlePT6BVjjA0Ab+1l2TkBwqkJErQ
```

In Docker, run the same command in the image:
`docker run --rm -i ghcr.io/docker-hunterpedia/rdock:1.0.0-rc.1 hash --user alice`.

## Configure the middleware

Keep the entries in a users file, one `user:hash` per line. Empty lines and lines starting with
`#` are ignored.

```text title="/etc/rdock/admin.htpasswd"
# rdock hash --user alice
alice:$argon2id$v=19$m=19456,t=2,p=1$Mk1XX0F08SxdcsXb41BuJw$Opsu4ymnvQTr81nzlePT6BVjjA0Ab+1l2TkBwqkJErQ
```

```yaml title="rdock.yaml"
listeners:
  web: { address: ":80" }
  websecure: { address: ":443", tls: {} }

certificates:
  example:
    cert_file: /etc/rdock/certs/example.pem
    key_file: /etc/rdock/certs/example.key

routes:
  admin:
    match: "Host(`admin.example.com`)"
    service: admin
    middlewares: [office-login]

services:
  admin:
    backends: [{ address: "admin:8080" }]

middlewares:
  office-login:
    type: basic_auth
    users_file: /etc/rdock/admin.htpasswd
    realm: Admin
    remove_header: true
```

| Setting | Default | Meaning |
|---|---|---|
| `users` | none | `user:hash` entries written in the configuration. |
| `users_file` | none | File with one `user:hash` entry per line. |
| `realm` | `rdock` | Name browsers show in the login prompt. |
| `remove_header` | `false` | Remove the `Authorization` header before forwarding, so the backend never sees the password. |

Set `users`, `users_file` or both. When a user appears in both, the entry in `users` wins.
ReverseDock watches the users file and reloads when it changes, so adding a user needs no
restart.

Inline entries look like this:

```yaml title="rdock.yaml (excerpt)"
middlewares:
  office-login:
    type: basic_auth
    users:
      - "alice:$argon2id$v=19$m=19456,t=2,p=1$Mk1XX0F08SxdcsXb41BuJw$Opsu4ymnvQTr81nzlePT6BVjjA0Ab+1l2TkBwqkJErQ"
```

## Supported hashes

| Format | Prefix | Status |
|---|---|---|
| argon2id | `$argon2id$` | Recommended. `rdock hash` creates these. |
| bcrypt | `$2a$`, `$2b$`, `$2x$`, `$2y$` | Accepted. `htpasswd -B` creates these. |
| Apache MD5 | `$apr1$` | Accepted with a warning. |
| MD5-crypt | `$1$` | Accepted with a warning. |
| SHA-1 | `{SHA}` | Accepted with a warning. |

The weak formats are accepted so that files from `htpasswd` and Traefik keep working.
`rdock validate` warns about each inline entry that uses one, with the hint to create an argon2id
entry with `rdock hash --user <name>`. Under `--strict` that warning is an error. A plain-text
password in `users` is an error; in a users file, an entry in an unknown format never matches.

**Cost ceilings.** An argon2id or bcrypt hash carries its own cost, and every request with a
wrong password does that work, so a hash asking for too much would let anyone exhaust the
proxy's memory or threads. Refused, in `users` at validation and in a users file when it is
loaded or reloaded (the reload is refused and the running configuration stays): argon2id with
more than `m=262144` (256 MiB), `t=10` or `p=8`, and bcrypt with a cost above `14`. These are
several times the minimums of OWASP's
[Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
(read 2026-11-13: argon2id at least `m=19456, t=2, p=1`; bcrypt at least `10`) and the same as
the bounds of `admin.passwords.argon2`.

## How requests are checked

- A request without valid credentials gets **401** with
  `WWW-Authenticate: Basic realm="Admin", charset="UTF-8"`, and does not reach the backend.
- argon2id and bcrypt are slow on purpose. ReverseDock checks them on a separate thread pool and
  remembers a successful check for five minutes, so a browser that sends the credentials with
  every request does not pay the cost each time.
- At most four checks run at once across every `basic_auth` middleware (fewer on a machine
  with fewer CPUs). A request that finds them all busy waits up to one second, then gets
  **503** (problem type [`overloaded`](/docs/reference/problems/#overloaded)) with
  `Retry-After: 1`. Failed checks are not remembered, so a flood of wrong passwords is held to
  that pace instead of piling up threads.
- One client (an IPv4 address, or an IPv6 /64) has at most two checks running at a time, so
  a few people behind one NAT can log in at the same moment; its other requests wait for a
  turn up to one second, then get **429** with `Retry-After: 1`. A single client flooding
  wrong passwords therefore cannot take every check from other users, and guesses at most
  two passwords per check's duration. A **429** for waiting is not a failed login: it does
  not count towards an [`abuse`](/docs/guides/abuse-protection/) ban `on: auth_failure`.
- A user name that does not exist is checked against a configured hash and refused, so the
  answer takes as long as a wrong password for a real user and does not tell which names
  exist. Put a [`rate_limit`](/docs/guides/rate-limiting/) or an
  [`abuse`](/docs/guides/abuse-protection/) middleware before `basic_auth` to slow guessing
  further.
- The authenticated user name appears in the `user` field of the
  [access log](/docs/guides/logs-and-metrics/). The `Authorization` header itself is redacted
  from the log by default.

## Check that it worked

```sh
rdock validate /etc/rdock/rdock.yaml
curl -s -o /dev/null -w '%{http_code}\n' https://admin.example.com/
curl -s -o /dev/null -w '%{http_code}\n' -u alice https://admin.example.com/
```

The first `curl` prints `401`. The second asks for alice's password and prints the backend's
status, for example `200`.

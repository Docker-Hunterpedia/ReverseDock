Besides the file and Docker, the admin API is a provider of its own <Status since="v0.5" />: routes, services and middlewares written through it are merged into the configuration as `name@api`, validated and applied exactly like a file reload, stored in `$RDOCK_DATA_DIR/state/`, and restored after a restart. Objects from the file or Docker stay read-only through the API.

The examples run on the server, over the admin socket. From elsewhere, use `http://127.0.0.1:2080` with `-H "Authorization: Bearer $TOKEN"` and a token with the `operator` role (see [Security model](/docs/concepts/security-model/#admin-api)).

```sh
api() { curl -s --unix-socket /var/lib/rdock/admin.sock -H 'Host: localhost' "$@"; }
```

## Read

```sh
api http://localhost/api/v1/config          # everything in use, with the owner of each object
api -i http://localhost/api/v1/config/api   # only the API's objects; note the ETag header
```

Secret values written in place are shown as `***`; `${file:…}` and `${env:…}` references are shown as written.

## Change, always with If-Match

Every change names the version it was based on, so two people cannot overwrite each other: without `If-Match` the answer is `428`, with an older version `412` and the current `ETag`.

```sh
api -X PUT http://localhost/api/v1/config/api \
  -H 'Content-Type: application/json' -H 'If-Match: "g7-3f2a9c1b0e4d5a6f"' \
  -d '{"routes":{"shop":{"match":"Host(`shop.example.com`)","service":"shop"}},
       "services":{"shop":{"backends":[{"address":"10.0.0.5:8080"}]}}}'
```

`PATCH` changes part of it: `Content-Type: application/merge-patch+json` (RFC 7396, `null` removes) or `application/json-patch+json` (RFC 6902 operations). A configuration that would not be applied is refused with `422` and the diagnostics, and nothing changes: unlike Docker objects, a broken API object is never just left out.

## One object at a time

`GET /api/v1/routes`, `/services` and `/middlewares` list every object with its `owner`; `GET /api/v1/routes/{name}` shows one. `PUT /api/v1/routes/shop` with the route as the body, or `DELETE`, changes one API object, with the same `If-Match` as above; objects owned by the file or Docker answer `403` with the provider to change them in.

## Backends, certificates, providers and listeners

- `GET /api/v1/backends` shows every service's backends: address, state (`up`, `down`, `trial`), requests in flight and whether they are drained. `POST /api/v1/backends/drain` with `{"service":"shop","backend":"10.0.0.5:8080"}` stops new requests to it while open ones finish; `/undrain` puts it back. A drained backend is out even when the service fails open; a restart forgets drains.
- `GET /api/v1/certificates` lists configured and automatic certificates; `POST /api/v1/certificates/shop.example.com/renew` renews the automatic certificate covering that name now (still within the back-off after failures).
- `GET /api/v1/providers` shows each provider's state with the diagnostics about its objects; `GET /api/v1/listeners` lists listeners, which only a restart changes ([ADR-0008](https://github.com/Docker-Hunterpedia/ReverseDock/blob/main/docs/decisions/0008-listener-changes-via-self-upgrade.md)).

## The same from the command line

On the server the CLI uses the admin socket; elsewhere it needs `--admin` and `RDOCK_ADMIN_TOKEN`.

```sh
rdock config history                 # applied configurations with their id
rdock config diff candidate.yaml     # what a document would change, nothing applied
rdock config rollback 1793479942801
rdock users list | add NAME --role operator | set NAME --disable | passwd NAME | reset-mfa NAME | remove NAME
rdock tokens list | create NAME --role metrics --days 365 --allow 10.0.0.0/8 | revoke ID
rdock backends list | drain SERVICE ADDRESS | undrain SERVICE ADDRESS
rdock audit list --limit 50
```

Passwords for `users add` and `users passwd` are read from standard input.

## Try first

```sh
api -X POST http://localhost/api/v1/config/validate -H 'Content-Type: application/json' -d @candidate.json
```

The answer has `valid`, the `diagnostics` and a unified `diff` against the current API objects. Nothing is applied.

## History and rollback

`GET /api/v1/config/history` lists applied configurations, newest first, each with an `id`. `POST /api/v1/config/rollback` with `{"id": …}` and `If-Match` restores the API objects of that entry; people confirm their password first (`POST /api/v1/auth/reauth`). The file part is never rolled back by the API: the file is its own source of truth.

## Export and import

`GET /api/v1/config/export` (admins, after a password check) returns `{"version":1,"api":{…}}`; `POST /api/v1/config/import` with that document and `If-Match` replaces the API objects on another instance. Write secrets as references: a document with masked `***` values is refused.

## GitOps

```yaml title="rdock.yaml (excerpt)"
admin:
  api_writes: false
```

Every configuration write through the API and the dashboard is then refused with `403`; reading, history and dry runs keep working. Every write and rollback is in the [audit log](/docs/concepts/security-model/#admin-api) with the version hashes before and after.

The `oidc` middleware <Status since="v0.8" /> logs browser users in with an OpenID Connect
provider before a request reaches the backend. The backend gets the user's identity in headers
and never handles the login itself; [rate limits, quotas](/docs/guides/quotas/), the cache key
and the access log see the user as the request's [consumer](/docs/guides/api-keys/).

## How the login works

1. A page request without a session is redirected to the provider's login, with the
   authorization code flow (OpenID Connect Core §3.1), **PKCE S256 always on**, a random
   `state` and a random `nonce`.
2. The provider sends the browser back to the callback path (`/_rdock/oidc/callback` by
   default). rdock checks the `state` against an encrypted, 10-minute state cookie, exchanges
   the code for tokens at the token endpoint and verifies the ID token: signature with the
   provider's published keys, `iss`, `aud` (and `azp` when there are several audiences), `exp`,
   `iat`, `nonce` and `at_hash`.
3. The identity is kept in an **encrypted, authenticated session cookie** (ChaCha20-Poly1305,
   keys derived with HKDF-SHA256). There is no session store, so any number of replicas accept
   the session as long as they share the key.
4. Later requests carry the cookie. rdock removes its own cookies before forwarding, sets the
   configured claim headers (removing copies the client sent) and passes the request on.

Requests that are **not page navigations get `401`** rather than a redirect, so an API client
or a `fetch()` call never receives the provider's login page: only `GET`/`HEAD` requests whose
`Sec-Fetch-Mode` is `navigate` (or, from clients that do not send it, whose `Accept` names
`text/html`) are redirected.

## A login in front of an app

```yaml title="rdock.yaml"
listeners:
  websecure: { address: ":443", tls: {} }

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app
    middlewares: [login]

middlewares:
  login:
    type: oidc
    issuer: https://auth.example.com/realms/main
    client_id: app
    client_secret: "${file:/run/secrets/oidc_client_secret}"
    claims_to_headers:
      email: X-Auth-Email
      groups: X-Auth-Groups
    session:
      key: "${file:/run/secrets/oidc_session_key}"

services:
  app:
    backends: [{ address: "app:8080" }]
```

Register the client at the provider with:

- **Redirect URI** `https://app.example.com/_rdock/oidc/callback` (the route's host and
  `redirect_path`).
- **Post-logout redirect URI** `https://app.example.com/` (the host and `post_logout_path`),
  for providers that support logout.

Create the session key once and give every replica the same file:

```sh
openssl rand -base64 48 > /run/secrets/oidc_session_key
```

The redirect URI is built only from the hosts the route's `Host` rule names, never from an
unchecked `Host` header; `rdock validate` refuses an `oidc` route whose rule has no `Host`
matcher unless the middleware sets `redirect_url` (the full URI, for example when the browser
sees another port).

## Settings

| Setting | Default | What it does |
|---|---|---|
| `issuer` | required | The provider's issuer. Its configuration is read from `<issuer>/.well-known/openid-configuration`. `https://` only (`http://` to a loopback address for development). |
| `client_id` | required | The client registered at the provider. |
| `client_secret` | none | A `${file:…}`, `${env:…}` or `${vault:…}` reference. Without it rdock is a public client and relies on PKCE alone. A secret written in the file is refused. |
| `token_endpoint_auth` | `client_secret_basic` | Or `client_secret_post` (the secret in the form body). |
| `scopes` | `openid email profile` | Must contain `openid`. Add `offline_access` where the provider issues refresh tokens only for it (Dex). |
| `redirect_path` | `/_rdock/oidc/callback` | The callback. The route must match it. |
| `redirect_url` | none | The full redirect URI, when it cannot be built from the request. |
| `logout_path` | `/_rdock/oidc/logout` | Ends the session (`GET`, `HEAD` or `POST`; other methods get `405`). Only a request from the site itself counts: `Sec-Fetch-Site: same-origin` or `none` (a typed URL, a bookmark), or, from browsers that do not send that header, an `Origin` or `Referer` of the route's own origin; anything else, `same-site` included, gets `403`, so another page cannot log users out with an image or a form. A plain link or a form on your site works. When the provider advertises an `end_session_endpoint`, the browser goes there next (RP-initiated logout) with `client_id` and `post_logout_redirect_uri`. |
| `post_logout_path` | `/` | Where the browser lands after logout. |
| `claims_to_headers` | none | `claim: Header`. Arrays are joined with `,`. Client-sent copies are always removed. |
| `consumer_claim` | `email` | The claim that becomes the consumer; `sub` when the token lacks it. An `email` counts only when the provider verified it (`email_verified: true`, or absent with `allowed.unverified_emails`); otherwise `sub` is the consumer. |
| `groups_claim` | `groups` | The claim with the user's groups (a string or an array). |
| `map_to_consumers` | `false` | Treat the consumer name as a [`consumers.<name>`](/docs/guides/api-keys/) entry: its groups are added and the user shares its quota, rate-limit and cache identity with its API keys. Turn it on only when users cannot choose the claim. |
| `allowed` | everyone | `emails`, `domains`, `groups`: a user matching **any one** entry may log in; others get `403`. E-mail entries count only with `email_verified: true` unless `unverified_emails: true`, which also lets an unverified `email` name the consumer: **unsafe** with a provider that lets users enter an address they do not own. |
| `unauthenticated` | `auto` | `auto` redirects page navigations and answers `401` to the rest; `redirect` redirects every `GET`/`HEAD`; `deny` always answers `401`. |
| `forward_access_token` | `false` | Pass the access token in `X-Forwarded-Access-Token`. It is then kept in the cookie, which grows. |
| `allow_private_targets` | `false` | Let the provider's endpoints resolve to private, loopback or link-local addresses (an in-cluster Keycloak or Dex). The address actually connected to is checked. |
| `algorithms` | RS, PS, ES, EdDSA | ID-token algorithms accepted, intersected with what the provider advertises. `none` does not exist; HS256/384/512 (keyed with the client secret) only when listed. |
| `leeway` | `60s` | Clock skew allowed for `exp` and `iat`. |

The `session` object:

| Setting | Default | What it does |
|---|---|---|
| `key` | required | At least 32 bytes, as a reference. Or `keys` (rotation) or `key_file`. |
| `keys` | none | `[current, previous…]`: the first encrypts, all decrypt. |
| `key_file` | none | A file holding the key, read on every reload. |
| `cookie_name` | `rdock_oidc` | rdock adds `__Host-` (or `__Secure-` with a `domain`). |
| `ttl` | `8h` | Longest session from login. |
| `refresh` | `true` | Renew the session with the refresh token, when the provider issues one, 30 s before the tokens expire. A failed refresh means a new login. |
| `same_site` | `lax` | Or `none` (needs `secure`). `strict` is refused: the browser would not send it on the way back from the provider. |
| `secure` | `true` | `false` only with `allow_insecure_cookies: true` on plain-HTTP routes, for local development. |
| `domain` | host-only | Share the session with subdomains. |

### How long a session lasts

A session ends at `login + ttl`. With a refresh token it is renewed whenever the ID token
expires (or the access token, with `forward_access_token`), and it also ends when the
provider's `refresh_expires_in` runs out. **Without a refresh token the session ends when the
ID token expires**; the next page navigation logs in again, usually without a prompt because
the provider still has its own session. Sessions are stateless, so one cannot be revoked
before it ends: keep `ttl` short where that matters. Back-channel logout and server-side
sessions need shared state and are planned with it.

### What the cookie holds

Only what later requests need: `sub`, the consumer, the groups, the verified e-mail address,
the claims listed in `claims_to_headers`, the times, the refresh token (with `refresh`) and the
access token (with `forward_access_token`). Larger values are split over `<name>_0`,
`<name>_1`… (at most four cookies of 3800 bytes); a session that does not fit fails the login
with a log line. Each login in progress has its own state cookie
(`__Host-rdock_oidc_state_<id>`), so logins in several tabs work; at most four are kept.

## Providers

The issuers below were checked against each provider's published configuration or
documentation on 2026-11-12.

```yaml title="rdock.yaml (excerpt: Keycloak)"
middlewares:
  login:
    type: oidc
    # https://<host>/realms/<realm> (Keycloak: "Securing applications", OIDC endpoints)
    issuer: https://keycloak.example.com/realms/main
    client_id: app
    client_secret: "${file:/run/secrets/oidc_client_secret}"
    session: { key: "${file:/run/secrets/oidc_session_key}" }
```

[Keycloak documentation](https://www.keycloak.org/securing-apps/oidc-layers) gives the
discovery endpoint as `/realms/{realm-name}/.well-known/openid-configuration`.

```yaml title="rdock.yaml (excerpt: Microsoft Entra ID)"
middlewares:
  login:
    type: oidc
    # https://login.microsoftonline.com/<tenant-id>/v2.0
    issuer: https://login.microsoftonline.com/00000000-0000-0000-0000-000000000000/v2.0
    client_id: 11111111-1111-1111-1111-111111111111
    client_secret: "${file:/run/secrets/oidc_client_secret}"
    consumer_claim: preferred_username
    session: { key: "${file:/run/secrets/oidc_session_key}" }
```

Entra's issuer is `https://login.microsoftonline.com/{tenant}/v2.0`
([Microsoft identity platform: OpenID Connect](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc));
use your tenant ID, not `common`, so the issuer in its tokens matches. Its configuration
advertises an `end_session_endpoint` and RS256. With a provider whose ID tokens carry no
`email_verified`, `allowed.emails` and `allowed.domains` match only with
`unverified_emails: true`; prefer `allowed.groups` there.

```yaml title="rdock.yaml (excerpt: Google)"
middlewares:
  login:
    type: oidc
    issuer: https://accounts.google.com
    client_id: 1234567890-abc.apps.googleusercontent.com
    client_secret: "${file:/run/secrets/oidc_client_secret}"
    allowed: { domains: [example.com] }
    session: { key: "${file:/run/secrets/oidc_session_key}" }
```

Google's issuer is `https://accounts.google.com`
([Google: OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect));
its configuration advertises RS256 and PKCE S256 and no `end_session_endpoint`, so
`logout_path` ends only the rdock session.

```yaml title="rdock.yaml (excerpt: Dex)"
middlewares:
  login:
    type: oidc
    # The `issuer` of Dex's own configuration.
    issuer: https://dex.example.com/dex
    client_id: app
    client_secret: "${file:/run/secrets/oidc_client_secret}"
    scopes: [openid, email, profile, offline_access]
    session: { key: "${file:/run/secrets/oidc_session_key}" }
```

[Dex](https://dexidp.io/docs/configuration/custom-scopes-claims-clients/) includes a refresh
token for the `offline_access` scope. ReverseDock's
CI logs in against Dex v2.46.1 with a static client and a static password user
([local connector](https://dexidp.io/docs/connectors/local/)) on every change.

## Consumers, limits and the cache

The consumer is set from `consumer_claim`, so a route can count per user:

```yaml title="rdock.yaml (excerpt)"
routes:
  app:
    match: "Host(`app.example.com`)"
    service: app
    middlewares: [login, per-user]

middlewares:
  per-user: { type: rate_limit, key: consumer, average: 100, period: 1m }
```

Put `oidc` **before** the `rate_limit` or `quota` that counts per consumer; `rdock validate`
refuses the other order. A `cache` on such a route needs `key.consumer: true` (one copy per
user) or `shared_across_users: true`.

An OIDC user is an identity of its own, keyed on the issuer and the consumer name: a user of
another provider, or an API-key consumer, with the same name never shares its quota, its rate
limit or its cached copies, and gets none of the groups of a `consumers.<name>` entry with the
same name. The access log and metering show the bare name. To make the provider's users *be*
configured consumers (their groups and per-group limits), set `map_to_consumers: true`, and
pick a `consumer_claim` the provider controls. An e-mail address names the consumer only when
the provider says it verified it; an unverified one falls back to `sub`, so nobody becomes
`victim@example.com` by typing that address into a provider's sign-up form.

## Several replicas and Kubernetes

Sessions and logins in progress live entirely in the browser's cookies, so requests can land on
any replica, as long as **every replica has the same session key** (mount the same Secret as a
file). A login that starts on one replica can finish on another. Key rotation: add the new key
first in `keys` on every replica, then drop the old one after `ttl`.

If the provider cannot be reached, existing sessions keep working (they need no provider);
new logins answer `503` with the problem type
[`identity-provider-unavailable`](/docs/reference/problems/#identity-provider-unavailable), and
refreshes fail until it is back. The provider's configuration and keys are fetched in the
background, after the first request, and refreshed every 10 minutes (and at once when a token
names an unknown key), so a reload never waits for the provider.

## What is logged and counted

- The access log's `consumer` and `user` fields name the user.
- [Metrics](/docs/reference/metrics/): `rdock_oidc_logins_total{middleware,result}`,
  `rdock_oidc_refreshes_total{middleware,result}`,
  `rdock_oidc_provider_errors_total{middleware,operation}`.
- A failed login answers `401` [`login-failed`](/docs/reference/problems/#login-failed) and logs
  the reason (wrong state, expired login, the provider's `error` code, which check of the ID
  token failed). The provider's `error_description` is never shown to the user.

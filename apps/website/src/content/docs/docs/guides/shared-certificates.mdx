Several instances that serve the same names must not each order the same certificate: Let's
Encrypt allows 5 certificates per exact set of names every 7 days, for all accounts together
([rate limits](https://letsencrypt.org/docs/rate-limits/), updated 2026-08-05). ReverseDock
<Status planned="v0.9" /> shares certificates through a **cluster store**, and the instances
coordinate so each certificate is ordered once.

## The store

- **The control plane** (`cluster.control`, the default store then;
  [run a cluster](/docs/guides/cluster/)). One process writes the store, under one lock and one
  clock, so the lease rules below are enforced.
- **A shared directory** that every instance mounts (NFS, EFS, a shared volume), without a control
  plane:

```yaml title="rdock.yaml (excerpt)"
cluster:
  instance: edge-1
  store:
    type: directory
    path: /mnt/rdock-shared
```

A single instance without `cluster` keeps its certificates in `$RDOCK_DATA_DIR/acme` (or
`acme.storage`) as before.

## How a certificate is ordered once

For each certificate, the instance that finds it due:

1. takes a **lease** on its name (`cluster.store.lease_ttl`, 60 s, renewed every third of it).
   Another instance that wants the same certificate waits;
2. **looks again** in the store: if another instance just stored a current certificate, it uses
   that one;
3. creates the order and **journals** it (the order's URL and the new key) before answering any
   challenge. If it dies, the next instance to take the lease finishes the same order instead of
   creating a new one;
4. stores the certificate, and the others pick it up within 10 seconds.

**How a certificate is stored.** The new chain and key are written to `certs/<name>/next/`
first; then `meta.json`, which names the chain's SHA-256, is replaced with compare-and-swap
against the version read under the lease (whatever it describes: other names, a chain that is no
longer there); only then are `cert.pem` and `key.pem` replaced and `next/` removed. An instance
loads the pair that matches `meta.json`, from either place, and only when the key matches the
chain. So a store that stops at any point (a crash, a lost lease, a full disk) leaves the previous
certificate or the new one loading, never a mismatched pair, and the next attempt replaces
whatever is left. A single instance stores its certificates the same way in its own directory,
and a directory written by 0.8 loads unchanged. The directory is named after the first name of
the certificate, so two requests with the same first name (a route with
`tls.domains: [a.example.com, www.a.example.com]` and another with ``Host(`a.example.com`)``) are
joined into one certificate with all their names.

The ACME account and the renewal time are shared too: every instance renews at the same moment
inside the CA's renewal window, and one renewal per certificate is made. The certificate's key
and the account key are stored with mode 0600 and never appear in logs or the admin API, but
every member of the store can read them: see
[the trust model](/docs/guides/cluster/#who-can-read-what-the-trust-model).

## HTTP-01 and TLS-ALPN-01: the barrier

A CA may ask any instance for the answer to a challenge, so the answer must be on all of them
first. The ordering instance writes its HTTP-01 and TLS-ALPN-01 answers to the store; every
instance copies them into memory (the store is never read while serving a request) and confirms.
The ordering instance waits until every **live** instance (one whose heartbeat changed in the
last 20 seconds, by the ordering instance's own monotonic clock, so wall-clock differences do not
matter) has confirmed, or `cluster.store.barrier_timeout` (10 s), before the CA is told to
validate. Each answer has its own id per order, so an instance never keeps an older order's
TLS-ALPN-01 answer or confirms one it does not hold. An instance that starts copies the answers
in the store before its listeners accept (waiting at most 5 seconds for the store). Answers that
an instance which died left behind are withdrawn by the next holder of that name, and removed by
any member after an hour.

An instance that is cut off from the store but still receives traffic from the internet cannot
answer, and validation through it fails. **Use DNS-01 in clusters**: it works from any instance
and needs none of this ([DNS challenge](/docs/guides/dns-challenge/)). `rdock validate` warns
when a cluster member answers HTTP-01 or TLS-ALPN-01.

## The limits of a shared directory

A shared directory has no common clock and no atomic compare-and-swap:

- a lease is a file whose expiry the holder writes by its clock and the others judge by theirs.
  Instances whose clocks disagree by more than the lease's margin can both believe they hold it:
  keep clocks synchronised (NTP);
- a holder that is paused (a stopped VM, a long garbage pause on a network filesystem) past its
  lease can still write once after another took over;
- it cannot tell instances apart: give each its own `cluster.instance` (or none, for a generated
  one). Two processes with the same name never hold a lease together (a lease names the process
  as well), but they share a heartbeat, so one logs "another process writes the heartbeat of this
  instance name".

This is the best-effort mode, which `rdock validate` points out. The control plane's store has
neither limit.

## Kubernetes

With `providers.kubernetes`, `acme` used to need `allow_acme` and one replica. Members of a
cluster whose store is the control plane share certificates and need neither. cert-manager stays
the usual way in Kubernetes; the Helm chart does not set up a cluster yet.

A service is the pool of backends that answers a route. This guide covers how to address backends, which protocol ReverseDock speaks to them, and how requests are spread across them.

## What you need

- A route, as in [Route a domain to an app](/docs/guides/route-a-domain/).

## The configuration

```yaml title="rdock.yaml"
listeners:
  web:       { address: ":80" }
  websecure: { address: ":443", tls: {} }

certificates:
  example:
    cert_file: /etc/rdock/certs/example.com.pem
    key_file: /etc/rdock/certs/example.com.key

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app
  docs:
    match: "Host(`docs.example.com`)"
    service: docs
  billing:
    match: "Host(`billing.example.com`)"
    service: billing

services:
  app:
    backends:
      - { address: "10.0.0.5:3000", weight: 3 }
      - { address: "10.0.0.6:3000" }
      - { address: "app-3.internal:3000" }
  docs:
    backends: [{ address: "unix:///run/docs/http.sock" }]
  billing:
    scheme: https
    tls:
      server_name: billing.internal.example.com
      ca_file: /etc/rdock/certs/internal-ca.pem
    backends: [{ address: "10.0.1.20:8443" }]
```

## Backend addresses

| Form | Example | Notes |
|---|---|---|
| IPv4 and port | `10.0.0.5:3000` | |
| IPv6 and port | `[2001:db8::5]:3000` | Brackets are required. |
| DNS name and port | `app-3.internal:3000`, `app:3000` | Container names on a Docker network work too. |
| Unix socket | `unix:///run/docs/http.sock` | The path must be absolute. |

**DNS names** are resolved when a configuration is applied and again every 10 seconds, so a container that restarts with a new IP address is picked up without a reload. A lookup that fails or takes longer than 2 seconds keeps the previous addresses and logs `cannot resolve backend` or `backend lookup timed out`. When a name resolves to several addresses, each address is a backend with the weight of the entry. A name that has never resolved leaves the service without backends, and its requests get `503`.

**Unix sockets** need ReverseDock to have permission to open the socket file. In a container, mount the socket's directory into the ReverseDock container.

## Protocols

`scheme` sets what ReverseDock speaks to the backends of a service:

| `scheme` | Protocol | Use it for |
|---|---|---|
| `http` (default) | HTTP/1.1 in clear text | Most applications. |
| `https` | TLS; HTTP/2 when the backend offers it through ALPN, otherwise HTTP/1.1 | Backends that only accept TLS, or traffic that crosses an untrusted network. |
| `h2c` | HTTP/2 in clear text | gRPC servers without TLS. See [WebSockets, SSE and gRPC](/docs/guides/websockets-sse-grpc/). |

The protocol between the client and ReverseDock is independent: a client on HTTP/2 can be served by an HTTP/1.1 backend.

## TLS to backends

With `scheme: https`, ReverseDock verifies the backend's certificate and host name against the system's trusted roots. The `tls` block changes that:

- **`server_name`**: the name sent in SNI and checked against the certificate, when it differs from the host in `address` (always set it when the address is an IP).
- **`ca_file`**: a PEM bundle of CA certificates to trust instead of the system roots, for an internal CA.
- **`verify: false`**: no verification at all.

```yaml title="rdock.yaml (excerpt)"
services:
  legacy:
    scheme: https
    tls: { verify: false }
    backends: [{ address: "10.0.1.30:8443" }]
```

:::danger[`verify: false` gives up the protection of TLS]
Anyone who can intercept the traffic between ReverseDock and the backend can read and change it. `rdock validate` warns about it. Prefer `ca_file` with the CA that signed the backend's certificate.
:::

A backend whose certificate fails verification gets no request, and the client receives `502`. Client certificates to backends (`tls.cert_file`, `tls.key_file`) <Status planned="v0.4" /> are accepted by `rdock validate` with a warning and refused by `rdock run`.

## Weights and balancing

Each backend has a `weight`, `1` by default. In the `app` service above, `10.0.0.5` gets 3 of every 5 requests and the other two get 1 each.

`load_balancer.policy` chooses how:

- **`round_robin`** (default): smooth weighted round-robin. Over each cycle every backend gets its share, and the requests of a heavy backend are spread out rather than sent in a row.
- **`random`**: weighted random choice.
- **`least_requests`** <Status since="v0.4" />: the backend with the fewest requests in flight relative to its weight (`weight / (in_flight + 1)`). Good for requests of very different durations. `least_conn` is the same policy: an HTTP/1.1 request holds one connection.
- **`p2c`** <Status since="v0.4" />: two weighted random picks, the less busy one wins. Close to `least_requests` with less coordination; Traefik's `p2c`.
- **`ip_hash`**, **`header_hash`**, **`cookie_hash`** <Status since="v0.4" />: consistent hashing of the client IP, of a header or of a cookie (`hash_on` names it), so the same key reaches the same backend. When a backend is added or removed, only the keys on its share of the ring move. A request without the header or cookie uses round-robin. Every instance maps a key the same way. Weights above 100 count as 100 here.

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    load_balancer: { policy: header_hash, hash_on: x-tenant }
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
```

## Sticky sessions <Status since="v0.4" />

With `sticky`, the first response sets a cookie naming the backend, and later requests with that cookie go to the same backend while it is in the pool:

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    sticky:
      cookie:
        name: srv
        secret: "${file:/run/secrets/sticky_key}"   # optional
        max_age: 1h                                  # optional; a session cookie otherwise
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
```

- The value is an HMAC-SHA256 of the backend address with a secret key, never the address itself, so a client can neither learn your backend addresses nor forge a cookie for a backend of its choice. Traefik stores an unsigned hash of the backend URL instead.
- Without `secret`, a key is generated on first start and kept in `$RDOCK_DATA_DIR/sticky.key`, so cookies survive restarts. Instances that share traffic need the same `secret`.
- To rotate the key, set the new `secret` and move the old one to `previous_secrets`: old cookies still work and are replaced with new ones.
- Cookies are `Secure`, `HttpOnly` and `SameSite=Lax` with `Path=/` by default (`secure`, `http_only`, `same_site`, `path`). `same_site: none` requires `secure`.
- When the backend in a cookie is gone, the request is balanced normally and gets a new cookie.

## Health checks <Status since="v0.4" />

Without health checks, a backend that is down still gets its share of requests, and those requests fail with `502`. There are two kinds, and they work together:

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
    health:
      active:                  # probe every backend in the background
        path: /healthz
        interval: 10s          # ± 10 % jitter
        timeout: 2s
        healthy: 2             # successes in a row to come back
        unhealthy: 3           # failures in a row to go out
        expected_status: "200-399"
      passive:                 # watch real requests
        failures: 5            # within `window`
        window: 30s
        ejection: 30s          # doubled for each ejection in a row, up to 5 minutes
```

**Active checks** run in the background, never on the request path. `mode` picks the probe:

| `mode` | Healthy when |
|---|---|
| `http` (default) | `method` (`GET` or `HEAD`) on `path` answers within `timeout` with a status in `expected_status`, and the body contains `expected_body` if set. The probe uses the service's scheme; `hostname` sets its `Host` and `headers` adds headers. Redirects are not followed. |
| `tcp` | A connection opens within `timeout` (also for Unix sockets). |
| `grpc` | `grpc.health.v1.Health/Check` answers `SERVING` ([gRPC health checking](https://github.com/grpc/grpc/blob/master/doc/health-checking.md)); `grpc_service` names the service to check, empty for the whole server. Needs `scheme: h2c` or `https`. |

`port` probes another port than the backend's. A new backend starts healthy, so a reload never empties a pool before the first probe.

**Passive checks** count failures of real requests: connection errors, resets and timeouts before the response headers, and the answers in `statuses` (default `[502, 503, 504]`). `failures` of them within `window` eject the backend for `ejection`. When that time is over, one request tries it: success brings it back, failure ejects it again for twice as long. `max_ejection_percent` (default 50) stops passive checks from ejecting more than that share of the pool, as Envoy's outlier detection does ([Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/outlier_detection.proto), checked 2026-10-29).

**When every backend is down**, `when_all_down: fail_open` (default) sends requests to all of them anyway: a broken health check, for example a wrong `path`, must not take your service offline. Envoy's panic mode and NGINX's rule for single-server upstreams do the same. `fail_closed` answers `503` with `Retry-After` instead.

**Slow start:** with `slow_start: 30s`, a backend that comes back gets a growing share of its weight over 30 seconds, so a cold cache or JIT is not hit with full traffic at once.

**Backups:** `backup: true` on a backend keeps it idle until no primary backend is available.

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    backends:
      - address: "10.0.0.5:3000"
      - address: "10.0.9.5:3000"
        backup: true
```

**Limits:** `max_requests` caps the requests in flight across the pool; more get `503` with `Retry-After` (a circuit breaker). `max_connections_per_backend` caps them per backend; a backend at its limit gets no new requests until one ends.

The metric `rdock_backend_up{service, backend}` is 1 while a backend takes traffic and 0 while it is out; `rdock_backend_ejections_total` counts ejections. Transitions are logged.

## Retries <Status since="v0.4" />

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
    retries:
      attempts: 2              # extra attempts after the first, at most 10
      on: [connect, "503"]     # connect, reset, timeout, "502", "503", "504"
      budget_percent: 20
```

A failed attempt is sent again, to another backend when there is one:

- **`connect`** (default): the connection could not be opened. Nothing reached the backend, so this is retried for every method.
- **`reset`**, **`timeout`**: the connection broke, or no answer came within `timeouts.read`, before the response headers.
- **`"502"`, `"503"`, `"504"`**: the backend answered with that status. On the last attempt, its answer goes to the client as it is.

Except for `connect`, only idempotent methods (`GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`, `TRACE`) are retried, unless `retry_non_idempotent: true`, which can repeat side effects such as a payment. Nothing is retried once the client has received any part of a response, or when the request body is larger than 64 KiB (the buffer that replays it). Traefik's retry middleware follows the same rules ([Traefik](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/retry/), checked 2026-10-29).

**The retry budget** keeps retries from piling onto a pool that is already failing: retries in flight may be at most `budget_percent` of the service's requests in flight, with 3 always allowed. These are Envoy's defaults ([Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/circuit_breaker.proto), checked 2026-10-29). Retries wait a random 0–25 ms before the first retry, doubling up to 250 ms.

**`Retry-After`:** a backend that answers `503` with `Retry-After` gets no requests for that long (at most 60 seconds) while other backends are available. `429` is passed to the client, because it usually limits one client, not the backend.

Metrics: `rdock_retries_total{service, reason}` and `rdock_retry_budget_exhausted_total{service}`.

Weighted `split` between services <Status planned="v0.4" /> is coming next. See the [roadmap](/docs/project/roadmap/).

## The `Host` header

By default the backend receives the `Host` header the client sent, which is what most applications expect. Set `pass_host_header: false` to send the backend's own address instead: its configured name, with the port unless it is the default for the scheme, or `localhost` for a Unix socket.

```yaml title="rdock.yaml (excerpt)"
services:
  storage:
    pass_host_header: false
    backends: [{ address: "storage.internal:9000" }]
```

Use it for backends that serve a fixed virtual host, such as object storage or another proxy.

## Check that it works

Send a few requests and read the `upstream` field of the [access log](/docs/guides/logs-and-metrics/), which records the address each request went to:

```sh
for i in 1 2 3 4 5; do curl -s -o /dev/null https://app.example.com/; done
```

Connections that could not be established are counted in the metric `rdock_upstream_errors_total`, labelled with the `service` and a `kind` of `connect`, or `timeout` when the connection attempt timed out.

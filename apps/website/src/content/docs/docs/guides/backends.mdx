A service is the pool of backends that answers a route. This guide covers how to address backends, which protocol ReverseDock speaks to them, and how requests are spread across them.

## What you need

- A route, as in [Route a domain to an app](/docs/guides/route-a-domain/).

## The configuration

```yaml title="rdock.yaml"
listeners:
  web:       { address: ":80" }
  websecure: { address: ":443", tls: {} }

certificates:
  example:
    cert_file: /etc/rdock/certs/example.com.pem
    key_file: /etc/rdock/certs/example.com.key

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app
  docs:
    match: "Host(`docs.example.com`)"
    service: docs
  billing:
    match: "Host(`billing.example.com`)"
    service: billing

services:
  app:
    backends:
      - { address: "10.0.0.5:3000", weight: 3 }
      - { address: "10.0.0.6:3000" }
      - { address: "app-3.internal:3000" }
  docs:
    backends: [{ address: "unix:///run/docs/http.sock" }]
  billing:
    scheme: https
    tls:
      server_name: billing.internal.example.com
      ca_file: /etc/rdock/certs/internal-ca.pem
    backends: [{ address: "10.0.1.20:8443" }]
```

## Backend addresses

| Form | Example | Notes |
|---|---|---|
| IPv4 and port | `10.0.0.5:3000` | |
| IPv6 and port | `[2001:db8::5]:3000` | Brackets are required. |
| DNS name and port | `app-3.internal:3000`, `app:3000` | Container names on a Docker network work too. |
| Unix socket | `unix:///run/docs/http.sock` | The path must be absolute. |
| SRV record <Status since="v0.4" /> | `srv://_http._tcp.api.example.com` | Every target of the record, with its port. |

**DNS names** are resolved when a configuration is applied and again when their records expire: the TTL is honoured, kept between 1 second and 5 minutes <Status since="v0.4" />. Names that DNS does not know but the system does (`/etc/hosts`, some container networks) are looked up through the system and refreshed every 10 seconds. A container that restarts with a new IP address is picked up without a reload. A lookup that fails or takes longer than 2 seconds keeps the previous addresses, logs `cannot resolve backend`, and is tried again after 5 seconds. When a name resolves to several addresses, each address is a backend with the weight of the entry. A name that has never resolved leaves the service without backends, and its requests get `503`.

**SRV records** (Consul, Kubernetes headless services, many service registries) list targets with a priority, a weight and a port. ReverseDock uses the targets of the lowest priority; higher priorities are kept as [backups](#health-checks) for when no lower one is available ([RFC 2782](https://www.rfc-editor.org/rfc/rfc2782.html)). Each target's weight is the entry's `weight` times its SRV weight (a weight of 0 counts as 1). Target names are resolved like any DNS name.

**Unix sockets** need ReverseDock to have permission to open the socket file. In a container, mount the socket's directory into the ReverseDock container.

## Protocols

`scheme` sets what ReverseDock speaks to the backends of a service:

| `scheme` | Protocol | Use it for |
|---|---|---|
| `http` (default) | HTTP/1.1 in clear text | Most applications. |
| `https` | TLS; HTTP/2 when the backend offers it through ALPN, otherwise HTTP/1.1 | Backends that only accept TLS, or traffic that crosses an untrusted network. |
| `h2c` | HTTP/2 in clear text | gRPC servers without TLS. See [WebSockets, SSE and gRPC](/docs/guides/websockets-sse-grpc/). |

The protocol between the client and ReverseDock is independent: a client on HTTP/2 can be served by an HTTP/1.1 backend.

## TLS to backends

With `scheme: https`, ReverseDock verifies the backend's certificate and host name against the system's trusted roots. The `tls` block changes that:

- **`server_name`**: the name sent in SNI and checked against the certificate, when it differs from the host in `address` (always set it when the address is an IP).
- **`ca_file`**: a PEM bundle of CA certificates to trust instead of the system roots, for an internal CA.
- **`verify: false`**: no verification at all.

```yaml title="rdock.yaml (excerpt)"
services:
  legacy:
    scheme: https
    tls: { verify: false }
    backends: [{ address: "10.0.1.30:8443" }]
```

:::danger[`verify: false` gives up the protection of TLS]
Anyone who can intercept the traffic between ReverseDock and the backend can read and change it. `rdock validate` warns about it. Prefer `ca_file` with the CA that signed the backend's certificate.
:::

A backend whose certificate fails verification gets no request, and the client receives `502`. Client certificates to backends (`tls.cert_file`, `tls.key_file`) <Status since="v0.4" /> are presented when a backend asks for one; see [Client certificates](/docs/guides/client-certificates/#present-a-certificate-to-backends).

## Weights and balancing

Each backend has a `weight`, `1` by default. In the `app` service above, `10.0.0.5` gets 3 of every 5 requests and the other two get 1 each.

`load_balancer.policy` chooses how:

- **`round_robin`** (default): smooth weighted round-robin. Over each cycle every backend gets its share, and the requests of a heavy backend are spread out rather than sent in a row.
- **`random`**: weighted random choice.
- **`least_requests`** <Status since="v0.4" />: the backend with the fewest requests in flight relative to its weight (`weight / (in_flight + 1)`). Good for requests of very different durations. `least_conn` is the same policy: an HTTP/1.1 request holds one connection.
- **`p2c`** <Status since="v0.4" />: two weighted random picks, the less busy one wins. Close to `least_requests` with less coordination; Traefik's `p2c`.
- **`peak_ewma`** <Status planned="v0.9" />: latency-aware. Two distinct backends are drawn at random and the one with the lower `latency × (in_flight + 1) / weight` wins. The latency is a moving average that jumps up at once when a request is slower than the average and decays over `decay` (default `10s`) otherwise, and that also decays while a backend is idle, so a backend that was slow is tried again. A slow or overloaded backend gets less traffic before it fails outright. This is Finagle's and Linkerd's Peak-EWMA ([Finagle](https://github.com/twitter/finagle/blob/develop/doc/src/sphinx/Clients.rst), [Linkerd](https://github.com/linkerd/linkerd2/blob/main/policy-controller/grpc/src/outbound.rs), checked 2026-11-13). Details below.
- **`ip_hash`**, **`header_hash`**, **`cookie_hash`** <Status since="v0.4" />: consistent hashing of the client IP, of a header or of a cookie (`hash_on` names it), so the same key reaches the same backend. When a backend is added or removed, only the keys on its share of the ring move. A request without the header or cookie uses round-robin. Every instance maps a key the same way. Weights above 100 count as 100 here.

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    load_balancer: { policy: header_hash, hash_on: x-tenant }
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
```

### Latency-aware balancing: `peak_ewma`

<Status planned="v0.9" />

```yaml title="rdock.yaml (excerpt)"
services:
  api:
    load_balancer:
      policy: peak_ewma
      decay: 10s            # time constant of the average (default)
      measure: first_byte   # or last_byte
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }, { address: "10.0.0.7:3000" }]
```

- **What is measured:** with `measure: first_byte` (default), the time from sending the request to the backend until its response headers arrive, as NGINX's `least_time header`. A large download or a slow client does not make a backend look slow, and WebSocket or SSE lifetimes never count. `last_byte` measures to the end of the response (NGINX's `last_byte`); upgraded connections give no sample.
- **Failures** (a refused or timed-out connection, a reset before the headers, or an answer that passive health counts as a failure, `502`–`504` by default) count as a sample of at least one second, so a backend that fails fast does not look fast.
- **A new backend** starts from the mean latency of the others (at least 1 ms), or 30 ms when nothing has been measured yet (Linkerd's defaults), so it neither floods nor starves.
- **Weights** divide the cost: a backend of weight 3 is chosen over one of weight 1 until it has about three times the requests in flight. Health checks, ejection, drain, `max_connections_per_backend`, priority tiers and zones remove backends before the choice; a sticky cookie wins over it; slow start lowers the weight of a ramping backend.
- The average reacts to the requests rdock sends, so it suits pools of three or more similar backends. With two, one slow request can keep a backend out for a few `decay` periods. `round_robin` stays the default.

## Sticky sessions

<Status since="v0.4" /> With `sticky`, the first response sets a cookie naming the backend, and later requests with that cookie go to the same backend while it is in the pool:

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    sticky:
      cookie:
        name: srv
        secret: "${file:/run/secrets/sticky_key}"   # optional
        max_age: 1h                                  # optional; a session cookie otherwise
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
```

- The value is an HMAC-SHA256 of the backend address with a secret key, never the address itself, so a client can neither learn your backend addresses nor forge a cookie for a backend of its choice. Traefik stores an unsigned hash of the backend URL instead.
- Without `secret`, a key is generated on first start and kept in `$RDOCK_DATA_DIR/sticky.key`, so cookies survive restarts. Instances that share traffic need the same `secret`.
- To rotate the key, set the new `secret` and move the old one to `previous_secrets`: old cookies still work and are replaced with new ones.
- Cookies are `Secure`, `HttpOnly` and `SameSite=Lax` with `Path=/` by default (`secure`, `http_only`, `same_site`, `path`). `same_site: none` requires `secure`.
- When the backend in a cookie is gone, the request is balanced normally and gets a new cookie.

## Health checks

<Status since="v0.4" /> Without health checks, a backend that is down still gets its share of requests, and those requests fail with `502`. There are two kinds, and they work together:

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
    health:
      active:                  # probe every backend in the background
        path: /healthz
        interval: 10s          # ± 10 % jitter
        timeout: 2s
        healthy: 2             # successes in a row to come back
        unhealthy: 3           # failures in a row to go out
        expected_status: "200-399"
      passive:                 # watch real requests
        failures: 5            # within `window`
        window: 30s
        ejection: 30s          # doubled for each ejection in a row, up to 5 minutes
```

**Active checks** run in the background, never on the request path. `mode` picks the probe:

| `mode` | Healthy when |
|---|---|
| `http` (default) | `method` (`GET` or `HEAD`) on `path` answers within `timeout` with a status in `expected_status`, and the body contains `expected_body` if set. The probe uses the service's scheme; `hostname` sets its `Host` and `headers` adds headers. Redirects are not followed. |
| `tcp` | A connection opens within `timeout` (also for Unix sockets). |
| `grpc` | `grpc.health.v1.Health/Check` answers `SERVING` ([gRPC health checking](https://github.com/grpc/grpc/blob/master/doc/health-checking.md)); `grpc_service` names the service to check, empty for the whole server. Needs `scheme: h2c` or `https`. |

`port` probes another port than the backend's. A new backend starts healthy, so a reload never empties a pool before the first probe.

**Passive checks** count failures of real requests: connection errors, resets and timeouts before the response headers, and the answers in `statuses` (default `[502, 503, 504]`). `failures` of them within `window` eject the backend for `ejection`. When that time is over, one request tries it: success brings it back, failure ejects it again for twice as long. `max_ejection_percent` (default 50) stops passive checks from ejecting more than that share of the pool, as Envoy's outlier detection does ([Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/outlier_detection.proto), checked 2026-10-29).

`ejection_jitter` <Status planned="v0.9" /> (default `0s`) adds up to that much at random to each ejection time, so that a backend ejected by many instances at once does not get all their traffic back at the same moment (Envoy's `max_ejection_time_jitter`).

### Outlier detection

<Status planned="v0.9" /> Counting failures in a window misses a backend that fails, say, 30 % of its requests: at low traffic it never reaches 5 failures in 30 seconds, at high traffic its neighbours' errors look the same. The two detectors of Envoy's outlier detection compare the backends of a pool with each other instead, once per `interval`, over the requests of that interval:

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    health:
      passive:
        outlier:
          interval: 10s
          success_rate:
            enabled: true
            stdev_factor: 1.9      # eject below mean − 1.9 σ
            minimum_hosts: 5       # backends with enough requests, or nothing is judged
            request_volume: 100    # requests in the interval for a backend to count
          failure_percentage:
            enabled: true
            threshold: 85          # eject at 85 % failures or more
            minimum_hosts: 5
            request_volume: 50
```

- **`success_rate`** computes each backend's success rate, then the mean and standard deviation σ over the backends with at least `request_volume` requests, and ejects those below `mean − stdev_factor × σ`. A backend failing 40 % in a pool of five healthy ones is ejected (60 % against a threshold of about 62 %).
- **`failure_percentage`** ejects a backend whose failures reach `threshold` percent of its requests.
- Both are off until `enabled: true`, and do nothing while fewer than `minimum_hosts` backends have enough requests; `minimum_hosts` below 3 is refused, because with so few backends a statistical test ejects healthy ones. The defaults are Envoy's ([outlier_detection.proto](https://github.com/envoyproxy/envoy/blob/main/api/envoy/config/cluster/v3/outlier_detection.proto), checked 2026-11-13).
- Failures are the same as for `failures`: connection errors, resets and timeouts before the headers, and `statuses`. An outlier goes through the same ejection: `ejection` doubled for each ejection in a row (Envoy multiplies instead), `max_ejection_percent`, then one trial request.
- `rdock_backend_outlier_ejections_total{service, backend, detector}` counts these ejections; they are also counted in `rdock_backend_ejections_total`.

**When every backend is down**, `when_all_down: fail_open` (default) sends requests to all of them anyway: a broken health check, for example a wrong `path`, must not take your service offline. Envoy's panic mode and NGINX's rule for single-server upstreams do the same. `fail_closed` answers `503` with `Retry-After` instead.

**Slow start:** with `slow_start: 30s`, a backend that comes back gets a growing share of its weight over 30 seconds, so a cold cache or JIT is not hit with full traffic at once. The long form <Status planned="v0.9" /> sets the shape and when it applies (Envoy's `SlowStartConfig`, [cluster.proto](https://github.com/envoyproxy/envoy/blob/main/api/envoy/config/cluster/v3/cluster.proto), checked 2026-11-13):

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    health:
      slow_start:
        window: 30s
        aggression: 1.0            # 1 is linear; above 1 ramps faster at first
        min_weight_percent: 10     # never less than this share of the weight
        on: [recovery, join]       # default [recovery]
```

The weight is `weight × max(min_weight_percent / 100, (elapsed / window)^(1 / aggression))`. `recovery` ramps a backend that comes back after failed probes or an ejection; `join` also ramps a backend that newly appears (a reload, a DNS answer, a new container or pod), but only when the pool already has a backend at full weight, so a start-up or an empty pool never ramps (as AWS target groups do). `slow_start: 30s` is the long form with these defaults. Since v0.9 the ramp works for backends of weight 1 too: weights are computed in thousandths while slow start is set. Slow start is refused with `ip_hash`, `header_hash` and `cookie_hash`: every change of a weight would move keys between backends.

### Priority tiers and failover

**Backups:** `backup: true` on a backend keeps it idle until no primary backend is available.

<Status planned="v0.9" /> `priority` generalises this to eight tiers, `0` (the default, used first) to `7`; `backup: true` is the same as `priority: 1`, and setting both is refused. `failover` on the service decides how traffic moves between tiers:

- **`strict`** (default): a tier gets traffic only when every tier above it has no available backend; it hands traffic back as soon as one returns.
- **`spill`**: as Envoy's priority levels, a tier keeps `healthy share × overprovisioning` of the traffic (at most all of it) and the rest goes to the next tier. With the default `overprovisioning: 1.4`, tier 0 keeps everything until fewer than about 71 % of its backends are available; at 50 % it keeps 70 % and 30 % goes to tier 1; at 25 %, 35 % and 65 % ([Envoy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/priority), checked 2026-11-13). When all tiers are degraded, their shares are scaled up to add up to 100 %.

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    failover: spill
    overprovisioning: 1.4
    backends:
      - address: "10.0.0.5:3000"
      - address: "10.0.0.6:3000"
      - address: "10.1.0.5:3000"     # the other site
        priority: 1
```

`when_all_down: fail_open` sends to every backend of the first tier when no backend of any tier is available. SRV targets of a higher SRV priority are one tier below their backend.

### Zones

<Status planned="v0.9" /> A backend can name its `zone`. With `locality: { mode: prefer }`, services use only backends in the proxy's own zone while at least one of them is available, and every backend otherwise, which is Kubernetes' `PreferSameZone` ([Virtual IPs and Service Proxies](https://kubernetes.io/docs/reference/networking/virtual-ips/#traffic-distribution), checked 2026-11-13). Cross-zone traffic often costs money and latency; a zone that loses its backends falls back at once.

```yaml title="rdock.yaml (excerpt)"
locality:
  zone: eu-west-1a        # or the RDOCK_ZONE environment variable
  mode: prefer            # default off
services:
  app:
    locality: { mode: prefer }   # optional: overrides the top-level mode for this service
    backends:
      - { address: "10.0.0.5:3000", zone: eu-west-1a }
      - { address: "10.0.1.5:3000", zone: eu-west-1b }
```

- The proxy's zone is `locality.zone`, else `RDOCK_ZONE`; with neither, `prefer` has no effect and a warning says so.
- Zones apply within the priority tier in use. A retry may leave the zone when the backends in it were tried already.
- `for_zones` lists the zones whose proxies should use a backend instead of its own `zone`. The Kubernetes provider fills `zone` and `for_zones` from EndpointSlices (`zone`, `hints.forZones`), so `prefer` follows Kubernetes Topology Aware Routing; when only some endpoints carry hints, Kubernetes is changing over and nothing is filtered, as kube-proxy does ([Topology Aware Routing](https://kubernetes.io/docs/concepts/services-networking/topology-aware-routing/), checked 2026-11-13).
- The default is `off`: Kubernetes also spreads traffic over all zones by default, and preferring one zone can overload it when its share of backends is small.
- Docker and Swarm labels have no zone setting yet: Docker runs on one host, and a Swarm service is one virtual IP. Zones for those are planned.

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    backends:
      - address: "10.0.0.5:3000"
      - address: "10.0.9.5:3000"
        backup: true
```

**Limits:** `max_requests` caps the requests in flight across the pool; more get `503` with `Retry-After` (a circuit breaker). `max_connections_per_backend` caps them per backend; a backend at its limit gets no new requests until one ends.

The metric `rdock_backend_up{service, backend}` is 1 while a backend takes traffic and 0 while it is out; `rdock_backend_ejections_total` counts ejections. Transitions are logged.

## Retries

<Status since="v0.4" /> ```yaml title="rdock.yaml (excerpt)"
services:
  app:
    backends: [{ address: "10.0.0.5:3000" }, { address: "10.0.0.6:3000" }]
    retries:
      attempts: 2              # extra attempts after the first, at most 10
      on: [connect, "503"]     # connect, reset, timeout, "502", "503", "504"
      budget_percent: 20
```

**By default** <Status since="v0.6" />, a service without `retries` behaves as if it had `retries: {}`: a connection that cannot be opened is tried again on another backend, up to twice, so a backend that stops (a rolling update, a scale-down, a stopped container) does not fail requests while ReverseDock catches up. A connection that timed out is only retried on a backend not tried yet. `retries: { attempts: 0 }` turns retries off. NGINX (`proxy_next_upstream error timeout`) and HAProxy (`retries 3`) retry failed connections by default too ([NGINX](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream), [HAProxy](https://docs.haproxy.org/3.2/configuration.html#4.2-retries), checked 2026-11-07).

A failed attempt is sent again, to another backend when there is one:

- **`connect`** (default): the connection could not be opened. Nothing reached the backend, so this is retried for every method.
- **`reset`**, **`timeout`**: the connection broke, or no answer came within `timeouts.read`, before the response headers.
- **`"502"`, `"503"`, `"504"`**: the backend answered with that status. On the last attempt, its answer goes to the client as it is.

Except for `connect`, only idempotent methods (`GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`, `TRACE`) are retried, unless `retry_non_idempotent: true`, which can repeat side effects such as a payment. Nothing is retried once the client has received any part of a response, or when the request body is larger than 64 KiB (the buffer that replays it). Traefik's retry middleware follows the same rules ([Traefik](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/retry/), checked 2026-10-29).

**A backend that does not answer** <Status since="v0.6" />: when a failed connection would be retried on another backend, an attempt gives up after `timeouts.connect_attempt` (default `1s`) instead of the full `timeouts.connect` (default `5s`); the last attempt, or a service with one backend, still waits `connect`. A stopped container is the usual case: its address no longer answers, and the kernel needs about 6 seconds of ARP probes to give up ([arp(7)](https://man7.org/linux/man-pages/man7/arp.7.html), checked 2026-11-06), so without this budget one request per stop would wait the whole connect timeout. Set `connect_attempt` equal to `connect` to keep the old behaviour, or raise it for backends that are slow to accept connections.

**The retry budget** keeps retries from piling onto a pool that is already failing: retries in flight may be at most `budget_percent` of the service's requests in flight, with 3 always allowed. These are Envoy's defaults ([Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/circuit_breaker.proto), checked 2026-10-29). Retries wait a random 0–25 ms before the first retry, doubling up to 250 ms.

**A backend that stalls** <Status planned="v0.9" />: `per_try_timeout` abandons an attempt that has waited that long for data and sends the request to another backend, within the budget and the rules above (only when `on` lists `timeout`, which is required, an idempotent method or `retry_non_idempotent`, a replayable body, and another backend to try):

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    retries:
      attempts: 2
      on: [connect, timeout]
      per_try_timeout: 500ms
    timeouts: { read: 60s }
```

Pingora, which rdock is built on, gives an attempt one read timeout for all its reads, so `per_try_timeout` replaces `timeouts.read` for every read of such an attempt: the wait for the response headers **and** each pause in the response body. Set it above the longest pause of streamed responses on that service (SSE, long polling), or leave it off there. The last attempt, and requests that cannot be retried (a `POST`, a WebSocket upgrade), wait `timeouts.read`. A stalled request whose retry the budget refuses answers `504`.

**Hedged requests** (a second attempt while the first is still running, as in "The Tail at Scale" or gRPC's `hedgingPolicy`) are refused <Status planned="a later version" />: Pingora 0.9 runs one upstream attempt of a request at a time, and has no hook to race two. `hedge` is accepted by `rdock validate` with a warning and refused by `rdock run`; use `per_try_timeout`.

**`Retry-After`:** a backend that answers `503` with `Retry-After` gets no requests for that long (at most 60 seconds) while other backends are available. `429` is passed to the client, because it usually limits one client, not the backend.

Metrics: `rdock_retries_total{service, reason}` and `rdock_retry_budget_exhausted_total{service}`.

## Splits: canary and blue/green

<Status since="v0.4" /> A service with `split` instead of `backends` sends each request to one of its target services by weight:

```yaml title="rdock.yaml (excerpt)"
services:
  app:
    split:
      - { service: app-v1, weight: 95 }
      - { service: app-v2, weight: 5 }    # canary: 5 % of requests
  app-v1: { backends: [{ address: "10.0.1.5:3000" }] }
  app-v2: { backends: [{ address: "10.0.2.5:3000" }] }
```

- Requests are spread by smooth weighted round-robin, so 5 % means one request in twenty, evenly spaced.
- Each target keeps its own balancing, health checks, retries and limits. A retry stays within the target that was chosen.
- Splits can point at other splits, up to 4 levels; cycles are refused.
- **Blue/green:** change the weights to `0` and `100` and reload. The switch is atomic: requests already running finish on the old target, new ones go to the new one.
- The access log and metrics name the service that answered (`app-v2`), not the split.

## Fixed answers

<Status since="v0.7" /> A service with `respond` answers every request with a status instead of sending it anywhere. It takes no `backends` and no `split`, and the status is from 200 to 599. The reply is ReverseDock's error page for that status, produced like a middleware's reply, so access logs, metrics and the route's response middlewares apply.

It is meant as a target in a split, for a share of traffic that must fail on purpose. Here one request in ten is answered with 500 while the rest reach the backend:

```yaml title="rdock.yaml"
listeners:
  web: { address: ":80" }

defaults:
  listeners: [web]
  tls: off

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app

services:
  app:
    split:
      - { service: app-real, weight: 9 }
      - { service: app-fail, weight: 1 }
  app-real:
    backends: [{ address: "app:3000" }]
  app-fail:
    respond: { status: 500 }
```

The [Kubernetes Gateway API controller](/docs/guides/kubernetes-gateway-api/) uses this form: a `backendRef` that points at nothing valid keeps its weighted share and answers 500, as the Gateway API requires, and a Service without ready endpoints answers 503.

## Mirroring

<Status since="v0.4" /> `mirror` on a route sends a copy of requests to another service, for example to try a new version with real traffic. The copy's answer is ignored, and the client never waits for it:

```yaml title="rdock.yaml (excerpt)"
routes:
  app:
    match: "Host(`app.example.com`)"
    service: app
    mirror: { service: app-next, percent: 10 }
```

- The copy is sent when the original request is done, with the same method, path, headers and body. Connection headers are removed.
- Requests with a body over 64 KiB, WebSocket upgrades and `CONNECT` are not mirrored.
- Only requests that reach the route's service are mirrored: a request refused by a middleware (for example `forward_auth`, `ip_allow` or `rate_limit`) or by a body limit is not copied.
- At most 64 copies per route are in flight; more are dropped rather than queued, so a slow mirror never slows the route.
- `rdock_mirror_requests_total{service, outcome}` counts copies `sent`, `failed`, `dropped`, `too_large` and with `no_backend`.
- Copies repeat side effects: mirror to a service that does not write to your production data.

## The `Host` header

By default the backend receives the `Host` header the client sent, which is what most applications expect. Set `pass_host_header: false` to send the backend's own address instead: its configured name, with the port unless it is the default for the scheme, or `localhost` for a Unix socket.

```yaml title="rdock.yaml (excerpt)"
services:
  storage:
    pass_host_header: false
    backends: [{ address: "storage.internal:9000" }]
```

Use it for backends that serve a fixed virtual host, such as object storage or another proxy.

## Check that it works

Send a few requests and read the `upstream` field of the [access log](/docs/guides/logs-and-metrics/), which records the address each request went to:

```sh
for i in 1 2 3 4 5; do curl -s -o /dev/null https://app.example.com/; done
```

Connections that could not be established are counted in the metric `rdock_upstream_errors_total`, labelled with the `service` and a `kind` of `connect`, or `timeout` when the connection attempt timed out.

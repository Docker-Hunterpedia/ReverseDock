ReverseDock <Status since="v0.9" /> can run as a cluster: several **data planes** (`rdock run`)
serve traffic, and one **control plane** (`rdock control run`, the same binary) gives them their
configuration and stores their certificates. The design is
[ADR-0031](https://github.com/Docker-Hunterpedia/ReverseDock/blob/main/docs/decisions/0031-v0-9-scale.md).

## What the control plane is, and is not

- It **publishes** configuration: you publish a document, it becomes the next **revision**, and
  every data plane pulls it, checks it, stores it and applies it, or refuses it with the reason.
- It is the **certificate store** of the cluster: certificates, their keys, the ACME account and
  the leases that make sure only one data plane orders a certificate
  ([shared certificates](/docs/guides/shared-certificates/)).
- It is **not in the request path**. A data plane never waits for it to serve a request. While it
  is away, data planes keep serving their last revision, even across restarts.
- It does **not** run providers. Docker, Swarm and Kubernetes stay on each data plane and merge
  into the published configuration as usual.
- It serves no traffic, and there is one of it. A highly available control plane is planned.

## Start the control plane

```yaml title="control.yaml"
control:
  listener: "0.0.0.0:7443"
  names: [control.example.com]
admin:
  listener: "127.0.0.1:8080"
```

```sh
rdock control run -c /etc/rdock/control.yaml --data-dir /var/lib/rdock-control
```

The control plane's file holds `control` and `admin` (and `observability`); anything a data plane
serves is published instead. `control.names` are the names data planes use in their URL: they go
on the control plane's server certificate, which its own cluster CA signs. The cluster listener
always uses TLS.

## Enrol a data plane

On the control plane's machine:

```sh
rdock control token create -c /etc/rdock/control.yaml --data-dir /var/lib/rdock-control
```

It prints a single-use join token (valid for `control.join_token_ttl`, one hour by default) and
the cluster CA's pin. Put the token in a file on the data plane and write its configuration:

```yaml title="rdock.yaml"
cluster:
  instance: edge-1
  control:
    url: https://control.example.com:7443
    ca_pin: "sha256:3b4c6f0f6ea41d1f2a9c8f1e5d4b3a29180f7e6d5c4b3a2918f7e6d5c4b3a291"
    join_token: "${file:/run/secrets/rdock-join}"
```

At its first start the data plane checks that the control plane's certificate chains to a CA with
that pin, makes its own key, sends a signing request with the token, and receives a client
certificate naming `edge-1`. The key never leaves the data plane; the token is spent. Later starts
use the identity in `$RDOCK_DATA_DIR/cluster/identity.json` (key, certificate and CA in one file,
mode 0600) and need no token and no control plane. A token that was used, expired or never
existed is refused, and so is a control plane whose certificate does not match the pin: the data
plane stops with an error instead of retrying. If the answer to the enrolment is lost (a timeout,
a crash before the identity was written), the data plane asks again with the same key and the
same token while the token is valid, and gets its certificate again; the token is not lost.

**One name, one machine.** The control plane refuses to enrol a name that is already enrolled and
not revoked, unless the caller presents that instance's current client certificate. Every call
is checked against the newest certificate issued to the name (the one a renewal replaced works
for ten more minutes), so a copied identity directory or an old certificate stops working. Give
each instance its own `cluster.instance`, or leave it out for a generated name: a configuration
file shared by several replicas (a Compose `replicas:` service, a Kubernetes Deployment) with a
fixed `cluster.instance` enrols only the first of them. To **replace a lost instance** under the
same name, revoke it first (`rdock control revoke edge-1`), then enrol the new machine with a new
token; the old machine's certificate stays refused. On a shared directory, which cannot check
anyone's identity, two processes with one name log "another process writes the heartbeat of this
instance name" and never hold a lease together.

Every later call is mutual TLS over HTTP/2. The client certificate lives
`control.identity_lifetime` (30 days by default) and is renewed when a third of it is left.

A data plane's own file keeps only what belongs to that machine: `cluster`, `admin`, `providers`,
`runtime`, `upgrade`, `locality`, `lifecycle`, `observability` and `secrets`. Routes, services,
listeners, certificates and `acme` come from the published configuration; writing them here is an
error. Its admin API reads everything but does not change configuration (as with
`admin.api_writes: false`).

## Publish

```sh
rdock control publish site.yaml -c /etc/rdock/control.yaml --data-dir /var/lib/rdock-control
# published revision 7 (sha256 9c1f…)
```

or `POST /api/v1/cluster/revisions` with `{"document": …}` (operator role, audited). The control
plane refuses what `rdock validate` refuses, an empty document, and a document with `cluster` or
`control`. References such as `${file:…}` and `${env:…}` are published as written and resolved
on each data plane, so the control plane never sees the values they point to; `${env:PORT}` in
a listener address gives each machine its own value. The other side of this: whoever may publish
can make every data plane read any file and variable rdock's user can read there and send it out
(in a header, an upstream URL, a static route), so the publishing role on the control plane is
trusted with every data plane (see [the trust model](#who-can-read-what-the-trust-model)).

Each data plane pulls the revision (a long poll; `cluster.control.poll_timeout`), checks it and
answers:

- **ACK**: it validated and compiled the revision, **stored it on disk**
  (`state/control/bundle.json`), then applied it.
- **NACK**: it could not use it (a port in use, a missing local file, an option its version does
  not know); it keeps serving the previous revision and sends the diagnostics.

`rdock control revisions` lists revisions with the instances that refused each and how their
rollout ended.

A data plane refuses without trying a revision of **another cluster**, a revision **not newer**
than the one it serves, an **empty** one and one that does not match its SHA-256.

**Rollback** is a new publication of an earlier revision's configuration:

```sh
rdock control rollback 6 -c /etc/rdock/control.yaml --data-dir /var/lib/rdock-control
```

A rollback goes to every data plane at once (its configuration already ran), whatever the
rollout mode.

## Roll out to a canary first

By default a new revision goes to **one canary** first and to the other data planes only after
the canary acknowledged it and a **soak time** passed:

```yaml title="control.yaml"
control:
  listener: "0.0.0.0:7443"
  rollout:
    mode: canary        # the default; `all` gives every instance each revision at once
    canary: edge-1      # optional; otherwise the first online instance by name
    soak: 5m            # default 60s (0s–24h)
    canary_timeout: 2m  # default 2m (10s–1h)
```

- **Which instance is the canary.** `rollout.canary` when that instance is online (it called
  within `control.offline_after`); otherwise the first online, unrevoked instance by name. When
  none is online at publication, the first one that comes online.
- **Meanwhile** every other instance stays on the **stable** revision: the last one whose rollout
  completed.
- **A refusal halts the rollout.** If the canary refuses the revision (NACK), or does not report
  on it within `canary_timeout`, the rollout halts: the other instances stay on the stable
  revision until you decide. The halt shows in `rdock control rollout status`, in
  `rdock control revisions`, on the dashboard's Cluster page and in the audit log
  (`cluster.rollout.halt`).
- **Resume** gives every instance the revision now (also during the soak, to promote early):

  ```sh
  rdock control rollout resume -c /etc/rdock/control.yaml --data-dir /var/lib/rdock-control
  ```

- **Abandon** publishes the stable revision's configuration again as a new revision, which every
  instance takes at once, so the canary goes back:

  ```sh
  rdock control rollout abandon -c /etc/rdock/control.yaml --data-dir /var/lib/rdock-control
  # abandoned; published revision 9 with the configuration of revision 7
  ```

Both are `POST /api/v1/cluster/rollout/resume` and `…/abandon` (operator role, audited);
`GET /api/v1/cluster/rollout` shows the state. Publishing a new revision while a rollout runs or
is halted starts a new rollout from the same stable revision. The first revision of a cluster has
nothing to stay on and goes everywhere at once. A refusal after the other instances were given the
revision is listed with it but holds nobody back. Rolling back automatically when the canary's
health drops is planned: `auto_rollback: true` is refused.

## See every instance

`rdock control instances`, `GET /api/v1/cluster/instances` and the dashboard's **Cluster** page
on the control plane show every data plane with:

| Field | Meaning |
|---|---|
| state | `synced` (serves the newest revision), `behind` (an older one, for example held by a rollout), `error` (refused the newest), `offline` (has not called within `control.offline_after`), `revoked` |
| serving, target | The revision it serves, and the one the rollout gives it now |
| version | The rdock version it last reported |
| last seen | When it last called the control plane |
| identity expires | The expiry of its client certificate |
| last error | Why it refused its last revision |

On a data plane the Cluster page says "Not a control plane": the cluster API answers `404` there.

## When the control plane is away

- Cluster-scoped limits fall back to each instance's share
  ([rate limiting](/docs/guides/rate-limiting/#share-a-limit-across-instances)).
- Data planes keep serving the revision they have; `rdock status` shows
  `"cluster": { "connected": false, "serving": 7 }` and `rdock_cluster_control_connected` is 0.
- A data plane that restarts meanwhile serves the stored revision.
- The agent asks again with backoff (at most every 30 seconds) and takes the next revision once
  the control plane is back.
- Certificates stored on the control plane keep serving; new ones are not ordered or renewed
  until it returns (renewal starts weeks before expiry).
- A data plane whose client certificate expires during a very long outage (at least 10 days with
  the defaults) keeps serving but must enrol again with a new token; it logs "the cluster
  certificate of … expired" with what to do (remove `identity.json`, set a new `join_token`)
  instead of reporting the control plane unreachable.
- A data plane whose clock differs from the control plane's by more than 2 s says so in its log
  at its first call; keep clocks in step (NTP).

A data plane that has never received a revision waits for its first one before it starts its
admin API and listeners.

## Remove an instance

```sh
rdock control revoke edge-3 -c /etc/rdock/control.yaml --data-dir /var/lib/rdock-control
```

A revoked instance can no longer fetch revisions or use the store. It keeps serving its last
revision until you stop it. The name can be enrolled again with a new token (a replacement
machine); the revoked machine's certificate stays refused, because every call is checked against
the newest certificate issued to the name.

Revocation stops future access; it **does not take back what the instance already read**. A
member that issues certificates has read the ACME account key and the private keys of every
certificate in the store (see below). If you revoke a member because it was compromised, also:

1. **Revoke it** (`rdock control revoke <name>`) and stop the machine.
2. **Replace the ACME account key.** Remove the account from the store (on the control plane
   `<data dir>/control/store/accounts/<directory>/account.json`; with a shared directory, the same
   path under `cluster.store.path`). The next order creates a new account under its lease. If you
   can, deactivate the old account at the CA with a tool that holds its key (RFC 8555 §7.3.6).
3. **Reissue every certificate**: `POST /api/v1/certificates/{name}/renew` on any member for each
   name (each renewal makes a new private key).
4. **Revoke the old certificates at the CA** with a tool that holds their keys or the old
   account, if the CA supports it and the exposure warrants it.

## Who can read what: the trust model

- **Every data plane that is a member of the store reads every secret in it**: the ACME account
  key and the private key of every certificate the cluster issues. That is the price of data
  planes that issue certificates themselves (an instance cut off from the control plane still
  completes an order another started, and any member can answer the CA). The control plane's
  store does not encrypt per member.
- **What a member may write is limited** to what the protocol needs: a certificate's files, its
  order journal and its challenge answers only while it holds that certificate's lease; the
  account only under the account's lease; only its own heartbeat and confirmations; limit
  counts only upwards; records of others only once they are left over (an ended limit window a
  minute later, by the control plane's clock; an answer after an hour; a heartbeat after a day).
  Leases are always taken in the name of the calling instance, as its client certificate says.
- **The control plane and whoever may publish to it are trusted with every data plane**: a
  publication runs on all of them (and its `${file:}` and `${env:}` references are resolved
  there), and the control plane holds the cluster CA, which can enrol new members.
- **Revocation** shuts a member out from then on; rotate the account key and reissue the
  certificates (above) when the member may have been compromised.

## What the control plane stores, and how to protect it

The control plane's data directory holds the cluster CA's private key, the join tokens' hashes,
the published revisions, and the certificate store: **certificate private keys and the ACME
account key** of the whole cluster. Treat it like a data directory, only more so:

- keep it on an encrypted disk readable only by rdock's user (files are written with mode 0600);
- back it up, and protect the backups like the disk;
- run the control plane where the data planes can reach the cluster listener but the internet
  cannot.

## Upgrading: control plane first

Upgrade the control plane before the data planes. A data plane of an older version refuses
(NACKs) a revision that uses settings it does not know, keeps the previous revision, and the
control plane shows it as `error` with its version and the reason.

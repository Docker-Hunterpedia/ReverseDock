Two common setups put Cloudflare in front of ReverseDock <Status since="v0.3" />: **proxied DNS records** (orange cloud), where Cloudflare connects to your server's public address, and a **Cloudflare Tunnel**, where a `cloudflared` container dials out to Cloudflare and no port is open at all. Facts about Cloudflare below come from its documentation, checked 2026-10-28.

## Proxied records with Full (strict)

Set the zone's SSL/TLS encryption mode to **Full (strict)**: Cloudflare then connects to ReverseDock over HTTPS and checks its certificate. Either certificate works:

- **Automatic certificates.** HTTP-01 and TLS-ALPN-01 requests from the CA pass through Cloudflare's proxy to the origin, so the [defaults](/docs/guides/automatic-https/) work. DNS-01 with the [`cloudflare` provider](/docs/guides/dns-challenge/) works too, and is the way to get a wildcard.
- **An Origin CA certificate.** Cloudflare issues it for your zone, valid up to 15 years; only Cloudflare trusts it, so it only works while the records stay proxied ([Origin CA](https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/)). Load it like any [certificate you provide](/docs/guides/tls-certificates/), and set `acme: false` if every host is covered by it.

```yaml title="rdock.yaml"
# yaml-language-server: $schema=https://raw.githubusercontent.com/Docker-Hunterpedia/ReverseDock/main/schema/rdock.v1.json
listeners:
  web:       { address: ":80" }
  websecure: { address: ":443", tls: {} }

security:
  trusted_proxies: [cloudflare]

acme:
  dns_provider: cf
  dns_providers:
    cf:
      type: cloudflare
      api_token: "${file:/run/secrets/cf_token}"

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app

services:
  app:
    backends:
      - address: "app:3000"
```

`trusted_proxies: [cloudflare]` makes the client IP come from `CF-Connecting-IP` for connections from Cloudflare's edge, with the ranges kept current automatically; see [Behind a proxy](/docs/guides/behind-a-proxy/#cloudflare). To accept only Cloudflare's connections, turn on Authenticated Origin Pulls and set `tls.client_auth: { mode: required, cloudflare: true }` on the listener <Status since="v0.4" />; see [Client certificates](/docs/guides/client-certificates/#cloudflare-authenticated-origin-pulls).

## Cloudflare Load Balancing

Cloudflare's load-balancer monitors probe each origin with `GET` and a `Cloudflare-Traffic-Manager` User-Agent, using the monitor's or the endpoint's `Host` ([monitors](https://developers.cloudflare.com/load-balancing/monitors/), checked 2026-10-29). Give the listener a ping path <Status since="v0.4" />, which answers `200 OK` for any host before routing, and point the monitor at it:

```yaml title="rdock.yaml (excerpt)"
listeners:
  websecure:
    address: ":443"
    tls: {}
    ping: /rdock/ping
```

The ping answers as long as ReverseDock accepts requests on that listener. To make the monitor follow your application instead, point it at a health route of the application.

## Cloudflare Tunnel

`cloudflared` connects out to Cloudflare and forwards requests to ReverseDock inside your Docker network, so the server needs no inbound ports ([Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)). Cloudflare terminates HTTPS with its own edge certificate; between `cloudflared` and ReverseDock the traffic stays on the Docker network, so ReverseDock listens on plain HTTP.

```yaml title="compose.yaml"
services:
  cloudflared:
    image: cloudflare/cloudflared:2026.10.0
    command: tunnel --no-autoupdate run
    environment:
      TUNNEL_TOKEN: ${TUNNEL_TOKEN:-}
    networks: [edge]

  rdock:
    image: ghcr.io/docker-hunterpedia/rdock:0.9.0-alpha.1
    volumes:
      - ./config:/etc/rdock:ro
      - rdock-data:/var/lib/rdock
    networks: [edge]
```

```yaml title="config/rdock.yaml"
# yaml-language-server: $schema=https://raw.githubusercontent.com/Docker-Hunterpedia/ReverseDock/main/schema/rdock.v1.json
listeners:
  web: { address: ":80" }

defaults:
  listeners: [web]
  tls: off

security:
  trusted_proxies: ["172.16.0.0/12"]
  client_ip_header: cf-connecting-ip

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app

services:
  app:
    backends:
      - address: "app:3000"
```

In the Cloudflare dashboard, add a public hostname for the tunnel with the service `http://rdock:80`. `cloudflared` passes Cloudflare's `CF-Connecting-IP` header on; trusting the Docker network range makes ReverseDock use it. The complete example is in [`deploy/docker/examples/cloudflare-tunnel`](https://github.com/Docker-Hunterpedia/ReverseDock/tree/main/deploy/docker/examples/cloudflare-tunnel).

## Cloudflare Access

<Status since="v0.8" /> When Cloudflare Access protects an application, Cloudflare adds a signed
JWT to every request it lets through. `type: cloudflare_access` checks it, so a request that
reaches your origin some other way is refused. Facts below are from Cloudflare's documentation,
[Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
(updated 2026-11-02) and
[Application token](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/)
(updated 2026-06-25), checked 2026-11-11.

```yaml title="rdock.yaml"
listeners:
  websecure: { address: ":443", tls: {} }

routes:
  internal:
    match: "Host(`internal.example.com`)"
    service: internal
    middlewares: [access]

middlewares:
  access:
    type: cloudflare_access
    team: acme                        # or acme.cloudflareaccess.com
    audience: 4714c1358e65fe4b408ad6d432a5f878f08194bdb4752441fd56faefa9b2b6f2
    claims_to_headers:
      email: X-Auth-Email
      common_name: X-Auth-Service-Token

services:
  internal:
    backends: [{ address: "internal:8080" }]
```

It is a preset over the [`jwt`](/docs/guides/jwt/) middleware:

- **Keys** from `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, fetched in the
  background, cached for 10 minutes and fetched again at once (at most every 30 s) when a token
  names an unknown key. Cloudflare rotates the key every 6 weeks and keeps the previous one valid
  for 7 days, so a rotation never refuses a request.
- **Issuer** `https://<team>.cloudflareaccess.com`, **algorithm** RS256 only, `exp` required.
- **`audience` is required**: the Application Audience (AUD) tag (Zero Trust → Access controls →
  Applications → the application → Additional settings). Without it, a token of any other Access
  application of the same team would pass. List several tags to accept several applications.
- **Token** from the `Cf-Access-Jwt-Assertion` header, then the `CF_Authorization` cookie. The
  header wins when both are present, as Cloudflare advises (the cookie is not always passed). The
  token stays in the request for backends that check it again.

The request's **consumer** is the user's `email`. A **service token** (machine-to-machine access)
has an empty `sub` and no email; its consumer is its `common_name` (the Client ID), in the group
`service-token`, so rate limits, quotas, metering and the access log tell users and services
apart. Both are keyed on the team: a service token never counts, caches or gets groups as a user
or as a `consumers.<name>` entry with the same name. Map `common_name` in `claims_to_headers` to pass it on. Custom identity-provider claims
arrive under `custom`, best effort; groups can be missing there.

Pair it with `security.trusted_proxies: [cloudflare]` (real client IPs) and Authenticated Origin
Pulls: the JWT proves Access let the request through, the other two prove it came through
Cloudflare at all.

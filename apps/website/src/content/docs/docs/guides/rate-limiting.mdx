The `rate_limit` middleware <Status since="v0.1" /> limits how fast requests may arrive. Requests
over the limit get **429 Too Many Requests** with a `Retry-After` header and never reach the
backend.

## How the limit works

Each key (by default, each client IP) has a bucket that holds up to `burst` tokens and refills
at `average` tokens per `period`. Every request takes one token. A request that finds the bucket
empty is refused, and `Retry-After` says in whole seconds, at least 1, when the next token is
available.

So `average: 10`, `period: 1s`, `burst: 50` allows a steady 10 requests per second and short
bursts of up to 50.

| Setting | Default | Meaning |
|---|---|---|
| `average` | required | Requests allowed per `period` on average. Must be at least 1. |
| `period` | `1s` | Period of `average`, for example `1s`, `1m` or `1h`. |
| `burst` | same as `average` | Size of the bucket: the most requests accepted at once. |
| `key` | `client_ip` | What to count by (see below). |

## What to count by

| `key` | One bucket per |
|---|---|
| `client_ip` | Resolved client IP, after [trusted-proxy handling](/docs/guides/behind-a-proxy/). An IPv6 client counts by its /64, which one subscriber usually holds. |
| `route` | Route. All clients of the route share one bucket. |
| `header:<Name>` | Value of a request header, for example `header:X-Api-Key`. Requests without the header share one bucket. |
| `cookie:<name>` <Status since="v0.4" /> | Value of a cookie, for example `cookie:session`. Requests without it share one bucket. |
| `claim:<name>` <Status since="v0.4" /> | A claim of the token verified by an earlier [`jwt`](/docs/guides/jwt/) middleware, for example `claim:sub`. |
| `consumer` <Status since="v0.8" /> | The [consumer](/docs/guides/api-keys/) an earlier `api_key` or `cloudflare_access` middleware set. Requests without one (`anonymous: allow`) are counted per client IP. |
| `group` <Status since="v0.9" /> | The consumer's **primary group**: the first entry of its `groups`. All consumers whose primary group is `acme` share one bucket, so a customer with many keys or users gets one limit. A consumer without a group is counted on its own (as with `consumer`); requests without a consumer per client IP. Group, consumer and address counts never mix. |

If ReverseDock runs behind a load balancer or CDN that is not listed in
`security.trusted_proxies`, every request seems to come from that proxy and all clients share
one bucket. List the proxy first.

## Example: protect a login endpoint

This configuration lets each client send 5 login attempts per minute, with up to 5 at once,
and leaves the rest of the site unlimited.

```yaml title="rdock.yaml"
listeners:
  web: { address: ":80" }
  websecure: { address: ":443", tls: {} }

certificates:
  example:
    cert_file: /etc/rdock/certs/example.pem
    key_file: /etc/rdock/certs/example.key

routes:
  login:
    match: "Host(`app.example.com`) && Path(`/login`) && Method(`POST`)"
    service: app
    middlewares: [login-limit]
  app:
    match: "Host(`app.example.com`)"
    service: app

services:
  app:
    backends: [{ address: "app:3000" }]

middlewares:
  login-limit:
    type: rate_limit
    average: 5
    period: 1m
```

The `login` route has the longer rule, so it has the higher priority and is checked first. See
[routing and priority](/docs/concepts/routing-and-priority/).

## Example: limit by API key

```yaml title="rdock.yaml (excerpt)"
middlewares:
  per-key:
    type: rate_limit
    key: "header:X-Api-Key"
    average: 100
    period: 1m
    burst: 20
```

Clients without the header share one bucket and can block each other. To keep them out of
the route, require the header in the rule, for example
``Host(`api.example.com`) && HeaderRegexp(`X-Api-Key`, `.`)``.

## Per group

<Status since="v0.9" /> `key: group` counts all consumers of a group together. With
`overrides`, the override of the **primary group** applies (with `key: consumer`, the first of
the consumer's groups that has one). It works with `scope: cluster` too: the group's count is
shared by the instances like any other key.

```yaml title="rdock.yaml (excerpt)"
consumers:
  ann: { groups: [acme, gold] }   # counted under acme
  bob: { groups: [acme] }         # shares acme's bucket with ann
  cy:  { groups: [globex] }
middlewares:
  per-customer:
    type: rate_limit
    key: group
    average: 100
    period: 1m
    overrides:
      globex: { average: 1000 }
```

Only **configured** groups count: those of `consumers`, a group a token middleware assigns
itself, and groups of a token's `groups_claim` that the `jwt` middleware lists in
`trusted_groups`. Other groups from a token are ignored here (the consumer is counted on its
own, without its group's override), so a token can never join a configured group's bucket or
create a bucket per value its identity provider lets users pick.

`in_flight` and `bandwidth` accept `key: group` with the same meaning. To give each
[tenant](/docs/guides/tenants/) one shared limit, put its consumers in a group named after it.

## Per consumer, with group overrides

<Status since="v0.8" /> With `key: consumer`, `overrides` gives the consumers of a group another
limit; the first of the consumer's groups that has one wins. `headers: draft` adds the IETF
draft's `RateLimit-Policy` and `RateLimit` headers. See
[Quotas and per-consumer limits](/docs/guides/quotas/), which also covers calendar quotas.

```yaml title="rdock.yaml (excerpt)"
middlewares:
  per-consumer:
    type: rate_limit
    key: consumer
    average: 10
    overrides:
      gold: { average: 100, burst: 200 }
```

## What to know

- **Per process, in memory.** Buckets live in the ReverseDock process. Two instances each
  enforce the limit on their own (unless the limit has `scope: cluster`, below), and buckets
  start full after every applied reload or restart.
- **Bounded memory.** Each `rate_limit` middleware tracks at most 65,536 keys. When that is
  reached, idle clients (full buckets) are dropped first, then the least recently used, so a
  flood of distinct addresses cannot exhaust memory.
- **Shared middlewares share buckets.** A middleware used by several routes counts their
  requests together (except with `key: route`). Define one middleware per route if you want
  separate limits.
- **Order matters.** Put `rate_limit` after `ip_allow` or `ip_deny` so blocked clients do not
  use up tokens, and before `basic_auth` to slow down password guessing.

## Share a limit across instances

With `scope: cluster` <Status since="v0.9" />, the instances of a
[cluster](/docs/guides/cluster/) share a `rate_limit` or a [`quota`](/docs/guides/quotas/)
instead of each enforcing it alone:

```yaml title="published configuration (excerpt)"
middlewares:
  api-rate:
    type: rate_limit
    average: 600
    period: 1m
    burst: 100
    scope: cluster        # default: instance
```

```yaml title="rdock.yaml on each instance (optional)"
cluster:
  limits:
    store: cluster          # the cluster store (control plane or shared directory); or `redis`
    sync_interval: 1s       # 100ms–10s
    headroom_percent: 10    # 0–100
    fallback: share         # or `instance`
```

**How it works.** For each key and window, the budget `L` is a counter in the store. Each
instance **claims** parts of it ahead of use, from a background task, and admits requests
against what it claimed plus a small headroom `c = max(1, ⌈L × headroom_percent / (100 × N)⌉)`;
the store never grants more than `L` in total. A request never waits for the store. A key an
instance has not seen yet in the window has no claim yet: until its first claim returns
(one store round trip), the instance admits up to its share `⌈L / N⌉`, so a client's first burst
(a browser's parallel requests) is not refused, and then adds what it admitted beyond its
grant to the store's count.

**The bound.** While the store answers, a cluster of `N` instances admits at most

> `L + N × max(c, ⌈L / N⌉)` requests per key and window

With `headroom_percent` at most 100, `c` is never above `⌈L / N⌉`, so this is
`L + N × ⌈L / N⌉`, about twice `L`. That worst case needs instances to meet a key for the first
time after the others used the budget up; a key whose requests keep reaching the same
instances stays within `L + N × c` (for `L = 600`, `N = 3` and the default 10 %: `c = 20`, 660).
A larger `headroom_percent` absorbs store latency at high request rates; a smaller one tightens
`c`. Once the store says the budget is used up, no headroom is used.

**Clocks.** Windows are cut by each instance's clock, and a window's count is removed a minute
after it ended, so instances whose clocks differ by less than a minute share one count per
window; they only change windows at slightly different moments. `N` does not depend on clocks:
an instance counts a member while that member's heartbeat keeps changing. A data plane warns at
start when its clock differs from the control plane's by more than 2 s; keep clocks in step
with NTP.

**What `scope: cluster` counts.** For `rate_limit`, the cluster admits at most `average`
requests per key in each `period`, in fixed windows from the Unix epoch (so up to twice
`average` around a window boundary), and each instance's own token bucket still shapes bursts.
For `quota`, each calendar window's `limit`.

**When the store is away**, each instance enforces its **share** on its own: `⌈L / N⌉` per
window against what it admitted itself (with `fallback: instance`, the whole `L`). It logs
"the limit store is away" once and `rdock_cluster_limits_store_up` drops to 0; clients see no
error from it. When the store answers again, what each instance admitted meanwhile is added to
the store's count, and the limit is shared again.

**Redis.** `store: redis` keeps the counters in a Redis-compatible server (Redis, Valkey) and
needs no control plane or shared directory:

```yaml title="rdock.yaml"
cluster:
  instance: edge-1
  limits:
    store: redis
    redis:
      url: rediss://redis.example.com:6380/0        # TLS; the path is the database
      username: rdock                               # optional ACL user
      password: "${file:/run/secrets/redis}"        # a reference, never the value
      ca_file: /etc/rdock/redis-ca.pem              # optional; else the system's roots
      timeout: 1s                                   # 100ms–10s, per connect and command
```

rdock uses `AUTH`, `SELECT`, `INCRBY`, `DECRBY`, `PEXPIREAT`, `ZADD`, `ZREMRANGEBYSCORE`,
`ZCARD` and `TIME` (members are counted by the server's clock); keys start with `key_prefix`
(`rdock:`) and expire a minute after their window, by the server's clock. Plain
`redis://` is accepted for a loopback address only, unless you set `allow_plaintext: true`.

**Not shared:** `in_flight` (`scope: cluster` is refused, a cluster-wide count is planned),
`bandwidth`, and [abuse](/docs/guides/abuse-protection/) counters. Without a `cluster` section a
limit with `scope: cluster` counts per instance. Cluster-scoped quotas do not appear in
`GET /api/v1/quotas`.

## Requests in flight: `in_flight` <Status since="v0.4" />

`rate_limit` counts requests over time; `in_flight` caps how many run at once, which protects a
backend from slow requests piling up (Traefik's `inFlightReq`):

```yaml title="rdock.yaml (excerpt)"
middlewares:
  reports-one-at-a-time:
    type: in_flight
    amount: 2              # running at once, per key
    key: client_ip         # same keys as rate_limit
    queue: 10              # wait for a slot instead of failing at once
    queue_timeout: 5s
```

A request over `amount` waits in the queue for up to `queue_timeout`; with a full queue, or
after the timeout, it gets `429` with `Retry-After`. Without `queue`, it gets `429` at once.

## Response bandwidth: `bandwidth` <Status since="v0.4" />

`bandwidth` limits response bytes per second per key, for example for large downloads:

```yaml title="rdock.yaml (excerpt)"
middlewares:
  downloads:
    type: bandwidth
    rate: 1MiB             # per second, per key
    burst: 4MiB            # sent at full speed first; defaults to `rate`
    key: client_ip
```

The response is not cut into pieces; after a chunk that uses up the allowance, the next one
waits until the rate allows it, so the average holds. Requests with the same key share the rate.

## Check that it worked

```sh
for i in $(seq 1 7); do
  curl -s -o /dev/null -w '%{http_code}\n' -X POST https://app.example.com/login
done
```

The first five lines show the backend's status; the last two show `429`. Add `-D -` to one of
the refused requests to see the `Retry-After` header.

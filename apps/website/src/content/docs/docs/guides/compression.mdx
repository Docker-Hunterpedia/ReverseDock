The `compress` middleware <Status since="v0.1" /> compresses responses with zstd, Brotli
<Status since="v0.4" /> or gzip, whichever the client accepts. HTML, CSS, JavaScript and JSON
usually shrink to a fraction of their size.

## Before you start

If your backend already compresses its responses, you do not need this middleware: responses
that already have a `Content-Encoding` are passed on unchanged.

## Configure the middleware

```yaml title="rdock.yaml"
listeners:
  web: { address: ":80" }
  websecure: { address: ":443", tls: {} }

certificates:
  example:
    cert_file: /etc/rdock/certs/example.pem
    key_file: /etc/rdock/certs/example.key

routes:
  app:
    match: "Host(`app.example.com`)"
    service: app
    middlewares: [gzip]

services:
  app:
    backends: [{ address: "app:3000" }]

middlewares:
  gzip:
    type: compress
```

| Setting | Default | Meaning |
|---|---|---|
| `algorithms` | `[zstd, br, gzip]` | Algorithms offered, in order of preference. |
| `min_size` | `1KiB` | Responses whose `Content-Length` is smaller are not compressed. |
| `content_types` | built-in list | Media types to compress. Setting it replaces the built-in list. |

## Which algorithm

The client's `Accept-Encoding` decides: the algorithm it weighs highest (`q=` values) wins, and
when several have the same weight, the order of `algorithms` breaks the tie. Current browsers
send `gzip, deflate, br, zstd`, all with the same weight, so they get zstd; older ones get
Brotli or gzip. `*` covers algorithms not named, and `q=0` refuses one.

The levels suit responses compressed on the fly: zstd level 3, Brotli quality 4 with a 4 MiB
window, gzip level 6. Brotli's highest quality, 11, is meant for files compressed ahead of time
and is many times slower. zstd's window stays under the 8 MiB that browsers accept
([RFC 8878](https://www.rfc-editor.org/rfc/rfc8878.html#section-3.1.1.1.2), checked
2026-10-29). Before v0.4 the default was `[gzip]`.

## Which responses are compressed

Compression uses an **allow-list** of media types. When `content_types` is empty, these are
compressed:

`text/*`, `application/json`, `application/javascript`, `application/x-javascript`,
`application/xml`, `application/xhtml+xml`, `application/rss+xml`, `application/atom+xml`,
`application/ld+json`, `application/manifest+json`, `application/vnd.api+json`,
`application/wasm`, `image/svg+xml`, `font/ttf`, `font/otf`.

In your own list, `type/*` covers a whole type, for example `text/*`. Parameters such as
`; charset=utf-8` are ignored when comparing.

A response is left as it is when any of these holds:

- It is a server-sent event stream (`text/event-stream`) or gRPC (`application/grpc…`). These
  are never compressed, even if your list includes them, because buffering would break them.
- It answers a `HEAD` request.
- Its status is 1xx, 204, 206 (partial content) or 304, or it has a `Content-Range`.
- It already has a `Content-Encoding` other than `identity`.
- Its `Content-Length` is below `min_size`. A response without a length, for example a chunked
  stream, is compressed when its type allows it.
- The client's `Accept-Encoding` accepts none of the configured algorithms.

## What changes on a compressed response

- `Content-Encoding` is set (`zstd`, `br` or `gzip`); `Content-Length` and `Accept-Ranges` are removed.
- A strong `ETag` becomes weak (`W/"…"`), because the bytes differ from the uncompressed ones.
- `Vary: Accept-Encoding` is added to every response that could have been compressed, also when
  this client did not ask for compression, so caches keep the versions apart.
- The body is compressed chunk by chunk as it arrives, so long responses keep flowing.

## Check that it worked

```sh
curl -s -o /dev/null -D - -H 'Accept-Encoding: gzip, br, zstd' https://app.example.com/
```

For an HTML page of 1 KiB or more the response headers include `Content-Encoding: zstd` and
`vary: Accept-Encoding`. Without the `Accept-Encoding` header, the same request returns the
uncompressed page with `vary: Accept-Encoding` only.

With mutual TLS <Status since="v0.4" />, clients prove who they are with a certificate during the TLS handshake. Use it for service-to-service traffic, partner APIs, admin tools, or to accept only Cloudflare's connections to your origin.

## Require a certificate on a listener

```yaml title="rdock.yaml (excerpt)"
listeners:
  websecure:
    address: ":443"
    tls:
      client_auth:
        mode: required                     # or optional
        ca_files: [/etc/rdock/clients-ca.pem]
```

- **`required`**: a handshake without a valid certificate fails; no request is read.
- **`optional`**: clients without a certificate are let in, and routes decide with the [`client_cert`](#check-a-certificate-per-route) middleware. A certificate that is sent is still verified.
- `ca_files` lists PEM files with the CAs that sign your client certificates. Certificates are always verified against them: modes that accept unverified certificates, such as Traefik's `RequireAnyClientCert`, are not offered, because a backend could then be fooled by any self-made certificate.
- The CA files are read on every reload; a missing or empty file refuses the configuration. They are also watched <Status planned="v0.9" />: a CA bundle rewritten on disk (by spiffe-helper, csi-driver-spiffe or your own rotation) is picked up without a restart.

## Check a certificate per route

```yaml title="rdock.yaml (excerpt)"
routes:
  admin:
    match: "Host(`admin.example.com`)"
    service: admin
    middlewares: [staff-only]
middlewares:
  staff-only:
    type: client_cert
    required: true                         # 403 without a verified certificate
    allow: ["*.staff.example.com", "spiffe://example.com/ops/*"]
    forward: xfcc                          # none, traefik or xfcc
```

`allow` matches the certificate's common name and its DNS, URI and email names; `*` stands for any run of characters. Without `allow`, any certificate from the listener's CAs is accepted.

## Check one field at a time

`allow` mixes every name, so ``"*.example.com"`` is also satisfied by a URI SAN or a common name
that ends the same way. Typed lists <Status planned="v0.9" /> check one field each; every list
that is set must match (and `allow`, if set), and within a list one entry is enough:

| Setting | Field | Matching |
|---|---|---|
| `subjects` | subject common name | `*` globs, case-insensitive |
| `organizations` | subject organization (O) | `*` globs, case-insensitive |
| `dns` | DNS SANs | `*` globs, case-insensitive |
| `uris` | URI SANs | `*` globs, **case-sensitive** |
| `emails` | email SANs | `*` globs, case-insensitive |
| `serials` | serial number in hex (colons allowed) | exact |
| `sha256` | SHA-256 of the certificate in hex (colons allowed): a pin | exact |

```yaml title="rdock.yaml (excerpt)"
middlewares:
  billing-clients:
    type: client_cert
    organizations: [Example Corp]
    dns: ["*.billing.example.com"]
```

## SPIFFE workload identities

`spiffe` <Status planned="v0.9" /> accepts only valid
[X.509-SVIDs](https://github.com/spiffe/spiffe/blob/main/standards/X509-SVID.md) of the trust
domains you list, and only the SPIFFE IDs you name:

```yaml title="rdock.yaml"
listeners:
  mesh:
    address: ":8443"
    tls:
      client_auth: { mode: required, ca_files: [/etc/rdock/certs/prod-bundle.pem] }
certificates:
  site: { cert_file: /etc/rdock/certs/site.pem, key_file: /etc/rdock/certs/site.key }
routes:
  api:
    match: "Host(`example.com`)"
    listeners: [mesh]
    service: api
    middlewares: [workloads]
middlewares:
  workloads:
    type: client_cert
    spiffe:
      trust_domains: [prod.example.com]
      ids: ["spiffe://prod.example.com/ns/web/sa/frontend"]
      id_prefixes: ["spiffe://prod.example.com/ns/jobs"]
      consumer: true
    forward: xfcc
services:
  api:
    backends: [{ address: "127.0.0.1:3000" }]
```

A certificate passes when, following the SPIFFE standards `X509-SVID.md` and `SPIFFE-ID.md`
(commit `5d15e3ee` of [spiffe/spiffe](https://github.com/spiffe/spiffe), checked 2026-11-13):

- it has **exactly one** URI SAN, with the scheme `spiffe`;
- the trust domain is non-empty, lower case `[a-z0-9._-]`, without port or user info, and one
  of `trust_domains`;
- the path is not empty (a leaf never carries a trust domain's own ID), with no empty, `.` or
  `..` segment, no trailing `/` and only `[a-zA-Z0-9._-]`; no query or fragment; at most 2048
  bytes;
- it is not a CA and may not sign certificates or CRLs;
- its ID is one of `ids` or lies under one of `id_prefixes`, segment by segment
  (`spiffe://prod.example.com/ns/jobs` accepts `/ns/jobs` and `/ns/jobs/sa/cron`, never
  `/ns/jobsx`). With neither list, any ID of the trust domains passes.

The chain is verified by the listener's `client_auth`, so its `ca_files` must be the trust
domain's bundle. One listener holds one CA pool: list one trust domain per listener; federation
with per-trust-domain bundles is planned.

The accepted SPIFFE ID is in the access log (`spiffe_id`) and in `X-Forwarded-Client-Cert`
(`URI=`). With `consumer: true` (off by default) it also becomes the request's **consumer**, so
`rate_limit` and `quota` with `key: consumer`, metering and the access log's `consumer` count
per workload. Its issuer is `spiffe://<trust domain>`, so it never shares counters with an API
key consumer or an OIDC user of the same name.

### Rotation

SVIDs live about an hour. Write them as files with
[spiffe-helper](https://github.com/spiffe/spiffe-helper) (daemon mode) or cert-manager's
[csi-driver-spiffe](https://cert-manager.io/docs/usage/csi-driver-spiffe/); rdock watches the
listener's `ca_files` and the services' `tls.ca_file`, `tls.cert_file` and `tls.key_file` and
reloads when they change. A certificate and key written as two files are briefly a mismatched
pair: that reload is refused (`the key … does not belong to the certificate …`), the running pair
stays in use, and the reload after the second file lands applies the new pair. New connections
to backends use the new certificate; pooled ones made with the previous one are not reused.

The SPIFFE Workload API (a gRPC socket) is planned: it needs a gRPC client in the data plane.
Checking a **backend's** SPIFFE ID is planned too: Pingora 0.9.1's upstream verifier checks the
chain and the host name, and offers no hook for a URI SAN check.

## Pass the identity to the backend

| `forward` | Headers |
|---|---|
| `none` (default) | nothing |
| `traefik` | `X-Forwarded-Tls-Client-Cert` (the certificate, base64 DER, URL-escaped) and `X-Forwarded-Tls-Client-Cert-Info` (`Subject`, `Issuer`, `NB`, `NA`, `SAN`), as Traefik's `passTLSClientCert` sends them ([Traefik](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/passtlsclientcert/), checked 2026-10-29) |
| `xfcc` | `X-Forwarded-Client-Cert` in Envoy's format: `Hash` (SHA-256), `Subject`, `URI`, `DNS` ([Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_conn_man/headers), checked 2026-10-29) |

Copies of these three headers sent by clients are removed from **every** request, on every route, so a backend can trust them.

## Cloudflare Authenticated Origin Pulls

With [Authenticated Origin Pulls](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/), Cloudflare presents a client certificate when it connects to your origin, so you can refuse connections that do not come through Cloudflare:

```yaml title="rdock.yaml (excerpt)"
listeners:
  websecure:
    address: ":443"
    tls:
      client_auth:
        mode: required
        cloudflare: true       # Cloudflare's global origin-pull CA, built in
```

`cloudflare: true` trusts the CA of global Authenticated Origin Pulls (`origin-pull.cloudflare.net`, valid until 2029-11-01), which ReverseDock ships. Every Cloudflare account uses that same certificate, so it proves the connection comes from Cloudflare, not from your zone. Cloudflare advises zone-level or per-hostname pulls with your own certificate for stricter checks ([Cloudflare](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/set-up/global/), checked 2026-10-29): upload a client certificate to Cloudflare, and list the CA that signed it in `ca_files` instead.

Turn on Authenticated Origin Pulls in the Cloudflare dashboard (SSL/TLS → Origin Server) before you set `mode: required`, or Cloudflare's connections are refused. See also [Behind Cloudflare](/docs/guides/cloudflare/).

## Present a certificate to backends

A backend that requires client certificates gets one from the service:

```yaml title="rdock.yaml (excerpt)"
services:
  payments:
    scheme: https
    backends: [{ address: "payments.internal:8443" }]
    tls:
      ca_file: /etc/rdock/internal-ca.pem
      cert_file: /etc/rdock/rdock-client.pem
      key_file: /etc/rdock/rdock-client.key
```

`cert_file` holds the certificate and any intermediates, leaf first; `key_file` the PEM key (PKCS#8, PKCS#1 or SEC1). Both are checked when the configuration loads, including that the key belongs to the certificate <Status planned="v0.9" />, and read again when they change. `ca_file` can name a different CA from the one that signs the client certificate.

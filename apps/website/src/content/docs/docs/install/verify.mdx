Every release is built and signed by the [release workflow](https://github.com/Docker-Hunterpedia/ReverseDock/blob/main/.github/workflows/release.yml) in GitHub Actions, without long-lived signing keys. You can check that what you downloaded is what that workflow built, from this repository, for a release tag.

| Artifact | What proves it |
|---|---|
| `rdock-<version>-<target>.tar.gz` | Listed in `SHA256SUMS`; build-provenance attestation |
| `rdock-<version>-<target>.spdx.json` | Listed in `SHA256SUMS`; SBOM attestation for the archive |
| `SHA256SUMS` | Keyless cosign signature in `SHA256SUMS.sigstore.json` |
| `ghcr.io/docker-hunterpedia/rdock:<version>` | Keyless cosign signature; provenance attestation |
| the image's SBOM | One SBOM attestation per platform, in the registry |

The SBOM of an archive is read from the binary inside it, not from the source tree: the build embeds the exact list of crates with cargo-auditable, and the release fails if an SBOM lists none. The JavaScript libraries bundled into the embedded dashboard are not listed. `1.0.0-rc.1` is the first release built this way. Releases up to `0.9.0-alpha.1` predate it: they carry one unsigned SBOM of the source tree, `rdock-<version>.spdx.json`, and no SBOM attestations.

## What you need

- [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) for signatures.
- The [GitHub CLI](https://cli.github.com/) (`gh`) for attestations, and `jq` for the SBOM commands.
- `sha256sum` (Linux) or `shasum` (macOS).

## Release archives

Download the archive for your platform, `SHA256SUMS` and `SHA256SUMS.sigstore.json` from the [release page](https://github.com/Docker-Hunterpedia/ReverseDock/releases) into one directory:

```sh
VERSION=1.0.0-rc.1
TARGET=x86_64-unknown-linux-musl
BASE="https://github.com/Docker-Hunterpedia/ReverseDock/releases/download/v$VERSION"
curl -fsSLO "$BASE/rdock-$VERSION-$TARGET.tar.gz"
curl -fsSLO "$BASE/SHA256SUMS"
curl -fsSLO "$BASE/SHA256SUMS.sigstore.json"
```

**1. The checksums were signed by the release workflow of this repository, for a tag:**

```sh
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/Docker-Hunterpedia/ReverseDock/\.github/workflows/release\.yml@refs/tags/v'
```

```text
Verified OK
```

The identity ties the signature to `.github/workflows/release.yml` running for a `v*` tag. A repository ruleset lets only administrators create release tags.

**2. Your archive matches the signed checksums:**

```sh
sha256sum --ignore-missing -c SHA256SUMS      # macOS: shasum -a 256 --ignore-missing -c SHA256SUMS
```

```text
rdock-1.0.0-rc.1-x86_64-unknown-linux-musl.tar.gz: OK
```

**3. The archive was built by GitHub Actions from this repository:**

```sh
gh attestation verify "rdock-$VERSION-$TARGET.tar.gz" --repo Docker-Hunterpedia/ReverseDock
```

The command exits with status 0 when the attestation matches, and prints the workflow and commit that built the file.

**4. The SBOM belongs to that archive.** (From `1.0.0-rc.1` on; releases up to `0.9.0-alpha.1` have no per-archive SBOM and no SBOM attestation: skip this step for them.) Step 2 already checks the SBOM file when it is in the same directory, because `SHA256SUMS` lists it. To check its attestation too (the predicate type carries the SPDX version of the file):

```sh
curl -fsSLO "$BASE/rdock-$VERSION-$TARGET.spdx.json"
gh attestation verify "rdock-$VERSION-$TARGET.tar.gz" --repo Docker-Hunterpedia/ReverseDock \
  --predicate-type "https://spdx.dev/Document/v$(jq -r .spdxVersion "rdock-$VERSION-$TARGET.spdx.json" | cut -d- -f2)"
```

If any step fails, do not run the binary. Download it again from the release page, and report a persistent failure as described in [Security](/docs/project/security/).

## Container images

The image is signed by digest with cosign, using the same workflow identity:

```sh
cosign verify ghcr.io/docker-hunterpedia/rdock:1.0.0-rc.1 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/Docker-Hunterpedia/ReverseDock/\.github/workflows/release\.yml@refs/tags/v'
```

cosign lists the checks it performed and prints the signature payload with the image digest. Check the build-provenance attestation too:

```sh
gh attestation verify oci://ghcr.io/docker-hunterpedia/rdock:1.0.0-rc.1 --repo Docker-Hunterpedia/ReverseDock
```

The SBOM of the image is attested to the manifest digest of each platform, not to the tag. Look the digest up, then verify (SPDX 2.3 is what the release workflow writes today):

```sh
digest=$(docker buildx imagetools inspect --raw ghcr.io/docker-hunterpedia/rdock:1.0.0-rc.1 |
  jq -r '.manifests[] | select(.platform.os == "linux" and .platform.architecture == "amd64") | .digest')
gh attestation verify "oci://ghcr.io/docker-hunterpedia/rdock@$digest" --repo Docker-Hunterpedia/ReverseDock \
  --predicate-type https://spdx.dev/Document/v2.3
```

This works from `1.0.0-rc.1` on; images up to `0.9.0-alpha.1` have no SBOM attestation.

Tags are never overwritten once published, but a tag is still a name. The `latest` tag moves only to the highest stable version: a patch for an older minor and a pre-release never take it. To be certain you deploy what you verified, use the digest that `cosign verify` printed:

```yaml title="compose.yaml (excerpt)"
services:
  rdock:
    image: ghcr.io/docker-hunterpedia/rdock:1.0.0-rc.1@sha256:<digest>
```

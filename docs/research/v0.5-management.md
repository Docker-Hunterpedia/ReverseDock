# v0.5 research: management (admin API and dashboard)

Research note for milestone **v0.5 "Management"**. Requirements in scope: M-ADM-01…04, F-UI-01…06, M-OBS-04, M-OBS-05, F-MGMT-01, F-MGMT-04, F-MGMT-05, H-ENG-04. Every fact was checked on 2026-10-31 against the source linked next to it; crate facts against crates.io and docs.rs. Lines marked *(our reasoning)* are conclusions, not sources. The decisions that follow are in [ADR-0024](../decisions/0024-management-api-and-dashboard.md).

## 1. Where we start

- `rdock-admin` (162 lines) is a Pingora `ServeHttp` app on its own listener (`127.0.0.1:2080`, [ADR-0019](../decisions/0019-zero-config-admin-address.md)), driven by a hand-written accept loop. Routes: `/healthz`, `/readyz`, `/metrics`, `GET /api/v1/status`, `POST /api/v1/config/reload`. One shared bearer token compared with `subtle`. Every handler returns a fully buffered `Response<Vec<u8>>`, so streaming (server-sent events) is impossible without replacing the server. `/metrics` is unauthenticated.
- The engine already keeps a configuration history and a last-known-good copy in `$RDOCK_DATA_DIR` (`rdock-config::state`), counts generations and reports every reload (`configuration applied` / `rejected`).
- `rdock-limits` has a keyed token bucket with a hard key cap (`RateLimiter`, returns `retry_after`) and a `ConcurrencyLimiter`.
- [Architecture §13](../05-architecture.md) planned axum, utoipa, rust-embed, argon2id users, `SameSite=Strict` sessions with CSRF tokens, scoped API tokens, roles, an audit log and SSE; §14 planned a 15-minute ring buffer with DDSketch. The design system ([08](../08-design-system.md)) and mock ([design/dashboard-mock.html](../design/dashboard-mock.html)) exist; the dashboard is English only (decided 2026-10-31).
- `deny.toml` has no ban list: nothing stops `openssl-sys`, `aws-lc-sys` or `native-tls` arriving through a default feature.

## 3. Security practice

**OWASP ASVS 5.0** ([chapters](https://github.com/OWASP/ASVS/tree/master/5.0/en)), the requirements that govern an admin surface:
- V6 authentication: passwords ≥ 8 characters (15 recommended), ≥ 64 allowed, no composition rules, a common-password check (6.2.1/4/5/9), breached-password check (6.2.12, L2); no default accounts (6.3.2); MFA (6.3.3, L2); brute-force controls that do not enable malicious lockout (6.1.1, 6.3.1); no user enumeration by message, status or timing (6.3.8); system-generated activation codes random, single-use and short-lived (6.4.1), which governs the bootstrap token.
- V7 sessions: validated server-side, ≥ 128 bits from a CSPRNG, new token on every login (7.2.1–7.2.4); inactivity and absolute timeouts (7.3.1/2); logout and disabling a user end sessions; users list and end their sessions, admins end anyone's (7.4.1–7.4.5, 7.5.2); re-authentication before sensitive changes (7.5.1).
- V8 authorization: documented rules (8.1.1); function-, object- and field-level checks (8.2.1–8.2.3); enforced on the server (8.3.1); changes apply immediately (8.3.2); admin interfaces never rely on network location alone (8.4.2).
- V3 web frontend: `__Host-` cookies with `Secure` and `HttpOnly` (3.3.1/3/4); anti-forgery on state changes (3.5.1–3.5.3); fixed CORS (3.4.2); CSP with `object-src 'none'`, `base-uri 'none'`, `frame-ancestors` (3.4.3, 3.4.6); `nosniff`, `Referrer-Policy`, HSTS on TLS (3.4.1/4/5).
- V13: don't expose API docs or monitoring endpoints unless intended (13.4.5). V11: approved password hash with current parameters (11.4.2), constant-time compares (11.2.4). V16: structured UTC audit records with actor, action, resource and result, never credentials, protected from injection and modification, shippable to another system (16.2.x, 16.3.1/2, 16.4.1–3).

**Cheat sheets.** [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): idle timeout 15–30 min for low-risk apps, 2–5 min for high-value ones, absolute 4–8 h; store only a hash of the verifier; `Clear-Site-Data` on logout. [CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): "SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments"; a synchronizer token for stateful apps; Fetch Metadata (`Sec-Fetch-Site`) as the primary signal with a mandatory Origin fallback. [REST](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html): tokens never in URLs, 413/415/405, `Cache-Control: no-store`. [Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html): log authentication, authorization failures, configuration changes and admin actions; never session IDs, tokens, passwords or keys.

**Token format.** GitHub's tokens use a type prefix, `_`, a Base62 body and a CRC32 checksum, 178 bits of entropy ([GitHub blog](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)); the [secret-scanning partner program](https://docs.github.com/en/code-security/secret-scanning/secret-scanning-partnership-program/secret-scanning-partner-program) recommends a prefix, high entropy and a 32-bit checksum so scanners match precisely.

**Lost updates.** [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html): a failed `If-Match` must not perform the change (412), with strong comparison. [RFC 6585 §3](https://www.rfc-editor.org/rfc/rfc6585.html): 428 when a request must be conditional.

| Product | What it does (checked 2026-10-31) | Take | Avoid |

*(our reasoning)* The planned model (authentication even on loopback, scoped tokens, roles, audit) is stronger than every peer; the gaps they show us are DNS rebinding (Host checks always on), always-on Origin checks, mandatory `If-Match`, and never taking credentials on the command line.

## 5. Server-sent events

[WHATWG HTML §9.2](https://html.spec.whatwg.org/multipage/server-sent-events.html): `text/event-stream`, fields `event`, `data`, `id`, `retry`; the browser resends the last `id` as `Last-Event-ID` when it reconnects; HTTP 204 stops reconnection; a comment line every 15 seconds keeps idle connections through proxies. `EventSource` cannot set headers, so browser streams authenticate with the session cookie. nginx buffers proxied responses by default and honours `X-Accel-Buffering: no`; `proxy_read_timeout` is 60 s ([nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)).

## 6. Grafana and Prometheus

The Grafana v1 JSON model example shows `schemaVersion: 42`, and a v2 resource model exists ([JSON model](https://grafana.com/docs/grafana/latest/dashboards/build-dashboards/view-dashboard-json-model/)); the grafana.com catalog requires the Classic model ([sharing](https://grafana.com/docs/grafana/latest/dashboards/share-dashboards-panels/)). Provisioning is YAML with `apiVersion: 1` and file providers ([provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/)). [Prometheus naming](https://prometheus.io/docs/practices/naming/): one prefix (`rdock_`), base units, `_total` counters, `_info` metadata, bounded label cardinality.

## 7. Alerts and webhooks

[Slack incoming webhooks](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/) need `text` (optional `blocks`), and the URL is a secret. [Discord webhooks](https://docs.discord.com/developers/resources/webhook) take `content` up to 2,000 characters and up to 10 embeds, and accept Slack payloads at `/slack`. [Standard Webhooks](https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/spec/standard-webhooks.md): headers `webhook-id`, `webhook-timestamp`, `webhook-signature`; HMAC-SHA256 over `id.timestamp.payload` as `v1,<base64>`; `whsec_` secrets; senders must guard against SSRF.

## 9. Keeping the admin side off the request path (H-ENG-04)

*(our reasoning)* A kill only frees resources; a stall reveals shared locks, shared bounded channels and worker starvation. The tests that prove ADR-0009 and ADR-0012 hold: abort the admin task under fixed-rate load; stall it (hold the config-write lock, 10,000 SSE subscribers that never read); flood the login endpoint while argon2 hashes; drive config apply and rollback through the API under load. In each, proxy p99 and error rate must stay at baseline. A static check keeps `rdock-proxy` from depending on `rdock-admin`.

# ReverseDock v0.1 — HTTP request-smuggling / desync defences and test vectors

> Working notes of the v0.1 research (2026-10-26), kept as the record behind [02-research.md](../02-research.md) and ADRs 0012–0016. Probe programs, logs and scratch directories mentioned below were throwaway and are not part of the repository.

Research note for milestone **v0.1 "Hello proxy"**. Scope requirements:
**B-SEC-04** (header/URI/body size limits enforced early, incl. chunked),
**B-SEC-08** (request-smuggling hardening: strict CL/TE, HTTP/2 pseudo-header validation, differential fuzz tests),
**B-NET-05** (hop-by-hop headers stripped), **B-NET-07** (WebSocket, SSE, gRPC streaming),
**B-NET-08** (forwarded headers honoured only from trusted proxies).

Base: Cloudflare **Pingora 0.9.0** (Apache-2.0, released 2026-09-04). This repo resolves
`pingora-core 0.9.0`, `pingora-proxy 0.9.0`, `pingora-http 0.9.0`, `h2 0.4.20`, `httparse 1.10.1`,
`http 1.5.0`, `rustls 0.23.46`, `rustls-webpki 0.103.16`, `tokio-rustls 0.26.6` (verified from the
`pingora-probe` lockfile, 2026-10-26). **Pingora does not depend on `hyper`** — its HTTP/1 parser is
`httparse` + Pingora's own framing; HTTP/2 is the `h2` crate.

## 0. Executive conclusion

Pingora 0.9.0 is **unusually strong** on H1/H2 framing — the Cloudflare March-2026 and October-2026
advisories (CVE-2026-2833/2835, CVE-2026-105298/105299) were fixed *in or before 0.9.0*, so 0.9.0 is
the first release that is not subject to any published Pingora smuggling CVE. Its parser already:
rejects conflicting/duplicate/invalid `Content-Length`; rejects HTTP/1.0 + `Transfer-Encoding`;
rejects a non-`chunked` final transfer-coding; rejects obs-fold and space-before-colon in requests;
rejects CR/LF/NUL/space in the request target; validates authority (duplicate `Host`, userinfo,
`Host`≠`:authority`, ambiguous absolute-form); strips hop-by-hop + `Connection`-nominated headers to
the upstream by default; and **re-frames every body it forwards** (de-chunks then re-chunks, or
forwards a validated `Content-Length`), which is the single most important anti-desync property.

**What ReverseDock must still add itself** (none of these are done by Pingora):

1. **Early size limits** (B-SEC-04): header-block byte cap, header count cap, URI byte cap, and a
   request-body cap that also counts decoded chunked bytes. Pingora's only limits are a 1 MiB−1 header
   hard cap (and it only blocks the *second* read), 256 headers, and an 8 KiB chunk-ext cap — far too
   loose and not configurable.
2. **A request-header (slowloris) deadline.** Pingora has only a per-read inactivity timeout
   (default 60 s), not an absolute "whole header block within N seconds" bound.
3. **Reject Host-less HTTP/1.1** (Pingora accepts `GET / HTTP/1.1` with no `Host`; RFC 9112 §3.2
   requires 400). H/2 already enforces authority presence.
4. **Strict-mode toggles** to reject what Pingora *tolerates*: bare-LF line endings, chunk extensions,
   and bodies on `GET`/`HEAD` — the residual surface for Kettle-2025 (0.CL/CL.0/Expect) and
   "funky chunks" desyncs when chained in front of a weaker back-end.
5. **Explicitly configure `h2` limits** via `default_h2_options()` (RUSTSEC-2026-0389: `H2Options::default()`
   does **not** carry the bounded limits).
6. **The trusted-proxy forwarded-header algorithm** (B-NET-08) and the **differential fuzz target**
   (B-SEC-08 acceptance criterion).

## 1. State of the art 2024–2026 and the test-vector classes

### 1.1 The governing RFCs (primary source for every "expected" verdict below)

- **RFC 9112 (HTTP/1.1 messaging), June 2022.** §6.1: a message with both `Transfer-Encoding` and
  `Content-Length` is subject to possible smuggling — a recipient MUST either reject or close after
  the response; `Transfer-Encoding` overrides `Content-Length`. §6.1: an HTTP/1.0 message (or any
  message where the sender can't be sure of 1.1) with `Transfer-Encoding` "ought to" be treated as
  having faulty framing. §6.3: if a `Transfer-Encoding` is present whose final coding is not
  `chunked`, the server MUST respond 400 and close. §7.1: `chunk-size` and `chunk-ext` end with CRLF;
  chunk data ends with CRLF; a recipient "ought to limit" chunk-ext length. §2.2/§2.3: senders MUST
  use CRLF; a recipient MAY recognise a bare LF as the line terminator and MUST ignore a preceding CR
  — this *permission* is the root of the bare-LF desync class. §3.2: a client MUST send `Host`, and a
  server MUST respond 400 to any 1.1 request lacking `Host` or with more than one.
  <https://www.rfc-editor.org/rfc/rfc9112> (retrieved 2026-10-26)
- **RFC 9110 (HTTP semantics), June 2022.** §8.6: a message with multiple `Content-Length`
  field-values (or one invalid value) has invalid framing and MUST be treated as unrecoverable;
  identical values MAY be collapsed. §7.6.1: connection-specific (hop-by-hop) header fields —
  `Connection` and every field it nominates — MUST be removed by an intermediary before forwarding;
  `Proxy-Connection`, `Keep-Alive`, `TE`, `Transfer-Encoding`, `Upgrade` are hop-by-hop.
  <https://www.rfc-editor.org/rfc/rfc9110> (retrieved 2026-10-26)
- **RFC 9113 (HTTP/2), June 2022.** §8.2.2: connection-specific header fields
  (`Connection`, `Keep-Alive`, `Proxy-Connection`, `Transfer-Encoding`, `Upgrade`) MUST NOT appear;
  `TE` may appear only with value `trailers`. §8.3.1: `:authority` is used to form `Host`; an
  intermediary converting to HTTP/1.1 MUST replace any `Host`. Malformed requests (bad pseudo-header,
  pseudo after regular field, `:path` containing CR/LF, etc.) MUST be treated as a stream error.
  <https://www.rfc-editor.org/rfc/rfc9113> (retrieved 2026-10-26)
- **RFC 7239 (`Forwarded`), June 2014.** `Forwarded: for=…;by=…;host=…;proto=…`; `for`/`by`
  node identifiers may be an IP (IPv6 must be bracketed and quoted, e.g. `for="[2001:db8::1]:443"`),
  an obfuscated token (`for=_hidden`), or `unknown`. <https://www.rfc-editor.org/rfc/rfc7239>
  (retrieved 2026-10-26)

### 1.2 James Kettle, "HTTP/1.1 must die: the desync endgame" (Black Hat USA 2025)

Author James Kettle (PortSwigger), published 2025-08-06, updated 2025-10-17.
<https://portswigger.net/research/http1-must-die> ; slides/whitepaper at
<https://i.blackhat.com/BH-USA-25/Presentations/US-25-Kettle-HTTP1-Must-Die-The-Desync-Endgame-wp.pdf>.
Thesis: upstream HTTP/1.1 is structurally unsafe; the durable fix is HTTP/2 to the origin plus strict
normalisation/validation at *both* tiers. New-for-2025 classes (raw vectors in §8 catalogue):

- **0.CL** — front-end ignores `Content-Length` (treats a bodyless request), back-end honours it →
  back-end waits for a body the front-end already framed as the next request. Needs an "early-response
  gadget" (e.g. IIS `/con`) to break the deadlock.
- **CL.0** — front-end honours `Content-Length`, back-end treats the body as zero-length → the body
  becomes the next request on the back-end.
- **TE.0** — back-end treats `Transfer-Encoding` as absent (coding 0-length) → chunk body smuggled.
- **Expect-based desync** — a valid or *obfuscated* `Expect` header (e.g. `Expect: y 100-continue`)
  parsed differently by the two tiers breaks body forwarding, yielding 0.CL or CL.0 (T-Mobile,
  GitLab, Netlify; Akamai CVE-2025-32094).
- **Visual spoofing / header obfuscation** — leading space before a header name, space before the
  colon, duplicate `Host`, bare-LF header terminator: one tier sees a header the other hides.

### 1.3 "Funky chunks" — chunk-extension / line-terminator differentials (2025)

Jeppe Bonde Weikop, 2025-06-18, <https://w4ke.info/2025/06/18/funky-chunks.html>. A bare `\n` inside a
chunk-size line / chunk extension is read as a line terminator by "TERM" parsers and as extension
bytes by "EXT" parsers; any TERM-front + EXT-back (or vice-versa) pair desyncs. Confirmed-affected:
Apache Traffic Server (CVE-2024-53868), Google Classic ALB, AIOHTTP (CVE-2024-52304), Go `net/http`
(CVE-2025-22871), Netty (CVE-2025-58056, disclosed 2025-06-18), Jetty, H2O, fasthttp, Gunicorn;
nginx chose not to fix the EXT behaviour. RFC 9112 §7.1: only full CRLF is a valid terminator and
control chars are not allowed in `chunk-ext` → correct behaviour is to **reject**.

### 1.4 HTTP Garden (differential fuzzer) and T-Reqs / Gudifu

- **HTTP Garden** — Ben Kallus & Sean Smith (Dartmouth) + Prashant Anantharaman & Michael Locasto
  (Narf Industries), arXiv 2405.17737 (2024). <https://arxiv.org/pdf/2405.17737>. Differential fuzzer
  of HTTP/1.1 *request streams*: ~35 origin servers each echo their parsed request as Base64 JSON
  (`body`/`uri`/`headers`/`version`); "transducers" (proxies/caches) forward to an echo server so the
  client can observe pipelining/boundary changes. Inputs are **sequences of byte-chunks** (modelling
  connection reuse/pipelining) mutated at byte, stream, and grammar level; parents chosen by NEZHA
  δ-diversity; discrepancy-inducing inputs are reported but never re-selected. **Runs targets in local
  Docker containers**; C/C++ instrumented with AFL++ `afl-cc`, Python with `python-afl`, coverage
  captured per-request via a ~38-line `afl-showmap` patch. Discrepancy categories: integer parsing
  (CL/chunk-size), chunk parsing (delimiters/ext/terminators), field-line parsing (bare CR/LF,
  injection), field-value parsing (empty list elements in `Transfer-Encoding`), and DoS. Reported
  100+ bugs, 68 fixed, 39 exploitable. **CI feasibility:** the full Docker matrix is too heavy for a
  PR gate but runs fine in a scheduled job; the *technique* (feed a byte-stream to two parsers, diff
  the interpretation) is what ReverseDock should reproduce in-process (see §4).
- **T-Reqs** (Jabiyev et al., CCS 2021) — grammar-based differential fuzzer that first systematised
  CL/TE smuggling discovery. **Gudifu** (RAID 2024) — graybox guided differential fuzzer for proxy
  request-parsing discrepancies (Dartmouth/Northeastern/Akamai), <https://par.nsf.gov/servlets/purl/10615789>.

### 1.5 How mainstream proxies handle these (where documented)

- **nginx** — rejects conflicting CL/TE; is an **EXT** parser for bare-LF in chunk extensions and
  maintainers declined to change it (w4ke.info, 2025-06-18). Request line/header bounded by
  `large_client_header_buffers 4 8k`.
- **HAProxy** — rejects ambiguous framing; recommends `timeout http-request 5s` against slowloris
  (<https://cdn.haproxy.com/blog/protect-your-web-server-against-slowloris>, retrieved 2026-10-26).
- **Envoy** — normalises/validates; returns **431** when header count/size exceeded; resets the H2
  stream (kgateway/Envoy docs, retrieved 2026-10-26).
- **Caddy / Go `net/http`** — was a **TERM** parser vulnerable to funky-chunks via `net/http`
  (CVE-2025-22871, fixed Go 1.24.x).
- **Traefik v3** — delegates H1/H2 parsing to Go `net/http`/`x/net/http2`; `readTimeout` default 60 s
  bounds whole-request read (CVE-2026-88012 advisory, retrieved 2026-10-26).

## 2. What Pingora 0.9.0 already does vs. what ReverseDock must add

### 2.1 HTTP/1 request read & parse (`…/pingora-core-0.9.0/src/protocols/http/v1/`)

Flow in `server.rs:278 read_request()` → `server.rs:484 validate_request()`:

- **Parser**: `httparse 1.10.1` via `parse_req_buffer` (`server.rs:1797`) using the **strict** default
  `req.parse()` unless the `patched_http1` feature is on (`parse_unchecked`). ReverseDock must **not**
  enable `patched_http1`. httparse request parsing has `allow_spaces_after_header_name=false` and
  `allow_obsolete_multiline_headers=false` (hard-coded for requests, `httparse/src/lib.rs:507-508`),
  so **obs-fold and "name : value" are rejected** (→ `InvalidHTTPHeader` → 400).
- httparse byte classes (`httparse/src/lib.rs:69-96`): URI token = `0x21..=0x7e | 0x80..=0xFF`
  (excludes space `0x20`, DEL, controls); header name = RFC 9110 `tchar`; header value =
  `\t | 0x20..=0x7e | 0x80..=0xFF` (**excludes CR/LF and other C0 controls except TAB**). So
  header-value CR/LF injection and control bytes are rejected at parse time.
- **Request-line escape hatch** (`server.rs:436-475`, `escape_illegal_request_line` `server.rs:1765`):
  on a `Token`/`Version` httparse error, Pingora percent-encodes space/`<`/`>`/`"`/controls in the URI
  and *retries*. Consequence: a raw space or control in the target is **normalised (%xx), not
  rejected**, at the H1 ingress. Forbidden bytes are instead caught when writing to the upstream
  (`client.rs:911 request_target_has_forbidden_byte` → `0x00|0x0a|0x0d|0x20`) and on H2 ingress.
- **CL + TE both present** (`server.rs:399-435`): `Content-Length` removed, keep-alive disabled
  (RFC 9112 §6.1). TE wins.
- **`validate_request()`** (`server.rs:484`):
  - `validate_request_authority()` (`authority.rs:49`) — see §2.4.
  - `validate_content_length()` (`common.rs:398`) → `content_length_for_framing` →
    `content_length_parse_all` (`common.rs`), which mirrors hyper's `from_digits`: rejects empty,
    non-digit, leading `+`/`-`, overflow; multiple CL lines / comma lists must all parse **and be
    equal**, else the message is rejected (`InvalidHTTPHeader` → 400). No-op when TE present.
  - TE present + **HTTP/1.0** → reject `"HTTP/1.0 requests cannot include Transfer-Encoding"`
    (`server.rs:496-505`) — this is the RUSTSEC-2026-0034 fix.
  - TE present + final coding **not `chunked`** → reject `"non-chunked final Transfer-Encoding"`
    (`server.rs:507-510`). `is_chunked_encoding_from_headers` (`common.rs:168`) looks only at the
    **last** `Transfer-Encoding` header's **last** comma token (trimmed, case-insensitive).
- **Hard limits** (NOT configurable, `common.rs:27-38`): `MAX_HEADER_SIZE = 1048575` (1 MiB−1),
  but the check (`server.rs:308`) "only blocks the second read" — the first read into an
  already-allocated buffer is allowed, so a single read can exceed it; `MAX_HEADERS = 256`;
  chunked: `PARTIAL_CHUNK_HEAD_LIMIT = 8 KiB` for chunk-size+ext (`body.rs:33,783`),
  `TRAILER_SIZE_LIMIT = 64 KiB` (`body.rs:38`). **No body-size limit at all.**
- **Chunk parsing** (`body.rs`): chunk-size line parsed by `httparse::parse_chunk_size`
  (`httparse/src/lib.rs:1263`) which **requires CR then LF** (`b'\r' => match next { b'\n' => break, _ => Err }`)
  — a **bare LF in the chunk-size line is rejected**. However, once in a chunk extension (after `;`),
  `_ if in_ext => {}` consumes arbitrary octets **including a bare `\n`** until a CRLF — so Pingora is
  an **EXT** parser (it does not treat bare-LF-in-ext as a terminator). Chunk *data* terminators are
  validated as full CRLF (`validate_crlf` `body.rs:1009`; bare `\r` or `\n` → `INVALID_CHUNK`).
  `usize`/buffer-index overflows on chunk size are rejected (`body.rs:683-737`).

### 2.2 Body framing toward the upstream — the key defence

Pingora does **not** pass raw request-body bytes through. It decodes with its own `BodyReader` and
re-encodes with its own `BodyWriter`:
- `finalize_h1_upstream_request_framing` (`proxy_common.rs:410`): if the (post-filter) request has a
  body but no `Content-Length` and no `Transfer-Encoding`, Pingora **adds `Transfer-Encoding: chunked`**.
- `do_write_chunked_body` (`body.rs:1379`) writes clean `"{:X}\r\n"` chunk framing with no passthrough
  of the client's chunk extensions or odd terminators.
- `Content-Length` is **not** a hop-by-hop header, so a validated CL is preserved; a chunked body is
  de-chunked and re-chunked. Either way, **the upstream receives exactly the requests Pingora parsed at
  the H1 server layer** — chunk-extension/terminator tricks cannot create a second request on the
  upstream stream. This neutralises the *pass-through* form of funky-chunks/TE.0 smuggling.

### 2.3 Connection reuse / draining (anti-desync)

- **HTTP/1 pipelining is OFF by default** (`server.rs:207 pipelining_enabled: false`); a reused
  keep-alive connection only carries pipelined-prefix bytes when explicitly enabled.
- `reuse()` (`server.rs:1449`) **drains the request body** before reuse and refuses reuse if bytes were
  over-read while pipelining is disabled — this is the RUSTSEC-2025-0037 fix.
- On any incomplete request-send or response-read, the **upstream** connection is marked non-reusable
  (`proxy_h1.rs:292-345`, returns `Ok(false)`).
- **Upgrades only switch after a 101** (`proxy_h1.rs:875,960 reject_mismatched_h1_upgrade_101`) — the
  RUSTSEC-2026-0033 "premature upgrade" fix.

### 2.4 Authority validation (`…/protocols/http/authority.rs`, `pingora-http/src/authority.rs`)

`validate_request_authority_fields` (`authority.rs:94`) rejects: duplicate `Host`; userinfo (`@`) in
`Host`, URI authority, or absolute-form target; `Host` ≠ URI authority. `validate_request_authority`
(`authority.rs:49`) additionally rejects ambiguous absolute-form (`AmbiguousAuthority`: `://host`,
`ht_tp://host`, `http:\host`, double colon/bracket via `has_ambiguous_port_suffix` `authority.rs:214`),
unparseable absolute-form authority, and `Host` ≠ absolute-form authority. **Gap:** for **origin-form
with no `Host`** (`GET / HTTP/1.1`), `raw_target_authority("/")` = `None` and `host = None` →
**returns `Ok` (accepted)**. RFC 9112 §3.2 requires a 400. H/2 rejects missing authority
(`v2/server.rs:333`), H/1 does not → **ReverseDock must reject Host-less HTTP/1.1.**

### 2.5 HTTP/2 downstream (`…/protocols/http/v2/server.rs` + `h2 0.4.20`)

The `h2` crate enforces at HPACK-decode (`h2/src/frame/headers.rs:862 load_hpack`): connection-specific
headers (`connection`, `transfer-encoding`, `upgrade`, `keep-alive`, `proxy-connection`) → malformed;
`te` ≠ `trailers` → malformed; pseudo-header after a regular field → malformed; repeated pseudo →
malformed; header names must be lowercase (`h2/src/hpack/header.rs:98 from_lowercase`); unknown
`:`-prefixed name → `InvalidPseudoheader`. `h2/src/server.rs:1658 convert_poll_message`: missing
`:method`/`:scheme`/`:path`, `:status` on a request, `:protocol` on non-CONNECT, empty `:path`,
malformed `:authority`/`:scheme`/`:path` → `PROTOCOL_ERROR`.

Pingora adds stream-local checks (`v2/server.rs:426 from_h2_conn_with_malformed_budget`):
`request_target_has_forbidden_byte` on `:path` (rejects `0x00|LF|CR|space`, `v2/server.rs:450`);
`validate_content_length_without_transfer_encoding` (rejects any TE in H2 + conflicting CL,
`v2/server.rs:466`); `invalid_request_authority` (`v2/server.rs:328` — duplicate `Host`, userinfo,
missing `Host`+`:authority`, absolute-form/ambiguous `:path`, ambiguous CONNECT authority) → **400**.
A per-connection budget of **32 malformed streams** (`MAX_MALFORMED_STREAMS_PER_CONN`, `v2/server.rs:63`)
caps rejection work. `:authority`≠`Host` is the RUSTSEC-2026-0388 fix (now 400).

**Default h2 limits** (`v2/server.rs:56-80 default_h2_options`): `max_header_list_size = 64 KiB`,
`max_concurrent_streams = 100`. **Critical:** per RUSTSEC-2026-0389, `H2Options::default()` does **not**
include these — ReverseDock MUST build options from `default_h2_options()` (or set both explicitly),
or it reintroduces the 16 MiB-header / unlimited-stream OOM.

### 2.6 Hop-by-hop stripping (B-NET-05) — `proxy_common.rs`, `peer.rs`

`HttpUpstreamRequestPolicy::default()` (`peer.rs:446`, used unless overridden): `strip_hop_by_hop=true`,
`strip_connection_nominated=true`, `reject_malformed_connection_nominations=true`,
`h1_upgrade=WebSocketOnly`. `strip_standard_hop_by_hop_headers` (`proxy_common.rs:178`) removes
**`Keep-Alive`, `Proxy-Connection`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`,
`Transfer-Encoding`, `Connection`, `Upgrade`, `HTTP2-Settings`**. `Connection`-nominated fields are
parsed (`ConnectionNominations::parse` `proxy_common.rs:95`, capped at 10) and removed; nominating
`Host`/`X-Forwarded-For`/`X-Forwarded-Host`/`X-Forwarded-Proto` or any `:`-pseudo → **400**; a
non-`tchar` token (e.g. `Connection: "X-Forwarded-For"`) → 400 in strict mode. This is the
RUSTSEC-2026-0390 fix. **WebSocket:** when the downstream is HTTP/1.1 with `Upgrade: websocket`,
Pingora re-adds clean `Connection: Upgrade` + `Upgrade: websocket` (`proxy_common.rs:355-372`).

ReverseDock must therefore **not** disable this policy (never use `HttpUpstreamRequestPolicy::preserve()`),
and should additionally remove any per-route/user headers in `upstream_request_filter` (B-NET-05
set/add/remove is a ReverseDock feature layered on top). Note `TE` is stripped entirely, including
`TE: trailers`; gRPC trailers still work because over H2 they are frame-level, not the `TE` header.

### 2.7 Timeouts / Expect

- `HttpSession` default `read_timeout = Some(60s)` (`server.rs:189`) is a **per-read inactivity**
  timeout, not an absolute header deadline → **slowloris gap**; ReverseDock must wrap `read_request()`
  in an absolute deadline (B-NET-09 "request-header").
- Downstream keep-alive: HTTP/1.1 defaults to keep-alive-on unless `Connection: close`
  (`respect_keepalive` `server.rs:798`); the proxy loop does not impose a default idle number →
  ReverseDock must set a keep-alive idle timeout.
- `Expect: 100-continue` matched **exactly** (case-insensitive) and only for HTTP/1.1
  (`common.rs:194 is_expect_continue_req`). An **obfuscated** `Expect` (`Expect: y 100-continue`) is
  *not* matched by Pingora — but it is **not stripped** either (Expect is not hop-by-hop), so it is
  forwarded to the upstream. Pingora's body re-framing defuses the classic Expect desync, but a
  strict front-end should still **normalise/strip unknown `Expect` values** (Kettle 2025).

## 4. Differential fuzz target (B-SEC-08 acceptance: "differential fuzz target exists")

### 4.1 Design goal

Detect any input where **what ReverseDock's front end believes about a request's framing and boundary
differs from what the upstream will actually receive** — the precise definition of a desync. Two
cargo-fuzz targets, both in `tests/fuzz/fuzz_targets/` (the repo already plans `tests/fuzz/` and a
weekly `fuzz.yml`, per `docs/06-repo-layout.md` §lines 18,71,135).

### 4.2 Target A (primary): **round-trip framing equivalence** — recommended

Harness (`h1_roundtrip_framing.rs`):

1. Use `arbitrary` to turn fuzz bytes into a `Vec<Vec<u8>>` (ordered byte-chunks), modelling
   pipelining/streaming exactly like HTTP Garden's "stream" inputs.
2. Feed the concatenation to **Pingora's own HTTP/1 server** (`pingora_core::protocols::http::v1::server::HttpSession::new`
   over an in-memory duplex / `tokio_test::io::Builder`) on a current-thread runtime. Drive
   `read_request()` then `read_body_bytes()` to completion. Record the **front-end verdict**:
   `accept|reject`, and if accepted: method, raw target, `Host`, version, framing kind
   (`content_length(n) | chunked | none`), the **decoded body bytes**, and the **over-read boundary**
   (how many trailing bytes remain = start of "request 2").
3. Build the request Pingora would send upstream through the *same code path ReverseDock uses*
   (apply `HttpUpstreamRequestPolicy::default()` sanitisation + `finalize_h1_upstream_request_framing`,
   then serialise via `http_req_header_to_wire` + the re-chunked/CL body).
4. **Re-parse that upstream byte stream with an independent parser** (`httparse` for the header block +
   a hand-written RFC-9112 framing decoder; optionally `hyper`'s server as a second oracle in Target B).
5. **Assert**: (a) the upstream stream parses as **exactly one** request with **no trailing bytes**;
   (b) its method/target/Host/framing/body **equal** the front-end interpretation from step 2. Any
   mismatch, or "front-end accepted but upstream stream yields ≥2 requests / a different body length",
   is a crash (a desync).

Rationale: this is a true end-to-end smuggling oracle — it does not need a second HTTP implementation to
*agree with Pingora on legality*, only to agree on **boundary and body length**, which is what an
attacker exploits. It is deterministic, in-process, no network, no Docker → runs under libFuzzer.

### 4.3 Target B (secondary): **parser-verdict differential vs hyper/httparse**

Harness (`h1_parser_differential.rs`): feed the same bytes to (i) Pingora's `read_request`+`validate_request`
and (ii) `hyper`'s HTTP/1 server parser (or a strict `httparse`+RFC-9112 reference). Normalise each to
`{accept?, framing kind, cl/te resolution}` and assert they don't **disagree in a dangerous direction**:
flag any case where Pingora **accepts** a message that hyper frames with a **different body length or
CL/TE resolution** (the T-Reqs/HTTP-Garden "origin-vs-origin" discrepancy class). Pure "both reject" or
"both accept, same framing" passes. (`hyper` is a dev-dependency of the fuzz crate only; it is not a
runtime dependency — Pingora itself does not use hyper.)

### 4.4 Seed corpus and CI

- Seed `tests/fuzz/corpus/h1/` with every raw vector from §8 plus T-Reqs/HTTP-Garden published seeds.
- **PR gate** (`rust` job): a bounded, deterministic replay — `cargo +nightly fuzz run h1_roundtrip_framing
  -- -runs=200000 -max_total_time=60` seeded from the committed corpus (libFuzzer needs nightly +
  `-Z sanitizer`; run it in a dedicated nightly step, MSRV stays stable for the library). Plus a plain
  `#[test]` table that replays the §8 catalogue through the same harness so the behaviour is also
  checked on stable in `nextest`.
- **Weekly `fuzz.yml`**: long-running `cargo fuzz run` for both targets, corpus persisted via cache.

## 5. Forwarded headers (B-NET-08)

### 5.1 How the field each tool trusts / sets

- **Traefik v3** — `entryPoints.<ep>.forwardedHeaders.trustedIPs` (or `.insecure: true` = trust
  everyone). Only when the peer is trusted does Traefik honour inbound `X-Forwarded-*`; it then
  **appends** the peer to `X-Forwarded-For`, sets `X-Forwarded-Proto/Host/Port/Server` and
  `X-Real-Ip`. Untrusted peer → inbound values are dropped and replaced. `X-Forwarded-Prefix` is only
  enforced against trusted IPs since the CVE-2024-52003 fix (v2.11.14/v3.2.1). ForwardAuth's
  `trustForwardHeader` is deprecated in v3.6 in favour of entrypoint trusted IPs. (doc.traefik.io
  entrypoints/migration; SentinelOne CVE-2024-52003 summary; retrieved 2026-10-26.)
- **nginx `realip`** — `set_real_ip_from <cidr>` lists trusted peers; `real_ip_header
  X-Forwarded-For|X-Real-IP|proxy_protocol`; `real_ip_recursive on` walks `X-Forwarded-For`
  right-to-left skipping trusted addresses to find the first untrusted = client. Default recursive off
  (uses the last address). (nginx ngx_http_realip_module docs.)
- **Envoy** — `xff_num_trusted_hops = N`: the client is the address **N hops from the right** of
  `X-Forwarded-For`; `X-Forwarded-Proto` is trusted only when N>0. 0 (default) = don't trust XFF, use
  the socket peer. (Envoy/Pomerium xff docs, retrieved 2026-10-26.)
- **Caddy** — `trusted_proxies <ranges>` (global); when the peer is trusted, reads
  `client_ip_headers` (e.g. `Cf-Connecting-Ip`) / walks XFF; `trusted_proxies_strict` makes it stop at
  the first **untrusted** hop (right-to-left) instead of taking the leftmost. Untrusted peer → socket
  address. (caddyserver.com global-options; caddy.community, retrieved 2026-10-26.)

### 5.2 Recommended algorithm for rdock (matches `docs/05-architecture.md` §6)

Trusted-proxy list is **required before any forwarded header is honoured** (B-NET-08; vision §5).

```
peer = TCP/TLS socket address
if peer ∉ trusted_proxies:
    client_ip = peer
    # strip & overwrite ALL inbound forwarding headers before upstream (do not trust):
    remove Forwarded, X-Forwarded-For/Proto/Host/Port/Prefix, X-Real-IP, CF-Connecting-IP
else:
    if peer ∈ verified_cloudflare_ranges and client_ip_header == auto:
        client_ip = CF-Connecting-IP            # W-CF-02 (v0.3)
    else:
        # right-to-left walk of X-Forwarded-For, skip trusted hops; first untrusted = client
        for addr in reverse(split(X-Forwarded-For)):
            if addr ∈ trusted_proxies: continue
            client_ip = addr; break
        else: client_ip = peer                  # all hops trusted
# toward upstream (trusted peer): APPEND, don't overwrite:
X-Forwarded-For  += client_ip
X-Forwarded-Proto = scheme (if absent)
X-Forwarded-Host  = original Host (if absent)
X-Real-IP         = client_ip
```

- **Overwrite** for untrusted peers (anti-spoofing); **append** for trusted peers (preserve the chain)
  — this is the Caddy-`trusted_proxies_strict` / nginx-`real_ip_recursive on` behaviour, not Envoy's
  fixed-count which is brittle with variable chains.
- Parse `Forwarded` (RFC 7239) tolerantly: bracketed+quoted IPv6 (`for="[2001:db8::1]:443"`),
  obfuscated tokens (`for=_x`, `for=unknown` → ignored for IP purposes). Prefer the explicit list
  over Envoy's hop-count. Cap the number of XFF elements parsed (DoS bound).

## 6. Hop-by-hop headers (B-NET-05) — summary of obligations

Pingora **already strips** (to the upstream, default policy, §2.6): `Connection`, every
`Connection`-nominated field, `Keep-Alive`, `Proxy-Connection`, `Proxy-Authenticate`,
`Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`, `HTTP2-Settings`; and rejects
nominations of `Host`/`X-Forwarded-*`/pseudo-headers. H2 upstream path strips the same
(`proxy_h2.rs:150,160`). WebSocket `Upgrade`+`Connection: Upgrade` are correctly re-synthesised for a
valid websocket upgrade; `TE: trailers` / gRPC trailers work over H2. **ReverseDock must:** keep the
default policy (never `preserve()`); apply its own response-side hop-by-hop strip (Pingora's policy is
request-side — response `Connection`/`Keep-Alive`/`Transfer-Encoding` handling is framing-managed, but
per-route response header rules must not re-introduce them); and treat B-NET-05 set/add/remove as a
ReverseDock middleware layered after Pingora's strip.

## 8. Numbered test-vector catalogue (for the e2e suite and fuzz seed corpus)

CRLF shown as `\r\n`; a lone `\n` means a bare LF (no CR). "Pingora 0.9" = observed behaviour of the
bundled parser; "rdock expected" = required ReverseDock behaviour (reject = 400 + close unless noted).
Each is both an e2e assertion ("smuggling test vectors rejected", roadmap v0.1) and a fuzz seed.

### A. Content-Length / Transfer-Encoding conflicts

1. **Duplicate CL, different values**
   `POST / HTTP/1.1\r\nHost: x\r\nContent-Length: 6\r\nContent-Length: 5\r\n\r\n12345` →
   **reject 400** (RFC 9110 §8.6). *Pingora 0.9: rejects* (`common.rs:398`+`content_length_parse_all`).
2. **Duplicate CL, identical** `…Content-Length: 5\r\nContent-Length: 5\r\n\r\n12345` →
   accept, one body of 5. *Pingora 0.9: accepts & collapses.*
3. **Comma CL list, conflicting** `Content-Length: 5, 6` → **reject 400**. *Pingora: rejects.*
4. **CL with plus sign** `Content-Length: +5` → **reject** (hyper CVE-2021-32715 class). *Pingora:
   rejects* (`from_digits` bars leading sign).
5. **CL hex / non-digit** `Content-Length: 0x5` → **reject**. *Pingora: rejects.*
6. **CL + TE both present**
   `POST / HTTP/1.1\r\nHost: x\r\nContent-Length: 6\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\n` →
   TE wins (CL dropped), connection **not** reused (RFC 9112 §6.1). *Pingora: CL removed, keep-alive
   disabled* (`server.rs:399-435`).
7. **TE: chunked, identity** (non-chunked final) → **reject 400** (RFC 9112 §6.3). *Pingora: rejects
   "non-chunked final Transfer-Encoding".*
8. **TE: identity, chunked** → accept as chunked. *Pingora: accepts.*
9. **TE: xchunked** → **reject** (final token ≠ `chunked`). *Pingora: rejects.*
10. **TE: chunked then second `Transfer-Encoding: cow`** (two TE lines) → **reject** (last line's last
    token ≠ chunked). *Pingora: rejects.*
11. **TE: " chunked" / "CHUNKED" / "\tchunked"** → accept (trimmed, case-insensitive). *Pingora: accepts.*
12. **HTTP/1.0 + TE** `POST / HTTP/1.0\r\nHost: x\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\n` →
    **reject 400** (RUSTSEC-2026-0034). *Pingora: rejects.*

### B. Chunked-body / "funky chunks"

13. **Bare-LF chunk-size terminator** `…chunked\r\n\r\n5\n12345\r\n0\r\n\r\n` → **reject**
    (RFC 9112 §7.1 CRLF required). *Pingora: rejects* (`httparse::parse_chunk_size` needs `\r\n`).
14. **Bare-LF inside chunk-ext (TERM.EXT)** `…chunked\r\n\r\n2;\nxx\r\n45\r\n…` → **reject in strict
    mode** (chunk-ext must not contain controls). *Pingora 0.9: TOLERATES — consumes `;\nxx` as an
    extension (EXT parser); body is re-chunked to upstream so no pass-through smuggle, but rdock strict
    mode should reject.* **rdock value-add.**
15. **Oversized chunk-ext** (ext > 8 KiB) → reject. *Pingora: rejects "Chunk ext over limit"
    (`body.rs:783`).*
16. **Chunk size overflow** `FFFFFFFFFFFFFFFF\r\n` → reject. *Pingora: rejects "chunk size overflows".*
17. **Bad chunk-data terminator** `5\r\n12345XX0\r\n\r\n` (no CRLF after data) → reject. *Pingora:
    rejects* (`validate_crlf`).

### C. Request target / authority

18. **CR/LF/NUL/space in target** `GET /a\r\nb HTTP/1.1…` → reject. *H1: raw CR/LF breaks the request
    line (httparse); a raw space is %-encoded by `escape_illegal_request_line` (normalise, not reject);
    forbidden bytes rejected when writing upstream & on H2 (`client.rs:911`, `v2/server.rs:450`).*
19. **Duplicate Host** `GET / HTTP/1.1\r\nHost: a\r\nHost: b\r\n\r\n` → reject 400. *Pingora: rejects.*
20. **Host-less HTTP/1.1** `GET / HTTP/1.1\r\n\r\n` → **reject 400** (RFC 9112 §3.2). *Pingora 0.9:
    ACCEPTS (gap).* **rdock must reject.**
21. **Userinfo in target/Host** `GET http://u@evil/ HTTP/1.1\r\nHost: evil\r\n\r\n` → reject. *Pingora:
    rejects.*
22. **Absolute-form ≠ Host** `GET http://a/ HTTP/1.1\r\nHost: b\r\n\r\n` → reject. *Pingora: rejects.*
23. **Ambiguous absolute-form** `GET http:\\\\evil/ HTTP/1.1…` / `GET ://evil/ …` → reject. *Pingora:
    rejects (`AmbiguousAuthority`).*

### D. Header syntax / visual spoofing (Kettle 2025)

24. **Space before colon** `GET / HTTP/1.1\r\nHost: x\r\nFoo : bar\r\n\r\n` → reject. *Pingora:
    rejects* (httparse request mode).
25. **Leading space before header name** `GET / HTTP/1.1\r\n Host: x\r\n\r\n` → reject. *Pingora:
    rejects.*
26. **Obs-fold** `GET / HTTP/1.1\r\nHost: x\r\nFoo: a\r\n b\r\n\r\n` → reject. *Pingora: rejects.*
27. **Control / CR / LF in header value** `X: a\rb` or `X: a\nb` → reject. *Pingora: rejects (value
    token class).*
28. **Bare-LF header terminators** `GET / HTTP/1.1\nHost: x\n\n` → **reject in strict mode**. *Pingora:
    ACCEPTS (httparse permits bare LF); re-serialised to upstream with CRLF so no pass-through, but
    strict mode should reject.* **rdock value-add.**

### E. Expect / upgrade / H2

29. **Obfuscated Expect** `GET / HTTP/1.1\r\nHost: x\r\nContent-Length: 6\r\nExpect: y 100-continue\r\n\r\nABCDEF`
    → rdock strict: normalise/strip unknown Expect. *Pingora: does not match it as 100-continue and does
    not strip it (forwards upstream).* **rdock value-add.**
30. **Premature upgrade body** `GET / HTTP/1.1\r\nHost: x\r\nUpgrade: websocket\r\nConnection: Upgrade\r\n\r\nSMUGGLED`
    → bytes after headers must NOT reach upstream before a 101. *Pingora: fixed — only switches after
    101 (RUSTSEC-2026-0033).*
31. **Connection nominates XFF** `GET / HTTP/1.1\r\nHost: x\r\nConnection: keep-alive, X-Forwarded-For\r\nX-Forwarded-For: 1.2.3.4\r\n\r\n`
    → reject (nomination of a protected header). *Pingora: rejects* (RUSTSEC-2026-0390, `proxy_common.rs:95`).
32. **H2 `:authority` ≠ `Host`** (HEADERS with `:authority: a`, `host: b`) → 400. *Pingora: rejects*
    (RUSTSEC-2026-0388).
33. **H2 connection-specific header** (`transfer-encoding`/`connection`/`upgrade`/`keep-alive` field) →
    stream error. *Pingora/`h2`: rejects* (`h2 frame/headers.rs:928`).
34. **H2 `TE` ≠ trailers** → stream error; **`TE: trailers`** → allowed (gRPC). *`h2`: enforces.*
35. **H2 uppercase header name / `:path` with CR/LF** → stream error / 400. *`h2`+Pingora: reject.*
36. **H2 body-flood / header-flood** (CONTINUATION flood, empty DATA, 1-byte HPACK header expansion,
    unbounded streams) → bounded. *Needs `default_h2_options()` (64 KiB header-list, 100 streams) +
    `h2 ≥ 0.4.16`; both satisfied by 0.9.0 config path.*

### F. Connection reuse / draining

37. **Undrained body before keep-alive reuse** (pipelined second request on a reused conn) → body
    drained, no cross-request bleed. *Pingora: drains (`reuse()` `server.rs:1449`); pipelining off by
    default (RUSTSEC-2025-0037).*
38. **Slowloris** (dribble header bytes, 1 byte per <60 s) → rdock must abort at the 10 s header

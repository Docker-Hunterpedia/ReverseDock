# v0.3 research: automatic HTTPS

Research note for milestone **v0.3 "Automatic HTTPS"**. Requirements in scope: B-TLS-02…08, B-TLS-12, B-TLS-13, W-CF-01…05, W-DNS-01, W-PLAT-04. Every fact was checked on 2026-10-28 against the source linked next to it. The decisions that follow from it are in [ADR-0020](../decisions/0020-automatic-https.md).

## 1. ACME client library

| Crate | Version | Verdict |
|---|---|---|
| [instant-acme](https://crates.io/crates/instant-acme) | 0.8.5 (2026-02-24), MSRV 1.70 | **Use.** RFC 8555 with ARI (`Account::renewal_info`, `NewOrder::replaces`), profiles (`NewOrder::profile`, `Account::profiles`), EAB (`ExternalAccountKey`), HTTP-01, DNS-01 and TLS-ALPN-01 key authorizations, serializable account credentials. Maintained by a rustls maintainer; HTTP through hyper-rustls. |
| [rustls-acme](https://docs.rs/rustls-acme) | 0.15.4 | No: TLS-ALPN-01 and HTTP-01 only, no DNS-01, no ARI or profiles, owns the accept stream and resolver, pins rcgen 0.13. |
| [tokio-rustls-acme](https://crates.io/crates/tokio-rustls-acme) | 0.9.1 | No: same design as rustls-acme, pulls reqwest and axum-server. |
| [acme2-eab](https://crates.io/crates/acme2-eab), acme-lib, acme-micro | — | No: OpenSSL, synchronous or unmaintained. |

instant-acme's default features are `aws-lc-rs` and `hyper-rustls`, and aws-lc-rs wins when both backends are enabled ([README](https://github.com/djc/instant-acme)). ReverseDock uses ring ([ADR-0013](../decisions/0013-tls-crypto-provider-ring.md)), so the dependency is `default-features = false, features = ["ring", "hyper-rustls", "time", "x509-parser"]`. Account keys are P-256 only; the certificate key is ours, because `Order::finalize_csr` takes any CSR. instant-acme 0.9.0 (MSRV 1.88) is unreleased on `main`; we start on 0.8.5.

[rcgen](https://crates.io/crates/rcgen) 0.14.10 (already a workspace dependency, ring feature) builds the CSR, the TLS-ALPN-01 validation certificate (`CustomExtension::new_acme_identifier`, OID 1.3.6.1.5.5.7.1.31; we set it critical as RFC 8737 requires) and the local CA. [hickory-resolver](https://crates.io/crates/hickory-resolver) 0.26.3 (MSRV 1.88, ring features) can check DNS-01 records at the authoritative nameservers.

## 2. Let's Encrypt in 2026

- **Profiles** ([profiles](https://letsencrypt.org/docs/profiles/)): `classic` 90 days, up to 100 names, 30-day authorization reuse; `tlsserver` 45 days, 25 names, 7-hour reuse, no Common Name; `shortlived` 160 hours, 25 names, IP addresses allowed. `tlsclient` was retired on 2026-07-08.
- **Shorter lifetimes** ([From 90 to 45](https://letsencrypt.org/2025/12/02/from-90-to-45)): `classic` becomes 64 days with 10-day reuse on 2027-02-10, and 45 days with 7-hour reuse on 2028-02-16. Staging changes about a month earlier. A fixed "renew 30 days before expiry" breaks; renewal must follow ARI, or a fraction of the lifetime.
- **IP-address and 6-day certificates** are generally available since 2026-01-15, with `shortlived` and HTTP-01 or TLS-ALPN-01 ([announcement](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability)).
- **OCSP is gone** ([ending OCSP](https://letsencrypt.org/2024/12/05/ending-ocsp)): certificates carry no OCSP URL since 2025-05-07, Must-Staple orders fail, and responders were turned off on 2025-08-06. Stapling only matters for other CAs.
- **ARI** is in production since 2023 ([upcoming features](https://letsencrypt.org/upcoming-features/)). Renewals sent with `replaces` inside the ARI window are exempt from all rate limits.
- **Rate limits** ([rate limits](https://letsencrypt.org/docs/rate-limits/)): 300 new orders per account per 3 hours; 50 certificates per registered domain per 7 days; 5 duplicate certificates per 7 days; 5 failed authorizations per name per account per hour; issuance for a name pauses after 1,152 consecutive failures. Staging (`https://acme-staging-v02.api.letsencrypt.org/directory`) has much higher limits and untrusted roots ([staging](https://letsencrypt.org/docs/staging-environment/)).
- **Expiry emails** ended on 2025-06-04 ([announcement](https://letsencrypt.org/2025/01/22/ending-expiration-emails/)); clients must warn about expiry themselves.
- **Profile choice** ([profiles](https://letsencrypt.org/docs/profiles/)): `classic` for those "happy to let others try new things first", `tlsserver` for those who "fully embrace automation", `shortlived` "not for everyone"; the directory's list is canonical.
- **DNS-PERSIST-01** was announced on 2026-02-18 ([announcement](https://letsencrypt.org/2026/02/18/dns-persist-01)); we found no production launch. Not in v0.3.
- **Profiles draft**: `draft-ietf-acme-profiles-02` (2026-08-28), not an RFC yet ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-acme-profiles/)).

## 3. Protocol details

- **ARI** ([RFC 9773](https://www.rfc-editor.org/rfc/rfc9773.html)): certID is `base64url(AKI keyIdentifier) "." base64url(serial)`; an unauthenticated GET returns `suggestedWindow {start, end}` and `Retry-After`. Pick a uniform random time in the window; renew at once if it has passed; poll again after Retry-After clamped to 1 minute … 1 day (6 hours when missing); exponential backoff on errors. Send `replaces` only when the directory has `renewalInfo`; `alreadyReplaced` (409) means another order already replaced it.
- **TLS-ALPN-01** ([RFC 8737](https://www.rfc-editor.org/rfc/rfc8737.html)): port 443, ALPN exactly `acme-tls/1`, SNI the name being validated; a self-signed certificate with one dNSName and the critical acmeIdentifier extension holding SHA-256 of the key authorization; no application data. It cannot validate wildcards.
- **HTTP-01**: `http://<name>/.well-known/acme-challenge/<token>` on **port 80 only**; up to 10 redirects are followed; IP addresses yes, wildcards no ([challenge types](https://letsencrypt.org/docs/challenge-types/)).
- **DNS-01**: TXT at `_acme-challenge.<name>`; required for wildcards; CNAME delegation of `_acme-challenge` is allowed; IP addresses no (same source).

## 4. Test CA

[Pebble](https://github.com/letsencrypt/pebble) v2.10.1 (2026-04-20), images `ghcr.io/letsencrypt/pebble` and `ghcr.io/letsencrypt/pebble-challtestsrv`. ACME on :14000 (`/dir`), management on :15000 (`/roots/0`, regenerated on every start). It validates HTTP-01 on :5002 and TLS-ALPN-01 on :5001 by default (both configurable). CI settings: `PEBBLE_VA_NOSLEEP=1`, `PEBBLE_WFE_NONCEREJECT=0` (default 5 % `badNonce`, which the client must otherwise retry). It supports ARI (including `alreadyReplaced`), profiles and an EAB-required mode from its config file. `pebble-challtestsrv` mocks DNS (`POST /set-txt`, `/clear-txt` on :8055, DNS on :8053) for DNS-01 and wildcard tests.

## 5. Cloudflare

- **IP ranges** ([ips](https://www.cloudflare.com/ips/)): `GET https://api.cloudflare.com/client/v4/ips` returns `ipv4_cidrs`, `ipv6_cidrs` and an `etag`; the plain lists are at `/ips-v4/` and `/ips-v6/`. There is no fixed change schedule (last change 2023-09-28): fetch periodically and ship a built-in copy.
- **Client IP** ([HTTP headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/)): `CF-Connecting-IP` is the single visitor address; `True-Client-IP` is the same value under another name (Enterprise); `X-Forwarded-For` is appended to. Trust these only from a peer inside Cloudflare's ranges. `CF-Ray` identifies the request.
- **DNS API** ([create DNS record](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/)): `POST /zones/{zone_id}/dns_records` with `{type: "TXT", name, content, ttl}`; permission DNS Write (dashboard: Zone → DNS → Edit); the zone ID from `GET /zones?name=` needs Zone Read.
- **Origin CA** ([Origin CA](https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/)): trusted only by Cloudflare, for proxied records with Full (strict); validity 7 days to 15 years; up to 200 names, no IP addresses.
- **Authenticated Origin Pulls** ([AOP](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/)): client certificates from Cloudflare to the origin; needs mTLS (M-TLS-01, v0.4), so W-CF-08 stays in v0.4.
- **Tunnel** ([run parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/run-parameters/)): image `cloudflare/cloudflared`, `tunnel --no-autoupdate run` with `TUNNEL_TOKEN`; ingress rules end with a catch-all ([configuration file](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/configuration-file/)). No inbound ports, so ACME HTTP-01/TLS-ALPN-01 cannot reach the origin; Tunnel setups use Cloudflare's edge certificate and plain HTTP or DNS-01 behind it.

## 6. How others do it

- **Caddy** ([automatic HTTPS](https://caddyserver.com/docs/automatic-https)): one certificate per name; HTTP-01 and TLS-ALPN-01 on by default; on failure it retries once, then switches challenge, then issuer, and for Let's Encrypt retries against staging "to avoid rate limit concerns"; then it backs off up to a day; renews at ⅓ remaining lifetime or by ARI; a local CA (10-year root, short-lived leaves) for `localhost` and internal names, installed with `caddy trust`; file locks in its storage so instances can share it.
- **Traefik** ([ACME resolver](https://doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/)): named resolvers, one `acme.json` per resolver (mode 0600), RSA 4096 by default, renews 30 days before expiry unless `certificatesDuration` is set, DNS through lego. We found no ARI support in its documentation.

## 7. Local CA trust

No mature crate installs a root into OS trust stores (`os-truststore` 0.0.2 and `koi-truststore` 0.4.1 are too new). mkcert shells out ([mkcert](https://github.com/FiloSottile/mkcert)): `security add-trusted-cert -d -k /Library/Keychains/System.keychain` on macOS; on Linux the anchors directory plus `update-ca-trust extract`, `update-ca-certificates` or `trust extract-compat`, whichever exists; NSS (Firefox) with `certutil -A`. `rdock trust` does the same; on Windows it prints the `certutil -addstore ROOT` command instead of using the Win32 API (`unsafe_code` is forbidden).

## 8. Open points for the implementation

The validation handshake must close without serving HTTP.

# v0.8 research: cache and extensibility

Research note for milestone **v0.8 "Cache and extensibility"**. Requirements in scope: F-WEB-03 (HTTP cache), F-EXT-01…05 (phased pipeline, native plugins, WASM, agents, SDK and signatures), F-GW-01…05 (API keys and OIDC, per-consumer limits, request validation, error envelope and transformation, metering), W-CF-06 (Cloudflare Access), M-L4-04 (UDP, and with it Gateway API `UDPRoute`, left open in v0.7), M-TM-05 (buffering), F-WEB-02 (directory listing), F-MGMT-02 (Terraform/OpenTofu provider) and W-OBS-02 (Vault and External Secrets). Every fact was checked on 2026-11-11 against the source linked next to it; crate facts against crates.io, the published sources and probe crates built on the repository's own lockfile. Lines marked *(our reasoning)* are conclusions, not sources; lines marked *unverified* were not confirmed against a primary source. Sections 2 to 5 were researched one topic at a time and read together for section 6. The decision is [ADR-0030](../decisions/0030-v0-8-cache-extensibility-gateway.md).

## 1. Where we start

- The milestone is five milestones' worth of surface: a cache, an extension model, API-gateway features, UDP and three smaller items. The roadmap's "done when" names four proofs: cache conformance against an RFC 9111 test-suite subset, a stampede test with a single origin fetch, a plugin SDK with two example plugins, and a WAF agent example with a CRS-compatible engine.
- Nothing of the cache exists: no code, no model placeholder, no gate entry. `pingora-cache` 0.9.0 is already compiled into every build because `pingora-proxy` depends on it.
- The `Middleware` trait has two phases, `request` and `response`, and no body phase; `forward_auth` is the only out-of-process call. The model and the gate have no `plugin`, `wasm` or `agent`.
- Status-code retries already ship ([ADR-0015](../decisions/0015-status-code-retries.md) superseded ADR-0010); the roadmap line "status-code retries if the upstream Pingora hook landed" is stale.
- Pingora 0.9.1 (2026-11-03) removes the zero-capacity `BufStream` panic that pins tokio below 1.54 in `Cargo.toml`; `pingora-proxy` is unchanged, so the 64 KiB request-body replay limit stays. The hook that buffers a request body before a backend is chosen is merged upstream but not released.
- `ListenerProtocol::Udp` parses and is refused as "planned for v0.8"; there is no UDP route or service in the model. The Kubernetes provider refuses `UDPRoute` and creates TCP Service ports only.
- `static.listing` parses and is refused as "planned for v0.8".
- The admin API already has per-object endpoints with mandatory `If-Match`, tokens with roles and a generated Go client: what a Terraform provider needs.
- Secrets are references (`${file:…}`, `${env:…}`, [ADR-0016](../decisions/0016-config-references-and-secrets.md)); the Kubernetes provider reads native Secrets.

## 2. The HTTP cache (F-WEB-03)

Research note for milestone **v0.8 "Cache and extensibility"**, topic A. Requirement in scope: **F-WEB-03** ("HTTP cache: memory + disk, RFC 9111, `Vary`, SWR/SIE, purge API (URL/tag), coalescing"). Roadmap "done when": "cache conformance against an RFC 9111 test-suite subset; stampede test shows a single origin fetch". Every fact was checked on 2026-11-11 against the source linked next to it; Pingora facts against the published 0.9.0 crate sources in the Cargo registry (file and line given) and a probe crate built on the repository's own lockfile with Rust 1.89. Lines marked *(our reasoning)* are conclusions, not sources; lines marked *unverified* were not confirmed against a primary source today.

Shorthand for sources: **pc** = `pingora-cache-0.9.0/src/` ([docs.rs source](https://docs.rs/crate/pingora-cache/0.9.0/source/src/)), **pp** = `pingora-proxy-0.9.0/src/` ([docs.rs source](https://docs.rs/crate/pingora-proxy/0.9.0/source/src/)); RFC links go to the section.

### 1. Where we start

- **No cache code exists.** There is no `rdock-cache` crate (`crates/` has 16 crates, none for the cache), no `cache` middleware variant in `crates/rdock-model/src/middleware.rs`, no gate entry for it in `crates/rdock-proxy/src/gate.rs` (the only "planned for v0.8" gates are UDP listeners and directory listing), and the access log has no `cache_status` field although `docs/05-architecture.md` §8 lists one. Every `cache` match in `crates/` is something else (DNS/JWKS/OAuth caches, `Cache-Control: no-store` on built-in answers, `static.cache_control`).
- The plan on paper: `docs/05-architecture.md` line 61 (`rdock-cache (P2) HTTP cache on pingora-cache: memory + disk storage, purge, SWR/SIE`), §6 hook table (`response_cache_filter` / cache hooks: "Cache track (P2)"), §8 (`cache` listed as a built-in middleware, P2), §19 ("Built on `pingora-cache` pinned to the Pingora version in use; storage: `pingora-memory-cache` (memory tier) + our disk `Storage` impl (segmented files, size quota, LRU eviction, crash-safe index)"; purge by URL and by tag (`Cache-Tag`)), `docs/06-repo-layout.md` line 109 (Cargo feature `cache`, "off until v0.8"), roadmap out-of-band track "Cache (depends on `pingora-cache` API stability; we pin and adapt)".
- **`pingora-cache 0.9.0` is already in `Cargo.lock` and already compiled**: `pingora-proxy` depends on it unconditionally, and `deny.toml` already carries an ignore for it (`RUSTSEC-2026-0391`, zstd 0.13 via `pingora-header-serde (pingora-cache)`). The Cargo feature `cache` therefore adds no third-party crate; it only adds our own code. *(our reasoning)* The "opt-in build" in architecture principle 3 buys nothing in dependency terms; the decision is only whether our cache crate is in the default binary.
- **What a cache must compose with** (`crates/rdock-proxy/src/proxy.rs`, `crates/rdock-middleware/src/`):
  - `request_filter` runs everything before Pingora's cache phase: path normalisation (`rdock_rules::path::normalize`, the forwarded path is rewritten), route match, `forwarded::apply` (the `X-Forwarded-*` set is rebuilt from the trusted-proxy decision), `x-request-id`, then every middleware's `request` phase (auth, `ip_allow`, `rate_limit`, `forward_auth`, rewrites). Pingora calls `proxy_cache` only after `request_filter` returns `false` (pp `lib.rs:1189`, `:1216`). *(our reasoning)* So access control always precedes a cache hit, and the cache sees the request as it will be sent upstream (after rewrites). Both are what we want; no `Middleware::request` may answer from the cache itself.
  - `upstream_response_filter` (strip hop-by-hop, passive health, status retries) runs **before** the response is offered to the cache, and `response_filter`/`response_body_filter` run after, on misses and on hits (pp `proxy_h1.rs:869-883` "cache the original response before any downstream transformation"; pp `proxy_cache.rs:337`, `:472`). *(our reasoning)* The store therefore holds the origin representation without hop-by-hop fields (RFC 9111 §3.1 allows exactly that) and before `compress`, `headers`, `cors`, error pages and the bandwidth throttle. One stored object serves every `Accept-Encoding`; `compress` keeps adding `Vary: Accept-Encoding` for downstream caches and weakening the ETag (`compress.rs:271-307`).
  - On a hit Pingora evaluates the client's conditionals and `Range` **before** `response_filter` (pp `proxy_cache.rs:308-337`): a 304 or 206 reaches our middlewares already formed. `compress` already skips 206 and HEAD (`compress.rs:1-6`), and a client holding our weak `W/"…"` tag still gets a 304 because `If-None-Match` uses weak comparison ([RFC 9110 §13.1.2](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.2)). *(our reasoning)* `If-Range` with that weak tag fails and yields a full 200, which is correct.
  - The `static` middleware answers from `request` with its own validators, ranges and `Cache-Control` (`static_files/answer.rs`: `preconditions`, `if_range_holds`, `select_ranges`); it never reaches the upstream path, so the proxy cache never sees it. *(our reasoning)* Its RFC 9110 precondition and range code is the house reference for behaviour, but Pingora brings its own for cache hits (§2.5), so nothing is shared.
  - `Reply` answers (middleware short-circuits, `respond` services, `fail_to_proxy` pages) are written by `self.reply` and never pass the cache hooks; they are never stored.

#### 2.6 Consequences for our design *(our reasoning)*

- **We pin and wrap.** Three breaking cache changes in one minor release (0.8 → 0.9) confirm the roadmap's "we pin and adapt". All `pingora::cache` types stay inside `rdock-cache`; `rdock-proxy` sees only our own small interface (enable, key, decide, vary, hit filter, purge), so a Pingora bump touches one crate.
- **`'static` everywhere versus hot reload.** Stores must outlive every request and cannot be dropped. A cache is therefore a named, process-lifetime object created once (`Box::leak` behind a registry keyed by store name; no `unsafe`), and a configuration reload may change policy (TTL, key, bypass) but must reuse the same store instance; changing a store's path or size needs a restart, or leaks one generation, which we refuse with a diagnostic. This also fits ADR-0009: the store is data-plane state, not provider state.
- **The cache is not a `Middleware`.** The `Middleware` trait has two header-only phases; caching needs the Pingora hook set and body access. The `cache` entry in a route's middleware list is configuration that `rdock-proxy` compiles into a per-route cache policy; its position in the list does not matter, because Pingora fixes the order (after all request middlewares, before all response middlewares).
- **Policy is ours to write.** pingora-cache gives mechanism (state machine, lock, vary slots, range, 304 merge) but `response_cache_filter`, `cache_hit_filter`, `cache_vary_filter`, the key, and all RFC rules beyond `Cache-Control` freshness are the embedder's job (§3 marks each).
- **SWR runs our whole pipeline again.** The background subrequest re-enters `early_request_filter` and `request_filter` with a fresh `RequestCtx`: route match, middlewares, access log, metrics, rate limits and `forward_auth` all run a second time for a request no client is waiting on. We must detect `session.subrequest_ctx` and skip counting, limiting, mirroring and auth side effects for it, and decide what the access log shows. This is the largest integration risk and the reason SWR is its own step in §8.
- **Status retries and the cache.** `upstream_response_filter` turns a retryable status into an error before the cache sees it, so a retried 503 is never stored; good.

*(our reasoning)* Configuration shape and defaults, following "every option, safe by default":

- **Off by default, per route.** Every product above ships the cache off. A `cache` middleware on a route turns it on and names a store; stores are declared once at top level (`caches: { name: { memory: { max_size }, disk: { path, max_size, min_free } , max_object_size } }`).
- **No default TTL.** With nothing configured we store only what the origin marks cacheable (`s-maxage`, `max-age`, `Expires`, `public` with a validator is not enough) — the nginx/HAProxy/Caddy-`strict` line, and the one cache-tests assumes (`freshness-none`). `default_ttl` per status exists as an option (nginx `proxy_cache_valid`, Varnish 120 s, Cloudflare's table) and is where heuristically cacheable statuses come in; heuristic freshness (10 % of `Last-Modified` age) is a separate option, off.
- **Never stored, no option to force in v0.8**: responses with `Set-Cookie`; `Vary: *`; `private`, `no-store`; requests with `Authorization` unless the response has `public`, `s-maxage` or `must-revalidate`; non-GET/HEAD; requests with a body (fat GET, §7); upgrades, gRPC, SSE; responses over `max_object_size`. nginx's `proxy_ignore_headers` and Varnish VCL allow overriding the first three; that is exactly the "unsafe combination" principle 10 refuses, so if it is ever offered it is a named, per-field, diagnosed opt-in (for example `ignore: [set-cookie]` rejected unless `strip_set_cookie: true`), not in the first release.
- **Request cookies**: Varnish passes any request with `Cookie`; nginx and Cloudflare do not look. Default: cache regardless of request cookies only when the origin said the response is cacheable (it is then the origin's statement that the response does not depend on the cookie); offer `bypass.cookies: [name…]` and `bypass.headers` for sites that need the Varnish behaviour. A route that has an authentication middleware (`basic_auth`, `jwt`, `forward_auth`, mTLS identity) and a cache gets a validation **error** unless the cache declares `shared_across_users: true` or keys on the identity; that is the combination that leaks.
- **Key** (fixed part, not configurable away): store name, route's service name (tenant boundary, §7), upstream scheme, `Host` as sent upstream, method class (GET; HEAD shares it), path exactly as forwarded, raw query string. Options: `query: all | ignore: [utm_*] | only: [a, b]`, `sort_query` (off), `headers: [name…]` (adds to the key, like Cloudflare's list), `cookies: [name…]`. Length-prefixed framing as `CacheKey::new` asks. No lower-casing or decoding of the path beyond what `rdock_rules::path::normalize` already forwards, so key and upstream request never disagree (§7).
- **Request directives**: default `honor_request_directives: false` for `no-cache`/`max-age=0` (any client could otherwise force origin fetches; nginx ignores them, Varnish's built-in VCL ignores them), `only-if-cached` honoured (cheap, safe), `max-stale` ignored. An option turns the RFC behaviour on; the conformance run uses it and says so.
- **Stale**: honour the origin's `stale-while-revalidate` and `stale-if-error` by default (they are explicit origin permission, RFC 5861); `stale_if_error` and `stale_while_revalidate` route overrides as upper bounds or defaults when absent; never when `must-revalidate`/`proxy-revalidate`/`s-maxage` forbid it.
- **Coalescing on by default** (nginx has it off; Varnish and the roadmap's stampede criterion want it on): `lock.age_timeout` 5 s, `lock.wait_timeout` 5 s (nginx's two defaults), `lock.max_retries` 2 (Pingora's).
- **Tags**: accept both `Cache-Tag` (comma-separated, case-insensitive) and `Surrogate-Key` (space-separated) on responses, configurable list of header names, strip them from client responses by default (Cloudflare and Fastly both do), limits 1,024 bytes per tag and 16 KB per header.
- **Purge** only through the admin API (`POST /api/v1/cache/{store}/purge` with `{ "urls": [...] }`, `{ "tags": [...] }`, `{ "prefix": ... }`, `{ "everything": true }`, `soft: true` mapping to `PurgeAction::Expire`), never a `PURGE` method on the data listeners by default; a data-plane `PURGE` is an option that requires an `ip_allow` on the same route (the Varnish ACL pattern) and fails validation without one.
- **Observability**: `Cache-Status: rdock; hit` / `; fwd=miss|stale|bypass|…; stored; collapsed; ttl=` (RFC 9211, on by default, option to hide), `cache_status` in the access log, `rdock_cache_requests_total{route,status}`, `rdock_cache_bytes`, `rdock_cache_objects`, `rdock_cache_evictions_total`, `rdock_cache_lock_wait_seconds`.

### 6. Disk store, memory tier and the stampede test *(our reasoning grounded in §2)*

**What the `Storage` contract fixes.** `get_miss_handler(key, meta)` hands us the serialised meta (`CacheMeta::serialize()` → two byte vectors) before the first body byte; `write_body` delivers chunks; `finish` must return the size and make the object visible atomically; dropping the handler means failure. `lookup` returns the meta plus a reader that should `seek(start, end)` so Pingora serves ranges from the store. `update_meta` rewrites meta without touching the body (304). `purge` gets either a logical key or an exact entry and is also how eviction removes objects. `EvictionManager::admit` only returns victims; `save`/`load` persist the LRU. `hash` is BLAKE2b-128, stable across machines and restarts, 32 hex digits.

**Layout options.**

| Option | For | Against |
|---|---|---|
| **A. One file per object**, `<root>/<ab>/<cd>/<32-hex combined key>`, fixed header (magic, format version, lengths, checksum of the meta block) + meta internal + meta header + body | nginx's and Pingap's model, proven; atomic by `rename`; `seek` is `pread` at `body_offset + start`; `sendfile`-friendly later; crash recovery = directory walk; trivially inspectable; no compaction | one inode and two directory entries per object; small objects waste a block; `update_meta` rewrites the head of the file or needs a sidecar |
| **B. Meta sidecar** (`<key>.meta` + `<key>.body`) | 304 refresh rewrites a tiny file atomically; body never rewritten | two inodes per object; two renames are not atomic together (need a commit order: body first, meta last, meta is the commit record) |
| **C. Segmented log / slab** (what architecture §19 says: "segmented files … crash-safe index") | few inodes, sequential writes, good for many small objects | needs our own index, compaction, free-space map and recovery; deletes are tombstones; ranges and streaming readers over a moving log are hard; far more to fuzz. This is a storage engine |

Recommendation: **A with the meta in a fixed-size-prefixed head, plus B's trick for refresh**: the file is `[header][meta][body]`; a 304 refresh writes a new small `<key>.m<generation>` file that supersedes the embedded meta (highest generation wins; folded back on the next full store or by the cleaner). Architecture §19's "segmented files" should be amended by the ADR: option C is not justified for v0.8.

**Writes.** Create `tmp/<random>` inside the same store root (same filesystem), write head and body through a buffered writer on the blocking pool (`tokio::fs` or `spawn_blocking`; the hooks are async already), on `finish` write the final lengths, then `rename` into place. `O_TMPFILE` + `linkat` would avoid visible temp files but is Linux-only and needs a raw syscall path that `unsafe_code = "forbid"` and cap-std do not give us (*unverified*: whether `cap-std 4.0.3`/`rustix` exposes it safely); a `tmp/` directory emptied at start is equivalent in effect. **fsync policy**: none by default — a cache may lose objects on power failure, it must not serve corrupt ones; the header checksum over the meta and the recorded body length (object rejected if the file is shorter) give that. `fsync: on_store` as an option for people who want warm restarts after crashes.

**cap-std.** Already a workspace dependency (`cap-std = "4.0.3"`, used by `rdock-middleware` for `static`). Open the store root once as a `cap_std::fs::Dir` and do every open/rename/remove relative to it: file names are derived from hashes only, but this makes "a cache key can never escape the store directory" structural rather than argued.

**Start-up and accounting.** Walk the root in a background task (nginx's "cache loader"; Pingap walks to size its budget): validate each header cheaply, register the object with the eviction manager through `access`/`admit` with its size, delete temp files and unreadable or wrong-version objects. Requests during the walk work normally (a lookup just opens the file; `get_eviction_weight` lets a hit register an untracked object). Use `EvictionManager::save/load` on graceful shutdown/start to keep LRU order; the walk remains the source of truth. Caps: `max_size` (bytes, by file length rounded to block size), `min_free` (statvfs), `max_objects` (inode guard), `max_object_size` (`set_max_file_size_bytes`), plus an `inactive` sweep. Eviction manager: `eviction::lru::Manager` (sharded, serialisable) for disk.

**Streaming while writing.** With `support_streaming_partial_write() == false` (Pingap's choice) the client that caused the miss still streams normally from upstream while the store is written, but **waiting readers get nothing until `finish`** and then read the file; for a large or slow object they wait up to the lock timeouts and then go to the origin uncached. Supporting partial reads means a shared in-memory write state per in-flight object (bytes written, a `watch` channel, the temp file opened by readers), as `MemCache` does with `TempObject`. Recommendation: ship v0.8 with `false`, document the lock timeouts as the bound, and add partial reads as a follow-up once the conformance and stampede gates hold.

**Memory tier.** Not `pingora-memory-cache`/TinyUFO as architecture §19 says (they do not implement `Storage`, §2.2). Options: (1) our own `Storage` holding `Bytes` in a sharded map with `eviction::lru::Manager` for weight accounting — small, and what "memory" in F-WEB-03 needs; (2) a tiered `Storage` that fronts the disk store with (1) for objects under a size threshold, promoting on hit (Pingap's shape, with TinyUFO as the hot index). v0.8: (1) and the disk store as two store kinds; (2) later, because the OS page cache already makes hot disk objects cheap to read. S3-FIFO/TinyLFU admission can come through `AdmissionPolicy` (min-uses style, like nginx `proxy_cache_min_uses`) without changing storage.

**Tags.** pingora-cache has no tag concept; `revalidate_merge_header` merely preserves `cache-tag`. We keep a tag index beside the store: tag → set of combined keys, in memory, rebuilt by the start-up walk from the stored headers, updated on store and purge. Purge by tag = `storage.purge(PurgeTarget::…, Invalidation)` for each key plus `eviction.remove`. Soft purge = `expire`. Purge by prefix or "everything" walks the index. The admin API calls a handle on the store; the data plane never calls the admin (ADR-0009, ADR-0012).

**What must be fuzzed** (`tests/fuzz`, outside the workspace): the on-disk header and meta decoder (arbitrary bytes must be rejected, never panic or over-allocate; `CacheMeta::deserialize` is Pingora's MessagePack + zstd, so it gets arbitrary input through us), the key framing (two different component tuples never frame to the same bytes), `Vary` parsing and variance building (names with odd case, `*`, duplicates, empty items), the `Cache-Tag`/`Surrogate-Key` parser, the response-policy function (`response_cache_filter` as a pure function of request and response headers: never "cacheable" when `Set-Cookie`, `private`, `no-store` or `Vary: *` is present — a property test, not only a fuzz target), and the `Cache-Control`/`Age` number parsing we add on top of Pingora's.

**The stampede test** (roadmap criterion), in `rdock-testkit` style:

1. Backend with a counter and a configurable delay answers `Cache-Control: max-age=60`. Fire N = 200 concurrent GETs for one cold key through `rdock`. Assert: backend counter == 1; all 200 answers are 200 with the same body; exactly one `Cache-Status` says `fwd=miss; stored`, the rest `hit` (or `collapsed`); `rdock_cache_lock_wait_seconds` has 199 observations. Run for the memory and the disk store, HTTP/1.1 and HTTP/2 clients.
2. Expiry stampede: let the object go stale, fire N again. Without SWR: one conditional request (`If-None-Match`), counter +1. With SWR: all N served stale immediately, one background revalidation.
3. Uncacheable origin (`no-store`): the writer releases with `GiveUp`, **all waiters go to the origin** (N fetches). This is by design in Pingora and RFC 9111 §4 ("it will need to forward the requests"); the test asserts that all N succeed, and that the predictor makes the **next** burst skip the lock entirely (no added latency). Document it.
4. Origin fails (connection reset or 502): `TransientError` elects a new writer; each waiter retries at most `max_lock_retries` (2) times, then goes uncached. Assert every client gets an answer (the origin's error or, with a stale object and SIE, the stale one) and that origin fetches are bounded by N, never unbounded retries.
5. Slow origin beyond `lock.age_timeout`: waiters re-compete (`AgeTimeout`); beyond `lock.wait_timeout` they go to the origin uncached (`WaitTimeout`). Assert the bound: fetches ≤ 1 + ceil(duration / age_timeout) writers plus timed-out waiters, and no request waits longer than `wait_timeout` + origin time.
6. Writer's client disconnects mid-body: the fill must either complete (Pingora 0.9.0 added "cancel-safe body and header writer primitives … to prevent stalled cache misses from applying backpressure") or release the lock so a waiter takes over; assert no waiter hangs to the timeout. *unverified* which of the two 0.9.0 does; the test decides.

*(our reasoning)* What this means for us:

- **Unkeyed headers.** `forwarded::apply` already replaces the `X-Forwarded-*` family from the trusted-proxy decision for every request, so an untrusted client cannot inject `X-Forwarded-Host`/`-Proto`. That leaves the override family (`X-Original-URL`, `X-Rewrite-URL`, `X-HTTP-Method-Override`, `X-Http-Method`, `X-Method-Override`, `X-Host`, `X-Forwarded-Server`, `Forwarded` when not rebuilt): on a cached route we **strip them from the upstream request by default** (option: `key.headers` to key on one instead). Stripping changes behaviour only for cached routes and is the "rewrite the request, not the key" rule. When the peer is a trusted proxy, the forwarded values it supplies are part of the key if they differ from the connection's own (scheme at least).
- **Fat GET**: a GET or HEAD with a body (`Content-Length > 0` or `Transfer-Encoding`) never uses or fills the cache.
- **Normalisation mismatches**: the key uses the path bytes exactly as forwarded upstream after `rdock_rules::path::normalize` and the route's rewrites, and the raw query string. One representation for both; no second, cache-only normalisation. `sort_query` and `query.ignore` are opt-in and documented with the entanglement caveat (ignored parameters are still sent upstream, so a reflected `utm_content` becomes poisonable: when a parameter is ignored in the key we **remove it from the upstream request** as well, or refuse the option).
- **Deception**: we have no "cache by extension" rule and no forced TTL in v0.8; with no default TTL a personalised page is stored only if the origin itself says `max-age`/`public`, which is the origin's bug, not a rule of ours overriding `Cache-Control`. When `default_ttl` is configured it applies only to responses **without** `Cache-Control`/`Expires`, never over `private`/`no-store`, and never to responses with `Set-Cookie`. An optional `content_type_guard` (Cloudflare's check) can come later.
- **Tenant isolation**: the key includes the store name and the service the route resolves to, and the `Host` sent upstream. Two routes that share a store but point at different services can never read each other's entries, even with the same host and path; two providers' objects (`name@provider`) differ by service name. `user_tag` carries the route for per-route accounting. Stores are not shared across namespaces by the Kubernetes provider unless configured.
- **Authenticated content**: §5 (validation error for auth middleware + cache without an explicit statement). `Authorization` handling per RFC 9111 §3.5. Client-certificate identity headers added by `client_cert` count as identity.
- **Purge authorisation**: purge lives on the admin API behind its existing users, tokens, roles and audit log (`crates/rdock-admin`: `auth.rs`, `tokens.rs`, `guard.rs`, `audit.rs`); a purge is a mutating call (operator role, audited with the selector, rate-limited because "purge everything" is a self-inflicted origin stampede). No unauthenticated `PURGE` on data listeners.
- **Header injection through stored headers**: stored headers come from `ResponseHeader` values that already passed Pingora's HTTP parser, and the hit path rebuilds a `ResponseHeader`; the risk is our own decoder accepting a crafted file. The store directory must be owned by the `rdock` user with mode 0700, objects carry a format version and checksum, and the decoder is fuzzed (§6). Anyone who can write the directory can serve arbitrary content; say so in the docs.
- **Leakage**: never store `Set-Cookie`, `Proxy-Authenticate`, `Proxy-Authentication-Info`; strip `Cache-Tag`/`Surrogate-Key` on the way out; `Cache-Status` `key` parameter off by default (it would disclose key structure); the access log records the cache status, not the key. Disk objects are plaintext: document it, and do not cache routes marked sensitive.
- **Resource exhaustion**: unbounded `Vary` cardinality (cap variants per primary key, as HAProxy's `max-secondary-entries` 10), unbounded query strings as keys (cap key length; over the cap ⇒ bypass), `max_object_size`, `min_free`.

### 8. Proposed scope *(our reasoning)*

### 1. Where we start

- **The trait has two phases.** `rdock_middleware::Middleware` (`crates/rdock-middleware/src/lib.rs`) has `async fn request(&self, &mut RequestHeader, &mut Context) -> Flow` and `async fn response(&self, &mut ResponseHeader, &mut Context)`, plus two special hooks (`translates_grpc_web`, `error_page`). `Flow` is `Next | Reply(Reply)`; a `Reply` is a status, headers and an optional body (`Bytes` in memory, or `File` ranges for `static`). There is no `upstream_request`, `request_body`, `response_body` or `log` phase in the trait.
- **Body work is not pluggable.** Response bodies are changed only by the proxy itself, through fields a middleware sets on `Context`: `compression` (streaming encoder), `replace_body` (error pages), `throttle` (`bandwidth`). `request_body_filter` in `crates/rdock-proxy/src/proxy.rs` only counts bytes for `max_body_bytes` and copies up to 64 KiB for a mirror (`MIRROR_BODY`).
- **Ordering is the route's list.** `compile.rs` builds every configured middleware once (`rdock_middleware::build`, a `match` over the closed enum `rdock_model::middleware::Middleware`) and each route gets `chain: Arc<[Arc<dyn Middleware>]>` in the order of `route.middlewares`. `request_filter` runs the chain in order; a `Reply` at position *i* runs the response phase of `chain[..i]` only. `response_filter` runs the chain in reverse. `fail_to_proxy` asks the chain for an error page. That already is "explicit ordering" for two phases.
- **`Context` is a closed struct** (client IP, TLS flag, route, request id, authority, user, JWT claims, client certificate identity, limiter slots, and the three body fields above). It has no slot for a plugin's own per-request state.
- **The public types are Pingora's.** The trait takes `pingora::http::RequestHeader` / `ResponseHeader` (Pingora 0.9, a 0.x crate). The trait's doc comment calls it "A built-in middleware".
- **Retry buffer.** Pingora keeps a fixed 64 KiB replay buffer per request (`BODY_BUF_LIMIT`, `pingora-core-0.9.0/src/protocols/http/v1/common.rs` and `v2/server.rs`); a larger body sets `retry_buffer_truncated()` and the request is neither retried nor mirrored (ADR-0022, `docs/research/v0.4-production-reliability.md`). Request buffering (M-TM-05) moved from v0.4 to v0.8.
- **`forward_auth` is our one out-of-process call today** (`forward_auth.rs`): a `GET` to `address` with the client's headers (all, or the `request_headers` list, hop-by-hop removed) and `X-Forwarded-Method/-Proto/-Host/-Uri`; default `timeout` 5 s; **fails closed** (502, or 504 on timeout); 2xx continues and copies `copy_headers` to the request after removing the client's own values; any other answer is returned to the client (body capped at 1 MiB, `Location` made absolute). It sends **no request body**, has no fail-open switch, no circuit breaker and no response phase. It uses `HttpClient` (`client.rs`), a small pooled client on Pingora's connector.
- **A gRPC precedent without tonic exists**: the active health check speaks `grpc.health.v1.Health/Check` hand-encoded over Pingora's connector (`crates/rdock-proxy/src/health.rs`, ADR-0022).
- **What the architecture planned** (`docs/05-architecture.md`): §2 names a crate `rdock-plugins` "(P2/P3) native plugin trait, WASM host (wasmtime), out-of-process agent client" (it does not exist); §8 sketches a trait with `phases()` bitflags and `on_request`, `on_upstream_request`, `on_response`, `on_response_body` (sync), `on_log`, and lists `wasm` (P3) and `agent` (P3) as middleware kinds; "each middleware declares what it needs (body? headers only?) so streaming is preserved unless a middleware explicitly buffers". Traefik `plugin.*` labels become a diagnostic warning (§11).
- **No placeholder in the model or the gate.** `rdock-model` has no `plugin`, `wasm` or `agent` variant and `gate.rs` has no "planned for v0.8" entry for them (it has UDP listeners and directory listing).
- **Workspace facts that constrain the design:** `publish = false` for every crate; `crates/rdock` is a binary crate only (`src/main.rs`, no `[lib]`); `unsafe_code = "forbid"`; `[profile.release]` sets `lto = "thin"`, `codegen-units = 1`, `strip = "symbols"` and **no `panic = "abort"`**, so release builds unwind; the lock already holds `hyper 1.12.0`, `h2 0.4.20`, `prost 0.14.4` (through `opentelemetry-otlp`), `tower 0.5.3`, `hyper-timeout 0.5.2` (through `kube-client`), `ring 0.17.14`; `tonic` and `reqwest` are absent. `deny.toml` bans OpenSSL, native-tls and aws-lc; it does **not** ban tonic. The "no tonic, no reqwest" line in `Cargo.toml` and ADR-0022 records that OTLP did not need them; neither text gives a reason against tonic itself.

- Rust has no stable ABI, so loading Rust `dylib`s with `dlopen` would tie every plugin to the exact compiler and dependency versions of the proxy, and loading a library needs `unsafe` in our crate, which the workspace forbids. `abi_stable` is unmaintained and `stabby` would put an FFI layer between every hook. A `rdock-build` wrapper can wait. The build needs a C compiler and CMake (zlib-ng), which the template's Dockerfile must provide.

#### 2.4 Stability policy options

*(our reasoning)*
- `rdock-plugin-api` follows semver on its own version line, separate from the proxy's: 0.x until v1.0 ("stability policy from v1.0" in F-EXT-02), then a break only with a major version. The binary states which API major it was built with (`rdock version`).
- **No Pingora types in the public API.** Pingora is 0.x and a bump would break every plugin. `pingora::http::RequestHeader` dereferences to `http::request::Parts`; the API should expose our own `Request`/`Response` views over `http` 1.x types (`Method`, `Uri`, `HeaderMap`, `StatusCode`) and `bytes::Bytes`. `http` and `bytes` are 1.x and already public dependencies of half the ecosystem.
- `#[non_exhaustive]` on `Flow`, `Reply`, the context accessors' return enums and config structs; the context is an opaque struct with methods, not public fields (today's `Context` has public fields, which would freeze its layout); new phases arrive as trait methods with default bodies. Sealed traits only for things plugins must not implement (the context).
- The built-in middlewares keep their private trait or move onto the public one; either way the public trait is a strict subset of what built-ins can do (no access to limiter slots, compression state or the session).

#### 2.5 Recommended trait shape *(our reasoning)*

```rust
// rdock-plugin-api (sketch; names open)
#[async_trait]
pub trait Plugin: Send + Sync + 'static {
    /// Declared once at build time; the proxy never calls a hook that is not declared.
    fn phases(&self) -> Phases;                 // REQUEST | REQUEST_BODY | UPSTREAM_REQUEST | RESPONSE | RESPONSE_BODY | LOG
    fn request_body(&self) -> BodyNeed { BodyNeed::None }   // None | Stream | Buffer { max_bytes }

    async fn request(&self, req: &mut Request, cx: &mut Ctx) -> Flow { Flow::Next }
    async fn request_body(&self, chunk: &mut Option<Bytes>, end: bool, cx: &mut Ctx) -> Result<(), Reject> { Ok(()) }
    async fn upstream_request(&self, req: &mut Request, cx: &mut Ctx) {}        // once per attempt (retries call it again)
    async fn response(&self, resp: &mut Response, cx: &mut Ctx) {}
    fn response_body(&self, chunk: &mut Option<Bytes>, end: bool, cx: &mut Ctx) {} // sync: Pingora's hook is sync
    fn log(&self, summary: &Summary, cx: &Ctx) {}                                // sync, read-only, after the response
}
pub type Factory = fn(name: &str, config: &serde_json::Value) -> Result<Arc<dyn Plugin>, ConfigError>;
```

- **Order:** `request` and `upstream_request` in chain order, `response` and `response_body` in reverse, `log` in chain order; this is today's rule extended. `request_body` runs in chain order.
- **Per-request state:** `cx.state::<T>()` / `cx.set_state(T)` over a typed map (`http::Extensions` is already in the tree), keyed per plugin instance so two instances of one plugin do not collide. No generic associated type: the chain is `Arc<[Arc<dyn Plugin>]>`.
- **Body:** `BodyNeed::Buffer { max_bytes }` makes the proxy collect the body before `request` runs, using the same mechanism M-TM-05 needs; up to 64 KiB it stays retryable and mirrorable, above that the route loses retries, and validation says so. `Stream` gives chunks in `request_body` after the upstream has been chosen (Pingora sends the request header upstream before the body filter runs), so a streaming body plugin can stop a request but cannot hide its headers from the backend.
- **Config:** a new model variant `plugin: { name, config }`; `config` is checked by the factory at compile (snapshot) time, so `rdock validate` reports plugin config errors with a path; an unknown `name` is an error that lists the plugins compiled into this binary.
- **`async-trait`** (already a dependency) stays: native `async fn` in traits is not `dyn`-compatible.

*(our reasoning)*
- **Most existing plugins: proxy-wasm.** It is the only ABI with a real catalogue (Envoy/Istio filters, Coraza). The cost: a 2020 ABI with core modules (not components), roughly fifty host calls with Envoy-shaped semantics (shared queues, timers, gRPC callouts, property paths), and no Rust host library to reuse, so we would write and maintain the host. It would not satisfy "component model" in F-EXT-03.
- **Safest sandbox and least code: a WIT world of our own** (`rdock:plugin/filter@0.1.0`): exports `on-request`, `on-response`, optionally `on-response-body`; imports nothing by default. Capabilities are imports the host links only when the config grants them: `log`, `clock`, `random`, and `http-fetch` with a host allow-list. A guest built without WASI (`wasm32-unknown-unknown` plus `wit-bindgen`) has no ambient authority by construction: if an import is not linked, instantiation fails at load time with a diagnostic, not at request time.
- `wasi:http/proxy` is the standard-shaped middle: a filter is an `incoming-handler` that may call `outgoing-handler` for "next". It needs `wasmtime-wasi-http` and `wasmtime-wasi` (more crates and its own hyper stack), models a handler rather than header-phase filters, and has no existing filter catalogue. Not for v0.8.
- http-wasm is small and Traefik-compatible in spirit, but the ABI repository has not moved since 2023 and its catalogue is Traefik's plugin site (plugins packaged for Traefik's loader).
- Recommendation: own WIT world on wasmtime 36, versioned and declared unstable; note proxy-wasm as a possible later adapter if users ask for Coraza-in-process. Both conflict with nothing else in this note.

#### 3.3 Limits, feature gate, and what "experimental" means *(our reasoning)*

- Per plugin: `fuel` per call (deterministic, default on), an epoch deadline as the wall-clock backstop, `memory_max` through `StoreLimits`, a module size limit, a cap on concurrent instances (pool size). Exhaustion is an error with a metric and follows the plugin's `on_error` (default: fail closed, 500).
- `response_body` for WASM is possible because the call is synchronous and fuel-bounded; host calls that need to await (`http-fetch`) are offered only in the async phases.
- **Cargo feature `wasm`, off by default**, in `rdock` and in a new `rdock-wasm` crate, so the default binary gains neither 48 crates nor ~13 MB. `deny.toml` has `all-features = true`, so the `deny` job checks wasmtime's tree anyway; the `rust` and `msrv` jobs need one extra `--features wasm` build (about 2 minutes of compile on a 4-vCPU runner without cache).
- "Experimental" operationally: not in the default release artefacts (a separate `-wasm` image tag at most); the config key sits under an explicit opt-in (`experimental: { wasm: true }`), without which `rdock validate` refuses a `wasm` middleware with a diagnostic; the WIT world carries a 0.x version and may break in any release; the docs page says so at the top; no 1.0 commitment.

*(our reasoning)*
- **Three ways to wire a CRS engine**, in order of cost:
  1. *HTTP check agent against a CRS reverse-proxy image.* The proxy sends the request as it is (method, path, headers, body up to a limit) to the agent; a 2xx means continue, a 403 (or the configured statuses) means block with the agent's status and body. The agent is `ghcr.io/coreruleset/coraza-crs:…-caddy-alpine` or `owasp/modsecurity-crs:…-nginx` with `BACKEND` pointing at a fixed 204 responder. This needs no new dependency and only the body-buffering work; it is `forward_auth` generalised (keeps the method and body, has a fail policy). Weaknesses: request phase only; the agent's own proxy hop needs a dummy backend; the engine parses a request that we re-serialise, so both parsers must agree (we forward the normalised request, which helps).
  2. *SPOP client against `coraza-spoa`.* A real agent protocol with request and response messages and a purpose-built, maintained image. We would write a SPOP client (frames, varints, typed values, HELLO, NOTIFY/ACK with pipelining): a few hundred lines, no dependency. The body must fit one frame (fragmentation is gone), so the inspected body is capped by the negotiated frame size. The protocol is HAProxy's; no other agent ecosystem speaks it.
  3. *`ext_proc` gRPC client.* The richest protocol and the one other gateways' agents speak, but there is no open CRS agent image to put in CI, and a correct client is the largest piece (stream state machine, mode overrides, mutation rules). `tonic` would add two crates; alternatively the hand-encoded route used for health checks extends to unary `ext_authz` easily and to a bidirectional stream with more work.
- Recommendation for v0.8: a generic **`agent` middleware with an HTTP transport** and option 1 as the shipped WAF example and CI test; record `ext_proc` (gRPC) as the planned second transport behind the ADR-0014 "planned for" gate so F-EXT-04's "gRPC/HTTP" is honest about what exists. Using tonic for that later is compatible with `deny.toml`; the ADR should state it, because `Cargo.toml` currently reads as a stance.
- **Defaults ("safe by default"):** fail **closed** (as `forward_auth` does and as Envoy defaults for both filters), with `on_error: deny | allow` explicit per middleware; `allow` adds a metric, a log field and optionally a request header so the backend can tell. Timeout per call configurable per middleware (Envoy: 200 ms; our `forward_auth`: 5 s; a WAF with CRS at paranoia level 1 sits in between, so propose 1 s and measure). A **circuit breaker** per agent (consecutive failures → open for a cool-down, during which the fail policy applies at once) keeps a dead agent from adding its timeout to every request; `rdock-balancer` already has the breaker logic for services.
- **Body:** `body: { max_bytes, on_oversize: deny | skip | partial }`. Default 64 KiB keeps requests retryable (the Pingora replay buffer); `deny` answers 413 like Envoy's `with_request_body`; `partial` sends the first N bytes and marks the request. CRS's own defaults (128 KiB without files, 12.5 MiB with) show that a WAF wants more than 64 KiB, which is M-TM-05 territory: buffering above the replay buffer costs retries and memory, and validation should say so.
- **Header mutation allow-list:** the agent may set only the headers named in `copy_headers` (today's `forward_auth` rule), never `Host`, `Content-Length`, `Transfer-Encoding`, hop-by-hop headers or `X-Forwarded-*`; the client's own values of those names are removed first. Request headers sent to the agent default to all minus hop-by-hop, with an allow-list option; `Authorization` and `Cookie` reach the agent by default because a WAF and an auth service both need them (documented).
- **Data-plane rule (ADR-0009/0012):** the agent is addressed like a service (a URL or a configured service with its own health state), never through the admin API or a provider at request time; agent failure affects only routes that use it.
- **Observability:** per agent `calls`, `denied`, `errors`, `timeouts`, `failure_mode_allowed`, latency histogram; access-log fields for the verdict; a client span per call.

Key-based cosign signatures are plain ECDSA P-256 or Ed25519 that ring can verify, but parsing the bundle format ourselves is more code than minisign for the same trust model. Keep "cosign bundle (keyless)" as a later option under principle 10 once a ring provider exists.

### 6. Security model for extensions

| Fact | Source |
|---|---|
| Envoy classifies `ext_authz` and `ext_proc` as "robust to untrusted downstream and upstream", Lua as robust to untrusted downstream "with the assumption of a trusted script", dynamic modules as "requires trusted downstream and upstream", Wasm as "unknown"; side-call services such as external authorization are assumed trusted | [Envoy threat model](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/security/threat_model) |
| Traefik: "Plugins can change the behavior of Traefik in unforeseen ways. | Caddy's extension guide has no trust or security section | [Extending Caddy](https://caddyserver.com/docs/extending-caddy) |
| Our release profile unwinds (no `panic = "abort"`); `futures-util` is in the tree | `Cargo.toml` |

*(our reasoning)* The three mechanisms have three different trust levels, and the docs should say so in one table:

| | Native plugin | WASM plugin | Agent |
|---|---|---|---|
| Trust | Full: it is our process. Memory-safe if it forbids `unsafe`, but it can read every header, body, key in memory and the file system | Sandboxed: sees what the host passes; no file, network, clock or environment unless granted | Separate process or host: sees what we send it |
| Sees | Request and response headers, bodies it asks for, `Ctx` accessors | Headers of its phases; bodies only if the config grants `body`; never TLS keys, other plugins' state, or config secrets | Headers (allow-list), body up to the limit, client IP, TLS facts we choose to send |
| Can do | Anything a built-in can do through the public API | Change headers, answer, call granted host functions within fuel, memory and time limits | Allow, deny, set allow-listed headers |
| Failure | Panic caught per call → 500 and a metric | Trap, out of fuel, over memory → `on_error` (default deny) | Timeout, error → `on_error` (default deny), breaker |

- **Secrets:** plugin config goes through the same redaction as built-in config (never echoed by the API). `Authorization`, `Cookie` and the client-certificate identity headers are passed to WASM plugins and agents only when the config names them (WASM) or does not exclude them (agents; see 4.3). A WASM plugin never receives the client certificate itself, only the identity fields `client_cert` already exposes.
- **Order relative to authentication:** order is the route's list, so an operator can put a plugin before `jwt` or `forward_auth`. Validation should warn when a `wasm`, `plugin` or `agent` middleware precedes an authentication middleware in a chain (it would see unauthenticated traffic and could answer before auth), and document the WAF-before-auth case as the intended exception.
- **Panic isolation for native plugins:** wrap each hook in `catch_unwind` (`AssertUnwindSafe(fut).catch_unwind()` from `futures-util` for async hooks; `std::panic::catch_unwind` for the sync ones). No `unsafe` is needed. A caught panic answers 500, counts in a metric and logs the plugin name; without the wrapper tokio would catch the panic at the task boundary and drop the whole client connection (every HTTP/2 stream on it). It works only while the profile unwinds: the template must not set `panic = "abort"`, and a poisoned lock inside the plugin is the plugin's problem.
- **Resource limits:** WASM as in 3.3; agents by timeout, body cap, connection pool size and breaker; native plugins have none beyond the proxy's own request limits, which is the reason they are "trusted code".
- **Supply chain:** native plugins enter through the user's own `Cargo.lock` (we recommend `cargo deny` in the template with our `deny.toml`); WASM through digest and signature (section 5); agents are images the operator pins by digest in their own deployment, and our example pins the CRS image by digest.
- **Reload:** WASM modules and agent definitions change through the normal snapshot swap; a module that fails to load, verify or link keeps the previous snapshot (existing behaviour for any compile error). Unlike Traefik we can add a plugin without a restart because loading is gated by the signature policy in the static file, which a provider cannot change.

### 1. Where we start

Read in the tree at commit `e7a4025`.

- **Middleware trait** (`crates/rdock-middleware/src/lib.rs`): two phases only, `request(&mut RequestHeader, &mut Context) -> Flow` and `response(&mut ResponseHeader, &mut Context)`, plus `error_page`. **No middleware sees a request or response body.** `Context` carries `client_ip`, `route`, `request_id`, `user` (set by `basic_auth`, logged), `claims` (set by `jwt`), `client_cert`, `replace_body`, `throttle`. There is no "consumer" yet. `docs/05-architecture.md` §8 still shows the planned trait with `on_response_body` and `on_log`; the code never grew them.
- **`jwt`** (`jwt/mod.rs`, `keys.rs`, `token.rs`): own implementation on `ring`. Algorithms RS256/384/512, PS256/384/512, ES256, ES384, EdDSA, HS256/384/512; each key pinned to one algorithm; `none` absent; `crit` refused; `jku`/`x5u` never followed; `exp` required; `iss`/`aud` checked unless `any`; 16 KiB token cap. Keys from `jwks_url` (background fetch, cached 600 s, early refresh on an unknown `kid` at most every 30 s, retry after 30 s, 1 MiB cap), `jwks_file`, or `hmac_secret` (a `${file:…}`/`${env:…}` reference, ≥ 32 bytes). Token from header (default `Authorization: Bearer`), then cookie, then query. `claims_to_headers` removes client-sent copies. An RSA JWK without `alg` is taken as RS256.
- **`basic_auth`** (`auth.rs`, `hashes.rs`): argon2id, bcrypt, `$apr1$`, `$1$`, `{SHA}`; constant-time compare with `subtle`.
- **`forward_auth`**: GET to an auth service through `HttpClient`, fail closed (502/504), `copy_headers` with client copies removed.
- **`HttpClient`** (`client.rs`): built on **Pingora's connector** (not hyper): pooled, 10 s DNS cache, `send` and `send_with_body` (so a form `POST` to a token or introspection endpoint is possible today), whole response in memory with a cap. The hyper-rustls client lives in `rdock-observability` (alert webhooks, OTLP export) and has the SSRF guard (private addresses refused unless allowed, no redirects, 5 s, 3 attempts).
- **Rate limits** (`ratelimit.rs`, `limits.rs`, `rdock-limits`): token bucket per key, 64 shards, 65 536 keys per middleware, in memory per instance. `RateLimitKey` already has `client_ip`, `route`, `header:<Name>`, `cookie:<name>`, **`claim:<name>`**. So "per API key" works today as `header:X-Api-Key` (keyed by the raw key value, unauthenticated) and "per JWT subject" as `claim:sub`. Answers are `429` with `Retry-After` only; no `RateLimit` headers; no windowed quota; nothing survives a restart.
- **Errors** (`rdock-proxy/src/errorpage.rs`, `errors.rs`): the built-in page is HTML, or `{"status":…,"error":…,"request_id":…}` as `application/json` when `Accept` contains `application/json` and not `text/html`. The `errors` middleware replaces bodies for status ranges from a file or a service. Middleware replies with `body: None` get the built-in page, so one renderer already produces every proxy-made error.
- **Transformation**: `headers` (set/add/remove, both directions), `rewrite`, `strip_prefix`, `add_prefix`, `replace_path`, `redirect`. No body transformation.
- **Request bodies in the proxy** (`proxy.rs` `request_body_filter`): chunks are counted for `max_body` (413) and copied for `mirror` up to 64 KiB. `buffering` (M-TM-05) is not implemented.
- **Observability**: `AccessRecord` has `request_id`, `route`, `service`, `status`, `bytes_in`, `bytes_out`, `duration_ms`, `user`, `cf_ray` and more: almost the metering event already, minus the consumer. The access log is written by its own thread from a 16 384-line queue and drops (and counts) when full. OTLP: traces only (`opentelemetry-otlp` 0.33.1 with `http-proto`, `trace`), exported through our own `ExportClient` on hyper-rustls. Metrics have no per-user label (cardinality).
- **Admin** (`rdock-admin`): API tokens `rdk_pat_<10-char id>_<32-char Base62 secret><6-char Base62 CRC32>`, stored as SHA-256 of the secret, lookup by public id, `subtle` compare, expiry, `allowed_from`, last use persisted at most every 60 s (ADR-0024). Alert webhooks are signed with Standard Webhooks (`whsec_`, HMAC-SHA256). `deny.toml` forbids every crate but the binary from depending on `rdock-admin`, so the data plane cannot call `tokens.rs`.
- **Cloudflare** (`rdock-cloudflare`): IP range sync and cache (W-CF-01), DNS-01 (W-CF-03); `CF-Connecting-IP` and `CF-Ray` are handled in the proxy. Nothing for Access (W-CF-06). `docs/04-requirements.md` still shows W-CF-01…05 unchecked although the v0.3 roadmap entry lists them as delivered: the checklist is stale *(our reasoning)*.
- **Retries**: see section 10. Status-code retries **already ship** (ADR-0015 superseded ADR-0010 on the day both were written).

#### 2.2 What it means *(our reasoning)*

- **Hash with SHA-256, not argon2.** A generated key carries far more than 112 bits (ours: 190), so a plain approved hash satisfies NIST, costs about a microsecond per request and needs no cache. argon2/bcrypt (what Traefik Hub's `htpasswd` format implies) would cost milliseconds of CPU per request or force a plaintext-keyed cache. Refuse configured hashes that are not `sha256:<64 hex>`; accept an `hmac-sha256` variant with a `${file:…}` pepper only if someone asks.
- **Reuse the ADR-0024 token format with a new prefix**, e.g. `rdk_key_<id>_<secret><crc>`: public id for lookup, logs, revocation and metering; CRC32 so a typo is refused without a lookup; one regular expression for scanners. The parse/checksum/hash functions must move out of `rdock-admin` (the data plane may not depend on it) into a small shared module (`rdock-model` or `rdock-limits`-style leaf crate). Keys minted elsewhere (migration from Kong, APISIX, AWS) have no id: look those up by the full SHA-256 in a hash map, then compare in constant time; refuse imported keys shorter than 20 characters (the AWS floor) with a diagnostic.
- **A `consumers` section**, not a middleware-local list: `consumers.<name>: { groups: [...], credentials: { api_keys: [{ id, sha256, expires, allowed_from }], jwt: { claim: sub, value: … } }, limits: …, metadata: {…} }`. A consumer is then one identity whatever the credential (API key, JWT subject, OIDC login, mTLS subject), which is the Kong/APISIX model and what limits, logs and metering need.
- **Stores, all hash-only**: (a) inline in the file configuration; (b) a keys file (`path`, reloaded by the existing watcher) for generated lists; (c) **the `api` provider as issuer**: `POST /api/v1/consumers/{name}/keys` returns the key once and stores the hash in the provider's snapshot (the only writable store, architecture §4 rule 6). Hashes are safe in snapshots and configuration history; a clear-text key must never enter them. (d) **external store** as RFC 7662 introspection through `HttpClient::send_with_body`: positive cache TTL capped by `exp`, short negative cache, fail closed, bounded cache size. (d) puts a network call on the request path of a cache miss, like `forward_auth`; it stays opt-in.
- **Middleware `api_key`**: `sources` (header with optional scheme, query, cookie; several allowed, first present wins, a repeated value is refused as in `jwt`), `hide_credentials: true` by default (safer than APISIX's default), `anonymous: <consumer>` opt-in, 401 with `WWW-Authenticate` on failure, identity headers to the backend (`X-Consumer-Name`, `X-Consumer-Groups`, `X-Credential-Id`) with client-sent copies removed. Query-string keys work but `rdock validate` warns (they end up in logs elsewhere; our access log already omits the query).
- **Flow**: the middleware sets `cx.consumer = Some(Arc<Consumer>)` (and `cx.user` for the log). `jwt`, `basic_auth`, `client_cert` and `oidc` can map to a consumer the same way. `rate_limit`/`quota` gain `key: consumer`; `AccessRecord` gains `consumer` and `credential_id`; the metering event takes both. Consumers are **not** a metric label (cardinality); per-consumer numbers come from metering.

| `ring` 0.17.14 (already in the tree) has `aead::AES_256_GCM`, `aead::CHACHA20_POLY1305`, `LessSafeKey::seal_in_place_append_tag` / `open_in_place`, 96-bit nonces, and `hkdf` | `ring-0.17.14/src/aead/`, `src/hkdf.rs` |

#### 3.4 What it means *(our reasoning)*

- **Own implementation, no crate.** `josekit` is banned outright (OpenSSL). `jsonwebtoken` has no ring backend. `openidconnect` would add a second crypto stack (RustCrypto `rsa`, `p256`, …) beside ring and bring `rsa 0.9`, which `cargo deny` would flag for RUSTSEC-2023-0071. What an RP needs beyond the code we have is small: fetch and check the discovery document, build the authorization URL (state, nonce, S256 challenge: SHA-256 and Base64 are in `ring`/`base64`), one form `POST` to the token endpoint (`HttpClient::send_with_body`), ID Token validation (the `jwt` module plus `nonce` and `azp` checks), and the session cookie. The JWKS cache, algorithm pinning and claims-to-headers code is reused unchanged.
- **Safe defaults where competitors are lax**: PKCE S256 always on (Traefik Hub and APISIX default to off); `state` and `nonce` both; `iss` response parameter checked when present; exact `redirect_uri` (`https://<host>/.rdock/oidc/callback` by default); the post-login target is a same-origin path only (no open redirector); `client_secret` only as `${file:…}`/`${env:…}`; the issuer must be https unless `allow_insecure_issuer` is set for tests; requests that are not navigations (`Accept` without `text/html`, or `Sec-Fetch-Mode` other than `navigate`) get 401 instead of a redirect (Envoy's `deny_redirect_matcher`, on by default).
- **Session: one stateless encrypted cookie.** `__Host-rdock-session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`; value = version byte, key id, 96-bit random nonce, AEAD ciphertext (ChaCha20-Poly1305 or AES-256-GCM from `ring`) of a compact record: `sub`, the selected claims, expiry, `sid`, and the refresh token only when refresh is enabled. Keys come from `session.secret` (a reference, ≥ 32 bytes) through HKDF, with `previous_secrets` for rotation (the pattern `StickyKeys` already uses). The ID Token is **not** stored whole; only an opt-in keeps it (RP-initiated logout wants `id_token_hint`). Keep the record under about 3.5 KiB; over that, split into numbered cookies (`…-1`, `…-2`) as Envoy and oauth2-proxy do, and refuse above a fixed number. With a random 96-bit nonce the number of cookies sealed under one key must stay far below 2^32 (the usual AES-GCM bound; *unverified today against NIST SP 800-38D*); deriving a sub-key per day from the secret keeps that true without operator action.
- **Multi-replica and Kubernetes**: stateless cookies work on any number of replicas as long as all share the secret (a Kubernetes Secret mounted as a file, which the chart can template). No store is needed in v0.8; that is why oauth2-proxy and APISIX default to cookies. What a stateless design cannot do: revoke one session before it expires, and **back-channel logout** (needs a `sid` index). Both wait for the shared state of v0.9 (H-HA); until then keep the session lifetime short (default 12 h, absolute) and offer RP-initiated logout (`/.rdock/oidc/logout` → `end_session_endpoint`). Refresh tokens stay opt-in: with rotation at the provider, two parallel requests can both try to refresh, and only one replica wins.
- **Policies**: `require: { groups: [..], claims: { email_verified: true, hd: example.com } }` evaluated on the session claims (403 on failure), `claims_to_headers` as in `jwt`, and a consumer mapping (`consumer_from: claim:email`). Keep it declarative; an expression language belongs to the extensibility work.
- **Gateway API**: the v0.7 controller rejects `ExtensionRef` and `ExternalAuth` filters (ADR-0029). OIDC on Kubernetes needs a way to attach a ReverseDock middleware to an HTTPRoute; that is a controller decision outside this note and should be made once for `oidc`, `api_key`, `rate_limit` and `jwt` together.

*(our reasoning)*
- **Two different things.** A *rate limit* protects the backend (token bucket, seconds, loses nothing important on restart). A *quota* is a commercial or fairness allowance (N requests per hour/day/month, calendar-aligned in UTC, must survive a restart). Keep `rate_limit` as it is and add `key: consumer`; add a `quota` middleware (or `consumers.<name>.quota` and `groups.<name>.quota`, group values as defaults and consumer values as overrides: the "plan" model of AWS and Tyk).
- **Overrides without one middleware per customer**: `rate_limit: { key: consumer, average: 100, per_group: { gold: { average: 1000 } } }`. One limiter per distinct limit value, chosen by the consumer's group at request time.
- **Storage in v0.8**: fixed-window counters in memory per instance, keyed by (consumer, window start). Persist them to `$RDOCK_DATA_DIR/quota/<middleware>.json` every few seconds and on shutdown (atomic rename, like the token store), reload on start, and drop windows that ended. Like AWS, document that quotas are per instance and approximate until distributed limits arrive (v0.9 H-HA); `rdock validate` should say so when a `quota` is configured together with the Kubernetes provider or several replicas.
- **Headers**: keep `Retry-After` on every 429 (already there; for a quota it is the time to the window end). Offer `headers: off | draft` on `rate_limit` and `quota`, where `draft` emits `RateLimit-Policy` and `RateLimit` in the -11 syntax with the policy named after the middleware. The draft changed shape between revisions and expires this month, so it should not be on by default and the docs must name the revision and date. Do not emit Kong's legacy trio.
- **Status**: 429 for both (the draft uses it in its examples; APISIX's 503 default confuses clients and health checks).

*(our reasoning)*
- **Compile once, validate cheaply.** Schemas are compiled when the configuration is compiled (`jsonschema` validators are built once and shared), `$ref` to anything remote is refused (no network resolver is compiled in, which is also the SSRF answer), files are read at reload like `jwks_file`. A schema that does not compile fails `rdock validate`.
- **What to validate, in this order of cost**: method and content type (`allowed_content_types`), required headers and query parameters against small schemas (no body needed: works today in the request phase), then the JSON body against `body_schema` with a hard size cap (default 1 MiB, never above `max_body`). Response validation is opt-in, log-only by default, and sampled; it needs the response body phase and doubles memory.
- **Two input shapes**: (1) `validate: { headers, query, body }` with inline or file JSON Schemas (2020-12 by default, `$schema` honoured) on a route; (2) `openapi: { file, … }`, which expands at configuration-compile time into (1) per operation, matching path templates to requests. (2) needs an OpenAPI model: `oas3` for 3.1; 3.0 documents need the `nullable`/Wright-00 differences translated before `jsonschema` sees them; 3.2 has no Rust model crate checked here (**unverified**) and adds little that validation needs. Ship (1) first; (2) for 3.1 next; accept 3.0 with a documented translation; refuse 3.2-only constructs with a diagnostic.
- **Buffering is the dependency, and there are three ways**:
  1. *Hold in `request_body_filter`* (works on 0.9.0 today, any size): accumulate chunks, hand Pingora empty chunks until the end, validate, then emit the whole body or fail. Cost: the backend was already selected and connected, and for HTTP/1 the request header is already written, so a rejected request shows up at the backend as an aborted one and consumed a connection. Acceptable for a first version, ugly as a design.
  2. *Read in `request_filter` and rely on the retry buffer*: only ≤ 64 KiB. Not general.
  3. *`early_request_body_buffer_limit()`* from Pingora `main`: exactly the right hook (body complete before routing-dependent work and before the backend is chosen; replay on retry included). Needs the next Pingora release.
  Build `buffering` (M-TM-05), request validation and request-body transformation on **one** internal abstraction ("the request body is complete in memory, up to N bytes"), implement it with (3) when a release carries it and with (1) otherwise. This also wants a new middleware phase `request_body(&self, body: &Bytes, cx) -> Flow`, run only for routes whose chain declares it, so streaming stays the default (architecture §8 already promises "each middleware declares what it needs").
- **Errors**: 400 for a schema failure, 415 for a content type, 413 for the cap, as `application/problem+json` with an `errors` array of `{ detail, pointer }` (JSON Pointer into the body, the example in RFC 9457). Cap the number of reported errors (e.g. 10) and never echo request values back (reflected-content and log-injection risk).
- **gRPC, multipart, streams**: not validated; a route with `validate.body` refuses bodies that are not JSON unless the content type is allowed without a schema.

*(our reasoning)*
- **Envelope = RFC 9457.** One renderer already makes every proxy-made error; change its JSON branch to `application/problem+json` with `type: about:blank` (or `https://reversedock.dev/problems/<slug>` for the few we define: `rate-limited`, `quota-exceeded`, `invalid-request`, `unauthenticated`, `upstream-unavailable`), `title`, `status`, optional `detail`, and extension members `request_id` and, for compatibility with today's body, `error`. Negotiation: `application/problem+json` or `application/json` in `Accept` (and no `text/html`) → problem JSON; browsers keep the HTML page. A route setting `errors_format: auto | json | html` covers API routes whose clients send `Accept: */*` (the common case that gets HTML today). The body shape change is user-visible: it needs a line in the ADR and the website page, but it keeps the old member names.
- **Upstream errors are not rewritten by default** (Envoy's rule). The existing `errors` middleware stays the opt-in for replacing backend error bodies; give it `format: problem` as a third source beside `file` and `service`.
- **Transformation, bounded and declarative**: headers exist. For bodies offer exactly one thing in v0.8: `transform: { request: { json_patch: [...] }, response: { json_patch: [...] } }` on `application/json` bodies under a size cap, with values allowed to reference a small fixed set of variables (`${request_id}`, `${consumer.name}`, `${claim.<name>}`, `${client_ip}`). JSON Patch is a standard, total (always terminates, linear in the patch), already in the tree, and a failed `test` operation is a natural guard. It needs the buffered-body phase (request side: section 5; response side: a response-body phase that must also drop `Content-Length`/`ETag` and run before compression).
- **No jq, no templates in core.** `jaq` would fit the licence and MSRV, but an interpreter on the request path has unbounded CPU and memory per request unless metered, and every such engine becomes an API we must keep stable. That belongs to the plugin/agent work (F-EXT), where the user owns the cost.

### 1. UDP relay (M-L4-04) and UDPRoute (W-K8S-01)

#### 1.1 Where we start

- `ListenerProtocol::Udp` parses (`crates/rdock-model/src/config.rs`) and `gate.rs` refuses it: "UDP listeners: not supported in this version (planned for v0.8)". Validation already lets a UDP and a TCP listener share an address (`validate.rs`, test "UDP and TCP may share a port").
- **There is no UDP route or service in the model.** `rdock-model/src/route.rs` has `Route` and `TcpRoute`; `service.rs` has `Service` and `TcpService { backends, proxy_protocol, timeouts: TcpTimeouts { connect 5 s, idle 600 s, termination_delay 100 ms } }`. A fragment carries routes, services, middlewares, TCP routes and TCP services (and, since v0.7, listeners and certificates).
- TCP (v0.6, ADR-0026) is our own accept loop (`listener.rs`) with a per-connection `tcp::serve()`: optional PROXY header, ClientHello peek, route selection (`tcp::select`), filters (`ip_allow`, `ip_deny`, `in_flight` per client IP), a backend chosen per connection by the HTTP services' pool (`TcpServiceRuntime.pool: Arc<ServiceRuntime>`), then `tcp/relay.rs`: two copy loops, one shared `Activity` clock, an idle timer and a termination delay. Metrics: `rdock_tcp_connections{listener,route}`, `rdock_tcp_bytes_total{route,direction}`, `rdock_tcp_rejected_total{listener,reason}`. Reload keeps sockets of unchanged addresses and drains removed listeners within `lifecycle.drain_timeout`.
- Kubernetes provider: `gateway/listeners.rs` answers a `UDP` listener with `Accepted=False/UnsupportedProtocol` ("UDP listeners are not supported yet (planned for v0.8)"); `gateway/l4.rs` reads UDPRoutes (they are in the inventory and the status writer) and gives every parentRef `Accepted=False/NotAllowedByListeners` or `NoMatchingParent`. `runtime/services.rs` builds the per-Gateway Service from `BTreeMap<u16, u16>` (port → target) and writes every port as `"protocol": "TCP"` with the name `port-<n>`. `features.rs` lists `UDPRoute` among the features not claimed.
- The proxy-header crate we pin (0.1.3) already models datagrams: `Protocol::Datagram`, `ProxiedAddress::datagram(source, destination)` (`proxy-header-0.1.3/src/lib.rs:106-133`).

*(our reasoning)*
- **A session is (listener, client address and port)**; the listener's local address is fixed per socket, which makes this Envoy's 4-tuple. Each session owns **one connected upstream socket** on an ephemeral port: the kernel then delivers only that backend's datagrams to it (anything else is dropped before it reaches us), an ICMP port-unreachable comes back as `ECONNREFUSED` on the next send or receive (a free passive health signal), and replies need no lookup. The cost is one file descriptor and one task per session, so sessions must be capped. A shared upstream socket with a reverse map saves descriptors but cannot tell two clients' answers apart when they talk to the same backend, so it is not an option for a transparent relay.
- **Structure:** one receive loop per listener socket (`recv_from` → look up or create the session → `send` on its upstream socket; never block the loop on a session, drop when a session's queue is full and count it); one task per session reads the upstream socket and `send_to`s the client through the listener socket, and ends on idle. A `HashMap<SocketAddr, Session>` behind a mutex is enough at first; `SO_REUSEPORT` with one socket per worker is the later scaling step (socket2 is already a dependency; the kernel's reuseport hash keeps a client on one socket).
- **Timeouts:** the three defaults span 3 s (Traefik), 60 s (Envoy) and 10 min (NGINX). **Default `idle: 60s`** follows Envoy and is the documented middle; NGINX's 10 minutes holds a descriptor per DNS query for ten minutes. Offer NGINX's two hints as options because they are what makes DNS cheap: `responses: 1` closes the session after one answer, `requests: 1` makes every datagram its own session (per-datagram balancing).
- **Balancing and weights:** the backend is chosen once per session by the existing pool (`rdock-balancer`), as for TCP connections. Weighted backends already exist per endpoint (the Kubernetes translator multiplies weights for TCP), so no weighted-split model is needed.
- **Reflection and amplification.** A relay never originates traffic: a datagram goes to a client only as the answer of a backend to a session that client address opened. That does not stop spoofed sources (inherent to UDP), so the relay must not make things worse: per-listener session cap (default in the order of Envoy's 1,024 per cluster; ours per listener, e.g. 4,096, configurable), per-client-IP session cap (reuse `in_flight`), `ip_allow`/`ip_deny` before a session is created, an optional per-client datagram rate limit, and no ICMP-like "error answers" from us. Document that amplification is a property of the backend protocol (DNS ANY, NTP monlist, memcached), not of the relay.
- **Source address of replies.** With a wildcard bind on a multi-homed host the kernel picks the reply's source address by route, which may differ from the address the client sent to, and the client drops the answer. Fix options: bind one socket per local address, or read the destination address of each datagram (`IP_PKTINFO`) and send from it. The second needs `unsafe` or a crate; **quinn-udp gives it in a safe API (`RecvMeta.dst_ip`, `Transmit.src_ip`)** and fits our constraints (MSRV 1.88 ≤ 1.89, socket2 0.6 in range, `unsafe` lives in the dependency, not in our crates). GSO/GRO come with it but matter only at high packet rates. Start with plain `tokio::net::UdpSocket`, bind per explicit address, and say in the docs that `:port` on a multi-homed host should name the address; adopt quinn-udp when the benchmark or a bug report asks for it.
- **Datagram size:** receive into a 65,535-byte buffer per socket (one buffer per loop, not per datagram); never truncate silently: count oversize or failed sends in `rdock_udp_dropped_total`.
- **PROXY protocol for UDP:** refuse `proxy_protocol` on UDP services with a diagnostic in v0.8. The spec does not define the framing and backends disagree; the encoder is there (proxy-header `Protocol::Datagram`) when a concrete consumer is named.
- **Health:** active UDP probing is protocol-specific (NGINX's generic probe only detects ICMP unreachable, and it is commercial there). v0.8: passive health from `ECONNREFUSED` on the connected socket and from "no answer within `idle` for N sessions in a row" is too vague to act on, so only the ICMP signal ejects; plus the existing **active TCP check against the same or another port** (a DNS server also listens on TCP 53). A DNS-query probe is a later option.
- **Metrics:** `rdock_udp_sessions{listener,route}` (gauge), `rdock_udp_datagrams_total{route,direction}`, `rdock_udp_bytes_total{route,direction}`, `rdock_udp_dropped_total{listener,reason}` with reasons `no_route`, `denied`, `session_limit`, `client_limit`, `backend_unreachable`, `oversize`, `queue_full`; session end reasons (`idle`, `responses`, `requests`, `backend_gone`) as a counter. No per-datagram access log; one optional record per session at its end, as Envoy does.
- **Model:** `udp_routes.<name> { listeners, service, middlewares }` (no `match`: UDP has nothing to match on, as in Traefik and the Gateway API; at most one route per listener, a second one is a validation error) and `udp_services.<name> { backends, timeouts { idle }, responses, requests }`. Reusing `tcp_routes` with a protocol switch would force ``HostSNI(`*`)`` and TLS settings onto UDP.
- **Reload and shutdown:** unchanged listener addresses keep their socket; a session keeps its backend until it ends, unless the backend left the configuration (then it is closed: NGINX sells that as `proxy_session_drop`). There is nothing to drain: on shutdown stop reading and close.
- **Test target:** DNS. CoreDNS v1.15.0 (2026-10-20, tag checked) in a container behind a `udp` listener, queried through rdock; plus our own echo server for size, ordering, idle and session-cap cases. Docker runs in the sandbox, so this is testable here.

*(our reasoning)*
- UDPRoute translates like TCPRoute: the rule's backendRefs pooled into one `udp_services` entry with the per-endpoint weights `l4.rs` already computes, attached to the port's `udp` listener; with several routes on a listener the oldest wins and all are `Accepted=True` (the TCPRoute logic and `priority.rs` already do this). A route with no usable endpoint gets no UDP route, so its datagrams are dropped (there is no "reject" for UDP).
- The weighted test passes with per-session balancing because every probe is a new source port. "Packet drops must respect weight" for invalid backends is not exercised by the suite; pooling endpoints by weight does not model it (an invalid backend contributes nothing instead of a dropping share). Either add a "blackhole" backend with the invalid reference's weight, or state the deviation. A blackhole backend is small and makes the status honest.
- `runtime/services.rs` must key ports by **(protocol, port)** and name them uniquely (`tcp-53`, `udp-53`): a Gateway with TCP and UDP listeners on port 53 is the canonical DNS case and needs a mixed-protocol Service (GA since 1.26). Renaming `port-<n>` changes every existing Service once; keep `port-<n>` for TCP and add `udp-<n>` to avoid that.
- `listeners.rs`: `UDP` becomes a supported protocol with route kind `UDPRoute`; a UDP and a TCP listener may share a port, a UDP listener conflicts only with another UDP listener on that port.
- Claim `UDPRoute` in `features.rs`; the CI job infers features from `GatewayClass.status.supportedFeatures`, so adding `GATEWAY-UDP` to `--conformance-profiles` is the only workflow change. cloud-provider-kind forwards UDP Service ports, so the kind job should work as it does for TCP; this is proven only by the CI run.
- With that, every kind in W-K8S-01 is implemented and five profiles run. W-K8S-01 can be closed when `GATEWAY-UDP` passes in CI.

*(our reasoning)* Why users ask for it: (1) slow uploads hold a worker of a backend with few workers (sync Gunicorn, PHP-FPM, Rails) for the whole upload; a buffering proxy holds the slow client instead and gives the backend the body at LAN speed; (2) a request whose whole body the proxy holds can be retried on another backend; (3) body-inspecting middlewares (signature checks, WAF, schema validation) need the whole body before the first byte reaches the backend; (4) some backends refuse chunked uploads and need `Content-Length`. Only NGINX buffers by default; Traefik, Caddy and Envoy stream unless told otherwise, as we do.

#### 2.4 Design options within Pingora 0.9.x *(our reasoning)*

| Option | What it gives | What it costs |
|---|---|---|
| **A. Hold in `request_body_filter`**: keep chunks (memory, then a spool file), release them at end of stream | (3) and (4): the backend gets the body only once it is complete and validated; `max_body` and validation errors answer before any body byte is forwarded. Uses only the public filter | The backend is already chosen, **connected and has the request header** when the client starts uploading, so (1) is not solved for backends that take a worker at accept or header time, and (2) is not solved (Pingora's own retry buffer is still 64 KiB). At end of stream the filter gets one call, so the whole body leaves as **one `Bytes`**: a spool file must be read back into memory in full |
| **B. Read in `request_filter`, replay through the retry buffer** | Solves (1) for bodies ≤ 64 KiB only | Above 64 KiB the request hangs (§2.1). A variant that enables retry buffering only for the last ≤ 64 KiB of a `Content-Length` body and swaps the tail for the whole body in the filter would work on paper and depends on three private behaviours; not acceptable |
| **C. Read in `request_filter`, then proxy through a subrequest fed from the spool** | Solves (1), (3), (4): the upstream is selected and connected only after the body is complete; the body can be streamed from a temp file chunk by chunk through `SubrequestHandle.tx` (`HttpTask::Body`), so memory stays bounded. Because we hold the body, a failed attempt can be repeated with a new subrequest, which gives (2) without Pingora's limit | The subrequest runs every phase again on a second session: context must travel through `SubrequestCtx`'s user context, access log, metrics, tracing, rate limits and middlewares must not run twice, and `pipe_subrequest` itself only takes an in-memory `Vec<Bytes>`, so the file-backed variant is our own copy of its loop. The API is public but young (0.7/0.8) and has no stability promise. **Needs a prototype before it is promised**; nothing here was run |
| **D. Upstream change**: a configurable replay limit or a "body source" hook in `ProxyHttp` | The clean fix for (1) and (2) | Not ours to schedule; worth an issue or PR upstream with our use case, independent of v0.8 |

- **Recommended v0.8 deliverable:** a `buffering` setting per route (or middleware) with `request: off | on`, `memory` (default 1 MiB, Traefik's threshold), `max` (defaults to the route's `max_body`; refuse `on` without any limit), spooling to `$RDOCK_DATA_DIR/spool/` beyond `memory`. Build it on option C if a one-week prototype shows the subrequest path keeps logs, metrics, retries and HTTP/2 correct; otherwise ship option A, named for what it is ("complete bodies only": the backend never sees a partial body and always gets `Content-Length`), and say in the docs that the backend connection is opened when the upload starts. Do not call option A "request buffering like NGINX".
- **Limits and safety:** `max` per request (413, from `Content-Length` before reading, counted while reading for chunked and HTTP/2); a global cap on spool bytes and on concurrently buffered requests (503 with `Retry-After` when full) because buffering turns a slow client into disk and memory use on the proxy; a total deadline for receiving the body (new, e.g. `timeouts.request_body`, since `listeners.timeouts.read` only bounds the gap between reads, the same gap NGINX's `client_body_timeout` has); spool files created through a cap-std `Dir` (already a dependency) with mode 0600, unlinked right after creation where the platform allows, and the directory emptied at start.
- **HTTP/2:** reading into the spool releases flow-control window as fast as the disk takes it, so the per-request and global caps are the only back-pressure; that is the point of buffering and the reason for the caps.
- **`Expect: 100-continue`:** with buffering on, the proxy must answer `100` itself (the backend is not contacted yet) after the checks that can refuse the request from its headers (`max_body`, auth, rate limits); verify Pingora's behaviour in the prototype.
- **Chunked uploads** get a `Content-Length` once buffered (NGINX does the same); trailers must be kept or dropped deliberately.
- **Retries:** with option C a buffered request may be retried for any body size up to `max`; idempotency rules of ADR-0015 still decide whether it may. With option A nothing changes.
- **Response buffering:** hold in `response_body_filter` up to a size to send `Content-Length` and to allow replacing a failed response; no disk spool. Low demand (nobody but NGINX defaults to it); leave for later and keep streaming as the only mode in v0.8. Upload streaming is what we already do.

### 3. Directory listing (F-WEB-02)

#### 3.1 Where we start

- `StaticConfig.listing: bool` exists (default false, "Only `false` in this version") and `gate.rs` refuses `true` with "directory listing (F-WEB-02): not supported in this version (planned for v0.8)".
- Path safety (ADR-0026, `static_files/root.rs`, `path.rs`): the root is a cap-std `Dir` opened once (`openat2` with `RESOLVE_BENEATH` on Linux 5.6+); `\`, NUL, invalid UTF-8 and `..` answer 404 before the file system is touched; `symlinks: none | within_root | all`; `hidden: refuse` for any dot component; `index: [index.html]`; `directory_redirect: true` (308 to the trailing slash); `nosniff: true`; `cache_control` default `no-cache`. Blocking work runs on the blocking pool.

#### 3.2 What others do

| Fact | Source |
|---|---|
| **NGINX** `autoindex off` (default). The module "processes requests ending with the slash character" when the index module finds no index file. `autoindex_format html | xml | json | jsonp` (1.7.9, default html; JSONP callback from the `callback` argument); `autoindex_exact_size on`; `autoindex_localtime off` (UTC). No sorting options, no limit | [ngx_http_autoindex_module](https://nginx.org/en/docs/http/ngx_http_autoindex_module.html) |
| **Caddy** `file_server browse [<template_file>]` "enables file listings for requests to directories that do not have an index file"; sub-options `reveal_symlinks` ("By default, the symlink targets are hidden"), `sort <name|namedirfirst|size|time> [asc|desc]`, `file_limit` (default **10000**; more entries are cut off); JSON or plain text by `Accept: application/json` or `text/plain`; `hide` removes paths from listings and from serving but "is not a security boundary" by the page's own words. | **Traefik** serves no files, so it has no listing. *Unverified* by a source; it follows from the absence of a file-server middleware | — |

*(our reasoning)* **Safe defaults for `listing: true`:**
- Only GET and HEAD, only for a path that names a directory, ends with `/` (otherwise the existing 308) and has **no index file**; the index always wins. Everything else is unchanged.
- An entry is listed only if a request for it would be served: dot entries are left out under `hidden: refuse`; with `symlinks: none` links are left out, with `within_root` a link is listed only if it resolves inside the root, link targets are never shown. Use `symlink_metadata` through the `Dir` handle; never build paths from strings.
- Output: a fixed, built-in HTML page (no user or client templates, no header/readme inclusion, no title scanning) and JSON when `Accept` prefers `application/json` (`[{name, type, size, modified}]`, UTC, RFC 3339). No XML, no JSONP (a callback parameter is reflected input).
- Encoding: names HTML-escaped in text, percent-encoded in `href` (including `?`, `#`, `%`, and a leading `./` so a name with `:` is not read as a scheme); names that are not UTF-8 are left out (they cannot be requested either). `Content-Type: text/html; charset=utf-8`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'sha256-…'` for the one inline style block (or no styles at all), `Referrer-Policy: no-referrer`.
- Size: at most `listing.limit` entries (default 10,000, Caddy's number; reading stops there and the page says it is cut off), read on the blocking pool; sorted by name with directories first, bytewise on the UTF-8 name so the order is stable; optional `?sort=name|size|time&order=asc|desc` handled server-side and ignored when invalid. No pagination in v0.8 (a cut-off notice is honest; `offset` can follow).
- Caching: `Cache-Control: no-cache` and no validator: a directory's modification time does not change when a file in it is rewritten, so an `ETag` from it would lie.
- The root: `listing: true` lists every directory without an index, the root included, which is what NGINX, Caddy and Apache do. A separate "not the root" switch adds a setting for little safety; the warning belongs in the docs and in `rdock validate` (a warning when `listing: true` is combined with `hidden: serve` or `symlinks: all`).
- Model: keep `listing: bool` and add nothing else, or make it `false | true | { limit }`. A bool plus the fixed limit is enough for a P3 item.
- Testable entirely in the sandbox (unit tests on a temp directory, the existing static suite).

*(our reasoning)*
- **Go is the only practical language.** The protocol is language-neutral gRPC, but the framework, the test harness, the documentation generator and the release tooling exist only for Go, and the registries expect GoReleaser-shaped assets. A Rust provider would mean writing the protocol server (tonic, which we do not allow) and all the tooling ourselves.
- **Where it lives.** Both registries need a public repository named `terraform-provider-<name>`; it cannot be this repository. Two workable shapes: (a) develop in `clients/terraform/` here (a Go module that imports `clients/go` through a `replace` directive), test it in our CI, and have the release workflow copy it to `Docker-Hunterpedia/terraform-provider-reversedock` and tag it there; (b) develop in the new repository. This session can only write to this repository, so (a) is the only shape that can start now, and it keeps the provider in step with the OpenAPI document. A maintainer must create the repository, a GPG key, the Terraform Registry sign-in and the OpenTofu issue; none of that can be done or tested from here. For the mirrored copy to build outside the monorepo, `clients/go` needs Go submodule tags (`clients/go/vX.Y.Z`) or must be vendored into the mirror.
- **Resource model: fine-grained resources over the per-object endpoints**, plus one whole-document resource:
  - `rdock_route`, `rdock_service`, `rdock_middleware`, `rdock_tcp_route`, `rdock_tcp_service` (and `rdock_udp_*` when they exist): `Create`/`Update` = `PUT /api/v1/{kind}/{name}`, `Read` = `GET` (404 removes it from state; an owner other than `api` is an error), `Delete` = `DELETE`, import by `name`. The body is the object as JSON; start with one `spec` attribute holding the object (a `jsonencode`d map validated against the schema) and add typed attributes for the common fields later, rather than hand-writing 170 schema attributes that drift from `rdock.schema.json`.
  - `rdock_config`: the whole API document through `PUT /api/v1/config/api`, for users who want one file; it conflicts with the fine-grained resources and the docs must say "one or the other".
  - Data sources: `rdock_status`, `rdock_object` (any owner, read-only), `rdock_certificates`.
- **Optimistic concurrency on one document.** Terraform applies independent resources in parallel (default parallelism 10) and every write needs the ETag of the whole configuration, so parallel writes would answer 412 to all but one. The provider serialises its writes with a process-wide mutex and, on 412, re-reads the ETag and retries: that is safe because a per-object `PUT` replaces only its own object, so "retry on a newer generation" cannot overwrite someone else's change to the same object without noticing (compare the object, not just the ETag, when deciding that an update is still needed). The same pattern (lock inside the provider, retry on a version conflict) is what providers over single-document stores do; naming specific providers that do it: *unverified*.
- **Ordering and validation.** Every write is validated against the whole merged configuration, so a route cannot be created before its service. Users get the right order by referencing (`service = rdock_service.app.name`), and destroy runs in reverse. `POST /config/validate` is usable at plan time only for `rdock_config` (it takes a whole candidate document).
- **Secrets and state.** The configuration holds only references (`${file:…}`, `${env:…}`), so the state file holds no secret values; the provider's `token` argument is `Sensitive` and read from `RDOCK_ADMIN_TOKEN` by default. Tokens and users are not managed by the provider in v0.8 (creating a token returns a secret once, which would have to be stored in state).
- **Drift** is detected by `Read`; a rollback or a dashboard edit shows up as a diff on the next plan. `admin.api_writes: false` must surface as one clear provider error.
- **Testing.** Unit tests with the framework's in-process server against an `httptest` fake of the API run anywhere. Acceptance tests need a running `rdock run` with an operator token and a `terraform` or `tofu` binary: a new CI job (build `rdock`, start it, `rdock tokens create`, `TF_ACC=1 go test`), once with Terraform and once with OpenTofu if the harness accepts it. In the sandbox: Go is 1.24.7 while `clients/go` and the framework need Go 1.25, and neither `terraform` nor `tofu` is installed; whether the Go toolchain and a CLI can be downloaded through the proxy was not tried.
- **Licences.** The framework and test module are MPL-2.0 (file-level copyleft, compatible with an Apache-2.0 provider that only imports them). Terraform itself is BUSL: we only run it in CI; OpenTofu is MPL-2.0. Add MPL-2.0 for this Go module to whatever licence check covers `clients/`.
- **Minimal honest v0.8:** provider source in `clients/terraform` with the five object resources, `rdock_config`, two data sources, generated docs, unit tests and one acceptance job in CI, the `.goreleaser.yaml` and `terraform-registry-manifest.json` (`protocol_versions: ["6.0"]`) ready; **not published** until a maintainer creates the repository and keys. Requirement F-MGMT-02 stays open with "published to both registries" as the missing part.

### 5. Vault and External Secrets (W-OBS-02)

#### 5.1 Where we start

- ADR-0016: `${NAME}`/`${env:NAME}` and `${file:/absolute/path}` (at most 64 KiB, one trailing newline removed) are resolved by the loader in ordinary strings; **secret fields keep the reference** and are resolved by the component that uses them. The list is `rdock_model::interpolation::SECRETS` (ACME DNS provider credentials, EAB key, alert channel secrets, `certificates.*.key_password`, sticky-cookie secrets, `middlewares.*.hmac_secret`). History, last-known-good and the admin API store the document as written.
- `rdock_config::interpolate::Lookup` has two synchronous methods, `env` and `file`. The DNS adapters call `secret::resolve()` "for every call, so a rotated file is picked up without a reload" (`rdock-dns-providers/src/secret.rs`). When the other secret fields are re-read (per use or per reload) was not traced in this pass: *unverified per field*.
- The Kubernetes provider reads TLS Secrets through the API (v0.7), so anything that ends up as a `kubernetes.io/tls` Secret is already consumed.

*(our reasoning)*
- **Client:** raw REST on our hyper-rustls client, as the DNS adapters do (ADR-0026 precedent). vaultrs cannot be used: reqwest is mandatory and we do not allow it. The surface is four calls (login, renew, read data, read metadata).
- **Reference form:** `${vault:<mount>/<path>#<key>}` with the server and login in a new top-level `secrets.vault { address, auth: token | kubernetes | approle, namespace, ca_file, … }`. The login credential is itself a reference (`${file:/var/run/secrets/kubernetes.io/serviceaccount/token}`, `${env:VAULT_TOKEN}`).
- **Only in secret fields.** `Lookup` is synchronous and runs in `rdock validate`; a network read there would make validation depend on Vault and would put secret values into loader strings. Secret fields are resolved by the component at use, where an async call fits. `${vault:…}` in an ordinary field is a diagnostic. This keeps ADR-0016's property (the configuration, history and API never hold the value) without change.
- **Caching and rotation:** cache per reference in memory only, never on disk; refresh on a timer (default 5 min, the order of ESO's `refreshInterval` examples) by reading the metadata version, and re-read the value when it changed; consumers that resolve per use (DNS) get the new value at once, consumers that hold a secret (cookie keys, HMAC) need a change notification that triggers the same swap a file change would. Renew the login token before `lease_duration` runs out; log in again when renewal fails.
- **Failure policy:** at boot a secret that cannot be read is an error for the feature that needs it, as a missing `${file:…}` is today (DNS-01 cannot run; the proxy still starts if nothing else needs it); after boot **keep the last good value**, report `rdock_secrets_refresh_errors_total{source}` and an alert event, and never fall back to an empty secret.
- **Never logged:** values, the login token, the service-account JWT, response bodies; paths and key names may be logged. Errors name the reference, not the content (the rule ADR-0016 already has).
- **TLS:** `https` only, platform verifier plus `ca_file`; `http://` only for loopback (the DNS adapters' `api_url` rule), since dev-mode servers listen on `http://127.0.0.1:8200`.
- **What CI tests against:** OpenBao in dev mode in a container (MPL-2.0), not Vault (BUSL); state in the docs that Vault is supported through the same API and tested only by users until someone runs it. KV v2 and the Kubernetes and AppRole logins being identical in both must be confirmed by that test, not assumed.
- **Scope:** v0.8 = the documentation and test path of §5.2 for everything that renders files or Secrets (this already satisfies "External Secrets"), plus `${vault:…}` for KV v2 with `token` and `kubernetes` login. AppRole, namespaces, dynamic secrets (database credentials, PKI certificates through Vault as an ACME-like issuer) and Vault Agent caching are later.

## 6. What the findings mean together *(our reasoning)*

- **The four "done when" proofs need no new dependency.** The cache runs on the `pingora-cache` already in the build with our own stores; the plugin API, the SDK examples and an HTTP agent are our code; the WAF example is a container beside the proxy.
- **One thing blocks three features: a request-body phase.** Request validation, body transformation, agents that inspect bodies and buffering all need the body before the request leaves. Pingora 0.9 offers it only after the backend is connected (hold chunks in `request_body_filter`). That is enough to reject a request before its body reaches the backend, and not enough to protect backend workers from slow uploads; the name of the setting must say which one it is.
- **The cache and the pipeline meet in subrequests.** Stale-while-revalidate re-runs the request pipeline in a background subrequest; until subrequests are marked and limits, auth, mirrors and logs are proven not to run twice, only stale-if-error ships.
- **Pingora 0.9.1 first.** It is a patch release that lifts the tokio cap; every later step builds on it, so it is the first change and is verified by the whole existing suite.
- **Security-sensitive parts get their own rules, written before the code:** the cache key and what is never stored (poisoning, deception), OIDC login (redirects, nonce, cookies), API keys (hashes only, never in snapshots or logs), agents (fail closed by default), UDP (session caps on by default against spoofed sources), `${vault:…}` (explicit failure policy, values never logged).
- **What cannot be finished from this repository:** publishing the Terraform provider (both registries require a repository named `terraform-provider-<name>`) and the `GATEWAY-UDP` conformance run (CI on kind). Both are built and tested as far as the repository allows, and the requirement boxes say what remains.
- **What is experimental or deferred**, each with a "planned for" diagnostic where a key exists: WASM plugins and module signatures (wasmtime 36 LTS is the only line our MSRV allows and its support ends in 2027), stale-while-revalidate, gRPC agent transports, response buffering, back-channel logout and server-side sessions, distributed quotas, RFC 7662 introspection, AppRole and dynamic secrets.

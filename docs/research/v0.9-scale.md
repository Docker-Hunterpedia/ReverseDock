## Part A — Binary upgrade, sockets, TLS, HTTP/2, allocators, soak (H-PERF-01…04, H-PERF-06)

All sources were read on 2026-11-13 unless another date is given; dates in brackets are publication dates. `pingora-core-0.9.1/…` means the vendored source under `~/.cargo/registry/src/*/`. Lines marked *(our reasoning)* are conclusions, not sourced facts; *unverified* means not checked against a primary source today.

Findings that change the plan:

- **The listener-change half of H-PERF-04 is already done in process.** Only the binary upgrade is missing, and rdock does not run Pingora's `Server`, so Pingora's upgrade path is not in our process at all.
- **Our listeners use a backlog of 128.** `std::net::TcpListener::bind` sets it; Pingora uses 65535 and the kernel limit is 4096.
- **TLS tickets do not survive a TLS reload or cross listeners.** `Ticketer::new()` is called per `server_config`, so every listener and every rebuilt acceptor gets its own random keys.
- **A second process on the same data dir is destructive today.** There is no lock, `Spool::open` deletes existing spool files, and `bind_socket` unlinks the admin socket.

Code read: `crates/rdock-proxy/src/server.rs`, `crates/rdock-proxy/src/listener.rs`, `crates/rdock/src/run.rs`, `crates/rdock-tls/src/policy.rs`, `crates/rdock-admin/src/server.rs`, `crates/rdock-middleware/src/held.rs`, `deploy/systemd/rdock.service`, `Dockerfile.release`, `pingora-core-0.9.1/src/server/{mod.rs,transfer_fd/mod.rs,bootstrap_services.rs}`.


### A.1 Where we stand (code facts)

1.1 rdock does not use Pingora's `Server`. `rdock run` builds its own `tokio` multi-thread runtime with default settings (`crates/rdock/src/run.rs:31-36`), installs its own signal handlers (HUP reloads; TERM, INT and **QUIT** all stop, `run.rs:217-229`) and runs its own accept loops (`crates/rdock-proxy/src/listener.rs:382-448`). Pingora's upgrade flag, `upgrade_sock`, daemonisation and pid file are therefore not in our process at all.

1.2 Listener-set changes already apply in process: bind first, publish only if every bind succeeds, unchanged addresses keep their socket, released addresses are handed to their successor, removed listeners drain (`crates/rdock-proxy/src/server.rs:288-317`, `587-618`; `docs/05-architecture.md:219`). The requirement text in `docs/04-requirements.md:147` ("until then listener changes need a restart — ADR-0008") and the roadmap wording "supervisor/worker model" are stale. Only the *binary* upgrade is missing. *(our reasoning)*

1.3 What a listener socket gets today:
- `std::net::TcpListener::bind` / `UdpSocket::bind`, then `set_nonblocking` (`listener.rs:132-167`).
- std sets `SO_REUSEADDR` on Unix and calls `listen(fd, 128)` on Linux ([rust-lang/rust `library/std/src/sys/net/connection/socket/mod.rs`, master](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/net/connection/socket/mod.rs)). Our pinned toolchain is 1.99.1; its source is not installed locally, so the 128 for that exact version is *unverified*.
- Accepted connections get `TCP_NODELAY` only (`listener.rs:492`).
- Not set anywhere: `SO_REUSEPORT`, a backlog, `SO_RCVBUF`/`SO_SNDBUF`, `SO_KEEPALIVE`, `TCP_FASTOPEN`, `TCP_USER_TIMEOUT`, `IPV6_V6ONLY`, DSCP (grep of `crates/rdock-proxy`).

1.4 TLS: `rdock_tls::server_config` calls `rustls::crypto::ring::Ticketer::new()` on every call (`crates/rdock-tls/src/policy.rs:40`). It is called once per listener and again whenever a reload rebuilds an acceptor (`server.rs:331-341`). Each call makes fresh random keys. So tickets from one listener are not accepted on another, a TLS-settings reload invalidates all tickets of that listener, and so would a restart or upgrade. `session_storage` is the rustls default, a 256-entry in-memory cache per config (`rustls-0.23.46/src/server/builder.rs:113`). 0-RTT is off (`max_early_data_size: 0`, `builder.rs:121`).

1.5 Data dir (`run.rs:72-138`, `engine.rs:215-228`): `sticky.key`, `admin.sock`, `spool/`, `cache/`, `quota/`, `acme/`, `pki/`, `cloudflare/`, `admin/`, `audit/`. Three things break with two processes on one data dir:
- There is **no lock**; a grep for `flock`/`lock_exclusive`/`fs4`/`fd-lock` finds nothing.
- `Spool::open` deletes every file already in the spool (`crates/rdock-middleware/src/held.rs:39-55`), so a new process would delete the held bodies of a draining old one.
- `bind_socket` unlinks and rebinds `admin.sock` (`crates/rdock-admin/src/server.rs:244-262`).

1.6 systemd unit: `Type=notify`, `ExecReload=/bin/kill -HUP $MAINPID`, `TimeoutStopSec=15s`, `DynamicUser=yes`, `NoNewPrivileges=yes`, `SystemCallFilter=@system-service`, `ProtectSystem=strict` (`deploy/systemd/rdock.service`). No `NotifyAccess=` is set. The release image is distroless `static-debian13:nonroot` with `ENTRYPOINT ["/usr/local/bin/rdock"]`, so rdock is PID 1 (`Dockerfile.release`).

1.7 Allocator: mimalloc is already the global allocator behind the default feature `mimalloc` (`crates/rdock/src/lib.rs:34-36`, `crates/rdock/Cargo.toml:28-31`). It took CPU per request from 139 to 90 µs on static musl (`benchmarks/results/2026-11-02-small-cpu/report.md:28`). The per-core runtime of #176 was measured and not adopted (`docs/07-roadmap.md:53`); no `per_core` code is in the tree.

### A.2 H-PERF-04 — how Pingora 0.9.1 upgrades

2.1 Sequence (`pingora-core-0.9.1/src/server/mod.rs`):
- The new process starts with `--upgrade` (`Opt::upgrade`, `configuration/mod.rs:278`). `Bootstrap::load_fds` creates a Unix stream socket at `upgrade_sock`, listens and waits for one connection (`bootstrap_services.rs:246-258`, `transfer_fd/mod.rs:129-227`).
- The operator sends **SIGQUIT** to the old process. It connects to `upgrade_sock` and sends all listening fds in one `sendmsg` with `SCM_RIGHTS`. The payload is the bind addresses joined by spaces (`mod.rs:273-302`, `transfer_fd/mod.rs:70-78`, `115-121`, `338-372`).
- The old process sleeps `CLOSE_TIMEOUT` = 5 s (`mod.rs:66`, `307`), then broadcasts shutdown; accept loops stop.
- It then sleeps `grace_period_seconds`, default `EXIT_TIMEOUT` = 300 s, with `thread::sleep` (`mod.rs:63`, `805-812`).
- Finally it shuts the runtimes down with `graceful_shutdown_timeout_seconds`, default 5 s (`mod.rs:816-837`).
- SIGTERM is the same without the fd transfer; SIGINT exits at once (`mod.rs:150-176`).

2.2 What is transferred: listening sockets only, keyed by address string (`Fds`, `transfer_fd/mod.rs:36-68`). Not transferred: established connections, TLS ticket keys or session caches, upstream pools, any application state. Pingora has no UDP listeners.

2.3 How old connections end:
- HTTP/1: keep-alive is switched off for sessions that start after shutdown (`apps/mod.rs:343-349`).
- HTTP/2: `graceful_shutdown()` sends GOAWAY and waits for streams. A source comment says there is no per-connection drain timeout and the runtime shutdown is the only ceiling (`protocols/http/v2/server.rs:127-132`, `159-164`).
- Anything alive after grace period plus runtime timeout is dropped with the runtime. WebSocket, SSE and long uploads live at most about 305 s by default.
- [Issue #357](https://github.com/cloudflare/pingora/issues/357) (opened 2024-08-20, closed 2024-08-30): a systemd stop timed out because of the 300 s default.

2.4 Daemon and pid file: `daemon: true` forks through the `daemonize` crate, moves the old pid file aside and can drop to `user`/`group` (`server/daemon.rs:82-246`). An optional `daemon_wait_for_ready` signals the parent with SIGUSR1 (`bootstrap_services.rs:212-221`). The source says "TODO: delete the pid when exit" (`mod.rs:229`).

2.5 Defects and pitfalls in the mechanism:
- **A failed send still shuts the old process down.** On `Err` from `send_to_sock` it logs and still takes the close-timeout and shutdown path (`mod.rs:290-322`).
- The receiver panics on errors: `unwrap()` on `socket`, `UnixAddr::new`, `bind`, `fchmodat`, `listen`, `recvmsg` (`transfer_fd/mod.rs:140-210`).
- The upgrade socket is world-accessible: `fchmodat(…, 0o666)` (`transfer_fd/mod.rs:161-171`), and the default path is `/tmp/pingora_upgrade.sock` (`configuration/mod.rs:232`). Any local user can connect and hand the new process sockets of its choice, or listen on the path first and receive the real listeners. *(our reasoning from the code)*
- Fixed limits: 2048-byte name buffer with "TODO: check the buf is large enough", 32 fds per message, 5 retries at 1 s (`transfer_fd/mod.rs:75`, `119`, `138`, `243-245`). [Issue #328](https://github.com/cloudflare/pingora/issues/328) (2024-07-15, open) asks for configurable retries; 0.9.1 has `upgrade_sock_connect_accept_max_retries` (`configuration/mod.rs:142`).
- Linux only: elsewhere `get_fds_from` returns `ECONNREFUSED` and `send_fds_to` is a no-op (`transfer_fd/mod.rs:229-240`, `381-392`).
- Blocking: `thread::sleep` retries on the calling thread.
- Fixed upstream in [PR #1001](https://github.com/cloudflare/pingora/pull/1001) (merged 2026-09-09, in 0.9.x): the accepted transfer socket leaked on every upgrade and received listeners lacked `FD_CLOEXEC`. The PR also notes that a new generation forked from the old one receives each socket twice.
- Unclaimed inherited `SO_REUSEPORT` sockets are now closed because they "can black-hole connections" (`transfer_fd/mod.rs:91-112`).

2.6 What `pingora-core` exposes: `pingora::server::Fds` (`new`, `add`, `get`, `serialize`, `deserialize`, `send_to_sock`, `get_from_sock`, `close_unclaimed`) and `ListenFds` (`server/mod.rs:57`, `127`). `send_fds_to`/`get_fds_from` are in a `pub(crate)` module (`mod.rs:22`) and cannot be called. `Fds` holds `RawFd`; turning one into a `TcpListener` needs `unsafe { from_raw_fd }`, which our crates forbid.

2.7 Conclusion *(our reasoning)*: reuse none of Pingora's transfer code. It is Linux-only, path-based with 0666, panicking, `RawFd`-based and TCP-only. Keep using what we already use: `HttpProxy::process_new(stream, &closing)` gives the HTTP/1 keep-alive-off and HTTP/2 GOAWAY behaviour once our `closing` watch fires (`listener.rs:433`, `582`). We implement ourselves: fd passing, the handover protocol, readiness and rollback, UDP, the admin sockets, the data-dir lock, drain bounds and metrics.

### A.3 H-PERF-04 — design space

3.1 **NGINX**: USR2 to the master renames the pid file to `.oldbin` and starts a new master and workers; both generations accept. WINCH stops the old workers gracefully. The old master "does not close its listen sockets" and can restart its workers (rollback with HUP to the old or TERM to the new master); QUIT to the old master finishes ([nginx.org control](https://nginx.org/en/docs/control.html)). Old workers "continue to service old clients" with no bound unless `worker_shutdown_timeout` is set (no default, since 1.11.11; [core module](https://nginx.org/en/docs/ngx_core_module.html)).

3.2 **HAProxy**:
- Before 1.8 a reload bound new `SO_REUSEPORT` sockets. Each socket has its own accept queue, so connections queued on the old socket were reset when it closed: 2–3 per million per reload, 155 per million in a lab at 55,000 conn/s and 10 reloads/s.
- The fix passes the listening fds over the CLI Unix socket with `SCM_RIGHTS` (`expose-fd listeners`, `-x`), "so that the connection is never closed"; at most 253 listeners ([Willy Tarreau, 2017-05-03](https://www.haproxy.com/blog/truly-seamless-reloads-with-haproxy-no-more-hacks)).
- In master-worker mode (`-W`) SIGUSR2 makes the master re-execute itself and fork new workers; the old ones unbind and "continue to process existing connections until they close" ([management guide 3.2](https://docs.haproxy.org/3.2/management.html)).
- `close-spread-time` spreads closes and is recommended below `hard-stop-after` ([configuration 3.2](https://docs.haproxy.org/3.2/configuration.html)); the exact `hard-stop-after` wording and default are *unverified*.

3.3 **Envoy hot restart**: old and new processes talk an RPC protocol over Unix domain sockets. The new process initialises fully, then asks for copies of the listen sockets, starts listening and tells the old one to drain. Counters and gauges are transferred. Existing connections are not handed over. `--drain-time-s` defaults to 600 s and `--parent-shutdown-time-s` to 900 s. With `reuse_port`, sockets are passed per worker index; lowering concurrency across a restart can drop queued connections ([hot restart](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/operations/hot_restart), [CLI](https://www.envoyproxy.io/docs/envoy/latest/operations/cli)). The current page does not mention shared memory.

3.4 **Cloudflare ecdysis** (Rust, crate `ecdysis` 1.1.1, Apache-2.0, 2026-04-14): the running process forks and the child `execve`s the new binary, inheriting the listening sockets. The parent keeps listening until the child reports ready, then closes its copy and drains. If the child fails during start it exits and nothing is lost. It has `Type=notify-reload` and socket-activation features, needs seccomp to allow `fork`/`execve`, and has been in production since 2021 ([Cloudflare blog, 2026-02-13](https://blog.cloudflare.com/ecdysis-rust-graceful-restarts)). `shellflip` 2.1.3 (BSD-3-Clause) is the Cloudflare variant that also passes state. Whether either is usable from a `forbid(unsafe)` crate with our own listeners is *unverified*.

3.5 **systemd** (man pages for systemd 262):
- `FDSTORE=1` with `FDNAME=` stores fds in the service manager. They come back on the next start via `LISTEN_FDS`, starting at fd 3, after the socket-activated ones, named `stored` if unnamed ([sd_notify](https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html), [sd_listen_fds](https://www.freedesktop.org/software/systemd/man/latest/sd_listen_fds.html)).
- `FileDescriptorStoreMax=` defaults to 0; `FileDescriptorStorePreserve=restart` is the default ([systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)).
- `MAINPID=` changes the tracked main process. `NotifyAccess=` is `none`/`main`/`exec`/`all`. `Type=notify-reload` sends SIGHUP and expects `RELOADING=1` with `MONOTONIC_USEC=`, then `READY=1`.
- *(our reasoning)* The fd store keeps the listening socket across a restart or crash, so new connections wait in the backlog instead of being refused. Established connections still die with the old process. It complements a handover and does not replace it.

3.6 **`SO_REUSEPORT`, eBPF, pidfd**:
- `net.ipv4.tcp_migrate_req` (default 0) migrates request and accept-queue sockets of a closing reuseport listener to another listener in the group, optionally steered by `BPF_SK_REUSEPORT_SELECT_OR_MIGRATE` ([kernel ip-sysctl](https://docs.kernel.org/networking/ip-sysctl.html)). Passing the same socket avoids the problem without sysctls or CAP_BPF. *(our reasoning)*
- `pidfd_getfd` (Linux 5.6) duplicates another process's fd without its cooperation but needs `PTRACE_MODE_ATTACH_REALCREDS` ([man-pages 6.19](https://man7.org/linux/man-pages/man2/pidfd_getfd.2.html)). Our unit's hardening and Yama settings may refuse it; `SCM_RIGHTS` over an inherited socket needs no privilege. *(our reasoning)*

3.7 **Migrating established connections**: none of the four proxies does it; old processes drain. kTLS moves only the record layer into the kernel after a user-space handshake ([kernel TLS](https://docs.kernel.org/networking/tls.html)); the document says nothing on passing such sockets between processes. HTTP/1 parser state, HTTP/2 stream and HPACK state and rustls state would also have to be serialised, and Pingora has no such interface. Not feasible for TLS/HTTP in v0.9 *(our reasoning; the absence of a rustls server-state export is unverified)*. UDP sessions and raw TCP relays hold no TLS state and could be migrated by passing their fds (§4.6).

3.8 **Bounding and observing the drain** *(our reasoning)*: a draining old process is an old binary, possibly a vulnerable one, still serving. Unbounded (NGINX, HAProxy defaults) is not "safe by default"; Pingora uses 300 s, Envoy 600 s plus 900 s. Proposal: `upgrade.drain`, default 10 m, `unlimited` allowed with a warning. Observability is in §4.5.

### A.4 H-PERF-04 — model for rdock

4.1 **Supervisor versus peer handover** *(our reasoning)*:

| | Permanent supervisor (NGINX/HAProxy master) | Peer handover (ecdysis, Envoy) |
|---|---|---|
| Processes in steady state | 2 | 1 |
| PID under systemd | stable | changes; needs `MAINPID=` |
| PID 1 in a container | works (supervisor reaps) | old process exiting ends the container |
| Upgrading the supervisor itself | needs self re-exec; inherited fds by number need `unsafe` or a crate | not applicable |
| Failed new binary | supervisor restarts old worker | old process never stopped listening |
| Fit with today's code | splits `rdock run` in two; signals, logs, exit codes forwarded | `rdock run` gains "start from handed-over sockets" and "hand over and drain" |

Recommendation: peer handover. The running process spawns the new binary with a Unix `socketpair` end as its **stdin**. `std::process::Command::stdin(Stdio::from(OwnedFd))` is safe std, needs no `CLOEXEC` changes and no socket path.

4.2 **Handover protocol** (proposal):
1. Trigger (§4.4). The old process verifies the new binary and runs `<new> validate` on the effective configuration.
2. Spawn `<new> run --inherit` with the socketpair. Send a versioned JSON manifest plus fds: every listener (name, address, transport), the admin TCP listener, the admin Unix listener, and the data-dir lock fd.
3. The new process loads the configuration, adopts the sockets, binds any it was not given, and builds everything **without accepting**.
4. The new process sends `ready`. The old process stops accepting on all listeners and on admin, and stops its writers (§4.3). Its fds stay open so there is one accept queue and nothing is reset (the HAProxy lesson).
5. The old process sends `go`. The new one starts accepting and sends `serving`. The old one sends `MAINPID=<new>` and `READY=1`, then closes its listener fds.
6. The old process drains until `upgrade.drain`, reports its open-connection count over the socketpair every second, and exits.
7. If the child exits, or `ready`/`serving` does not arrive within `upgrade.start_timeout`, the old process resumes accepting and reports the failure. Nothing was closed.

4.3 **Shared state during the overlap** *(our reasoning from the code in §1.5)*:
- **Data-dir lock**: add `<data>/rdock.lock` with an advisory `flock`. `std::fs::File::try_lock` has been stable since Rust 1.89, our MSRV (*unverified today*). The lock belongs to the open file description, so passing the fd keeps it held with no gap. A second independent `rdock run` is refused with a diagnostic.
- **Spool**: must become per process (`spool/<pid>/`, cleaned when the lock is taken without a predecessor), or the new process deletes the old one's held bodies.
- **Admin sockets**: the new process must adopt the fds, not unlink and rebind. The old one stops accepting admin connections at step 4, so a CLI call never reaches the stale process.
- **ACME, local CA, Cloudflare range sync, alerts, metering, audit log, config history**: single writer. The old process stops these at step 4 and the new one starts them at step 5.
- **Quota counters**: the old process flushes at step 4. Increments on its draining connections afterwards are lost unless sent over the socketpair at exit. Proposal: send them.
- **Disk cache**: the index is in memory (`crates/rdock-cache/src/store/index.rs:1`). Proposal: the old process serves draining requests with caches bypassed after step 4. How a second process's files interact with the store is *unverified*.
- **Providers**: Docker and Swarm watches are read-only; the old process stops them and keeps its last runtime. Kubernetes: the lease holder identity is `<pod>_<random>` per process (`runtime/mod.rs:225`) and the old leader releases on shutdown (`runtime/lease.rs:13`), so two processes cannot both lead.
- **Metrics**: counters restart from zero; Prometheus handles resets. Add `rdock_upgrade_generation`, `rdock_upgrades_total{result}`, `rdock_upgrade_draining_connections` (fed by the old process), `rdock_upgrade_drain_deadline_seconds`.
- **Sticky cookies** survive: `sticky.key` is on disk (`run.rs:72-93`).
- **TLS tickets** do not survive today (§1.4); see §7.
- **On-disk format skew**: the manifest carries a data-format version. The new binary refuses a data dir newer than it understands, so a downgrade is refused before `ready`. The old binary never reads formats written by the new one because it stopped writing and only drains.

4.4 **Triggers and security** *(our reasoning)*:
- Triggers: `rdock upgrade [--binary <path>]` over the admin **Unix socket** only (mode 0600 already, `server.rs:259`), and SIGUSR2 (the NGINX convention; SIGQUIT keeps meaning stop). Never the TCP API or dashboard: an upgrade executes a file.
- The binary must be a regular file, not group- or world-writable, owned by root or the running user.
- Optional `upgrade.trusted_keys`: verify `<binary>.minisig` with the existing verifier (`crates/rdock-wasm/src/minisign.rs`), which would move to a shared crate. Releases today are signed with keyless cosign bundles and attestations (`.github/workflows/release.yml`), not minisign. Either add a minisign signature to releases or document `cosign verify-blob` as an operator step; Sigstore verification in-process is a large dependency.
- Privileges: the unit runs unprivileged with `NoNewPrivileges` and ambient `CAP_NET_BIND_SERVICE`; the child inherits the same credentials and needs no bind because sockets are inherited. With `DynamicUser=yes` and `ProtectSystem=strict` the binary must be replaced by root at `/usr/local/bin/rdock`; rdock only re-executes its own path.
- The audit log records who triggered the upgrade, the binary's SHA-256 and the result.

4.5 **Platforms**:
- systemd: add `NotifyAccess=main` (the old main process sends `MAINPID=`), keep `ExecReload` as HUP for configuration. `KillMode` stays the default so a stop ends both generations. `TimeoutStopSec` is unrelated to the upgrade drain. How systemd treats a main PID that is not its direct child is *unverified*; it needs a test under real systemd.
- Container as PID 1: refuse `rdock upgrade` with a diagnostic ("replace the container; in-place upgrade needs a service manager or `rdock supervise`"). A new image means a new container, and Kubernetes and Swarm rolling updates replace instances. In-place upgrade matters on systemd or bare metal and for Docker with a bind-mounted binary. A minimal `rdock supervise` PID 1 reaper is a planned item, only on demand.
- macOS: handover by `SCM_RIGHTS` should work with `rustix` (*unverified*); test on Linux and gate the rest.

4.6 **UDP sessions and TCP relays**: both generations share the UDP listener socket, so datagrams of existing sessions reach whichever process reads. Baseline: at step 4 the old process ends its UDP sessions, as an in-process hand-off already does (`server.rs:294-296`); clients' next datagrams open sessions in the new process. Stretch: migrate sessions, since a session is client address, route and a connected backend socket (`docs/05-architecture.md:434`); pass each backend socket with `SCM_RIGHTS` and its metadata. Raw TCP relays could be migrated the same way, both fds plus buffered bytes; proposed as planned, not v0.9.

std's `unix_socket_ancillary_data` is still unstable ([rust-lang/rust#76915](https://github.com/rust-lang/rust/issues/76915), open, last activity 2026-10-22). tokio's `UnixStream` has no ancillary-data API (*unverified today*). The handover is a few messages; do it with `rustix` on a blocking `std::os::unix::net::UnixStream` inside `spawn_blocking`.

4.8 **Testing** *(our reasoning)*: the e2e tests already start the real binary (`crates/rdock/tests/e2e_lifecycle.rs:22`), and `rdock-testkit` has HTTP, TCP and UDP backends and clients. New `e2e_upgrade.rs` (Linux):
- **Held set**, opened before the swap and exercised every 100 ms: a WebSocket echo, an SSE stream, a chunked upload trickling one byte per 100 ms, an HTTP/2 stream with a slow response, a TLS-passthrough TCP echo, a UDP echo session.
- **Connect loop**: at least 1,000 new connections per second per listener (HTTP, HTTPS, TCP), one request each. Assert zero connect errors, zero resets, every response complete, and the answering process changes from old to new once (pid from the admin status endpoint).
- **(a) Binary upgrade** to a copy of the same binary:
  - held connections stay alive until `upgrade.drain` (set to 5 s) and are closed at the deadline;
  - the HTTP/2 client sees GOAWAY at handover while its stream continues;
  - the old process exits within drain plus 2 s, with no zombie and no leftover spool files;
  - the UDP session behaves per §4.6;
  - `admin.sock` answers throughout, and the lock stays held.
- **(b) Listener-set change**: a reload adds, removes and moves listeners under the same load. Held connections on unchanged listeners are untouched, those on removed listeners live until drain, and the connect loop on unchanged addresses sees no failure.
- **Failure cases**: the child exits before `ready`, the child is killed between `ready` and `serving`, the binary is unverifiable or world-writable, the process is PID 1. In each the old process keeps serving with zero failed connections.
- **CI**: runs on the hosted `ubuntu-24.04` runner inside the existing `rust` job. A weekly job runs the unit under real systemd for the `MAINPID=` path, and a Docker job checks the PID 1 refusal (both *unverified* on hosted runners).

### A.5 H-PERF-01 — runtime and sockets

5.1 Pingora 0.9.1 knobs, all on its `Server`, which we do not run:
- `threads` per service (default 1; `Service::threads()` override, `server/mod.rs:727`).
- `work_stealing` (default true) selects between a multi-thread runtime and `NoStealRuntime`, N current-thread runtimes (`pingora-runtime-0.9.1/src/lib.rs:239`, `529-534`, `592-650`).
- `listener_tasks_per_fd`, `max_blocking_threads`, `blocking_threads_ttl_seconds`, `runtime_enable_alt_timer`, poll-time histogram options (`configuration/mod.rs:74-177`).
- No CPU pinning anywhere in `pingora-runtime` (grep for `affinity`: none).
- Listener options in `TcpSocketOptions`: `ipv6_only`, `tcp_fastopen`, `tcp_keepalive`, `dscp`, `so_reuseport`, send and receive buffers; backlog fixed at 65535 with "TODO: configurable backlog" (`listeners/l4.rs:64-65`, `98-122`).
- `pingora::protocols::l4::ext` is public: `set_recv_buf`, `set_snd_buf`, `set_tcp_fastopen_backlog`, `set_dscp`, `set_tcp_keepalive`, `get_tcp_info`, all taking `RawFd`.

5.2 tokio 1.54.1 `Builder`: `worker_threads` (default: cores), `max_blocking_threads` (512), `thread_keep_alive` (10 s), `global_queue_interval`, `event_interval` (61), `max_io_events_per_tick`, `on_thread_start`, `thread_stack_size`. `disable_lifo_slot`, `enable_alt_timer` and the poll-time histogram need `tokio_unstable`. There is no affinity API ([docs.rs](https://docs.rs/tokio/1.54.1/tokio/runtime/struct.Builder.html)). Pinning would go through `on_thread_start` with `rustix`'s `sched_setaffinity` (*unverified signature*) or `core_affinity` 0.8.3 (MIT/Apache-2.0, 2025-03-01).

5.3 Accept models:
- One shared listen socket with epoll wakes the busiest worker (LIFO). Per-worker `SO_REUSEPORT` sockets balance better, but a stalled worker stalls its own queue: maximum latency 72.65 ms shared versus 144.55 ms with reuseport in the author's test ([Cloudflare, 2017-10-23](https://blog.cloudflare.com/the-sad-state-of-linux-socket-balancing/)).
- Envoy assigns "all streams for a given connection to a single worker thread" and offers `ExactBalance` for "a small number of connections that rarely cycle" ([benchmark FAQ](https://www.envoyproxy.io/docs/envoy/latest/faq/performance/how_to_benchmark_envoy), [listener API](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/listener/v3/listener.proto)).
- *(our reasoning)* rdock has one accept task per listener on a work-stealing runtime and spawns a task per connection, so long-lived connections are not pinned to the accepting thread. Per-thread reuseport would only raise the accept rate, and the TLS-new scenario is limited by handshakes, not `accept`. `SO_REUSEPORT` also lets another process of the same user bind the port silently, which weakens our "address in use" diagnostic, and every extra socket must be passed in a handover. Keep it off by default; offer it as an option.

5.4 Missing, and proposed as `listeners.<name>.socket` (bind through `socket2`):
- `backlog`: default 4096. `somaxconn` defaults to 4096 since Linux 5.4 and caps the value ([ip-sysctl](https://docs.kernel.org/networking/ip-sysctl.html)); today's 128 is the gap that matters most under connection bursts.
- `reuse_port` (default false), `receive_buffer`, `send_buffer` (unset = kernel autotuning).
- `keepalive` idle/interval/count and `user_timeout` for accepted connections.
- `fast_open`: off by default; needs sysctl bit 0x2 on the server (ip-sysctl).
- `ipv6_only`, `dscp`.
- Process level: `runtime.worker_threads`, `runtime.max_blocking_threads`, `runtime.cpu_affinity` (planned, benchmark first).
- Refuse `reuse_port` together with a `udp` listener until §4.6 handles it.

### A.6 H-PERF-03 — HTTP/2 and backpressure

6.1 Pingora exposes the whole `h2::server::Builder` as `H2Options` (`protocols/http/v2/server.rs:53`), set per `HttpProxy` through `h2_options` (`apps/http_app.rs:116`). `default_h2_options()` sets `max_header_list_size` 64 KiB and `max_concurrent_streams` 100 (`server.rs:56-74`), and we use exactly that (`listener.rs:215`). Also in Pingora: a budget of 32 malformed streams per connection (`server.rs:59-63`) and `HttpServerOptions::h2_idle_timeout`, which we set to the listener's idle timeout (`listener.rs:213`). There is **no downstream keep-alive PING**; `ping_pong` is used only in the client (`v2/client.rs:592`).

6.2 `h2` 0.4.20 (2026-10-06, MIT, MSRV 1.63; `Cargo.lock`) builder knobs and defaults:
- Settable: `initial_window_size`, `initial_connection_window_size`, `max_frame_size`, `max_header_list_size`, `header_table_size`, `max_concurrent_streams`, `max_concurrent_reset_streams`, `reset_stream_duration`, `max_pending_accept_reset_streams`, `max_local_error_reset_streams`, `max_send_buffer_size`, `data_frame_budget`, `enable_connect_protocol` (`h2-0.4.20/src/server.rs:698-1067`).
- Defaults: initial window 65,535 (`frame/settings.rs:44`), pending-accept resets 20, local error resets 1024, reset streams 50 for 1 s, send buffer 400 KiB per stream (`proto/mod.rs:34-47`).

6.3 Flood mitigations in our pinned version:
- **Rapid Reset (CVE-2023-44487)**: `max_pending_accept_reset_streams` since 0.3.17 (2023-04-13, changelog). hyper states it was not affected with h2 ≥ 0.3.18 ([seanmonstar, 2023-10-10](https://seanmonstar.com/blog/hyper-http2-rapid-reset-unaffected/)).
- **CONTINUATION flood**: fixed in 0.3.26 and 0.4.4 ([RUSTSEC-2024-0332](https://rustsec.org/advisories/RUSTSEC-2024-0332.html), 2024-04-03).
- **MadeYouReset (CVE-2025-8671)**: h2 before 0.4.11 was "potentially susceptible" ([Cloudflare blog](https://blog.cloudflare.com/madeyoureset-an-http-2-vulnerability-thwarted-by-rapid-reset-mitigations)); Pingora before 0.6.0 has [RUSTSEC-2025-0070](https://rustsec.org/advisories/RUSTSEC-2025-0070). The limit is `max_local_error_reset_streams`, "Limit error resets" in 0.4.2 (2024-01-17).
- 0.4.16–0.4.20 add limits on small DATA frames (`data_frame_budget`). Pingora requires `h2 >= 0.4.16`.

6.4 Bounded queues in our paths (code):
- Mirror bodies are capped at 64 KiB (`proxy.rs:1826`).
- UDP session queue is 64 datagrams, dropped when full (`udp/mod.rs:56`).
- Agent answers are capped at 1 MiB (`agent.rs:44`).
- Metering, alerts and ACME use bounded `mpsc` channels (`metering.rs:271`, `alerts/mod.rs:89`, `manager.rs:86`).
- No `unbounded_channel` exists in non-test code (grep).
- Held bodies go to the spool on disk, limited by the route's `max_body` (`held.rs`).
- Not audited here: cache fill memory per object, WASM host buffers, and Pingora's own response buffering toward a slow HTTP/2 client beyond the 400 KiB h2 send buffer (*unverified*).

6.5 Proposal *(our reasoning)*: expose `http2.max_concurrent_streams` (100), `initial_stream_window`, `initial_connection_window`, `max_frame_size`, `max_header_list_size`, `max_pending_accept_reset_streams`, `max_local_error_reset_streams`, `max_send_buffer` per listener, with h2's and Pingora's defaults unchanged. Raise window defaults only with upload benchmark evidence. Refuse values that disable a flood limit unless spelled `unlimited`. A downstream keep-alive PING needs a Pingora change and is planned. Add a test with a slow HTTP/2 reader asserting that proxy memory stays flat.

### A.7 H-PERF-02 — TLS

7.1 rustls 0.23.46 (Apache-2.0 OR ISC OR MIT, MSRV 1.71):
- Stateful resumption uses `session_storage`, default `ServerSessionMemoryCache::new(256)`; stateless uses `ticketer`, default none; `send_tls13_tickets` is 2 (`server/builder.rs:113-123`).
- `ring::Ticketer::new()` is a `TicketRotator` over ChaCha20-Poly1305 keys, rotating every 6 h and accepting the previous key, so the lifetime is 12 h (`crypto/ring/ticketer.rs:23-33`, `193`; `ticketer.rs:245-331`).
- `TicketRotator::new` takes a plain `fn()` generator, so keys cannot be injected; shared keys need our own `ProducesTickets` (`server/server_conn.rs:83-113`).
- rustls warns that configs sharing a ticketer or session store must have equivalent client-auth and certificate-resolver settings, or a session from a listener without client authentication could be resumed on one that requires it (`server_conn.rs:268-292`).

7.2 Guidance:
- TLS 1.3 tickets: "Servers MUST NOT use any value greater than 604800 seconds (7 days)" ([RFC 8446 §4.6.1](https://www.rfc-editor.org/rfc/rfc8446.txt)).
- [RFC 5077 §5.5](https://www.rfc-editor.org/rfc/rfc5077.txt): keys at least 128 bits strong, used for nothing else, "changed regularly".
- Cloudflare rotates ticket keys hourly, keeps them 18 h for decryption, distributes them without writing to disk, and notes that a leaked long-lived key breaks forward secrecy ([blog, 2015-02-24](https://blog.cloudflare.com/tls-session-resumption-full-speed-and-secure/)).
- Mozilla's current server-side TLS text on tickets was not retrieved (*unverified*).

7.3 0-RTT stays off: early data "is not forward secret" and has "no guarantees of non-replay between connections" (RFC 8446 §2.3), and §8 asks servers to implement an anti-replay method. A proxy cannot know which upstream requests are replay-safe. *(our reasoning)*

7.4 Handshake offload:
- Pingora 0.9.1 has it for rustls: `TlsSettings::set_offload_threadpool(shards, threads_per_shard)` builds dedicated current-thread runtimes, and `Acceptor::tls_handshake` runs the whole handshake there (`listeners/tls/rustls/mod.rs:43-47`, `98-106`, `170-177`, `228-255`; `offload.rs`).
- Our `acceptor()` already goes through `TlsSettings::…build()` (`listener.rs:116-129`), so enabling it is one call. Caveat: each rebuilt acceptor creates its own pool.
- `ResolvesServerCert::resolve` is synchronous; for I/O during selection rustls points to `Acceptor`/`LazyConfigAcceptor`. We resolve from memory, so this is not a limit for us.
- Signing cost (RSA versus ECDSA with ring) and what linkerd does are *unverified*; our TLS-new numbers are with a P-256 certificate (`benchmarks/README.md`).
- *(our reasoning)* With ECDSA the offload mostly adds thread hops; it can pay for RSA certificates or to keep handshake storms from starving established connections. Ship as `tls.handshake_threads` (default 0 = off) only after benchmarks with an RSA-2048 and a P-256 certificate.

7.5 Proposal *(our reasoning)*:
- One process-wide ticketer per security class (TLS policy plus client-auth identity), shared by listeners and kept across reloads.
- Our own `ProducesTickets` on ring ChaCha20-Poly1305 with a 16-byte key name, current plus previous key, rotation `tls.tickets.rotate` default 6 h (rustls's current default).
- Keys handed to the new process over the upgrade socketpair, never written to disk by default.
- Optional `tls.tickets.key_file` for sharing across instances, operator-rotated, with a diagnostic if it is older than 24 h. Automatic distribution belongs to the control plane (H-HA).
- `tls.session_cache.size` (default 256 per class) and `tls.tickets.enabled`.

Compare peak req/s, p99, CPU per request, RSS at the end, RSS after load stops, and RSS growth from `soak/analyze.py`. Ship the winner as the default feature and keep the others as Cargo features, not a runtime option. This needs a quiet machine.

8.5 Sizing guidance to document (sourced where possible, otherwise measured by us):
- Workers = CPUs available to the cgroup; say what tokio counts in a CPU-limited container.
- Per-connection memory, from our 64 KiB buffers.
- `LimitNOFILE`: two fds per proxied request (`run.rs:39-43`).
- Backlog and `somaxconn`.
- `upstream_idle_connections`.
- HTTP/2 windows × streams as worst-case memory per connection.
- Disk cache and spool placement.
- NUMA: pin the process to one node with `numactl` or cgroup cpusets rather than in-process pinning, until `runtime.cpu_affinity` has evidence.

### A.9 Soak

9.1 Tooling: `benchmarks/soak/` (`run.sh`, `soak.js`, `probe.sh`, `analyze.py`) runs k6 at a fixed rate against rdock limited to 2 CPUs and 1 GiB, with a reload every 5 min, a backend outage every 15 min and a certificate change every 30 min. It samples RSS, threads, fds and connections every 30 s and checks growth limits (16 MiB memory, 64 fds).

9.2 History: the v0.5 release candidate passed 24 h (86,306,108 requests, none failed, +0.3 MiB) on a Hetzner server with 8 vCPUs (`benchmarks/results/2026-11-02-small-cpu/soak/report.md`). v0.6 passed 2 h; its 24 h run was cut when the server was retired on 2026-11-07 (`docs/07-roadmap.md:53`). There is no test server now.

9.3 GitHub-hosted limits: a job is terminated after 6 hours; self-hosted jobs may run 5 days; a workflow run 35 days ([Actions limits](https://docs.github.com/en/actions/reference/limits)). Standard Linux runners for public repositories have 4 CPUs and 16 GB ([runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)).

9.4 What is honest *(our reasoning)*:
- A 24 h soak of one process cannot run on hosted runners. Chaining jobs restarts the process, which is exactly what a soak must not do.
- Possible on hosted runners: a weekly soak of about 5 h at a reduced rate, labelled as such. Memory, fd, failure and reload checks are valid; latency is not, because of shared hardware.
- The roadmap criterion "24 h soak at target RPS" needs a rented machine or a self-hosted runner for a day, and a number for "target RPS", which the roadmap does not define.
- For v0.9 the soak must add a binary upgrade every 30 min with held WebSocket and SSE connections, check that every old generation exits by its deadline, compare steady-state RSS between generations, and follow pid changes in `probe.sh`.

### A.10 Recommended design and step order

## Part B — Issue 181: the performance plan and today's hot path

Nothing was built, run or measured. Everything below is from reading issues, published results, CI logs, `main` at `dab5194` and the Pingora 0.9.1 sources on 2026-11-13. Compared with `3bbab6a` (v0.6) using `git show` and `git diff`. Lines marked *(our reasoning)* are conclusions, not measurements.

### B.3 Step 4, the TLS tail

#### What the result files say that the issue does not

From `benchmarks/results/*/tls/*-10000.json`:

| Run, `tls` at 10,000 req/s | p99 ms | p99.9 ms | max ms | dropped iterations |
|---|---:|---:|---:|---:|
| ReverseDock v0.5 | 2.10 | 30.72 | 73.7 | 183 |
| NGINX (v0.5 session) | 1.76 | 4.84 | 23.8 | 0 |
| HAProxy (v0.5 session) | 1.79 | 63.59 | 113.9 | 273 |
| ReverseDock v0.6 | 2.50 | 40.93 | 62.8 | 300 |
| NGINX (v0.6 session) | 2.02 | 5.78 | 25.4 | 0 |
| HAProxy (v0.6 session) | 2.20 | 55.17 | 113.7 | 10 |

- HAProxy has the same tail, worse than ours. The issue table shows "—" in that cell.
- In `single`, `lb` and `routes` nobody drops an iteration and all three proxies have a p99.9 of 3.7–8.6 ms.
- At 20,000 req/s ReverseDock drops 2,642 and 2,447 iterations with a max of 132.6 and 150.1 ms.

*(our reasoning)* This is one or two stalls per run, not a steady delay:

- `load.js:22` preallocates `min(2000, max(50, RATE/20))` VUs: 500 at 10,000 req/s. k6 drops an iteration only when no VU is free, so more than 500 requests were in flight, which needs about 50 ms without completions.
- A total stall of T ms at 10,000 req/s leaves (T − 30.7) × 10 requests slower than 30.7 ms. The 300 requests that p99.9 needs give T ≈ 61 ms; the observed max is 73.7 ms.

#### Most likely cause: a handshake burst at the start of every run

- `run.sh:62` runs the warm-up as a separate k6 process, so each measured run starts with no connections.
- k6 1.3.0 hands iterations to VUs over an unbuffered channel (`lib/executor/ramping_arrival_rate.go`, `activeVUPool`, fetched 2026-11-13). *(our reasoning, not verified in the Go runtime)* waiting receivers are served in arrival order, so all preallocated VUs are used in turn and each opens its own TLS connection.
- VUs ÷ rate is 50 ms at every rate, so handshakes arrive at the target rate for the first 50 ms: 5,000, 10,000 or 20,000 per second.
- ReverseDock's measured `tls-new` peak is 5,821 per second. At 5,000 it keeps up (p99.9 3.4 ms). At 10,000, 500 handshakes take about 86 ms of both CPUs (max observed 73.7 ms). At 20,000, 1,000 take about 172 ms (max observed 132.6 ms).
- Our accept loop accepts and spawns without bound (`listener.rs:402-414`) and the handshake runs on the tokio workers (`listener.rs:544`). There is no limit on concurrent handshakes, so requests on established connections queue behind them.
- It fits #176: per-core made the tail worse (4.3 → 18.3 ms at 5,000) because a core cannot hand its handshake backlog to the other.

What this does not explain: why NGINX shows no stall. One possibility is that NGINX accepts one connection per event-loop pass by default, so the burst waits in the accept backlog, which k6's `http_req_duration` does not count. I did not verify that.

#### Hypotheses ruled out by reading

- **Nagle and delayed ACK.** `TCP_NODELAY` is on downstream (`listener.rs:492`, before the handshake) and upstream (`pingora-core-0.9.1/src/connectors/l4.rs:231`). The 8 KiB buffer sits above TLS, so header and body are one plaintext write and one record. NGINX also has `tcp_nodelay on` by default and `tcp_nopush off` (nginx.org core module, 2026-11-13).
- **Ticket rotation.** `rdock-tls/src/policy.rs:40` uses the ring `Ticketer`; it takes a lock only when a ticket is issued at a handshake (`rustls-0.23.46/src/ticketer.rs:248, 337`), never on a reused connection.
- **Pingora's 10 ms timers.** `pingora-timeout-0.9.1/src/timer.rs:39` rounds when a timeout fires, not when I/O is ready.

Not ruled out: CFS throttling during the burst. The CPU ladder recorded `nr_throttled` only for `single`.

#### Cheapest experiment

Run `tls` at 10,000 req/s twice in the same session: as today, and with the connections opened gradually (a `ramping-arrival-rate` start in the same k6 process, or a p99.9 that excludes the first 2 s). Record `cpu.stat` `nr_throttled` and the `rdock_connections_total` delta. The effect is about 6×, so it shows on a noisy machine. `strace -c` on the same run confirms one `sendto` per response under TLS.

If the tail goes away, two separate decisions follow:

- The benchmark should not measure its own connection storm in a scenario named "reused connections".
- The product has a real weakness: a storm of new TLS connections delays established ones. Bounding concurrent handshakes per listener, or a handshake pool (H-PERF-02), addresses it.

### C.1 Where we start

| Fact | Source |
|---|---|
| Policies today: `round_robin` (smooth weighted), `random`, `least_conn` = `least_requests` (`weight / (in_flight + 1)`), `p2c` (two weighted random picks, fewer in-flight relative to weight wins), `ip_hash`, `header_hash`, `cookie_hash`. #### C.2.2 What to measure, and interactions *(our reasoning)*

- **Nothing in Pingora helps**; the balancer stays ours (ADR-0022 already decided that). Peak-EWMA is ~60 lines next to `p2c` in `rdock-balancer`: per `BackendState` a `Mutex<{ rtt_ns: f64, updated: Instant }>`, a `Choice.cost: f64` input, and a new `Balancer::PeakEwma`.
- **Latency = time to response headers** of the attempt (`attempt_started` → `upstream_response_filter`), not time to last byte. Reasons: it is what NGINX calls `header` and what tower's default completion measures; total time punishes backends for large downloads and client speed; streams never end. The in-flight term (`pending + 1`) already covers long bodies because our `InFlight` guard lives until the request ends.
- **Excluded from the RTT sample**: upgrades (WebSocket/`CONNECT`), gRPC streaming and SSE cannot be told apart before the header, but TTFB is still meaningful for them; exclude only requests answered by a middleware, cache hits, and attempts that failed before headers. A failed or timed-out attempt records its elapsed time (a peak), which is what makes Peak-EWMA shed a stalling backend before passive health reaches 5 failures.
- **Default RTT**: seed new backends with **the pool's current mean estimate, floor 1 ms, 30 ms when the pool has none** (Linkerd's default and floor). Tower's 1 s default would starve new backends for several decay periods in a fast pool; Finagle's penalty has the same effect.
- **Weights**: divide the cost by the weight (`cost / weight`, compare without division as `less_loaded` does today). **Slow start**: the ramped weight feeds the same division, so a ramping backend looks more expensive; no second mechanism. **Health/ejection/drain/max per backend**: unchanged, they filter `eligible()` before the pick. **Sticky sessions**: checked before the balancer today and stay so; the sticky hit still records its RTT. **Hash policies**: unaffected.
- **Two distinct picks**: our `p2c` can draw the same backend twice (`p2c(&list, 0, 0)` test). For Peak-EWMA use distinct draws when ≥ 2 eligible, as tower does; consider the same fix for `p2c`.
- **"Adaptive weights from observed health"** (second half of H-LB-01): the honest reading is ALB's ATW / Envoy's success-rate ejection. Proposal: no separate weight controller; Peak-EWMA plus the statistical detectors of §3 cover it. A continuous "success-rate weight" is a cut line.
- Config: `load_balancer: { policy: peak_ewma, decay: 10s }` (default 10 s: Finagle and Linkerd, 2026-11-13). Default policy stays `round_robin` (Traefik `wrr`, NGINX, Envoy default; unchanged behaviour on upgrade).

#### C.3.2 Gap against our passive health *(our reasoning)*

Already equal or stricter than Envoy's consecutive detectors: counting window, status list, cap on ejected share, back-off, half-open trial (Envoy has none). Missing:

1. **Statistical detectors**: success-rate (mean − 1.9 σ across hosts) and failure-percentage (85 %), evaluated every interval with minimum hosts and volume. These catch the backend that fails 30 % of requests and never reaches "5 in 30 s" at low volume or stays just under at high volume.
2. **Latency outlier**: none in Envoy core. With Peak-EWMA (§2) a slow backend already loses traffic; a latency ejection is a cut line.
3. **Jitter** on ejection time (Envoy offers it, default 0), to stop synchronized returns.
4. **Slow start on join**: new backends get full weight at once. Envoy starts at creation, HAProxy/ALB deliberately not at start-up or into an empty pool.
5. **Shape**: no `aggression`, floor is "1 weight unit" instead of a percentage.

Proposal: `health.passive.outlier: { success_rate: {…}, failure_percentage: {…}, interval: 10s }`, both **off by default** with Envoy's numbers when turned on (Envoy itself enforces failure-percentage at 0 %; success-rate needs ≥ 5 hosts, which most of our pools lack). `slow_start: 30s` keeps working; the long form `slow_start: { window, aggression: 1.0, min_weight_percent: 10, on: [recovery, join] }` adds the rest. `join` applies only when the pool already has a healthy backend that is not ramping (ALB's rule), so a start-up or an empty pool never ramps. Refuse `slow_start` with hash policies (NGINX does; a ramp breaks key affinity) with a diagnostic. Counters: two `AtomicU32` (total, failed) per backend swapped each interval by the existing health task.

- **A true hedge is not possible inside `ProxyHttp` in 0.9.1.** Two ways around it, both costly: (a) answer from `request_filter` with our own hyper client (`ServiceFetcher` already exists for error pages) racing two backends, which bypasses Pingora's upstream path: connection pool (ADR-0023), h2 to backends, response/body filters, cache, retries, passive-health accounting would all need a second implementation; (b) subrequests, which duplicate the whole pipeline (middlewares, limits, logs) and still need glue to cancel the loser.   - **Rotation**: add `client_auth.ca` paths and `services.*.tls.{ca_file,cert_file,key_file}` to `referenced_files`; then `spiffe-helper` (daemon mode) or csi-driver-spiffe writing files rotates SVIDs with no further code. SVIDs live about an hour, so this watch is required, not optional. Verify that a reload re-reads upstream client certificates without dropping pooled connections wrongly (pool `group_key` already separates TLS identities; *unverified*).
  - **To backends**: `services.<s>.tls: { cert_file, key_file, ca_file, verify_hostname: false }` already expresses "present my SVID, verify the chain against the bundle". Checking the **backend's SPIFFE ID** is not possible with Pingora 0.9.1's fixed verifier → document as open, needs an upstream hook; do not pretend hostname-less verification is identity.

### C.11 Tenant isolation (H-SEC-07)

| Fact | Source |
|---|---|
| Kong workspaces partition services, routes, plugins with RBAC per workspace; "Kong Gateway Enterprise ships with the `default` Workspace"; routing still happens on one data plane, and a route that duplicates one in another workspace is refused with `409 Conflict` when the host matches | [Kong workspace entity](https://developer.konghq.com/gateway/entities/workspace/) |
| Envoy Gateway multi-tenancy: "each tenant deploy their own Envoy Gateway controller in their respective namespace", `watch.namespaces`; Gateway Namespace Mode puts proxy infrastructure in the Gateway's namespace; `mergeGateways` shares one fleet | [Envoy Gateway deployment modes](https://gateway.envoyproxy.io/docs/tasks/operations/deployment-mode/) |
| Gateway API's own tenancy model (namespaces, `allowedRoutes`, ReferenceGrant) is already enforced by our provider and passes conformance | ADR-0029; `CLAUDE.md` status line |
| Traefik isolates by namespace in the CRD provider (cross-namespace references off by default); Caddy and HAProxy have no tenant concept in the open-source core | *unverified today* |
| Our model: objects are `name@provider` with one owner; merge order `file > api > kubernetes > swarm > docker`; losers are flagged *shadowed*; only API-provider objects are mutable through the admin API | ADR-0009; ADR-0024 |

*(our reasoning)* "Tenant" in our model can only mean **a scope over API-provider objects plus consumers**, because file and label providers have a single operator and Kubernetes already has namespaces. Minimum coherent step for v0.9:

1. **Token and user scopes**: `scope: { tenant: <name> }` on tokens/users. A tenant-scoped caller sees and edits only API objects named `<tenant>/<name>` (prefix enforced server-side on create; reads of other providers' objects filtered to nothing or to redacted names), cannot touch listeners, certificates, settings, users, or other tenants' consumers/keys. Unscoped = today's behaviour.
2. **Host claims**: `tenants.<t>.hosts: ["*.acme.example.com"]`. A tenant route whose `Host`/`HostSNI` is not inside its claim, or that has no host matcher at all, is **refused at validation** (Kong's 409, stronger: by claim, not by first come). Tenant objects may reference only their own services/middlewares (a small allow-list of shared middlewares by name). Tenant middlewares are limited to a safe set: no `plugin`, `wasm`, `agent`, `forward_auth` to arbitrary addresses, `static` (reads our disk), `errors.file`: refused for scoped callers.
3. **Limits per tenant**: object-count caps (routes, services, middlewares) reusing ADR-0025's admin limits.
4. **Audit**: audit entries carry `tenant`; tenant-scoped callers read only their own entries.
5. **Metrics/logs**: do **not** add a `tenant` label to existing families (cardinality × every label set). Offer `GET /tenants/<t>/metrics` that filters the existing families by the tenant's route/service names, and a `tenant` access-log field derived from the route name. Label isolation on the Prometheus endpoint itself belongs to the scraper.

Cut to the control plane (`rdock-control`, H-HA-01): tenant-owned listeners/certificates and ACME, per-tenant data-plane isolation (separate processes/pools), tenant self-service of users, tenant quotas on bandwidth/CPU, a dashboard tenant switcher. State plainly that tenants share one data plane: a noisy tenant is contained only by the limits of §6 and §7.

### C.16 Risks

- **Peak-EWMA on small pools** (2–3 backends, typical for Docker users): P2C degenerates to "compare the only two"; one slow request (a peak) starves a backend for up to a decay period. Mitigation: documented as a policy for ≥ 3 homogeneous backends; default stays round robin.
- **Statistical ejection with few hosts** ejects healthy backends; Envoy's minimum of 5 hosts is the guard. Keep it non-optional below 3.
- **Fingerprint peek on every TLS connection**: one extra read path on the handshake hot path, exposure to malformed/oversized hellos (the parser is bounded and already fuzz-worthy: add it to H-ENG-03 fuzzing), and ECH will hide the inner hello (the outer one is what we would fingerprint). Carrying data via `OnceLock` in `Handshake` is untested.
- **JA4 trademark/licence drift**: FoxIO controls the name and could change terms for future revisions; pin the spec commit we implement and keep JA4+ out.
- **GeoIP correctness and law**: wrong country = wrongful block; stale DB breaches GeoLite's EULA; geo fields in logs are personal data. All off by default, freshness metric, docs.
- **`maxminddb` 0.33.0 freshness** (published yesterday) and unknown handling of crafted files.
- **Abuse bans by IP** behind NAT/CGNAT or a misconfigured trusted proxy ban many users or the proxy itself; bounded tables can be churned by attackers to evict real entries (LRU) → ban list kept separate from the counter table.
- **SVID rotation**: with ~1 h lifetimes, a missed file event means an outage; the watcher must cover CA and upstream files and reload must be atomic for cert+key pairs (two files change non-atomically: retry on a mismatched pair, as certificate reload presumably does today: *unverified*).
- **Tenancy gives a false sense of isolation**: one process, shared CPU, shared listeners; any middleware that reads files or calls out is an escape hatch unless refused for scoped callers.
- **Scope**: this half of v0.9 is thirteen steps before the control plane, fd transfer and HTTP/3; the cut lines above are what keep it shippable.

### D.1 Where we start

#### D.1.1 What the code already has

- **Complete, serialisable snapshots.** A provider emits a whole `Snapshot { provider, fragment, diagnostics, revision }`, never a diff (`crates/rdock-config/src/merge.rs`, ADR-0009). `Fragment` and `Snapshot` derive `Serialize`/`Deserialize`.
- **Last-known-good and history on disk.** `StateDir` (`crates/rdock-config/src/state.rs`) writes `state/lkg.json`, `state/history/<ms>-<hash>.json` (50 entries) and `state/providers/<name>.json`, all with temp file plus rename. Entries hold the document as written, with references unresolved.
- **Boot from LKG.** `Engine::boot` falls back to `lkg.json` when the file cannot be used. `restore_snapshots` serves stored provider snapshots until providers report (`crates/rdock/src/engine.rs`).
- **One apply path.** File reload, provider events and API writes all go through `Engine::apply` → `compile_and_apply`, which either applies or returns a `Report` with `result: rejected` and diagnostics. This is already an ACK/NACK in all but name.
- **API provider with optimistic concurrency.** `api_etag`, `api_write(candidate, if_match)` and `api_dry_run` exist (`crates/rdock/src/engine/api.rs`); writes need `If-Match` (ADR-0024).
- **ACME challenge answers are three lock-free maps** the data plane only reads (`crates/rdock-tls/src/challenge.rs`: `add_http01`, `add_tls_alpn01`; ADR-0020). The TLS-ALPN-01 certificate is built from the key-authorization digest (`crates/rdock-acme/src/issue.rs`, `validation_certificate(&name, key_authorization.digest())`).
- **ACME storage lock.** `Storage::lock` creates `<root>/lock` exclusively and treats it as stale after 30 s (`crates/rdock-acme/src/storage.rs`). The manager returns early from `step` when it cannot hold the lock (`manager.rs`, `hold_lock`).
- **instant-acme can resume an order.** `Account::order(url)`, `Order::url()` and `Order::finalize_csr(csr_der)` exist in instant-acme 0.8.5 (local registry source, `account.rs:140`, `order.rs:235`, `order.rs:90`).
- **Server-side SSE with replay.** The admin API streams with increasing ids, a replay buffer and `Last-Event-ID` (`crates/rdock-admin/src/stream.rs`, ADR-0024).
- **mTLS listener code.** The admin server has its own `TlsAcceptor` over `hyper_util::server::conn::auto::Builder`, and ADR-0024 defines `admin.tls.client_ca_files` with identities mapped to roles.
- **A local CA built on rcgen** with name constraints (`crates/rdock-acme/src/local_ca.rs`).
- **Credential formats** with id, secret and CRC32 (`rdock-credentials`).

#### D.1.2 What blocks multi-instance use today

| State | Where it lives | Effect with N instances |
|---|---|---|
| Config generation | Per-process counter (`Report.generation`) | Not comparable across instances; a cluster needs its own revision and content hash |
| File document, API snapshot | Local file; `state/providers/api.json` | Each instance has its own; the dashboard edits one instance |
| ACME account and certificates | `$RDOCK_DATA_DIR/acme/` (or `acme.storage`) | Each instance registers an account and orders every name. `acme` with `providers.kubernetes` is refused unless `allow_acme` (`rdock-model/src/validate.rs`, ADR-0029) |
| ACME lock | One lock for the whole directory, 30 s stale, no fencing | Serialises all names behind one holder. A paused holder can write after takeover |
| HTTP-01 / TLS-ALPN-01 answers | In-process maps | Only the ordering instance can answer. Let's Encrypt fetches "potentially multiple times from multiple vantage points" and says "If you have multiple web servers, you have to make sure the file is available on all of them" ([challenge types](https://letsencrypt.org/docs/challenge-types/), last updated 2026-02-12) |
| ARI renewal time | Random point in the window, chosen per process (ADR-0020) | Instances pick different moments. The first renewal consumes `replaces` |
| Local CA | `$RDOCK_DATA_DIR/pki/` created on first use | Each instance mints its own root; a client that trusts one fails on another |
| Rate limits | `RateLimiter`: 64 shards of in-memory token buckets (`rdock-limits/src/lib.rs`) | A limit of L admits up to N×L |
| Quotas | Per-process registry, flushed to `$RDOCK_DATA_DIR/quota` | Per instance (ADR-0030 says so) |
| Cache and purge | Per-instance stores | A purge reaches one instance (architecture §19) |
| Admin users, tokens, audit, sessions | `admin/users.json`, `admin/tokens.json`, `audit/`, in-memory map | Per instance |
| Sticky-cookie key | `$RDOCK_DATA_DIR/sticky.key`, created at first start (`crates/rdock/src/run.rs`) | Cookies signed by one instance fail on another unless the service sets its own secret |
| TLS session tickets | `rustls::crypto::ring::Ticketer::new()` per process (`rdock-tls/src/policy.rs`) | No resumption across instances; a performance cost only |
| OIDC session keys | Secret references resolved per instance | Works if every instance resolves the same secret. Refresh rotation can race across replicas (ADR-0030) |
| Vault | Each instance logs in and refreshes itself | No blocker |

Not in the model yet: no `cluster` or `control` section, no `rdock-control` crate (architecture §2 lists it as P3).

### D.2 Prior art

#### D.2.1 Envoy xDS

Source: [xDS protocol](https://www.envoyproxy.io/docs/envoy/latest/api-docs/xds_protocol), read 2026-11-13.

- **Four variants:** state-of-the-world (SotW) or incremental (delta), each on separate streams per type or on one aggregated stream (ADS). "A single ADS stream is available per Envoy instance."
- **ACK/NACK:** the client echoes the `version_info` it last applied. A NACK carries `error_detail` and the previous version. Each response has a nonce and requests echo the latest one. "The management server should not send a `DiscoveryResponse` for any `DiscoveryRequest` that has a stale nonce."
- **SotW removal:** for Listener and Cluster, a resource missing from a response is deleted. "A response containing no resources means to delete all resources of that type."
- **Warming:** "Warming of `Cluster` is completed only when a `ClusterLoadAssignment` response is supplied by management server."
- **Ordering:** "to avoid traffic drop, sequencing of updates should follow a make before break model" (CDS, EDS, LDS, RDS, then removals).
- **Control-plane outage:** "the last known configuration received by Envoy will persist until the connection is reestablished." The page describes in-memory persistence only.
- **Status view:** CSDS reports per client `SYNCED` ("sent the config to client and received ACK"), `NOT_SENT`, `STALE` ("hasn't received ACK/NACK") and `ERROR` ("received NACK") ([csds.proto](https://www.envoyproxy.io/docs/envoy/latest/api-v3/service/status/v3/csds.proto), read 2026-11-13).
- *(our reasoning)* xDS needs ordering and warming because it ships a graph of separately versioned resources. Our unit is one validated, compiled document swapped atomically, so one revision with one ACK/NACK is enough. xDS wire compatibility is not a requirement.

#### D.2.2 Kong hybrid mode

Source: [hybrid mode](https://developer.konghq.com/gateway/hybrid-mode/), read 2026-11-13.

- **Roles:** only control-plane nodes touch the database. Data planes connect out to the control plane (cluster port 8005, telemetry 8006).
- **mTLS modes:** `shared` (one certificate pair for all), `pki` (per-node certificates from a common CA), `pki_check_cn`.
- **Outage:** the data plane "will keep serving requests using cached configurations" and "can be restarted while in disconnected mode, and will load the last configuration in the cache" (`dbless.lmdb`; the FAQ names `config.json.gz`). Deleting the cache leaves a node that starts empty.
- **Reconnect:** "any manual configuration will be overwritten the next time the Control Plane connects to the node."
- **Version skew:** "Control planes only allow connections from Data Planes with the same major version"; newer minor versions on the data plane are refused.
- **Sync:** every change was a full push until 3.10, which added incremental sync.
- **View:** `/clustering/data-planes` lists each node's version and config hash.
- **Limits in hybrid mode:** rate limiting has no `cluster` strategy; use `local` or `redis`.

#### D.2.3 Traefik

- **OSS has no clustered ACME.** "it is not possible to run multiple instances of Traefik 2.0 with Let's Encrypt enabled". "Early versions (v1.x) of Traefik used a KV store to attempt to achieve this", but "due to sub-optimal performance that feature was dropped in 2.0." The page recommends Traefik Enterprise or cert-manager ([ACME reference](https://doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/), v3.7 docs, read 2026-11-13).
- **Enterprise** splits controllers and proxies on Raft; quorum is (N/2)+1. Controllers "store cluster data, including events, certificates, and configuration"; proxies keep routing on the last known configuration when quorum is lost ([concepts](https://doc.traefik.io/traefik-enterprise/concepts/), read 2026-11-13). DNS-01 credentials "must be defined on the controllers" ([Enterprise ACME](https://doc.traefik.io/traefik-enterprise/tls/acme/)). How proxies answer HTTP-01 is not documented there: *unverified*.
- **Rate limit:** the OSS `rateLimit` middleware is a token bucket with an optional `redis` block that "enables distributed rate limiting by using Redis to store rate limit tokens across multiple Traefik instances" ([reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/ratelimit/), v3.7 docs, read 2026-11-13). The page does not say what happens when Redis is unreachable. That it arrived in 3.4 comes from a search result for Traefik's announcement, not an opened page: *unverified*.

#### D.2.4 Caddy and certmagic

Sources: [storage.go](https://raw.githubusercontent.com/caddyserver/certmagic/master/storage.go), [filestorage.go](https://raw.githubusercontent.com/caddyserver/certmagic/master/filestorage.go), [solvers.go](https://raw.githubusercontent.com/caddyserver/certmagic/master/solvers.go), [config.go](https://raw.githubusercontent.com/caddyserver/certmagic/master/config.go), master branch, read 2026-11-13.

- **One interface:** `Storage` (key-value) plus `Locker`. "Processes running in a cluster should use the same Storage value (with the same configuration)."
- **Lock per name:** the key is `issue_cert_<name>`, shared by obtain and renew.
- **Re-check after the lock:** "check if obtain is still needed -- might have been obtained during lock"; for renew, "read storage to see if another instance already renewed this."
- **File locks:** created with `O_EXCL`, refreshed every 5 s (`lockFreshnessInterval`), stale after twice that, polled every second. The source says: "This does mean that mutual exclusion is not guaranteed to be perfectly enforced in the presence of stale locks." It calls `Sync` because "we suspect that sometimes file systems (particularly AWS EFS) don't do this on their own".
- **Fencing is advice, not enforced:** "If possible, a Locker should implement a coordinated distributed locking mechanism by generating fencing tokens." Callers "must be tolerant of some mis-synchronizations." An optional `LockLeaseRenewer` extends a lease during long operations.
- **Distributed challenges:** `distributedSolver` writes the challenge to `<issuer>/challenge_tokens/<domain>.json` in `Present` and deletes it in `CleanUp`. The receiving instance "must handle it by checking to see if the challenge token exists in storage". That is a storage read on the request path.
- *(our reasoning)* certmagic is the working model for "no control plane, shared storage". Its two weak points are the ones we should not copy unchanged: no enforced fencing, and a storage lookup inside the request path.

#### D.2.5 HAProxy, NGINX Plus, Pingap

- **HAProxy peers** replicate stick-table entries, but the nodes "won't sum their individual counters, so `http_req_rate` on one will overwrite the value on the other"; summing is the Enterprise Stick Table Aggregator ([HAProxy blog](https://www.haproxy.com/blog/introduction-to-haproxy-stick-tables), read 2026-11-13). The peers section of the configuration manual was not reached (page too large): reload hand-over and TLS on peers are *unverified*.
- **HAProxy Data Plane API** is "a service that lets you configure the load balancer using HTTP, RESTful commands" and "runs as a standalone program or service" ([docs](https://www.haproxy.com/documentation/haproxy-data-plane-api/), read 2026-11-13). Transactions, versioning and multi-node management were not on that page: *unverified*.
- **NGINX Plus `zone_sync`** synchronises shared zones for sticky sessions, `limit_req` and keyval between nodes; it is commercial ([module docs](https://nginx.org/en/docs/stream/ngx_stream_zone_sync_module.html), read 2026-11-13). Membership is static or by DNS `resolve`; `zone_sync_ssl_verify` defaults to `off`. The page documents no consistency model and no partition behaviour.
- **Pingap** stores configuration "in files or in etcd" and keeps certificates in `~/.pingap/acme/<domains>.toml`. Its README describes no control plane, shared certificates or distributed limits ([README](https://github.com/vicanso/pingap), read 2026-11-13). No other Pingora-based proxy was checked.

#### D.3.3 Pull, not push

*(our reasoning)* The data plane opens the connection, as in Kong and Envoy. It works behind NAT, the control plane needs no route to data planes, and a data plane keeps one outbound dependency. The agent is a background service like a provider: the request path never waits on it (ADR-0009, ADR-0012).

#### D.3.4 Enrolment and mTLS *(our reasoning)*

- `rdock control init` creates a cluster CA (P-256, the rcgen code of `local_ca.rs`) and the control plane's server certificate.
- A **join token** `rdk_join_<id>_<secret><crc32>` (the `rdock-credentials` format) carries the SHA-256 of the cluster CA certificate, so the data plane authenticates the control plane before sending anything. Tokens expire (default 1 hour) and are single-use by default, hashed at rest, audited.
- The data plane generates its key locally, sends a CSR with the token, and receives a client certificate naming its instance id. Keys never travel.
- Certificates renew over the authenticated channel. Removing an instance is a deny-list on the control plane, the only relying party. The lifetime trades off against outage length: a data plane whose certificate expires during a long outage must re-enrol.
- Unsafe opposites, refused unless set explicitly: shared certificate for all data planes, plain HTTP on a non-loopback cluster listener.
- Docker Swarm and kubeadm embed a CA hash in their join tokens in a similar way: *unverified* today.

#### D.3.5 Versioned bundles, ACK/NACK, last-known-good *(our reasoning)*

- **Bundle** = base document as written (references unresolved, so `${file:}`, `${env:}` and `${vault:}` secrets stay on each data plane) + the API fragment (routes, services, middlewares, consumers with hashed keys) + cluster keys (sticky-cookie key) + member list.
- **Version** = cluster id, a monotonic revision assigned by the control plane, and the SHA-256 of the canonical JSON. State-of-the-world, like provider snapshots; no deltas in v0.9.
- **Publish:** the control plane runs the validate and compile dry run first, so it cannot publish what `rdock validate` refuses.
- **Apply on the data plane:** persist the bundle, run `Engine::apply`, then POST `ack` or `nack` with the `Report` diagnostics. A NACK keeps the previous revision, as today's rejected reload does.
- **Reasons for a NACK the control plane cannot foresee:** a missing local secret file, a port in use, a conflict with a local provider, an older binary that refuses an unknown field.
- **Safety rules:**
  - a bundle with another cluster id is refused;
  - a lower revision is refused unless it is marked as a rollback of a revision the data plane has seen;
  - an empty bundle never replaces a non-empty one without that mark.

  These cover a control plane that returns with a lost disk.
- **Last-known-good:** `state/lkg.json` and `state/providers/*.json` already exist. Needed: an origin `control` beside `file` and `last-known-good`, the bundle stored with its revision, and boot from it when the control plane is unreachable.
- **Version skew:** upgrade the control plane first. It shows each data plane's version; an older data plane NACKs what it does not know. This is a simpler rule than Kong's and needs a maintainer decision (§8.5).

#### D.3.6 Staged rollout and rollback *(our reasoning)*

- **Waves:** a canary set (one instance, a count, a percentage or a label selector), then the rest, with a soak time between waves.
- **Halt criteria, cheap and local:** any NACK; an instance that disconnects after applying and does not return within a timeout; a listener that failed to bind.
- **Health criteria, optional:** 5xx share and healthy-backend count against the pre-apply baseline, taken from the ring-buffer summary the data plane already keeps (ADR-0024).
- **Rollback** is publishing the previous revision again as a new revision marked as a rollback; it is audited and needs `If-Match` like any write.
- **Default:** canary of one, automatic halt, manual rollback. Automatic rollback is an option, off by default, because rolling back on a noisy metric can itself cause an outage.

#### D.3.7 Provider-sourced configuration

- Docker, Swarm and Kubernetes providers keep running **per data plane**. They read local sockets or the API server, and ADR-0029 already has every replica watch and translate identically.
- The control plane owns what the file and the API own today. With a control plane configured, the data plane's local API writes are off, as in GitOps mode (`admin.api_writes: false`, ADR-0024).
- Running a provider inside the control plane, as Traefik Enterprise does, would let data planes run without a Docker socket. `Snapshot` is already serialisable, so a provider snapshot could ride in the bundle. *(our reasoning)* Optional, after v0.9.
- On Kubernetes the API server is the configuration control plane already; `rdock-control` there adds certificates, limits and the view, not routing.

### D.4 Shared certificate storage and coordination

#### D.4.1 What Let's Encrypt enforces today

Source: [rate limits](https://letsencrypt.org/docs/rate-limits/), last updated 2026-08-05, read 2026-11-13.

| Limit | Value |
|---|---|
| New orders per account | 300 every 3 hours |
| New certificates per registered domain | 50 every 7 days |
| New certificates per exact set of identifiers | 5 every 7 days, no override |
| Authorization failures per identifier per account | 5 per hour |
| New registrations per IPv4 address | 10 every 3 hours |

- The domain and exact-set limits "are global. All new order requests count toward them, regardless of which account submits them."
- "Renewals coordinated by ARI offer the unique benefit of being exempt from all rate limits", provided the replaced certificate "must not have been previously replaced using ARI".
- *(our reasoning)* With one certificate per name (ADR-0020), six uncoordinated replicas exhaust the exact-set limit on first start, and only one replica's `replaces` renewal can succeed. Separate accounts do not help. Whether `replaces` requires the same account as the original order (RFC 9773) was not re-read: *unverified*; sharing one account avoids the question.

#### D.4.2 Correctness needs *(our reasoning)*

1. **Lock per name** with expiry and a **fencing token** the store checks on write. Expiry alone is not enough: a holder paused past the TTL must not overwrite its successor.
2. **Re-check after acquiring**, as certmagic does: load from the store, and skip if another instance finished.
3. **Order ownership.** Before finalising, write an order journal to the store: order URL and the new private key. A successor can then resume the same order with `Account::order(url)` and download the certificate. Without the journal, a crash between finalise and store write costs a second issuance.
4. **Challenge answers on every instance before the CA is told to validate.** For TLS-ALPN-01 only the name and the key-authorization digest need to travel; each instance builds its own validation certificate, as `issue.rs` already does locally.
5. **Keep the request path free of I/O.** Replicate answers into the existing maps and wait for a barrier (all live members acknowledged, or a timeout) before validation. This differs from certmagic's lookup on request and preserves ADR-0020. DNS-01 needs none of this; Let's Encrypt says it "works well even if you have multiple web servers".
6. **One shared ACME account** in the store, as certmagic keeps it.
7. **One renewal time per certificate.** Store the chosen point in the ARI window in the shared metadata, so instances agree and the view is coherent. `CertMeta` in `storage.rs` today holds only `names`, `directory`, `profile`, although ADR-0020 lists more.
8. **OCSP and CRL** need no sharing: Let's Encrypt certificates carry no OCSP URL (ADR-0020), and stapling for other CAs can stay per instance.
9. **The local CA** must be one per cluster, or names it serves are refused in cluster mode.

#### D.5.3 Mapping our semantics *(our reasoning)*

- **`quota`** (fixed calendar windows): the easiest and the most wanted, because quotas bill. A fixed-window counter per instance, summed, is exact up to the flush interval. With Redis: `INCRBY` on a key per window with an expiry.
- **`rate_limit`** (token bucket: `average`, `period`, `burst`): keep the local bucket for burst shaping. Add a cluster check on the summed sliding-window estimate against `average × period + burst`. A Redis GCRA script gives exact token-bucket behaviour at one round trip per request.
- **`in_flight`** (concurrency): needs decrements and crash cleanup, so it must be a per-instance gauge with a heartbeat, summed over live members. Refuse `scope: cluster` for it as planned in v0.9.
- **`bandwidth`**: stays per instance.

#### D.5.4 Recommendation *(our reasoning)*

- **`scope: instance` stays the default** (today's behaviour). With `cluster` configured, a validation warning states that a limit of L admits up to N×L.
- **`scope: cluster`** with `store`:
  - `control`: per-instance counters relayed through the control plane. No new dependency. Falls back when the control plane is down.
  - `peers`: the same counters exchanged directly between data planes over the cluster mTLS channel, members from the bundle. This is the "built-in gossip counters" of H-HA-04 with authentication for free and no SWIM crate while clusters are tens of instances.
  - `redis`: `mode: async` (default, bounded over-admission, no round trip) or `mode: sync` (exact, one round trip per request).
- **`on_store_error`** default `local`: keep enforcing with the last known share, L divided by the last known member count. This is neither open nor closed, which is what the two-stage designs of Envoy and Kong converge on. Explicit opposites: `allow` and `deny`.
- **Redis client:** the `redis` crate, or a RESP client of a few hundred lines on tokio-rustls, in line with the in-tree SigV4, minisign and JSON Patch code. Maintainer decision (§8.5).

### D.6 Multi-instance view and tenant isolation

#### D.6.1 What the control plane aggregates (F-UI-07)

Per instance *(our reasoning)*:
- id, name, labels (zone), binary version;
- connected or last seen, and certificate expiry of its enrolment;
- desired and applied revision with the status words of CSDS: synced, stale, error;
- origin (control, last-known-good), diagnostics of the last apply;
- provider health, listeners, backend health counts;
- per certificate: names, serial, expiry, so a serial mismatch between instances is visible;
- the ring-buffer summary (ADR-0024), pushed every few seconds because the control plane cannot call a data plane.

How others expose it:
- Kong lists data planes with version and config hash (§2.2).
- Envoy has CSDS (§2.1).
- Traefik Enterprise's dashboard "shows all the relevant information about your cluster at a glance" ([docs](https://doc.traefik.io/traefik-enterprise/), read 2026-11-13).

Commands the view implies:
- **Cache purge fan-out** (promised "until the v0.9 control plane", architecture §19): a command on the stream with acknowledgement and a bounded log replayed on reconnect. An instance that fell off the log purges everything.
- Drain, and renew a certificate.

#### D.6.2 Tenancy (H-SEC-07)

- **Kong Workspaces:** "Workspaces are a way of namespacing Kong Gateway entities so they can be managed independently." Custom roles "are scoped to a single Workspace". But the data plane "routes client traffic based on the configuration applied across all Workspaces", so Kong needs route collision detection. "CA Certificates apply to all Workspaces." Konnect "doesn't report analytics per Workspace" ([Workspace](https://developer.konghq.com/gateway/entities/workspace/), read 2026-11-13).
- Envoy, HAProxy and NGINX have no tenancy in the proxy *(our reasoning from the pages read; not a quoted fact)*.
- Kubernetes Gateway API already gives namespaces and `allowedRoutes`; our translator honours them (ADR-0029).

Minimum coherent with ADR-0024 *(our reasoning)*:
1. A **tenant** names a set of API-owned objects, the host patterns it may claim and optional object counts. A `default` tenant always exists.
2. Users and tokens gain an optional tenant beside their role. A tenant-scoped operator reads and writes only its tenant's objects; admins stay global.
3. **Host ownership** is the isolation that matters on a shared data plane: a route whose `Host` is outside its tenant's patterns is refused. This is Kong's collision problem solved by ownership instead of detection.
4. Metrics and the access log carry a bounded `tenant` label. Audit records name the tenant.
5. Not in scope: per-tenant data planes, per-tenant certificates or CAs, tenants for file or Docker objects.

Building the control-plane API with the tenant field from the first version avoids a breaking change later, even if only `default` exists in v0.9.

  - It has no endpoint that lists issued certificates.
- **Toxiproxy** (`ghcr.io/shopify/toxiproxy:2.13.0`) and `Rdock::start`/`restart`/`signal` exist in the testkit.

#### D.7.2 Proof 1: "3-instance cluster survives control-plane outage"

Runs without Docker: one `rdock control` and three `rdock run` processes on loopback.

1. Enrol three data planes with join tokens; publish revision 2; all three ACK.
2. Drive requests at all three for the whole test and count failures.
3. `SIGKILL` the control plane. Assert zero failed requests for 60 s and that each `rdock status` reports "control plane unreachable, serving revision 2".
4. Restart one data plane while the control plane is down. It must come up from the stored bundle and serve revision 2.
5. Change a local provider source (a file fragment or a labelled container). It must still apply.
6. Restart the control plane with its state. All three reconnect; publish revision 3; all ACK.

Fault variants:
- `SIGSTOP` instead of kill: connections hang, so the heartbeat timeout is exercised.
- The control plane returns with an empty state directory: the bundle is refused and revision 2 kept.
- Revision 3 references a secret file that is missing on one instance: that instance NACKs and keeps revision 2, the canary halts, the view shows `error`.
- An expired join token and a removed instance are refused.
- With Docker (CI): Toxiproxy between data planes and control plane for latency and resets.

#### D.7.3 Proof 2: "no duplicate certificate issuance across instances"

**Deterministic part, runs everywhere:** N managers against one store and a fake issuer under paused tokio time.
- Exactly one issue call per name.
- A holder paused past the lease TTL has its write refused by the fencing token.
- A successor resumes the journalled order.

**End-to-end part, needs Pebble (CI):**
1. Three data planes with the same five `tls: auto` hosts, started together, with the control plane as store.
2. A round-robin TCP forwarder (testkit) sits on the validation port in front of the three plain listeners. Each validation request therefore lands on a different instance, which proves answer replication. The same is done for TLS-ALPN-01.
3. Assert exactly five `Issued certificate serial` lines in the Pebble log, and that all three instances serve the same serial per name.
4. Move the ARI window with `/set-renewal-info/`. Assert exactly five more issuances and convergence on the new serials.

Fault variants:
- Kill the lease holder after validation and before finalise; with the order journal the count stays at five.
- Kill it after finalise and before the store write; the successor downloads the same certificate.
- Stop the control plane during the renewal window: no issuance and no duplicate, old certificates served, alert raised; one issuance per name after it returns.
- Repeat the base case with the shared-directory store and no control plane.

#### D.7.4 Limits, Kubernetes, CI wiring

- **Limits:** three instances, cluster limit 100/s.
  - Even load must admit between 100 and 100 × (1 + ε).
  - All load on one instance shows the difference between `divide` and a shared store.
  - A store outage must follow `on_store_error`.
  - Redis tests run against the local `redis-server` or a Valkey container, behind `RDOCK_REDIS_TESTS`.
- **Kubernetes (CI only):** chart with the control plane as a Deployment with a volume and three replicas; delete the control-plane pod; the example Gateway keeps answering.
- **CI job:** a new `cluster` job, not a required check until a maintainer adds it to the ruleset.

### D.8 Recommended design for v0.9 *(our reasoning)*

#### D.8.1 Shape

- **`rdock control`**: a subcommand of the same binary, so it can reuse `rdock-admin` (users, tokens, audit, dashboard) without breaking the `deny.toml` rule that only the binary depends on it.
- **New library crates:**
  - `rdock-cluster`: protocol types, the data-plane agent, the `ClusterStore` trait with leases and compare-and-swap.
  - `rdock-control`: registry, bundle history, rollout, store server, cluster CA.
- **Data plane:** a `cluster.control` section with the URL, CA pin and identity paths. The agent is a background service; ADR-0009 and ADR-0012 hold.
- **One active control plane.** Its outage is survivable by design, which is what the milestone asks. A highly available control plane (Raft; `openraft` 0.10.0 declares no MSRV) is refused as planned.
- **ACME:** data planes issue, under a per-name lease from the store, with re-check, order journal, shared account and the replication barrier. The control plane is store, lock service and relay, not an ACME client. This keeps one code path for the mode without a control plane, and the control plane needs no route to the CA.

#### D.8.2 Cut lines

| Essential for the two proofs | Optional in v0.9 | Refused as "planned" |
|---|---|---|
| Enrolment with join tokens and mTLS | Canary waves by percentage or label | Highly available control plane |
| Bundles with revision and hash, ACK/NACK, stored before ACK, boot from it | Health-based halt criteria; automatic rollback (off by default) | Delta bundles |
| Safety rules for cluster id, lower revision, empty bundle | Cache purge fan-out | Providers running in the control plane |
| Manual rollback, canary of one, halt on NACK | `quota` and `rate_limit` with `scope: cluster` on `control`, `peers`, `redis` | `in_flight` with `scope: cluster` |
| `ClusterStore` with `control` and shared-directory backends | S3 store with a conditional-write probe | Kubernetes Secret, PostgreSQL, etcd, Consul stores |
| Per-name lease with fencing, re-check, order journal, shared account, shared renewal time | Tenants beyond `default` | Shared TLS ticket keys (H-PERF-02) |
| Challenge replication with barrier | Sticky-cookie key in the bundle | Server-side OIDC sessions |
| Instance list with revision, status, certificates (API and one dashboard page) | Shared local CA | gRPC or xDS wire compatibility |

#### D.8.3 Implementation steps, each leaving the workspace green

1. ADR, model (`cluster`, `control`), schema; the gate refuses the new sections as planned until each step lands.
2. `rdock-cluster`: types, `ClusterStore` trait, in-memory and directory backends, with the lease and fencing simulation tests.
3. ACME manager on `ClusterStore`: per-name lease, re-check, journal, shared account and renewal time. The single-instance behaviour is the directory backend, so existing tests keep passing.
4. Challenge replication and barrier; shared-directory variant of proof 2.
5. `rdock control`: cluster CA, join tokens, enrolment, registry.
6. Bundle publish, agent, ACK/NACK, origin `control`, safety rules; proof 1.
7. `control` backend of `ClusterStore`; full proof 2 in CI; lift the `allow_acme` refusal for this store.
8. Rollout (canary, halt, rollback), instance list API, dashboard page, CLI.
9. Distributed limits: `quota` first, then `rate_limit`.
10. Optional items, docs, chart, release.

#### D.8.4 Risks

- **Private keys in the store.** The control plane becomes a second place holding certificate keys and the ACME account key. Its disk and backups need the care of a data directory.
- **A partitioned instance that still gets public traffic** cannot answer HTTP-01 or TLS-ALPN-01. The barrier only covers connected members. DNS-01 is the recommendation for clusters.
- **Clock dependence** of leases in the directory and S3 backends.
- **Version skew** between control plane and data planes surfaces only as a NACK.
- **Bundle size** with thousands of routes: state-of-the-world is simple but grows. Kong needed incremental sync later.
- **Approximate limits** will be reported as bugs unless the bound is documented and visible in metrics.
- **Scope.** This topic is one of five in the milestone. H-PERF (fd transfer) and HTTP/3 are independent and should not wait on it.

#### D.8.6 Open questions for the maintainer

1. Where does issuance run: data planes under a lease (recommended), or only the control plane, which keeps DNS credentials and the account key off the data planes but stops all issuance when it is down and makes it an ACME client?
2. Is a single active control plane acceptable for v0.9, with high availability planned?
3. Certificate lifetime for data-plane identities, which bounds how long an outage a data plane can sit out before re-enrolment.
4. Version-skew rule: "control plane first, older data planes NACK", or a stricter rule like Kong's?
5. Redis: the `redis` crate or an in-tree RESP client?
6. Is the shared-directory store's "best effort, no fencing" acceptable as a documented mode, or must the mode without a control plane wait for an S3 store with real compare-and-swap?
7. May the Kubernetes provider ever write Secrets (a change to ADR-0029), or does cert-manager remain the only certificate path in clusters without `rdock-control`?
8. Does tenancy ship in v0.9 beyond the `default` tenant?
9. Should `scope: instance` stay the default for limits once a cluster is configured, with a warning, or should cluster mode require an explicit choice?
10. `CertMeta` holds less than ADR-0020 describes. Extend it in step 3, or record the difference in the new ADR?

#### E.2.5 `h3` maturity: the weak point
- The README says: "The `h3` crate is still very experimental. While the client and servers do work, there may still be bugs. And the API could change".
- Last release 0.0.8 on 2025-05-06. Master is active (latest commit 2026-09-20) with unreleased fixes: backpressure before reading more frames (#344), flush of buffered data (#360), a `stop_sending` panic (#331, 2026-01-22), and the RFC 9220 `:protocol` extension (#236, 2026-01-04). - Our `deny.toml` has `unknown-git = "deny"`, so a git pin of h3 master is not allowed today.
- **Compliance report** (duvet, commit 43745ad, https://hyper.rs/h3/ci/compliance/report.html; I counted the embedded JSON). Of 239 RFC 9114 requirements: 21 cited and tested, 29 cited without a test, 16 implied, 73 exceptions (left to the user of h3), about 95 TODO or incomplete. Of 138 MUSTs: 18 tested, 23 cited only, 13 implied, 35 exceptions, about 49 TODO.
- **What that leaves to us:** TODO or exception items include rejecting `Transfer-Encoding` (§4.1), connection-specific fields and `TE` other than `trailers` (§4.2), cookie concatenation (§4.2.1), userinfo in `:authority` (§4.3.1), and "Intermediaries … MUST NOT forward a malformed request" (§4.1.2; exception text: "h3 is not meant to be used for intermediaries"). We must do this validation ourselves.
- **QPACK:** the 0.0.8 server decodes with `qpack::decode_stateless`, which rejects dynamic-table references (`src/qpack/decoder.rs:218-262`). Static table only is permitted by RFC 9204 and reduces the attack surface.
- **In 0.0.8:** `send_grease`, `enable_extended_connect`, `enable_datagram`, `enable_webtransport`, `max_field_section_size` (`src/server/builder.rs:64-116`), `shutdown(max_requests)` for GOAWAY, `recv_trailers`/`send_trailers`.
- **Not in 0.0.8:** WebSocket over h3 (the `:protocol` work is on master only).
- **Production users:** `reqwest` 0.13.5 (optional `http3`), `xitca-http` 0.9.3, `tonic-h3`; `salvo` uses its own `salvo-http3` fork. I found no large public edge deployment of the h3 server. quiche by contrast runs Cloudflare's edge, "millions of HTTP/3 requests per second" per the tokio-quiche post.

#### E.2.6 Honest comparison
- **tokio-quiche + BoringSSL** has the more proven HTTP/3 stack. It costs a second TLS stack (certificate resolver, SNI, client auth and policy all re-implemented against BoringSSL), C++/cmake/bindgen in the build, a static-musl problem, 90 more crates and a second artifact.
- **quinn + h3** uses our existing `rustls::ServerConfig` and resolver, adds 7 crates, stays `cargo deny` clean and fits one static artifact. It rests on an experimental HTTP/3 crate with a stale release.
- For an experimental, off-by-default ingress the second is the better fit *(our reasoning)*. The h3 risk is contained by owning message validation, setting hard limits, and keeping h3 behind a thin internal trait.

### E.3 Integration shape

3.1 **(a) Socket hop (loopback or Unix socket, h1 or h2c).**
- Client address would travel by PROXY v2 (we have encode and parse). TLS facts need TLVs trusted only on that hop.
- It adds a real listener, file descriptors and syscalls per request.
- I found no published measurement of such a hop's cost (searched 2026-11-13).
- It has no advantage over (c), because ADR-0012 already lets us hand Pingora any `Stream` *(our reasoning)*. Not recommended.

3.2 **(b) Custom server session, no hop.** Implement `pingora::protocols::http::custom::server::Session` for an h3 request stream, then call `engine.process_new_http(Session::new_custom(Box::new(s)), &closing)`.
- **What the trait covers** (`pingora-core-0.9.1/src/protocols/http/custom/server.rs:28-176`, about 45 methods): request header, body read, `read_body_or_idle`, response header/body/trailers, `response_duplex_vec`, timeouts, `digest()`, `client_addr()`, `server_addr()`, retry buffering, `finish`, `shutdown`, `abandon`. `read_request` returns `Ok(true)` for Custom (`server.rs:126`), so the header must be parsed before the session is built.
- **What we gain:** trailers, body streaming with QUIC flow control as backpressure, client address and stream reset are native. Whether 1xx can be sent with h3 0.0.8 is *unverified* (`send_response` just writes a HEADERS frame). No re-serialisation, so no h1 smuggling surface.
- **Risks:**
  - The trait is `#[doc(hidden)]`, so it is not a stable API.
  - We must implement retry buffering ourselves.
  - `send_proxy_task`/`write_proxy_tasks` panic by default and must stay disabled or be implemented.
  - `pingora-proxy` treats custom downstreams specially (`proxy_h1.rs:49`, `AuthorityPolicy::Custom`).
- **TLS facts:** `SslDigestExtension::set` is `pub(crate)` (`protocols/tls/digest.rs:79`), so we cannot attach our `Handshake` to a self-built `SslDigest`. Carry SNI and client certificate in `RequestHeader::extensions_mut()` (`pingora-http-0.9.1/src/lib.rs:290`) and read them through one helper at `proxy.rs:757` and `:1669`. `session.is_http2()` is used at `proxy.rs:732, 864, 1299` and needs an h3 case.

3.3 **(c) In-process duplex, HTTP/1.1 into `process_new`.**
- Pingora implements its IO traits for `tokio::io::DuplexStream` (`pingora-core-0.9.1/src/protocols/mod.rs:200-228`); our own tests already do `ConnStream::new(Box::new(duplex), …)` (`crates/rdock-proxy/src/conn.rs:299`).
- One duplex per h3 request stream; we serialise a validated request as HTTP/1.1.
- It uses only the public, well-exercised H1 path. Our IO type can be recovered with `Session::stream()` (`server.rs:890`) plus `as_any()`, which carries the TLS facts.
- Costs: one serialise and parse per request, trailers and 1xx behaviour to be checked, and an h1 translation surface we must fuzz.

3.4 Recommendation: build (b), timebox the spike, keep (c) as the fallback. The spike passes if a streaming POST, trailers, a mid-body client reset, an upstream retry and the cache path work through `RdockProxy` unchanged apart from the helper in 3.2.

### E.4 Operational and protocol requirements

4.1 **Advertisement.**
- RFC 9114 §3.1.1: advertise with `Alt-Svc: h3=":443"`.
- RFC 7838 §3.1: without `ma` the entry is fresh for 24 hours; `Alt-Svc: clear` invalidates.
- NGINX's example is `add_header Alt-Svc 'h3=":8443"; ma=86400'` (https://nginx.org/en/docs/http/ngx_http_v3_module.html). Envoy: clients such as Chrome "will only attempt HTTP/3 if it is explicitly advertised" (https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/http3).
- RFC 9460 HTTPS records (`alpn="h3,h2"`) let a client try QUIC on the first connection. We do not own DNS, so document it and do not automate it in v0.9 *(our reasoning)*.

4.2 **Sockets.**
- `bind_udp` (`listener.rs:151`) and `Socket::Udp` exist. A UDP and a TCP socket on one port need no `SO_REUSEPORT`; the model already accepts a `udp` listener on `:443` next to an HTTPS one (`rdock-model/src/validate/tests.rs:109-123`).
- One quinn endpoint is one socket, so there is no connection-ID routing problem across threads inside one process. Scaling out with `SO_REUSEPORT` and a custom `cid_generator` is later work.

4.3 **Reloads and binary upgrades.** How others do it:
- **NGINX:** `quic_bpf` (default off): "Since 1.31.7, this also allows established QUIC connections to be preserved during configuration reloads and during live upgrade". `quic_host_key`: "By default, a random key is generated on each reload. Tokens generated with old keys are not accepted."
- **HAProxy 3.2:** `tune.quic.socket-owner connection` (default; one socket per connection) "is also the only way to ensure soft-stop is conducted properly without data loss for QUIC connections". `cluster-secret` derives stateless-reset and Retry token keys. "QUIC also provides connection migration support but currently haproxy does not support it." https://docs.haproxy.org/3.2/configuration.html
- **Envoy:** "Hot restart is not gracefully handled for HTTP/3 yet."
- **QUIC-LB:** still a draft, draft-ietf-quic-load-balancers-22 (2026-10-23). https://datatracker.ietf.org/doc/draft-ietf-quic-load-balancers/
- **For us** *(our reasoning)*: quinn cannot move a connection to another process. In the experimental contract QUIC connections do not survive a binary upgrade or listener replacement: send GOAWAY, drain for a bounded time, close, hand the socket over. Persist the reset key and token key so the new process can send stateless resets and accept old tokens.

4.4 **DoS posture.**
- RFC 9000 §8.1: before address validation a server sends at most three times the bytes received; quinn passes the runner's amplification-limit test (2.4).
- Retry defaults elsewhere: NGINX `quic_retry off`; HAProxy turns Retry on dynamically at 100 half-open connections (`tune.quic.retry-threshold`, default 100) and has `quic-force-retry`.
- Proposed default: `retry: auto` at the same threshold, with `always` and `never` available *(our reasoning)*.

4.5 **0-RTT.** RFC 9001 §9.2: 0-RTT is exposed to replay. HAProxy's `allow-0rtt` is "disabled by default, due to security considerations". Keep it off and refuse it in config.

4.6 **Migration.** Disable active migration (`ServerConfig::migration(false)`) while experimental. NAT rebinding is separate, and quinn passes both rebind tests.

4.7 **Buffers.**
- quinn README: high aggregate rates on one endpoint "can require a larger UDP buffer than is configured by default", and Linux may need privileges to raise it.
- Envoy: watch `downstream_rx_datagram_dropped`; non-zero means the receive buffer is too small.
- NGINX and HAProxy both expose GSO as a switch (NGINX default off).

4.8 **Kubernetes.** Gateway API has no HTTP/3 listener protocol. Issue #687 was closed "not planned" on 2023-03-17 with "no changes required in APIs to support HTTP3", delegating to controllers; the same thread notes MixedProtocolLBService went GA in Kubernetes 1.26. https://github.com/kubernetes-sigs/gateway-api/issues/687. I did not re-read the v1.7.0 release notes for an HTTP/3 item (*unverified* that none exists).

4.9 **Docker.** UDP 443 must be published explicitly (`-p 443:443/udp`); our Dockerfile has `EXPOSE 80 443` only. A firewall that drops UDP 443 makes clients stay on TCP, which is the designed fallback.

4.10 **Observability.** quinn has a `qlog` feature (pulls the `qlog` crate, BSD-2-Clause). Minimum metrics: connections, handshake failures, Retry sent, streams, resets, datagrams dropped, and an `h3` protocol label in access logs.

### E.5 Security record and tooling

5.1 **quinn-proto** (RustSec, https://rustsec.org/packages/quinn-proto.html): all denial of service, all fixed at or before 0.11.18.

| Advisory | Issued | What | Fixed in |
|---|---|---|---|
| RUSTSEC-2024-0373 (CVE-2024-45311, 7.5) | 2024-09-08 | panic via `Endpoint::retry()` | 0.11.7 |
| RUSTSEC-2026-0037 (CVE-2026-31812, 8.7) | 2026-03-09 | panic on invalid transport parameters | 0.11.14 |
| RUSTSEC-2026-0185 (CVE-2026-25800, 7.5) | 2026-06-22 | memory exhaustion in stream reassembly | 0.11.15 |
| RUSTSEC-2026-0339, -0341, -0342 | 2026-10-12 | unbounded CID retirements; reassembly guard bypass; zero-length DATAGRAM growth | 0.11.17 |
| RUSTSEC-2026-0338, -0340, -0343 | 2026-10-12 | zero-length STREAM panic (unordered reads); ACK_FREQUENCY panic; datagram accounting panic | 0.11.18 |

5.2 **quiche** (https://github.com/cloudflare/quiche/security/advisories): 10 advisories.
- 2026: unbounded HTTP/3 datagram flow map in tokio-quiche (2026-11-10, High); path event queue growth (2026-07-14, High); HTTP/3 and QPACK resource exhaustion (CVE-2026-12523, 2026-07-14, High, fixed in 0.29.3); use-after-free in FFI (2026-06-19, Moderate).
- 2025: infinite loop on CID retirement (2025-08-07, High); two congestion-window ACK issues (2025-06-17).
- 2024: two (2024-03-12, Low and Moderate).

5.3 **s2n-quic:** DoS when configured to send Retry (2026-09-22, High); excessive memory allocation (2026-06-10, Moderate). https://github.com/aws/s2n-quic/security/advisories

5.4 **h3:** no published advisory, but issue #379 (2026-10-22, "Header Accordions") is open and fix PR #378 is unreviewed.
- `max_field_section_size` defaults to unlimited, and more than 32,768 fields panics `http::HeaderMap`.
- The oss-security summary lists h3 as unpatched with the mitigation "set a reasonable `max_field_section_size`". https://github.com/hyperium/h3/issues/379, https://openwall.com/lists/oss-security/2026/10/22/1
- In 0.0.8 the limit is enforced while decoding and counts 32 bytes per field (`decoder.rs:249-253`, `field.rs:10`). A limit of 1 MiB or less therefore caps a section at about 31,775 fields, below the panic threshold *(our reasoning from the source)*. We must always set it; I propose 64 KiB.

5.5 **Translation risks.**
- RFC 9114 §4.1.2 lists what is malformed: prohibited or missing pseudo-headers, pseudo-headers after fields, uppercase names, invalid characters, and a `Content-Length` that differs from the DATA total. Intermediaries must not forward such messages.
- "CDN Tsunami" (SRDS 2026, https://arxiv.org/html/2607.26589v1, reported 2026-08-20) abuses h3-to-h1 translation two ways: header decompression amplification, and one origin connection per stream opened on HEADERS and held open by trickled DATA. Proposed mitigations: cap decompressed request size (64 KB), limit origin connections per client connection, time out stalled bodies.
- Our existing per-route limits and header deadline need an h3 equivalent.

5.6 **Tools.**
- **h3i** (Cloudflare, crate 0.7.0 of 2026-09-17, BSD-2-Clause): a client that "can bend RFC rules", with a CLI and a library and qlog record/replay (`--qlog-input`). It depends on quiche, so it needs BoringSSL; keep it outside the workspace like `tests/fuzz`.
- **h3spec** (Haskell, 0.1.12, BSD-3-Clause): error-case tests for QUIC and HTTP/3. https://hackage.haskell.org/package/h3spec
- **curl:** only the ngtcp2 backend is non-experimental; "HTTP/3 support using quiche in curl is considered EXPERIMENTAL" (https://curl.se/docs/http3.html). The GitHub `ubuntu-24.04` image (20261101.360.1) ships curl 8.5.0-2ubuntu10.16; the same package in this sandbox reports no HTTP3 feature. The official image is `curlimages/curl` (8.23.0, 2026-10-28); whether it has HTTP3 is *unverified* (the curl-container Makefile shows `--with-nghttp2` and no ngtcp2). Check `curl -V` and pin by digest, or build curl with ngtcp2 in a cached step.
- **Chrome:** the runner has Chrome 156, and Playwright 1.64.1 is already a dev dependency. Forcing QUIC with `--origin-to-force-quic-on` is *unverified* on that version.
- **QUIC interop runner:** needs our own endpoint image implementing its test cases; leave for after experimental.
- Not researched: `quiche-client`, `h2load` with h3.

### E.7 Recommendation

7.1 **Stack and shape.** quinn 0.11.12 + h3 0.0.8 + h3-quinn 0.0.10 on our rustls/ring config, behind cargo feature `http3`, integrated as a Pingora custom session (3.2), with the duplex path (3.3) as fallback. Supersede ADR-0006 with a new ADR, and update H-PERF-05, roadmap v0.9 and docs/05 §18 and 06 §2, which all name tokio-quiche and BoringSSL.

7.2 **Experimental contract.**
- **In:** h3 ingress on `https` listeners; GET/POST with streaming bodies; trailers; GOAWAY on shutdown; Retry; stateless reset; `Alt-Svc`; the same router, middlewares, cache and access log.
- **Refused with the "planned" diagnostic:** h3 to backends, 0-RTT, active migration, datagrams, WebTransport, CONNECT-UDP, WebSocket over h3, server push, PROXY protocol on the QUIC socket, Gateway API exposure.
- **Not promised:** connections surviving an upgrade; throughput targets.

7.3 **Config sketch.** A block on the `https` listener, so one logical listener owns both sockets; a `udp` listener on the same address then becomes a validation error.

```yaml
listeners:
  websecure:
    address: ":443"
    tls: { ... }
    http3:
      enabled: false          # default
      advertise: true         # Alt-Svc on this listener's responses
      advertise_max_age: 1h   # RFC default is 24h; short while experimental
      advertise_port: null    # for port mappings (public 443 -> container 8443)
      retry: auto             # auto (threshold 100) | always | never
      max_idle: 30s           # HAProxy's default
      max_concurrent_streams: 100
      max_header_size: 64KiB  # hard upper bound 1MiB (5.4)
      max_connections: null   # plus a per-client cap
      congestion: cubic       # cubic | newreno | bbr
      gso: true
      qlog: null              # directory; off
```

Without the feature compiled in, `http3.enabled: true` gets the gate diagnostic, as `type: wasm` does in `gate.rs`.

7.4 **Tests.**
- **Unit:** pseudo-header and field validation table (RFC 9114 §4.1–4.3), limits.
- **e2e, no Docker needed:** an in-tree quinn+h3 client in `rdock-testkit`, covering Retry, large bodies, trailers, reset mid-body, GOAWAY on reload, `Alt-Svc` present/absent, and fallback when UDP is closed.
- **CI job `http3`** (not required, like `wasm`): `just http3` (clippy, tests, MSRV with the feature), then curl `--http3-only` from a pinned image, an h3i-based malformed-request suite in a non-workspace crate, and a Chrome check that `nextHopProtocol` is `h3`.
- **Fuzz:** a target for our h3-to-`RequestHeader` mapping.

7.5 **Step order.**
1. New ADR and requirement text.
2. Feature flag, model, schema, gate diagnostic.
3. QUIC listener on the existing UDP bind, with our certificate resolver.
4. Custom-session spike (3.4); decide (b) or (c).
5. Validation and limits.
6. `Alt-Svc`.
7. Reload and hand-over behaviour with persisted keys.
8. Metrics and logs.
9. CI job and interop.
10. Website page.

7.6 **Risks.**
- h3 stays unreleased (stale fixes; issue #379 open). Mitigate with limits, a thin trait around h3, and a decision on question 2.
- Pingora's custom-session trait is hidden API and may change in 0.10.
- quinn's advisory rate (nine in 2024–2026) means prompt bumps.
- One endpoint per listener caps UDP throughput.

7.7 **Open questions for the maintainer.**
1. Should release binaries include `http3` (runtime-off), or stay feature-off like `wasm` until it leaves experimental?
2. If h3 0.0.9 does not appear, do we allow one git source in `deny.toml`, vendor a patched copy, or ship on 0.0.8 with limits?
3. `retry` default: `auto` at 100 half-open, or `always`?
4. On upgrade: close QUIC connections after a short drain (proposed), or invest in per-connection sockets or BPF now?
5. Where do the reset and token keys live: derived from an existing secret, or a new file in the state directory?
6. Is "interop with h3i/curl" satisfied by the CI job in 7.4, or is a QUIC interop runner image required for v0.9?

## Decisions

The open questions at the end of Parts A, C, D and E were answered by the maintainer in [ADR-0031](../decisions/0031-v0-9-scale.md) and [ADR-0032](../decisions/0032-http3-on-quinn-and-h3.md). The lines below give the main answers; where an ADR does not say, the line says "left open". Part B ends with a recommendation rather than questions.

### Part A: upgrade and performance

- Peer handover or a permanent supervisor: peer handover; no permanent supervisor (ADR-0031). A supervisor and in-container upgrades are open after v0.9 by decision.
- Default `upgrade.drain`: 10 minutes, `unlimited` allowed with a warning.
- Upgrades in containers: refused as PID 1 with a diagnostic (replace the container); systemd gets `MAINPID=` and `NotifyAccess=main`.
- Binary verification: the file must be a regular file, not group- or world-writable, owned by root or the running user; `upgrade.trusted_keys` adds an optional minisign check.
- UDP at handover: sessions end at the handover; migration is open after v0.9.
- `SO_KEEPALIVE` default: `keepalive` is a listener socket option and everything except the backlog keeps the kernel's behaviour; the values are left open.
- Soak and "target RPS": a weekly job of about 5 hours on a hosted runner with a binary upgrade every 30 minutes; the 24-hour criterion and the 4- and 8-CPU measurements stay open until a machine is rented; "target RPS" is the soak's existing rate.
- Backlog default 4096: yes, listed as a behaviour change in the consequences; whether a deprecation note is needed is left open.
- Ticket keys on disk: only with `tls.tickets.key_file`; in memory and handed to the next process otherwise.

### Part B: issue 181

- Step 3's 60 microsecond target is restated as relative gates (allocations, system calls, CPU time per request within twice the A/A spread); routing gets a host index and the per-request allocations go.
- Statistics rings are lazy and not recorded when nothing can read them.
- The nightly gate gains a CPU-per-request ratio and `MIN_THROUGHPUT_RATIO` becomes 0.98.
- Step 4 (TLS tail): `tls.max_handshakes` exists, unlimited by default until the experiment is run; an offload pool only with benchmark evidence.
- Allocator: mimalloc stays the default; a jemalloc feature exists for comparison.
- Steps 5 and the 24-hour soak: left open until a machine exists.

### Part C: balancing and security

- Hedging: refused as planned; `retries.per_try_timeout` only.
- Peak-EWMA sample: time to first byte, `decay` 10 s; a `measure: header|last_byte` option is left open. Whether `p2c` draws two distinct backends: left open.
- Tiers: `priority: 0..=7` with `failover: strict | spill`; `backup` stays as tier 1 (so the alias is kept).
- Own zone: `Backend.zone` and `locality`, off by default; the Kubernetes provider keeps EndpointSlice zones and hints; the source of the proxy's own zone (node RBAC or `RDOCK_ZONE`) is left open.
- Abuse middleware: `type: abuse`, bans in their own bounded list, per instance unless a cluster store is configured; global versus per-route default is left open.
- JA3 or JA4: JA4 computed from our ClientHello parser, JA3 as an explicit option, a `ClientFingerprint` matcher; nothing from the FoxIO-licensed JA4+ family.
- GeoIP: `geoip.database`, no database bundled or downloaded, `max_age` 30 days with `on_stale`; which free source the docs recommend first, opt-in `country`/`asn` logging and the `maxminddb` pin are left open.
- SPIFFE: file-based rotation with watched files; the Workload API is planned; whether a SPIFFE ID becomes the consumer is left open.
- Tenants: `tenants.<name>` scopes tokens and users to a name prefix and host claims; a scoped caller cannot define middlewares that read files or call out; minting consumers and keys by scoped tokens is left open.
- ADR-0022's "doubling (Envoy)" wording: left open.
- H-SEC-02 and H-SEC-06: closed by reference to ADR-0030; their open items stay listed in the roadmap.

### Part D: cluster

- Where issuance runs: data planes issue, under a per-name lease with a fencing token where the store has one, a re-check after taking it, and a shared ACME account.
- Control plane: one active; a highly available one is planned.
- Data-plane certificate lifetime: short-lived client certificates from the control plane's CA; the value is left open.
- Version skew: bundles of another cluster, a lower revision or an empty bundle are refused; a stricter skew rule is left open.
- Redis: optional backend with an in-tree RESP client; no Redis crate.
- Stores: the control plane and a shared directory; S3, Kubernetes-Secret, PostgreSQL and etcd stores are open after v0.9; the Kubernetes provider does not write Secrets (ADR-0029 is not changed).
- Tenancy: ships in v0.9 as in Part C; tenant-owned listeners and certificates, a tenant label on core metrics and a tenant dashboard view are planned.
- Limits scope: `scope: instance | cluster`, default `instance`; cluster scope uses leased shares with a documented error bound and falls back to the local limit when the store is away; `in_flight` with cluster scope is refused as planned; a warning when a cluster is configured is left open.
- `CertMeta` versus ADR-0020 (Part D question 10): left open.

### Part E: HTTP/3

- Release binaries: `http3` is off by default and not in release binaries or images while experimental.
- If h3 0.0.9 does not appear: `deny.toml` keeps refusing git sources and `h3` is not pinned to a commit; vendoring a patched copy versus shipping 0.0.8 with limits is left open.
- `retry` default: `auto`, starting at 100 half-open connections.
- On upgrade: QUIC connections do not move; the old side sends GOAWAY, drains for a bounded time and closes.
- Reset and token keys: stored in the data directory; deriving them from an existing secret is left open.
- ADR-0006 is superseded by ADR-0032; ADR-0008 is superseded by ADR-0031 together with ADR-0012.

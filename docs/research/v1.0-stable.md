### 1. How comparable projects define stability (facts)

All pages read on 2026-11-13.

#### 1.1 Traefik

Source: <https://doc.traefik.io/traefik/deprecation/releases/> and <https://doc.traefik.io/traefik/deprecation/features/>.

- "The Traefik Proxy project follows the semantic versioning scheme and maintains a separate branch for each minor version."
- Support windows, as of v3.6: "Every `minor` is supported for 6 months from its GA release date", so several minors can be supported at once. "The last `minor` after releasing a new `major` is supported for 2 years following the `major` release (starting with v3)." Before v3.6 only the latest minor had active support.
- Two support classes: *active support* ("receives any bug fixes") and *security support* ("receives only critical bug and security fixes").
- The page's table today: 3.7 (released 2026-05-05) is the only line with active and security support; 3.6 active support ended 2026-05-07 and security support 2026-08-16; 2.11 security support ended 2026-09-07.
- Deprecations are published as a table with the columns Feature, Deprecated, End of Support, Removal. The page states no general removal timeline; removal is given per feature. "All target dates … may be subject to change."

#### 1.2 Caddy

Sources: <https://github.com/caddyserver/caddy/security/policy>, <https://github.com/caddyserver/caddy/issues/5050>.

- Supported versions for security fixes: `2.latest` only; anything older is unsupported. No backport statement.
- I found **no official stability or versioning policy page**. In issue 5050 (2022-09-20) the maintainers wrote "We do follow semver, mostly" (mholt) and "We're not really doing semver right now" (francislavoie: "v2" is a product name, `2.x` releases remove deprecations, and Go's module-path rule makes a v3 costly for plugins). That is an issue comment from 2022, not a policy.

#### 1.3 Envoy

Sources: <https://github.com/envoyproxy/envoy/blob/main/CONTRIBUTING.md> (Breaking change policy), <https://github.com/envoyproxy/envoy/blob/main/api/API_VERSIONING.md>, <https://github.com/envoyproxy/envoy/blob/main/RELEASES.md>, <https://github.com/envoyproxy/envoy/blob/main/EXTENSION_POLICY.md>.

- **Deprecation needs a replacement first**: "this may only be done when a replacement implementation and configuration path is available in Envoy on main."
- **Two-phase deprecation**: in the first release cycle, use of a deprecated feature logs a warning and increments the stat `runtime.deprecated_feature_use`. In the second cycle "use of the deprecated configuration will cause a configuration load failure", which an operator can override per feature in runtime config (or with `envoy.features.enable_all_deprecated_features`). `envoy.features.fail_on_any_deprecated_feature` makes every deprecated field fatal at once, for people who want to find them early.
- Operators get "a window of at least 12 months or until the organization moves to the next major API version."
- **API**: v3 "is the final major version of the API and will be supported forever"; "no field will ever be removed". Breaking changes inside a major version are listed (renaming or renumbering fields, changing types, singular to repeated, stricter validation). Exceptions: `vNalpha` packages, and files, messages or fields annotated `work_in_progress`. Changes to *default values* are explicitly not covered by the policy.
- **Extensions** carry a status: `stable` ("expected to be production usable"), `alpha` ("functional but has not had substantial production burn time"), `wip` ("not intended for production use"), plus a separate *security posture* (for example `robust_to_untrusted_downstream`).
- **Releases**: quarterly; stable releases are supported for about 12 months; backports are security fixes, crash fixes and bug fixes the release maintainers accept. Latest: 1.40.0 (2026-10-13, end of life 2027-10-13).

#### 1.4 HAProxy

Source: <https://www.haproxy.org/>.

- "Branches with an even number are called 'LTS'" and are maintained 5 years; odd branches "are only called 'stable'" and "are maintained between 12 and 18 months".
- Today: 3.4 LTS (released 2026-06-03, end of life 2031-Q2), 3.3 stable (end of life 2027-Q1), 3.2 LTS, 3.0 LTS; 2.8 and 2.6 receive critical fixes only.

#### 1.5 NGINX

Sources: <https://nginx.org/en/download.html>, <https://docs.nginx.com/nginx/admin-guide/installing-nginx/installing-nginx-open-source/>.

- Two lines: *mainline* (odd middle number, new features and fixes, updated every one to two months; 1.31.8 today) and *stable* (even middle number, updated about once a year; critical fixes are "always backported from the Mainline version"; 1.30.6 today). Older stable lines are listed as "legacy".
- I found no written deprecation policy on those pages.

#### 1.6 Kubernetes

Sources: <https://kubernetes.io/docs/reference/using-api/deprecation-policy/>, <https://kubernetes.io/docs/reference/using-api/> (API versioning), <https://kubernetes.io/releases/version-skew-policy/>.

- **Stages**: alpha (off by default, "may be dropped at any time without notice", may change incompatibly), beta (well tested, "the support for a feature will not be dropped, though the details may change", migration instructions provided), stable (`vX`, kept for the whole major version).
- **API rules**: an element can only be removed by incrementing the API version (Rule 1); a version cannot be deprecated in favour of a less stable one (Rule 3); GA versions are not removed within a major version, beta versions are served 9 months or 3 releases after deprecation, alpha may go without notice (Rule 4a).
- **CLI**: user-facing CLI elements work for 12 months or 2 releases after deprecation when GA, 3 months or 1 release when beta, 0 when alpha (Rule 5a); "Deprecated CLI elements must emit warnings (optionally disable) when used" (Rule 6).
- **Behaviour**: "Deprecated behaviors must function for no less than 1 year after their announced deprecation" (Rule 7).
- **Metrics** have their own stability classes: after deprecation a STABLE metric works for 3 releases or 9 months, BETA 1 release or 4 months, ALPHA 0 (Rule 11b). A deprecated metric gets "(Deprecated from x.y)" in its help text and a warning at registration, then becomes *hidden* (off unless `--show-hidden-metrics-for-version` is set), then is deleted.
- **Support**: release branches for the three most recent minors; about 1 year of patches each.

#### 1.7 Gateway API

Source: <https://gateway-api.sigs.k8s.io/docs/concepts/versioning/> (the older `/concepts/versioning/` URL answers 404 today).

- Two channels. **Standard**: beta or GA resources and graduated fields; "We recommend using the Standard Channel by default". **Experimental**: everything in Standard plus alpha resources and new fields; "makes no backwards compatibility guarantees and breaking changes may be released at any point".
- Graduation to Standard needs: full conformance test coverage, multiple conformant implementations, widespread use, "at least 6 months of soak time as an alpha API", "no significant changes for at least 1 minor release and 3 months", and owner approval. A feature with "no progress in 6 months" is dropped.
- Standard minors may only graduate features, loosen validation, or remove resources under the Kubernetes deprecation policy. Standard releases target a 4-month cadence with a fixed date and flexible content.
- "We do not provide stability guarantees for source code imports."

#### 1.8 Rust crates and Cargo

Sources: <https://doc.rust-lang.org/cargo/reference/semver.html>, <https://github.com/obi1kenobi/cargo-semver-checks>, crates.io API.

- For `0.y.z`, a change in `y` is treated as major; "only changes in the left-most non-zero component are considered incompatible".
- Major changes include: removing or renaming a public item, adding an enum variant or a public field without `#[non_exhaustive]`, adding a non-defaulted trait item, adding `#[non_exhaustive]` to an existing public item, and removing a Cargo feature.
- Raising the MSRV is "possibly-breaking": "It is generally recommended to treat this as a minor change, rather than as a major change."
- `cargo-semver-checks` lints for these; see section 2.3 for its limits.

#### 1.9 Pingora

Sources: <https://github.com/cloudflare/pingora> (README), crates.io API.

- No versioning or release-cadence statement in the README. Latest crate: `pingora` 0.9.1 (2026-11-03), still `0.x`.
- "APIs related to caching are currently highly volatile." "Pingora proxy integration with caching should be considered experimental." TLS: "rustls(experimental)".
- MSRV: "a rolling MSRV … policy of 6 months"; "Our current MSRV is 1.85."
- **Consequence for us (fact plus inference):** ReverseDock's default TLS backend (rustls, ADR-0002) and its cache (`rdock-cache` on `pingora-cache`) both sit on parts Pingora itself calls experimental. A 1.0 promise about our configuration is still possible, because users see our schema and not Pingora's API, but it means we absorb upstream breaks ourselves.

#### 1.10 What the comparison shows

| Project | Version scheme | Stages | Deprecation | Security support |
|---|---|---|---|---|
| Traefik | SemVer | none formal | per-feature table, no fixed period | each minor 6 months; last minor of a major 2 years |
| Caddy | "semver, mostly" | none formal | changelog | latest 2.x only |
| Envoy | quarterly 1.N | stable / alpha / wip per extension; WIP annotations in the API | warn one cycle, fail (overridable) the next, at least 12 months | about 12 months per release |
| HAProxy | X.Y, even = LTS | experimental directives (not checked today) | not checked | LTS 5 years, others 12 to 18 months |
| NGINX | mainline / stable | none | none found | current stable and mainline |
| Kubernetes | 1.N | alpha / beta / GA | written rules per surface (API, CLI, behaviour, metrics) | 3 minors, about 1 year each |
| Gateway API | SemVer bundle | Experimental / Standard channels | Kubernetes policy for Standard | not applicable |

The two models worth copying are Envoy's two-phase deprecation (warn, then fail with an override) and Kubernetes' per-surface rules, including a separate rule for metrics.

### 2. What ReverseDock exposes, and what guards it today

#### 2.1 What the project already says (facts)

- `docs/06-repo-layout.md` §4: "Versioning: SemVer. `0.x` may break config between minors with a migration note and `rdock config migrate`. Config schema is versioned (`apiVersion`-style `version: 1` optional key)." and "Support policy: last two minor releases get security fixes".
- `SECURITY.md`: `0.x` latest release only; "`1.x` and later: the two most recent minor releases".
- `docs/04-requirements.md`: F-OSS-05 is the only open F-OSS item.
- `crates/rdock-model/src/config.rs:28`: `version: Option<u32>`, "Only `1` exists; omit it to use the latest."
- **`rdock config migrate` does not exist.** `rdock config` has `history`, `diff` and `rollback` (`crates/rdock/src/admin_cli.rs:18`); `rdock migrate` has only `traefik` (`crates/rdock/src/lib.rs:165`). The sentence in `06` describes a command that was never built.

#### 2.4 Recommendations for section 2

1. **One script, three schemas.** Write `scripts/check-schema-compat.py` (standard library only, run with `-I` like `check-docs.py`) that compares two JSON Schemas and fails on: a removed property, a property that became required, a removed enum value, a narrowed type, `additionalProperties` tightened, a tightened numeric or length bound, and a changed default. Use it for `schema/rdock.v1.json`, `schema/agent.v1.json`, `values.schema.json` and the new access-log schema. Our schemas are generated by one tool in one style, so a small purpose-built checker is more reliable than a general WIP diff tool.
2. **Baseline = the last release tag**, read with `git show <tag>:schema/…`. No second copy of the schema in the tree.
3. **`oasdiff breaking`** on `schema/openapi.json` in the `clients` job (already required). Install the pinned release with a checksum, as `ci.yml` does for actionlint.
4. **Snapshots that only grow**: `schema/metrics.v1.txt`, `schema/cli.v1.json`, `schema/access-log.v1.json`, generated by hidden subcommands or tests, with drift tests like the two that exist.
5. **Skew tests** for rows 17 to 19 need the previous release's binary in CI. Download it from the GitHub release and verify it with `gh attestation verify`, which also exercises our own verification path.
6. **An override, not a bypass**: an intended break is declared in the PR (label `breaking-change` plus an entry in a committed `schema/compat-exceptions.json` with a reason and the deprecation that preceded it), so the check stays required and the exception is reviewed.
7. Fix `docs/06-repo-layout.md` §4: `rdock config migrate` does not exist.

### 3. Experimental features today, and a maturity scheme

#### 3.1 How the code marks things today (facts)

There are five separate mechanisms and no shared vocabulary.

| Mechanism | Where | What the user sees |
|---|---|---|
| Cargo feature, off in release builds | `wasm` (`rdock`, `rdock-wasm`, `rdock-middleware`, `rdock-proxy`); `http3` is listed in `docs/06-repo-layout.md` and ADR-0032 only | Without the feature, `type: wasm` is refused: "this build does not include WASM plugins; build with --features wasm" (`gate.rs`, `not_built`) |
| "EXPERIMENTAL" in doc comments | `crates/rdock-model/src/middleware.rs:71` and `:827`, `rdock-wasm/src/lib.rs:1`, `wit/filter.wit:1` | The word reaches the JSON Schema description (`schema/rdock.v1.json:5620`) and so the generated reference |
| `rdock version` | `crates/rdock/src/lib.rs:397` | "WASM plugins: ABI 0.1.0 (experimental)" or "not in this build" |
| The "planned" gate (ADR-0014) | `crates/rdock-proxy/src/gate.rs:23`: "`<what>`: not supported in this version (planned for `<milestone>`)"; a warning in `rdock validate`, an error in `rdock run` | Accepted by the schema, refused at run time. 14 occurrences in Rust sources; examples: hedging, background refresh for `stale-while-revalidate`, gRPC and SPOP agents, PROXY protocol on UDP |
| Website status badges | `<Status since="v0.5" />`, `<Status planned="v0.9" />`; `apps/website/src/data/status.json` is proved against the binary by `scripts/check-status.ts` | A badge per setting or page |

Further facts:

- **`http3` does not exist in code.** No `http3` string in any `crates/**/*.rs` or `crates/*/Cargo.toml`. It is planned in ADR-0032 and the feature table.
- **No runtime signal for experimental use.** With the `wasm` feature on, loading a WASM plugin logs no "experimental" warning and sets no metric (no match in `crates/rdock-middleware/src/wasm.rs` beyond the module comment).
- Things the documents call unfinished but the code does not mark: the HTTP cache sits on `pingora-cache`, which Pingora calls "highly volatile" and which ADR-0030 calls alpha; the cluster (v0.9, unreleased); UDP routes and `rdock upgrade` are new; the Terraform provider is unpublished; `rdock-plugin-api` is `0.x`.
- Website metrics marked `planned="v0.9"` are already registered in `metrics.rs` on `main` (for example `rdock_upgrades_total`). That is consistent with "unreleased", but it shows the badge means "release in which it ships", not maturity.
- Non-required CI jobs are a hidden maturity signal: `wasm`, `terraform-provider`, `http-cache`, `openbao`, `oidc-dex`, `waf-example`, and all of `kubernetes.yml`.

#### 3.2 Recommendation: three levels, one source of truth

| | Experimental | Beta | Stable |
|---|---|---|---|
| Promise | None. May change or be removed in any release, including a patch | Will not be removed without a deprecation. Details may change in a minor, with a migration note and, where possible, `rdock migrate` | Covered by the full policy of section 5 |
| Default | Off. Needs an explicit opt-in | Available; never on by default when it changes behaviour | Available |
| Release binaries | May be compiled out (Cargo feature) | Always compiled in | Always compiled in |
| `rdock validate` | Warning `experimental: <feature>`; an error under `--strict` unless the feature is opted into | Note (not a warning) | Silent |
| Run time | One `WARN` at load, and `rdock_experimental_features{feature}` = 1 | Listed in `rdock status` | Nothing |
| Security policy | Fixes on `main` only; no backports; a security bug is still handled privately | Backports as for stable | Backports |
| CI | May be a non-required job | Required job | Required job |
| Docs | Badge "experimental" and a caveat box | Badge "beta" | Badge "since vX.Y" |

**Opt-in for experimental features.** One top-level key, for example:

```yaml
experimental:
  - wasm
  - http3
```

Without the entry, a configuration that uses the feature is refused with a diagnostic naming the key. This puts the acknowledgement in the file, where a reviewer sees it, and gives `validate` a path to point at. It also removes the need for the word "EXPERIMENTAL" in doc comments. A Cargo feature remains a build matter (binary size, dependencies) and is independent of the level.

**One registry.** A single table in `rdock-model` (feature id, level, since, path patterns) from which come: the validate diagnostics, the schema annotation (`x-rdock-stability`), the website badges (replacing the hand-kept half of `status.json`), the `rdock status` listing and the metric. The existing `planned` gate stays as it is: "planned" means not implemented, which is a different thing from a maturity level.

**Rules for moving.**

- *Experimental → beta*: an ADR or an ADR amendment; e2e tests in a required job; documentation page; no open known defect that loses data or bypasses a security control; at least one released minor as experimental.
- *Beta → stable*: no incompatible change for one full minor and at least 3 months (the Gateway API's rule); fuzzing where the feature parses untrusted input; the surface is in the compatibility checks of section 2; where an external suite exists, it passes in a required job.
- *Demotion* never happens silently: a stable feature can only be deprecated. An experimental feature with no progress for two minors is removed (Gateway API drops after 6 months without progress).
- A feature cannot be more stable than what it stands on. If the upstream part is declared experimental (Pingora's cache integration), we may still call our *configuration* stable only if we are prepared to carry the upstream break ourselves; that is a maintainer decision (question 6).

**Proposed starting classification** (for discussion, not verified against usage):

- *Experimental*: WASM plugins and their ABI; HTTP/3 when it lands; the Terraform provider and Go client until published.
- *Beta*: cluster and `rdock control`; binary upgrade by handover; HTTP cache; UDP routes; native plugin SDK; agents; OIDC login; quotas and metering; GeoIP, JA4 and `abuse`; Kubernetes Ingress translation; Vault references.
- *Stable at 1.0*: file provider and reload; HTTP proxying, routing rules, TLS, ACME; Docker and Swarm providers with both label grammars; P0 and P1 middlewares; admin API `/api/v1`, users, tokens, audit log; TCP routes; metrics and access log; the Gateway API controller for the profiles that pass conformance.

#### 4.2 What the standards say (facts, read 2026-11-13)

- **SLSA**: the current specification is v1.2, status "Approved", with a Build track and a Source track (<https://slsa.dev/spec/v1.2/>). Build L1 = "Provenance showing how the package was built"; L2 = "Signed provenance, generated by a hosted build platform"; L3 = "Hardened build platform" (<https://slsa.dev/spec/v1.2/build-track-basics>).
- **GitHub artifact attestations**: "Artifact attestations by itself provides SLSA v1.0 Build Level 2"; reusable workflows give the isolation needed for Build Level 3. Public repositories sign with the Sigstore public-good instance and the bundle goes to a public transparency log (<https://docs.github.com/en/actions/concepts/security/artifact-attestations>).
- **OpenSSF Scorecard** has 20 checks (<https://github.com/ossf/scorecard/blob/main/docs/checks.md>). *Signed-Releases* looks for release assets ending in `.minisig`, `.asc`, `.sig`, `.sign`, `.sigstore`, `.sigstore.json` or `.intoto.jsonl`; signatures earn 8 points and provenance on every release the full 10. *SBOM* gives full marks for an SBOM published as a release artefact. *Pinned-Dependencies* scans Dockerfiles, shell scripts and workflows for hash pinning. *SAST* looks for CodeQL or SonarCloud. *CII-Best-Practices* looks for the OpenSSF Best Practices badge.
- **Sigstore**: keyless verification is by identity: `cosign verify-blob <file> --bundle artifact.sigstore.json --certificate-identity=… --certificate-oidc-issuer=…` (<https://docs.sigstore.dev/cosign/verifying/verify/>). Our documented commands match this form.
- **Reproducible builds**: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts" (<https://reproducible-builds.org/docs/definition/>).
- **SBOM minimum elements**: CISA published a *draft* "2025 Minimum Elements for an SBOM" on 2025-08-22 for comment (<https://www.cisa.gov/resources-tools/resources/2025-minimum-elements-software-bill-materials-sbom>). I did not read the PDF and do not know whether it has been finalised.

#### 4.3 Assessment and gaps

### 5. Policy draft (recommendation)

Written so it can become `docs/10-stability.md` (or an ADR "Stability, deprecation and support policy") plus a public page under `docs/project/`. An ADR is required by the documentation rules, since this changes the public-API and config-model contract.

#### 5.1 Versions

- `MAJOR.MINOR.PATCH`, SemVer 2.0.0, for the `rdock` binary, the image and the chart's `appVersion`.
- **Patch**: bug and security fixes only. No new configuration keys, no new metrics, no default changes, except where a security fix needs one (then it is called out in the advisory).
- **Minor**: additions; new deprecations; beta features may change with a migration note; experimental features may change freely.
- **Major**: the only place where a stable surface may break. Not more than once a year (HashiCorp's guidance for providers: "no more than once per year", <https://developer.hashicorp.com/terraform/plugin/best-practices/versioning>), and only after the deprecation period.
- Separate version lines: `rdock-plugin-api` (already separate), the WASM ABI (the WIT package version), the config schema (`v1`), the admin API (`/api/v1`), the cluster protocol and the data-directory format (integers), the Helm chart (`version` follows SemVer; Helm treats `appVersion` as informational, <https://helm.sh/docs/topics/charts/>), and later the Terraform provider and Go client.
- Suggested cadence: a minor every 8 to 12 weeks. Cadence decides how long "two minors" is (question 2).

#### 5.2 What counts as breaking, per surface

| Surface | Breaking (needs a major, after deprecation) | Not breaking |
|---|---|---|
| Config file | Removing or renaming a key; changing a type; making an optional key required; removing an enum value; rejecting a file that validated before; **changing a default that changes behaviour**; changing the meaning of an existing value | New optional keys; new enum values (consumers of the schema must tolerate unknown values); new warnings; stricter rejection of a configuration that was *unsafe* (see 5.6); wording of diagnostics |
| Rule grammar | A rule that parsed no longer parses or matches differently; priority order changes | New matchers and functions |
| Labels (`rdock.*`) | As for config | New labels |
| Traefik label subset | Dropping a label listed as supported | Following Traefik's own deprecations with the same warning Traefik gives; the supported Traefik version range is stated and may move forward in a minor |
| CLI | Removing or renaming a command, flag or env variable; changing exit-code meaning (`0`, `1`, `2`); changing JSON output fields or types; changing a default | New commands, flags, JSON fields; **all human-readable text output**, including `--help` and diagnostics wording |
| Admin API `/api/v1` | Removing a path, method, field or enum value; making a request field required; changing types, status codes, auth scopes | New paths, optional request fields, response fields, enum values in responses (documented: clients must ignore unknown fields and values) |
| Metrics | Removing or renaming a metric or label; changing type, unit or histogram buckets of a stable metric | New metrics; new label *values*. A new label *name* on an existing metric is breaking for aggregations and is treated as a new metric |
| Access log (JSON) | Removing or renaming a field; changing type | New fields. The text format is not stable |
| Problem types | Removing or changing the `type` URI or status of a problem | New types; wording of `title` and `detail` |
| Plugin SDK | Per the Cargo SemVer reference (<https://doc.rust-lang.org/cargo/reference/semver.html>) | Additions behind `#[non_exhaustive]` and defaulted trait items |
| WASM ABI | Any change to an existing import or export of a released world | A new world version served side by side |
| Cluster protocol | A control plane that cannot serve data planes of the two previous minors; a data plane that cannot talk to a control plane one minor newer | Additive fields |
| Data directory | A new binary that cannot read the previous minor's directory; a format bump without a documented downgrade statement | New files |
| Environment | Removing or renaming a documented variable | New variables. `RDOCK_BUILD_*`, `RDOCK_*_TESTS`, `RDOCK_FAULT*`, `RDOCK_UPDATE_GOLDEN` are internal |
| Image | Entrypoint, default command, user id, data path, exposed ports, healthcheck | Base image updates |
| Helm values | As for config, on `values.schema.json`; renaming created resources | New values |
| Rust crates other than `rdock-plugin-api` and `rdock`'s `run` entry | **No promise.** They are internal, unpublished, and may change in any release | — |

Explicitly *not* covered: performance characteristics, log message wording, the dashboard's look and URLs, undocumented behaviour, anything experimental, error text.

#### 5.3 Deprecation

- **A replacement first** (Envoy's rule): nothing is deprecated until its replacement is in a release.
- **Period**: a stable element works for at least **two minor releases and six months** after the release that deprecates it, whichever is longer, and is removed only in a major. Beta: one minor and three months, removal allowed in a minor. Experimental: none. (Kubernetes uses 12 months for GA user-facing CLI and behaviour; six months is a proposal for a small project and is question 3.)
- **Never in favour of something less stable** (Kubernetes Rule 3).
- **How a deprecation surfaces**, all from one registry (the one of section 3.2):
  1. `rdock validate`: a warning with the path, the replacement and the removal version: `deprecated: listeners.web.tls.min_version: use tls.versions (deprecated in 1.3, removed in 2.0)`. `--strict` fails on it, so CI pipelines find it early. `--format json` carries `code`, `since`, `removal`, `replacement`.
  2. `rdock migrate config` (5.5) rewrites it.
  3. At load and reload: one `WARN` per deprecated element (not per request).
  4. Metric `rdock_deprecated_config_in_use{element}` = 1, so fleets can alert (Envoy has `runtime.deprecated_feature_use`).
  5. `rdock status` and the admin API (`GET /api/v1/config` diagnostics) list them; the dashboard shows a banner.
  6. Labels: the same warning in the provider's diagnostics and events.
  7. Schema: `"deprecated": true` plus the text in `description`, so editors strike it through; the generated reference shows a "deprecated since" badge.
  8. OpenAPI: `deprecated: true` on the operation or field, and the HTTP `Deprecation` and `Sunset` response headers (RFC 9745 and RFC 8594; not re-read today).
  9. CLI: a warning on stderr when a deprecated flag or command is used (Kubernetes Rule 6).
  10. Metrics: Kubernetes' model: help text prefixed "(Deprecated since x.y)", then hidden unless `observability.metrics.show_deprecated` is set, then removed.
  11. Docs: a page "Deprecations" with Traefik's four columns (feature, deprecated in, end of support, removal), generated from the registry; a "Deprecated" section in `CHANGELOG.md` (Keep a Changelog already has one).
- **A dry run of the future**: `rdock validate --deprecations=error` (or `--target 2.0`) treats every deprecated element as an error, like Envoy's `fail_on_any_deprecated_feature`.
- I do not recommend Envoy's second phase (fail by default with an override) inside a major: with SemVer, a configuration that loaded in 1.3 must load in 1.9.

#### 5.4 Support and security fixes (F-OSS-05)

- **Supported**: the two most recent minor releases of the current major (already in `SECURITY.md`). When `1.N` is released, `1.N-2` ends.
- **After a new major**: the last minor of the previous major gets security fixes for a fixed period. Traefik gives 2 years; for a volunteer project I suggest 6 months (question 4).
- **What is backported**: security fixes of CVSS v4 "medium" and above, and fixes for crashes, data loss and certificate-issuance failures. Other bug fixes go to the newest minor only. Fixes to experimental features are never backported.
- **How**: fix on `main` first, cherry-pick to `release/1.N` by PR (same ruleset as `main`), tag from the branch. Embargoed fixes go through a GitHub security advisory's private fork.
- **Skew**: data planes may be up to two minors older than the control plane and never newer; data-directory formats are readable by the next two minors; a downgrade across a format bump is refused (the code already refuses a newer format) and documented.
- **Dependencies**: a supported line receives dependency updates only for security advisories that affect it.
- **Pre-releases** (`-alpha`, `-rc`): no support; only the latest.
- State plainly on the support page that there is one maintainer and no SLA; the targets in `SECURITY.md` (3 working days, 7 days, 90 days) are targets.

#### 5.5 Config schema versioning

- `version: 1` stays optional through 1.x and means schema v1. Within v1, only additive changes and deprecations.
- A `v2` schema is introduced in a **minor** of the 1.x line, opt-in with `version: 2`, published as `schema/rdock.v2.json`. For at least two minors both are accepted; the loader converts v1 to the internal model, so there is one model and two front ends.
- The next major makes v2 the default and keeps *reading* v1 for one more major with a deprecation warning.
- **`rdock migrate config [--to 2] [--write]`**: reads a v1 file and prints v2 (or the diff), preserving comments where the YAML library allows it (not verified for serde-saphyr), and also rewrites deprecated v1 keys inside v1. It belongs under the existing `rdock migrate` (next to `traefik`), with the code in `rdock-migrate`. This replaces the never-built `rdock config migrate`.
- Labels follow the same version: a `rdock.version=2` label is not needed; label keys map to schema paths, so a v2 rename is accepted under both names during the overlap, with the deprecation warning.
- The stored API-provider snapshot, last-known-good file and history entries record the schema version they were written with and are migrated on read.
- The `$id` of the schema must be a URL that will not move. Today it points to `raw.githubusercontent.com/…/main/…`, which serves the *current* file under an unversioned branch; move to `reversedock.dev` (or a tag-pinned URL) before 1.0 (question 7).

#### 5.6 Security exceptions

A change that makes an unsafe configuration fail (the project's "unsafe combinations are refused" rule) may ship in a minor or a patch without the deprecation period when it fixes a vulnerability. It needs: an advisory or changelog entry under "Security", a diagnostic that names the fix, and where possible one minor of warning first. Everything else waits for the period.

#### 5.7 MSRV and toolchain

- Facts: MSRV is 1.89 (`Cargo.toml`), defined as "the highest MSRV among our dependencies" (`docs/06` §2), checked by the required `msrv` job; the build toolchain is pinned to 1.99.1. Pingora keeps a rolling 6-month MSRV. Cargo's guidance is to treat an MSRV bump as a minor change.
- Recommendation: the MSRV matters only to people who build from source or write native plugins; release binaries are built with the pinned toolchain.
  - Raising the MSRV is allowed in a **minor**, never in a patch, and is listed in the changelog under "Changed".
  - The new MSRV must be a Rust release at least **6 months old** (Pingora's rule), unless a security fix in a dependency forces it.
  - `rdock-plugin-api` keeps its own, lower-if-possible `rust-version`, since it is what third parties compile against.
  - Supported minors keep the MSRV they were released with; a backport that needs a newer compiler is rewritten or the line ends early with notice.
- Platform tiers, to be stated: tier 1 Linux x86-64 and aarch64 (musl, static); tier 2 macOS arm64 (built and smoke-tested, no upgrade handover); Windows not supported.

#### 5.8 What has to exist before 1.0 (checklist)

1. The ADR and the public policy page (5.1 to 5.7), `SECURITY.md` and `docs/06` §4 aligned with it; F-OSS-05 ticked.
2. The feature registry and the three levels (3.2), with `experimental:` opt-in.
3. The deprecation plumbing (5.3 items 1 to 5 and 7) exercised by at least one real deprecation before 1.0, so the path is tested.
4. Compatibility checks of 2.4 as required checks: schema script, `oasdiff`, metrics and CLI snapshots, `cargo-semver-checks` for the plugin API.
5. `rdock migrate config`.
6. Release branches with a ruleset, the `latest` rule, and one rehearsed backport release.
7. Release-integrity gaps 2, 3, 5, 7 and 11 closed; a decision on 1, 4, 6, 8 and 9.
8. `rdock-plugin-api` published at a version plugin authors can pin, or the SDK declared beta at 1.0.

### 7. Open questions for the maintainer

2. **Release cadence after 1.0.** "Two minors" is 4 months at an 8-week cadence and a year at a 6-month cadence. Which?

### 0. Summary of findings

1. **Versions today.** Traefik v3.7.19 is "Latest"; v3.8.0-rc.3 is out the same day. Caddy v2.11.9 (5 Nov 2026). NGINX mainline 1.31.8, stable 1.30.6.
2. **The Traefik translator is in good shape for labels**, with 81 fixtures, but the suite compares the translator's output with hand-written expectations. Nothing runs Traefik, and nothing runs a real Compose file end to end. The vision's principle 6 ("a conformance suite that runs real Compose files") and the 1.0 criterion are therefore not yet met in the sense a reader would assume.
3. **`rdock migrate traefik` has five correctness gaps on real input** (section 1.5): Compose `${VAR}` interpolation and `$$` escapes are not handled, dynamic-file server weights are dropped without a note, `basicAuth.usersFile` in a dynamic file is refused with a label-specific message, TOML dynamic files are not read, and a router without `tls` becomes an HTTPS route without a note.
4. **"Changing the image name" does not work literally**: a Traefik container is almost always configured through `command:` flags or `TRAEFIK_*` variables (static configuration), which `rdock run` does not accept. The criterion needs a decision (section 7, Q1).
5. **Caddy**: recommend reading the adapted JSON (`caddy adapt`), not the Caddyfile. Of the 41 standard directives, 27 have a full or partial equivalent and 14 have none.
6. **NGINX**: a faithful subset exists for `server`/`listen`/`server_name`, prefix and exact locations, `proxy_pass`, `upstream`, `return`, TLS files, body size, basic auth and static roots. Regex locations, `if`, `map`, `rewrite … last`, `try_files` with named locations and variables in general do not translate faithfully and must be refused or flagged per construct.
7. **Parser**: `nginx-lint-parser` 0.24.0 (MIT) is the only maintained, permissively licensed NGINX parser on crates.io; a hand-written parser of about 300 lines is the lower-risk choice (section 3.4).
8. **Other tools' lesson** (ingress2gateway 1.0): translation is backed by tests that run both proxies and compare behaviour, and the tool reports each untranslated item with its source object and a suggestion. That is the model to copy.

#### 1.2 Facts: what ReverseDock has today

#### 1.5 Findings: gaps in `rdock migrate traefik` on real input (read, not run)

All from `crates/rdock-migrate/src/lib.rs` and `crates/providers/rdock-provider-docker/src/labels.rs`.

1. **Compose interpolation.** `Scope::draft` drops every label whose value contains `${` (except `.replacement`) with "`${…}` references are not allowed in labels". That rule is right for the provider, which sees labels after Compose has interpolated them, but `rdock migrate traefik` reads the raw Compose file, where ``Host(`${DOMAIN}`)`` is very common. Compose interpolates label values (`${VAR}`, `${VAR:-default}`, `${VAR:?err}` …): https://docs.docker.com/reference/compose-file/interpolation/. Result: the router's rule is dropped and the route disappears with a warning.
2. **`$$` escapes.** The same page says "`$$` (double-dollar sign) when your configuration needs a literal dollar sign". `basicauth.users` hashes in Compose files are written `$$apr1$$…` or `$$2y$$…`. `compose()` does not unescape them, so the migrated hash is wrong.
3. **Server weights dropped silently.** `take_servers` keeps only each server's `url`; `weight` and `preservePath` vanish without a note. This breaks the rule "unsupported semantics are diagnostics, never silent" (ADR-0003).
4. **`usersFile` in a dynamic file.** The file path goes through the label translator, so `basicAuth.usersFile` gets the label-only refusal, although `basic_auth.users_file` exists and the website's own example 3 uses it.
5. **TOML.** The file provider accepts YAML and TOML; `traefik()` parses YAML only (`serde_saphyr::from_str`).
6. **Plain-HTTP routers.** A Traefik router without `tls` serves plain HTTP. In the dynamic path `tls: {}` and "no tls" both flatten to no label, so the route gets ReverseDock's defaults (`defaults.listeners: [websecure]`, `defaults.tls: auto`). The website page documents this as a difference, but the tool prints no note.
7. **`serversTransports`, `weighted`, `mirroring`, `failover`** objects of a dynamic file produce generic "not in the supported subset" warnings per flattened key (or "the container exposes no port" for a service that has no `loadBalancer`), which are hard to read for a file migration.
8. **Static configuration** in the same Compose file (`command:` flags of the Traefik service) is ignored, so the output never contains listeners, ACME settings or the entrypoint map.

#### 1.6 Recommendation: what "documented subset, conformance-tested" should mean

**(a) Documented subset.** Generate the subset table from one machine-readable source instead of three hand-written ones (`docs/05-architecture.md` §11, `reference/docker-labels.mdx`, `from-traefik.mdx`). Proposal: a `tests/conformance/traefik-labels/coverage.yaml` listing every option of table 1.3 with `status: supported | partial | warned | unmapped | none`, the fixture that proves it, and the Traefik version it was checked against. A test fails when an option marked `supported` has no fixture, and a script renders the website table. A weekly job (`.github/workflows/weekly.yml` exists) fetches the option anchors of the pinned Traefik docs branch and reports options missing from `coverage.yaml`, so a new Traefik minor (v3.8 is at rc.3) shows up as a diff rather than as a bug report.

**(b) Three test layers.**

| Layer | What it proves | Needs | Where |
|---|---|---|---|
| L1 translation fixtures (exists, 81) | labels → model objects and diagnostics | nothing | `cargo test`, required check `rust` |
| L2 Compose corpus goldens (new) | real Compose files → `rdock migrate traefik` output, snapshot-compared, and the output passes `Config::validate` | nothing | `cargo test` |
| L3 differential (new) | Traefik and rdock give the same routing answer for the same labels | Docker, pinned images | separate CI job, not in `just ci` |

**(c) Corpus for L2 and L3.** Sources, in order of licence safety:

1. Traefik's own documentation examples (Docker provider page, each middleware page's "Labels" tab, user guides). Traefik is MIT-licensed (source above), so examples can be copied with the copyright notice in `NOTICE` and a `SOURCE` line per fixture (URL, commit, date). About 60 files are reachable this way.
2. Compose files written by the project for the platforms the roadmap names (Dokploy, Coolify, Portainer; roadmap v0.2 scope). Write them from each platform's documented label pattern rather than copying, because licences differ. I did not check those projects' licences (section 6).
3. Shapes, not copies, of popular self-hosting setups: reverse proxy plus forward-auth (Authelia/Authentik pattern), wildcard certificate with `tls.domains`, a `chain` of security headers, a TCP passthrough database, a UDP DNS service. Hand-written.

Target: at least 100 corpus files, each tagged with the options it uses, so coverage of table 1.3 can be computed. Do not scrape public repositories: licences are mixed and the files carry private hostnames, which the repository rules forbid.

**(d) The differential test (L3).** For each corpus file:

1. Start the file's services with `traefik/whoami` backends (already used in `benchmarks/compose.yaml`) and both proxies on one Docker network: `traefik:v3.7.x` pinned by digest, and the rdock image under test in zero-config mode with `expose_by_default` matching Traefik's `exposedByDefault` for that case.
2. Send a generated request matrix to both: for every `Host`, path prefix, method, header and query value that appears in any rule, the matching request and a near miss (other host, sibling path such as `/apiv2` for `/api`, wrong method), over each entry point. Hosts are sent with `curl --resolve` style overrides; certificates come from a static self-signed pair so no ACME is involved.
3. Compare a **routing answer**, not bytes: (i) status code, (ii) which backend container answered (`whoami` prints its hostname), (iii) the request line and selected headers the backend saw (path after strip/rewrite, `Host`, `X-Forwarded-Proto`, `X-Forwarded-Prefix`, added and removed custom headers, `Authorization` after `removeHeader`), (iv) for redirects, status and `Location`, (v) selected response headers set by `headers` middlewares.
4. Known deliberate differences live in an allow-list file with one entry per difference and a link to the ADR or doc line (opt-in exposure, several exposed ports, router without entry points, rate-limit burst default and delay, 502 instead of 500 for unreachable forward auth, `X-Forwarded-*` handling from untrusted peers). An unlisted difference fails the job.

This is the approach ingress2gateway 1.0 uses (section 4), and the repository already has the pieces: pinned competitor images in `benchmarks/compose.yaml` (`traefik:v3.5.4` there, which is three minors old and should be raised when this job is added) and a kind-based conformance job in `.github/workflows/kubernetes.yml` as a model for a Docker-dependent job.

**(e) Pass threshold.** Proposal, for the maintainer to confirm:

- L1: 100 %, as today.
- L2: 100 % of corpus files produce valid output; every dropped label appears as a note (no silent loss, checked by counting input labels against mapped plus noted ones).
- L3: for options marked `supported`, **100 % of requests agree** apart from allow-listed differences. For `partial`, the stated loss is the allow-list entry. A corpus file that uses an `unmapped` or `none` option is run with that label removed on the Traefik side as well, so the rest of the file is still compared.
- Published number on the website: "N of M Traefik v3.7 label options supported; K corpus files; Traefik version and date", generated from `coverage.yaml`.

**(f) Fix the gaps of 1.5** before calling the tool 1.0: items 1–4 and 6 are small; 5 (TOML) needs a TOML parser dependency (check `deny.toml`; `toml` is MIT/Apache-2.0) or a documented "convert to YAML first"; 8 is the larger piece (section 5.4).

#### 2.4 Recommendation: read the adapted JSON, not the Caddyfile

Recommend `rdock migrate caddy <caddy.json>` reading Caddy's JSON (the output of `caddy adapt --config Caddyfile`, or `GET /config/` from a running Caddy's admin API), documented as:

```sh
caddy adapt --config Caddyfile | rdock migrate caddy - -o conf.d/site.yaml
```

Reasons:

1. **Caddyfile meaning lives in Caddy's adapter, not in its syntax.** Directive sorting into the default order, sorting of same-named directives by matcher specificity, `order` overrides, snippets and `import` with arguments, `{$VAR}` substitution before parsing, and what a site address implies (automatic HTTPS, redirect server, host matcher) would all have to be re-implemented and kept in step with each Caddy release. Parsing is the easy part (crates exist: `caddyfile-rs` 0.1.0, MIT, 2026-02-10; `caddyfile` 0.1.1, Apache-2.0, 2023-08-18; https://crates.io/crates/caddyfile-rs, https://crates.io/crates/caddyfile); adapting is not.
2. **JSON is explicit.** Routes are an ordered list with matchers and handlers, which maps onto routes with computed priorities.
3. **It covers every Caddy user**: Caddyfile, JSON, API-driven and other adapters.
4. **Version drift is observable**: JSON fixtures in the repository are produced by a pinned Caddy image, and a weekly job regenerates them with the newest image and diffs.
5. Caddy users have the `caddy` binary by definition.

Costs, and how to handle them:

- **Sugar is expanded.** `forward_auth`, `handle_path`, `redir`, `php_fastcgi`, `try_files` and `basic_auth` appear in JSON as generic handlers (`forward_auth` as a `reverse_proxy` with a response handler). The translator needs shape recognisers for the common ones, each pinned by a fixture adapted from a one-line Caddyfile; an unrecognised `reverse_proxy` with `handle_response` is a "not translated" finding.
- **No source lines.** Findings point at a JSON pointer (`/apps/http/servers/srv0/routes/3/handle/0`) plus the host and path matchers of the enclosing route, which is what a user recognises.
- **Names.** JSON routes are anonymous; generate names from host and path (`app-example-com`, `app-example-com-api`), de-duplicated.
- **Secrets.** `{$VAR}` values are already substituted in adapted JSON, so secrets can be inline. The tool must never echo values of known secret fields in findings, and the guide must say so. Runtime placeholders (`{env.X}`, `{http.request.*}`) remain and are findings unless they match a known pattern (`{http.request.uri}` in a redirect).
- **Do not run `caddy` from `rdock`** by default: it would execute a binary found on `PATH` with the user's file. An opt-in `--adapt-with <path-to-caddy>` can be added later.

Diagnostics for what cannot be translated (shared report, section 5.2), with fixed codes so the guide can link to them:

| Code | When | Text pattern |
|---|---|---|
| `caddy.handler.unsupported` | handler module with no equivalent (`templates`, `map`, `vars`, `push`, `acme_server`, `intercept`, FastCGI transport) | "`<handler>` has no equivalent; the route is written without it" or, when the handler answers the request, "the route is left out" |
| `caddy.matcher.unsupported` | `expression`, `file`, `vars`, `vars_regexp`, `protocol`, `tls`, `url_pattern`, `remote_ip` when different from client IP | "matcher `<m>` cannot be expressed; route left out" (never widen a match silently) |
| `caddy.matcher.case` | every `path` matcher | "Caddy matches paths case-insensitively; the migrated route is case-sensitive" (info), or emit `PathRegexp` with `(?i)` behind a flag |
| `caddy.placeholder` | a placeholder in a value | "placeholder `{…}` is not evaluated" |
| `caddy.default.changed` | a Caddy default that differs | e.g. "`lb_policy` was Caddy's default `random`; written explicitly", "Host header: Caddy 2.11 sends the upstream host to HTTPS upstreams; `pass_host_header: false` written" |
| `caddy.tls.manual` | `on_demand`, issuers other than ACME, DNS plugin without adapter, cipher lists | "configure by hand: …" with the target field named |
| `caddy.app.ignored` | apps other than `http`, `tls`, `pki` (e.g. `layer4`, plugins) | "app `<name>` is not migrated" |

#### 3.3 Recommendation: the realistic subset

- **Translate**: the Y and C rows, with each C condition tested by the tool. A C row whose condition fails becomes a "manual" finding and the location is written as a **disabled** route (`enabled: false` exists in `Route`) with the original lines as a comment, so nothing is exposed with the wrong behaviour.
- **Refuse by construct, not by file**: one `if` or `map` must not block the other 20 locations.
- **Never widen silently**: a location that cannot be matched exactly is disabled, not approximated.
- **Compute inheritance in the tool**: `proxy_set_header`, `add_header`, `limit_req` and `limit_conn` all use "inherited only if the current level has none". Resolve the effective set per location before mapping. This is the single largest source of wrong hand migrations.
- **State defaults that change**: body limit (1m → none), TLS verification to backends (off → on), connect timeout (60 s → 5 s), buffering (on → streaming), `limit_req` status (503 → 429), default server behaviour. One "defaults that change" block per report.

Recommendation: **write the parser in `rdock-migrate`**. The NGINX configuration grammar is small: a directive is a name, arguments, then `;` or a `{ … }` block; arguments are bare words or single- or double-quoted strings with backslash escapes; `#` starts a comment outside quotes; `*_by_lua_block { … }` bodies are raw (balanced braces); the `map`, `geo`, `types`, `split_clients` and `charset_map` blocks hold "key value;" lines; `${var}` and `$var` are left as text. Its risks: 0.x with a release train tied to a linter, 1,166 total downloads, one extra crate (`rowan`), an optional `wit-bindgen` feature to keep off, and no stated MSRV. I did not read its source.

The translator, not the parser, is the work: location precedence, `proxy_pass` URI arithmetic and inheritance resolution.

#### 4.2 Lessons (recommendations drawn from the facts)

1. **Behavioural tests, not structural ones**, for anything called "supported". This is the ingress2gateway 1.0 headline and the direct answer to the 1.0 criterion.
2. **A warning in a scrolling log gets missed.** Put the count in the exit summary, offer `--strict` (exit non-zero when anything needs review), and write the findings next to the affected object in the output as well as in the report.
3. **Every finding names its source object and a next step.** Message, source location, target object, suggestion, documentation link.
4. **Stable diagnostic codes** (decK) so CI can allow or forbid specific ones and docs can link to them.
5. **Keep the source's defaults explicit** in the output and tell the user they may remove them, instead of silently adopting the target's defaults.
6. **Do not claim a converter.** Caddy's wording ("adapters, not converters") and ingress2gateway's ("assistant, not a one-shot replacement") set expectations; the unfinished nginx-adapter shows what happens when unsupported directives are only warnings and the result still runs.
7. **Refuse escape hatches by name** (snippets, `if`, Lua), with the rule quoted.
8. **Static plus dynamic.** traefik-migration-tool converted `traefik.toml` and `acme.json` as well as routes; a tool that migrates only routes leaves the user to write listeners and ACME by hand.
9. **A compatibility switch ages badly** (`ruleSyntax`). Prefer a one-time translation with a report over a permanent "Traefik mode" flag.

### 5. Recommended design

#### 5.1 CLI shape

Existing (fact): `rdock migrate traefik <INPUT> [--expose-by-default] [-o, --output <FILE>]`; `-` is standard input; YAML to standard output; one summary line on standard error; exit 0 unless the input is unreadable.

Proposed, keeping every existing flag and default:

```text
rdock migrate traefik <INPUT>... [--expose-by-default] [--static <FILE>] [--env-file <FILE>]
rdock migrate caddy   <INPUT>                      # adapted JSON; `-` for stdin
rdock migrate nginx   <INPUT> [--root <DIR>]       # nginx.conf; includes resolved under --root

common:
  -o, --output <FILE>        rdock.yaml fragment (default: standard output)
      --report <FILE>        findings as JSON (schema/migrate-report.v1.json); `-` = standard error
      --report-format <text|json>   format of the summary on standard error (default text)
      --strict               exit 2 when any finding is `manual` or `dropped`
      --full                 write a complete rdock.yaml (listeners, defaults, acme) where the input has them
      --no-header            leave the `#` note header out of the YAML
```

- `-o` absent means nothing is written to disk, so the default is already a dry run; no `--dry-run` flag is needed. Say so in `--help`.
- Exit codes: 0 translated (findings may exist), 1 input unreadable, 2 `--strict` and review needed. Today's behaviour is codes 0 and 1.
- `--static` (Traefik): a `traefik.yml`, or the Compose file whose Traefik service carries `command:` flags; produces listeners, the entrypoint map, `acme` and provider settings, used with `--full`.
- `--env-file` (Traefik, Compose input): values for `${VAR}`; without it, `.env` next to the Compose file is not read (no surprise file access) and unresolved variables are findings.
- B-CFG-04 in `docs/04-requirements.md` lists `migrate traefik|nginx`; add `caddy` there in the same PR (requirement IDs stay; the text of an open item can be extended).

#### 5.2 Shared report structure

One Rust type in `rdock-migrate`, serialised to JSON with a committed schema, rendered as the YAML comment header (as today) and as text:

```json
{
  "tool": "rdock migrate nginx", "rdock_version": "1.0.0",
  "source": { "kind": "nginx", "files": ["nginx.conf", "conf.d/app.conf"], "checked_against": "nginx 1.30" },
  "summary": { "objects_written": 14, "exact": 31, "approximate": 6, "manual": 3, "dropped": 2, "info": 9 },
  "findings": [
    { "code": "nginx.proxy_pass.uri_in_regex_location",
      "level": "manual",
      "source": { "file": "conf.d/app.conf", "line": 42, "text": "proxy_pass http://app/v2/;" },
      "target": "routes.app-example-com-3",
      "message": "proxy_pass has a URI inside a regular-expression location; NGINX cannot determine the replacement either",
      "suggestion": "write the rewrite explicitly: middlewares.<m> { type: rewrite, regex, replacement }",
      "doc": "https://reversedock.dev/docs/migrate/from-nginx/#proxy-pass-uri" }
  ],
  "defaults_changed": [
    { "what": "request body limit", "source": "1m (client_max_body_size default)", "rdock": "none", "written": "routes.*.max_body: 1m" }
  ]
}
```

Confidence levels (four, fixed):

| Level | Meaning | Effect on output |
|---|---|---|
| `exact` | same behaviour, proven by a differential or golden test | object written |
| `approximate` | written, with a stated difference (e.g. 429 instead of 503, `leasttime` → `least_requests`) | object written; `# REVIEW(code): …` comment above it |
| `manual` | not translated; the user must decide | object written with `enabled: false` where the model allows it, else left out; `# TODO(code): …` with the source lines |
| `dropped` | source setting has no meaning or no equivalent and is left out | nothing written |

Plus `info` for settings that are the built-in behaviour (WebSocket headers, `X-Forwarded-*` lines).

Two invariants, both testable: (1) **every source item is accounted for**: number of source directives/labels/handlers = exact + approximate + manual + dropped + info; (2) **the output validates**: `Config::validate` has no errors (the existing `check` in `rdock-migrate/src/lib.rs` does this for Traefik).

The current Traefik notes (free-text strings in `Migration.notes`) become findings with codes; `Migration.notes` can stay as a rendered view for compatibility.

#### 5.3 Test strategy

| Kind | Traefik | Caddy | NGINX | Runs in |

### 7. Open questions for the maintainer

1. **What does "switches by changing the image name" mean?** A Traefik container is configured through `command:` flags or `TRAEFIK_*` variables that `rdock run` rejects, and Traefik exposes containers by default while ReverseDock does not. Options: (a) reword the criterion to "changes the image and removes Traefik's flags; labels stay" and rely on zero-config mode; (b) make `rdock run` accept a documented subset of Traefik static flags and variables (`--entrypoints.<n>.address`, `--providers.docker.exposedbydefault`, `--certificatesresolvers.<r>.acme.email` …) as a compatibility layer; (c) keep the criterion and provide `rdock migrate traefik --static --full` as the supported path. (b) is the literal reading and the largest commitment (public API, ADR); section 4.2 item 9 argues against a permanent compatibility mode.
2. **Pass threshold for the differential suite**: is "100 % agreement for options marked supported, apart from an allow-list of documented differences" acceptable, and who approves additions to the allow-list?
3. **`exposedByDefault`**: should zero-config mode, or a migration profile, follow Traefik's default (`true`) when only `traefik.*` labels are present? Today a Traefik setup that relied on the default exposes nothing after the switch, safely but surprisingly.
4. **NGINX for 1.0**: tool or guide? F-MGMT-03 marks `migrate nginx` P3; the roadmap's v1.0 scope names the "NGINX directive subset". Is a guide plus an `experimental` tool enough for 1.0?
5. **Own NGINX parser or `nginx-lint-parser`** (MIT, 0.24.0)? The note recommends the former.
6. **Caddy input**: is JSON-only acceptable for 1.0 (documented as `caddy adapt … | rdock migrate caddy -`), or is direct Caddyfile input required?
7. **Target Traefik version**: pin the subset to v3.7 for 1.0 and track v3.8 when it is released, or wait for v3.8 final?
8. **TOML dynamic files**: add a TOML parser dependency, or document "convert to YAML first"?
9. **`acme.json` import**: wanted? Without it a switch re-issues every certificate, which matters for CA rate limits on large hosts. It handles private keys, so it needs its own security review.
10. **Per-router TLS options and `ipStrategy`**: stay "no equivalent" (listener-level TLS policy, one global `trusted_proxies`), or is a model change wanted before the config schema is frozen at 1.0? After 1.0 the stability guarantee makes this harder.
11. **Corpus licensing**: is copying Traefik's MIT-licensed documentation examples into `tests/conformance/` with attribution in `NOTICE` acceptable under the project's Apache-2.0/DCO policy?
12. **Report schema as public API**: should `schema/migrate-report.v1.json` and the finding codes fall under the 1.0 stability guarantee, or be marked unstable for the first release?
13. **Requirement text**: B-CFG-04 lists `migrate traefik|nginx`; may `caddy` be added to that open item, or does it need a new ID?

**(4) Disk full — three layers, cheapest first**

| Layer | How | Root? | What it proves |
|---|---|---|---|
| A. `/dev/full` | Point a file sink (access log file, if configurable to a path) at `/dev/full`; every write returns `ENOSPC` | No | A log sink that cannot write does not block or fail requests |
| B. tmpfs data directory, binary on the host | `sudo -n mount -t tmpfs -o size=2m,mode=0700,uid=$(id -u) tmpfs <dir>`; `RDOCK_DATA_DIR=<dir>`; fill with a ballast file (`fallocate`/`dd`) until `ENOSPC`; unmount in `Drop` | Yes: passwordless `sudo` on hosted runners (above). Skip with a message when `sudo -n true` fails | The real `ENOSPC` on every writer of the data directory |
| C. tmpfs in Docker, the real image | `docker run --read-only --cap-drop ALL --tmpfs /var/lib/rdock:size=2m,uid=…,mode=0700 rdock:ci …` in the `docker` job, next to the existing read-only smoke test | No (Docker group only) | The shipped image behaves the same; no host privileges at all |

Alternatives considered:

- **Loop-mounted quota'd filesystem** (`truncate`, `mkfs.ext4`, `mount -o loop`): needs root like tmpfs and is slower; only worth it if a real filesystem's behaviour matters (ext4 reserved blocks, delayed allocation making `ENOSPC` appear at `fsync`/`close` instead of `write`). tmpfs reports `ENOSPC` at `write`, so it does not exercise "write succeeded, fsync failed". Recommendation: tmpfs in CI; one ext4 loop run before the release as a lab check.
- **`RLIMIT_FSIZE`** (`sh -c 'trap "" XFSZ; ulimit -f N; exec rdock …'`): no root, but the error is `EFBIG`, not `ENOSPC`; the limit is per file, not per directory; and without ignoring `SIGXFSZ` the default action kills the process. Useful only as a fallback where neither `sudo` nor Docker exists.
- **Unprivileged user namespace** (`unshare -Urm` then mount tmpfs): Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor (not verified against the runner image in this session); `sudo` is simpler and documented.
- **FUSE fault-injection filesystems**: more moving parts than tmpfs for no gain here.

Sub-cases for layer B (each with the load helper running):

1. Disk fills while serving: requests keep succeeding; stdout log unaffected.
2. A configuration write through the API while full: answered with a clear `5xx` (`507` or `503`) and a diagnostic, **or** applied in memory with a warning — whichever the design says (open question Q2); never a half-written history or LKG file.
3. An ACME order completes while full: the certificate is not half-written (`meta.json` hash check in `storage.rs`), the old certificate keeps serving, the order is retried after space returns and is not repeated in a tight loop (count orders at `fake_acme`).
4. Audit: `write_failures` rises and is visible (metric or status); after space returns new records append and `rdock audit verify` passes on the files (records lost during the outage are a documented gap, not a broken chain) (Q2).
5. Abuse bans, quota counters, cluster bundle (`state/control/bundle.json`), upgrade spool: a failed persist is logged and counted; in-memory state stays authoritative.
6. Restart while full: rdock starts from what is on disk, or refuses with a clear message; it never truncates an existing file to zero. Run `rdock audit verify` and compare SHA-256 of `acme/certs/**`, LKG and history before and after.
7. Space returns (delete the ballast): the next write succeeds without a restart, within one retry interval.

#### 2.5 Recommendation: methodology for the v1.0 report

**Topology.** Three machines, as HAProxy does: load generator → proxy → backend, on a private network of at least 10 Gbit/s. Never share a host between generator and proxy for published numbers. Before every session measure (a) generator → backend directly, to show the ceiling is well above the proxy's peak (target: ≥ 2× the fastest proxy's peak), and (b) a low-rate reference client straight to the backend for baseline latency. Publish both.

**Proxy sizing.** Pin the proxy to a fixed core set with `taskset`/cpuset (not a CFS quota: the isolation report found quota throttling pauses the whole process and distorts tails). Rungs: 2, 4 and 8 cores. Give each proxy the same cores, the same memory limit, the same file-descriptor limit.

**Load generation.** Open model only for latency. Recommendation: **two generators with different jobs**:

- `oha` (or k6 `constant-arrival-rate`) at fixed rates with latency correction for the latency ladder; cross-check one rung with `wrk2` for HTTP/1.1, because two independent corrected tools agreeing is the best defence against a generator artefact.
- `h2load` for HTTP/2 peak throughput with explicit `-c` and `-m`, reported as throughput only.

Report latency only at rates below the knee (Envoy: "never measure latency at max load"): 25 %, 50 % and 75 % of each proxy's own measured peak, **and** at fixed absolute rates so the proxies can be compared at equal load. Peak = highest rate with < 0.1 % failed and achieved ≥ 99 % of target.

**Duration and repetition.** 30 s warm-up, 120 s measured, 5 repetitions per cell, proxies interleaved (A, B, C, D, E, A, …) so drift hits all equally. Report median and min–max of the repetitions. Run an A/A pair to state the noise floor (`perreq` already does this).

**TLS settings, identical for all five.**

- Protocol: TLS 1.3 only (min = max = 1.3). One extra `tls12` scenario only if wanted.
- Cipher suite: `TLS_AES_128_GCM_SHA256` forced on the **client** side (the generator offers only this one), because not every proxy lets TLS 1.3 suites be configured server-side.
- Key exchange: X25519 only, offered by the client. (This excludes hybrid post-quantum groups on purpose; a separate `X25519MLKEM768` scenario is worth adding only where all five support it — not verified per proxy.)
- Certificate: one ECDSA P-256 leaf and one intermediate, the same files for every proxy; a second run with RSA-2048 because many deployments still use it.
- Session resumption: tickets **on** with each proxy's default lifetime for `tls-resumed`; the client told not to resume for `tls-new`. State what each proxy did (count full and resumed handshakes from each proxy's statistics, as Envoy's FAQ advises).
- OCSP stapling off; no client certificates; ALPN `h2,http/1.1` on the proxy, the client choosing per scenario.
- Record which TLS library each proxy used (rustls + ring; OpenSSL or AWS-LC for NGINX and HAProxy, by image; Go `crypto/tls` for Caddy and Traefik). This is the one difference that cannot be equalised and must be stated.

**Tuning parity rules.**

1. Each proxy runs its **current stable release** (§2.2) from its **official image or package**, with the build stated.
2. Two configurations per proxy, both published: **default** (the shortest configuration that does the job, as today) and **tuned** (what that project's own documentation recommends for throughput). Invite each project's maintainers to review their tuned configuration before publication and record whether they answered (Q7).
3. Same worker count: rdock `runtime` threads = NGINX `worker_processes` = HAProxy `nbthread` = `GOMAXPROCS` for Caddy and Traefik = the pinned cores.
4. Same features on and off for all: access log off, compression off, no retries beyond each proxy's default connect retry (state it), no health checks, no metrics endpoint scraped during the run, admin/API off or idle.
5. Same upstream behaviour: keep-alive to the backend with a pool large enough not to be the limit; HTTP/1.1 to the backend in every scenario unless the scenario says otherwise.
6. Same HTTP/2 limits: `max_concurrent_streams` 100 (or one stated value), same initial stream and connection windows where configurable.
7. Same host tuning for every run, recorded in the report: kernel version, `net.core.somaxconn`, `net.ipv4.tcp_max_syn_backlog`, `net.ipv4.ip_local_port_range`, `net.ipv4.tcp_tw_reuse`, `fs.file-max`/`nofile`, CPU governor `performance`, turbo and SMT state, NIC model, queue count, IRQ affinity, offloads (`ethtool -k`), `irqbalance` stopped. A script applies them and a second script dumps them into the result folder.
8. Host networking for the proxy (`--network host`), not a Docker bridge, on the dedicated machines.

### 3. Independent security review

The criterion: "Independent security review of HTTP parsing, TLS/ACME and the admin surface." The project cannot do this itself. What it can do is make the review cheaper and more useful.

#### 3.1 Facts: how reviews are commissioned

**OSTIF** (Open Source Technology Improvement Fund), https://ostif.org/get-an-audit/:

- Process: optional preparation (OSTIF's best-practices guide, OpenSSF Scorecard, Best Practices badge, documentation, prior reviews) → introduction meeting → questionnaire → OSTIF drafts a request for proposals for the project's approval → OSTIF sends it to its network, collects bids and selects a team on cost and expertise → audit (kickoff, sync meetings, draft report, closing) → remediation, often during the audit → public report after fixes.
- OSTIF scopes, sources and vets the vendor, manages the engagement and "has helped projects raise funds and find sponsors to cover all or part of the costs".
- Cost: "Initial audits typically range from about $30k to $200k", depending on complexity, hours, audit type and prior testing. OSTIF's own reports give data points: a 10-audit programme averaging $74,000 per audit, and one case where scoping took a $143,000 quote to $71,000 (OSTIF impact reports, self-reported; found via search, PDFs not opened).
- Disclosure: 90 days, extendable by 30.
- Contact: the intake form on that page. No formal eligibility rule is stated. Total duration is not stated.

#### 3.3 Recommendation: what to do before an audit

Work the project (and its AI assistants) can do, in order of value per effort:

1. **Standalone threat model** (`docs/security/threat-model.md` or an ADR): assets (private keys, ACME account keys, admin credentials and tokens, API-key hashes, audit log, configuration, backends' trust in `X-Forwarded-*`), actors (internet client, backend, container that can set labels, tenant with Kubernetes RBAC, operator, admin, CA, DNS provider, plugin/agent, cluster member), trust boundaries with a data-flow diagram per surface (data plane, admin, providers, ACME, cluster, plugins), per-boundary threats (STRIDE is enough) mapped to the existing §15 controls and to the tests that prove them, and an explicit **non-goals and known gaps** list. Auditors price on this.
2. **Audit scope document**: commit, crates and line counts per surface, what is upstream (Pingora, h2, rustls, ring, instant-acme) and at which pinned version, feature flags in release builds (so `wasm`, `http3`, `fault-injection`, `alloc-count` are out), how to build and run the e2e suite, test accounts.
3. **Fuzzing gaps** from the table: (a) an HTTP/2 target and an h2→h1 differential; (b) ACME response and storage decoding; (c) response-side HTTP/1 framing and the upgrade sequence; (d) label and Kubernetes translation; (e) schema-driven fuzzing of the admin API against `schema/openapi.json`; (f) persist corpora (cache or a corpus branch) and lengthen the weekly run; consider ClusterFuzzLite (free on GitHub Actions) so Scorecard and auditors see continuous fuzzing. OSS-Fuzz needs acceptance by Google, which looks at project importance — likely premature.
4. **CodeQL** for Rust, JavaScript/TypeScript (dashboard, website) and Go (Terraform provider, clients) plus Actions; keep Semgrep. Make at least one SAST job required once the baseline is clean.
5. **Scorecard workflow** (`ossf/scorecard-action`) publishing to the Security tab, and the **Best Practices badge** self-assessment. OSTIF lists both as preparation.
6. **Reconcile documents with CI**: either add `cargo audit`, Trivy on the image and `actions/dependency-review-action`, or change §15/§06/F-OSS-02 to say what actually runs. An auditor will check claims against workflows.
7. **`cargo-vet`** (or at least `cargo deny` plus a written policy): record which third-party crates were reviewed; import the audit sets published by Mozilla, Google, Bytecode Alliance and others to cover most of the tree cheaply. Moderate ongoing cost; do it only if the maintainer wants the claim "every dependency is audited or exempted with a reason".
8. **Internal review, per surface**, with the checklist below, each item ending in a test name or a written "not applicable because …". File the result next to the threat model; give it to the auditors.
9. **Fix-readiness**: a private fork or security advisory workflow rehearsed once; a release procedure for a security fix; decide the embargo and CVE process (SECURITY.md already promises CVSS v4 and 90 days).

**C. TLS**

- Protocol versions and suites: TLS 1.2 and 1.3 only; no renegotiation, no compression (rustls); default suites documented with a dated source.
- SNI: missing SNI, SNI not matching `Host` (domain fronting policy: allow, or `421`), default-certificate behaviour, wildcard matching rules, IDNA handling.
- ClientHello peek: bounded (16 KiB, 128 extensions), reassembly across records, rewind correctness; fuzzed.
- Session resumption: ticket key generation, rotation, lifetime, sharing "per security class" (a ticket from a listener without client auth must not resume on one that requires it; H-PERF-02) — a high-value review item because it is project code.
- mTLS: chain verification, revocation policy (CRL/OCSP or documented absence), SPIFFE checks, header injection of client-certificate data only after stripping client-supplied copies.
- Upstream TLS: verification on by default, SNI and name checks, `insecure` only explicit and diagnosed.
- Handshake DoS: `tls.max_handshakes` bound (`e2e_sockets.rs`), handshake timeout.
- Private keys: file modes, never logged, zeroisation where practical, behaviour on a certificate/key mismatch.
- TLS-ALPN-01 validation certificates never served to ordinary clients (`issues_through_tls_alpn01_and_hides_validation_certificates`).

**D. ACME**

- Account key: generation, storage mode `0600`, one account per directory URL, never in logs, API answers or exports; key rollover and deactivation.
- CA trust: directory over HTTPS with the system roots; `ca_root` only explicit; redirects; response size and time limits; `Retry-After` honoured; backoff with jitter; staying inside Let's Encrypt limits (§4).
- Challenge handling: HTTP-01 token path traversal and token charset; answer only for known tokens; TLS-ALPN-01 only with the `acme-tls/1` ALPN; DNS-01 hook execution (argument injection through names — names must be validated before reaching `exec`), provider credentials handling and scoping.
- Issuance policy: which names may be requested (labels from containers can ask for arbitrary hostnames — who may cause issuance and at what rate?), on-demand TLS off by default with an `ask` endpoint and rate limits (§15), wildcard rules, IP-address identifiers.
- Storage: atomic writes, `meta.json` hash binding, behaviour on a corrupt store, lock handling, cluster leases and fencing, journalled order resume (key reuse risks), clock dependence in the shared-directory mode.
- Renewal: ARI window handling, replaced-certificate identification, behaviour on revocation, failure alerting before expiry.
- Local CA (`pki/root.pem`): root key protection, name constraints, lifetime, never used for public names.

**E. Admin surface**

- Authentication: no default credentials; password hashing parameters; constant-time comparisons; login rate limits and lockout; TOTP replay protection (`last_step` is in `totp.rs`); session lifetime, rotation at login and privilege change, logout invalidation; OIDC login for the admin (if any) with the same checks as the middleware.
- Authorisation: every endpoint in `schema/openapi.json` mapped to a role (viewer/operator/admin) and a token scope, with a test that enumerates the OpenAPI document and asserts a denial for each lower role (a generated test closes the "new endpoint forgot its check" hole); object-level checks for tokens restricted by address.
- CSRF: cookie-authenticated state changes need a token or a custom header plus `SameSite`; token-authenticated calls exempt; `Origin`/`Sec-Fetch-Site` checks; CORS policy (no wildcard with credentials); WebSocket/SSE endpoints check `Origin`.
- Exposure: default bind (loopback or Unix socket), DNS-rebinding protection (validate `Host`), behaviour when bound to a public address without TLS (refuse or warn loudly), the admin Unix socket's mode and peer checks (`rdock upgrade` is socket-only).
- Dashboard: Content-Security-Policy (the code already avoids inline styles for it), no third-party requests (tested), output encoding of names that come from labels and Kubernetes objects (stored XSS through a container label is the classic route), clickjacking headers.
- Secrets: never returned (`***`), not in history, audit, diagnostics, error messages, the `explain` output, metrics labels, or the events stream; configuration export masks them; `${vault:…}`/env interpolation results not echoed.
- **SSRF**: every place the process makes a request to a configured or user-influenced URL — alert webhooks (`crates/rdock-observability/src/alerts/deliver.rs` mentions private addresses), forward-auth, OIDC discovery and JWKS (refused on private addresses unless allowed, §15), ACME directory, DNS provider APIs, Vault, agents, Cloudflare IP list sync, plugin/module fetch (not implemented). For each: who can set the URL (file, label, Kubernetes object, API role), redirect following, DNS rebinding between check and use, link-local and metadata addresses (169.254.169.254, IPv6 forms, IPv4-mapped), response size and time limits, and whether the response body is reflected to the caller.
- Configuration API: `If-Match` required (tested: 428), validation before apply, size limits, rollback authorisation, rate limits on writes (isolation results), audit of every write.
- Audit log: hash chain coverage (rotation and retention boundaries), what an attacker with file access can do (truncate the tail — detectable only with an external anchor), write-failure behaviour (currently logged and counted, request not failed — a deliberate choice to document).
- Denial of service from the admin side onto the data plane: covered by the isolation test; keep.

**F. Providers and multi-tenancy**

- Docker: read-only API use; label injection (a container setting `rdock.*` labels can claim any hostname, attach middlewares, point at other containers' addresses, request certificates) — document the trust model and the constraints available; socket-proxy guidance.
- Kubernetes: cross-namespace references only with `ReferenceGrant`; Secret access scope in the chart's RBAC; hostname collisions between namespaces; status writes.
- Traefik label compatibility: options that widen access silently.
- Cluster: join-token single use and lifetime, mTLS enrolment, bundle signature or hash verification, revocation, what a compromised data plane can do to others and to the store.

**G. Static files** (`e2e_static.rs` covers much): canonicalised root; `..`, encoded and double-encoded traversal; backslashes; NUL; symlink policy including races between check and open (cap-std is used for the cache; is it for static?); dotfiles; directory listing escapes and HTML encoding of file names; `Range` handling (many ranges, overlapping); content-type sniffing headers; precompressed-file selection; case-insensitive filesystems.

**H. Cross-cutting**: panics reachable from the network (the lint forbids `unwrap`/`expect`/`panic` in library crates; check arithmetic overflow and slicing), unbounded allocations driven by peers, regexes from configuration (the `regex` crate is linear-time; check size limits for compiled programs), timing side channels in comparisons of secrets, log injection (CR/LF in logged request data), integer parsing of durations and sizes, time handling (clock steps), file-descriptor exhaustion behaviour, signal handling during upgrade.

### 4. The 60-second HTTPS criterion

"Fresh VPS, DNS pointed, `docker compose up` → valid HTTPS in under 60 seconds with one label."

#### 4.1 Facts: what exists

`crates/rdock/tests/e2e_acme.rs::a_labelled_container_gets_https_within_a_minute` (needs `RDOCK_ACME_TESTS=1` and `RDOCK_DOCKER_TESTS=1`; both set in the required `rust` job):

- starts Pebble, then a `traefik/whoami:v1.11.0` container with labels `rdock.enable=true`, `rdock.host=vps.example.com`, `rdock.port=80`;
- starts the **host binary** with a configuration holding two listeners, `acme.ca` and `acme.ca_root` pointing at Pebble, and `providers.docker: {}`;
- starts the clock at `Rdock::start`, waits for a certificate chaining to Pebble's root on the TLS port, makes a request, asserts 200 from whoami and **elapsed < 60 s**.

What it proves: discovery → order → HTTP-01 → certificate → serving works end to end inside a minute against a CA on the same machine. What it does not prove, compared with the wording of the criterion:

| Difference | In the test | In the criterion |
|---|---|---|
| CA | Pebble on localhost, started with `PEBBLE_VA_NOSLEEP=1` (no validation delay), no network latency, no multi-vantage validation | A public CA (Let's Encrypt) over the internet, validating from several locations |
| How rdock runs | The binary on the host with an explicit configuration | The published image via `docker compose up`, zero-config |
| "One label" | Three labels (`enable`, `host`, `port`) and a configuration file | One label; whether zero-config makes `rdock.host=…` alone enough is not shown by this test |
| Image pull | Not included (whoami is pulled earlier by other tests or cached) | A fresh VPS pulls both images; whether the 60 s includes pulls is undefined (Q11) |
| DNS | Pebble's test DNS resolves everything to the host | Real DNS, already propagated |
| "Valid" | Chains to Pebble's test root | Chains to a publicly trusted root (or the staging root during rehearsals) |
| Ports | Random high ports | 80 and 443 |

The model has `acme.staging: bool` ("Use the CA's staging environment (untrusted certificates, high rate limits)", `crates/rdock-model/src/acme.rs`), and `deploy/docker/examples/` has `https`, `labels`, `socket-proxy` and `cloudflare-tunnel` examples.

#### 4.2 Facts: Let's Encrypt limits

Production (https://letsencrypt.org/docs/rate-limits/, last updated 2026-08-05):

| Limit | Value | Refill |
|---|---|---|
| New registrations per IP | 10 per 3 hours | 1 per 18 min |
| New registrations per IPv6 /48 | 500 per 3 hours | — |
| New orders per account | 300 per 3 hours | 1 per 36 s |
| New certificates per registered domain | 50 per 7 days | 1 per 202 min |
| New certificates per exact set of identifiers | **5 per 7 days** | 1 per 34 h; no override |
| Authorization failures per identifier per account | 5 per hour | 1 per 12 min |
| Consecutive authorization failures per identifier per account | up to 1,152, then issuance for that identifier is paused | resets on a success |
| Request rates per IP | `new-nonce` 20/s, `new-account` 5/s, `new-order` 300/s, other `/acme/*` 250/s, `/directory` 40/s | `503` with `Retry-After` |

Renewals coordinated through ARI are exempt from all rate limits.

Staging (https://letsencrypt.org/docs/staging-environment/, last updated 2026-04-10): directory `https://acme-staging-v02.api.letsencrypt.org/directory`; new registrations 50 per 3 hours per IP; new orders 1,500 per 3 hours per account; certificates per registered domain 30,000 per second; per exact set 30,000 per week; authorization failures 200 per hour; roots "(STAGING) Pretend Pear X1", "(STAGING) Bogus Broccoli X2" and two others, not in any trust store.

#### 4.3 Recommendation: a definition, then two proofs

**Define the clock** (Q11). Proposal: *t₀* = the moment `docker compose up -d` is invoked on a host that already has Docker and both images pulled, with ports 80/443 reachable and the A/AAAA record already resolving from public resolvers; *t₁* = the first moment an external client completes `GET https://<name>/` with full chain verification and gets the application's 200. Pass: *t₁ − t₀* < 60 s. Report the image-pull time separately, because it depends on the VPS's bandwidth, not on ReverseDock.

**Proof A — CI (deterministic, every pull request).** Strengthen the existing test, or add a sibling in the `docker` job:

1. Use the **image** built in the job and a **compose file** identical to the documented quick start except for the ACME directory (Pebble) — ideally the example in `deploy/docker/examples/https/` with an override file.
2. Exactly the labels the documentation's quick start shows (one, if zero-config allows).
3. Run Pebble **without** `PEBBLE_VA_NOSLEEP` in this one test so validation has its default random delay (the variable's exact default delay range was not re-checked today), and optionally put Toxiproxy with 100 ms latency in front of the directory.
4. Measure from `docker compose up -d` to the first verified 200; record the timeline from the log (container seen, order created, challenge ready, validated, finalised, certificate stored, first handshake).
5. Assert < 60 s; print the phases so a regression shows where the time went.

**Proof B — real world (per release candidate, manual or a dispatch-only workflow).**

Prerequisites (maintainer): a domain or delegated subdomain with an API for records, and a cloud account (Q12).

Procedure, scripted in `scripts/prove-60s/` and published with its output:

1. Create a fresh VPS from a stock image (for example Ubuntu 24.04 with Docker installed by cloud-init). Record provider, plan, region and image.
2. Create `run-<timestamp>.<zone>` → the VPS address with a short TTL (60 s). Use a **new name per run** so stale caches and the "exact set" limit never interfere.
3. Wait until the record resolves from several public resolvers and from the zone's authoritative servers; this wait is outside the clock ("DNS pointed").
4. Copy the documented compose file with the one label set to the name, and `acme.staging: true` (or the equivalent environment variable). `docker compose pull` (timed separately).
5. From a **second machine**, start a probe loop (every 250 ms: TCP connect to 443, TLS handshake verifying against the staging roots, `GET /`).
6. `docker compose up -d` → *t₀*. First verified 200 → *t₁*.
7. Collect: probe log, `rdock` log with timestamps, `docker compose` versions, the certificate (issuer, serial, `notBefore`).
8. Destroy the VPS and the record.
9. Repeat 10 times (different times of day, at least two regions or providers); publish min, median, max and the phase breakdown.
10. **One** final run per release against Let's Encrypt **production** with a fresh name, to show a publicly trusted chain; verify with an unmodified `curl`.

Limits to respect:

- Staging for all repetitions; its limits are far above 10 runs, but a new ACME account is created on every fresh VPS, and staging allows **50 new registrations per 3 hours per IP** — irrelevant with a new IP each run, relevant if runs share a NAT address.
- Production: each run uses a new name under one registered domain → counts against **50 certificates per registered domain per 7 days**; never re-issue the same name (**5 per exact set per 7 days**, no override); a failed validation counts against **5 failures per identifier per hour**. One production run per release stays far inside all of these.
- Each fresh VPS registers a new production account: **10 registrations per IP per 3 hours**.
- Never loop production issuance in CI.
- Certificates from the runs appear in Certificate Transparency logs with the run names; use names that reveal nothing.

Risks to the 60 s that the measurement will show: the CA's multi-vantage validation time, DNS not yet visible to the CA's resolvers (the script's propagation check should query the authoritative servers), the provider's firewall defaults, IPv6-only or IPv4-only reachability when the CA prefers AAAA, and Docker event latency.

Publish the result as a docs page ("Proof: HTTPS in under 60 seconds") with the script, raw logs and date.

#### 5.1 Facts: what exists

- Requirement F-MGMT-05 ("Docs site with interactive config playground (schema-driven)") is still unchecked in `docs/04-requirements.md`. `docs/09-website.md` phase W3 plans "`rdock-config` compiled to WebAssembly for exact diagnostics, after a spike".

#### 5.2 Facts: the WebAssembly route, from the manifests (nothing built)

Dependency tree of the code that would be compiled (`rdock-config` → `rdock-model` → `rdock-rules`, `rdock-credentials`):

| Crate | Direct dependencies | `wasm32-unknown-unknown` |
|---|---|---|
| `rdock-rules` | `ipnet`, `regex`, `thiserror` | Pure Rust; fine |
| `rdock-model` | `ipnet`, `regex`, `schemars` 1.2.3, `serde`, `serde_json`, `thiserror`, `url` 2.5.8, `rdock-rules`, **`rdock-credentials`** | Pure Rust except through `rdock-credentials` |
| `rdock-credentials` | `base64`, `blake2` 0.11, `crc32fast`, **`ring` 0.17.14**, `subtle`, `thiserror` | **The blocker.** ring "currently requires a C (but not C++) toolchain" (https://github.com/briansmith/ring/blob/main/BUILDING.md); its `build.rs` has a wasm32 branch and its manifest has the feature `wasm32_unknown_unknown_js = ["getrandom/js"]` (read in the vendored `ring-0.17.14/Cargo.toml`). | `rdock-config` | `rdock-model`, `serde`, `serde-saphyr` 2.0.0 (features: `deserialize` only), `serde_json`, `serde_path_to_error`, `thiserror` | `serde-saphyr`'s dependencies with that feature set (`granit-parser`, `smallvec`, `num-traits`, `annotate-snippets`, `encoding_rs_io`) are pure Rust per its manifest. `std::fs`/`std::env` are used in `includes.rs`, `state.rs`, `interpolate.rs` and `load_file`; they compile on the target and fail at run time, which is fine if the entry point is `load_str`/`load_str_with` with a no-op `Lookup` |

How `rdock-model` uses `rdock-credentials`: only in `crates/rdock-model/src/validate/gateway.rs` — `API_KEY.prefix`, `API_KEY.is_id(..)` and `is_sha256_hex(..)`, i.e. string-format checks. It does not need ring's digest, RNG or Ed25519 for validation. Splitting those format helpers out (or putting ring behind a feature of `rdock-credentials` that `rdock-model` does not enable) would make the whole validation tree pure Rust and remove the clang requirement. That is a small refactor in two crates; it needs the usual care because `rdock-model` changes require `just schema` (the schema itself should not change).

Other facts that matter: the semantic validator is large (`crates/rdock-model/src/validate.rs` and `validate/*`: 8,473 lines), which is exactly the logic a JSON Schema cannot express (cross-references, rule grammar, unsafe combinations, the "planned for vX.Y" gate). Diagnostics are a `Vec<Diagnostic>`; whether they carry source spans that map back to YAML positions was not checked (it decides how good editor squiggles can be).

Size of a WASM build: **not measured** (no builds allowed). My estimate, from typical figures for `regex` + `serde_json` + a YAML parser + `url`/IDNA tables with `opt-level = "z"`, LTO and `wasm-opt`: 1.5–3 MB raw, 400–900 kB compressed. Treat as a guess until the spike measures it.

#### 5.3 Facts: the JavaScript route

| Library | Version | Licence | Size | Note |
|---|---|---|---|---|
| Ajv | 8.20.0 (npm registry) | MIT | 111,708 bytes minified, **32,805 gzip** (bundlephobia API, `ajv@8.20.0`); 4 small dependencies | Compiles schemas to functions with `new Function` → needs `unsafe-eval` in a Content-Security-Policy, **or** Ajv's standalone mode: generate the validator at build time and ship it as plain code (size then depends on the schema; a 313 kB schema will generate a large module — not measured). Draft 2020-12 through `ajv/dist/2020`. Error objects carry an instance path, not a text position |
| `@cfworker/json-schema` | 4.1.6 | MIT | 23,155 minified, 6,582 gzip, no dependencies | Interpreting validator, no `eval`; drafts 4, 7, 2019-09, 2020-12 |
| `@hyperjump/json-schema` | 1.18.0 | MIT | not measured | Strict, spec-complete |
| `json-schema-library` (already in the bundle through `@valtown/codemirror-json-schema`) | 11.6.16 | MIT | part of the existing 264 kB | Interpreting; also powers completion and hover |

The existing stack already validates in the editor with positions, completion and hover. Adding Ajv would validate the same schema a second time and give nothing the page lacks; its error positions would have to be mapped back to YAML nodes by hand.

#### 5.4 Recommendation

**Keep the existing CodeMirror + JSON Schema playground as the base, do not add Ajv, and add exact diagnostics from Rust compiled to WebAssembly as a lazily loaded second layer** — after the spike that `docs/09-website.md` already calls for. Order:

1. **Spike (1–2 days of work, no user-visible change):** split the ring-free format helpers so `rdock-model` builds for `wasm32-unknown-unknown` without clang; add a tiny crate (for example `crates/rdock-playground-wasm`, `publish = false`, outside the default workspace members like the fuzz workspace so it never touches the required checks) exposing one function `validate(text) -> JSON diagnostics` on `load_str_with` + `validate()`; build with `wasm-bindgen`; measure raw and compressed size and cold-start time; check whether diagnostics have positions. Decision gate: compressed size ≤ about 1 MB and diagnostics that can be placed in the editor (by span, or by JSON-pointer path mapped through the `yaml` document, which the page already parses).
2. **If the gate passes:** load the module only after the first edit or on a "Full check" button, in a Web Worker, as a CodeMirror `linter` source next to the schema linter; keep the page working without it (the schema layer is the fallback and the no-JS note stays). Extend `check-playground.ts`: the WASM diagnostics for a dangling service reference and a bad rule appear; still no off-origin requests. CSP: WebAssembly needs `'wasm-unsafe-eval'` in `script-src` — a deliberate, narrow addition to decide (Q13).
3. **If the gate fails:** stay schema-only, tick F-MGMT-05 as "schema-driven" (which is literally what the requirement and the vision line say), and close the smaller gaps in JavaScript only where cheap (for example a `Host(...)` rule syntax check is not cheap; do not re-implement the rule grammar in TypeScript).

Trade-offs:

| | Schema only (today) | + Ajv | + WASM validator |
|---|---|---|---|
| Finds unknown fields, types, enums | Yes | Yes (duplicate) | Yes |
| Finds dangling references, bad rules, unsafe combinations, "planned for vX.Y" | No | No | **Yes — the same answers as `rdock validate`** |
| Download on the playground page | 264 kB gzip | + 33 kB, or a generated validator of unknown size | + an estimated 0.4–0.9 MB, lazy |
| Drift from the real validator | The schema is generated from the model and checked in CI, so types cannot drift; semantics are simply absent | Same | None: it is the same code. The WASM build must be rebuilt per release and the site must state which version it validates against |
| Build and CI cost | None new | Small | A wasm target in the website job (toolchain target, `wasm-bindgen-cli`, `wasm-opt`), pinned and cached; one more thing that can break the website build; MSRV and the pinned toolchain apply |
| Maintenance | None | A second validator to keep configured like the first | The crate split must be kept (a lint or a CI check that `rdock-model` has no `ring` in its tree for the wasm target: `cargo tree --target wasm32-unknown-unknown -i ring`) |
| Security posture | No `eval` | `unsafe-eval` or standalone code generation | `wasm-unsafe-eval` |
| Privacy promise ("nothing leaves the page") | Kept and tested | Kept | Kept; add to the test |

Why not Ajv: it does not close the gap users hit (semantics), it duplicates what `json-schema-library` already does with editor integration, and its default mode conflicts with a strict CSP. It would only be the right choice if the page did not already have a schema-aware editor.

One more low-cost improvement that needs no decision: the page could link each schema diagnostic to the configuration reference anchor for that field (the reference is generated from the same schema).

# v0.6 research: Swarm, L4, static

Research note for milestone **v0.6 "Swarm, L4, static"**. Requirements in scope: W-SWM-01…03, M-L4-01…03, F-WEB-01, W-DNS-03, the Traefik `tcp.*` label subset, and the performance plan of [#181](https://github.com/Docker-Hunterpedia/ReverseDock/issues/181) (H-PERF-01, H-PERF-06). Every fact was checked on 2026-11-06 against the source linked next to it; crate facts against crates.io, docs.rs and the sources of the versions locked in `Cargo.lock`. Lines marked *(our reasoning)* are conclusions, not sources. Sections 2 to 8 were researched one topic at a time and read together for section 9.

## 1. Where we start

- The config model is ahead of the engine: `Listener.protocol: tcp`, `proxy_protocol`, `TcpRoute`, `TcpService`, `SwarmProvider` and the `HostSNI`/`HostSNIRegexp`/`ClientIP`/`ALPN` rule terms all exist and parse; `rdock run` refuses them with "planned for v0.6" (`crates/rdock-proxy/src/gate.rs`), and the Docker provider rejects `traefik.tcp.*` the same way. v0.6 is mostly engine work behind a model that is already documented.
- Our own accept loop per listener ([ADR-0012](../decisions/0012-own-listeners-pingora-http-engine.md)) is the shape every v0.6 data-plane feature builds on: PROXY protocol parsing, the ClientHello peek, TLS termination for TCP and the per-core runtime experiment all sit in `listener.rs::serve()` before Pingora sees a connection.
- The Docker provider's label translator is pure and tested by the conformance suite; the Swarm provider reuses it and adds only an API loop. `rdock-provider-swarm` is a skeleton today.
- Static serving has a working ancestor in the dashboard's rust-embed server (`rdock-admin/src/dashboard.rs`: strong ETags, conditionals, `.br`/`.gz` sidecars, SPA fallback) and a `compress` middleware that already refuses to compress twice; what is new is the file system and streaming replies.
- DNS-01 has the `DnsSolver` trait, propagation polling and a Cloudflare adapter with an in-process fake API; the seven new adapters are REST clients behind the same trait.
- Performance: one multi-thread tokio runtime, one accept task per listener, one shared upstream pool; 2 to 2.6 futex calls per request ([#176](https://github.com/Docker-Hunterpedia/ReverseDock/issues/176)); the release build has no frame pointers, so profiling needs a build profile first.

## 2. Swarm provider (W-SWM-01…03)

Every fact was checked on 2026-11-06 against the source linked next to it. Lines marked *(our reasoning)* are conclusions, not sources.

### Where we start

- `rdock-provider-docker` (2,420 lines) has two halves (ADR-0018): `watch.rs` (397 lines) talks to the Engine API through bollard 0.21.1 (`default-features = false, features = ["http", "pipe"]`, released 2026-08-16, still the latest; [crates.io](https://crates.io/crates/bollard)); `labels.rs` (585 lines) with `native.rs`, `traefik.rs` and `tree.rs` is the pure translator `translate(&[Container], &DockerProvider) -> Translation { fragment, diagnostics }` that the conformance suite (`tests/conformance/traefik-labels`) and `rdock migrate traefik` also drive.
- The loop subscribes to `container` and `network` events before listing, re-lists on each event (coalesced over 100 ms), reconciles every 60 s, keeps the last snapshot when the socket is lost and reconnects with backoff 1–30 s. A `kill`/`stop`/`pause` event marks the container `stopping` so it leaves its pool before it exits (W-DKR-06).
- The translator's input is `Container { name, labels, networks: BTreeMap<String, Option<IpAddr>>, host_network, exposed_ports, health, stopping, dns_name }`. Address selection: `rdock.network` / `traefik.docker.network` label, else `providers.docker.network`, else the container's only network, else a diagnostic; port: label, else the single exposed port, else a diagnostic listing the ports. Unhealthy containers leave the pool unless none is healthy (fail open).
- `rdock-provider-swarm` is a skeleton (`Cargo.toml`, README, `lib.rs`). The model already has `SwarmProvider { endpoint, expose_by_default, network, traefik_labels, endpoint_mode }` with `SwarmEndpointMode::{Vip (default), Tasks}` (`crates/rdock-model/src/providers.rs`), the website reference documents `providers.swarm` as planned for v0.6, and architecture §12 and ADR-0009 fix the merge priority `file > api > kubernetes > swarm > docker`.
- *(our reasoning)* Swarm reuses the translator unchanged: a running task becomes a `Container` (name `service.slot`, labels from the service, networks from the task), so native and Traefik labels, diagnostics and the conformance fixtures carry over. What is new is the API loop and where labels and addresses come from.

### 2. Endpoint modes and Traefik v3

- Traefik v3 split the Docker provider "into 2 providers": Docker ("without Swarm support") and Swarm; v2's `providers.docker.swarmMode` "would prevent Traefik to start" ([v2→v3 details](https://doc.traefik.io/traefik/migrate/v2-to-v3-details/)).
- Traefik's Swarm provider **polls**: `SetDefaults` sets `RefreshSeconds = 15 s`; the ticker runs when `Watch` is true; the file never opens the event stream; the only explanation is the comment `// TODO: This need to be change. Linked to Swarm events docker/docker#23827` ([pswarm.go](https://github.com/traefik/traefik/blob/master/pkg/provider/docker/pswarm.go)). The reference says `refreshSeconds` "Defines the polling interval for Swarm Mode" and `watch` (default `true`) "watch Docker events" ([provider reference](https://doc.traefik.io/traefik/reference/install-configuration/providers/swarm/)).
- Each tick: `ServiceList`, `NetworkList` (filter `scope=swarm`), then per service `TaskList` with filters `service=<id>` and `desired-state=running`; a task is kept only if `Status.State == running` and it has at least one network attachment; the task is named `<service>.<slot>` (global services: `<service>.<taskID>`); `NodeInspect` per task supplies the node IP; labels come from `service.Spec.Annotations.Labels` (JSON `Spec.Labels`); addresses from `task.NetworksAttachments` keyed by network name, with the comment "Not sure about this next loop - when would a task have multiple IP's for the same network?" (pswarm.go).
- `traefik.swarm.lbswarm=true` routes to `service.Endpoint.VirtualIPs`: "Traefik will not perform any kind of load balancing and will delegate this task to swarm"; a `dnsrr` service in this mode logs "Ignored … endpoint-mode not supported" and is dropped (pswarm.go, [routing reference](https://doc.traefik.io/traefik/reference/routing-configuration/other-providers/swarm/)). *(our reasoning)* With one VIP backend, per-task health checks, sticky cookies, weights and retries to another backend have nothing to act on; Swarm's IPVS balances per connection, so an HTTP/1.1 keep-alive pool pins to one task.
- Labels: `extractSwarmLabels` decodes the prefixes `traefik.enable`, `traefik.docker.` and `traefik.swarm.`; both prefixes together are an error ("both Docker and Swarm labels are defined"); `traefik.docker.*` under Swarm logs "deprecated. Please use traefik.swarm.* labels instead". The Swarm-specific keys are `traefik.swarm.network` and `traefik.swarm.lbswarm` ([shared_labels.go](https://github.com/traefik/traefik/blob/master/pkg/provider/docker/shared_labels.go)).
- "Docker Swarm does not provide any port detection information to Traefik", so `traefik.http.services.<s>.loadbalancer.server.port` is mandatory; "Traefik uses labels found on services, not on individual containers"; `exposedByDefault` is `true`; `allowEmptyServices` (default `false`) keeps a server-less load balancer for unhealthy services; `useBindPortIP` (default `false`) uses the host binding instead of the task IP (provider and routing references above).
- Rolling updates: `stop-first` (default) stops the old task before the new one starts; `start-first` "new task is started first, and the running tasks briefly overlap" ([Compose deploy](https://docs.docker.com/reference/compose-file/deploy/)). *(our reasoning)* In `tasks` mode a stopping task shows `DesiredState: shutdown` while `Status.State` is still `running`: that is the drain signal, the equivalent of the Docker provider's `kill` event. In `vip` mode Swarm removes the task from the VIP itself; we see nothing.

### 3. Overlay networks

- "Docker hosts must be part of a swarm to use overlay networks, even when connecting standalone containers."; `--attachable` "enables both standalone containers and Swarm services to connect to the overlay network. Without `--attachable`, only Swarm services can connect"; "Services or containers can be connected to more than one network at a time."; ports 2377/tcp, 7946/tcp+udp, 4789/udp; `--opt encrypted` "imposes a non-negligible performance penalty" ([overlay driver](https://docs.docker.com/engine/network/drivers/overlay/)).
- `ingress` "is created automatically when you initialize or join a swarm"; services without `--network` connect to it; published ports hand requests to IPVS; "Swarm services connected to the same overlay network effectively expose all ports to each other."; `tasks.<service>` DNS returns "a list of all task IP addresses for that service, one per running replica" ([swarm networking](https://docs.docker.com/engine/swarm/networking/)).
- "You can't use `--endpoint-mode dnsrr` together with `--publish mode=ingress`" ([routing mesh](https://docs.docker.com/engine/swarm/ingress/)).
- Traefik picks the network from `traefik.swarm.network`, else `providers.swarm.network`, "otherwise it will randomly pick one (depending on how docker is returning them)" ([routing reference](https://doc.traefik.io/traefik/reference/routing-configuration/other-providers/swarm/)). Its reference setup attaches the proxy to an `overlay` network with `attachable: true` and names it in `--providers.swarm.network` ([Swarm setup](https://doc.traefik.io/traefik/setup/swarm/)).
- *(our reasoning)* A task on several networks has one address per network; only an address on a network the proxy is also attached to is reachable, and the `ingress` address (`10.255.x`) never is, because the proxy cannot join `ingress` by choice. The proxy can learn its own networks by inspecting its own container (Docker's default hostname is the container's short ID unless `hostname:` is set; to verify against the `docker run` reference, which only says "Container host name"), so the rule becomes: label, else provider setting, else the single network shared by proxy and task, else the Docker provider's "several networks; choose one" diagnostic. Never random.

### 4. Secrets and configs

- Secrets mount at `/run/secrets/<secret_name>` "in an in-memory filesystem", stored in the encrypted Raft log and sent only to managers and to nodes running tasks that use them; up to 500 KB; "After you create a secret, you cannot update it."; "You cannot remove a secret that a running service is using." Rotation: create `<name>_v2`, then `docker service update --secret-rm <old> --secret-add source=<new>,target=<same file>` ([secrets](https://docs.docker.com/engine/swarm/secrets/)). Long syntax: `source=`, `target=`, `uid=`, `gid=`, `mode=`; Compose default mode `0444` ([service create](https://docs.docker.com/reference/cli/docker/service/create/), [Compose services](https://docs.docker.com/reference/compose-file/services/)).
- Configs mount at `/<config-name>` by default, are "not encrypted at rest and are mounted directly into the container's filesystem without the use of RAM disks", also 500 KB, immutable, rotated the same way (`--config-rm`/`--config-add`). Docker's nginx example keeps the TLS key and certificate as secrets and `site.conf` as a config ([configs](https://docs.docker.com/engine/swarm/configs/)).
- *(our reasoning)* Nothing new to build: `rdock.yaml` can be a Swarm config and reference `/run/secrets/*` through `${file:…}` and `tls.certificates[].cert/key` paths, exactly as today. Because secrets and configs are immutable, every rotation is a service update that replaces the task, so no in-place reload path is needed; the docs page shows the pattern (`rdock.yaml` as config, certificates, tokens and DNS credentials as secrets, `0400`). ADR-0009 rule 7 stays: no secrets in labels.

### 5. Global mode and shared state

- Global mode "Ensures exactly one task continuously runs per physical node until stopped." and "Every time a new node becomes available, the scheduler places a task for the global service on the new node." ([Compose deploy](https://docs.docker.com/reference/compose-file/deploy/), [deploy services](https://docs.docker.com/engine/swarm/services/)).
- Host-mode publishing: "If a node has no task, the service does not listen on that port"; with several tasks per node "you cannot specify a static target port", so use "a global service rather than a replicated one" ([routing mesh](https://docs.docker.com/engine/swarm/ingress/)). Traefik Enterprise's Swarm guide: "When using host mode, the real client ip address is shown on request headers", "the host mode will determine that only one container of a service can run on each docker node", and it recommends "set the service deploy mode to global" with a placement constraint ([Traefik Enterprise](https://doc.traefik.io/traefik-enterprise/installing/customizing/swarm/)). Traefik's open-source setup publishes 80/443 with `mode: host`, one replica constrained to `node.role == manager`, and says of ACME storage: "Ensure the `/letsencrypt` path is on a shared volume or NFS so all nodes can read certificates." ([Swarm setup](https://doc.traefik.io/traefik/setup/swarm/)). Traefik's ACME page: "it is not possible to run multiple instances of Traefik 2.0 with Let's Encrypt enabled" because challenges cannot be routed to the right instance; distributed ACME is a Traefik Enterprise feature ([ACME](https://doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/)).
- Let's Encrypt: 10 new accounts per IP per 3 hours; 300 new orders per account per 3 hours; 50 certificates per registered domain per week; **5 certificates per exact set of identifiers per week, counted across all accounts**; 5 failed authorizations per identifier per account per hour ([rate limits](https://letsencrypt.org/docs/rate-limits/)).
- *(our reasoning)* In v0.6 replicas share nothing (the cluster control plane is v0.9). N independent replicas each with ACME would issue N duplicate certificates per name: three nodes use three of the five weekly duplicates, and one redeploy that loses the volumes breaks the limit. Through the routing mesh an HTTP-01 challenge can land on a replica that did not order it. v0.6 therefore documents two supported shapes: (a) one ACME-enabled replica (`replicas: 1`, placement constraint, host-mode ports, DNS pointed at that node or an external balancer in front) and (b) global mode with certificates supplied as Swarm secrets or via DNS-01 on exactly one replica; `rdock validate` warns when ACME is on and `providers.swarm` is set without a note that the data dir is per node. Admin users and tokens are also per replica until v0.9. A shared NFS data dir is refused, not supported: two ACME managers writing one account and one store is a race we cannot make safe.

- Swarm methods exist: `list_services(Option<ListServicesOptions { filters, status }>)`, `inspect_service`, `list_tasks(Option<ListTasksOptions { filters }>)`, `inspect_task`, `list_nodes`, `inspect_node`, `list_secrets`, `list_configs`, `inspect_swarm`, `events`, `list_networks` ([Docker](https://docs.rs/bollard/0.21.1/bollard/struct.Docker.html), [ListServicesOptions](https://docs.rs/bollard/0.21.1/bollard/query_parameters/struct.ListServicesOptions.html), [ListTasksOptions](https://docs.rs/bollard/0.21.1/bollard/query_parameters/struct.ListTasksOptions.html)).
- Models cover `Service { spec, endpoint, update_status, service_status }`, `ServiceEndpoint { spec, ports, virtual_i_ps: Vec<{ network_id, addr }> }`, `EndpointSpecModeEnum::{VIP, DNSRR}`, `ServiceSpec { labels, task_template, mode, update_config { order: STOP_FIRST | START_FIRST }, networks, endpoint_spec }`, `Task { id, name, labels, spec, service_id, slot, node_id, status { state, message, container_status { container_id, pid, exit_code } }, desired_state }`, `TaskState` ([Service](https://docs.rs/bollard/0.21.1/bollard/models/struct.Service.html), [Task](https://docs.rs/bollard/0.21.1/bollard/models/struct.Task.html), [bollard-stubs source](https://docs.rs/crate/bollard-stubs/latest/source/src/models.rs)).
- **`Task.networks_attachments` is missing**: bollard-stubs has no `NetworksAttachments` field or `NetworkAttachment` type (0 matches in `models.rs`), because moby's swagger declared it only in examples until [moby/moby#53082](https://github.com/moby/moby/pull/53082) (merged 2026-07-24, in `v1.53.yaml` from docker-v29.7.0). [bollard#767](https://github.com/fussybeaver/bollard/issues/767) (opened 2026-08-09, open): the maintainer agreed to bump; the regenerated spec (docker-v29.7.2) is additive for `Task` but makes `SwarmJoinRequest` fields required, so the fix "can just ride the next minor" (comment 2026-10-12). No 0.22 release yet.
- *(our reasoning)* `tasks` mode is impossible on bollard 0.21.1 as published. Options: wait for 0.22; `[patch.crates-io]` a regenerated bollard-stubs (a fork to maintain); or fetch `/tasks` ourselves. The workspace already has hyper 1.12, hyper-util 0.1.21 and hyperlocal 0.9.1 (bollard's own unix-socket transport), so a 150-line `api` module with serde structs holding only the fields we read (`ID`, `ServiceID`, `Slot`, `NodeID`, `DesiredState`, `Status.State`, `NetworksAttachments[].Network.{ID,Spec.Name}`, `NetworksAttachments[].Addresses`) costs little, survives spec drift, and keeps bollard for events and for the Docker provider. Recommended; revisit when bollard 0.22 ships.

### 7. Testing

- Hosted `ubuntu-latest` runners have 4 vCPU, 16 GB RAM, 14 GB SSD ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)); the Ubuntu 24.04 image ships Docker Server 28.0.4 (API 1.48), Compose 2.38.2 ([Ubuntu2404-Readme](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md)). Only `ubuntu-slim` "runs in unprivileged mode" and cannot run Docker-in-Docker (runners page). `docker:dind` requires `--privileged` and generates TLS certificates by default (port 2376) ([docker image](https://hub.docker.com/_/docker)). The CI `rust` job already runs the Docker provider's end-to-end test against the runner's daemon (`.github/workflows/ci.yml`).
- moby tests multi-node Swarm with several `dockerd` processes on one host: `internal/testutil/daemon/swarm.go` starts nodes (`StartNodeWithBusybox`), `SwarmInit`/`SwarmJoin` on `DefaultSwarmPort = 2477` ([swarm.go](https://github.com/moby/moby/blob/master/internal/testutil/daemon/swarm.go)).
- Traefik unit-tests its Swarm provider with fake clients (`fakeServicesClient`, `fakeTasksClient` implementing `ServiceList`, `TaskList`, `NodeInspect`, `NetworkList`; [pswarm_mock_test.go](https://github.com/traefik/traefik/blob/master/pkg/provider/docker/pswarm_mock_test.go)); its integration suite `integration/docker_test.go` has no Swarm test (only a comment mentioning swarm boot time; [docker_test.go](https://github.com/traefik/traefik/blob/master/integration/docker_test.go)).
- *(our reasoning)* Three layers: (1) pure tests and fixtures: recorded `/services` and `/tasks` JSON (including a `dnsrr` service, a job service, a task in `shutdown` with `running` state, a multi-network task) drive the translator, no daemon; (2) single-node `docker swarm init` on the PR runner: labels, scale 1→3→1, `start-first` and `stop-first` updates with a request loop asserting no 5xx, secret rotation, provider degraded when the socket proxy drops; (3) a weekly 3-node job: three `docker:dind --privileged` containers on one runner joined over a bridge network, the proxy as a global service with host-mode ports, which exercises overlay/VXLAN across daemons but not real NICs or MTU; the real multi-host run happens on the Hetzner test server before the release. The roadmap's "3-node Swarm e2e" is (3) plus the Hetzner run.

### Recommendation *(our reasoning)*

Default `endpoint_mode: tasks` and change the model's current `Vip` default before it ships: `tasks` is the only mode where we see health, drain on `DesiredState: shutdown`, keep sticky sessions and retries meaningful, and reach the roadmap's "rolling update without 5xx"; `vip` stays as the opt-in for people who want Swarm's balancer, with a diagnostic that disables active health checks and sticky cookies for that service and a diagnostic (not a drop) for `dnsrr` services. Update: subscribe to `service`, `node`, `network`, `secret` and `config` events for immediate re-lists, and poll `/services` + `/tasks?filters={"desired-state":["running"]}` every `poll_interval` (default 5 s, floor 1 s) because tasks emit no events; the Docker provider's coalescing, 60 s reconcile and backoff carry over. Network: label `rdock.network` / `traefik.swarm.network`, then `providers.swarm.network`, then the one network shared by the proxy's own container and the task, excluding `ingress`; otherwise the existing "choose one" diagnostic. Labels: `Spec.Labels` only, `traefik.swarm.*` and the deprecated `traefik.docker.*` both accepted with a warning for the latter, job-mode services skipped with a diagnostic. Fetch `/tasks` with our own serde structs over hyper/hyperlocal until bollard 0.22 adds `networks_attachments`. Out of scope for v0.6: shared ACME and admin state across replicas (v0.9), `useBindPortIP`-style host bindings, Windows nodes, hot reload of Swarm configs (immutable by design), and Swarm-API `POST` calls of any kind. An ADR is needed (config model: default change and `poll_interval`; new provider; label grammar `traefik.swarm.*`).

Open questions *(our reasoning)*:
- Poll lag versus `stop-grace-period` (10 s default): a 5 s poll removes a stopping task 0–5 s after Swarm marks it; is that enough for "no 5xx" with `stop-first`, or do the docs require `start-first` for zero-downtime updates?
- Whether to ask the bollard maintainer for a 0.22 date before writing our own `/tasks` client, and whether the Docker provider should also move to the same thin client later.
- Whether v0.6 should refuse `acme` with `providers.swarm` and more than one replica, or only warn: refusing is safer; warning keeps single-node Swarm users unblocked.

### 1. Where we start

- The config model already has everything but the engine: `Listener.protocol: tcp` and `Listener.proxy_protocol: ProxyProtocolIn { trusted: Vec<IpNetwork> }` (`crates/rdock-model/src/config.rs:145-166, 280-283`); `TcpRoute { match, listeners, priority, service, tls: TcpRouteTls { passthrough } }` (`route.rs:243-267`); `TcpService { backends, proxy_protocol: Option<V1|V2> }` (`service.rs:415-432`). `rdock run` refuses all of them with "planned for v0.6" (`crates/rdock-proxy/src/gate.rs:38-58`), and the Docker provider rejects every `traefik.tcp.*`/`traefik.udp.*` key the same way (`labels/traefik.rs:25`, fixture `tests/conformance/traefik-labels/tcp-router.yaml`).
- The rule grammar already parses `HostSNI` (exact, `*.example.com`, `*`), `HostSNIRegexp`, `ClientIP` and `ALPN` (`crates/rdock-rules/src/ast.rs:60-67, 171-180`); only evaluation against a TCP connection is missing.
- Listeners are ours ([ADR-0012](../decisions/0012-own-listeners-pingora-http-engine.md)): one `accept_loop` per listener with `ArcSwap<Settings { tls: Option<Arc<Acceptor>>, timeouts }>` swapped on reload, a `JoinSet` of connections, stop-and-drain bounded by `lifecycle.drain_timeout` (default 8 s, `settings.rs:592-598`) (`crates/rdock-proxy/src/listener.rs:178-305`). `serve()` sets `TCP_NODELAY`, wraps the socket in Pingora's `L4Stream`, attaches a `SocketDigest`, runs `acceptor.tls_handshake(l4)` under the header timeout, and for cleartext reads the first bytes and `rewind`s them to detect h2c (`listener.rs:306-366`). This is exactly the shape an L4 listener needs: the TLS branch becomes "terminate, then relay", the cleartext branch becomes "peek, then relay".
- `acceptor()` builds a Pingora rustls `Acceptor` from a `ListenerTls` policy plus the shared `SniResolver` (`listener.rs:116`; `rdock-tls::policy::server_config`), so a `tcp` listener with `tls` gets per-listener versions, ciphers and SNI certificate selection for free ([architecture §12](../05-architecture.md)).
- Health: `HealthMode::Tcp` (`rdock-model/src/service.rs:152-160`) probes with a connect-and-drop (`rdock-proxy/src/health.rs:106-147`); M-L4-05 is done. `rdock-limits::ConcurrencyLimiter::new(amount, queue, queue_timeout, max_keys)` exists (`concurrency.rs:35-48`). The real-client-IP algorithm is specified over `trusted_proxies` (`TrustedProxy`, `values.rs:572`; [architecture §9](../05-architecture.md)).
- [Architecture §17](../05-architecture.md) still says TCP routes "implement `ServerApp` under `services::listening::Service`"; ADR-0012 superseded that for HTTP, and the same reasons apply here (per-listener TLS, live add/remove, bind errors before publish). The ADR for v0.6 should update §17.

### 3. SNI passthrough: peeking the ClientHello

What has to be parsed ([RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html), [RFC 6066](https://www.rfc-editor.org/rfc/rfc6066.html#section-3)):
- Record (§5.1): `TLSPlaintext { ContentType type; ProtocolVersion legacy_record_version; uint16 length; opaque fragment[length] }`; `handshake(22)`; "The length MUST NOT exceed 2^14 bytes".
- `legacy_record_version` "MUST be set to 0x0303… other than an initial ClientHello where it MAY also be 0x0301" (§5.1), so the first bytes are `16 03 01` or `16 03 03`.
- "Handshake messages MAY be coalesced into a single TLSPlaintext record or fragmented across several records" (§5.1): a parser must reassemble type-22 records until the handshake length is satisfied.
- Handshake header (§4): `HandshakeType msg_type` (`client_hello(1)`), `uint24 length`. ClientHello (§4.1.2): `legacy_version = 0x0303`, random(32), legacy_session_id<0..32>, cipher_suites<2..2^16-2>, legacy_compression_methods<1..2^8-1>, extensions<8..2^16-1>.
- SNI (RFC 6066 §3): extension `server_name(0)`, `ServerNameList { ServerName server_name_list<1..2^16-1> }`; `HostName` is "ASCII encoding without a trailing dot"; "Literal IPv4 and IPv6 addresses are not permitted"; "MUST NOT contain more than one name of the same name_type".
- Size: the X25519MLKEM768 client share alone is "1216 bytes (1184 bytes for the ML-KEM part and 32 bytes for X25519)" ([draft-ietf-tls-ecdhe-mlkem-05](https://datatracker.ietf.org/doc/html/draft-ietf-tls-ecdhe-mlkem)), so a current ClientHello exceeds one 1460-byte TCP segment.
- Limits used by others: nginx `preread_buffer_size 16k`, `preread_timeout 30s` ([core](https://nginx.org/en/docs/stream/ngx_stream_core_module.html)); HAProxy examples `tcp-request inspect-delay 5s` ([manual](https://docs.haproxy.org/3.2/configuration.html)).

*(our reasoning)* The peek loops on `read` until `5 + length` bytes of the first record are in, then across further type-22 records until the handshake `length` is met, with a 16 KiB cap and the listener's header deadline; every byte read is `rewind`ed (passthrough and termination both see the original stream). Bytes that are not `16 03 0x` are "not TLS": a `HostSNI(*)` route relays them unchanged, anything else is closed and counted.

ECH: [RFC 9849](https://www.rfc-editor.org/rfc/rfc9849.html) (Standards Track, March 2026). `public_name` is "The DNS name of the client-facing server"; the client "SHOULD place the value of `ECHConfig.contents.public_name` in the "server_name" extension" of the outer ClientHello (§6.1); in split mode the client-facing server and the backend server differ (§3.1). *(our reasoning)* A passthrough route sees the ECH public name, never the inner name: one `HostSNI(public)` route per ECH-fronted backend is the only correct behaviour, and the docs say so. Server-side ECH decryption is out of scope for v0.6.

### 4. TLS termination for TCP routes (M-L4-02)

- Mechanism: the listener's existing `Acceptor` (SNI resolver, policy, tickets) terminates; the plaintext is relayed to the backend, optionally re-encrypted with `TransportConnector` + `BasicPeer { sni }`. Only **implicit TLS** protocols work: the client's first bytes must be a ClientHello.
- Works: MQTT on 8883 ("TCP ports 8883 and 1883 are registered with IANA for MQTT TLS and non TLS communication respectively", [MQTT 3.1.1 §4.2](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)); SMTP submissions on 465 ("a TLS handshake begins immediately", [RFC 8314 §3.3](https://www.rfc-editor.org/rfc/rfc8314.html#section-3.3)); IMAPS 993, LDAPS 636, and PostgreSQL 17+ clients with `sslnegotiation=direct`: "start SSL handshake directly after establishing the TCP/IP connection… only allowed with sslmode=require or higher… introduced in PostgreSQL version 17" ([libpq](https://www.postgresql.org/docs/17/libpq-connect.html)); the server "will recognize connections which immediately begin SSL negotiation" and the client "is required to use the ALPN extension… "postgresql"" ([protocol flow](https://www.postgresql.org/docs/17/protocol-flow.html)).
- Does not work: PostgreSQL's default `sslnegotiation=postgres` ("the frontend initially sends an SSLRequest message… The server then responds with a single byte containing S or N", [protocol flow](https://www.postgresql.org/docs/17/protocol-flow.html)); MySQL, where the server speaks first ("The initial handshake starts with the server sending the Protocol::Handshake packet… the client can request an SSL connection… with the Protocol::SSLRequest packet", [MySQL internals](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_connection_phase.html)); SMTP 25/587 and IMAP 143 STARTTLS (HAProxy: `req.ssl_sni` "will not work for explicit TLS based protocols, like SMTP (25/587) or IMAP (143)", [manual](https://docs.haproxy.org/3.2/configuration.html#7.3.5-req.ssl_sni)).
- Traefik's answer for PostgreSQL: "reads the first bytes sent by a Postgres client, identifies if they correspond to" a STARTTLS negotiation, "acknowledges and signals the client that it can start the TLS handshake", recommends `sslmode=require` ([TCP TLS](https://doc.traefik.io/traefik/v3.7/reference/routing-configuration/tcp/tls/)). *(our reasoning)* The SSLRequest is one fixed 8-byte message; answering `S` and then peeking is ~30 lines and serves both passthrough and termination, so v0.6 should include it as `starttls: postgres` on a TCP listener (default off). MySQL stays documented as "passthrough only"; the diagnostic for `tls` on a route whose backend port is 3306 should say so.

### 5. PROXY protocol (M-L4-03)

Spec ([proxy-protocol.txt](https://www.haproxy.org/download/2.9/doc/proxy-protocol.txt), revision 2020/03/05): v1 is one US-ASCII line `PROXY TCP4|TCP6|UNKNOWN <src> <dst> <sport> <dport>\r\n`, at most 107 bytes including CRLF; v2 starts with the 12-byte signature `0D 0A 0D 0A 00 0D 0A 51 55 49 54 0A`, byte 13 = version (2) and command (`0x0` LOCAL, `0x1` PROXY; others "must drop"), byte 14 = family/transport (`0x11` TCP over IPv4, `0x21` TCP over IPv6, `0x00` UNSPEC), bytes 15–16 = address block length, then addresses and TLVs `{type:1, length:2, value}`: `0x01` ALPN, `0x02` AUTHORITY, `0x03` CRC32C, `0x04` NOOP, `0x05` UNIQUE_ID, `0x20` SSL (sub-TLVs `0x21`–`0x25`), `0x30` NETNS. The header is sent "once, immediately after the connection is established, before any other data"; the receiver "must not process the connection until it has a complete, valid header", may time out (≥ 3 s suggested), uses the real endpoints for LOCAL (health checks), "must be explicitly configured… must never try to guess", and access "should be filtered so that only trusted proxies can send the header".

- Before the TLS handshake or the preface read, if `listener.proxy_protocol` is set and the peer is in `trusted`, read the header under the listener's request-header timeout with a 16 KiB cap.

### 7. Health, balancing, lifetime

- Probes: `HealthMode::Tcp` already connects and drops; with `proxy_protocol` on the service a probe must send a `LOCAL` v2 header first, or the backend reads garbage (spec: LOCAL is for "health checks", the receiver "must use the real connection endpoints"). Balancing reuses `rdock-balancer` selection per new connection; sessions, retries and status-code policies do not apply. *(our reasoning)*
- Lifetime: `copy_bidirectional` propagates a half-close and only returns when both directions are done, so a backend that closes while the client keeps the socket open hangs until the client gives up; NGINX closes both sides unless `proxy_half_close on`, Traefik caps the tail at `terminationDelay` (100 ms). *(our reasoning)* Relay loop = `copy_bidirectional` inside an idle timer (reset on bytes in either direction; default 10 min like NGINX `proxy_timeout`, per listener) plus a `termination_delay` (default 100 ms) that starts when one direction ends. Draining a listener means waiting for connections that may live for hours; `drain_timeout` (8 s) then aborts them, which is the right default for a reload but should be logged with the count, and `rdock_tcp_connections{listener,route}` and `rdock_tcp_bytes_total{direction}` make it visible.

### 8. Testing

- SNI passthrough with a real database: PostgreSQL 17 in Docker with `ssl=on`, `server.crt`/`server.key` ([ssl-tcp](https://www.postgresql.org/docs/17/ssl-tcp.html)); `psql "host=db.test sslmode=require sslnegotiation=direct"` through a `tcp` listener must reach the right container by SNI, and the same command without `sslnegotiation=direct` must fail with a clear diagnostic unless `starttls: postgres` is on. An MQTT broker on 8883 with `mosquitto_sub --cafile … -p 8883` covers ALPN-less implicit TLS; termination is proven by the broker seeing plaintext on 1883 while the client sees the listener's certificate (`rdock-testkit::TestCa`).
- ClientHello corner cases with `openssl s_client`: `-servername`, `-noservername` ("Suppresses sending of the SNI"), `-alpn`, and `-max_send_frag` ("The maximum size of data fragment to send") to split the hello across records ([openssl-s_client](https://docs.openssl.org/master/man1/openssl-s_client/)); a raw test client that writes the hello one byte at a time covers TCP segmentation; `nc` sending `GET / HTTP/1.1` and random bytes to a TLS-only `tcp` listener must be closed without a route match and counted; a 20 KiB "record" must hit the cap.
- PROXY protocol: socat has no PROXY-protocol support (its `PROXY:` address is HTTP CONNECT, [man page](http://www.dest-unreach.org/socat/doc/socat.html)), so use HAProxy in Docker as the client (`server … send-proxy-v2` / `send-proxy`) and as the backend (`bind … accept-proxy`) to verify both directions, plus `proxy-header::encode_v1/v2` in `rdock-testkit` for malformed headers (bad signature, truncated TLV, LOCAL command, UNSPEC family, 107-byte v1 limit) and for an untrusted peer that sends a valid header.

*(our reasoning)* **Recommendation.** Keep ADR-0012's model: a `tcp` listener is our accept loop with a different `serve()`, no Pingora `Service`/`ServerApp`. Per connection:
1. Optional PROXY header: trusted sources only, required once trusted (`optional: true` to relax), 16 KiB cap, the listener's header timeout; parsed and written with proxy-header 0.1.3. The same step runs on `http`/`https` listeners and feeds `SocketDigest.peer_addr`, so B-NET-08 sees the real client.
2. Optional `starttls: postgres` (answer the 8-byte SSLRequest with `S`).
3. ClientHello peek with our own parser in `rdock-tls` (looping reads, 16 KiB cap, deadline; tls-parser and the rustls `Acceptor` as test oracles); non-TLS bytes only match `HostSNI(*)`.
4. Route match on `HostSNI`/`HostSNIRegexp`/`ALPN`/`ClientIP` with the existing grammar; routes on a listener that answers TLS-ALPN-01 may never match `acme-tls/1`.
5. Passthrough (rewind and relay) or termination with the listener's `Acceptor`, then `l4::ext::connect` or `TransportConnector` (TLS to backend) with the outbound PROXY v1/v2 header first.
6. `copy_bidirectional` under an idle timeout (default 10 min) and a 100 ms termination delay; per-client-IP `inflightconn` through `rdock-limits`; bytes and connections as `rdock_tcp_*` metrics.

Out of scope for v0.6: UDP (M-L4-04), server-side ECH, MySQL STARTTLS, Traefik `serversTransport`/`tls.options`/`certresolver` on TCP routers, weighted TCP services, Pingora's fd-transfer upgrade. Open questions for the ADR: whether `drain_timeout` should have a per-listener override for long-lived database connections, and whether `HostSNI(*)` on an `https` listener (mixed HTTP and TCP on `:443`) is allowed in v0.6 or stays a diagnostic.

## 4. Static files (F-WEB-01)

Requirement: "Static files: MIME, ranges, conditional requests, cache headers, SPA fallback, precompressed assets" ([04-requirements](../04-requirements.md) F-WEB-01, P1); done when a "static-file suite (ranges, conditionals, traversal attempts)" passes ([07-roadmap](../07-roadmap.md) v0.6). Directory listing is F-WEB-02 (P3) and stays out. Every fact was checked on 2026-11-06 against the source linked next to it.

### 1. Where we start

- [Architecture §8](../05-architecture.md) lists `static` (P1) among the built-in middlewares that run in the `request` phase and may short-circuit ("401/403/429/301/static"), and §16 asks for a "canonicalised root, symlink policy, deny dotfiles by default".
- `rdock-middleware`: `Middleware::request` returns `Flow::Reply(Reply { status, headers, body: Option<Bytes> })` (`crates/rdock-middleware/src/lib.rs`); `maintenance` and `errors` answer this way. The proxy's `reply()` (`crates/rdock-proxy/src/proxy.rs` ≈ L440) sets `Content-Length`, runs the response phase of the earlier middlewares in reverse, honours `HEAD`, and writes the body with one `write_response_body(Some(body), true)`: a reply is fully buffered, there is no streaming reply today. Streaming exists only for upstream bodies, in `response_body_filter` (compression encoder, `replace_body`, `bandwidth` throttle).
- `compress` already refuses what a static server must protect: it skips `HEAD`, 206, `Content-Range`, bodies with a `Content-Encoding`, and it appends `Vary: Accept-Encoding`, drops `Accept-Ranges` and `Content-Length`, and turns a strong `ETag` into `W/` when it encodes (`compress.rs`). So a `static` reply with `Content-Encoding: br` or a 206 is never compressed twice; a plain reply of a compressible type is compressed on the fly, which is Caddy's `encode` + `file_server` behaviour.
- `rdock-admin/src/dashboard.rs` (rust-embed, ADR-0024) already implements, in 110 lines: strong `ETag` from SHA-256, `If-None-Match` → 304, `.br`/`.gz` siblings chosen from `Accept-Encoding` (no q-values), `Vary: Accept-Encoding`, `charset=utf-8` for `text/*` and JavaScript, `public, max-age=31536000, immutable` under `assets/` and `no-cache` elsewhere, and SPA fallback to `index.html` when the last path segment has no `.`. It has no `Range`, `Last-Modified`, `If-Modified-Since` or `If-Range`. The negotiation, charset and fallback rules can move into a shared helper; the file-system part is new.
- `rdock-rules::path::normalize` (`crates/rdock-rules/src/path.rs`) decodes only unreserved escapes (so `%2e%2e` becomes `..` and is removed with the other dot segments), upper-cases the rest (`%2F`, `%5C`, `%00` stay encoded in `forwarded`), collapses `//`, rejects truncated escapes and fragments with 400. A static handler receives `forwarded`, decodes it exactly once more, and must re-check `..`, `\`, NUL and UTF-8 on the result.
- Already in the workspace (`Cargo.toml`): `percent-encoding` 2.3.2, `httpdate` 1.0.3, `tokio` with `fs`, `brotli`, `zstd`, `flate2`, and `mime_guess` through rust-embed's `mime-guess` feature. `Route.service` is a required `String` (`crates/rdock-model/src/route.rs`), so a route that is answered entirely by a middleware still has to name a service.

### 2. HTTP semantics to implement

| Rule | Source (RFC 9110 unless noted; checked 2026-11-06) |
|---|---|
| Strong validator changes on every change of the representation; `ETag` is a quoted opaque string, `W/` marks weak; strong comparison needs both strong and byte-equal, weak comparison ignores `W/` | [§8.8.1, §8.8.3, §8.8.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.3) |
| `Last-Modified` is implicitly weak unless the server knows the file cannot change twice in one second | [§8.8.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.2.2) |
| `If-Match` uses strong comparison, false → 412; `If-None-Match` uses weak comparison, false → 304 for GET/HEAD, 412 otherwise; `If-Modified-Since` is ignored when `If-None-Match` is present, when the date is invalid or the method is not GET/HEAD; `If-Unmodified-Since` is ignored when `If-Match` is present | [§13.1.1–13.1.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1) |
| `If-Range` is ignored without `Range`; only strong validators (a date only if strong); false → ignore `Range`, send 200 | [§13.1.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5) |
| Order: If-Match → If-Unmodified-Since → If-None-Match → If-Modified-Since → If-Range → perform | [§13.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2.2) |
| `Range` is defined for GET only, MUST be ignored for unrecognised methods, MAY be ignored at all; an int-range is invalid when last-pos < first-pos; a suffix longer than the file means the whole file; satisfiable = first-pos < length or non-zero suffix; satisfiable → SHOULD 206, otherwise SHOULD 416; a server MAY ignore or reject more than two overlapping ranges or many small unordered ones; overlapping ranges MAY be coalesced | [§14.1.1–14.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2), [§15.3.7.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.7.2) |
| Single-part 206 MUST carry `Content-Range`; multipart uses `multipart/byteranges` with the boundary, `Content-Range` in each part and none in the header section; a 206 MUST include `Date`, `Cache-Control`, `ETag`, `Expires`, `Content-Location`, `Vary` if a 200 would | [§15.3.7](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.7) |
| 416 SHOULD carry `Content-Range: bytes */<length>`; `Accept-Ranges: bytes` advertises support, `none` denies it | [§15.5.17](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.17), [§14.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.3) |
| 304 MUST include `Content-Location`, `Date`, `ETag`, `Vary` (and `Cache-Control`, `Expires`) if a 200 would | [§15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5) |
| HEAD: no content, SHOULD send the same header fields as GET | [§9.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2) |
| Without `Content-Type` a recipient MAY assume `application/octet-stream` | [§8.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.3) |
| "Unconstrained multiple range requests are susceptible to denial-of-service attacks"; servers ought to ignore, coalesce or reject egregious sets | [§17.15](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.15) |
| Without an explicit expiry a cache MAY apply a heuristic lifetime, typically 10 % of the `Last-Modified` age; `no-cache` forces revalidation, `no-store` forbids storing; a cache that does not support ranges MUST NOT store partial responses | [RFC 9111 §4.2.2, §5.2.2, §3.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.2) |
| `immutable` tells clients not to revalidate during the freshness lifetime; meant for versioned URLs; clients should ignore it outside HTTPS | [RFC 8246](https://www.rfc-editor.org/rfc/rfc8246.html) |
| `text/javascript` is the only current JavaScript type (`.js`, `.mjs`); `application/javascript` is obsolete; charset optional, modules are always UTF-8 | [RFC 9239 §2](https://www.rfc-editor.org/rfc/rfc9239.html) |
| `X-Content-Type-Options: nosniff` blocks scripts and styles whose type is wrong and disables sniffing of other responses; "site security testers usually expect this header" | [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Content-Type-Options) |

`Content-Disposition` is a download hint, not needed for a site; actix-files sends it by default and offers `disable_content_disposition` ([docs.rs](https://docs.rs/actix-files/latest/actix_files/struct.Files.html)). *(our reasoning)* We send none and keep an `attachment` option for later.

### 3. Precompressed assets

- Caddy `file_server precompressed`: sidecars `.br`, `.zst`, `.gz`, default order `br zstd gzip`; the uncompressed file is checked first and the sidecar sets `Content-Encoding`; `encode` compresses on the fly when there is no sidecar ([Caddy](https://caddyserver.com/docs/caddyfile/directives/file_server)).
- NGINX `gzip_static off|on|always` (default off, module not built by default, `always` serves `.gz` to everyone); `gzip_vary` is off by default so `Vary` must be enabled separately ([gzip_static](https://nginx.org/en/docs/http/ngx_http_gzip_static_module.html), [gzip](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)). `brotli_static on|off|always` in `ngx_brotli`, default off ([README](https://raw.githubusercontent.com/google/ngx_brotli/master/README.md)). NGINX recommends equal modification times on original and `.gz`.
- tower-http `ServeDir`: `precompressed_gzip/br/deflate/zstd` look for `.gz`, `.br`, `.zz`, `.zst`; both files must exist; falls back to the plain file ([docs.rs](https://docs.rs/tower-http/latest/tower_http/services/struct.ServeDir.html)).
- Ranges apply to the "selected representation", so a `Range` on `app.js` served as `app.js.br` is a byte range of the Brotli bytes, with `Content-Encoding: br` and the sidecar's own `ETag` and length ([RFC 9110 §14.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.1.2)). *(our reasoning)* Each variant gets its own strong `ETag` (its own mtime and size), and `Vary: Accept-Encoding` on every answer, 304 and 416 included; `If-Range` is compared against the variant's tag. No double compression: `compress` skips responses that carry a `Content-Encoding` (§1).

### 4. SPA fallback, directories, index

- NGINX `try_files file ... uri | =code`: checks each file in order, `$uri/` tests a directory, the last argument is an internal redirect or a status ([core](https://nginx.org/en/docs/http/ngx_http_core_module.html)); `index` defaults to `index.html` and also works by internal redirect ([index](https://nginx.org/en/docs/http/ngx_http_index_module.html)). The SPA idiom `try_files $uri $uri/ /index.html` therefore answers 200 with `index.html`, never 404.
- Caddy `try_files` rewrites to the first existing file (`{path}/` matches directories, `=404` form, default policy `first_exist`) ([try_files](https://caddyserver.com/docs/caddyfile/directives/try_files)); `file_server` defaults `index index.html index.txt`, redirects `/dir` → `/dir/` with 308 when an index exists and strips a trailing slash from files (`disable_canonical_uris` turns this off), answers 404 for a directory without index and without `browse`, and `pass_thru` hands a miss to the next handler ([file_server](https://caddyserver.com/docs/caddyfile/directives/file_server), [staticfiles.go](https://raw.githubusercontent.com/caddyserver/caddy/master/modules/caddyhttp/fileserver/staticfiles.go)).
- Go `ServeFile` redirects `/index.html` to `/` ([net/http](https://pkg.go.dev/net/http#ServeFile)); tower-http redirects to the trailing slash and appends `index.html` by default; `fallback` keeps the fallback's status, `not_found_service` forces 404; non-GET/HEAD get 405 ([docs.rs](https://docs.rs/tower-http/latest/tower_http/services/struct.ServeDir.html)).
- The dashboard falls back only when the last segment has no extension (`dashboard.rs`). *(our reasoning)* The same rule, plus explicit `except` prefixes (`/api/`), keeps missing `app.3f2.js` a 404 so a stale bundle fails loudly instead of returning HTML, which is the classic SPA bug. Fallback answers 200 with `index.html`'s own validators and `no-cache`.

### 5. Path safety

- Decode exactly once: "implementations must not percent-encode or decode the same string more than once" ([RFC 3986 §2.4](https://www.rfc-editor.org/rfc/rfc3986.html#section-2.4)); dot segments are removed by §5.2.4. Caddy's `SanitizedPathJoin` does `path.Clean("/"+p)` then `filepath.IsLocal` and joins to the root ([caddyhttp.go](https://raw.githubusercontent.com/caddyserver/caddy/master/modules/caddyhttp/caddyhttp.go)); tower-http answers 404 for any segment containing `..` or a backslash ([docs.rs](https://docs.rs/tower-http/latest/tower_http/services/struct.ServeDir.html)); Go rejects `..` elements ([net/http](https://pkg.go.dev/net/http#ServeFile)).
- Rust: `Path::components` never resolves `..` ("`a/c` and `a/b/../c` are distinct") and `canonicalize` needs an existing path ([std](https://doc.rust-lang.org/std/path/struct.Path.html#method.components)); `CString::new` fails on an interior NUL ([std](https://doc.rust-lang.org/std/ffi/struct.CString.html#method.new)); `str::from_utf8` returns `Err` for invalid sequences ([std](https://doc.rust-lang.org/std/str/fn.from_utf8.html)), overlong forms included *(our reasoning)*.
- Kernel confinement: `openat2(2)` (Linux 5.6) with `RESOLVE_BENEATH` refuses any resolution that leaves `dirfd` (absolute symlinks included), `RESOLVE_NO_SYMLINKS` refuses every symlink, `RESOLVE_NO_XDEV` refuses mount crossings; escapes give `EXDEV`, symlinks `ELOOP`, and `EAGAIN` asks for a retry after a possible rename race ([man7](https://man7.org/linux/man-pages/man2/openat2.2.html)). [cap-std](https://crates.io/crates/cap-std) 4.0.3 (2026-08-20, Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT, 3.4.6 published the same day) uses `openat2` on 5.6+ and opens each component itself elsewhere; "symlinks as long as they remain within the sandbox", absolute paths and absolute symlinks are errors, MSRV 1.70 ([README](https://raw.githubusercontent.com/bytecodealliance/cap-std/main/README.md)). This also covers macOS development builds.
- Symlinks: Caddy follows them and warns that "symbolic links within the root can still allow accesses outside of the root"; `hide` is "not a security boundary" and hides only the Caddyfile by default ([file_server](https://caddyserver.com/docs/caddyfile/directives/file_server)). NGINX `disable_symlinks off` (default: not checked) `| on | if_not_owner [from=]` ([core](https://nginx.org/en/docs/http/ngx_http_core_module.html)). actix-files serves hidden files only with `use_hidden_files` ([docs.rs](https://docs.rs/actix-files/latest/actix_files/struct.Files.html)).
- Case: Linux file systems are case-sensitive, so `.ENV` is a different file from `.env`; a dotfile rule applied to each decoded path component needs no case folding *(our reasoning)*. Windows device names do not apply to a Linux binary.

### 6. MIME

- [mime_guess](https://crates.io/crates/mime_guess) 2.0.5 (2024-06-29, MIT, previous release 2022-02-16, ≈ 1,000 extensions taken from mime-db; already in the tree). | SPA | `try_files {path} /index.html` | `try_files $uri $uri/ /index.html` | – | – | – |

*(our reasoning)* Traefik users run nginx next to Traefik for every SPA; a built-in `static` with Traefik-compatible routing is a feature gap ReverseDock can advertise, and `rdock migrate traefik` can mention it when it sees an nginx/static container.

### 9. Configuration shape

Two shapes fit the model. **A `static` service type** (`services.<s>.static.root`, next to `backends` and `split`) keeps "routes point to services" and nothing changes in `Route`; but every service field (load balancer, health, retries, timeouts, sticky, `max_requests`) is meaningless for it, `upstream_peer` must be bypassed in the proxy, and middlewares like `basic_auth` still run before it anyway. **A `static` middleware** is what [Architecture §8](../05-architecture.md) planned, reuses `Flow::Reply`, composes with `basic_auth`, `headers`, `compress` and `cache` later, and gets the Docker shorthand `rdock.middlewares` for free; its costs are that `Reply` must grow a streaming body (an `Option<BoxStream<Bytes>>` or a file handle the proxy drains) and that a route still needs a `service`. *(our reasoning)* Middleware, plus `route.service` becomes optional when the chain ends with a terminal middleware (`static` without `pass_through`, `maintenance`, `redirect`), checked by `rdock validate`; a `static` with `pass_through: true` keeps needing a service, which also gives "static assets, API to the backend" in one route.

```yaml
middlewares:
  site:
    static:
      root: /srv/site            # required; opened once as a directory handle, must exist at apply
      index: [index.html]        # NGINX default `index.html` (nginx.org, checked 2026-11-06)
      fallback: /index.html      # off by default; only GET/HEAD whose last segment has no extension
      fallback_except: [/api/]   # prefixes that stay 404
      precompressed: [zstd, br, gzip]   # sidecars, same order as `compress`; [] turns it off
      symlinks: none             # none (RESOLVE_NO_SYMLINKS) | within_root (RESOLVE_BENEATH) | all
      hidden: refuse             # dot-files and dot-directories answer 404; `allow` opts in
      listing: false             # F-WEB-02, P3
      directory_redirect: true   # /dir → /dir/ (308) when an index exists; Caddy default
      max_ranges: 1              # more ranges → full 200 (RFC 9110 §14.2 MAY ignore); up to 16 as multipart
      cache_control:
        default: no-cache                                   # revalidate with the strong ETag
        "/assets/**": public, max-age=31536000, immutable   # hashed names only (RFC 8246)
      nosniff: true
      types: { mjs: text/javascript }   # overrides mime_guess
      pass_through: false        # true = a miss continues to the service (Caddy `pass_thru`)
routes:
  site: { match: "Host(`example.com`)", middlewares: [site] }   # no service needed
```

Docker labels follow the existing grammar (`rdock.middlewares.<name>.static.root=/srv/site`) plus a shorthand `rdock.static.root=/srv/site` that creates a `static` middleware for the container's route and makes it terminal. The path is on the rdock process's file system, so with Docker it is a volume mounted into the rdock container, which the docs must say first; `rdock validate` reports a root that does not exist or is not a directory.

Defaults with their sources: index `index.html` ([nginx](https://nginx.org/en/docs/http/ngx_http_index_module.html)); listing off (actix: "by default show files listing is disabled"; Caddy `browse` is opt-in); hidden files refused (Architecture §16 "deny dotfiles by default"; CVE-2026-77281 shows a hide list is weaker than a rule on every component); symlinks not followed (NGINX and Caddy follow by default and CVE-2024-23334 is the failure mode; `within_root` is one `openat2` flag away); `max_ranges: 1` (RFC 9110 §17.15; tower-http exposes the same switch); `no-cache` default (RFC 9111 §4.2.2 heuristics would otherwise cache HTML for 10 % of its age); `nosniff` on (MDN). Each "all"/"allow" option is offered, as the design rule requires, with a diagnostic rather than a refusal.

### 10. The static-file suite

No conformance suite exists for static serving; Caddy relies on Go's `net/http` tests and tower-http on its own. *(our reasoning)* `tests/static/` in `rdock` e2e, against a fixture tree (small text file, 5 MiB binary, `app.js` + `app.js.br` + `app.js.zst` + `app.js.gz`, `index.html`, `dir/index.html`, `dir-no-index/`, `.env`, `.git/config`, symlinks to a file inside and outside the root, a UTF-8 named file):

- Ranges: `bytes=0-99`, `bytes=100-`, `bytes=-100`, suffix longer than the file (whole, 206), `bytes=0-0,-1` (two ranges → full 200 with default, multipart with `max_ranges: 2`, boundary and per-part `Content-Range`), unsatisfiable `bytes=9999999-` → 416 with `bytes */len`, `last < first` → ignored, malformed → ignored, `Range` on HEAD and POST → ignored, `If-Range` with matching and stale tag, with a date, with a weak tag (ignored).
- Conditionals: `If-None-Match` exact, list, `W/`, `*`; `If-Modified-Since` newer and older, ignored next to `If-None-Match`, invalid date; `If-Match` and `If-Unmodified-Since` → 412; the 304 carries `ETag`, `Vary`, `Cache-Control` and no body; precedence order of §13.2.2.
- HEAD: same headers as GET, `Content-Length` of the file, empty body, with and without `Range`.
- Precompressed: `Accept-Encoding` with q-values, `*`, `identity`, unsupported coding → plain; sidecar `ETag` differs from the plain one; `Range` over the `.br` variant; sidecar for a file that has none; `compress` after `static` does not re-encode; `Vary` on 200, 206, 304.
- SPA: `/`, `/dir`, `/dir/` (308 then 200), `/about` → 200 `index.html`, `/app.missing.js` → 404, `/api/x` → 404 with `fallback_except`, `/index.html` served directly, `/dir-no-index/` → 404.
- Traversal: `/../etc/passwd`, `/%2e%2e/`, `/..%2f`, `/%2e%2e%2f`, `/..;/`, `/a/..%5c..%5c`, `/%5c..%5cetc`, `/%00`, `/file.txt%00.html`, overlong `%C0%AE%C0%AE/`, `/./.env`, `/.ENV`, `/.git/config`, symlink inside the root (404 under `none`, 200 under `within_root`), symlink outside the root (404 under `within_root`, 200 only under `all`), a root deleted or renamed after start (handle still works, reload reports it), 400 from `rdock-rules` for truncated escapes.
- Streaming and load: a 5 MiB file over HTTP/1.1 and HTTP/2 with TLS, byte-exact; 500 concurrent downloads of the same file (no blocking-pool starvation measured as p99 of a parallel tiny request); a slow reader hits `min_send_rate`; `bandwidth` middleware before `static` throttles.
- Validation: missing root, root is a file, `fallback` with an extension, `symlinks: all` prints a warning in `rdock validate` output.

*(our reasoning)* Recommendation: implement `static` as a terminal middleware in `rdock-middleware` that opens its root once as a `cap_std::fs::Dir` (openat2 `RESOLVE_BENEATH` on Linux 5.6+, per-component checks on macOS) and, by default, refuses symlinks, dot-files, listings and multi-range requests; decode the forwarded path once, reject `\`, NUL and invalid UTF-8, then let the kernel do the containment. Generate a strong `ETag` from mtime-ns and size like NGINX and Caddy (cheap, no hashing), `Last-Modified` from mtime, full RFC 9110 §13 precedence and single-range 206 by default; sidecars `.zst`/`.br`/`.gz` by `Accept-Encoding` q-values reusing `compress::negotiate`, with `Vary` everywhere. Extend `Reply` with a streaming body so the proxy drains a `tokio::fs::File` in 256 KiB chunks through `write_response_body`, and let `route.service` be optional behind a terminal middleware; that needs an ADR (config-model change) and a `migrate traefik` note. Open questions for the ADR: whether `fallback` should also require `Accept: text/html` (Caddy and nginx do not check it), whether `cache_control` globs reuse the rule grammar or plain prefixes, and whether `mjs` → `text/javascript` goes into mime_guess upstream or stays a local override.

### 2. The seven providers

Per provider: authentication and least privilege, the calls, the record model, propagation, limits, and the lego names we may mirror. All checked 2026-11-06.

**Route 53**
- Auth: SigV4 with an access key pair, `X-Amz-Security-Token` for STS credentials; endpoint `route53.amazonaws.com`, signed as region `us-east-1` (`cn-northwest-1` in China) ([endpoints](https://docs.aws.amazon.com/general/latest/gr/r53.html)).
- Least privilege: `route53:GetChange` on `arn:aws:route53:::change/*`, `route53:ListHostedZonesByName` on `*`, `route53:ListResourceRecordSets` and `route53:ChangeResourceRecordSets` on the one hosted zone, the latter conditioned on `route53:ChangeResourceRecordSetsNormalizedRecordNames: ["_acme-challenge.example.com"]` and `route53:ChangeResourceRecordSetsRecordTypes: ["TXT"]` with `ForAllValues:StringEquals` ([lego](https://go-acme.github.io/lego/dns/route53/), [condition keys](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/specifying-rrset-conditions.html): lowercase, no trailing dot, `*` written `\052`).
- Zone: `GET /2013-04-01/hostedzonesbyname?dnsname=<candidate>&maxitems=…` while walking labels up; names come back with a trailing dot, `Config.PrivateZone` marks private zones, ≤ 100 per page with `NextDNSName`/`NextHostedZoneId` ([ListHostedZonesByName](https://docs.aws.amazon.com/Route53/latest/APIReference/API_ListHostedZonesByName.html)).
- Write: `POST /2013-04-01/hostedzone/{Id}/rrset/`, XML `ChangeBatch/Changes/Change{Action, ResourceRecordSet{Name, Type, TTL, ResourceRecords/ResourceRecord/Value}}`; a record **set** carries all values, so a second value means `ListResourceRecordSets`, append, `UPSERT`; the batch is atomic; a concurrent change to the same zone fails with `PriorRequestNotComplete` (HTTP 400); the answer carries `ChangeInfo.Id` ([ChangeResourceRecordSets](https://docs.aws.amazon.com/Route53/latest/APIReference/API_ChangeResourceRecordSets.html)). TXT values are quoted, ≤ 255 characters per string, ≤ 4,000 per value ([record types](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/ResourceRecordTypes.html)).
- Propagation: `GET /2013-04-01/change/{Id}` is `PENDING` then `INSYNC` = served by every Route 53 name server, "generally … within 60 seconds" ([GetChange](https://docs.aws.amazon.com/Route53/latest/APIReference/API_GetChange.html)).
- Limits: token buckets per account, 50 burst and 10 requests/s refill, for all actions together and per action (the old 5 requests/s figure is gone); change throughput 1,500 burst and 100 changes/s, an `UPSERT` counting 2; throttling is HTTP 400 `Throttling` "Rate exceeded"; AWS asks for exponential backoff with jitter ([throttling](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/throttling-api-requests.html), [quotas](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/DNSLimitations.html)).
- lego: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `AWS_HOSTED_ZONE_ID`, `AWS_PROFILE`, `AWS_ASSUME_ROLE_ARN`; TTL 10, propagation 120 s, poll 4 s; `AWS_WAIT_FOR_RECORD_SETS_CHANGED` waits for `INSYNC` ("may be unstable") ([lego](https://go-acme.github.io/lego/dns/route53/)).

**Google Cloud DNS**
- Auth: service-account JSON (`client_email`, `private_key`, `private_key_id`); RS256 JWT `{iss, scope, aud: "https://oauth2.googleapis.com/token", exp ≤ 1 h, iat}` POSTed as `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=…` → `access_token`, `expires_in` 3600 ([Google](https://developers.google.com/identity/protocols/oauth2/service-account), [RFC 7523](https://www.rfc-editor.org/rfc/rfc7523.html)).
- Least privilege: scope `https://www.googleapis.com/auth/ndev.clouddns.readwrite`; permissions `dns.changes.create`, `dns.changes.get`, `dns.managedZones.list` plus `dns.resourceRecordSets.{list,create,delete,update}`; `roles/dns.admin` can be granted on one zone ([changes.create](https://docs.cloud.google.com/dns/docs/reference/rest/v1/changes/create), [access control](https://docs.cloud.google.com/dns/docs/access-control)).
- Zone: `GET https://dns.googleapis.com/dns/v1/projects/{project}/managedZones?dnsName=<candidate>.` walking labels, `pageToken` pagination, zones have `visibility` public or private ([managedZones.list](https://docs.cloud.google.com/dns/docs/reference/rest/v1/managedZones/list)).
- Write: `POST …/managedZones/{zone}/changes` with `additions`/`deletions` of `{name, type: "TXT", ttl, rrdatas: ["\"…\""]}`; a deletion must match the existing set exactly, so adding a value is one atomic change that deletes the old set and adds the new one ([Change](https://docs.cloud.google.com/dns/docs/reference/rest/v1/changes)). TXT strings ≤ 255 characters, ≤ 1,000 per record ([records overview](https://docs.cloud.google.com/dns/docs/records-overview)).
- Propagation: `Change.status` goes `pending` → `done`, and `done` means "the request to update the authoritative servers was sent, but those servers might not have applied the update yet": an authoritative poll is still needed ([Change](https://docs.cloud.google.com/dns/docs/reference/rest/v1/changes)).
- Limits: per-project read and write quotas per minute (values shown per project), ≤ 1,000 additions and deletions per change, 100,000 bytes of rrdata per change ([quotas](https://docs.cloud.google.com/dns/quotas)).
- lego: `GCE_PROJECT`, `GCE_SERVICE_ACCOUNT_FILE`, `GCE_SERVICE_ACCOUNT` (inline JSON), `GCE_ZONE_ID`, `GCE_ALLOW_PRIVATE_ZONE`; TTL 120, propagation 180 s, poll 5 s ([lego](https://go-acme.github.io/lego/dns/gcloud/)).

**Azure DNS**
- Auth: `POST https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token` with `client_id`, `client_secret` (or `client_assertion`, a certificate-signed JWT), `scope=https://management.azure.com/.default`, `grant_type=client_credentials` → `access_token`, `expires_in` 3599 ([Entra](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-client-creds-grant-flow)); or a managed identity: `GET http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/` with `Metadata: true`, optional `client_id` ([IMDS](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-use-vm-token)).
- Least privilege: built-in **DNS Zone Contributor** (`Microsoft.Network/dnsZones/*`, id `befefa01-2a29-4197-83a8-272ff33ce314`) assigned at zone or record-set scope; lego recommends Reader on the zone plus DNS Zone Contributor on the `_acme-challenge` TXT record sets ([roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/networking), [lego](https://go-acme.github.io/lego/dns/azuredns/)).
- Zone: no lookup by name; the zone is `{subscriptionId}/{resourceGroupName}/{zoneName}`, so the config names it (lego: `AZURE_ZONE_NAME`, or it lists the resource group).
- Write: `PUT https://management.azure.com/subscriptions/{sub}/resourceGroups/{rg}/providers/Microsoft.Network/dnsZones/{zone}/TXT/{relativeName}?api-version=2018-05-01` with `{"properties": {"TTL": 60, "TXTRecords": [{"value": ["…"]}]}}`; the record set holds the list, so add = GET, append, PUT with `If-Match: <etag>` (`If-None-Match: *` to create only); 200 updated, 201 created, synchronous; `DELETE` on the same URL removes the set ([Record Sets – Create Or Update](https://learn.microsoft.com/en-us/rest/api/dns/record-sets/create-or-update?view=rest-dns-2018-05-01)).
- Propagation: changes "appear in the Azure DNS name servers within 60 seconds"; there is no status API ([FAQ](https://learn.microsoft.com/en-us/azure/dns/dns-faq)).
- Limits: ARM token buckets per subscription and principal (writes 200 burst, 10/s; reads 250, 25/s); Microsoft.Network 1,000 PUT and 10,000 GET per 5 minutes; 429 with `Retry-After` ([throttling](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/request-limits-and-throttling)).
- lego: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_CLIENT_CERTIFICATE_PATH`, `AZURE_SUBSCRIPTION_ID`, `AZURE_RESOURCE_GROUP`, `AZURE_ZONE_NAME`, `AZURE_ENVIRONMENT` (public, usgovernment, china), `AZURE_AUTH_METHOD` (`env`, `msi`, `cli`, `wli`, `oidc`); TTL 60, propagation 120 s, poll 2 s ([lego](https://go-acme.github.io/lego/dns/azuredns/)).

**DigitalOcean**
- Auth: `Authorization: Bearer <token>`; custom scopes `domain:read` (list), `domain:create` or `domain:update` (create records), `domain:delete` (remove); scopes cover domains and records alike, no per-zone scope ([scopes](https://docs.digitalocean.com/reference/api/scopes/), [create record](https://github.com/digitalocean/openapi/blob/main/specification/resources/domains/domains_create_record.yml)).
- Zone: no name filter on `/v2/domains`; lego finds the zone by SOA walk and puts its name in the path ([lego](https://github.com/go-acme/lego/blob/master/providers/dns/digitalocean/digitalocean.go)).
- Write: `POST https://api.digitalocean.com/v2/domains/{zone}/records` `{type: "TXT", name, data, ttl}` → 201 with an integer `id`; records are individual, so several TXT values at one name are separate records; cleanup `DELETE /v2/domains/{zone}/records/{id}` (lego keeps the id per challenge) or `GET …/records?name=<fqdn>&type=TXT` first ([list](https://github.com/digitalocean/openapi/blob/main/specification/resources/domains/domains_list_records.yml)). The spec states no TTL minimum ([domain_record.yml](https://github.com/digitalocean/openapi/blob/main/specification/resources/domains/models/domain_record.yml)).
- Propagation: no status API. Limits: 5,000 requests per hour and 250 per minute per token, `ratelimit-limit/-remaining/-reset` headers, 429 with `retry-after` ([description](https://github.com/digitalocean/openapi/blob/main/specification/description.yml)).
- lego: `DO_AUTH_TOKEN`, `DO_API_URL`; TTL 30, propagation 60 s, poll 5 s, HTTP timeout 30 s ([lego](https://go-acme.github.io/lego/dns/digitalocean/)).

**Hetzner**
- Auth: DNS moved into the Cloud API, `Authorization: Bearer <token>` with a token of the Cloud **project** holding the zone; "Tokens created in the old DNS Console do not work with the new Cloud API"; tokens are per project, so a zone in its own project is the scope unit ([Hetzner](https://docs.hetzner.com/networking/dns/migration-to-hetzner-console/features-and-differences)). Migration from `dns.hetzner.com` is manual and one-way; we found no published shutdown date ([process](https://docs.hetzner.com/networking/dns/migration-to-hetzner-console/process)).
- Write: base `https://api.hetzner.cloud/v1`, RRset model, zone addressed by id **or name**: `POST /zones/{zone}/rrsets/{name}/TXT/actions/add_records` `{ttl, records: [{value: "\"…\""}]}` and `…/actions/remove_records` `{records}`; each returns an `action` with `status` `running`, `success` or `error`, polled at `GET /actions/{id}` ([lego client](https://github.com/go-acme/lego/blob/master/providers/dns/hetzner/internal/hetznerv1/internal/client.go), [hetznerv1.go](https://github.com/go-acme/lego/blob/master/providers/dns/hetzner/internal/hetznerv1/hetznerv1.go)). Several values per RRset are the model.
- Propagation: action `success`, then an authoritative poll. Limits: 3,600 requests per hour per project, `RateLimit-Limit/-Remaining/-Reset`, 429 ([Cloud API spec](https://docs.hetzner.cloud/cloud.spec.json)).
- lego: `HETZNER_API_TOKEN` (legacy `HETZNER_API_KEY` deprecated); TTL 120 (floored at 60 in `master`), propagation 60 s, poll 2 s ([lego](https://go-acme.github.io/lego/dns/hetzner/), [hetzner.go](https://github.com/go-acme/lego/blob/master/providers/dns/hetzner/hetzner.go)).

**deSEC**
- Auth: `Authorization: Token <secret>`; token policies with `domain`, `subname`, `type`, `perm_write` (most specific wins; a default all-`null` policy first) limit a token to writing `_acme-challenge` TXT of one domain; every token can read ([tokens](https://desec.readthedocs.io/en/latest/auth/tokens.html)).
- Write: `POST /api/v1/domains/{domain}/rrsets/` `{subname: "_acme-challenge", type: "TXT", ttl, records: ["\"…\""]}` (201; 400 if the RRset exists), `PATCH /rrsets/{subname}.../TXT/` to change `records`, `records: []` or `DELETE` to remove; bulk `PATCH rrsets/` is atomic and costs one DNSSEC signing; TXT contents must be double-quoted; `ttl` ≤ 86,400 and ≥ the domain's `minimum_ttl` (set by deSEC, example 900, lower on request) ([RRsets](https://desec.readthedocs.io/en/latest/dns/rrsets.html), [domains](https://desec.readthedocs.io/en/latest/dns/domains.html)).
- Propagation: modifications are published "immediately"; no status API ([domains](https://desec.readthedocs.io/en/latest/dns/domains.html)).
- Limits: reads 10/s and 50/min; RRset writes **per domain** 2/s, 15/min, 100/h, 300/day (`dns_api_per_domain_expensive`), the one that bites ACME since an order spends 2–4 writes per name ([rate limits](https://desec.readthedocs.io/en/latest/rate-limits.html)).
- lego: `DESEC_TOKEN`; TTL 3600, propagation 120 s, poll 4 s ([lego](https://go-acme.github.io/lego/dns/desec/)).

**RFC 2136**
- Protocol ([RFC 2136](https://www.rfc-editor.org/rfc/rfc2136.html), 1997): opcode UPDATE (5); sections Zone (the zone's SOA question), Prerequisite, Update, Additional; add = RR in the zone's class; delete one RR = class NONE with its RDATA; delete the RRset = class ANY, TTL 0; response codes NOERROR … REFUSED, YXRRSET, NXRRSET, NOTAUTH, NOTZONE; all-or-nothing. Send to the primary (SOA `MNAME`) first, then other NS on SERVFAIL, NOTIMP or no answer; UDP if it fits, TCP for a reliable response code. Several TXT values at one name are plain additional RRs.
- TSIG ([RFC 8945](https://www.rfc-editor.org/rfc/rfc8945.html), 2020, obsoletes 2845 and 4635): `hmac-sha256` mandatory and recommended, `hmac-sha1` mandatory but not recommended, `hmac-md5` "MUST NOT be used", `hmac-sha384`/`-sha512` optional; fudge 300 s recommended.
- Reference clients: lego `master` (env prefix `DNSUPDATE_`: `_NAMESERVER`, `_TSIG_KEY`, `_TSIG_SECRET`, `_TSIG_ALGORITHM`, `_TSIG_FILE`, `_TTL`, `_DNS_TIMEOUT` 10 s) defaults to `hmac-sha1`, fudge 300 hard-coded, UDP, and deletes the existing RRset before inserting, which breaks a parallel apex + wildcard ([lego](https://github.com/go-acme/lego/blob/master/providers/dns/rfc2136/rfc2136.go)); certbot (`dns_rfc2136_server` IP only, `_port`, `_name`, `_secret`, `_algorithm`, `_sign_query`) defaults to HMAC-MD5, supports MD5/SHA1/224/256/384/512, TCP, TTL 120, propagation 60 s, finds the zone by SOA with the AA flag ([certbot](https://certbot-dns-rfc2136.readthedocs.io/en/stable/), [source](https://github.com/certbot/certbot/blob/main/certbot-dns-rfc2136/src/certbot_dns_rfc2136/_internal/dns_rfc2136.py)).
- Servers: BIND `update-policy { grant keyname. name _acme-challenge.example.com. txt; }` ([certbot](https://certbot-dns-rfc2136.readthedocs.io/en/stable/)); Knot `acl: action: update, key: […], update-type: [TXT], update-owner: name, update-owner-name: [_acme-challenge]` ([Knot](https://www.knot-dns.cz/docs/latest/html/configuration.html)); PowerDNS `dnsupdate=yes`, `allow-dnsupdate-from`, zone metadata `TSIG-ALLOW-DNSUPDATE`, `dnsupdate-require-tsig` (5.0+) ([PowerDNS](https://doc.powerdns.com/authoritative/dnsupdate.html)).

### 4. A common adapter design

*(our reasoning)* The `DnsSolver` trait stays as it is (present/cleanup of one value); what changes is a shared `rdock-dns-providers` crate (or module) with:
- `ZoneFinder`: walk labels from the FQDN up, ask the provider's zone list at each step (Route 53 `ListHostedZonesByName`, Google `managedZones?dnsName=`, deSEC `owns_qname`, RFC 2136 SOA, Cloudflare `zones?name=`), skip private zones unless `allow_private_zone: true`, cache the answer per order; an explicit `zone`/`zone_id` short-circuits it (Azure requires it).
- `TxtSet` semantics per provider: record-per-value APIs (Cloudflare, DigitalOcean, RFC 2136) create and delete one record; set-based APIs (Route 53, Google, Azure, Hetzner, deSEC) read-modify-write the set under a per-zone `tokio::Mutex`, retry on `PriorRequestNotComplete` and `If-Match` 412, and never delete another value. This is what lets `tls.domains: ["*.example.com", "example.com"]` run as one order.
- `Propagation` strategy: `ChangeStatus` (Route 53 `GetChange` until `INSYNC`, Hetzner action until `success`, Google `done`) **and then** the existing `wait_until_visible` authoritative poll for everyone, since only Route 53's `INSYNC` means the record is served.
- `Backoff`: exponential with full jitter, cap 30 s, honour `Retry-After`, `ratelimit-reset` and `RateLimit-Reset`; a 4xx other than 429/409/412 is final. Budget: five attempts per call, the whole present within `dns_propagation_timeout`.
- Every option, safe by default: secrets only through `${file:…}`/`${env:…}` (`rdock validate` refuses literal keys that look like credentials); TSIG algorithm default `hmac-sha256`, `hmac-md5` refused with a diagnostic, `hmac-sha1` allowed with a warning; RFC 2136 over TCP by default with TSIG required unless `insecure_unsigned: true`; 30 s per API call; no redirects; Azure/Google/AWS endpoints fixed per cloud (`environment: public|usgovernment|china`), never free-form URLs except for tests (`api_url`, loopback only unless `https://`).
- Config shape extends the existing enum: `type: route53 { access_key_id, secret_access_key, session_token?, hosted_zone_id?, region? }`, `google_cloud_dns { credentials_file | credentials, project?, zone? }`, `azure_dns { tenant_id, client_id, client_secret | client_certificate | managed_identity: true, subscription_id, resource_group, zone, environment }`, `digitalocean { api_token }`, `hetzner { api_token, zone? }`, `desec { token }`, `rfc2136 { nameserver, tsig_key_name, tsig_secret, tsig_algorithm, zone?, transport: tcp|udp }`; shared `ttl`, `propagation`, `api_url` (tests). Environment mirrors `RDOCK_DNS_<PROVIDER>_*` only through `${env:…}`, so nothing is read implicitly.

### 5. Testing with mocked APIs

- lego tests each provider against an `httptest.Server` built with its `servermock` helper: routes per `METHOD path`, responses from JSON fixture files, request headers, query parameters and bodies checked against fixtures, and `TestLive*` tests that skip unless the env var set marks a live run ([desec_test.go](https://github.com/go-acme/lego/blob/master/providers/dns/desec/desec_test.go)). certbot mocks the client library with `unittest.mock` (for RFC 2136 it patches `dns.query.tcp/udp` and the SOA lookup) and never touches the network ([dns_rfc2136_test.py](https://github.com/certbot/certbot/blob/main/certbot-dns-rfc2136/src/certbot_dns_rfc2136/_internal/tests/dns_rfc2136_test.py)).
- [wiremock](https://crates.io/crates/wiremock) 0.6.5 (2025-08-24, MIT/Apache-2.0, no declared MSRV): hyper 1.7, tokio 1.47.1, deadpool 0.12.2, assert-json-diff 2.0.2, regex, base64 0.22 ([Cargo.toml](https://docs.rs/crate/wiremock/0.6.5/source/Cargo.toml)). Our Cloudflare test already does the same job in 119 lines with hyper alone.
- *(our reasoning)* Plan: move the fake-API server into `rdock-testkit::fake_api` (route table of method + path pattern → status, headers, JSON or XML body; records every request; per-call failure injection: 429 with `Retry-After`, 5xx, `PriorRequestNotComplete`, 412), and write one **contract test** generic over `DnsSolver` that every adapter runs: present two values for one name (apex + wildcard), cleanup one, the other stays; retry after 429; refuse a literal secret; zone found by walking labels; token read from a file and re-read after rotation; private zone skipped. Provider fixtures are recorded JSON/XML answers checked into `crates/rdock-dns-providers/tests/fixtures/<provider>/`. RFC 2136 runs against an in-process UDP/TCP server built on `hickory-proto` that verifies TSIG with `TSigVerifier`, plus a CI job against BIND 9 and Knot containers with `update-policy`/`acl` restricted to `_acme-challenge` TXT. Live tests (`RDOCK_LIVE_DNS_<PROVIDER>=1` with real tokens) stay out of CI and run on the test server before a release, as the Pebble suite does. Wiremock is not needed.

### 6. Why these seven, and the escape hatches

- lego lists 231 DNS providers, including `exec`, `httpreq`, `acmedns` and `manual` ([lego](https://go-acme.github.io/lego/dns/)); Traefik's resolver uses that list. Caddy's [libdns](https://github.com/libdns/libdns) (MIT) offers "over 80 packages" behind `RecordAppender`/`RecordDeleter` interfaces. Our `exec` and `webhook` already cover anything either can reach: an `exec` hook can call `lego`'s CLI or any libdns-based tool.
- [acme-dns](https://github.com/joohoi/acme-dns) (MIT) is a purpose-built DNS server: the user CNAMEs `_acme-challenge.<name>` to a subdomain it owns; `POST /register` returns `username`, `password`, `fulldomain`, `subdomain` (optionally `allowfrom` CIDRs); `POST /update` with `X-Api-User`, `X-Api-Key` and `{subdomain, txt}` (exactly 43 characters) sets the value; it keeps two TXT values, so apex + wildcard work. It is the standard answer for registrars without an API and for not giving a proxy zone-wide write rights.
- *(our reasoning)* The seven cover the three hyperscalers, the two providers our Docker/VPS audience runs on, the free DNSSEC host, and the standard that reaches every self-hosted server (BIND, Knot, PowerDNS). An `acme-dns` adapter is ~60 lines on the shared REST client and the only generic one worth adding to W-DNS-03's list (it needs no provider credentials at all); a "libdns-compatible" or "lego exec" adapter adds nothing over `exec`. Providers beyond that are answered with `exec`/`webhook` and a documented recipe, not with more adapters.

*(our reasoning)* Recommendation: raw REST on the existing hyper-rustls client for all six HTTP providers, with two small signing helpers on ring (SigV4 HMAC chain; RS256 JWT for Google service accounts and Azure certificate assertions): the AWS SDK fails on three of our rules at once (aws-lc-rs by default, MSRV 1.94.1 against our 1.89, tens of crates for three calls), the Azure crate is unmaintained, and the Google crate is unaudited bulk for two endpoints. RFC 2136 on `hickory-proto` + `hickory-net` 0.26.3 with `dnssec-ring`, defaulting to `hmac-sha256` over TCP and refusing MD5. Build the shared `fake_api` harness and the generic contract test first and port the Cloudflare adapter onto it, then deliver in this order: RFC 2136 (self-hosters, no account needed in CI), DigitalOcean and Hetzner (simplest REST, our core audience), deSEC, Route 53, Google, Azure (each heavier in authentication), and `acme-dns` as the eighth if time allows. Open questions: whether the AWS credential chain (instance profiles, IRSA) belongs in v0.6 or waits for a `credentials: ambient` option; whether to require `zone`/`hosted_zone_id` instead of label walking when a token may see many zones (saves rate budget, fewer ambiguous matches); and a published date for the legacy Hetzner DNS API shutdown.

## 6. Performance: runtime model and the plan from #181

Requirements in scope: H-PERF-01 (tunable runtime, `SO_REUSEPORT`, socket buffers), H-PERF-06 (allocator benchmarked), H-ENG-01/02. Issues [#176](https://github.com/Docker-Hunterpedia/ReverseDock/issues/176) (thread-per-core experiment) and [#181](https://github.com/Docker-Hunterpedia/ReverseDock/issues/181) (the v0.6 plan). Every fact was checked on 2026-11-06 against the source linked next to it; crate facts against the sources of the versions locked in `Cargo.lock` (pingora-core 0.9.0, pingora-runtime 0.9.0, tokio 1.53.3, rustls 0.23.46, mimalloc 0.1.52). Lines marked *(our reasoning)* are conclusions, not sources.

### 1. Where we start

- **Numbers** (2 CPUs, 1 GiB, k6 open model; [report](../../benchmarks/results/2026-11-02-small-cpu/report.md), [soak](../../benchmarks/results/2026-11-02-small-cpu/soak/report.md)): single-backend peak 24,619 req/s against NGINX 24,889 and HAProxy 31,895 (0.77×); 76 µs CPU per request at 10,000 req/s against NGINX's 56; p99.9 in `tls` 30.7 ms against 4.8; 0 % failed at the 40,000 target.
- Soak: 62 MiB RSS after 24 h (30 MiB before mimalloc); the longest requests were 5.0 s, one per backend stop. `perf` and `strace -c` show 2 to 2.6 `futex` calls and context switches per request (#176).
- **Runtime:** `rdock run` builds one `tokio::runtime::Builder::new_multi_thread().enable_all().thread_name("rdock")` with no `worker_threads`, so tokio starts one worker per CPU core ([run.rs](../../crates/rdock/src/run.rs) L28–31; [tokio runtime docs](https://docs.rs/tokio/1.53.3/tokio/runtime/index.html)).
- The admin API has its own runtime with `admin.threads` = 2 by default ([settings.rs](../../crates/rdock-model/src/settings.rs) L98–131); the soak counted 11 threads in all.
- **Listeners** (ADR-0012): one `tokio::net::TcpListener` per listener and one accept task per listener (`tokio::spawn(accept_loop(...))`, [listener.rs](../../crates/rdock-proxy/src/listener.rs) L207); every accepted connection is spawned into a `JoinSet` and so runs on whichever worker takes it (L254).
- Per connection: `connections_total` and `connections` label lookups, `set_nodelay`, the optional TLS handshake under the header timeout, then Pingora's `process_new` (L242–350). No `SO_REUSEPORT`, no socket-buffer options.
- **Upstream pool:** one `HttpProxy` per listener, built with `ServerConf { upstream_keepalive_pool_size: security.limits.upstream_idle_connections (4096, ADR-0023), max_retries: 16 }` (listener.rs L151–175).
- That pool is Pingora's single LRU shared by every worker; its cap is `upstream_keepalive_pool_size × threads`, and `threads` is 1 in our `ServerConf` ([connectors/mod.rs](https://docs.rs/crate/pingora-core/0.9.0/source/src/connectors/mod.rs) L92–96, L143–145).
- **Per request in our code:** `observe_request` on shared Prometheus atomics and one `live::Sample` for the admin ring buffers ([proxy.rs](../../crates/rdock-proxy/src/proxy.rs) L1104–1110); the access-log record is skipped when nobody reads it (#173).
- Downstream writes go through an 8 KiB user-space buffer flushed at the end of the response ([conn.rs](../../crates/rdock-proxy/src/conn.rs) L43–49, #174).
- **Timeouts:** `timeouts.connect` defaults to 5 s, `read`/`write` 60 s, `idle` 90 s ([service.rs](../../crates/rdock-model/src/service.rs) L329–336). The soak ran with `retries: { attempts: 2, on: [connect, reset] }` ([soak/rdock.yaml](../../benchmarks/soak/rdock.yaml) L19).
- **Build:** `profile.release` has `lto = "thin"`, `codegen-units = 1`, `strip = "symbols"` ([Cargo.toml](../../Cargo.toml) L180–183), no frame pointers: today's binary gives `perf` no call graphs.
- mimalloc is the global allocator ([main.rs](../../crates/rdock/src/main.rs) L11–15); rustls uses ring only and `deny.toml` bans `aws-lc-rs`/`aws-lc-sys` ([deny.toml](../../deny.toml) `[bans]`).

- How no-steal mode schedules: `current_handle()` returns the handle of a **random** thread of the pool (lib.rs L575–586). `start_service` spawns its accept tasks through it (listening.rs L287, L309) and `run_endpoint` spawns every accepted connection through it again (L232).
- So with `work_stealing: false` Pingora pins a *connection* to one thread, chooses that thread at random, and keeps the pool shared. A `TODO` at listening.rs L195–197 notes that reused connections should be re-spawned in no-steal mode. `get_runtime_at(index)` gives a deterministic per-thread handle (lib.rs L685).
- *(our reasoning)* Reusable: `pingora_runtime::Runtime::new_no_steal(n, "rdock")` (already a dependency) for N current-thread runtimes with per-thread handles, and `HttpProxy::process_new` unchanged.
- *(our reasoning)* Ours to build: one accept loop per thread on a per-thread `SO_REUSEPORT` socket (tokio [`TcpSocket::set_reuseport`](https://docs.rs/tokio/1.53.3/tokio/net/struct.TcpSocket.html#method.set_reuseport)) or a shared socket accepted from every thread; one `HttpProxy` per (listener, thread) so each thread owns its pool, which multiplies ADR-0023's 4096 by N unless divided; per-thread metrics shards aggregated at scrape; admin feeds and reload kept off the request path (ADR-0009, H-ENG-04).

### 3. Per-core models elsewhere

- **tokio:** `tokio::spawn` requires `Send + 'static` because a task may move between threads; `LocalSet`/`spawn_local` run `!Send` tasks on one thread but cannot be used inside `tokio::spawn` ([spawn](https://docs.rs/tokio/1.53.3/tokio/task/fn.spawn.html), [LocalSet](https://docs.rs/tokio/1.53.3/tokio/task/struct.LocalSet.html)).
- Pingora's `ProxyHttp` and sessions are `Send` anyway, so a per-core model gains from the missing cross-thread wake-up, not from dropped `Send` bounds. Tokio's scheduler notes that notifying a sibling worker is "expensive" and throttles stealers to half the workers ([tokio blog, 2019-10-13](https://tokio.rs/blog/2019-10-scheduler)); the 2–2.6 futex per request in #176 is that notification.
- **Linux `SO_REUSEPORT`** (since 3.9) lets several sockets bind one address to improve `accept(2)` load distribution; `SO_INCOMING_CPU` (settable since 4.4) sets a socket's CPU affinity; `SO_ATTACH_REUSEPORT_CBPF`/`EBPF` pick the socket with a BPF program (TCP since 4.6, `BPF_PROG_TYPE_SK_REUSEPORT` since 4.19) ([socket(7)](https://man7.org/linux/man-pages/man7/socket.7.html)).
- The kernel chooses the socket by a hash of the 4-tuple; changing the number of listening sockets could misroute a handshake's final ACK ([LWN, 2013](https://lwn.net/Articles/542629/)). `net.ipv4.tcp_migrate_req` (default 0) migrates child sockets to another listener after `close()` ([ip-sysctl](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html)). ADR-0012 keeps sockets of unchanged addresses across reloads, so this matters only when a listener is removed.
- **NGINX:** `listen ... reuseport` (1.9.1) creates one listening socket per worker process; `worker_processes auto`; `worker_cpu_affinity auto` (1.9.10); `rcvbuf=`/`sndbuf=` per listener; `backlog` 511 on Linux ([ngx_http_core_module](https://nginx.org/en/docs/http/ngx_http_core_module.html#listen), [ngx_core_module](https://nginx.org/en/docs/ngx_core_module.html)).
- **HAProxy 3.2:** `nbthread` defaults to the CPUs the process is bound to; `thread-groups` default 1, up to 64 threads per group and 16 groups; a `bind` line is one socket for all threads unless `shards <n> | by-thread | by-group` (default 1) or `tune.listener.default-shards`, which the manual says reduces "in-kernel locking on a single socket" at the cost of some CPU; `cpu-policy` default `first-usable-node`; `cpu-map` pins threads ([configuration manual 3.2](https://docs.haproxy.org/3.2/configuration.html) §3.1, §3.2, §5.1).
- **Envoy:** `--concurrency` defaults to the minimum of hardware threads, cpuset and cgroup CPU limit, so it honours `--cpus` ([CLI](https://www.envoyproxy.io/docs/envoy/latest/operations/cli)); listener `enable_reuse_port` defaults to true, one socket per worker ([listener.proto](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/listener/v3/listener.proto)).
- Envoy's threading model: every worker accepts on every listener, a connection is bound to one worker for its lifetime, and the kernel balances well "for most workloads" but not for "a small number of very long lived connections" ([threading model](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/intro/threading_model)).
- *(our reasoning)* For `slow` (100 ms backend) the kernel hash spreads k6's up to 4,000 connections evenly enough. The risk Envoy names, few long-lived connections pinning one core, is WebSocket and HTTP/2 traffic, which #176's gate must cover with a scenario of its own. `SO_INCOMING_CPU`/BPF steering is a later refinement, worth it only with RSS-aligned queues on bare metal.

| Traefik | `forwardingTimeouts.dialTimeout` 30 s | [serversTransport](https://doc.traefik.io/traefik/reference/routing-configuration/http/load-balancing/serverstransport/) |
| NGINX | `proxy_connect_timeout` 60 s (cannot exceed about 75 s); `proxy_next_upstream error timeout` | [ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_connect_timeout) |

- Envoy's `RetryPolicy`: `num_retries` default 1, `per_try_timeout` falls back to the route timeout, back-off base 25 ms and max 10× base, the `previous_hosts` predicate avoids the host already tried ([route_components.proto](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto)).
- Happy Eyeballs ([RFC 8305 §5](https://www.rfc-editor.org/rfc/rfc8305.html#section-5)): start the next attempt after a Connection Attempt Delay of 250 ms (minimum 100 ms, maximum 2 s) while earlier attempts continue in parallel. Envoy applies it to address families through `happy_eyeballs_config` (cluster.proto).
- **Why a stopped container costs a SYN timeout, not a RST:** a RST needs a host that answers. After `docker stop` the container's interface is gone, and the proxy's kernel re-resolves the stale neighbour entry with 3 unicast probes, then 3 broadcasts, 1 s apart (`ucast_solicit`, `mcast_solicit`, `retrans_time_ms`, [arp(7)](https://man7.org/linux/man-pages/man7/arp.7.html)).
- *(our reasoning)* So about 6 s pass before the neighbour is declared unreachable and the connect fails; our 5 s timer fires first, which is the 5.0 s the soak recorded.
- Without an application timer the SYN is retried `tcp_syn_retries` = 6 times, about 127–131 s ([tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html), [ip-sysctl](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html)).
- `TCP_USER_TIMEOUT` applies only in synchronized states, so not to SYN-SENT; `SO_SNDTIMEO` affects blocking `connect(2)`, not a non-blocking socket like tokio's; `TCP_SYNCNT` per socket limits SYN retransmits (tcp(7), socket(7)).
- *(our reasoning)* Three designs: (a) a shorter default, 3 s like Caddy, which still costs 3 s per stop; (b) a per-attempt connect budget when a retry is possible, for example 1 s on a non-final attempt when another backend exists and the full `timeouts.connect` on the last; (c) Happy-Eyeballs style: after a sub-delay start the connect to the next backend while the first continues, and take whichever completes.
- *(our reasoning)* (c) is fastest but needs a connect outside Pingora's `upstream_peer` flow and doubles backend connections under a flapping host. (b) fits ADR-0015 and `retries.on: connect` as they stand, keeps the different-backend rule, and meets #181's target (longest request under 1.5 s) with `attempts: 2`. Keep 5 s as the single-attempt default, documented with the Envoy source.

### 5. CPU per request: 76 µs against 56 µs

- Everything in our own path above 2 % of samples was fixed in #93 (report). What Pingora does per request: `RequestHeader::build` allocates an `http::HeaderMap` and a second `CaseMap` HeaderMap for original header-name case, `ResponseHeader` likewise ([pingora-http lib.rs](https://docs.rs/crate/pingora-http/0.9.0/source/src/lib.rs) L85–87, L170, L452–457, L510).
- The HTTP/1 server parses into a 256-entry `httparse` array and a 4 KiB `BytesMut` header buffer ([v1/server.rs](https://docs.rs/crate/pingora-core/0.9.0/source/src/protocols/http/v1/server.rs) L303, L334; `INIT_HEADER_BUF_SIZE` in common.rs L29); each L4 stream carries a 64 KiB read buffer and a 1,460 B write buffer ([l4/stream.rs](https://docs.rs/crate/pingora-core/0.9.0/source/src/protocols/l4/stream.rs) L363–370).
- In our code: `observe_request` atomics and the live sample (§1), both shared across workers, so every increment is a cross-core cache-line transfer.
- Cloudflare's numbers for Pingora are against its own NGINX-based service: "about 70% less CPU and 67% less memory", explained by sharing connections across all threads (connection reuse 87.1 % → 99.92 %) ([blog, 2022-09-14](https://blog.cloudflare.com/how-we-built-pingora-the-proxy-that-connects-cloudflare-to-the-internet/)). That is a connection-reuse win on a multi-tenant edge, not a per-request CPU claim; with one backend and 4,096 idle connections our lab already reuses every connection.
- **Method:** a `profiling` profile inheriting `release` with `debug = "line-tables-only"`, `strip = "none"` and `RUSTFLAGS="-C force-frame-pointers=yes"` ([rustc codegen options](https://doc.rust-lang.org/rustc/codegen-options/index.html)).
- `perf record -g --call-graph fp` on the proxy's cgroup at 10,000 req/s; `perf stat -e context-switches,cpu-migrations` for the futex count; `strace -c -f` for syscalls per request; each over the same 30 s window as `cpu.stat`. Budget per hot symbol as in #181 step 3.

### 6. TLS tail latency

- rustls `max_fragment_size: None` means the TLS maximum of 16 KiB per record; the docs say a value a little under the TCP MSS "may improve latency for stream-y workloads" ([server_conn.rs](https://docs.rs/crate/rustls/0.23.46/source/src/server/server_conn.rs) L310–317; default in builder.rs L111).
- Our 8 KiB write buffer sits above TLS (`ConnStream` wraps the handshaken stream, listener.rs L312–350), so a 1 KiB response is one plaintext write and one record.
- `send_tls13_tickets` defaults to 2 tickets after every TLS 1.3 handshake (builder.rs L123); the ring `Ticketer` rotates keys every 6 h with a 12 h ticket life ([ring/ticketer.rs](https://docs.rs/crate/rustls/0.23.46/source/src/crypto/ring/ticketer.rs) L20–33). Neither runs on a reused connection, so the `tls` p99.9 is not record sizing or tickets.
- rustls's own benchmarks (2024-01-04) find "best overall performance when used together with the aws-lc-rs cryptography provider instead of ring", and a ring upgrade that cost up to 21 % server-side handshake latency ([memorysafety.org](https://www.memorysafety.org/blog/rustls-performance/)).
- A third-party rerun puts aws-lc ahead by up to 67 % in bulk transfer and behind by up to 16 % in TLS 1.3 handshakes ([rustls-bench-results](https://github.com/aochagavia/rustls-bench-results), not an official source). aws-lc-rs stays banned (ADR-0013); the `tls-new` lead (5,821 against HAProxy's 3,227) shows ring is enough.
- *(our reasoning)* A 30.7 ms p99.9 at 10,000 req/s is one request in a thousand waiting for a worker; the plain-HTTP tail is within 2× NGINX, so the extra wait is specific to TLS reads or writes crossing workers (a read-ready wake on one worker, the task on the other). Record it with `perf sched latency` and `perf trace` before changing anything; if the no-steal runtime removes it, document that.

### 7. mimalloc

- The `mimalloc` crate 0.1.52 (libmimalloc-sys 0.1.49) builds mimalloc **v3.3.2** by default (`MI_MALLOC_VERSION 30302`) and v2 with the `v2` feature; the `secure` feature defines `MI_SECURE=4` ([build.rs](https://docs.rs/crate/libmimalloc-sys/0.1.49/source/build.rs) L9–11, L82), which the README prices at "around 10% on average" ([mimalloc readme](https://github.com/microsoft/mimalloc/blob/master/readme.md); v3.4.5 of 2026-08-05 is current).
- Options (readme): `MIMALLOC_PURGE_DELAY` (default 1000 ms in v3) delays returning freed memory to the OS; `MIMALLOC_ARENA_EAGER_COMMIT=2` (default) commits arenas eagerly on overcommit systems, i.e. Linux; `MIMALLOC_RESERVE_HUGE_OS_PAGES=n` reserves n GiB of 1 GiB pages at start; `MIMALLOC_ALLOW_LARGE_OS_PAGES=1` uses 2 MiB pages; `MIMALLOC_SHOW_STATS=1` prints what each heap holds at exit.
- The README's jemalloc comparison (sh6bench 2.5× faster than jemalloc) dates from 2021-01-30 on glibc, not musl; no newer official number exists.
- *(our reasoning)* 62 against 30 MiB: mimalloc keeps freed 64 KiB connection buffers in per-thread heaps (11 threads in the soak) and purges only after 1 s, while musl returned every buffer to the kernel at once, which is what cost 27 % of CPU. Measure `MIMALLOC_PURGE_DELAY=100` and `MIMALLOC_ARENA_EAGER_COMMIT=0` on the ladder; take them only at zero cost in µs per request (#181 step 7). `secure` is not for the data plane.

### 8. Lab for 4 and 8 CPUs

- In the 2-CPU lab, k6 on 4 CPUs sustained the 40,000 req/s target at about 32,000 completed with HAProxy ([compose.yaml](../../benchmarks/compose.yaml) L8–25, L85; report).
- k6's guidance is only "up to 80% used by k6, 20% idle", 1–5 MB per VU, `discardResponseBodies`, `ulimit -n 250000` and a full `ip_local_port_range` ([running large tests](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/)); it gives no requests per core.
- *(our reasoning)* That is about 8,000 req/s per k6 CPU. An 8-CPU ReverseDock near 90,000 req/s needs 12 k6 CPUs, 8 proxy CPUs and 4 to 6 backend CPUs, so a 16-vCPU machine covers the 2- and 4-CPU rungs but not the 8-CPU one.
- Hetzner, EU prices excluding VAT: cloud CCX43 16 dedicated vCPUs, 64 GB, €276.49/month or €0.4431/hour; CCX53 32 vCPUs, €0.8558/hour, about €21 a day ([general purpose](https://www.hetzner.com/cloud/general-purpose/)); dedicated AX102 Ryzen 9 7950X3D 16 cores, from €159/month plus €129 setup ([AX matrix](https://www.hetzner.com/dedicated-rootserver/matrix-ax/)).
- Docker: `--cpus` is a CFS quota (`--cpu-period`/`--cpu-quota`, throttled once the quota of a 100 ms period is spent); `--cpuset-cpus` limits a container to specific CPUs ([resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)).
- *(our reasoning)* Pin proxy, backend and k6 to disjoint `--cpuset-cpus` sets, avoiding sibling hyperthreads for the proxy, so the ladder measures cores and not CFS throttling; keep `--cpus` for the published 2-CPU numbers so they compare with v0.5.

### 9. Recommendation

*(our reasoning)* Try the cheap step first: keep our accept loops (ADR-0012) but run N `current_thread` runtimes through `pingora_runtime::Runtime::new_no_steal` (or tokio directly), one accept loop per runtime on a per-thread `SO_REUSEPORT` socket, and one `HttpProxy` per (listener, thread) with `upstream_idle_connections / N` as the per-thread pool. That is a few hundred lines behind a `runtime.model: steal | per_core` switch, and it answers #176's gate (futex per request < 0.5, single ≥ 0.9× HAProxy) before anyone touches metrics sharding or the admin feeds; if the gate passes, the per-thread metrics shards and a long-lived-connection scenario follow in the ADR. Connect budget: design (b), a per-attempt budget (1 s on a non-final attempt with another backend available, `timeouts.connect` on the last), defaulting to the existing 5 s for single attempts, with ADR-0015 amended rather than replaced; try (c) only if the soak still shows waits above 1.5 s. Measurement order: 1) the connect budget in the soak lab (small, independent); 2) a `profiling` build with frame pointers and a `perf record` baseline of `main` at 10,000 req/s, so step 3 has a before picture; 3) the per-core prototype on the full suite plus a WebSocket/long-lived scenario; 4) CPU per request against the budget per symbol; 5) the TLS tail, re-measured after 3; 6) mimalloc options; 7) the 4/8-CPU ladder on a 32-vCPU hourly server with `--cpuset-cpus`; 8) tighten `compare.py`.

### 2. The TLS database passthrough test

- libpq sets SNI by default: "If set to 1 (default), libpq sets the TLS extension 'Server Name Indication' (SNI)"; but "unless the proxy is aware of the PostgreSQL protocol handshake this would require setting `sslnegotiation` to `direct`" ([libpq-connect](https://www.postgresql.org/docs/17/libpq-connect.html)). `sslsni` arrived in PostgreSQL 14 ([commit 5c55dc8b](https://github.com/postgrespro/postgres/commit/5c55dc8b47338e72a4e598c155d2048d756fd10e)).
- `sslnegotiation=postgres` (default) sends an 8-byte SSLRequest first and waits for `S`; `direct` "start[s] SSL handshake directly after establishing the TCP/IP connection", "introduced in PostgreSQL version 17", allowed only with `sslmode=require` or higher; `sslmode` defaults to `prefer` ([libpq-connect](https://www.postgresql.org/docs/17/libpq-connect.html)). So with default clients a `HostSNI` route never sees a ClientHello; Traefik solves this with a Postgres STARTTLS detector, tested in `TestPostgresSTARTTLS` (sends `{0,0,0,8,4,210,22,47}`, expects `S`, then `tls.Client`) and `TestPostgresSTARTTLSPassthrough` ([tcp_test.go](https://raw.githubusercontent.com/traefik/traefik/master/integration/tcp_test.go)); caddy-l4 ships an `l4postgres` matcher ([modules](https://github.com/mholt/caddy-l4/tree/master/modules)).
- Traefik's fixture: `postgres:17-alpine`, `POSTGRES_HOST_AUTH_METHOD=trust`, an entrypoint that generates a self-signed certificate, `chown 70:70`, `chmod 0600`, then `docker-entrypoint.sh postgres -c ssl=on -c ssl_cert_file=/tmp/server.crt -c ssl_key_file=/tmp/server.key` ([tcp.yml](https://raw.githubusercontent.com/traefik/traefik/master/integration/resources/compose/tcp.yml)). PostgreSQL requires `server.key` at `0600` or root-owned `0640` ([ssl-tcp](https://www.postgresql.org/docs/17/ssl-tcp.html)); the image accepts `-c` options and `--user` ([image docs](https://github.com/docker-library/docs/blob/master/postgres/content.md)).
- Alternatives: Redis `tls-port 6379`, `port 0`, `tls-auth-clients no`, client `redis-cli --tls --cacert`; the TLS page never mentions SNI ([Redis TLS](https://redis.io/docs/latest/operate/oss_and_stack/management/security/encryption/)). Mosquitto `listener 8883` with `cafile`/`certfile`/`keyfile`; setting `cafile` is what switches a listener to TLS ([mosquitto-dev](https://eclipse.org/lists/mosquitto-dev/msg02209.html)). `openssl s_server -servername <name> -cert2 -key2` serves a second certificate for one SNI name ([openssl-s_server](https://docs.openssl.org/3.6/man1/openssl-s_server/)).

Pick *(our reasoning)*: the acceptance test is PostgreSQL 17 with `psql "sslmode=require sslnegotiation=direct host=db.example.test"` through an `rdock` `HostSNI` passthrough route to Traefik's `postgres:17-alpine` fixture (one container, `-c` flags, no volumes), asserting the server certificate's CN reaches the client untouched, plus a second route terminating TLS (M-L4-02) with the test CA from `rdock-testkit/src/certs.rs`. A companion case sends the default `sslnegotiation=postgres` and documents the outcome: either a clear diagnostic ("no TLS ClientHello; set sslnegotiation=direct or enable the postgres preface") or, if M-L4-01 grows a Postgres preface detector like Traefik and caddy-l4, a pass. Redis and Mosquitto add nothing SNI-specific; the pure SNI-routing matrix (two names, two backends, wrong name refused) runs against the testkit's own TLS backends with no container.

### 3. The static-file suite

- No conformance suite exists for static serving; `h2spec` covers RFC 7540/7541 only and was last pushed in October 2023 ([h2spec](https://github.com/summerwind/h2spec)). The suite is ours *(our reasoning)*: a table-driven `e2e_static.rs` on the existing `Rdock` harness, one fixture tree, rows of (request, expected status, expected headers, expected body bytes).
- Groups: ranges (single, multiple, suffix, unsatisfiable 416, `If-Range`, a `max_ranges`-style cap), conditionals (`ETag` + `If-None-Match` 304, `If-Modified-Since`, `If-Match` 412), precompressed sidecars (`.br`, `.zst`, `.gz` chosen from `Accept-Encoding`, with `Vary`), index and SPA fallback, hidden files, symlinks out of the root, traversal.
- Traversal payloads, each expected to yield 400 or 404 and never a byte from outside the root. From [WSTG-ATHZ-01](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/05-Authorization_Testing/01-Testing_Directory_Traversal_File_Include): `../`, `..\`, `%2e%2e%2f`, `%2e%2e/`, `..%2f`, `%2e%2e%5c`, `..%5c`, `%252e%252e%255c`, `..%c0%af`, `..%c1%9c` (overlong UTF-8 "only works in systems that are able to accept overlong UTF-8 sequences"), `....//`, `....\\`, `%00` before an extension, `file:///etc/passwd`. From [PortSwigger](https://portswigger.net/web-security/file-path-traversal): `/etc/passwd` (absolute), `....\/`, `%252e%252e%252f`, `..%ef%bc%8f`, `/var/www/images/../../../etc/passwd` (start-of-path validation), `../../../etc/passwd%00.png`.
- Path normalisation in the rules parser is already under `proptest` ([06-repo-layout §5](../06-repo-layout.md)); the static handler must resolve the final filesystem path and check it stays under the root after every decoding step *(our reasoning)*.

### 4. PROXY protocol tests

- Senders: socat's `PROXY:` address is an HTTP CONNECT client, not the PROXY protocol, and users were still asking for the feature in January 2026 ([cygwin list](https://sourceware.org/pipermail/cygwin/2026-January/259205.html)). Traefik's integration tests build headers with `github.com/pires/go-proxyproto` (`proxyproto.Header{…}.WriteTo(conn)`) for v1 and v2, in `TestProxyProtocolTrusted` and `TestProxyProtocolNotTrusted` ([proxy_protocol_test.go](https://raw.githubusercontent.com/traefik/traefik/master/integration/proxy_protocol_test.go)); go-proxyproto is Apache-2.0, v0.11.0 on 2026-02-06 ([pkg.go.dev](https://pkg.go.dev/github.com/pires/go-proxyproto@v0.11.0)). HAProxy sends v2 with `server … send-proxy-v2` and `send-proxy-v2-ssl` ([manual §5.2](https://docs.haproxy.org/3.2/configuration.html#5.2-send-proxy-v2)).
- Vectors from the spec: `PROXY TCP4 192.168.0.1 192.168.0.11 56324 443\r\n`, `PROXY UNKNOWN\r\n`, the 107-character limit, the 12-byte v2 signature, `LOCAL` vs `PROXY`, `AF_UNSPEC`, TLVs ([proxy-protocol.txt](https://www.haproxy.org/download/3.2/doc/proxy-protocol.txt)).
- Plan *(our reasoning)*: a 40-line v1/v2 encoder in `rdock-testkit` (vectors above) drives the positive cases (client IP in access log and `X-Forwarded-For`, v1 and v2, IPv4 and IPv6, `LOCAL`, TLVs ignored), plus one `haproxy:3.2` container with `send-proxy-v2-ssl` as the interoperability check and as the outbound receiver (`accept-proxy` on its bind) for M-L4-03 outbound. Negatives: a header from an address outside `trusted` closes the connection and increments a counter; a trusted peer that sends no header is rejected when the listener requires one; a truncated or over-long v1 line and a bad v2 signature are rejected; a plain client on a listener without PROXY configured is unaffected.

### 6. CI cost

Standard runners are free for public repositories and the `rust` job has a 30-minute budget today. Estimated additions per PR *(our reasoning, not measured)*: single-node swarm suite 3–5 min (init, pull `traefik/whoami`, scale and two rolling updates), Postgres passthrough and termination 1–2 min (`postgres:17-alpine` pull plus startup), static suite under 1 min, PROXY protocol unit cases seconds plus 1 min for the HAProxy container, DNS mocks seconds: 6–9 minutes, best placed in a new `e2e-l4-swarm` job that runs in parallel with `rust` rather than inside it. Moves to `weekly.yml` or the lab: the 3-node swarm with overlay and node drain, a 30-minute rolling-update loop counting 5xx, the dind experiment, and any test that needs `privileged`.

*(our reasoning)* The acceptance wording "3-node Swarm e2e" cannot be met on a standard runner, so the PR gate proves the provider logic on one node and the lab proves the network; "passthrough of a TLS database connection" is only honest with `sslnegotiation=direct` or a Postgres preface detector, and the note above makes that choice explicit for the design agent; the static and PROXY suites are ours to write and small; the DNS adapters reuse a harness that already exists.

## 9. What this means for v0.6 *(our reasoning)*

**Decisions to carry into the ADR** (one ADR for the L4 data plane and the Swarm provider; static files and the DNS adapters change the config model too, so they are sections of the same ADR unless it grows past a page each):
1. L4 stays on ADR-0012: a `tcp` listener is our accept loop with a different `serve()`; per connection: optional PROXY header (trusted sources only, required once trusted), optional `starttls: postgres`, ClientHello peek with our own parser in `rdock-tls`, route match with the existing grammar, passthrough or termination, `copy_bidirectional` under an idle timeout and a termination delay. PROXY protocol via proxy-header 0.1.3; the same parser feeds the real client IP on HTTP listeners.
2. Swarm: default `endpoint_mode: tasks` (changing the model's current `vip` default before it ships), events for services/nodes/networks/secrets/configs plus a 5 s task poll, deterministic network choice, our own `/tasks` fetch until bollard 0.22 exposes `networks_attachments`. One ACME replica or certificates as secrets; shared data dirs refused.
3. Static files as a terminal `static` middleware with a streaming `Reply`, `route.service` optional behind a terminal middleware, root opened once as a `cap_std::fs::Dir`, symlinks, dot-files, listings and multi-range off by default.
4. DNS: raw REST on the existing hyper-rustls client with SigV4 and RS256 helpers on ring; RFC 2136 on hickory-proto/net with `hmac-sha256` over TCP; a shared fake-API harness and one contract test every adapter runs.
5. Performance: Pingora's no-steal runtime with per-thread `SO_REUSEPORT` sockets and one `HttpProxy` per (listener, thread) behind a `runtime.model` switch, measured against #176's gate before anything deeper; a per-attempt connect budget (1 s on non-final attempts) as an amendment to ADR-0015.

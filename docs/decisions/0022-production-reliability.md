# ADR-0022: Production reliability: backend state, health, retries, limits, mTLS, JWT and tracing

- Status: accepted
- Date: 2026-10-29

## Context
v0.4 makes ReverseDock safe for busy production APIs (M-LB-01…10, M-TLS-01, M-SEC-01, M-RT-02…07, M-TM-01…07, M-OBS-01…03, M-L4-05, W-CF-07, W-CF-08, H-ENG-01…03). The configuration model already accepts most service settings (policies, `health`, `retries`, `sticky`, `split`, upstream client certificates, `observability.tracing`), and the gate of [ADR-0014](0014-http-semantics-v0-1.md) refuses them with "planned for v0.4". [Research](../research/v0.4-production-reliability.md) checked Pingora 0.9, the crates and the behaviour of Envoy, Traefik, NGINX, HAProxy and Caddy on 2026-10-29. Open questions: where backend state lives across reloads, what counts as a failure, how retries avoid amplification, which defaults are safe, how client certificates reach routes, and which libraries to use for JWT and tracing.

## Decision

**Backend state survives reloads.** A registry in `rdock-balancer`, keyed by service name and resolved address and shared by configuration generations through weak references (like the DNS cells), holds each backend's in-flight requests, passive-health record, active-health status and slow-start time. A reload that keeps a backend keeps its state; a removed backend's state is dropped with the last generation using it. The data plane reads and updates it with atomics and short locks; nothing on the request path waits on a probe or a provider ([ADR-0009](0009-provider-ownership-and-merge.md), [ADR-0012](0012-own-listeners-pingora-http-engine.md)).

**Balancing (M-LB-01…03).** Policies: `round_robin` (smooth weighted, default), `random`, `least_requests` and `least_conn` (both count in-flight requests per backend, weighted as `weight / (in_flight + 1)`; Pingora has no per-backend connection count, and with HTTP/1.1 one request holds one connection), `p2c` (two weighted random picks, fewer in-flight wins), and `ip_hash`, `header_hash`, `cookie_hash` (a ketama-style ring of our own with 160 points per unit of weight, weights capped at 100, and a fixed FNV-1a hash, so every instance maps a key the same way; a request without the header or cookie falls back to round-robin; Unix-socket backends hash by path, which `pingora-ketama` cannot). Traefik's `p2c`, `hrw` and `leasttime` map to `p2c`, `ip_hash` and `least_requests`. Sticky sessions (`sticky.cookie`) store `HMAC-SHA256(secret, backend address)` truncated to 16 bytes in hex, never the address itself; the secret comes from `sticky.cookie.secret` (a `${file:…}`/`${env:…}` reference) or is generated once and kept in `$RDOCK_DATA_DIR/sticky.key` (mode 0600); `previous_secrets` keeps old cookies valid during a key rotation. A cookie naming a backend that is gone or unhealthy falls back to the policy and is replaced. Cookies default to `Secure`, `HttpOnly` and `SameSite=Lax` (Traefik's default is neither secure nor HTTP-only).

**Health (M-LB-04, M-LB-05, M-LB-07, M-LB-09, M-L4-05).**
- *Active* checks run in a background task per service: `mode: http` (default; `https` follows the service scheme), `tcp` or `grpc` (`grpc.health.v1.Health/Check`, hand-encoded, healthy only on SERVING). Defaults: `interval` 10 s with ±10 % jitter, `timeout` 2 s, `healthy` 2, `unhealthy` 3, `expected_status` `200-399`, `method` GET, optional `hostname`, `headers` and `expected_body` (substring). Redirects are not followed. A new backend starts healthy, so a reload never empties a pool before the first probe.
- *Passive* health counts failures per backend: connect errors, timeouts, resets before response headers and, by default, 502/503/504 answers (`passive.statuses`). `failures` (5) within `window` (30 s) eject the backend for `ejection` (30 s), doubling on each consecutive ejection up to 300 s (Envoy's outlier detection). After the ejection, one request is let through (half-open); success closes the breaker, failure re-ejects. At most `max_ejection_percent` (50 %) of a pool is ejected at once.
- *When every backend is down*, `health.when_all_down: fail_open` (default) sends to all backends, as Envoy's panic mode and NGINX's single-server rule do: a broken health check must not cause a full outage. `fail_closed` answers 503 instead.
- *Slow start* (`slow_start`, off by default): a backend that becomes healthy ramps its weight linearly over the duration.
- *Backup pools* (`backup: true` on a backend) receive traffic only when no primary backend is healthy.
- *Circuit breaker* per service: `max_requests` (in-flight across the pool, default unlimited) and `max_connections_per_backend` (M-LB-08) answer 503 with `Retry-After` when reached. States (`closed`, `open`, `half_open`) are exported as metrics and in `rdock status`.

**Retries (M-LB-06).** Retries keep the rules of [ADR-0010](0010-retry-semantics.md) and [ADR-0015](0015-status-code-retries.md): idempotent methods unless `retry_non_idempotent`, a body that fits the 64 KiB replay buffer, never after the client saw a response. Connect failures are the exception to the method rule: nothing reached the backend, so they are retried for every method. `retries.on` takes `connect` (default), `reset`, `timeout`, `502`, `503` and `504`. Each retry goes to a different backend when one is available (the failed ones are excluded for this request). Backoff is fully jittered exponential from 25 ms, capped at 250 ms (Envoy). The **budget** allows retries while they are at most `budget_percent` (20 %) of the service's in-flight requests, with at least 3 concurrent retries always allowed, so a failing pool cannot be overloaded by retries. A 503 with `Retry-After` pauses that backend for that long (capped at 60 s); a 429 is passed through, because it usually limits one client rather than the backend. Pingora's `max_retries` is set to 16 and our per-request counter enforces `attempts`. The response carries the last real backend answer.

**Routing (M-RT-02…07).** `split` services run (weighted, nested up to 4 levels, with a cycle check), and a reload that changes weights is atomic. `mirror` on a route sends a copy of `percent` of requests to another service, without waiting, without the response, with bodies over 64 KiB not mirrored, bounded by a concurrency limit. `rdock validate` reports routes that can never match because an earlier route with the same listener and an equal or broader rule always wins (shadowed routes). `grpc_web` (middleware) converts gRPC-Web to gRPC with Pingora's module.

**Limits (M-TM-01…07).** `rate_limit.key` gains `header:<name>`, `cookie:<name>`, `claim:<name>` (after `jwt`) and `route` besides `ip`; answers are 429 with `Retry-After`. `in_flight` (Traefik `inFlightReq`) caps concurrent requests per key, with an optional queue (`queue`, `queue_timeout`) instead of an immediate 429. `limits.max_in_flight` sheds load globally with 503 and `Retry-After`. `bandwidth` limits response bytes per second per route or client. `buffering` reads the whole request body before proxying (up to `max_body`), for slow uploads to fragile backends. Routes gain `max_body` and `timeouts.idle`. `compress` gains brotli and zstd through Pingora's encoders, negotiated by q-value, with `min_size` and content types.

**Client certificates (M-TLS-01, W-CF-08).** A TLS listener takes `tls.client_auth: { mode, ca }`. `mode` is `optional` (verify a certificate if one is sent) or `required`; a certificate is always verified against `ca` (PEM files, or `cloudflare` for the built-in Authenticated Origin Pulls CA). Modes that accept unverified certificates are not offered: they are unsafe and nothing needs them. A route on an `optional` listener can demand a certificate with the `client_cert` middleware (`required: true`, optional `subjects`/`sans` patterns), answering 403. The `client_cert` middleware also forwards the identity, in Traefik's `X-Forwarded-Tls-Client-Cert(-Info)` format or Envoy's XFCC; incoming copies of these headers are always removed. The docs follow Cloudflare's advice to prefer zone-level or per-hostname AOP with your own certificate over the shared global one. Upstream mTLS (`services.<s>.tls.cert_file`/`key_file`) is parsed and checked at load time and passed to Pingora's `client_cert_key`.

**JWT (M-SEC-01).** The `jwt` middleware verifies JWS tokens with our own verifier on ring (no JWT crate has a ring backend; see the research). Keys come from `jwks_url` (fetched in the background, cached for 10 minutes, refreshed early on an unknown `kid` at most every 30 s; a request never waits for a fetch), `jwks_file` or inline `keys`. Each key is pinned to one algorithm (from the JWK's `alg`, or its type), `algorithms` is an allowlist (default: RS256, ES256, EdDSA), and `none` and HMAC with public keys are impossible. `issuer` and `audiences` are required unless explicitly set to `any` (RFC 8725 §3.8–3.9). `leeway` is 60 s. The token comes from `Authorization: Bearer` by default, or a header, cookie or query parameter. `claims_to_headers` copies claims to request headers after clearing any client-supplied copies; `forward_token` (default true) keeps the token for the backend.

**Tracing and observability (M-OBS-01…03).** `opentelemetry` / `opentelemetry_sdk` / `opentelemetry-otlp` 0.33 with `http-proto` over our hyper-rustls client (no tonic, no reqwest). One server span per request named `{method} {route}` with the stable HTTP semantic conventions, one client span per upstream attempt with `http.request.resend_count`, W3C `traceparent`/`tracestate` propagation, parent-based sampling with `sample_ratio`; `OTEL_*` environment variables are honoured where they do not conflict with the file. Export is batched off the request path and drops spans when the collector is slow. Metrics gain per-backend request, failure and latency series (label values come only from the configuration, so cardinality is bounded), health and breaker states, and retry and budget counters. `access_log.sample` logs a share of successful requests and every error.

**Cloudflare Load Balancing (W-CF-07).** `listeners.<l>.ping: <path>` answers `200 OK` on that path for any `Host` before routing, for Cloudflare monitors and other load balancers.

**DNS discovery (M-LB-10).** Backend names are resolved with `hickory-resolver`, honouring record TTLs (bounded to 1 s … 5 min), and `srv://_service._proto.name` backends use SRV records with their weights and ports.

**Benchmarks and chaos (H-ENG-01…03).** `bench/` holds scripts and identical configurations for ReverseDock, NGINX, Traefik, Caddy and HAProxy, run with constant-rate load (oha and h2load), and the published report lists hardware, versions and command lines. A chaos suite in the test kit drives toxiproxy (latency, resets, partial outages, flapping backends) and asserts the documented behaviour; it runs in CI behind `RDOCK_CHAOS_TESTS=1`.

## Consequences
- The v0.4 gates go away feature by feature; until a feature lands, its settings stay refused.
- New dependencies: `ring` as a direct dependency (already built for rustls), `opentelemetry`, `opentelemetry_sdk`, `opentelemetry-otlp`, `prost` (through the exporter). No new crypto backend.
- The JWT verifier is security-critical code of our own; it gets fuzzing and test vectors from RFC 7515/7518/8037.
- Traefik label translation gains health checks, sticky cookies, `p2c`/`hrw`/`leasttime`, retries, `inFlightReq`, `passTLSClientCert` and `circuitBreaker` (as passive health and `max_requests`; arbitrary expressions are reported as not carried over).
- Bodies over 64 KiB are never retried or mirrored, because Pingora's replay buffer is fixed.

# ADR-0032: HTTP/3 ingress on quinn and h3 with our rustls configuration, experimental and feature-gated

- Status: accepted
- Date: 2026-11-13
- Supersedes: [ADR-0006](0006-http3-separate-track.md)

## Context

ADR-0006 put HTTP/3 in a separate BoringSSL build on `tokio-quiche` with an internal h2c hop, because "a rustls build cannot host quiche" and Pingora's server `Session` was H1/H2 only. [Research](../research/v0.9-scale.md) on 2026-11-13 found that two of those facts changed:

- **quinn 0.11.12 with h3 0.0.8 and h3-quinn 0.0.10 builds on rustls 0.23 with ring only**, on Rust 1.89, adding 7 crates whose licences `deny.toml` already allows. A probe served a request through a forced Retry. quinn's server passes the QUIC interop runner's tests it supports against seven clients (run of 2026-11-12).
- **Pingora's `Session` has had a `Custom` variant since 0.7.0**, and `HttpProxy::process_new_http` accepts a session from our own accept loop. The trait is hidden API.
- `tokio-quiche` 0.23.0 is still BoringSSL only: 90 more crates, cmake, a C++ compiler and libclang in the build, a dynamically linked C++ runtime that a static musl build must replace, and a second TLS stack with its own certificate resolver. Pingora has shipped no HTTP/3 and names no date.
- **The weak point is the `h3` crate**: its README calls it experimental, its last release is 18 months old with fixes unreleased on its main branch, its compliance report leaves intermediary validation (RFC 9114 §4.1–4.3) to the user, and issue #379 (header-count panic) is open. `max_field_section_size` is unlimited by default.
- Published attacks on HTTP/3 front ends abuse header decompression and one origin connection per stream held open by trickled data.

## Decision

- **Stack:** `quinn`, `h3` and `h3-quinn` on the `rustls::ServerConfig` and certificate resolver the HTTPS listener already uses, behind the cargo feature `http3`, **off by default and not in release binaries or images** while experimental. One artifact; no BoringSSL. A build without the feature refuses `http3.enabled: true` with a diagnostic, as `type: wasm` is refused.
- **Shape:** an HTTP/3 request stream enters the normal pipeline as a Pingora custom session, so the router, middlewares, cache and access log are the ones HTTP/1 and HTTP/2 use. If the custom-session path does not pass its spike (streaming upload, trailers, client reset mid-body, upstream retry, cache), the fallback is an in-process duplex stream carrying a validated HTTP/1.1 request; a socket hop is not used. `h3` sits behind a thin internal trait.
- **We validate, not h3:** pseudo-headers, field names and values, connection-specific fields, `Content-Length` against the data received, and the `:authority` form are checked before a request reaches the pipeline; a malformed request is reset, never forwarded. `max_header_size` is always set (default 64 KiB, hard ceiling 1 MiB, which also stays below the header-count panic). The mapping has a fuzz target.
- **Configuration** on the `https` listener, which then owns the UDP socket on the same address (a `udp` listener there is refused):
  `http3: { enabled: false, advertise: true, advertise_max_age: 1h, advertise_port, retry: auto | always | never, max_idle: 30s, max_concurrent_streams: 100, max_header_size: 64KiB, max_connections, max_connections_per_client, congestion: cubic | newreno | bbr, gso: true, qlog }`.
  `retry: auto` starts sending Retry at 100 half-open connections (HAProxy's threshold). `Alt-Svc` is added to the listener's HTTP/1 and HTTP/2 responses when `advertise` is on.
- **Refused as planned:** HTTP/3 to backends, 0-RTT, active connection migration, datagrams, WebTransport, CONNECT-UDP, WebSocket over HTTP/3, server push, PROXY protocol on the QUIC socket, Gateway API exposure.
- **Reloads and upgrades:** QUIC connections do not move between processes. On a listener replacement or a binary upgrade (ADR-0031) the old side sends GOAWAY, drains for a bounded time and closes; the stateless-reset and token keys are stored in the data directory so the next process answers old connections with a reset and accepts old tokens.
- **Proof:** an in-tree quinn and h3 client in the testkit for end-to-end tests (Retry, large bodies, trailers, reset, GOAWAY on reload, `Alt-Svc`, fallback when UDP is closed); a non-required CI job `http3` that also runs curl with HTTP/3 from a pinned image and a malformed-request suite built on Cloudflare's h3i outside the workspace.

## Consequences

- H-PERF-05, the roadmap's v0.9 line and the architecture and layout documents name quinn and h3 instead of `tokio-quiche` and BoringSSL. There is no `rdock-h3` artifact.
- The feature rests on an experimental crate and on hidden Pingora API. It leaves "experimental" only after an `h3` release that contains the unreleased fixes, an interop run, and a soak. `deny.toml` keeps refusing git sources; we do not pin `h3` to a commit.
- quinn has had nine advisories in 2024–2026, all denial of service and all fixed; version bumps must be prompt.
- One QUIC endpoint per listener bounds UDP throughput; per-thread sockets with connection-ID routing are later work.
- HTTP/3 upstream still waits for a Pingora connector.

## As implemented (v0.9 step 8)

- **Path: the Pingora custom session.** The spike the decision names passed on the custom-session path, so the duplex fallback was not built. Evidence, all in `crates/rdock/tests/e2e_http3.rs` through `RdockProxy` unchanged apart from one helper that reads the TLS facts: an 8 MiB upload in 64 KiB DATA frames streams to an HTTP/1.1 backend (chunked without `content-length`, passed on with it); response trailers from an h2c backend reach the HTTP/3 client; a client reset mid-body ends the upstream request (the backend sees its connection close) and the QUIC connection keeps serving; a refused backend is retried on the next one, and a `502` is retried with the request body replayed from the retry buffer; the cache serves the second request and a `rate_limit` limits the fourth. The session (`rdock-proxy/src/http3/session.rs`) implements every method of `pingora::protocols::http::custom::server::Session` 0.9.1 except the cancel-safe proxy-task API, which stays disabled (`proxy_tasks_enabled` is `false`, so Pingora never calls the panicking defaults). Pingora's `SslDigestExtension::set` is crate-private, so the handshake facts travel in the request's extensions and `proxy.rs` reads them through one helper, only for custom sessions.
- **Our own decoding and validation.** h3 0.0.8's QPACK decoder is private and folds pseudo-header fields into an `http::Request` with the last duplicate winning, so order, duplicates and `:status` cannot be checked after it. rdock reads the HEADERS frame itself (through h3's `i-implement-a-third-party-backend-and-opt-into-breaking-changes` feature, which exposes the frame types; h3 is pinned with `=`), decodes it with its own static-table QPACK decoder (RFC 9204; Huffman from RFC 7541 Appendix B, canonical code built from the lengths; integers above 2^32 refused; dynamic references refused as rdock announces no table) and checks it (`rdock-proxy/src/http3/request.rs`): only `:method`, `:scheme` (`https` only), `:authority`, `:path`; each once; before regular fields; `:status`, `:protocol` and unknown ones refused; `CONNECT` refused; lowercase `token` names; values without NUL, CR, LF, other controls except HTAB, or surrounding whitespace; `connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `upgrade` refused, `te` only `trailers`; `:authority` or `host`, equal when both, one `host`, no userinfo, `host[:port]`; origin-form path or `*` for `OPTIONS`, visible ASCII, no fragment; one numeric `content-length`, held against the DATA received by the session. `cookie` fields are joined for HTTP/1.1. A malformed head resets the stream with `H3_MESSAGE_ERROR`, a section over `max_header_size` gets `431`, a QPACK error closes the connection with `QPACK_DECOMPRESSION_FAILED`; each is counted in `rdock_http3_malformed_requests_total{listener,reason}` and none reaches the pipeline. A `content-length` mismatch is found only as DATA arrives, after the valid head went upstream: the stream is reset and the upstream request abandoned, so the backend never gets a complete request. h3 then decodes the same frame again (same limit) to build its request stream; a disagreement is counted as reason `h3`. The mapping is always compiled (also without the feature), unit-tested in the required `rust` job and fuzzed (`tests/fuzz`, target `http3_request`: no panic, decode-encode round trip, and the forwarded HTTP/1.1 head parses back with `httparse` as exactly one head with the same method, target and field count). The fuzz crate now depends on `rdock-proxy` (26 more crates in its lock file, all at the main lock's versions).
- **Settings, defaults and bounds** (`listeners.<l>.http3`, `https` listeners only; validation errors outside the bounds): `enabled` false; `advertise` true; `advertise_max_age` 1 h, whole seconds from 1 s to 30 d; `advertise_port` the listener's, 1–65535; `retry` `auto` (Retry while 100 or more handshakes are in progress), `always`, `never`; `max_idle` 30 s, 1 s–10 min; `max_concurrent_streams` 100, 1–10,000; `max_header_size` 64 KiB, 1 KiB–1 MiB (always passed to h3 as `max_field_section_size`); `max_connections` 10,000, 1–1,000,000; `max_connections_per_client` 100, 1–`max_connections` (the two connection defaults are our choice, no external source); `congestion` `cubic` (`newreno`; `bbr` with a warning, quinn marks it experimental); `gso` true. With `enabled`, a `udp` listener on an overlapping address is refused. Not configurable: stream receive window 1 MiB, connection window 4 MiB, 16 unidirectional streams, datagrams off, migration off, NEW_TOKEN tokens not sent (quinn without its `bloom` feature), Retry-token lifetime quinn's 15 s.
- **Abuse bounds.** Connections: the two limits, checked on `Incoming` before any handshake work (refused with `CONNECTION_REFUSED`); handshake within `timeouts.request_header`; anti-amplification is quinn's (RFC 9000 §8.1, at most three times the bytes received before validation). Headers: the HEADERS frame within `timeouts.request_header`, the decoded section within `max_header_size` (decoding stops as soon as it passes; 1 MiB also keeps a section below the 32,768 fields that panic `http::HeaderMap`, h3 issue #379); QPACK has no dynamic table. Resets: more than `max(100, max_concurrent_streams)` streams reset by the client, cut short or refused as malformed within 10 s close the connection with `H3_EXCESSIVE_LOAD` (counted as `reset_flood`). Bodies: `timeouts.read` between DATA frames and, after the first `timeouts.read`, at least 1 KiB/s on average, so a trickling stream cannot hold its upstream connection. Tested: the header-size limit (431 and nothing forwarded), the reset flood (150 cut-short streams close the connection with `0x107`), the malformed cases, the content-length cases; not tested end to end: the slow-body floor (unit-tested), the connection limits and the handshake deadline.
- **Refused as planned** (gate, `status.json`): `scheme: h3` on services, `http3.early_data`, `migration`, `datagrams`, `webtransport`, `extended_connect` (WebSocket over HTTP/3 and CONNECT-UDP), `qlog` (quinn's `qlog` feature pulls qlog 0.15, which turns on serde_json's `preserve_order` for the whole binary), `http3.enabled` with `proxy_protocol` on the listener, and with `tls.fingerprint` (no ClientHello is read for QUIC connections, so fingerprint rules would be bypassed). 0-RTT is off in the configuration (`max_early_data_size` 0; quinn accepts early data only at `u32::MAX`) and a test proves a resuming client's early data is not accepted. Server push is never sent (no setting). Gateway API exposure has no setting. Request trailers are read and dropped: Pingora's custom session has no way to pass them upstream.
- **Reloads and upgrades.** Each `https` listener with HTTP/3 has a side next to it in `DataPlane`. A reload that changes HTTP/3 settings or TLS updates the endpoint in place (new connections); one that removes the listener, moves it or turns HTTP/3 off stops the side: no new connections, GOAWAY on every connection, requests in flight may finish for the reload drain but at most 10 s, then the endpoint closes. h3 0.0.8's `accept` ends after GOAWAY only once the client has sent one too, so a connection ends when its last request does. A side binds its UDP socket in the background and retries every 250 ms while the port is busy (a stopping side, the previous process in an upgrade, or anything else), so HTTPS never waits for it and `Alt-Svc` appears only once the endpoint serves. Keys: `<data dir>/quic.key` (two 32-byte hex keys, created with `write_atomic`, mode 0600). The upgrade path is not covered by an end-to-end test.
- **Observability.** Access log `proto: "HTTP/3"`, SNI and `tls_version: "TLSv1.3"`; `tls_cipher` is `unknown` (quinn does not expose the negotiated suite). Metrics: `rdock_http3_connections_total`, `rdock_http3_connections`, `rdock_http3_retries_total`, `rdock_http3_connections_closed_total{reason}` (`idle`, `client`, `drained`, `limit`, `client_limit`, `handshake`, `protocol`, `reset_flood`), `rdock_http3_malformed_requests_total{reason}`, `rdock_http3_requests_total{status_class}`. `rdock version` prints `HTTP/3: quinn and h3 (experimental)` or `not in this build` (and `"http3"` in `--json`, a line the default build now prints too). Each side that starts logs one warning that HTTP/3 is experimental.
- **Dependencies.** `quinn` 0.11.12 (no default features; `runtime-tokio`, `rustls-ring`), `h3` 0.0.8, `h3-quinn` 0.0.10; with `quinn-proto` 0.11.19, `quinn-udp` 0.5.16, `lru-slab` 0.1.3 and `rand_pcg` 0.10.2 that is 7 crates on Linux, plus `web-time` 1.1.0 for wasm targets only (the research's count was right). Licences MIT OR Apache-2.0 (quinn crates), MIT (h3, h3-quinn), MIT OR Apache-2.0 OR Zlib (lru-slab); `cargo deny check` (which builds the all-features graph) passes; no aws-lc, no git source. The default build's graph has none of them (optional dependencies only). The release-binary size with the feature was not measured.
- **Proof and CI.** `e2e_http3` (13 tests) with the testkit's quinn and h3 client (`rdock-testkit` feature `http3`, which also has a raw mode for frames h3's client refuses to build). The non-required CI job `http3` runs `just http3` and `scripts/http3-curl.sh`. `curlimages/curl` has no HTTP/3 (its Makefile configures `--with-openssl --with-nghttp2` only, read 2026-11-13), so the script uses curl from `debian:trixie-20261027-slim` pinned by digest (Debian 13's curl 8.14.1 is built `--with-openssl-quic --with-nghttp3`, `debian/rules` of 8.14.1-2+deb13u7 read 2026-11-13); that step could not run in the development sandbox and is unverified. The h3i suite is not built: it needs quiche and BoringSSL in its own crate and could not be made self-contained in the job; it stays planned, and so does a QUIC interop-runner image.
- **What the research or this ADR had wrong.** (1) The h3 weak point is larger than "leaves intermediary validation to the user": its decoded field list is not reachable without the opt-in feature, hence our own decoder. (2) h3's server `accept` does not finish after our own GOAWAY. (3) Pingora's HTTP/1 upstream path synthesises `Host` from the URI only for HTTP/2 downstream requests, so the mapping sets `Host` itself. (4) The `qlog` option in the configuration sketch cannot be offered on quinn 0.11 without a global serde_json behaviour change. (5) curl's official image has no HTTP/3.

# ADR-0030: v0.8: an HTTP cache on pingora-cache with our own stores, a phased pipeline with native plugins and HTTP agents, consumers and API keys, OIDC login, UDP routes, and what waits

- Status: accepted
- Date: 2026-11-11

## Context
v0.8 carries the HTTP cache (F-WEB-03), extensibility (F-EXT-01…05), API-gateway features (F-GW-01…05), Cloudflare Access (W-CF-06), UDP (M-L4-04, and `UDPRoute` left open by v0.7), buffering (M-TM-05), directory listing (F-WEB-02), a Terraform/OpenTofu provider (F-MGMT-02) and Vault and External Secrets (W-OBS-02). [Research](../research/v0.8-cache-extensibility.md) checked the facts on 2026-11-11. The findings that shape this decision:
- `pingora-cache` 0.9.0 is already compiled into every build, is alpha (three breaking changes in 0.9.0), takes everything as `&'static`, and ships no usable store: `MemCache` is documented as for testing and there is no disk backend. It supplies mechanism (state machine, lock, Vary slots, ranges, 304 handling, purge); policy is ours. Its old path-only default key was CVE-2026-2836.
- Stale-while-revalidate runs a background subrequest through our whole request pipeline.
- `http-tests/cache-tests` runs with Node and calls itself "not a conformance test suite".
- The `Middleware` trait has `request` and `response` only. Pingora's `response_body_filter` is synchronous. Pingora 0.9 can hold a request body only after the backend is connected, and replays at most 64 KiB; the hook that buffers before a backend is chosen is merged upstream and unreleased.
- Pingora 0.9.1 removes the panic that pins tokio below 1.54.
- Rust has no stable ABI; `linkme` needs unsafe; release builds unwind. wasmtime 36 LTS is the only wasmtime line MSRV 1.89 allows (48 crates, support ends in 2027). No open, container-distributed Coraza server for `ext_proc`/`ext_authz` was found; the CRS project publishes reverse-proxy images. `sigstore-verify` needs aws-lc-rs; `minisign-verify` is one crate.
- High-entropy API keys need a fast hash, not a password hash. `josekit` needs OpenSSL, `jsonwebtoken` has no ring backend, `openidconnect` pulls `rsa` with an open advisory. `jsonschema` without default features brings no network stack. The IETF `RateLimit` headers are a draft.
- `GATEWAY-UDP` has nine tests against a UDP echo. Both Terraform registries require a public repository named `terraform-provider-<name>`. External Secrets Operator, the CSI driver and Vault Agent all end in files or native Secrets. `vaultrs` requires reqwest; Vault is BUSL, OpenBao is MPL-2.0.
- Status-code retries already ship (ADR-0015).

## Decision

### Order and what "v0.8" means
The work lands in this order, each step leaving the workspace green: Pingora 0.9.1 and the tokio cap → the phased pipeline and body phase → UDP and UDPRoute → directory listing → the cache → plugin API, SDK and agents → consumers, API keys, limits, metering, envelope, Cloudflare Access → request buffering, validation and JSON Patch → OIDC login → `${vault:…}` and secrets documentation → the Terraform provider source → WASM (experimental). The roadmap's four proofs (cache suite, stampede test, SDK with two examples, WAF agent example) come from steps that add no dependency. A step that does not reach its tests is left out with a "planned for" diagnostic and the roadmap says so; nothing ships half-wired.

### Pingora 0.9.1
`pingora` moves to 0.9.1 (exact minor pinned as before) and the `tokio <1.54` cap is removed only if the whole suite, including the e2e connection tests that caught the original panic, passes on the newest tokio 1.x the lockfile resolves; otherwise the cap stays and the reason is recorded.

### Pipeline and body phase (F-EXT-01)
- The chain gains phases `upstream_request` (after the backend is chosen, before the request is sent), `request_body`, `response_body` and `log`, beside `request` and `response`. A middleware declares the phases it uses and whether it needs the request body; a route whose chain needs none pays nothing.
- **Request bodies are held, not pre-buffered.** A middleware that needs the body gets it through one shared holder that collects chunks in `request_body_filter` up to a limit (`hold_body.max`, default 1 MiB, at most 64 MiB because the whole body is read back into memory when it is released, never above the route's `max_body`) and within a time (`hold_body.timeout`, default 30 s, then `408`), in memory up to 64 KiB and then in an unlinked `0600` spool file in the data directory. The backend connection exists by then, and nothing of the body is forwarded until every body middleware has answered; a rejection aborts the upstream request. The request head has left before the body is known, so the client's framing is kept (a chunked upload stays chunked), and a chain with a middleware that may replace the body drops `Content-Length` (HTTP/1.1 chunked, HTTP/2 stream framing). The setting is named for what it does (`hold_body`), and the docs say it does not shield backend workers from slow uploads. True pre-buffering (M-TM-05 in full) waits for the upstream hook; M-TM-05 stays open with that note.
- `response_body` is synchronous by Pingora's design: it can transform and count, not await. Phases that would need to await there are refused at validation.
- Order is explicit: within a phase, middlewares run in the route's list order on the way in (`request`, `upstream_request`, `request_body`) and in reverse on the way out (`response`, `response_body`, `log`), and `rdock explain` prints the phases.

### Native plugins and the SDK (F-EXT-02, F-EXT-05)
- A new crate `rdock-plugin-api` is the only thing a plugin depends on: `http`-crate types, a `Plugin` trait with the phases above, a typed per-request state slot, a `Factory` that builds a plugin from its YAML configuration and reports diagnostics, and nothing from Pingora. It is `0.x` and `#[non_exhaustive]` where it can be; the stability promise starts at 1.0.
- Plugins are compiled in: a user binary lists its factories in an explicit registry and calls `rdock::run(registry)`; `rdock` gains a library target for this. No `dlopen`, no link-time registration (no unsafe). A cargo template and a test harness (`rdock-plugin-api::testing`) make the SDK; two examples are built and tested in CI: `header-rewrite` and `ip-blocklist`.
- A plugin is used as `middlewares.<m>: { type: plugin, name: <registered name>, config: {…} }`. An unknown name is a validation error naming the registered ones. A panic inside a plugin is caught, counted (`rdock_plugin_panics_total{plugin}`) and answers 500 for that request only.
- Plugins run with the proxy's privileges; the docs say so first.
- *Amended at implementation:* the API's heads are owned `http`-typed views (`RequestHead`, `ResponseHead`) that the adapter writes back only when the plugin changed them; framing headers (`Content-Length`, `Transfer-Encoding`, hop-by-hop) cannot be set by a plugin. A panic in `request`, `upstream_request` or `request_body` answers 500; in `response` the head is replaced by a 500 before it leaves; in `response_body` the head is gone, so the chunk passes unchanged; in `log` it is only counted. `rdock` is a library whose `run(registry)` is the whole command line; it sets mimalloc as the global allocator behind a default feature, so a custom binary behaves like the stock one. `rdock version` prints the plugin API version and the registered plugins.

### Agents (F-EXT-04) and the WAF example
- `type: agent` calls an out-of-process service over HTTP on the existing client: the request line and an allow-list of headers, and the held body up to `max_body` (default 64 KiB; above it the configured `on_oversize: skip | reject`), go to the agent; its answer is `allow` (optionally with header changes from an allow-list) or a response to send. Defaults: `timeout: 1s`, **`on_error: deny`** (fail closed), a circuit breaker that opens after consecutive failures and then applies `on_error` without calling, metrics per agent.
- The agent contract is two shapes behind one setting: `protocol: rdock` (a small JSON document, specified in the docs) and `protocol: forward` (the request is replayed to the agent as an ordinary HTTP request and a 2xx means allow), which is what a WAF reverse-proxy image understands.
- **WAF example:** a Compose file runs a CRS project image (pinned by digest) as a `forward` agent; a CI smoke test proves a clean request passes, an attack pattern is refused with 403, and a stopped agent refuses requests. gRPC `ext_proc`/`ext_authz` and SPOP are not built; `protocol` refuses them as planned.
- *Amended at implementation:* `protocol` defaults to `rdock`; `on_oversize` defaults to `reject` (413), and `skip` applies only to a declared length (a chunked body that grows past `max_body` is refused with 413, because rdock cannot pass on what it has held without holding all of it). Failures answer 502, 504 on timeout and 503 while the breaker is open. The headers sent to the agent are an allow-list (`accept*`, `cache-control`, `content-type`, `origin`, `referer`, `user-agent`, plus `request_headers`; `["*"]` for all): credentials and cookies go only when listed. A request without a body (or whose body is not sent) is decided in the `request` phase, before routing; one with a body in `request_body`, after its head went to the backend, so the agent's header changes apply only in the first case and are counted as `too_late` otherwise; client copies of those headers are removed in both. For this the middleware context learns whether the request has a body (`has_body`) and a body middleware may waive its hold for one request (`waive_body_hold`).

### WASM and signatures (F-EXT-03, F-EXT-05) — experimental, last
Behind cargo feature `wasm` (off by default): wasmtime 36 LTS, our own WIT world mirroring the plugin phases, a fresh instance per request, fuel and epoch limits, a memory cap, capabilities `log`, `clock`, `random` only. Modules are loaded from files with a mandatory `sha256` and a minisign signature against keys pinned in the configuration; `allow_unsigned: true` is the only way around it and warns. If this step does not reach its tests it moves to the next milestone and the requirement stays open.

### HTTP cache (F-WEB-03)
- New crate `rdock-cache` owns every use of `pingora::cache`: policy as pure functions, the stores, the tag index, metrics.
- **Configuration:** top-level `caches.<name>` (a store: `memory` with `max_size`, or `disk` with `path`, `max_size`, `max_objects`) and a `cache` middleware that names a store. Stores are process-lifetime objects: adding one applies on reload, changing or removing one needs a restart and is diagnosed. Policy on the middleware reloads freely.
- **Safe defaults:** off unless a route has the middleware; **no default TTL** (only what the origin's headers allow, heuristic freshness off); `GET` and `HEAD` only; never stored: responses with `Set-Cookie`, `Cache-Control: private` or `no-store`, `Vary: *`, responses to requests with `Authorization` unless the origin says `public`/`s-maxage`/`must-revalidate`, requests with a body; `max_object_size` 64 MiB; statuses 200, 203, 204, 206 (as ranges of a stored 200), 300, 301, 308, 404, 410 only with explicit freshness. Each has its opposite as an explicit setting (`default_ttl` per status, `heuristic_freshness`, `statuses`, `set_cookie: strip`, `authorization: store`, `request_directives: ignore`, `lock.enabled: false`, `tags.keep`, `cache_status: false`), except `no-store`, `private`, `Vary: *`, methods other than `GET`/`HEAD` and requests with a body, which are the origin's explicit instruction or can never be answered correctly from a store and have no opposite (amended in the change that implemented the cache).
- **Key:** store, route name, scheme, lower-cased host, normalised path, the query string as sent (options: sort, allow-list, deny-list), and the method class. Request headers enter the key only through `Vary` or `key.headers`. Query parameters an `only`/`ignore` rule leaves out of the key are also removed from the forwarded request, and the URL/method override headers (`X-Original-URL`, `X-HTTP-Method-Override`…) are removed on caching routes unless keyed. A route whose chain has an authenticating middleware (declared by the middleware: `basic_auth`, `jwt`, `client_cert`, `forward_auth`) anywhere in its chain is a validation error unless `shared_across_users: true` or the key includes the identity (`key.consumer`; for `forward_auth`, a `key.headers` entry the middleware copies back). Anywhere, not only before `cache`: Pingora looks the cache up after every `request` phase, so the position of `cache` in the list does not change when it runs (amended at implementation). Mirrored requests skip the cache, so a mirror sees every request its service sees.
- **Semantics we add to Pingora's mechanism:** origin `Age`, the full 304 header update, invalidation of the URL (and `Location`/`Content-Location` on the same host) after a successful unsafe method, request directives (`no-cache`, `no-store`, `max-age`, `min-fresh`, `max-stale`, `only-if-cached`), `Cache-Status` (RFC 9211) on every answer and in the access log, `stale-if-error` (RFC 5861) through `should_serve_stale`. **`stale-while-revalidate` is not served in v0.8**: its background subrequest re-runs the pipeline; the directive is honoured as plain staleness (revalidate in the foreground) and the setting that would enable background refresh is refused as planned.
- **Coalescing** on by default: one fetch per key, waiters up to `lock.timeout` 5 s (also the longest a writer holds the lock), then they fetch on their own without storing; a failed or uncacheable fetch releases waiters to fetch individually (pingora-cache elects a new writer after a failed fill; our lock wrapper releases the waiters instead).
- **Stores:** memory (LRU by size; one index under a mutex, bodies reference-counted outside it, rather than sharded, so one object can use the whole `max_size`) and disk (one file per object under two hashed directory levels, a checksummed header with metadata then the body, temp file plus rename for visibility, a start-up walk that rebuilds the index and drops damaged or partial files, LRU eviction by size and count). A purge never loses to a late fill: fills in progress are registered in the store's index with their URL and tags, a purge marks the ones it covers, and their commit (rename and index insertion, under the same lock) is discarded; this replaces the generation in the file name (amended at implementation). The disk root is opened with cap-std. No partial reads for waiters and no memory tier over disk in v0.8.
- **Tags and purge:** tags from `Cache-Tag` and `Surrogate-Key` response headers (removed before the client sees them unless kept). Purge only through the admin API (`POST /api/v1/cache/{store}/purge` by URL, prefix, tag or all; role-gated, audited); no `PURGE` method on the data plane. Each replica has its own cache; the docs say a purge reaches one instance until v0.9.
- **Proof:** `cache-tests`, pinned by commit, runs in CI against rdock; the job fails on any failing test of kind "must"/"should not" in the suites named in the harness unless it is on a reviewed allow-list with a reason. The stampede test (N concurrent requests, one origin fetch, plus the failure and uncacheable variants) and a kill-and-restart test of the disk store are ordinary tests. The decoder of the disk file header gets a fuzz target.

### Consumers, API keys, limits, metering, envelope (F-GW-01, 02, 04, 05)
- **Consumers:** top-level `consumers.<name>` with `groups`, credentials and per-consumer limits. A request's consumer is set by an authenticating middleware (`api_key`, `jwt` claims mapping, `oidc`) and is visible to later middlewares, the access log, metrics and the cache key.
- **API keys:** `type: api_key` reads a key from a header (default `Authorization: Bearer` and `X-API-Key`), never from the query unless asked. Keys have the form `rdk_<id>_<secret><checksum>`; only `id` and SHA-256 of the secret are stored (inline, in a file re-read on change, or issued through the admin API into the `api` provider). Comparison is constant-time; keys may expire; the credential is removed before the request goes upstream by default. The token-format code shared with admin tokens moves to a crate the data plane may use. No clear-text key appears in snapshots, history, audit entries or logs (a test asserts it).
- **Limits and quotas:** `rate_limit` gains `key: consumer` and per-group overrides; a new `quota` middleware counts requests per consumer per window (`hour`, `day`, `month`) with counters persisted in the data directory. Counters are per instance and approximate (the docs say so; shared counters are v0.9). `RateLimit`/`RateLimit-Policy` headers are opt-in while the draft moves; `Retry-After` is always sent.
- **Envelope:** errors produced by rdock answer `application/problem+json` (RFC 9457) when the client accepts JSON and the route or `defaults` sets `errors.format: problem`; HTML stays the default for browsers. Every middleware reply goes through one renderer.
- **Metering:** `observability.metering` sends one event per request with a consumer (id, consumer, route, status, bytes, duration, time) as CloudEvents over a webhook and/or OTLP logs, batched, at-least-once with event ids, from a bounded queue that drops and counts when full. A hanging receiver never delays a request.
- **Cloudflare Access (W-CF-06):** `type: cloudflare_access` with `team` and `audience` is a preset over `jwt` (certs URL, issuer, RS256, header then cookie); `audience` is mandatory.

- **As implemented (amended at implementation):**
  - *Consumers* carry `groups`, inline `keys` (`{ id, hash, expires, note }`) and a watched `keys_file` (`id:hash[:expires]` lines); limits are not written on the consumer but on the middlewares, per group (`rate_limit.overrides`, `quota.overrides`; the first of the consumer's groups with an override wins). The `api` provider is the only provider that contributes consumers, and they keep their bare names (a consumer is an identity, not a routing object); for a consumer the file also defines, the API adds keys and the file's groups stay. In v0.8 `api_key` and `cloudflare_access` set the consumer; the `jwt` claims mapping and `oidc` follow with OIDC.
  - *Keys:* `rdk_` + 12-character ID + `_` + 32-character secret + 6-character CRC32, all Base62 (190-bit secret; the 12-character ID keeps keys apart from `rdk_pat_` tokens for scanners). The format code, SHA-256, constant-time comparison and a redacting `Secret` type are in the new crate `rdock-credentials`; admin tokens are byte-for-byte unchanged. Keys from other systems (no ID) are not accepted in v0.8. Admin endpoints: `GET/PUT/DELETE /api/v1/consumers/{name}`, `POST /api/v1/consumers/{name}/keys` (the clear-text key is in that answer only), `DELETE /api/v1/consumers/{name}/keys/{id}`; viewers list without hashes. Hashes are not masked in `GET /api/v1/config` (they are not secrets, as this ADR says of snapshots and history).
  - *`key: consumer`:* a route whose chain counts per consumer (`rate_limit`, `in_flight`, `bandwidth` with `key: consumer`, or any `quota`) without an authenticating middleware **earlier in the list** is a validation error; requests that still have no consumer (`anonymous: allow`) are counted per client IP. Quota counters are exact on one instance, capped at 100,000 keys per quota (later keys share one counter), and kept in a process-wide registry, so a reload keeps them unless the window changes.
  - *Envelope:* `errors.format` is `html` (the default, exactly the earlier behaviour), `problem` (problem details for every client that accepts JSON, including `*/*` and no `Accept`; HTML only for clients asking for `text/html` and no JSON type) or `auto` (problem details only for clients that ask for JSON and not HTML), at `defaults.errors` and per route. Type URIs are `https://reversedock.oday-bakkour.com/docs/reference/problems/#<slug>`, the documentation site's address today; they move with the site when the project's own domain replaces it, which will be noted as a change. A middleware's own body and `errors` pages take precedence; `basic_auth`'s plain-text 401 is used only with `html`.
  - *Metering* is emitted from the proxy's `logging` hook (no middleware needed) with a new UUIDv7 per event (the request ID can come from a trusted proxy). The OTLP sink sends OTLP/HTTP logs in the JSON encoding through the alert webhook's hyper-rustls client rather than enabling the OpenTelemetry SDK's `logs` feature, so no dependency or feature is added. Six attempts per batch, pauses doubling from 0.5 s to 30 s.
  - *Cloudflare Access* takes `certs_url` to replace the derived certs URL (tests, an egress mirror; https or loopback only). A service token's consumer is its `common_name` in the group `service-token`; a token with neither `email` nor a service token's `common_name` is refused.

### Request validation and transformation (F-GW-03, F-GW-04)
`type: validate` checks parameters (path, query, header) and JSON bodies against inline JSON Schema 2020-12 or an OpenAPI 3.1 document, compiled at configuration time with `jsonschema` (no default features); bodies use the held-body holder. Failures answer 400 with the envelope and the first errors. `type: transform` applies JSON Patch (RFC 6902) to request bodies (held) and sets headers; response-body transformation is limited to what the synchronous phase allows on bodies up to a cap. No template or jq engine in core.

- **As implemented (amended at implementation):**
  - *`validate`* takes inline schemas for `path`, `query`, `headers`, `cookies` and `body`, or `openapi` (a 3.1 document, JSON or YAML, watched; 3.0 is refused because its Schema Objects are not JSON Schema 2020-12), not both. The rule grammar has no named captures, so path parameters come from the named groups of `path.regex` (with `openapi`, from the path templates). Parameter values are converted to the declared scalar type; a repeated name whose schema is not an array fails, so parameter pollution is refused. OpenAPI parameters with a non-default `style`/`explode` or with `content` are refused at load as planned, not checked wrongly. `unknown_operations: deny` (default) answers `404` or `405` with `Allow`; validation warns when a `cors` middleware stands after such a `validate`, which would refuse preflights first. `jsonschema` 0.60.1 is built without default features (no resolver at all), `$ref`s outside the document are refused at configuration time, `pattern` uses the `regex` engine, and `format` is asserted by default (`formats: false` treats it as an annotation). Failures list at most `max_errors` (default 5) entries `{ pointer, message }` under `errors` with `errors_truncated` when cut; the message is built from the keyword and the schema, never from the instance. Invalid JSON is a `validation-failed` entry at `/body` (400); a non-JSON content type is the new kind `unsupported-media-type` (415). `mode: report` logs and counts instead of refusing. Extension members are rendered in problem details and also in the pre-v0.8 JSON object (they never existed there before, so `html` stays compatible).
  - *`transform`* implements JSON Patch itself in `rdock-model` (`json_patch`, with RFC 6901 pointers, all-or-nothing on a copy, RFC 6902 appendix A as tests) rather than reusing the `json-patch` crate the admin API uses, so error messages name operations and pointers without echoing values. A replaced request body is sent **without `Content-Length`** (chunked or stream-framed), as the body phase already does for any replacing middleware: the head leaves before the patched length is known, so the length is not "corrected" but dropped. A failed request patch answers the new kind `patch-failed` (422) with the operation's index and name. Response bodies are patched only for 2xx other than 204, 205 and 206, JSON, identity encoding (an encoding `compress` chose is fine: it runs after the body phase) and at most `max_body`; `Content-Length`, `ETag`, `Accept-Ranges` and digest headers are removed from a patched response. A chunked body that grows past the cap is sent as received from then on. *Cache:* the cache stores the backend's response before any response hook runs and replays hits through the chain, so the store never holds a patched body wherever `transform` stands; there is therefore no ordering to warn about, and the behaviour is documented instead of a validation warning.

### OIDC login (F-GW-01)
`type: oidc` is a relying party built on the existing ring JWT and JWKS code: discovery, authorization code with PKCE always on, `state` and `nonce`, the ID-token checks of OpenID Connect Core §3.1.3.7, a stateless session in an AEAD-sealed cookie (`__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Lax`, split when large) keyed by a secret reference with rotation, refresh when a refresh token exists, RP-initiated logout, claims to headers and to the consumer, redirect targets restricted to the route's own hosts, 401 instead of a redirect for non-navigation requests. No server-side sessions and no back-channel logout (they need shared state: v0.9). Tested against a mock provider in `rdock-testkit` (with scripted faults) and against Dex in CI; the cookie decoder gets a fuzz target.

- **As implemented (amended at implementation):**
  - *Crypto and format:* the cookie is ChaCha20-Poly1305 (ring) with a random 96-bit nonce, `v1.` and base64url; keys come from HKDF-SHA256 over each configured key (at least 32 bytes) with a fixed salt and the purpose (`session`, `state`) and the relying party (issuer and client ID) as info, so a state cookie never opens as a session and a session of one `oidc` middleware never opens in another. `session.key`, `session.keys` (`[current, previous…]`) and `session.key_file` are alternatives; `client_secret`, `session.key` and `session.keys` are secret fields (references only, `${vault:…}` accepted). A session larger than 3800 bytes is split over `<name>_0…` (at most four); one that does not fit fails the login with a log line rather than dropping claims.
  - *What the session holds:* `sub`, the consumer, groups, the e-mail (only when `email_verified` is true, unless `allowed.unverified_emails`), the `claims_to_headers` claims as text, login time, absolute expiry, refresh time, and the refresh token (with `refresh`) or access token (with `forward_access_token`, passed as `X-Forwarded-Access-Token`). `ttl` defaults to 8 h (the research note suggested 12 h); without a refresh token the session ends when the ID token expires; with one it is refreshed 30 s before expiry, a provider's `refresh_expires_in` caps it, and parallel refreshes of one token on one instance share a result for 30 s (rotation-safe on one replica; across replicas one may lose and log in again, as the note predicted). The ID token, and with it `id_token_hint`, is not kept: logout sends `client_id` and `post_logout_redirect_uri`, which RP-Initiated Logout 1.0 allows; the userinfo endpoint is not used.
  - *State:* one cookie per login in progress, named `<cookie>_state_<id>` with an 8-character random ID that is also the prefix of `state`; 10 minutes; at most four (the oldest are expired). The post-login target is the request's own path and query (absolute-form targets lose their authority; anything starting `//` or `/\` or containing `\` becomes `/`), never a parameter.
  - *Paths and hosts:* defaults are `/_rdock/oidc/callback` and `/_rdock/oidc/logout` (the note's `/.rdock/…` would be refused by `static`'s dotfile rule and some WAFs). The redirect URI uses the request's host only when it is one of the positive `Host` names of the routes that use the middleware (passed from compilation as `BuildEnv::route_hosts`), else `redirect_url`; validation refuses an `oidc` route without a `Host` matcher and without `redirect_url`. The scheme is `https` when `session.secure` (default) or the connection is TLS.
  - *Navigation rule:* `unauthenticated: auto` (default) redirects `GET`/`HEAD` with `Sec-Fetch-Mode: navigate`, or without that header with `Accept` naming `text/html` and no `X-Requested-With`; `redirect` and `deny` are the opposites.
  - *Verification:* algorithms are `algorithms` (default RS*, PS*, ES256, ES384, EdDSA) ∩ the provider's `id_token_signing_alg_values_supported`; HS* only when listed, keyed with the client secret (at least 32 bytes). `iat` must be present and not in the future; `at_hash` uses the hash of the ID token's algorithm (SHA-512 for EdDSA). `token_type` must be `Bearer` when an access token is returned. The issuer in the discovery document must equal the configured one (a bare host's trailing `/` aside).
  - *Provider access:* discovery and keys use the data plane's Pingora HTTP client, started lazily on the first request and refreshed every 10 minutes (the document every hour, early on an unknown `kid`, retry after 30 s); a provider is shared by the middleware's configurations across reloads while its settings are unchanged. The private-address guard checks the address the client resolved and connects to (`allow_private_targets`, default off). A login waits at most 3 s for a first fetch, then answers `503` `identity-provider-unavailable`; callback failures answer `401` with the new kind `login-failed`.
  - *Cookies:* `same_site: strict` is refused (the session cookie would not come back from the provider's cross-site redirect and the login would loop); the state cookie is always `Lax` (or `None`). `secure: false` needs `allow_insecure_cookies: true` and plain-HTTP routes. Two `oidc` middlewares with the same `cookie_name` are warned about.
  - *Consumers:* `consumer_claim` (default `email`, `sub` when absent) and `groups_claim` (default `groups`) set the consumer, with the groups of a `consumers.<name>` entry of the same name added. `jwt` gained `consumer_claim`/`groups_claim` in the same step; with `consumer_claim` it authenticates as `Identity::Consumer`.
  - *Tests:* a fake provider in `rdock-testkit` (`oidc::FakeIdp`, with knobs for nonce, audience, issuer, expiry, `alg: none`, key rotation, refresh rotation and refusal, an authorization error and an unavailable provider; no slow-response knob, since the fake answers synchronously) and a cookie-keeping `Browser`; the `oidc-dex` CI job logs in through Dex v2.46.1's password form (image pinned by digest) in an `#[ignore]`d test; the fuzz target `oidc_cookie`. Metrics: `rdock_oidc_logins_total`, `rdock_oidc_refreshes_total`, `rdock_oidc_provider_errors_total`.

### UDP and UDPRoute (M-L4-04, W-K8S-01)
- `udp` listeners, `udp_routes` (a listener's datagrams go to one service; `ClientIP` rules only) and `udp_services`. A session is one client address mapped to one connected upstream socket chosen by the balancer; it ends after `idle` (default 60 s) or after `responses` replies when set. **Sessions are capped by default** (per listener and per client address) because source addresses can be spoofed; datagrams over the cap are dropped and counted. `ip_allow`/`ip_deny` apply. rdock never sends a datagram that is not a reply on a live session. Metrics mirror the TCP ones. Reloads keep sessions of unchanged listeners. A removed listener drains its sessions for `lifecycle.drain_timeout` and keeps its socket meanwhile (replies leave from it), but *amended at implementation:* a listener replaced on its address (a reload whose new `udp` listener needs the address of one it removes, or of one still draining) ends its sessions immediately and gives up the socket, so the address is never blocked; a provider listener that still cannot bind is retried with a bounded backoff, and the Kubernetes provider keeps released internal ports out of new allocations for 30 s.
- Labels: `rdock.udp_routes.*`/`rdock.udp_services.*` and the Traefik `traefik.udp.*` subset.
- Kubernetes: `UDPRoute` translates like `TCPRoute`; `UDP` listeners are accepted; per-Gateway Service ports are keyed by (protocol, port); the feature is claimed only with its fixture tests, and `GATEWAY-UDP` joins the conformance job.

### Directory listing (F-WEB-02)
`static.listing: true` lists a directory when no index file exists: built-in HTML or JSON by `Accept`, names escaped and percent-encoded, a restrictive `Content-Security-Policy`, the existing `hidden` and `symlinks` policy, at most 10,000 entries, server-side sort by name. No templates. `rdock validate` warns when listing is on together with `hidden: allow` or `symlinks: all`.

### Secrets (W-OBS-02)
- External Secrets Operator, the Secrets Store CSI driver and Vault Agent are supported as they are: they produce files and native Secrets that `${file:…}` and the Kubernetes provider already read. v0.8 adds the documentation, examples and a rotation test.
- `${vault:<mount>/<path>#<field>}` reads KV v2 over raw REST on our client (token or Kubernetes login), with `secrets.vault` naming the address, CA and auth. Values are fetched at load and refreshed on an interval; a failed refresh keeps the last value and marks the configuration degraded; a failed first read fails the load like a missing file. Values never appear in logs, diagnostics or the admin API. Tested against OpenBao.
- **As implemented (amended at implementation):** `secrets.vault` has `address` (https, or http only to loopback unless the unsafe `insecure_http: true`, which validation warns about), `ca_file`, `namespace` (sent as `X-Vault-Namespace`), `auth.token` (a `${file:}`/`${env:}` reference read for every request; a literal is refused) or `auth.kubernetes` (`role`, `mount: kubernetes`, `token_file` defaulting to the service-account token), `refresh` (default 5m, at least 1s, warned below 10s), `timeout` (default 5s, shorter than `refresh`) and `allow_private_targets` (default true). The client lives in `rdock-observability` beside the alert and metering client and reuses its guarded resolver; Kubernetes tokens are replaced after two thirds of their lease and after a `403`. `${vault:…}` is accepted **only in secret fields**, not wherever `${file:}` is: an ordinary field is interpolated at load, so the value would enter the loaded configuration that `GET /api/v1/config` serves. References are collected from the configuration file only, never from provider objects. Values are held in a process-wide store read by the same use-time resolution as `${file:}`, read at **every** load (not only the first), and read again by a refresh task that reloads on a change. "Degraded" is shown as `secrets.vault` in `rdock status` (`state`, `error`, `references`, `last_read`) and counted in `rdock_vault_refresh_failures_total`. `rdock validate` reads Vault as a start does, because some secret fields are checked when compiled (a JWT key's length); a validation without the server fails like one without the referenced file. Tested by end-to-end tests against a fake KV v2 server in `rdock-testkit` and, in the `openbao` CI job, against OpenBao 2.7.2 in dev mode with token login; the Kubernetes login is tested only against the fake.

### Terraform/OpenTofu provider (F-MGMT-02)
The provider's source lives in `clients/terraform` (Go, `terraform-plugin-framework`, on the generated Go client and the per-object admin endpoints with `If-Match` and retry on 412): `reversedock_route`, `reversedock_service`, `reversedock_middleware` (the registries require resource names to start with the provider name; TCP routes and services are not manageable because the admin API's object endpoints do not expose them), data sources, import. It is built and unit-tested in CI, with acceptance tests against a running rdock under Terraform and OpenTofu. **Publishing needs a separate repository named `terraform-provider-reversedock` and a signing key, which are maintainer actions**; F-MGMT-02 stays open until then.

## Consequences
- New crates: `rdock-cache`, `rdock-plugin-api`, a small shared credentials crate; `rdock` gains a library target. New dependencies outside feature gates: `jsonschema` (already a dev-dependency) and nothing else; behind `wasm`: wasmtime 36 and `minisign-verify`.
- Model: `caches`, `consumers`, `udp_routes`, `udp_services`, `secrets.vault`, `observability.metering`, and middlewares `cache`, `plugin`, `agent`, `api_key`, `quota`, `cloudflare_access`, `validate`, `transform`, `oidc`; `rate_limit.key: consumer` with `overrides` and `headers`; `defaults.errors.format` and `routes.<r>.errors.format`; `static.listing` and `udp` listeners leave the gate. Additive; existing configurations keep their meaning.
- The request path gains phases. Routes that use none of them must not get slower: the 2-CPU benchmark is run before and after, and a regression blocks the step.
- The cache, OIDC, API keys and agents are security surfaces. Each is reviewed against its section above before the milestone is released, as the admin surface was in v0.5.
- Open after v0.8 by decision: full pre-buffering (M-TM-05) until Pingora releases its hook; stale-while-revalidate; gRPC agents; Terraform publication; and WASM if its step slips. The roadmap and requirement notes say so.
- [Architecture §6, §8, §17 and §19](../05-architecture.md) are updated to match; §19's `pingora-memory-cache` and segmented-file store are replaced by this design.

# ADR-0031: v0.9: binary upgrade by peer handover, a control plane in the same binary with data planes that issue certificates under a lease, latency-aware balancing, edge security matchers, and what waits

- Status: accepted
- Date: 2026-11-13

## Context

v0.9 "Scale" carries H-HA-01…05, H-LB-01…04, H-SEC-01…07, H-PERF-01…06, F-UI-07 and the open performance plan of issue 181. [Research](../research/v0.9-scale.md) checked the facts on 2026-11-13. The findings that shape this decision:

- **Listener changes already apply in process** (bind first, keep unchanged sockets, drain removed ones). Only the binary upgrade is missing. rdock does not run Pingora's `Server`, and Pingora's fd transfer is Linux-only, path-based with mode 0666, panics on errors and shuts the old process down even when the transfer failed. H-PERF-04's "supervisor/worker model" and "listener changes need a restart" describe a design we no longer need.
- **Two processes on one data directory are destructive today**: no lock, the spool is emptied on open, the admin socket is unlinked and rebound.
- **Listeners bind with a backlog of 128** (the standard library's value); TLS tickets use fresh random keys per listener and per rebuilt acceptor, so resumption does not cross listeners or survive a TLS reload.
- **Issue 181**: v0.7 and v0.8 added almost nothing to a request that uses no new feature; what is left in our code is a handful of allocations worth about 1 % each, a **linear scan over a listener's routes**, and per-route statistics rings of 187 KiB allocated up front. The TLS tail reads as one stall per benchmark run caused by a burst of handshakes, not a steady delay; that is a hypothesis until measured. The lab was retired on 2026-11-07; a GitHub-hosted job ends after 6 hours.
- **Pingora 0.9.1's `ProxyHttp` cannot race two upstream attempts for one request**, so hedging cannot be built on it.
- **JA4** (the TLS client fingerprint) is BSD-3-Clause; the rest of the JA4+ family is under the FoxIO licence. We already parse the ClientHello for SNI passthrough.
- **H-SEC-02 and H-SEC-06** are met by v0.8 (agents with the CRS example; `oidc`, `jwt`, `forward_auth`, `cloudflare_access`) except for the items ADR-0030 left open.
- For a control plane: Envoy's xDS ACK/NACK with version and nonce, Kong's hybrid mode (data planes cache the last configuration on disk) and certmagic's storage locks are the prior art. Everything the control channel needs (axum, hyper, rustls, rcgen, ring, zstd) is in the tree. `tonic`, `aws-sdk-s3`, `foca` and `openraft` are excluded by weight, MSRV or licence.
- Let's Encrypt's limits make duplicate issuance a real cost; a per-name lease with fencing, a re-check after taking it, and a shared account are what prevent it.

HTTP/3 is decided separately in [ADR-0032](0032-http3-on-quinn-and-h3.md).

## Decision

### Order and what "v0.9" means
The work lands in this order, each step leaving the workspace green: measurement helper and the per-request fixes of issue 181 → listener socket and runtime options → shared TLS tickets and HTTP/2 options → data-directory lock, per-process spool, adoptable admin sockets → binary upgrade by handover → balancer (Peak-EWMA, outlier detectors, slow start, tiers, zones, per-try timeout) → edge security (JA4, GeoIP, abuse counters, mTLS identity) → cluster store and ACME under a lease → `rdock control`, bundles, rollout, instance view → distributed limits → admission control and tenants → HTTP/3 (ADR-0032) → soak and documentation. A step that does not reach its tests is left out with a "planned for" diagnostic and the roadmap says so; nothing ships half-wired.

### Performance (issue 181, H-PERF-01, H-PERF-06)
- A **measurement helper** in `benchmarks/` records allocations, system calls and CPU time per request for a fixed request count, and the `cpu.stat` ladder as a script. `main` at the start of v0.9 is the baseline. Gates that can be evaluated without the lab: allocation and system-call counts do not rise; CPU time per request shows no regression beyond twice the A/A spread; the nightly gate stays green. No absolute microsecond figure is claimed from a development sandbox.
- **Routing uses a host index** per listener (exact hosts, one-label wildcards, then routes without a host rule), preserving priority order. Per-request string and vector allocations in forwarded-header cleanup, the client stream and upstream selection are removed.
- **Statistics rings are lazy**: allocated on the first request of a route or service, and not recorded at all when neither the admin API nor an error-rate alert can read them.
- Issue 181's step 3 target (≤ 60 µs) is restated as the relative gates above; steps 5 (4 and 8 CPUs) and the 24-hour soak stay open until a machine exists. The nightly gate gains a CPU-per-request ratio; `MIN_THROUGHPUT_RATIO` becomes 0.98, not 1.0, because the runner's achieved rate rounds below the target.
- **Listener sockets** bind through `socket2`: `listeners.<l>.socket.{backlog, reuse_port, receive_buffer, send_buffer, keepalive, user_timeout, fast_open, ipv6_only, dscp}`. `backlog` defaults to 4096 (Linux `somaxconn` since 5.4); everything else keeps the kernel's behaviour. `reuse_port` with a `udp` listener is refused.
- **Runtime**: `runtime.worker_threads` and `runtime.max_blocking_threads`. Per-core runtimes stay unadopted (#176); CPU pinning is planned.
- **Handshake limit**: `listeners.<l>.tls.max_handshakes` bounds concurrent TLS handshakes per listener (default: unlimited until the experiment of issue 181 step 4 is run; the option exists either way). A handshake offload pool ships only with benchmark evidence.
- **Allocator**: mimalloc stays the default. A jemalloc cargo feature exists for comparison; the matrix and a sizing page are published when measured.
- **As implemented (step 1, commit `416ec80`):** `tls.max_handshakes` applies to `https` listeners; on `tcp` listeners (TLS-terminating TCP routes) it is refused as planned. A reload changes `backlog`, the buffers and `fast_open` on the running socket; `reuse_port` and `ipv6_only` are set before `bind`, so a change keeps the running value until a restart and the reload says so. Of the per-request candidates, metric handles resolved once per route and service and dropping the backend id `String` were not done (allocations per request went from 137.5 to 125.5 without them; [results](../../benchmarks/results/2026-11-13-perreq/report.md)). The counting allocator `stats_alloc` is a dependency only of the bench-only `alloc-count` feature of `rdock`, never of a release build; `benchmarks/perreq` is a workspace member. The jemalloc feature and the allocator matrix are not done yet (H-PERF-06).

### TLS and HTTP/2 (H-PERF-02, H-PERF-03)
- One **ticketer per security class** (TLS policy plus client-authentication identity), shared by listeners and kept across reloads: our own `ProducesTickets` on ring ChaCha20-Poly1305 with a key name, current and previous key, `tls.tickets.rotate` 6 h (rustls's default), `tls.tickets.enabled`, `tls.session_cache.size`. Keys live in memory, are handed to the next process in an upgrade, and are written to disk only with `tls.tickets.key_file`. 0-RTT stays off and is refused.
- `listeners.<l>.http2.{max_concurrent_streams, initial_stream_window, initial_connection_window, max_frame_size, max_header_list_size, max_pending_accept_reset_streams, max_local_error_reset_streams, max_send_buffer}` with today's values as defaults. A value that removes a flood limit must be spelled `unlimited`.
- **As implemented (step 2):** the security class is the TLS policy, the client-authentication mode **and** the SHA-256 identity of its CA certificates, the listener's name when it serves certificates of its own (`tls.certificates`: other server identities, rustls's second condition), and the resumption settings themselves; the session cache is shared per class like the ticketer. Keys from a `key_file` are bound to their class with HKDF-SHA256 (the class id as salt), so one file used by listeners of two classes never lets a ticket cross between them, while instances with the same configuration still derive the same keys. The key file holds one to eight 32-byte keys in base64, one per line, the first current; it is refused when its group or others may read or write it, is watched like other referenced files, and a warning is logged when it is older than 24 hours. Keys from a file are never rotated by rdock and never handed over (the next process reads the file). The lifetime announced is twice `rotate`, capped at 7 days, so `rotate` is at most 84 h. There is no setting that enables 0-RTT, so none needs refusing; `max_early_data_size` is set to 0 explicitly. HTTP/2 ceilings without `unlimited`: 10,000 streams and pending-accept resets, 100,000 local error resets; windows and sizes follow RFC 9113 §6.5.2. The slow-reader test is an ordinary test (a client that never reads a 256 MiB HTTP/2 response; the proxy grows by less than 64 MiB).

### Binary upgrade (H-PERF-04)
- **Peer handover, no permanent supervisor.** The running process verifies and spawns the new binary with one end of a socketpair as its standard input, sends a versioned manifest and the listening sockets, admin sockets and data-directory lock with `SCM_RIGHTS` (`rustix`, no `unsafe` of ours), waits for `ready`, stops accepting, sends `go`, and drains. If the child exits or does not become ready within `upgrade.start_timeout`, the old process resumes accepting; nothing was closed.
- **One writer.** `<data dir>/rdock.lock` is an advisory lock that a second independent `rdock run` is refused on; the spool becomes per process; admin sockets are adopted, not rebound. ACME, the local CA, alerts, metering, audit and configuration history stop in the old process before they start in the new one. Quota counts of draining connections are sent to the new process at exit.
- **Triggers**: `rdock upgrade [--binary <path>]` over the admin Unix socket and `SIGUSR2`. Never the TCP API or the dashboard: an upgrade executes a file. The binary must be a regular file, not group- or world-writable, owned by root or the running user; `upgrade.trusted_keys` adds a minisign check with the verifier that moves out of `rdock-wasm`.
- **Drain** is bounded: `upgrade.drain` 10 m by default, `unlimited` allowed with a warning. HTTP/1 keep-alive goes off and HTTP/2 gets GOAWAY in the old process; UDP sessions end at the handover. Metrics: `rdock_upgrades_total{result}`, `rdock_upgrade_draining_connections`, `rdock_upgrade_generation`.
- **As PID 1 in a container the command is refused** with a diagnostic: replace the container. systemd gets `MAINPID=` and `NotifyAccess=main`.
- H-PERF-04's requirement text is corrected in place (the ID is unchanged) to say what is true: listener changes are in process; the binary upgrade is a handover.
- **As implemented (step 2):**
  - *Binary.* Without `--binary` the upgrade runs `upgrade.binary` (default `/usr/local/bin/rdock`, where the unit and the image install it); the binary is never derived from the running executable. Besides the file checks, its directory must be owned by root or rdock's user and not writable by group or others unless sticky, since whoever may rename files there could swap the binary between the checks and the start. The file is opened once for the checks, the SHA-256 and the signature. `<binary> validate <config>` runs for a file configuration (zero-config has none).
  - *Protocol.* Length-prefixed JSON over the socket pair, descriptors in batches of 32 with `rustix` `sendmsg`/`recvmsg` (`MSG_CMSG_CLOEXEC`), blocking calls in `spawn_blocking`. The manifest carries a protocol version and the data directory's format (new file `<data dir>/rdock.format`); a newer one is refused before `ready`, and so is a data directory with a newer format at any start. Listener sockets are matched by address and transport, so a renamed listener keeps its socket; sockets no listener claims are closed. `SIGUSR2` and `rdock upgrade` share one queue; a second request while one runs is refused.
  - *Writers.* Stopped in the old process at `ready` and started in the new one after `go`: ACME (its plan emptied, which releases its storage lock), the local CA, the Cloudflare range sync, alerts, the providers (the Kubernetes provider releases its lease), the provider bind retry, the Vault refresh and the quota files (written once more, then left alone; the new process reads them again). Metering is not a writer of shared files (it sends to network sinks), so each process reports its own requests. The audit log and the configuration history are written through the admin API and the engine: from the spawn on the old admin API answers changes with 503 and, once paused, closes each connection after the request in progress; the new process reads the end of the audit chain again after `go` (and the old one does after a failed attempt), so the hash chain stays intact. The new process records the configuration it boots in the history, as a restart does. The disk and memory caches are bypassed in the old process from the spawn, because the new process's start-up walk removes unfinished cache files.
  - *Drain.* Connections of a stopping listener that have not sent a request yet get up to 2 s (bounded by the drain) before Pingora's `cleanup` closes idle ones: `cleanup` drops a connection still waiting for its first request without an answer, which lost a request accepted just before the handover in about one run in three. `rdock_upgrade_drain_deadline_seconds` was added to the metrics.
  - *Faults* for the tests (`RDOCK_UPGRADE_FAULT`: exit before `ready`, exit after `ready`, pretend PID 1) exist only in debug builds and with the `fault-injection` feature; each can only make an upgrade fail.
  - *Not done:* a run under real systemd (the `MAINPID=` path is untested); other platforms (refused); UDP session migration (sessions end at the handover).

### Balancing (H-LB-01…03, H-HA-05)
- `policy: peak_ewma`: power of two choices over `ewma × (in_flight + 1) / weight`, time to first byte as the sample, `decay` 10 s. The default policy stays `round_robin`.
- `passive.outlier.success_rate` and `.failure_percentage` with Envoy's thresholds (1.9 σ, 85 %, minimum 5 hosts), off by default; `ejection_jitter`; `slow_start { window, aggression, min_weight_percent, on: [recovery, join] }`, refused with hash policies.
- `priority: 0..=7` on backends with `failover: strict | spill` (overprovisioning 1.4); `backup` stays as tier 1.
- `Backend.zone` and `locality { zone, mode: prefer | off }`, off by default; the Kubernetes provider keeps EndpointSlice zones and hints.
- `retries.per_try_timeout`. **Hedging is refused as planned**: it needs a Pingora hook that does not exist.

### Edge security (H-SEC-01, 03, 04, 05)
- **JA4** computed from our ClientHello parser (JA3 as an explicit option): access-log field, `rate_limit`/`abuse` key, a `ClientFingerprint` matcher. Nothing from the FoxIO-licensed JA4+ family enters the tree.
- **GeoIP**: `geoip.database` (MaxMind DB format, `maxminddb` without its `mmap` feature), matchers `ClientCountry`, `ClientContinent`, `ClientASN`, reload on change, `max_age` 30 d with `on_stale: warn | refuse`. No database is bundled or downloaded. An unknown address never matches.
- **Abuse counters**: `type: abuse` counts events (statuses, failed authentications) per key with a TTL and bans past a threshold; bans live in their own bounded list with expiry, an admin view and an unban call; IPv6 by /64; per instance unless a cluster store is configured.
- **mTLS identity**: typed subject, DNS-SAN and URI-SAN rules, `spiffe { trust_domains, ids }` with the SVID validity rules, the CA and upstream client-certificate files watched. The SPIFFE Workload API is planned (it needs `tonic`).
- H-SEC-02 and H-SEC-06 are closed by reference to ADR-0030; their open items stay listed in the roadmap.

### Cluster (H-HA-01…04, F-UI-07)
- **`rdock control`** is a subcommand of the same binary. New library crates: `rdock-cluster` (protocol types, the data-plane agent, the `ClusterStore` trait with leases and compare-and-swap) and `rdock-control` (registry, bundle history, rollout, store server, cluster CA).
- **Enrolment** with single-use join tokens; the control plane's CA issues each data plane a short-lived client certificate; every later call is mTLS over HTTP/2 on the existing stack. No gRPC, no xDS wire compatibility.
- **Pull.** A data plane long-polls for the bundle after its revision. A bundle is the file-origin configuration with a revision and a hash, compressed. The data plane validates and compiles it, **stores it before it acknowledges**, and answers ACK or NACK with diagnostics. On start without the control plane it boots from the stored bundle. Refused without applying: another cluster's bundle, a lower revision, an empty bundle.
- **Rollout**: one canary, then the rest; a NACK halts; rollback is publishing an earlier revision. Automatic rollback on health is off by default.
- **Providers stay on the data planes** (Docker and Kubernetes are local facts). One active control plane; a highly available one is planned.
- **Certificates: data planes issue, under a lease.** `ClusterStore` backends are the control plane and a shared directory. Per name: take the lease (with a fencing token where the store has one), re-check the store, issue, write. The ACME account and the renewal time are shared; HTTP-01 and TLS-ALPN-01 tokens are replicated to connected members before the CA is told to validate. Without a store the behaviour is today's. With one, `allow_acme` in the Helm chart may be turned on.
- **Distributed limits**: `quota` and `rate_limit` gain `scope: instance | cluster` (default `instance`); cluster scope uses leased shares from the store with a documented error bound and fails to the local limit when the store is away. A Redis-compatible backend is optional and uses an in-tree RESP client. `in_flight` with cluster scope is refused as planned.
- **Instance view**: `GET /api/v1/cluster/instances` (revision, status, version, certificates) and one dashboard page.

### Admission control and tenants (H-LB-04, H-SEC-07)
- `rate_limit` and `quota` gain the key `group`. `admission { mode: aimd | gradient, min, max }` sheds load with 503 and `Retry-After`, lowest route `priority` class first; off by default.
- **Tenants**: `tenants.<name>` scopes API tokens and users to objects under a name prefix and to host claims; a scoped caller cannot define middlewares that read files or call out. No tenant means today's behaviour. Tenant-owned listeners and certificates, a tenant label on core metrics and a dashboard tenant view are planned.

### Proof
- **Upgrade**: `e2e_upgrade` holds a WebSocket, an SSE stream, a slow upload, an HTTP/2 stream, a TLS-passthrough TCP relay and a UDP session across a binary upgrade and across a listener change, while a connect loop opens at least 1,000 connections per second; zero failed new connections, held connections alive until the drain deadline, the old process gone after it. Failure cases keep the old process serving.
- **As implemented (step 2):** `crates/rdock/tests/e2e_upgrade.rs` passes on a shared 4-vCPU sandbox with the whole file running at once: about 1,450 new connections per second during the upgrade test over HTTP, HTTPS and TCP together (3,600 when it runs alone), none failed; the held set (WebSocket, SSE, chunked upload, HTTP/2 stream, TLS passthrough, UDP) works until the 5 s drain deadline and is closed within 3 s after it; the HTTP/2 connection gets GOAWAY while its stream goes on; the answering pid changes once; the admin socket answers and the lock stays held throughout; the old process exits within drain + 2 s, is reaped and leaves no spool directory; a TLS session resumes across the upgrade; the failure cases (exit before `ready`, exit after `ready`, world-writable binary, bad signature, upgrade over TCP, PID 1) leave the old process serving with no failed connection, and a later upgrade succeeds. The listener-change case runs under the same load. The ≥ 1,000 per second is for the three listeners together, not each.
- **Cluster**: three data planes and a control plane as processes; the control plane is killed, data planes keep serving, restart from the stored bundle, and catch up when it returns. Three instances and Pebble: one order per name, counted at the CA.
- **Soak**: a weekly job of about 5 hours on a hosted runner with a binary upgrade every 30 minutes, labelled as what it is. The roadmap's 24-hour criterion stays open until a machine is rented; "target RPS" is the soak's existing rate.

## Consequences
- New crates `rdock-cluster` and `rdock-control`; `rustix` and `socket2` become direct dependencies (both already locked); `maxminddb` is new (ISC). A Redis backend adds no crate.
- Model: `runtime`, `upgrade`, `cluster`, `control`, `tenants`, `geoip`, `listeners.<l>.socket`, `.http2`, `tls.tickets`, `tls.session_cache`, balancer and passive-health additions, middlewares `abuse` and `admission`, matchers `ClientCountry`, `ClientContinent`, `ClientASN`, `ClientFingerprint`. Additive; existing configurations keep their meaning, except that a second `rdock run` on one data directory is now refused and the listen backlog rises from 128 to 4096.
- The control plane holds certificate private keys and the ACME account key; its disk and backups need the care of a data directory. An instance cut off from the cluster cannot answer HTTP-01 or TLS-ALPN-01; DNS-01 is the recommendation for clusters.
- Open after v0.9 by decision: a permanent supervisor and in-container upgrades; the systemd fd store; migration of UDP sessions and TCP relays; per-thread `SO_REUSEPORT` acceptors and CPU pinning; hedging; the SPIFFE Workload API; JA4+; a highly available control plane; delta bundles; S3, Kubernetes-Secret, PostgreSQL and etcd stores; cluster-scoped `in_flight`; challenge actions; the 4- and 8-CPU measurements and the 24-hour soak.
- ADR-0008 (listener changes via self-upgrade) is superseded by this ADR together with ADR-0012.

# ADR-0033: v1.0 "Stable": the stability promise, maturity levels, migration tools and the proofs

- Status: accepted
- Date: 2026-11-14

## Context

v1.0 is a promise, not a feature set ([roadmap](../07-roadmap.md), [vision §7](../01-vision.md)). [Research](../research/v1.0-stable.md) on 2026-11-13 found:

- **Nothing checks for a breaking change today.** The config schema and the OpenAPI document have drift checks only. Neither contains a `deprecated` keyword, and no deprecation mechanism exists.
- **"Experimental" is marked five different ways** (a Cargo feature, doc comments, `rdock version` text, the "planned for" gate, website badges). Using an experimental feature gives no runtime signal.
- **`rdock config migrate`** is named in `docs/06-repo-layout.md` and does not exist.
- **Traefik conformance is weaker than the 1.0 criterion reads.** The 81 fixtures compare the translator with hand-written expectations; no Traefik process and no real Compose file is involved. `rdock migrate traefik` drops Compose `${VAR}` labels, loses server weights, and ignores static configuration. `rdock run` rejects Traefik's flags, so "changing the image name" does not work literally.
- **Chaos:** of the six scenarios, two are covered, three partly, and disk full has no test. Architecture §20 claims a free-space pre-check for certificate writes that the code does not have.
- **Release integrity** is good (keyless cosign, build-provenance attestations, SHA-pinned actions) with gaps: the SBOM is unsigned and scans the source tree, base images are pinned by tag, reproducibility is claimed and untested, and `docs/06` names scanners CI does not run.
- **Pingora** is still `0.x` and calls its rustls backend and cache integration experimental.
- An independent security review needs an outside party and money. The project has neither a rented benchmark machine nor a budget (maintainer, 2026-11-13).

## Decision

### The promise
- SemVer for the binary, the image and the chart's `appVersion`. A stable surface breaks only in a major, after its deprecation period. Patch releases carry fixes only.
- **Stable surfaces at 1.0**, each with a written definition of "breaking" in `docs/10-stability.md`: the config file (schema v1), the rule grammar, `rdock.*` labels, the documented Traefik label subset, the CLI (commands, flags, exit codes, JSON output; not human-readable text), the admin API `/api/v1`, metric names and labels, JSON access-log fields, problem types, documented `RDOCK_*` variables, the image contract, Helm values, the data-directory format (readable by the next two minors).
- **Not promised:** internal crates (all but `rdock-plugin-api`), performance, log wording, the dashboard's look, error text, anything below stable.
- **Deprecation:** a replacement ships first; a stable element then works for at least two minors and six months and is removed only in a major. It surfaces from one registry as a `rdock validate` warning (`--strict` fails; JSON carries code, since, removal, replacement), one WARN per element at load, the metric `rdock_deprecated_config_in_use{element}`, the admin API and dashboard, `"deprecated": true` in the schema and OpenAPI, and a generated "Deprecations" page.
- **Security exception:** a change that refuses an unsafe configuration may ship in a minor or patch when it fixes a vulnerability, with a "Security" changelog entry and a diagnostic naming the fix.
- **Support (F-OSS-05):** the two newest minors of the current major get security fixes; after a new major, the last minor of the previous one for six months. Fixes land on `main` first and are cherry-picked to `release/X.Y`. The policy page says there is one maintainer and no SLA.
- **MSRV** may rise in a minor, never in a patch, to a Rust release at least six months old.
- **Schema versioning:** v1 is additive through 1.x. `rdock migrate config` rewrites deprecated keys now and converts to a later schema when one exists; it replaces the never-built `rdock config migrate`. The schema `$id` moves to a tag-pinned URL.

### Maturity levels
- Three levels, **experimental / beta / stable**, from one registry in `rdock-model` that feeds validation, `rdock version`, the schema, the website badges and the stability page.
- Experimental features need an explicit opt-in (`experimental: [name, …]` at the top of the config) and are refused without it; using one logs once and sets `rdock_experimental_feature_in_use{feature}`. Beta may change in a minor with a migration note. Promotion needs: tests required in CI, documentation, one release at the lower level, and no open correctness issue.
- **Levels at 1.0.** Stable: the HTTP proxy, file and Docker providers, labels, automatic HTTPS, reliability features, the admin API, users and audit, the dashboard, Swarm, TCP, static files, DNS-01 adapters, the Gateway API controller. Beta: the cache, the plugin SDK and agents, consumers and quotas, OIDC, validation and transformation, UDP, Vault references, the v0.9 balancer and edge-security additions, binary upgrade, the cluster and `rdock control`, distributed limits, admission control and tenants, the Terraform provider and Go client. Experimental: WASM plugins, HTTP/3. TLS and the cache are offered at their level on Pingora parts that Pingora calls experimental; the page says so and we carry upstream breaks.

### Compatibility checks (required in CI)
A schema-diff script of our own, `oasdiff` for the OpenAPI document, snapshot tests for metric names, CLI `--help` structure and JSON outputs and access-log fields, and `cargo-semver-checks` for `rdock-plugin-api`. Each compares with the last release tag and fails on a change that the stability page calls breaking, unless the element is below stable.

### Migration
- **Traefik:** fix the gaps found (Compose interpolation with `--env-file`, `$$`, weights, `usersFile`, the plain-HTTP note), map the cheap unmapped options, add `--static` (reads `traefik.yml` and `command:` flags for entry points, ACME and Docker provider settings) and `--full`. "Conformance-tested" means three layers: the translation fixtures, a Compose corpus with golden output, and a differential CI job that runs a pinned Traefik and rdock on the same labels and compares status, answering backend, forwarded request and redirects; agreement must be total for options marked supported, apart from a reviewed allow-list. The subset is pinned to Traefik v3.7.
- **The 1.0 criterion is reworded:** a Traefik-on-Docker user changes the image, removes Traefik's flags (or runs `rdock migrate traefik --static`) and keeps their labels. `rdock run` does not accept Traefik's flags. When a Docker setup has only `traefik.*` labels and no `rdock.expose`, validation says that containers are not exposed by default.
- **Caddy:** `rdock migrate caddy` reads adapted JSON (`caddy adapt … | rdock migrate caddy -`), not the Caddyfile.
- **NGINX:** `rdock migrate nginx` with our own small parser for the faithful subset; constructs without a faithful translation (`if`, `map`, `rewrite … last`, named locations, variables) are refused per construct and written as disabled routes. It ships as beta.
- **One report** for all three: four levels (exact, approximate, manual, dropped), stable codes, `--report`, `--strict` (exit 2), and the invariant that every source item is accounted for. Guides list the defaults that change.
- Later: `acme.json` import, Caddyfile input, TOML dynamic files, NGINX `limit_req`, `stream {}` and `proxy_cache`.

### Proofs
- **Chaos suite** as a CI workflow on Toxiproxy and tmpfs: control plane down, Docker socket down (also at boot and hanging), CA down during renewal, disk full, backend flapping, config rollback under load. Pass: no failed request, a stated recovery bound, an intact data directory and audit chain. Disk-full rules: a configuration write that cannot be stored is refused; a mutating admin call whose audit record cannot be written fails; certificate writes check free space first.
- **Benchmarks:** competitor images updated, an HTTP/2 scenario, TLS parity rules, and a default and a tuned configuration per proxy, run on free hosted runners with pinned cores and published with that limit stated. The report says what a dedicated three-machine run would add; that run stays open.
- **60-second HTTPS:** a CI test with the release image, Compose and one label against Pebble, and a script for a fresh-VPS run against Let's Encrypt staging that a maintainer can run.
- **Security review:** the project prepares (threat model, an internal review per surface with fixes, fuzz targets for HTTP/2 frames, ACME responses, response framing and admin bodies, longer fuzz runs, Scorecard and CodeQL, docs aligned with what CI runs). The independent review itself needs a funder or a grant and is the maintainer's to commission; **1.0 is not tagged as final without it**. Until then releases are `1.0.0-rc.N`.
- **Release integrity:** SBOM built from the binaries and signed, base images pinned by digest, a weekly rebuild-and-compare job, release branches with their ruleset and a `latest` rule that never moves backwards.
- **Playground:** the shipped schema-driven one stands; exact diagnostics through a WebAssembly build of the validator are later work.

## Consequences

- A new document `docs/10-stability.md` and website pages for the policy, deprecations and maturity. `SECURITY.md`, `docs/06` and F-OSS-02/03/05 are aligned with what exists.
- `experimental:` is a config-model change: `type: wasm` and `http3.enabled` need the opt-in from this release on.
- New requirement IDs for the Caddy migration and the chaos suite; none is renumbered.
- The order: registry and maturity levels → deprecation plumbing and `rdock migrate config` → compatibility checks → migration report and Traefik work → Caddy → NGINX → chaos suite and the disk-full rules → security preparation → benchmarks and the 60-second proof → release integrity → documents. The result is released as `1.0.0-rc.1`.
- Open, and outside what the project can do alone: the independent security review, a dedicated-hardware benchmark, a 24-hour soak, a real-world 60-second run, the Best Practices badge registration, publishing `rdock-plugin-api` to crates.io.

## As implemented (steps 1–2)

Added 2026-11-14. The decision above is unchanged; this note records how its first two steps map onto the code and where the ADR's lists left a choice.

- **Registry.** `crates/rdock-model/src/maturity.rs` (`FEATURES`): each entry has an id, a level, the milestone it appeared in, a summary, the cargo feature a build needs (if any), the schema locations it covers (`listeners.*.http3`, `middlewares.*.type=wasm`, `services.*.load_balancer.policy=peak_ewma`) and a detector for its use. A test fails when a top-level section, a middleware `type`, a provider or a cargo-feature-gated setting is not listed, or when a listed location is not in the schema. Every location below stable carries `x-rdock-maturity` in the schema; the whole registry is `x-rdock-features` at the schema's root, which the website generates from.
- **Levels where the ADR's list was ambiguous, resolved to the more conservative level:**
  - Beta although shipped before v0.8: alert channels and rules (`observability.alerts`, v0.5; the ADR's stable list names the admin API, users and audit, and the dashboard, not alerts); the PROXY protocol (`listeners.*.proxy_protocol`, `tcp_services.*.proxy_protocol`, v0.6; the stable list names TCP, not the PROXY protocol); Kubernetes Ingress translation (`providers.kubernetes.ingress`, v0.7; only the Gateway API controller is named stable); fixed-status services (`services.*.respond`, v0.7).
  - Beta among the v0.8 additions not named in the beta list: `hold_body` and `cloudflare_access` middlewares; problem-details answers (`defaults.errors`, `routes.*.errors`) count with validation and transformation.
  - Beta among the v0.9 additions: listener socket and HTTP/2 options, the TLS handshake bound, shared TLS session resumption (`tls.tickets`, `tls.session_cache`) and `runtime` (one feature, `tuning`); the long form of `slow_start`, outlier detection, priority tiers, zones and per-try timeouts count with latency-aware balancing (`balancing`); `key: group` on limits counts with consumers; identity rules on client certificates (`client_cert` `subjects` … `spiffe`) are beta while `client_cert` itself stays stable (v0.4).
  - Stable as listed: the v0.1 middlewares, observability (logs, metrics, traces), `in_flight`, `bandwidth`, `jwt`, `client_cert`, `grpc_web`, health checks, retries, sticky sessions, splits and mirroring (v0.4 reliability), `static` (v0.6), and the configuration file's own keys (`$schema`, `version`, `experimental`).
- **Opt-in.** `experimental` is a list of strings; the schema restricts it to the experimental ids. The check runs in `Config::validate` (file and merged), so `rdock validate`, `rdock run`, reloads, provider objects and the configuration API all apply it. The cargo-feature check stays in `rdock-proxy`'s gate (a warning in `validate`, an error in `run`); the opt-in error's hint names the cargo feature, and the gate runs only once the opt-in is satisfied, so the two never contradict each other.
- **Run time.** `crates/rdock/src/engine/maturity.rs`: one WARN per experimental feature, one INFO per beta feature, one WARN per deprecated element (instead of one per use), the two gauges, and `features_in_use` / `deprecations_in_use` in the status document.
- **Deprecation registry.** `crates/rdock-model/src/deprecation.rs` (`REGISTRY`). Rewrite rules: rename a key, replace a value, move a mapping under another parent (with dropped keys and computed extra entries), or manual. An entry with `read_by_model: false` is rewritten by the loader before the model reads it (file, configuration API, and Docker labels via their configuration paths), so a rename needs no serde alias. Diagnostics gained optional `code`, `element`, `since`, `removal` and `replacement` fields (absent otherwise, so other JSON output is unchanged).
- **The real deprecation.** No serde alias or "legacy" setting exists in the model; the one setting kept for compatibility with a better replacement already released is `observability.alerts.webhook` (v0.3), which the alert sender has turned into a channel named `webhook` since v0.5. It is deprecated in 1.0, removed in 2.0, with the rewrite to `observability.alerts.channels.webhook` (`type: webhook`; `allow_private_targets: true` for a loopback URL; `timeout` dropped, since it has had no effect since v0.5).
- **Test hook.** The registry's `TEST_ENTRIES` (a renamed key `routes.<name>.rule`, a CLI flag `version --json`, an API operation `GET /api/v1/listeners` with `Deprecation` and `Sunset` dates) exercise the paths the real entry cannot (load-time renames, labels, CLI, API headers). Only debug builds turn them on, with `RDOCK_TEST_DEPRECATIONS=1`; release binaries never read the variable.
- **`rdock migrate config`.** `crates/rdock-migrate/src/config.rs`. It uses serde-saphyr 2.0.0's `Spanned` locations (already a dependency; no YAML crate added) to edit the text in place and verifies the edited text against the rewritten document; when an edit is not possible it writes the document out again and says that comments and formatting are lost. `version: 1` (or none) is the only version read; `SCHEMA_MIGRATIONS` is the empty list a v1 → v2 conversion will fill.
- **Not done in these steps:** a deprecated metric's help text prefix (the registry can list metrics; nothing renders them yet), deprecation warnings for documents written through the configuration API (renamed keys are rewritten, not reported), and the compatibility checks (step 3).

## As implemented (step 3)

Added 2026-11-14. The compatibility checks of the decision, as built; the decision is unchanged except where this note says a tool was not adopted.

- **One gate, one engine.** `scripts/compat.py` (Python standard library only, run with `-I`, tests in `scripts/test_compat.py`) holds a JSON Schema differ with two directions: *input* (the configuration file, the Helm values schema, API requests: what was accepted must stay accepted) and *output* (the access log, API responses, CLI JSON: what was written must stay written with a type readers expect). It resolves `$ref` with its sibling keywords, compares each definition once per use context, matches `oneOf`/`anyOf` alternatives by a constant discriminator, then by definition name, then by kind, and reports what it cannot classify as *needs review*, which fails like a break.
- **`oasdiff` not adopted.** v1.37.0 (the newest tag on 2026-11-14; release binaries could not be downloaded here, so it was built from its Go module, whose checksum the Go checksum database verifies) runs on our 480 kB OpenAPI 3.1 document in 0.3 s and finds removed paths, type changes, removed request enum values, newly required request fields and removed security schemes. At its default levels it does not report a removed optional response field or a removed error status, both breaking by docs/10-stability.md, and it knows neither our maturity marks nor our exceptions. The OpenAPI differ is therefore ours, on the schema engine; on the real history from v0.5.0-alpha.1 and v0.8.0-alpha.1 both tools report no breaking change.
- **`cargo-semver-checks` 0.51.0** (Apache-2.0 OR MIT, MSRV 1.93, below the pinned 1.99.1 toolchain) with `--baseline-rev <tag>`, installed in CI by `taiki-e/install-action`; built here from crates.io and run against v0.8.0-alpha.1: 202 checks pass in 12 s, and a removed `pub fn` is caught. The plugin SDK is beta, so its findings are exempt until promotion.
- **Baseline and modes.** The newest `v*` tag reachable from HEAD; report mode below `1.0.0-rc.1`, enforce from then on, `RDOCK_COMPAT_MODE` and `RDOCK_COMPAT_BASELINE` override. A clone without the tag is an error that says how to fetch tags; the `compat` job checks out with `fetch-depth: 0` and `fetch-tags: true`.
- **Maturity and deprecations.** Exempt: anything under `x-rdock-maturity` below stable on either side, any location the current registry (`x-rdock-features`) puts below stable (for baselines from before the marks), CLI commands, metrics, problem types and variables whose snapshot entry says so, operations marked in the OpenAPI document, and an element in the deprecation registry (schema or `schema/compat/deprecations.json`, baseline or tree) once the tree reaches its removal release.
- **Snapshots** under `schema/compat/`: `cli`, `metrics`, `access-log`, `problems`, `env` and `deprecations` from `rdock schema --compat <surface>` (hidden), `labels` from a test of the Docker provider, `image` from `Dockerfile.release` by the script; `just compat` writes them, a test in `rust` and the `compat` job fail when they are stale. Metrics come from a catalogue the registry now keeps as it registers each metric; the admin API's metrics from the table that also writes their `# HELP` lines. The metrics row of docs/10-stability.md now says plainly that a new label name on an existing metric is breaking.
- **Exceptions** in `schema/compat/exceptions.json`: surface, element, rule, reason (required), release; an entry counts while the baseline is older than its release.
- **First inventory** (report mode, baseline v0.8.0-alpha.1, the newest tag on the remote on 2026-11-14): no breaking change and nothing to review in the configuration schema, the OpenAPI document, the Helm values schema, the image contract or the plugin SDK. The snapshot surfaces have no baseline copy until the next release; one-off comparisons of the 0.8 sources found no removed metric, label set or bucket change, access-log field, problem type, CLI flag or documented variable. Against older tags the gate finds real 0.x breaks (for example `security.limits.max_header_bytes` 32 KiB → 64 KiB and `middlewares.*.type=redirect.permanent` true → false since v0.1, `providers.kubernetes.gateway_class` removed since v0.6), which shows the differ is sensitive without being noisy.
- **Not machine-checked**, as docs/10-stability.md §9 lists: semantic behaviour, defaults applied in code, the rule grammar, the roles an operation needs (not stated in the OpenAPI document), label value translation, and what `cargo-semver-checks` says it misses.


## As implemented (step 4)

Added 2026-11-14. The migration report and the Traefik work of the decision, as built; the decision is unchanged except where this note says so.

- **One report** (`crates/rdock-migrate/src/report.rs`). A `Builder` registers every source item (a label, a dotted file key, a flag, a `TRAEFIK_*` variable, a Compose service, a whole TOML file) and takes exactly one finding per item; `finish` fails with an accounting error when an item has none or two, and `rdock migrate traefik` exits 2 on it (a bug, never the user's input). Findings about the written result (a validation error of a fragment, label routes left to the Docker provider) have no item and are counted apart. Codes are a list in the same file (38 today), each with its level, a summary and general help; `schema/migrate-report.v1.json` (`rdock schema --migrate-report`, `just schema`) carries them as `x-rdock-codes` and is beta in the maturity registry (`migrate-report`); the CLI snapshot carries the schema under `json_outputs`. A route that uses a middleware or service that was not migrated is written `enabled: false` and reported, so a route never goes live without its authentication.
- **Exit codes.** `0` migrated, `1` the input is not one of the kinds read, `2` an error and, with `--strict`, anything manual or dropped, as the decision says. The shared exit-code table calls `1` "a failed check" and `2` "an error"; `--strict` follows the decision's `2` rather than the table's `1`, so CI can tell "the input is not Traefik's" (1) from "review needed" (2). Whether that is the right reading is an open question for the maintainer.
- **The coverage table** is code: `crates/providers/rdock-provider-docker/src/labels/coverage.rs`, one row per Traefik v3.7 Docker label (the keys of Traefik's generated `docker-labels.yml` on the v3.7 branch, plus `retry.status`, `.disableRetryOnNetworkError`, `.retryNonIdempotentMethod`, `.timeout`, `.maxRequestBodyBytes` and `encodedCharacters`, which only the per-middleware pages list), with status exact / approximate / manual / none, what it becomes, the difference or the reason, and an example value. The research's five statuses (S, P, W, T, N) became four, because "translatable but unmapped" is a state of the code, not of the option: every T row of research table 1.3 that step 4 maps is now exact or approximate, the rest are manual or none with the alternative named. Tests: the translator takes exactly the rows marked exact or approximate (each row's example on an exposed container); every Traefik label a fixture uses is in the table; every row has a fixture (two Swarm rows name the Swarm provider's tests instead). Totals: 94 exact, 41 approximate, 14 manual, 101 none (250 rows). The test that writes `tests/conformance/traefik-labels/coverage.json` also writes `schema/compat/labels.json`, whose Traefik list is now "every label marked exact or approximate" instead of step 3's "labels the fixtures use without a warning"; no label left the list.
- **Newly honoured labels** (a behaviour change for running setups, in the changelog): server weight, `sticky` and the cookie path, `chain` (inlined into routes after all containers are read, so a chain on one container works for a router on another), `ipWhiteList` (HTTP and TCP), the custom security headers, `accessControl*` (a `cors` middleware, `<name>-cors` when the headers middleware also sets headers, added after it in every route that uses it), `compress` encodings and included types, the rate limit's header key, the TCP PROXY protocol version and termination delay. Warnings for labels without an equivalent now carry the table's reason. A container with Traefik router labels and no `traefik.enable`/`rdock.enable` gets a diagnostic saying that containers are not exposed by default and how to get Traefik's behaviour; this is how "validation says so" is implemented, since `rdock validate` does not see containers.
- **Compose interpolation** (`crates/rdock-migrate/src/compose.rs`) follows the Compose Specification's interpolation chapter and Docker's `.env` syntax (both read 2026-11-14): `$VAR`, `${VAR}`, `:-`, `-`, `:?`, `?`, `:+`, `+`, nesting, `$$`; a `$` that starts no valid reference is kept (so `$2y$…` in an unescaped hash keeps `$2y` but `$abc` is a reference, as Compose reads it). Values come from `--env-file` (repeatable) and only with `--process-env` from the environment; `.env` next to the file is never read implicitly.
- **TOML** is not read: no TOML parser is a dependency (the `toml_edit` crate is in `Cargo.lock` only behind a build-time dependency no workspace build enables), so a TOML file is one manual finding that says to convert it, as the decision's "Later" list has it.
- **`--static`** reads `traefik.yml` and, always, the `command:` flags and `TRAEFIK_*` variables of a Compose service whose image is Traefik's. Credentials are never read: lego DNS providers that have an adapter (Cloudflare, DigitalOcean, Hetzner, deSEC, Route 53, Google Cloud DNS) are written with `${env:…}` references to the same variables, the report names them, and only the variable *names* of Traefik's service are kept; EAB keys and engine credentials are manual. An entry point that only TCP routers use becomes a `tcp` listener. Without `--full` the static part is reported and used to check the fragment; with `--full` it is written, and for a Compose file the label routes are left to the Docker provider (`output.labels_live`), since the labels stay on the containers.
- **Corpus**: 46 cases in `tests/conformance/traefik-compose/`, written by hand in the shapes of Traefik's documented examples (nothing copied, so no attribution was needed); `crates/rdock-migrate/tests/corpus.rs` compares output and report with the goldens, requires that the output validates or fails exactly as `expect_invalid` documents, and that no credential reaches it. The research's target of at least 100 files is not reached; the remaining shapes are listed in the corpus README.
- **Differential test** (`tests/conformance/traefik-diff/`, workflow `traefik-diff`, not required): `traefik:v3.7.19` and `traefik/whoami:v1.12.0` pinned by index digest (Docker Hub's tag API, 2026-11-14), both proxies with the same entry points and certificate and no ACME, rdock's HTTPS redirect off (Traefik has none unless configured). A case may use only labels marked exact, or approximate with an allow-list entry naming the option; the comparison covers status, the answering backend, the path and selected headers the backend saw, redirects and selected response headers. Image pulls are blocked in the development sandbox, so the job has not run: rule parsing, the matrix, the comparison, the gate and the generated project are unit-tested against recorded (hand-written) answers, and actionlint passes.

## As implemented (steps 5–6)

Added 2026-11-14. `rdock migrate caddy` and `rdock migrate nginx`, as built; the decision is unchanged except where this note says so.

- **Caddy reads adapted JSON** (`crates/rdock-migrate/src/caddy.rs` and `caddy/`). The JSON shapes are those of Caddy v2.11.9 (the latest release on 2026-11-14), confirmed from the JSON reference's documentation API (`https://caddyserver.com/api/docs/config/…`, which the client-side page at caddyserver.com/docs/json/ renders) and from the adapter's tests and source at the `v2.11.9` tag (`caddytest/integration/caddyfile_adapt/*.caddyfiletest`, `caddyconfig/httpcaddyfile/`, `modules/caddyhttp/`); each translation cites its source. A module whose shape could not be confirmed (plugins, the route53 DNS plugin's credential fields) is reported as manual or written with standard environment references. Caddy cannot run in the development sandbox (no `caddy` binary, no image pulls), so the 20-case corpus under `tests/conformance/caddy-json/` is hand-written in those shapes, each case with the Caddyfile it stands for; `just caddy-corpus` (`adapt.sh`, `caddy:2.11.9` pinned by digest) re-adapts them for a maintainer or CI to compare.
- **Flattening.** Caddy runs every matching route in order and chains handlers until one answers; ReverseDock picks one route. The translator follows every path through a server's routes (groups, `terminal`, subroutes, `invoke`), and each path that ends in an answering handler becomes a route: the conjunction of the matchers on the path (host and path disjointness removes redundant negations), the handlers before it as middlewares in Caddy's order, a priority that keeps Caddy's order. A route that always answers excludes nothing after it; otherwise later routes get its negated matchers. A path through an untranslatable matcher or handler is written disabled, and so are later paths that would otherwise catch requests the untranslatable matcher kept away (never widen); a matcher that follows a URI rewrite is refused, since Caddy matches the rewritten URI. At most 64 paths per server are followed; beyond that the rest is reported. Requests no handler answers get Caddy's empty 200; ReverseDock answers 404, reported once.
- **Caddy traps, as built:** path matchers are case-insensitive in Caddy, so they become case-insensitive `PathRegexp` (or `Path`/`PathPrefix` without letters) and `strip_path_prefix` a case-insensitive `rewrite`; the default selection policy `random` and the 3s dial timeout are written explicitly; HTTPS upstreams get `pass_host_header: false` (Caddy 2.11's `HTTPTransport.RequestHeaderOps`); placeholders are refused except the forwarding headers and `{uri}` at the end of a redirect.
- **`internal` issuer:** a route cannot select the local CA; ReverseDock's local CA signs private names automatically (`rdock_tls::is_local_ca_name`), so an internal issuer is exact for private names and manual for public ones.
- **NGINX parser** (`crates/rdock-migrate/src/nginx/parser.rs`, about 400 lines, no dependency): blocks nest at most 64 deep without recursion, files are at most 4 MiB, includes at most 8 deep and 256 files, nothing outside the main file's directory without `--include-outside`; an `nginx -T` dump is read without touching the disk. Property tests (`tests/nginx_parser.rs`) and a fuzz target (`tests/fuzz`, `nginx_parser`, which compiles the parser from its source file so the fuzz lock gains no crate) check that it never panics and that a printed tree parses back to the same tree. Includes resolve against the main file's directory rather than NGINX's prefix; the two are the same in the standard layout.
- **Location precedence** is written as priority tiers (server `return` and redirecting `rewrite`; `=` and the trailing-slash redirect; `^~` excluding longer plain prefixes; regular expressions in file order; plain prefixes by length; the server's own root). `crates/rdock-migrate/tests/nginx_locations.rs` compares the routes, evaluated with ReverseDock's rule semantics, with an independent implementation of NGINX's documented algorithm (`tests/support/nginx_reference.rs`) for the reference's example, the `proxy_pass` cases and 256 random location sets; `crates/rdock/tests/e2e_migrate_nginx.rs` runs rdock with a migrated configuration and checks the answering backend and the upstream path for a request matrix. The one approximation is `location /a` + `proxy_pass …/`, where NGINX sends an empty path segment (`//x`) and ReverseDock, which refuses such paths, sends one slash.
- **Defaults:** NGINX's effective values are written where that keeps behaviour (`max_body: 1MiB`, `timeouts.connect: 1m`, passive health and retries for upstreams of several servers, `precompressed: []`); upstream TLS verification stays on and is reported as security-relevant. A named default server keeps its names (the unknown-host difference is reported); a `server_name _` default server becomes a catch-all that excludes the other servers' names.
- **Not done:** `limit_req`/`limit_conn` (reported: 503 and delaying versus 429 at once), the three `if` patterns, `error_page` and `auth_request` translations, `stream {}`; for Caddy, direct Caddyfile input, `handle_errors`, `layer4`. A differential job against real NGINX and Caddy containers was not added: deriving it from `traefik-diff` would change that harness, which this step leaves alone.
- **Maturity:** `migrate-nginx` is beta in the registry, as decided; `rdock migrate caddy` is not in the registry (the decision names no level for it), and its report is beta with the other two (`migrate-report`).

## As implemented (step 7)

Added 2026-11-14. The chaos suite and the disk-full rules of the decision, as built; the decision is unchanged except where this note says so.

- **"Control plane down" is both.** The cluster control plane is `e2e_cluster::three_data_planes_survive_a_control_plane_outage` (unchanged, referenced, not duplicated). The in-process admin side is `chaos_admin`: 300 half-sent requests held against the admin listener, a flood of the most expensive reads and back-to-back configuration writes over the socket, and the admin socket file removed, with a normal build. A panicking or aborted admin runtime still needs the `fault-injection` build and stays in `benchmarks/isolation/`; no CI job builds that feature.
- **Pass criteria, as asserted.** Zero failed client requests in every scenario (the testkit's open-model generator, `rdock_testkit::load`: a fixed rate whatever the answers, a 5 s deadline per request, keep-alive reuse with one resend only when a pooled connection was closed before the request was sent). Recovery bounds: Docker provider `connected` within 40 s of the socket's return; a hanging socket noticed within 45 s (request timeout 30 s); rdock ready within 15 s with the socket absent or hanging; a rolled-back route set served within 1 s of the `200`; configuration writes resume within 30 s of space returning, without a restart; the admin API answers within 10 s after the attack; a flapped backend back in rotation within 10 s; a renewal after the CA returns within 60 s with exactly one order. The data directory: no temporary file left, every stored JSON file parses, history readable; `rdock audit verify` passes after every scenario that writes.
- **Disk-full mechanisms.** `rdock_testkit::disk`: a dedicated tmpfs filled with a ballast file (`ENOSPC`; root or passwordless `sudo`; `RDOCK_CHAOS_DISK=tmpfs`, the `chaos` job), or `RLIMIT_FSIZE` set to zero on the running rdock with `prlimit` (`EFBIG`; rootless; the default, run in `rust`). The second does not lower `statvfs`, so rdock counts the file-size limit as no room; it also makes the test's stdout and stderr files unwritable, which proves log sinks that cannot write do not fail requests, at the cost of the process log during the fault. A restart on a full disk is tested on the tmpfs only. A loop-mounted ext4 (`ENOSPC` at `fsync` with delayed allocation) is not tested.
- **Configuration writes** (the configuration API and its rollback, which share one path): the history entry and the API snapshot are staged (`rdock_config::state::stage`: written and synced to a temporary file) between compiling and handing the runtime to the data plane, and renamed into place after the data plane took it; a staging failure refuses the change with `507` (`ApiWrite::NotStored`), a data-plane refusal drops the staged files. A file reload keeps the best-effort writes (the operator's file is its stored copy). A data plane receiving a bundle already stored it before applying and NACKs on a write error. The control plane maps a state error of a publication to `507` (not covered by a test).
- **Audit order of operations**: reserve first, change second, record third. `Audit::prepare` (called by the authentication middleware for every gated call, and by first-admin setup) reserves `RESERVE` = 16 KiB past the end of the newest file with `fallocate(FALLOC_FL_KEEP_SIZE)`, or checks free space where that is not supported, and refuses when the file-size limit leaves no room (`KEEP_SIZE` is not bound by it). The record of an admitted call then lands in reserved blocks, so lack of space cannot strike between the change and its record; an I/O error other than space still can, and is handled by the next two points. Every append is one write of the line and its newline, then `fdatasync`; any error cuts the file back to its last complete record (`set_len`), retried before the next append if the cut fails, and a torn tail found at a handover is cut too. A lost record is counted (`rdock_admin_audit_write_failures_total`) and the next `prepare` writes an `audit.gap` record naming how many were lost before admitting anything, so the chain stays verifiable and the gap is in the log itself. Logins, logout, the MFA and re-authentication steps, ending one's own sessions and the two dry runs are not gated: a full disk must not lock operators out of the read-only views that show it, and these change no configuration; their records are still attempted and a lost one is counted and followed by the gap record.
- **Certificates**: `Storage::check_room` (`CERT_ROOM` = 1 MiB: journal, chain and key twice, metadata, temporary files, rounded to 4 KiB blocks, about 64 KiB, with a sixteen-fold margin) runs before the certificate lease is taken, since in a single instance the lease is a file too. Cluster stores are not on this file system and are not checked. A write that fails after issuance was already covered by the `next/` + `meta.json` commit and its test; the failure now also counts in `rdock_state_write_failures_total{what="certificate"}`.
- **Writers found on the way** (behaviour on a full disk, before → after): configuration state, ACME storage, the cluster directory store, quota counters, ban lists, the Cloudflare range cache left their temporary file behind → removed; quota counters and ban lists were logged every second → once a minute per file, counted; the disk cache store failed the response → serves it uncached, counted as `rdock_cache_dropped_total{reason="write_error"}`; a held body that could not be spooled failed the request → kept in memory up to 1 MiB; the lock file's pid and the bootstrap token stopped a restart → skipped with a warning; the log subscriber panicked when standard error could not be written → drops the line; users and tokens answered `500` → `507`, nothing changed. Unchanged: the sticky-cookie and QUIC key files (written once at first start; a fresh data directory on a full disk is refused with a clear message), the access log and application log (stdout and stderr, never in the data directory), the TLS session ticket file (read only), the upgrade handover (sockets only), metering (network sinks).
- **ACME, also found on the way**: instant-acme's default client has no request deadline; a `TimedClient` (the same hyper and rustls build) bounds each request and its body to 30 s and remembers `Retry-After` on `429`/`503`, which delays the next attempt. `RDOCK_TEST_ACME_RETRY` (debug builds only) shortens the first backoff for the suite.
- **Free space** is read every 15 s: `rdock_data_dir_available_bytes`, `rdock_data_dir_size_bytes`, `data_dir` in the status document and `rdock status`, and the alert rule `disk` (`observability.alerts.rules.disk`, default 5 % — the node exporter's warning level — or 256 MiB). The dashboard does not show it yet.
- **Not done**: the cluster rollback abandoned under load, and a 3-instance cluster whose lease holder alone cannot reach the CA (by design the failed holder releases the lease and any instance may take it at the next attempt; untested); Toxiproxy toxics against the CA (the fake CA's own modes cover refused, hanging and erroring connections); the Docker image with `--tmpfs` (layer C of the research). The `chaos` job's tmpfs, Toxiproxy, Docker and Pebble variants have not run: the development sandbox cannot pull images (the tmpfs variant did run there, as root).

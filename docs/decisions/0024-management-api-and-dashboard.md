# ADR-0024: Management: admin API, security model, live data and dashboard

- Status: accepted
- Date: 2026-10-31

## Context
v0.5 makes ReverseDock manageable without editing files (M-ADM-01…04, F-UI-01…06, M-OBS-04, M-OBS-05, F-MGMT-01, F-MGMT-04, F-MGMT-05, H-ENG-04). Today's admin listener is a small Pingora app with five routes and one shared token; it cannot stream. [Research](../research/v0.5-management.md) checked the crates, OWASP ASVS 5.0 and the cheat sheets, the admin surfaces of Traefik, Caddy, HAProxy, Envoy and Pingap, the SSE specification, Grafana, Prometheus naming and the Slack, Discord and Standard Webhooks formats on 2026-10-31. The goal set for this milestone is the strongest security of any proxy admin surface and no measurable cost on the request path. Open questions: which server and libraries, how people and programs authenticate, what each role may do, how concurrent edits are handled, how live data reaches the browser without touching the data plane, and what the dashboard is built with.

## Decision

### Server and isolation
- `rdock-admin` becomes an **axum 0.8** server (tower-http for limits, timeouts and headers; **utoipa 6** for OpenAPI 3.1) on its own listener, as before (`admin.listener`, default `127.0.0.1:2080`, [ADR-0019](0019-zero-config-admin-address.md)).
- It runs on its **own tokio runtime with 2 worker threads** (`admin.threads`), so a flood of API requests, slow SSE clients or password hashing can never take worker threads from the proxy. Password hashing runs on a blocking pool capped by `rdock_limits::ConcurrencyLimiter` (2 at a time: 19 MiB each).
- The data plane never calls the admin side ([ADR-0009](0009-provider-ownership-and-merge.md), [ADR-0012](0012-own-listeners-pingora-http-engine.md)). The admin side reads the same `ArcSwap` snapshots and receives events through bounded channels that drop and count when full; it never holds a lock the request path takes. A CI check fails if `rdock-proxy` depends on `rdock-admin` (H-ENG-04).
- Every admin response carries `Cache-Control: no-store` (API), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin` and a CSP of `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'` (inline styles only, because CodeMirror and uPlot insert `<style>` elements; never inline scripts); HSTS when served over TLS. Request bodies are capped (1 MiB by default, 413), media types checked (415), methods allow-listed (405), JSON parsed strictly with unknown fields refused.

### Where the admin listens
- **Loopback by default.** A non-loopback `admin.listener` requires `admin.tls` (certificate and key); plain HTTP on a non-loopback address is refused with a diagnostic, because browsers do not keep `Secure` cookies on plain HTTP to a LAN address.
- **Remote admin over mTLS** (optional): `admin.tls.client_ca_files` makes the listener require a client certificate; `admin.tls.identities` maps certificate names to a role, as Caddy's remote admin does. Certificate identities still pass through the same role checks and audit log.
- **Unix socket for the CLI** (`admin.socket`, default `$RDOCK_DATA_DIR/admin.sock`, mode 0600): `rdock reload`, `status` and the other CLI commands use it, authenticated by file permissions and recorded in the audit log as actor `cli`. The v0.1–v0.4 shared token file `$RDOCK_DATA_DIR/admin/token` is deleted on first start of v0.5; `RDOCK_ADMIN_TOKEN` stays and now carries an API token.
- **DNS rebinding:** requests whose `Host` (and, for unsafe methods, `Origin`) is not in `admin.allowed_hosts` are refused with 421. The default is derived from the listener (`localhost`, `127.0.0.1`, `::1` for loopback). The check is always on, also with authentication; Caddy keeps it, Pingap drops it once credentials exist.

### Identities
- **No default accounts and no credentials on the command line.** At first start, when no admin user exists, ReverseDock writes a **bootstrap token** (`rdk_boot_…`, 160 random bits, `$RDOCK_DATA_DIR/admin/bootstrap-token`, mode 0600) and prints its path, not its value. It allows exactly one action, creating the first admin user, then it is deleted; it expires after 24 hours and a new one is written at the next start while no admin exists (ASVS 6.4.1).
- **Users** have a name, a role and an Argon2id password hash (PHC string). Parameters default to the OWASP minimum m=19456 KiB, t=2, p=1 (`admin.passwords.argon2`); weaker values are refused, stronger ones accepted, and hashes are upgraded at the next login. Passwords: at least 12 characters (configurable, never below 8), up to 128, no composition rules, refused when they appear in the bundled list of the 100,000 most common passwords or in an optional offline breached-password file (`admin.passwords.blocklist_file`). No password ever leaves the process; nothing is sent to an external service.
- **MFA:** TOTP (RFC 6238, HMAC-SHA1 on ring, 6 digits, 30 s, ±1 step, each code usable once) with 10 single-use recovery codes stored hashed. `admin.mfa: required_for_admins` (default), `required` or `optional`. An admin without TOTP must enrol before doing anything else.
- **Login** answers the same 401 body after the same Argon2 work for unknown users (verified against a dummy hash) and wrong passwords (ASVS 6.3.8). Rate limits: 5 attempts per minute per client address (taken from the socket, never from forwarded headers) and 10 per 15 minutes per user name, answering 429 with `Retry-After`; no permanent lockout, so nobody can lock an admin out.
- **Sessions** are server-side: a 256-bit random ID in a `__Host-rdock_session` cookie (`Secure; HttpOnly; SameSite=Strict; Path=/`), stored only as its SHA-256. New ID at login and on every privilege change. Idle timeout 30 minutes, absolute 8 hours (`admin.sessions`, bounded to 5 min–12 h). Logout deletes the session and sends `Clear-Site-Data`. Disabling a user, changing their role, password or MFA ends all their sessions. Users see and end their own sessions; admins end anyone's.
- **Re-authentication:** creating or changing users and tokens, changing roles, MFA reset, rolling back the configuration and exporting it require the password (and TOTP) again within the last 5 minutes (ASVS 7.5.1).
- **CSRF:** a synchronizer token (HMAC-SHA256 of the session ID) returned by `GET /api/v1/session` must be sent as `X-CSRF-Token` on every unsafe method; in addition, unsafe requests whose `Sec-Fetch-Site` is not `same-origin` (falling back to an exact `Origin` match when the header is missing) are refused. No CORS headers are ever sent. Nothing changes state on GET.
- **API tokens** look like `rdk_pat_<id>_<secret><crc32>`: a public 10-character ID for lookup and audit, a 32-character Base62 secret (190 bits) stored only as SHA-256 and compared in constant time, and a CRC32 checksum so scanners and ReverseDock itself reject mistyped tokens without a lookup. The token is shown once. Each has a role no higher than its creator's, an expiry (default 90 days, maximum 1 year; no expiry only with `admin.tokens.allow_no_expiry: true`), an optional CIDR allow-list, and `last_used_at`/`last_used_from`. Tokens are accepted only in `Authorization: Bearer`, never in a query string. The token pattern is published so users can add it to gitleaks, trufflehog or GitHub custom patterns.

### What each role may do
| | viewer | operator | admin |
|---|:-:|:-:|:-:|
| Read configuration (secrets always masked as `***`), status, metrics, logs and events | ✓ | ✓ | ✓ |
| Validate and preview configuration changes | ✓ | ✓ | ✓ |
| Change API-owned routes, services, middlewares and certificates; apply and roll back configuration; reload | | ✓ | ✓ |
| Drain and undrain backends, renew certificates, purge (later) | | ✓ | ✓ |
| Manage users, roles, tokens and sessions; read the audit log; change admin settings; export configuration | | | ✓ |

Checks run on the server per endpoint, per object and per field (ASVS 8.2.1–8.2.3); the dashboard only hides what the server would refuse. A token with the `metrics` role reads `/metrics` and nothing else, for Prometheus. `/metrics` and `/api/openapi.json` require authentication; `admin.metrics_unauthenticated_on_loopback: true` restores today's open `/metrics` on a loopback listener for existing scrapers. Secrets are never returned by any role, never written to the audit log, events, logs or exports, and appear only as `***` or as the `${file:…}`/`${env:…}` reference they came from.

### Audit log
Every write, login (success and failure), logout, MFA event, permission refusal, token use from a new address and session end is recorded as one JSON line in `$RDOCK_DATA_DIR/audit/` (mode 0600): UTC time, sequence number, request ID, actor (user, token ID, certificate identity, `cli` or `bootstrap`), authentication method, client address, action, resource, hashes of the configuration before and after, result and reason. Each line carries the SHA-256 of the previous line, so a removed or edited line breaks the chain, and `rdock audit verify` checks it. Files rotate at 64 MiB and are kept for 400 days (`admin.audit.retention`); the chain continues across files. Records can also be forwarded to an alert channel or syslog (`admin.audit.forward`). Only admins read the audit log.

### Configuration through the API
- `GET /api/v1/config` returns the effective configuration with the owner of each object (`file`, `docker`, `api`, …) and secrets masked; `GET/PUT/PATCH /api/v1/config/api` reads and replaces the API provider's snapshot (`application/merge-patch+json`, RFC 7396, or `application/json-patch+json`, RFC 6902). Objects owned by the file, Docker or Kubernetes providers are read-only through the API (F-UI-03); per-resource endpoints exist for routes, services, middlewares and certificates.
- **Every change needs `If-Match`** with the ETag of the version it was based on (`"g<generation>-<sha256 prefix>"`): without it 428, with an outdated one 412 and the current ETag (RFC 9110, RFC 6585). Caddy makes this optional; we do not.
- `POST /api/v1/config/validate` is a dry run that returns diagnostics and the diff (similar, line based, with a 200 ms deadline); applying goes through the same validate → compile → swap path as a file reload, so the API can never apply what `rdock validate` would refuse. History and rollback use the existing on-disk history; a rollback is itself a conditional, audited write.
- **GitOps mode** (M-ADM-04): `admin.api_writes: false` refuses every write to configuration through the API and the dashboard, for setups where Git and the file provider are the source of truth; import and export (`GET/POST /api/v1/config/export|import`) move the whole API snapshot, with secrets as references only.
- The CLI gains the same operations (`rdock config history|diff|rollback`, `rdock users`, `rdock tokens`, `rdock audit`, `rdock backends drain`), all through the admin socket (F-MGMT-01).

### Live data without touching the request path
- **Metrics ring buffer** in `rdock-observability`: per route and per service, 900 one-second slots holding request, status-class, error and byte counters and a 40-bucket logarithmic latency histogram (50 µs to 60 s, at most 9 % error), about 183 KiB per route. This replaces the DDSketch plan in architecture §14, which needs 0.9–4.5 MiB per route at this resolution. The request path only increments atomics in the current slot: no lock, no allocation. Served by `GET /api/v1/metrics/summary`.
- **Streams** `GET /api/v1/logs/stream` and `/events/stream` are server-sent events: increasing `id`s, a replay buffer (10,000 entries) so `Last-Event-ID` resumes after a reconnect, an `event: reset` when the client fell too far behind, a comment every 15 seconds, `X-Accel-Buffering: no`, no compression. Filters run on the server; log lines pass through the same redaction as the access log. Each subscriber has a bounded queue that drops (and sends `event: lagged`) instead of slowing anyone down; at most 4 streams per identity. Streams re-check authorization every 60 seconds and close when the session or token ends; a revoked client gets 204 so the browser stops reconnecting. Browsers authenticate streams with the session cookie.
- The admin side exports its own metrics: `rdock_admin_requests_total{endpoint,status_class}`, `rdock_admin_login_failures_total`, `rdock_admin_sse_subscribers`, `rdock_admin_sse_dropped_events_total`, `rdock_alerts_sent_total{channel,result}`.

### Alerts and webhooks (M-OBS-04, F-MGMT-04)
`observability.alerts` gains channels — `slack`, `discord` (native payload with `allowed_mentions` empty, so host names cannot ping everyone), `slack_compatible` (Discord's `/slack`, Mattermost, Rocket.Chat), `webhook` (signed with Standard Webhooks: `webhook-id`, `webhook-timestamp`, `webhook-signature`, `whsec_` secrets) and `smtp` (lettre over rustls with ring; STARTTLS or implicit TLS; plaintext only to a loopback relay) — and rules for certificate renewal failures and expiry, backend and service down, error rate and p99 above a threshold, rejected configurations and admin security events. The v0.3 `alerts.webhook` keeps working as a `webhook` channel. Alerts fire and resolve, are deduplicated with a minimum interval, and are delivered from a bounded queue with jittered retries, never from the request path. Outbound delivery refuses private, loopback and link-local targets unless a channel sets `allow_private_targets: true`, follows no redirects and times out after 5 seconds. Webhook URLs, tokens and SMTP passwords are secrets.

### OpenAPI and clients (F-MGMT-01)
The OpenAPI 3.1 document is generated from the code and served at `/api/openapi.json`; a copy is committed in `schema/openapi.json` and CI fails when it is out of date. A conformance test runs every documented request and checks responses against the document. A typed TypeScript client is generated for the dashboard and a Go client in `clients/go`, both checked for drift in CI.

### Dashboard (F-UI-01…06)
- An SPA in `apps/dashboard` following the [design system](../08-design-system.md), **English only** (no RTL or translations; this replaces the Arabic and RTL items of the design system and F-UI-01). Built with Vite, React 19, Tailwind v4, shadcn/ui on Base UI, TanStack Query, Table and Router, CodeMirror 6, uPlot and a client generated by `@hey-api/openapi-ts` ([research](../research/v0.5-management.md#8-dashboard-frontend)); npm dependencies are pinned exactly and their licences checked in CI. It is embedded with rust-embed (`admin.dashboard: true`), served with strong ETags, pre-compressed `.br`/`.gz` files, `immutable` caching for hashed assets and no external request of any kind: fonts and icons are bundled.
- Pages: Overview, Routes, Services, Middlewares, Certificates, Listeners, Providers, Security (users, tokens, sessions, audit), Logs, Metrics, Config (editor with schema completion, validate, diff, apply, history, rollback) and Settings. Objects show their owner; only API-owned objects are editable. Light and dark mode; keyboard navigation; WCAG 2.2 AA.
- Budget: initial load at most 300 KiB of compressed JavaScript and CSS, with the config editor and charts loaded only on their pages; Lighthouse performance ≥ 95 on the Overview page.
- Done when (roadmap): Playwright covers every page in light and dark mode at 400–1440 px with axe accessibility checks, and fails on any request that leaves the admin origin.

### Docs site (F-MGMT-05) and Grafana (M-OBS-05)
The website gains a configuration playground that validates YAML against the published JSON Schema entirely in the browser. `deploy/grafana/` ships a dashboard in Grafana's Classic JSON model (data source as a variable, fixed `uid`) with provisioning YAML; CI checks that every metric it queries is exported.

### Dependencies
New: axum, tower-http, utoipa, utoipa-axum, rust-embed, lettre (no default features), similar, json-patch (no `utoipa` feature). `deny.toml` bans `openssl-sys`, `openssl`, `native-tls`, `aws-lc-sys` and `aws-lc-rs`, so a default feature can never bring another TLS stack in.

## Consequences
- The admin surface becomes the largest attack surface after the proxy itself; it is designed against ASVS 5.0 level 2 with the level 3 items above (constant-time compares, enumeration resistance, immediate permission changes), and v0.5 is done only after the security review checklist for it is complete.
- Upgrading from v0.4: the shared admin token file goes away. The CLI keeps working through the admin socket; scripts that read the token file must create an API token. `/metrics` needs a token unless `admin.metrics_unauthenticated_on_loopback` is set. Both are breaking and are listed in the changelog and the upgrade guide.
- First start requires creating an admin user (with TOTP) before the dashboard is usable; the bootstrap token path is printed in the log.
- The admin runtime adds 2 threads and, with the metrics ring buffer, about 183 KiB per route of memory. The request path gains a handful of atomic increments per request; the nightly benchmark check guards that.
- WebAuthn is not part of v0.5: the maintained Rust implementation depends on OpenSSL. TOTP covers MFA until a ring-based option exists.
- The configuration model grows `admin.tls`, `admin.socket`, `admin.allowed_hosts`, `admin.threads`, `admin.sessions`, `admin.passwords`, `admin.mfa`, `admin.tokens`, `admin.audit`, `admin.api_writes`, `admin.metrics_unauthenticated_on_loopback` and the alert channels and rules; each has a safe default and unsafe combinations are refused.

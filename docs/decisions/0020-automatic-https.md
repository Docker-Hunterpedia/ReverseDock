# ADR-0020: Automatic HTTPS: ACME manager, challenges, renewal and the local CA

- Status: accepted
- Date: 2026-10-28

## Context
v0.3 makes HTTPS automatic (B-TLS-02…08, B-TLS-12, B-TLS-13, W-DNS-01, W-CF-01…05). Architecture §10 sketches the ACME manager; [research](../research/v0.3-automatic-https.md) checked the libraries and the CA landscape on 2026-10-28. Since that sketch, Let's Encrypt has moved: profiles with 45-day and 6-day certificates, `classic` shrinking to 64 days in 2027 and 45 days in 2028, OCSP turned off, and ARI renewals exempt from rate limits. In v0.1 and v0.2, a `tls: auto` route without a matching certificate is refused with "planned for v0.3" ([ADR-0018](0018-docker-provider-and-merge.md)). Open questions: which client library, how challenges reach the data plane without coupling it to the manager, what one certificate covers, when to renew, what is on by default, and what happens for names no public CA will sign.

## Decision

**Library.** `rdock-acme` uses `instant-acme` 0.8 with `default-features = false` and the `ring`, `hyper-rustls`, `time` and `x509-parser` features ([ADR-0013](0013-tls-crypto-provider-ring.md)). `rcgen` builds CSRs, TLS-ALPN-01 validation certificates and the local CA. Certificate keys are ECDSA P-256. The challenge solvers, the scheduler and storage are our own code.

**Separation from the data plane.** The ACME manager is a background task, like a provider ([ADR-0009](0009-provider-ownership-and-merge.md), [ADR-0012](0012-own-listeners-pingora-http-engine.md)). It writes to three lock-free maps that the data plane only reads: HTTP-01 tokens (answered on every plain listener at `/.well-known/acme-challenge/<token>` before routing), TLS-ALPN-01 validation certificates (chosen by the resolver when the ClientHello offers exactly `acme-tls/1`; that handshake is closed without HTTP) and issued certificates (merged into the SNI index next to manual ones; a manual certificate for the same name wins). Issuing or renewing a certificate swaps the index; it is not a configuration reload. If the manager stalls, existing certificates keep serving.

**What gets a certificate.** After each apply, the desired set is computed from the compiled configuration: every `Host(…)` name of a route with `tls: auto` (explicit or from `defaults.tls`) on a TLS listener that no manual certificate covers. `HostRegexp` and `Host` with `*` are not eligible (on-demand TLS stays P2). **One certificate per name**, so one failing name never blocks another. `tls.domains` overrides this for its route: one certificate with exactly those names (for wildcards, or to group names). Names are deduplicated across routes and providers. A name that leaves the desired set keeps its certificate on disk until it expires, but is no longer renewed.

**Challenges.** All three challenge types are available, for any name. `acme.challenges` (default `[http-01, tls-alpn-01]`) is tried in order, filtered by what can work: HTTP-01 needs a plain listener and TLS-ALPN-01 a TLS listener. The CA connects to ports 80 and 443, but the listeners may use other ports behind a port mapping (`-p 80:8080`), so the port is not checked. When a challenge fails, the next attempt uses the next type, as Caddy does. DNS-01 is used for a route that names `tls.dns_provider`, for every route when `acme.dns_provider` sets a default, and always for wildcards (which only DNS-01 can validate). It also covers names the CA cannot reach, such as hosts behind a firewall or a Cloudflare Tunnel. DNS-01 goes through a `DnsProvider` trait in `rdock-acme` (create and remove a TXT record) with these adapters:

- `cloudflare` in `rdock-cloudflare`: a token needing Zone → DNS → Edit, and an optional `zone_id`;
- `exec`: runs a configured program with `present`/`cleanup`, the name and the value as arguments (never through a shell), with a timeout (W-DNS-02, moved from v0.6);
- `webhook`: POSTs the same as JSON to an `https://` URL, with an optional bearer token taken from a `${file:…}` or `${env:…}` reference (W-DNS-02).

The record is checked at the zone's authoritative nameservers (`hickory-resolver`, ring features) before the CA is told to validate, following a CNAME on `_acme-challenge` (delegation). After 2 minutes the check is skipped and the CA validates anyway. Records are removed after validation, successful or not.

**Renewal.** Right after issuance and then whenever Retry-After expires, `renewalInfo` is fetched (RFC 9773); the renewal time is a uniform random point in the suggested window, and renewal orders carry `replaces`. If the CA has no ARI, or ARI fails, renewal starts when a third of the lifetime remains, measured on the certificate itself (`notAfter − notBefore`), so it works for 90-, 64-, 45- and 6-day certificates alike. Every certificate, renewals included, gets a new private key. A failed attempt is retried once after a short pause, then with the next challenge type. Against Let's Encrypt, retries after a failure first validate against the staging directory and return to production only once staging succeeds, so a misconfigured name does not use up production rate limits (Caddy does the same). Further failures back off exponentially from 1 minute to 24 hours with jitter. The existing certificate keeps serving until it expires. `rateLimited` and `alreadyReplaced` errors are handled specifically (wait for Retry-After; fetch ARI again). At most 4 orders run at once per CA, and an identical order is never started twice.

**Profiles, CAs, EAB.** ReverseDock renews through ARI and never by hand, which is the case Let's Encrypt recommends `tlsserver` for ("fully embrace automation", [profiles](https://letsencrypt.org/docs/profiles/), checked 2026-10-28). So when `acme.profile` is not set, an order asks for `tlsserver` if the CA's directory advertises it, and otherwise sends no profile (CA default). That also matches where `classic` is heading (45 days in 2028). `acme.profile` set explicitly is always sent, and an unknown profile is an error naming the ones the directory lists. An IP-address host requires `profile: shortlived` and HTTP-01 or TLS-ALPN-01. `acme.ca` takes the known names or a directory URL, and `acme.ca_root` trusts the root of a CA whose endpoint is not publicly trusted (an internal step-ca, or Pebble in tests); `ca: buypass` is refused, because Buypass stopped issuing certificates on 2025-10-16 ([Buypass](https://www.buypass.com/products/tls-ssl-certificates/go-ssl), checked 2026-10-28); `staging: true` switches Let's Encrypt to its staging directory. EAB (`acme.eab`) is passed to account creation. No order asks for OCSP Must-Staple. Stapling is attempted only when a certificate carries an OCSP URL (B-TLS-07), so Let's Encrypt certificates get none.

**On by default.** Without an `acme` section, ACME runs with the defaults: Let's Encrypt production, no contact address, the profile rule above. Let's Encrypt stopped sending expiry emails on 2025-06-04 ([announcement](https://letsencrypt.org/2025/01/22/ending-expiration-emails/), checked 2026-10-28), so the contact address is optional and expiry warnings come from ReverseDock's own alerts. Running it means accepting the CA's terms of service; the account's terms URL is logged once at creation, and the docs say so on every HTTPS page. `acme: false` turns automatic issuance off; `tls: auto` routes then need manual certificates, as in v0.2.

**Names a public CA will not sign.** `localhost` and `*.localhost`, `.local`, `.internal`, `.home.arpa`, `.test` and `.example`, and loopback or private IP addresses (RFC 1918, `fc00::/7`) get a certificate from the **local CA** instead of ACME. The CA is created on first use in `$RDOCK_DATA_DIR/pki/` (keys 0600): a P-256 root valid for 10 years whose **name constraints** permit only those names and address ranges, so even a leaked root key cannot sign a public name; an intermediate valid for 30 days that does the signing, so the root key is used only to rotate it; leaves valid for 7 days, renewed at a third remaining. Single-label names (`nas`) cannot be expressed in name constraints and do not get a local certificate; the diagnostic suggests `nas.internal` or `nas.home.arpa`. `rdock trust` installs the root into the OS trust store by calling the platform tool (`security` on macOS; the anchors directory plus `update-ca-certificates`, `update-ca-trust` or `trust` on Linux; NSS `certutil` when present), and `rdock trust --uninstall` removes it. On Windows it prints the `certutil -addstore ROOT` command. Trust installation is never automatic.

**Storage.** `$RDOCK_DATA_DIR/acme/` (or `acme.storage`): `accounts/<ca-host>/account.json` and `certs/<name>/{cert.pem,key.pem,meta.json}`, written with mode 0600 and atomic rename. `meta.json` holds names, issuer, validity, profile, ARI window, the certID and the last error. A lock file (`acme/lock`, created exclusively, refreshed every 10 s, stale after 30 s) keeps two processes sharing a data directory from ordering twice. Clustered storage stays P3.

**Alerts (B-TLS-12).** Metrics `rdock_cert_expiry_timestamp_seconds{name,source}`, `rdock_cert_renewal_failures_total{name}` and `rdock_acme_orders_total{ca,result}`; a warning log line and an entry in `rdock status` after 3 consecutive failures or when a certificate has less than 7 days left; and an optional `observability.alerts.webhook` URL that receives the same events as JSON.

**Cloudflare (W-CF-01, W-CF-02).** `security.trusted_proxies: [cloudflare]` uses Cloudflare's published ranges, fetched from `api.cloudflare.com/client/v4/ips` once a day (honouring `etag`), cached in the data directory and backed by a list compiled into the binary, so startup never waits for the network. `client_ip_header: cf-connecting-ip` takes the address from `CF-Connecting-IP` only when the peer is inside those ranges. `CF-Ray` is added to the access log when present.

**Zero-config mode (v0.3 form).** The [ADR-0018](0018-docker-provider-and-merge.md) defaults gain listener `websecure` on `:443` and `defaults.listeners: [websecure]` with `tls: auto`. `web` on `:80` redirects to HTTPS and answers HTTP-01. ACME uses the defaults above. Labels with `rdock.tls=off` keep serving plain HTTP on `web`. The admin listener stays on its default ([ADR-0019](0019-zero-config-admin-address.md)).

## Consequences
- Pointing DNS at the host and adding one label or one `Host(…)` route is enough for a trusted certificate, and the "planned for v0.3" refusal of `tls: auto` is gone.
- A new behaviour on upgrade: `tls: auto` routes that v0.2 refused now order certificates from Let's Encrypt production. The changelog and the upgrade page say so, together with `acme: false` and `staging: true`.
- One certificate per name means more orders on first start than grouping would, but renewals through ARI are exempt from rate limits, and a bad name never holds others back.
- The data plane depends only on three read-only maps; ACME, DNS and CA outages never stop traffic that already has certificates.
- New dependencies: `instant-acme` (ring) and `hickory-resolver` (ring). `rdock-cloudflare` gets an HTTP client through `hyper-rustls`, which instant-acme already brings in.
- CI runs Pebble and `pebble-challtestsrv` containers for issuance, ARI renewal, CA outage and wildcard DNS-01 tests, gated like the Docker end-to-end tests.
- Authenticated Origin Pulls (W-CF-08) waits for mTLS in v0.4; on-demand TLS and DNS-PERSIST-01 are not part of v0.3.
- W-DNS-02 (exec and webhook DNS providers) moves from v0.6 to v0.3, so any DNS host works from the first HTTPS release; the named adapters of W-DNS-03 stay in v0.6.

# ReverseDock — Roadmap

Milestones, not dates. Each milestone ships a usable binary and has acceptance criteria that CI can verify. Requirement IDs refer to [04-requirements.md](04-requirements.md); P-levels to the [feature matrix](03-feature-matrix.md). Every ID in 04 appears in exactly one milestone below or in the *Unscheduled* list at the end.

| Milestone | Theme | You can… |
|---|---|---|
| **M0** | Foundations | build, lint, test, release; model + schema exist |
| **v0.1** | Hello proxy | replace NGINX for host/path routing with manual certs |
| **v0.2** | Docker-native | replace Traefik on a Compose/Dokploy box using existing labels |
| **v0.3** | Automatic HTTPS | go from DNS → HTTPS with one label; survive 45-day certs |
| **v0.4** | Production reliability | run busy APIs: LB, health, retries, limits, mTLS, JWT, compression |
| **v0.5** | Management | operate it from a dashboard and REST API with history/rollback |
| **v0.6** | Swarm + L4 + static | multi-node Docker, TCP/SNI passthrough, static sites, more DNS providers |
| **v0.7** | Kubernetes | run it as a Gateway API controller |
| **v0.8** | Cache + extensibility | cache like NGINX, extend with plugins/agents, API-gateway features |
| **v0.9** | Scale | multi-instance control plane, distributed limits, zero-downtime binary upgrade, HTTP/3 (experimental) |
| **v1.0** | Stable | stability guarantees, audit, conformance, docs site |

## M0 — Foundations
**Status:** implemented; first published pre-release `0.1.0-alpha.2`: workspace, `rdock-rules`, `rdock-model` + schema, `rdock-config` loader, `rdock validate|schema|version`, CI, release pipeline, Dockerfile.
**Scope:** workspace skeleton (all crates with READMEs), `rdock-model` + JSON Schema export, `rdock-rules` parser with property tests, CI (fmt/clippy/nextest/deny/audit/Semgrep), release pipeline (`cargo-dist`, checksums, SBOM, cosign — empty releases are fine), `justfile`, Dockerfile skeleton, CONTRIBUTING/SECURITY/CoC/issue templates, ADRs 0001–0010. IDs: F-OSS-01, F-OSS-02, F-OSS-03.
**Done when:** `just ci` is green; `schema/rdock.v1.json` is generated and validated against the YAML examples in `docs/05-architecture.md`; a tagged pre-release produces signed artifacts.

## v0.1 — Hello proxy (P0 core)
**Status:** released as `0.1.0-alpha.3`. Listener changes apply in-process without a restart ([ADR-0012](decisions/0012-own-listeners-pingora-http-engine.md), superseding ADR-0008); settings planned for later versions are reported by `rdock validate` and refused by `rdock run` ([ADR-0014](decisions/0014-http-semantics-v0-1.md)).
**Scope:** B-NET-01…13, B-TLS-01/09/10/11, B-CFG-01…10, B-SEC-01…09, B-SEC-11, B-SEC-12, B-OBS-01…03, F-OSS-04, W-PLAT-01/03/05, W-OBS-01…03 (P0 parts). File provider with watch, SIGHUP/CLI reload, LKG, history, `restart required` path for listener changes (ADR-0008). Middlewares: headers, redirect, rewrite/strip/add prefix, basic_auth, forward_auth, ip_allow/deny, rate_limit, cors, compress (gzip), errors, maintenance. Error pages. `rdock validate|run|reload|status|version`. Official image + Compose example + systemd unit.
**Done when:** e2e suite proves h1/h2/h2c/WebSocket/SSE/gRPC proxying, forwarded-header rules, reload under load (no failed requests in a 60 s `oha` run during 20 reloads), listener-change restart path under Docker and systemd, smuggling test vectors rejected, differential fuzz target exists.

## v0.4 — Production reliability (P1 traffic)
**Status:** released as `0.4.0-alpha.1`. Design: [ADR-0022](decisions/0022-production-reliability.md); research: [v0.4 production reliability](research/v0.4-production-reliability.md). Plan and issues: the [v0.4 milestone](https://github.com/Docker-Hunterpedia/ReverseDock/milestone/5). Order: configuration model → backend state and balancing → health and circuit breaking → retries → routing (splits, mirroring, gRPC-Web) → limits and compression → client certificates and Cloudflare AOP → JWT → tracing and metrics → DNS discovery and ping → chaos suite and benchmarks → release. M-TM-05 (request buffering) moves to v0.8: Pingora 0.9 replays at most 64 KiB of a request body, so a whole upload cannot be held before it is forwarded without an upstream change. The 24 h soak and memory-leak tests (H-ENG-02, H-ENG-03) passed on the v0.5 release candidate ([results](../benchmarks/results/2026-11-02-small-cpu/soak/report.md)). The overload collapse found by the first benchmarks ([#86](https://github.com/Docker-Hunterpedia/ReverseDock/issues/86)) is fixed by [ADR-0023](decisions/0023-upstream-connection-pool.md).
**Scope:** M-LB-01…10, M-TLS-01, M-SEC-01, M-RT-02…07, M-TM-01…04, M-TM-06, M-TM-07, M-OBS-01/02/03, M-L4-05, W-CF-07, W-CF-08, H-ENG-01…03 (first benchmark publication). Retries per ADR-0010 (transport failures before response headers).
**Done when:** chaos suite (toxiproxy: latency, resets, partial outages; backend flapping) passes with documented behaviour; retry budget prevents amplification in a simulated outage; mTLS and JWT suites pass; published benchmark report vs NGINX/Traefik/Caddy/HAProxy with identical configs.

## v0.5 — Management (P1 admin)
**Scope:** M-ADM-01…04, F-UI-01…06, M-OBS-04, M-OBS-05 (Grafana dashboards), F-MGMT-01/04/05 (docs site v1), H-ENG-04, audit log, tokens/RBAC, SSE logs/events, ring-buffer charts, config editor with schema validation + diff + rollback, OpenAPI + generated TS client.
**Status:** released as `0.5.0-alpha.1`. Design: [ADR-0024](decisions/0024-management-api-and-dashboard.md); research: [v0.5 management](research/v0.5-management.md). Plan and issues: the [v0.5 milestone](https://github.com/Docker-Hunterpedia/ReverseDock/milestone/6). Order: admin server and security model → users, sessions, MFA and tokens → audit log → configuration API (If-Match, history, rollback, GitOps mode) → live data (ring buffer, SSE) → OpenAPI and clients → alerts and webhooks → dashboard shell and pages → Grafana and docs playground → isolation tests and security review → release. The dashboard is English only. Performance on small machines ([#93](https://github.com/Docker-Hunterpedia/ReverseDock/issues/93)): with the open-file limit raised, mimalloc, no `getrandom` per request and buffered writes to the client, ReverseDock on 2 CPUs completes about twice what 0.4.0-alpha.1 did and as much as NGINX, with no failed requests under overload; HAProxy stays ahead on plain throughput ([results](../benchmarks/results/2026-11-02-small-cpu/report.md), follow-up [#176](https://github.com/Docker-Hunterpedia/ReverseDock/issues/176)). The release candidate passed the [24-hour soak](../benchmarks/results/2026-11-02-small-cpu/soak/report.md) with the admin side on: 86 million requests, none failed, memory flat, every reload applied (H-ENG-02, H-ENG-03).
**Done when:** Playwright suite covers all pages in light and dark mode at 400–1440 px, with axe checks and no request leaving the admin origin; API conformance tests against OpenAPI; admin never on request path (verified by killing the admin task under load — H-ENG-04); security review checklist for the admin surface complete.

## v0.7 — Kubernetes (P2)
**Scope:** W-K8S-01…05, Helm chart, Ingress translation, leader election, status conditions.
**Status:** released as `0.8.0-alpha.1`, together with v0.8 (there is no 0.7 release: the release workflow refuses a tag that does not match the workspace version in `Cargo.toml`, so v0.7 could not be tagged after v0.8 had landed on `main`). **No soak, no benchmark and no multi-node lab were run for this release**; the evidence is the CI listed below. Research: [v0.7 research](research/v0.7-kubernetes.md); design: [ADR-0029](decisions/0029-kubernetes-gateway-api.md). Delivered: a Gateway API v1.7.0 controller in the same binary (GatewayClass, Gateway, HTTPRoute, GRPCRoute, TLSRoute with passthrough, TCPRoute, ReferenceGrant, ListenerSet; one Service and address per Gateway; status written by a Lease leader), EndpointSlice backends, TLS from Secrets and cert-manager, Ingress translation with the ingress-nginx annotations that map one to one onto a middleware, the Helm chart, raw manifests and Kustomize base, examples, and the model changes the controller needs (providers contribute listeners and certificates, per-listener certificates, `redirect` with `hostname`, `path`, `prefix` and `status`, services that answer a fixed status). **What is proven where:** the translator and the status computation are tested on fixtures, among them transcriptions of the upstream conformance tests; the chart is linted, rendered and checked with kubeconform in the `chart` job of `.github/workflows/kubernetes.yml`; the cluster runtime has tests against a bare kube-apiserver that run when `RDOCK_TEST_KUBECONFIG` is set (they are not wired into CI). Nested Kubernetes does not run in the development sandbox, so the cluster steps are proven by two CI jobs of `.github/workflows/kubernetes.yml`. **Both passed on 2026-11-11, on commit `19e88cc` ([run](https://github.com/Docker-Hunterpedia/ReverseDock/actions/runs/43046671411))**: `gateway-conformance` ran the upstream Gateway API v1.7.0 conformance suite (Standard channel CRDs) on kind (kind v0.33.0, node image v1.37.0, Service addresses from cloud-provider-kind) against the chart-installed controller, with the features inferred from `GatewayClass.status.supportedFeatures`, and reported, with no test skipped and none failed: `GATEWAY-HTTP` core 40 passed and extended 31, `GATEWAY-GRPC` core 17 and extended 7, `GATEWAY-TLS` core 21 and extended 8, `GATEWAY-TCP` core 20 and extended 7. "Extended success" means every test for the extended features this implementation claims (`crates/providers/rdock-provider-kubernetes/src/features.rs`) passed; it does not mean every extended feature of the Gateway API is supported. The same core results were obtained on two earlier commits of the branch the same day, before ListenerSet support was added (19 extended tests for HTTP only). `helm-k3s` installed the chart with `helm install --wait` on k3s v1.37.2+k3s1 without Traefik, applied the Gateway and HTTPRoute of `examples/kubernetes/` and got answers from the echo pods through the Gateway's address over HTTP and HTTPS, ran `helm upgrade` (three replicas, same Gateway address, still serving) and `helm uninstall` (no per-Gateway Service left). The job does not test Ingress, cert-manager, RKE2 or the namespaced mode. Both jobs now fail the workflow; they are not yet in the repository ruleset's required checks (only a maintainer can add them). **Not done:** no conformance report has been committed or submitted to the upstream Gateway API repository: a report must come from a run against the released tag (`implementation.version` is the tag), see `tests/conformance/gateway-api/README.md`; the chart is not published to an OCI registry (the release workflow does not push it), so it is installed from a checkout of the tag. The release PR ticked W-K8S-01…04 in [04](04-requirements.md); W-K8S-05 stays open because RKE2 has no job and is untested. **Left out:** UDPRoute and UDP listeners (M-L4-04, v0.8; added there, and `GATEWAY-UDP` passes on kind in the same job, 2026-11-12, commit `43d81de`), `timeouts.request` and `retry` on routes (the data plane has no total request deadline or per-route retry policy), several mirrors per rule, filters on one of several backends, the Gateway API CORS filter, static Gateway addresses, `GatewayHTTPListenerIsolation`; BackendTLSPolicy is applied but not claimed; a Gateway's `supportedFeatures` lists only what the translator claims. The chart's default image tag, `0.8.0-alpha.1`, is the first published image that contains the controller.
**Done when:** upstream Gateway API conformance profiles `GATEWAY-HTTP`, `GATEWAY-GRPC`, `GATEWAY-TLS` pass on kind in CI (`GATEWAY-TCP` is a regular profile in Gateway API v1.7.0 and runs too; `GATEWAY-UDP` waited for M-L4-04 in v0.8 and passes on kind since 2026-11-12, commit `43d81de`: core 21 and extended 7 passed, so all five profiles pass); Helm install on k3s documented and tested. **Met in CI:** the three named profiles (and `GATEWAY-TCP`) pass on kind, and the Helm install on k3s is tested in CI and documented (2026-11-11, commit `19e88cc`, [run](https://github.com/Docker-Hunterpedia/ReverseDock/actions/runs/43046671411)). Released as `0.8.0-alpha.1`; no report has been submitted upstream yet.

## v0.8 — Cache and extensibility (P2)
**Scope:** M-TM-05 (request buffering, from v0.4), F-WEB-02, F-WEB-03 cache (memory + disk, purge API, SWR/SIE), F-EXT-01…05 (stable native trait, WASM experimental, out-of-process agents, plugin SDK + signatures), F-GW-01…05, W-CF-06 (Cloudflare Access JWT), M-L4-04 UDP, F-MGMT-02 Terraform provider (W-OBS-03 P2 part), W-OBS-02 Vault/External Secrets, status-code retries if the upstream Pingora hook landed (ADR-0010).
**Done when:** cache conformance against an RFC 9111 test-suite subset; stampede test shows a single origin fetch; plugin SDK with two example plugins; WAF agent example (CRS-compatible engine) wired as an agent.
**Status:** released as `0.8.0-alpha.1`, together with v0.7. **No soak, no benchmark and no multi-node lab were run for this release**; the evidence is the CI listed below. The release PR ticked in [04](04-requirements.md) the IDs delivered in full (M-L4-04, F-EXT-01, F-EXT-02, F-GW-02…05, F-WEB-02, W-CF-06, W-OBS-02); M-TM-05, F-WEB-03 (background refresh for `stale-while-revalidate`), F-EXT-03 and F-EXT-05 (WASM is not in release builds), F-EXT-04 (gRPC and SPOP agents), F-GW-01 (external key store) and F-MGMT-02 (provider not published) stay open. **The four "done when" proofs:** (1) *cache conformance against an RFC 9111 test-suite subset* is **met, with two allow-listed required failures**: on 2026-11-12, commit `c292639`, the `http-cache` job ran `http-tests/cache-tests` (commit `7e2c53785f41eedc57aa73c8cc19a6729eef39ed`, Node.js 24) against the cache at its safe defaults and the gate passed with 205 tests passing and 2 required failures, both on the reviewed `tests/conformance/http-cache/allowlist.json` (`other-date-update`, `other-date-update-expires`); the rest of the run: 35 optional failures, 54 "check" tests answering yes and 36 no, 4 setup failures (the suite's `Set-Cookie` storage tests: rdock refuses to store `Set-Cookie` by default), 4 harness failures (interim 1xx responses), 26 tests not evaluated because a test they depend on did not pass, 5 untested; (2) the *stampede test* passes (one origin fetch for 50 concurrent misses); (3) the *plugin SDK with two example plugins* exists and is tested in the `rust` job; (4) the *WAF agent example* runs in the `waf-example` job. Beyond the four proofs, `GATEWAY-UDP` passed on kind in CI on commit `43d81de` (core 21, extended 7), so all five Gateway API profiles pass. **Left open after v0.8** (by decision or limitation): full request pre-buffering (M-TM-05) and, because of it, the request head reaches the backend before an agent or `validate` body verdict (a Pingora 0.9.1 limitation); background refresh for `stale-while-revalidate`; gRPC and SPOP agents; publication of the Terraform provider (needs its own public repository `terraform-provider-reversedock` and a signing key, both maintainer actions); the `Date` rewrite (needs an upstream Pingora change); a dashboard UI for consumers, keys and quotas; OIDC back-channel logout and early session revocation; the RFC 7662 external key store; the 2-CPU before/after benchmark that ADR-0030 asks for was **not run**; and the jobs `http-cache`, `openbao`, `oidc-dex`, `wasm`, `waf-example` and `terraform-provider` are **not required checks** (only a maintainer can add them to the ruleset). WASM plugins are implemented but experimental, behind the cargo feature `wasm`, off in default builds, tested in the `wasm` job.
**Cache (F-WEB-03) status:** released in `0.8.0-alpha.1` ([ADR-0030](decisions/0030-v0-8-cache-extensibility-gateway.md), crate `rdock-cache`): memory and disk stores, RFC 9111 storability, freshness, revalidation, `Vary` and invalidation, request coalescing, `stale-if-error`, tags and the admin purge API (one instance). The stampede test passes (50 concurrent misses, one origin fetch; plus the failing-origin, uncacheable and lock-timeout variants) in `crates/rdock/tests/e2e_cache.rs`. **RFC 9111 suite:** the `http-cache` job (`.github/workflows/cache.yml`) runs the public suite `http-tests/cache-tests`, pinned by commit, against the cache at its safe defaults. Its first complete run (2026-11-12) had 8 failing required tests; six were fixed with an end-to-end test each (`no-cache` beside `max-age`/`Expires`, the first member of `Age`, and `CDN-Cache-Control`, now honoured by default as RFC 9213 describes, option `targeted`). The ADR-0030 gate is in place: the job fails on a failing required test that is not on `tests/conformance/http-cache/allowlist.json` (id and reason) and on a stale entry; it is **not a required check** until a maintainer adds it to the ruleset. **Known defect (allow-listed):** a stored response is served with the current `Date` instead of the origin's (`other-date-update`, `other-date-update-expires`), because Pingora 0.9.1 replaces `Date` on every response it writes and has no setting to stop it; it needs an upstream Pingora change. **Not done:** background refresh for `stale-while-revalidate` (open by decision, refused as planned).
**Extensibility (F-EXT-02, F-EXT-04, F-EXT-05 SDK half) status:** released in `0.8.0-alpha.1` ([ADR-0030](decisions/0030-v0-8-cache-extensibility-gateway.md)): the `rdock-plugin-api` crate (own `0.x` line), `type: plugin` with panic isolation, `rdock` as a library (`rdock::run(registry)`), the `testing` harness, the two example plugins `header-rewrite` and `ip-blocklist` with a `custom-rdock` binary and a template (all tested in the `rust` job), and `type: agent` (`rdock` JSON and `forward` protocols, fail closed, circuit breaker). The WAF proof is `examples/waf`: the CRS project's ModSecurity image as a `forward` agent, whose smoke test (clean request 200, attacks 403, stopped WAF refused) runs in the `waf-example` job. **Not done:** gRPC agents (`ext_proc`, `ext_authz`) and SPOP are refused as planned.

**WASM plugins and signatures (F-EXT-03, F-EXT-05 signature half) status:** in the source of `0.8.0-alpha.1` as the experimental last step, behind the cargo feature `wasm` that no default build, release binary, image or required CI job enables (build with `--features wasm` to use it) ([ADR-0030](decisions/0030-v0-8-cache-extensibility-gateway.md)): the crate `rdock-wasm` on wasmtime 36.0.20 (the LTS line whose MSRV 1.86 fits 1.89), `type: wasm` with the WIT world `rdock:plugin/filter@0.1.0` (head phases only), a fresh instance per request with fuel, epoch-deadline and memory limits, no WASI, capability grants `log`/`clock`/`random`, `on_error` fail closed by default, and modules checked against a `sha256` pin and a minisign signature (Ed25519 on ring, BLAKE2b-512 for the prehashed `ED` form, legacy `Ed` accepted) before they are compiled. A build without the feature refuses `type: wasm` with "this build does not include WASM plugins; build with --features wasm". Tests run in the non-required `wasm` job (`just wasm`): limits and traps, import checks, signatures good/bad/missing/wrong key, the `no_std` Rust example guest `examples/plugins/wasm-header` built for `wasm32-wasip2`, and an end-to-end run of the real binary with reloads. **Not done:** bodies and the `upstream_request`/`log` phases for WASM, outbound HTTP from a guest, modules from URLs or OCI registries, Sigstore signatures, and `rdock plugin check`.
**Gateway (W-CF-06, F-GW-01, F-GW-02, F-GW-04 envelope half, F-GW-05) status:** released in `0.8.0-alpha.1` ([ADR-0030](decisions/0030-v0-8-cache-extensibility-gateway.md)): `cloudflare_access`; `errors.format` with RFC 9457 problem details for every answer rdock makes; the crate `rdock-credentials`, `consumers` and `api_key` with keys minted and revoked through the admin API and `rdock keys`; `rate_limit.key: consumer` with group overrides and the `quota` middleware with persisted counters; `observability.metering` to a CloudEvents webhook and OTLP logs; `oidc` login (PKCE, stateless encrypted sessions, refresh, logout; a fake provider in the testkit and the CI job `oidc-dex` against Dex v2.46.1) and `jwt.consumer_claim`. Open in v0.8: the RFC 7662 external key store.
**Validation, transformation and secrets (F-GW-03, F-GW-04 transformation half, W-OBS-02) status:** released in `0.8.0-alpha.1` ([ADR-0030](decisions/0030-v0-8-cache-extensibility-gateway.md)): `validate` with inline JSON Schema 2020-12 or an OpenAPI 3.1 document (`jsonschema` without default features, schemas compiled at load, remote references refused) and the `validation-failed` problem type; `transform` with header rules and JSON Patch (RFC 6902, own implementation with the RFC's appendix A as tests) on held request bodies and on JSON response bodies up to a cap in the synchronous body phase; `${vault:<mount>/<path>#<field>}` for Vault/OpenBao KV v2 with token or Kubernetes login on the existing hyper-rustls client, refreshed on an interval, degraded on a failed refresh, values only in memory. Tested by unit tests, end-to-end tests against a fake KV v2 server in `rdock-testkit`, and the new CI job `openbao` against OpenBao 2.7.2 in dev mode (token login; the Kubernetes login only against the fake). Left out: OpenAPI parameter styles other than the defaults and `content` parameters (refused as planned), AppRole and other Vault auth methods, KV v1 and dynamic secrets.
**Pipeline, UDP, directory listing and Terraform (F-EXT-01, M-L4-04, F-WEB-02, F-MGMT-02, M-TM-05) status:** released in `0.8.0-alpha.1` ([ADR-0030](decisions/0030-v0-8-cache-extensibility-gateway.md)): Pingora 0.9.1 (tokio cap removed), the phased middleware pipeline and the `hold_body` middleware (a request body held until complete, in memory and then in a spool file; **M-TM-05 stays open**: it is not full pre-buffering, and the request head reaches the backend before an agent or `validate` verdict on the body); `udp` listeners, `udp_routes`, `udp_services` and Gateway API `UDPRoute`; `static.listing` (off by default); the Terraform and OpenTofu provider source in `clients/terraform` (built, unit-tested and acceptance-tested against a running rdock in the `terraform-provider` job). **Not done:** publication of the provider (a separate repository and a signing key, maintainer actions).

## v0.9 — Scale (P3)
**Scope:** H-HA-01…05 (`rdock-control`, ACK/NACK rollout, shared cert storage, distributed rate limits), H-LB-01…04, H-SEC-01…07, H-PERF-01…06 (zero-downtime binary upgrade by peer handover of the listening sockets; listener changes already apply in process, ADR-0012), F-UI-07, **HTTP/3 ingress experimental** (feature-gated `quinn` + `h3` on rustls, ADR-0032).
**Plan:** [ADR-0031](decisions/0031-v0-9-scale.md), [ADR-0032](decisions/0032-http3-on-quinn-and-h3.md) and the [research note](research/v0.9-scale.md). ADR-0031 fixed the order of work (measurement helper and the per-request fixes of issue 181 → listener sockets and runtime → shared TLS tickets and HTTP/2 options → data-directory lock and binary upgrade → balancer → edge security → cluster store and ACME under a lease → `rdock control`, rollout, instance view → distributed limits → admission control and tenants → HTTP/3 → soak and documentation) and says that a step that does not reach its tests is left out with a "planned for" diagnostic rather than shipped half-wired.
**Status:** **released as `0.9.0-alpha.1`** (2026-11-14). The release PR ticked in [04](04-requirements.md) the IDs delivered in full (H-PERF-03, H-PERF-04, H-HA-01…04, H-LB-01, H-LB-02, H-LB-04, H-SEC-01, H-SEC-04, F-UI-07) and, as it had announced, H-SEC-02 and H-SEC-06, which are closed by reference to ADR-0030 with their open items listed; H-PERF-01, H-PERF-02, H-PERF-05, H-PERF-06, H-HA-05, H-LB-03, H-SEC-03, H-SEC-05 and H-SEC-07 stay open. HTTP/3 is experimental and behind the cargo feature `http3`, which release binaries and images leave off. The code went through three independent review-and-fix passes (cluster and shared limits; HTTP/3 and the binary upgrade; tenants, admission control and edge security); the ADRs' "As implemented" notes describe the state after them. **The 24-hour soak, 8-CPU numbers and dedicated-hardware numbers were not produced** (see "Done when" below); what ran is the CI listed per area.
**Performance and sockets (H-PERF-01, H-PERF-06; issue 181):** a per-listener host index for routing, fewer allocations per request, statistics rings allocated on first use, `listeners.<l>.socket` (`backlog` 4096 instead of 128, `reuse_port`, buffers, keep-alive, `user_timeout`, `fast_open`, `ipv6_only`, `dscp`) bound through `socket2`, `runtime.worker_threads` and `runtime.max_blocking_threads`, and `tls.max_handshakes` on `https` listeners. Measured on a shared 4-vCPU development sandbox ([results](../benchmarks/results/2026-11-13-perreq/report.md)): allocations per request 137.5 → 125.5 with 3 headers and 169.6 → 140.5 with 20, system calls unchanged, CPU per request at 10,000 routes 2.4× → 1.03× that of one route; everything else within the machine's noise. Only the counts are exact; no absolute microsecond figure is claimed. A burst of 500 TLS handshakes stalled established connections for 45–93 ms without `tls.max_handshakes`, and a bound of 8 cut that to 6–20 ms at the price of slower new handshakes; the default stays unset until the experiment is repeated on lab hardware. The measurement tool is `benchmarks/perreq`; the nightly gate (`benchmarks/compare.py`) now also checks CPU per request at 2.4× NGINX's and its throughput floor is 0.98× NGINX's. **Not done:** CPU pinning and per-thread acceptors, the TLS handshake offload pool, `tls.max_handshakes` on `tcp` listeners (refused as planned), NUMA guidance, the allocator matrix and the sizing page. The `jemalloc` cargo feature exists for the comparison (off by default and in release builds; a musl build was not tried).
**TLS tickets and HTTP/2 (H-PERF-02, H-PERF-03):** one ticket key set and session cache per security class, shared by listeners and kept across reloads and binary upgrades (`tls.tickets`, `tls.session_cache`; `tls.tickets.key_file` for several instances; 0-RTT stays off), and `listeners.<l>.http2` with today's values as defaults and `unlimited` spelled out where a flood limit would go. A test shows a client that never reads a 256 MiB HTTP/2 response grows the proxy by less than 64 MiB. **Not done:** the handshake offload pool, a downstream keep-alive PING (needs a Pingora change).
**Binary upgrade (H-PERF-04):** `rdock upgrade [--binary]` over the admin Unix socket and `SIGUSR2`, Linux only, refused as PID 1 in a container. The running process checks the binary (regular file, owners and modes of the file and of every directory above it, no symbolic link, ELF, not older than the running version unless `--allow-downgrade`, optional minisign signature), runs `validate`, executes the verified file descriptor, hands over the listening and admin sockets, the data-directory lock and the ticket keys with `SCM_RIGHTS` (`rustix`), and drains for `upgrade.drain` (10 minutes by default); if the new process fails, the old one keeps serving. `rdock run` takes `<data dir>/rdock.lock`, so a second independent run on one data directory is refused. Proof: `crates/rdock/tests/e2e_upgrade.rs` (`a_binary_upgrade_drops_nothing_and_drains_within_its_bound`, `a_listener_change_by_reload_drops_nothing`, `a_failed_upgrade_leaves_the_old_process_serving`, `pid_1_is_refused`, `a_second_run_on_one_data_directory_is_refused`) in the `rust` job: about 1,450 new connections per second over HTTP, HTTPS and TCP together during the upgrade on a shared 4-vCPU sandbox (3,600 when the test ran alone; the ADR asks for 1,000), none failed; a WebSocket, an SSE stream, a chunked upload, an HTTP/2 stream, a TLS-passthrough relay and a UDP session stay up until the drain deadline. **Not done / untested:** a run under real systemd (the `MAINPID=` path is untested), other platforms (refused), migration of UDP sessions and TCP relays (they end at the handover), in-container upgrades.
**Balancer (H-LB-01…03, H-HA-05):** `policy: peak_ewma`, the success-rate and failure-percentage outlier detectors with `ejection_jitter`, slow start in the long form with `join` (and a fix for backends of weight 1, which never ramped), priority tiers with `failover: strict | spill`, `retries.per_try_timeout`, and zones (`locality`, `zone`, EndpointSlice zones and hints, off by default). Unit tests per policy and the balancer's end-to-end tests in the `rust` job. **Refused as planned:** hedged requests (`hedge`: Pingora 0.9.1's `ProxyHttp` cannot race two upstream attempts). **Not done:** progressive draining (`drain.duration`), zone labels for Docker and Swarm, the pod's zone from the Helm chart. `per_try_timeout` is the read timeout of an attempt that can still be retried, not a hard deadline on the body.
**Edge security (H-SEC-01, H-SEC-03, H-SEC-04, H-SEC-05):** JA4 (and optional JA3) fingerprints from our ClientHello parser with `ClientFingerprint` and `key: ja4`; GeoIP (`ClientCountry`, `ClientContinent`, `ClientASN` from operator-supplied MaxMind DB files, `maxminddb` 0.32.0, never bundled or downloaded); the `abuse` middleware with a bounded, persisted ban list that never evicts, `GET`/`DELETE /api/v1/abuse/bans` and `rdock bans`; typed `client_cert` rules and SPIFFE X.509-SVID checks, with client CA and upstream certificate files watched. **Not done:** `verified_bot` bot heuristics, the SPIFFE Workload API (needs `tonic`) and checking a backend's SPIFFE ID (Pingora 0.9.1 has no verifier hook), JA4+, challenge actions, a `geoip` middleware that injects headers, per-trust-domain bundles on one listener. H-SEC-02 and H-SEC-06 are met by v0.8 except for the items ADR-0030 left open (gRPC `ext_proc`/`ext_authz` agents and SPOP, a body verdict before the request head, OIDC back-channel logout, RFC 7662 introspection); they are not delivered by v0.9 code; the release PR ticks them in 04 because they are closed by reference to ADR-0030.
**Cluster (H-HA-01…04, F-UI-07):** `rdock control run` (same binary; crates `rdock-control` and `rdock-cluster`): a cluster CA, single-use join tokens, enrolment over TLS pinned to the CA, mutual TLS over HTTP/2, bundles with revision, hash and cluster id pulled by long poll and stored before the ACK, NACK with diagnostics, rollback, revocation; a data plane that loses the control plane keeps serving and restarts from its stored bundle. Staged rollout (`control.rollout`: one canary, a soak time, a halt on a NACK or a silent canary, resume and abandon; automatic rollback on health is refused as planned). Certificates are ordered once per name across instances: a lease with a fencing token on the control plane's store (or a shared directory, best effort), a re-check after taking it, an order journal the next holder resumes, one shared account and renewal time, challenge answers replicated with a barrier. `scope: cluster` on `rate_limit` and `quota` shares leased budgets through the cluster store or a Redis-compatible server (in-tree RESP client), bounded by `L + N × max(c, ⌈L / N⌉)` per key and window while the store answers (`c = max(1, ⌈L × headroom_percent / (100 × N)⌉)`), falling back to `⌈L / N⌉` per instance when it is away. The dashboard's Cluster page and `GET /api/v1/cluster/instances` are the instance view. **Review fixes that matter to an existing setup:** storing a certificate is now a commit (the new chain and key are written aside, `meta.json` naming the chain is replaced with compare-and-swap, then the files are moved into place), where 0.8 replaced `cert.pem`, `key.pem` and `meta.json` one after the other with nothing marking the set complete; the first version of this commit logic could leave a pair that never loaded again, but that state existed only in the development tree before 0.9.0-alpha.1 and is fixed. A directory written by 0.8 loads unchanged. Enrolment of an enrolled name is refused unless its current certificate is presented, and the store authorises each member's writes. **Not done / open:** a highly available control plane, delta bundles, S3, Kubernetes-Secret, PostgreSQL and etcd stores, cluster-scoped `in_flight` (refused as planned), per-instance provider health and listener summaries in the instance view, the Helm chart's `allowAcme` (per-replica join tokens are not modelled), a test against a real Redis or Valkey (only the testkit's RESP server), and the variant of the control-plane-outage proof with Toxiproxy or `SIGSTOP`.
**Admission control and tenants (H-LB-04, H-SEC-07):** `key: group` on `rate_limit`, `quota`, `in_flight` and `bandwidth` (the consumer's primary group; token-claim groups count only when listed in `jwt.trusted_groups`); the `admission` middleware (AIMD or gradient, `priority_class: critical | normal | sheddable`, `503` with `Retry-After` and the `overloaded` problem, off by default, per instance); `tenants.<name>` scoping admin users and API tokens to a name prefix and host claims with a fail-closed classification of every admin operation, audited refusals, backend address policy enforced at resolution on the data plane, `tenants.<t>.limits`. Proofs: `e2e_admission`, `e2e_tenants` and `rdock-admin/tests/tenants.rs` in the `rust` job. **Refused as planned:** tenant-owned listeners and certificates, a tenant label on core metrics, a dashboard tenant view. **Not done:** cluster-wide admission, a `tenant` access-log field, `GET /tenants/<t>/metrics`, tenants on the control plane.
**HTTP/3 ingress, experimental (H-PERF-05, [ADR-0032](decisions/0032-http3-on-quinn-and-h3.md)):** `listeners.<l>.http3` on `https` listeners, only in builds made with the cargo feature `http3` (quinn 0.11.12 and h3 0.0.8 on the listener's rustls configuration; not in release binaries or images; a build without it refuses `http3.enabled: true`). Each request stream is decoded by our own QPACK decoder, validated, and run through the normal Pingora pipeline as a custom session, so routing, middlewares, the cache, retries and the access log are shared; a frame-size guard in our own QUIC adapter stands in front of h3, which buffers whole frames. `Alt-Svc`, Retry policy, per-listener and per-client connection limits, a bounded memory worst case, GOAWAY and a drain of at most 10 s on reload, shutdown and upgrade, stateless-reset and token keys in `<data dir>/quic.key`. Proof: `crates/rdock/tests/e2e_http3.rs` with the testkit's quinn and h3 client (large upload, trailers, client reset, retry with the body replayed, the cache, oversized frames, GOAWAY, a binary upgrade that drains HTTP/3 and resets old connections, shutdown), unit tests and the `http3_request` fuzz target in the required `rust` job, and the non-required `http3` job, whose curl step (curl 8.14.1 from a Debian image pinned by digest) passed on pull-request runs. **Refused as planned:** HTTP/3 to backends (`scheme: h3`; Pingora has no QUIC connector), 0-RTT, active migration (a client whose NAT rebinds loses the connection), datagrams, WebTransport, extended CONNECT (WebSocket over HTTP/3, CONNECT-UDP), qlog, PROXY protocol on the QUIC socket and `tls.fingerprint` with HTTP/3. Server push is never sent; request trailers are read and dropped. **Open:** the h3i malformed-request suite and a QUIC interop-runner image (not built), the release-binary size with the feature (not measured), a soak with HTTP/3, and an `h3` release that contains its unreleased fixes (the condition for leaving "experimental").
**Soak and scaling measurements (H-ENG-02, H-ENG-03, H-PERF-01):** `benchmarks/soak/hosted` runs one release `rdock` without Docker (HTTP and HTTPS, a rate limit, the cache, a held WebSocket and event stream, 400 req/s from an open-model generator, a reload every 5 minutes and, in the first half, a binary upgrade every 30 minutes) and judges failed requests (at most 0.001 %), upgrades, reloads, held connections and a per-process rise in memory, descriptors and threads by a rule that is tested on synthetic series; the weekly `soak` workflow runs it for 5 h 20 min on a GitHub-hosted runner. `perreq/run.sh scaling` and the hand-run `scaling` workflow measure rdock pinned to 1, 2 and 4 CPUs (the 4-CPU row shares cores with the generator and is a lower bound). **Only smoke runs exist**, on a shared 4-vCPU sandbox: a 10-minute soak (239,978 requests, none failed, 2 upgrades, 6 reloads; judged one process of 4.7 minutes, which with the real parameters would not have been judged) and three rounds of scaling (about 18,500 req/s on 1 CPU, 31,600 on 2 and 42,900 on 4, the last a lower bound with rdock's CPUs 61 % busy) ([soak](../benchmarks/results/2026-11-13-soak-smoke/report.md), [scaling](../benchmarks/results/2026-11-13-scaling-smoke/report.md)). They show that the tooling works, not rdock's long-run behaviour or its scaling. **The weekly job has not completed a full run yet**; its hosted-runner CPU layout is unverified. On the default run's shape the memory rule passes a leak of 0.5 MiB an hour and fails 1 MiB an hour on a 100 MiB process, so slower leaks need the 24-hour soak.
**Done when**, item by item (the proof is the CI job named; all are in the `rust` job unless stated):
- *3-instance cluster survives control-plane outage:* **met.** `e2e_cluster::three_data_planes_survive_a_control_plane_outage` (control plane killed with `SIGKILL`; requests to all three data planes see no failure for the time they take to notice plus 10 s; one restarts from its stored bundle; the next revision reaches all three; a NACKed revision leaves all three on the previous one; a revoked instance takes no new revision). The no-failure window is the time the data planes take to notice the outage plus 10 s (the plan said 60 s), and the Toxiproxy and `SIGSTOP` variants are not built.
- *No duplicate certificate issuance across instances:* **met.** `e2e_cluster::three_data_planes_issue_once_through_the_control_plane_store`, `e2e_cluster::three_data_planes_issue_once_against_pebble` (Pebble in Docker, `RDOCK_ACME_TESTS=1`), `rdock-acme/tests/cluster_issuance.rs` and `e2e_cluster_acme.rs`: one order per name counted at the CA, also with the lease holder killed after it journalled its order. The shared-directory mode is best effort (documented, with a validation warning).
- *fd-transfer e2e keeps WebSocket/SSE connections alive across an upgrade and a listener change:* **met** by `e2e_upgrade` (above), on Linux, not under real systemd.
- *HTTP/3 interop with h3i/curl:* **met for curl, open for h3i.** curl over HTTP/3 against a running rdock passes in the `http3` job (not a required check). The h3i suite was not built: it needs quiche and BoringSSL in its own crate and could not be made self-contained in the job. The malformed-request cases are covered by our own unit tests, the `http3_request` fuzz target and `e2e_http3` instead.
- *24 h soak at target RPS without memory growth:* **not met.** The criterion needs a dedicated machine for 24 hours. The weekly hosted soak (about 5 h 20 min, 400 req/s) **stands in for it** and has not yet completed a full run; the only result is the 10-minute smoke run above.
- Not a "done when" item but part of the plan and **open:** 8-CPU and dedicated-hardware measurements (only the 1, 2 and 4 CPU smoke rows exist, from a shared sandbox), the allocator matrix and sizing page, and a run under real systemd.
**Refused as planned and left open by decision** (each is a setting or feature the configuration refuses with "planned for a later version", or an item the ADRs list as open; the settings are in `apps/website/src/data/status.json`): hedged requests; automatic rollback of a rollout on the canary's health; `in_flight` with `scope: cluster`; a highly available control plane and delta bundles; S3, Kubernetes-Secret, PostgreSQL and etcd stores; tenant-owned listeners and certificates, a tenant label on core metrics and a dashboard tenant view; HTTP/3 to backends, 0-RTT, active migration, datagrams, WebTransport, extended CONNECT, qlog, PROXY protocol on the QUIC socket and TLS fingerprints with HTTP/3; `tls.max_handshakes` on `tcp` listeners; the SPIFFE Workload API and checking a backend's SPIFFE ID; `verified_bot` and JA4+; challenge actions for `abuse`; CPU pinning and per-thread `SO_REUSEPORT` acceptors; a permanent supervisor and in-container upgrades; the systemd fd store; migration of UDP sessions and TCP relays; `drain.duration`; per-instance health in the instance view; and the 4- and 8-CPU measurements and the 24-hour soak.

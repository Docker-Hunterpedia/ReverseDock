## [0.9.0-alpha.1] — v0.9 "Scale"

Released 2026-11-14 ([ADR-0031](https://github.com/Docker-Hunterpedia/ReverseDock/blob/main/docs/decisions/0031-v0-9-scale.md) and [ADR-0032](https://github.com/Docker-Hunterpedia/ReverseDock/blob/main/docs/decisions/0032-http3-on-quinn-and-h3.md)). HTTP/3 is experimental and only in builds made with the cargo feature `http3`, which the release binaries and images leave off. The 24-hour soak, 8-CPU and dedicated-hardware measurements were not run; a weekly 5 h 20 min hosted soak stands in for the soak and had not completed a full run when this was written. What is refused as planned, and what is open, is in `docs/07-roadmap.md`. Everything under Added is new in this release, including the fixes made to it during review; those fixes are part of each feature's description, not listed separately.

### Added

#### Binary upgrade and process model

- **Binary upgrade by peer handover** (H-PERF-04, ADR-0031): `rdock upgrade [--binary <path>]` (over the admin Unix socket only, operator role; never the TCP API or the dashboard) and `SIGUSR2` replace the running binary on Linux without refusing or resetting a connection. The running process checks the binary (a regular file that is an ELF executable, with no symbolic link anywhere in its path, owned by root or rdock's user and not writable by group or others, in directories owned and protected the same way all the way up to `/` unless sticky; not older than the running version unless `--allow-downgrade` is given (`allow_downgrade` in `POST /api/v1/upgrade`; `SIGUSR2` never downgrades); with `upgrade.trusted_keys`, a minisign signature in `<binary>.minisig`), runs `<binary> validate` on the configuration file, starts `rdock run --inherit` with a socket pair as its standard input and hands over a versioned manifest, the listening sockets (TCP and UDP), the admin sockets, the data directory's lock and the TLS ticket keys with `SCM_RIGHTS` (`rustix`). Every run of the candidate (`--version`, `validate`, the new process) executes the file descriptor that was checked, hashed and verified (`/proc/self/fd/<n>`), so replacing the path afterwards cannot run an unverified file. From then until the handover ends the old process serves without the HTTP caches and its admin API answers changes with 503 (a request already sent on a connection accepted just before the handover is still answered). The new process builds everything without accepting and says `ready`; the old one stops accepting and its shared-state writers (ACME, local CA, Cloudflare range sync, alerts, providers, Vault refresh, quota files), says `go`; on `serving` it sends systemd `MAINPID=` and drains for `upgrade.drain` (10 minutes; `unlimited` with a warning) with HTTP/1 keep-alive off and HTTP/2 `GOAWAY`, reporting its open connections every second and its quota counts at exit; UDP sessions end at the handover. If the new process exits or does not report within `upgrade.start_timeout` (30 s), the old one resumes and nothing was closed. Refused as PID 1 (replace the container) and outside Linux. A manifest or data directory with a newer format is refused before `ready` (`<data dir>/rdock.format`). Metrics `rdock_upgrades_total{result}`, `rdock_upgrade_generation`, `rdock_upgrade_draining_connections`, `rdock_upgrade_drain_deadline_seconds`; an `upgrade` audit record with who asked, the binary's SHA-256 and the result; `rdock status` shows `pid` and `upgrade_generation`. The systemd unit gains `NotifyAccess=main`. New guide: Upgrade the binary in place.
- **One process per data directory** (ADR-0031): `rdock run` takes an advisory lock on `<data dir>/rdock.lock` before writing anything; a second independent `rdock run` on the same data directory is refused with the holder's pid. Held request bodies spool to `spool/<pid>/` (removed at exit; leftovers of dead processes are removed when the lock is taken fresh). The admin API can serve already-open sockets instead of unlinking and binding `admin.sock`, and answers requests in flight before it stops. See Changed.

#### Performance, sockets and TLS

- **Listener socket options** (H-PERF-01, ADR-0031): `listeners.<l>.socket` with `backlog`, `reuse_port`, `receive_buffer`, `send_buffer`, `keepalive` (`idle`, `interval`, `count`), `user_timeout`, `fast_open`, `ipv6_only` and `dscp`, bound through `socket2`. Unset options keep the kernel's behaviour. Options that do not fit the listener's transport are refused (TCP options on a `udp` listener, `ipv6_only` on an IPv4 address), `reuse_port` on a `udp` listener is refused, and `user_timeout` and `fast_open` are refused outside Linux. A reload changes `backlog`, the buffers and `fast_open` on the running socket without binding again; `keepalive`, `user_timeout` and `dscp` apply to new connections; a changed `reuse_port` or `ipv6_only` keeps the running value until a restart and the reload reports it.
- **Bound on concurrent TLS handshakes** (H-PERF-01, ADR-0031): `listeners.<l>.tls.max_handshakes` on `https` listeners. While the bound is reached the listener stops accepting, so new connections wait in the listen backlog instead of taking the CPU from established ones; no bound by default. Metrics `rdock_tls_handshakes_in_flight{listener}` and `rdock_tls_handshake_waits_total{listener}`. On `tcp` listeners it is refused as planned.
- **Runtime threads** (H-PERF-01, ADR-0031): `runtime.worker_threads` and `runtime.max_blocking_threads`, read at start; a reload that changes them reports that a restart is needed. `rdock status` and `rdock_runtime_threads{kind}` show the values in use.
- **Shared TLS session resumption** (H-PERF-02, ADR-0031): one ticketer (our own ChaCha20-Poly1305 `ProducesTickets` with a key name, current and previous key) and one session cache per security class (TLS policy, client-authentication mode and CA certificates, certificate scope, resumption settings), shared by listeners and kept across reloads and binary upgrades, so a ticket from one listener resumes on another of the same class and never on one that requires client certificates when it was issued without. `listeners.<l>.tls.tickets` (`enabled`, `rotate` 6h by default, at most 84h; `key_file` with operator-provided keys for several instances, bound to each class with HKDF so one file never joins two classes, refused when readable by group or others, read again on change, a warning after 24 hours) and `.tls.session_cache.size` (256). 0-RTT stays off.
- **HTTP/2 settings** (H-PERF-03, ADR-0031): `listeners.<l>.http2` with `max_concurrent_streams`, `initial_stream_window`, `initial_connection_window`, `max_frame_size`, `max_header_list_size`, `max_pending_accept_reset_streams`, `max_local_error_reset_streams` and `max_send_buffer`; defaults are the values before v0.9 (Pingora 0.9.1 and h2 0.4.20), ranges follow RFC 9113, and removing a flood limit must be written `unlimited`. A reload applies them to new connections.
- **Per-request measurement helper** (issue 181, ADR-0031): `benchmarks/perreq` counts allocations (with the bench-only `alloc-count` cargo feature, never in release builds), system calls and CPU time per proxied request without Docker, and runs the TLS-tail experiment; `benchmarks/cpu-ladder.sh` records the `cpu.stat` ladder in the Docker lab (untested); the `tls-ramped` benchmark scenario reaches its rate over 2 s. Baseline and results: `benchmarks/results/2026-11-13-perreq/`.
- **Hosted soak, CPU-scaling mode and a comparison allocator** (H-ENG-02, H-ENG-03, H-PERF-01, H-PERF-06, ADR-0031): `benchmarks/soak/hosted` runs one release `rdock` for hours without Docker (Python 3 standard library and `openssl`): HTTP and HTTPS, a rate limit, the cache, JSON access logging, a WebSocket and an event stream held open, 400 req/s from an open-model generator, a reload every 5 minutes and, in the first half of the run, a binary upgrade by peer handover every 30 minutes whose handover it follows to the new pid and whose promises about held connections it checks. It samples RSS, PSS, descriptors, threads and rdock's own counters, and its analysis fails the run on failed requests (at most 0.001 %, counted separately inside and outside upgrade and reload windows), a broken upgrade, reload or held connection, a panic, or a per-process rise in memory, descriptors or threads (Theil–Sen slope, projected growth over 24 h above 10 % of the level and a last-quartile median above the second by more than max(1 MiB, 1 %); judged on the longest process or a majority of processes); the rule is tested against synthetic flat, noisy, step, leak and sawtooth series. The weekly `soak` workflow runs it for 5 h 20 min on a GitHub-hosted runner; it **stands in for, and is not**, the 24-hour soak at target RPS on dedicated hardware, which stays open. `rdock-perreq scale` and `benchmarks/perreq/run.sh scaling` measure peak throughput and CPU per request of rdock pinned to 1, 2 and 4 CPUs (`runtime.worker_threads` to match) by closed-loop saturation, with how busy rdock's and the generator's CPUs were; at the machine's full CPU count the generator shares cores with the proxy and the row is marked a lower bound; the `scaling` workflow runs it by hand (`workflow_dispatch`) and gates nothing. 8 CPUs and dedicated-hardware numbers stay open. New cargo feature `jemalloc` on `rdock` (`tikv-jemallocator` 0.7.0, off by default and in release builds; mimalloc stays the allocator we ship) for the allocator comparison; the matrix is not measured yet.

#### Balancing

- **Latency-aware balancing** (H-LB-01, ADR-0031): `load_balancer.policy: peak_ewma`, power of two distinct random choices over `latency × (in_flight + 1) / weight` with Finagle's and tower's peak-sensitive moving average (`decay` 10 s; `measure: first_byte` by default, or `last_byte`). A backend without a sample starts from the pool's mean (at least 1 ms, 30 ms when nothing is measured); a failed attempt counts as at least one second. The state survives reloads. `round_robin` stays the default; `p2c` is unchanged.
- **Outlier detection** (H-LB-02, ADR-0031): `health.passive.outlier` with Envoy's `success_rate` (mean − 1.9 σ, 5 hosts, 100 requests) and `failure_percentage` (85 %, 5 hosts, 50 requests) detectors, evaluated every `interval` (10 s), off until `enabled: true`; `minimum_hosts` below 3 is refused. Outliers go through the existing ejection (back-off, `max_ejection_percent`, trial request). `health.passive.ejection_jitter` (default 0). Metric `rdock_backend_outlier_ejections_total{service, backend, detector}`.
- **Slow start, long form** (H-LB-02, ADR-0031): `health.slow_start: { window, aggression, min_weight_percent, on: [recovery, join] }` with Envoy's formula; `join` ramps a backend that newly appears in a pool that already had one at full weight. `slow_start: 30s` is the long form with its defaults.
- **Priority tiers** (H-LB-03, ADR-0031): `priority: 0..7` on backends (`backup: true` is tier 1; both together are refused) and `failover: strict | spill` on services with `overprovisioning` (1.4) for `spill`, as Envoy's priority levels.
- **Zones** (H-HA-05, ADR-0031): `zone` and `for_zones` on backends, top-level `locality: { zone, mode: prefer | off }` (zone also from `RDOCK_ZONE`) and a per-service `locality.mode`; off by default. The Kubernetes provider keeps EndpointSlice zones and `hints.forZones`.
- **Per-try timeout** (H-LB-03, ADR-0031): `retries.per_try_timeout` abandons a stalled attempt and retries it on another backend within the budget and the retry rules; `on` must list `timeout`. `services.<s>.hedge` is accepted and refused as planned: Pingora 0.9 cannot race two upstream attempts.

#### Edge security

- **TLS client fingerprints** (H-SEC-03, ADR-0031): `listeners.<l>.tls.fingerprint` (`ja4`, on by default once set; `ja3`, off; `header` and `ja3_header` to pass the values to backends; client copies of those headers are removed on every listener). JA4 follows FoxIO's `technical_details/JA4.md` at commit `8eda4ce4` (BSD 3-Clause, attribution in `NOTICE`; nothing of the FoxIO-licensed JA4+ family); JA3 is offered for existing block lists and documented as legacy. The ClientHello parser now records cipher suites, extensions, `supported_versions`, signature algorithms, groups and point formats, refuses duplicate extension types (RFC 8446 §4.2) and more than 128 extensions, and has a `tls_fingerprint` fuzz target. Access-log fields `ja4`, `ja3`; middleware `Context.fingerprint`; rule matcher `ClientFingerprint(…)` in HTTP routes (needs a listener with `tls.fingerprint`) and TCP routes (computed only when a rule uses it); `key: ja4` for `rate_limit`, `in_flight`, `bandwidth` and `abuse`. Nothing is read or computed unless configured.
- **GeoIP** (H-SEC-04, ADR-0031): top-level `geoip` (`database`, `asn_database`, `max_age` 30 days after the GeoLite EULA of 2026-02-12, `on_stale: warn | refuse`, opt-in `log.country`/`log.asn`), MaxMind DB files read into memory with `maxminddb` 0.32.0 (ISC, no `mmap`); GeoIP2/GeoLite2, DB-IP Lite and IPinfo Lite record shapes; files watched and swapped on change, unchanged files reused across reloads. Matchers `ClientCountry`, `ClientContinent`, `ClientASN` in HTTP, TCP and UDP rules on the resolved client address; unknown and non-global addresses never match (so a negation matches them). A geo rule without a database is refused. Metrics `rdock_geoip_build_timestamp_seconds{database}`, `rdock_geoip_database_age_seconds{database}`. New guide: GeoIP.
- **Abuse counters and bans** (H-SEC-01, ADR-0031): middleware `type: abuse` counts events (`401`, `4xx`, `auth_failure` from `basic_auth`, `api_key`, `jwt`, `cloudflare_access`) per key (`client_ip` with IPv6 by /64, `consumer`, `ja4`, `header:`) in a fixed window and bans past `threshold` for `ban`; `action: deny` (403, new problem type `banned`), `tarpit` (capped by `tarpit.max_held`) or `tag`; `exempt` (loopback by default, `security.trusted_proxies` always). Bounded counter table; a separate bounded ban list that is never evicted (new bans are refused when full, `rdock_abuse_bans_refused_total`); bans persisted in `<data dir>/abuse` (0600) across restarts and binary upgrades. Admin API `GET /api/v1/abuse/bans` (viewer) and `DELETE /api/v1/abuse/bans/{key}` (operator, audited as `abuse.unban`), CLI `rdock bans list|remove`, metrics `rdock_abuse_actions_total`, `rdock_abuse_bans`, access-log field `abuse`. `key: consumer` before the middleware that sets the consumer is refused, and bans or limits by `ja4` alone warn (one JA4 is shared by a client build and can be copied; pair `ClientFingerprint` with `ClientIP` in a rule). New guide: Abuse protection.
- **Identity rules on client certificates and SPIFFE** (H-SEC-05, ADR-0031): `client_cert` gains typed lists `subjects`, `organizations`, `dns`, `uris` (case-sensitive), `emails`, `serials`, `sha256`, and `spiffe: { trust_domains, ids, id_prefixes, consumer }` with the X.509-SVID rules (exactly one URI SAN, a valid SPIFFE ID with a non-root path, a leaf that is not a CA and cannot sign); the SPIFFE ID goes to `Context.spiffe_id`, the access log (`spiffe_id`) and, with `consumer: true`, the request's consumer under the issuer `spiffe://<trust domain>`. The listeners' `client_auth.ca_files` and the services' `tls.ca_file`/`cert_file`/`key_file` are now watched, so rotated SVIDs and bundles apply without a restart. The SPIFFE Workload API and checking a backend's SPIFFE ID stay planned.

#### Cluster, control plane and shared state

- **Cluster with a control plane** (H-HA-01, H-HA-02, ADR-0031): `rdock control run` (the same binary; crates `rdock-control` and `rdock-cluster`) with a `control` section (`listener`, `names`, `identity_lifetime` 30 d, `join_token_ttl` 1 h, `history` 50, `offline_after` 90 s). A cluster CA (ECDSA P-256) is created on first start; `rdock control token create` (or `POST /api/v1/cluster/tokens`) gives a single-use join token `rdk_join_…` (stored as SHA-256) and the CA pin. Data planes with `cluster.control` (`url`, `ca_file` or `ca_pin`, `identity_dir`, `join_token` as a secret reference, `poll_timeout`) enrol once with a CSR over TLS pinned to the CA and get a client certificate renewed with a third of its life left; every later call is mutual TLS over HTTP/2. Publishing (`rdock control publish <file>`, `POST /api/v1/cluster/revisions`, operator role, audited) validates the document and stores it as the next revision with its SHA-256 and the cluster id (zstd); data planes long-poll for it, refuse another cluster's, an older or an empty revision, compose it with their own sections (`cluster`, `admin`, `providers`, `runtime`, `upgrade`, `locality`, `lifecycle`, `observability`, `secrets`), store it before they ACK, or NACK with diagnostics and keep the previous revision; a start without the control plane serves the stored revision (new configuration origin `control`). `rdock control revisions | rollback <n> | instances | revoke <name>` and `GET /api/v1/cluster/instances`, `POST /api/v1/cluster/instances/{name}/revoke`, `GET /api/v1/cluster/revisions`; a revoked instance takes no new revision. Enrolling a name that is enrolled and not revoked is refused unless the caller presents that instance's current certificate (a revoked name can be enrolled again with a new token), every call is admitted only for the newest certificate issued to the name (the one a renewal replaced works ten more minutes), a retry of an enrolment with the same key is answered again while its token is valid, the identity is one file (`identity.json`, mode 0600), an expired client certificate is reported as such, and the control plane's store lets a member write only what the protocol needs (a revoked member is shut out from then on but nothing it already read is taken back; every member reads every key, including the ACME account key and certificate private keys). The cluster listener has header and body deadlines, caps connections (fewer without a client certificate) and enrolments, and bounds every body; a data plane warns when its clock is more than 2 s off the control plane's. Data planes with a control plane do not accept configuration writes through their own admin API. Metrics `rdock_cluster_bundle_revision`, `rdock_cluster_bundles_total{result}`, `rdock_cluster_control_connected`, `rdock_control_revision`, `rdock_control_instances{state}`. New guide: Run a cluster with a control plane.
- **Shared certificates** (H-HA-03, ADR-0031): `cluster.store` (`type: control`, the default with a control plane, or `type: directory` with `path`, best effort with a validation warning; `lease_ttl` 60 s, `barrier_timeout` 10 s). Each certificate is ordered once across instances: a lease per name with a fencing token, a re-check of the store after taking it, an order journal (URL and new key) the next holder resumes, one shared ACME account and one shared renewal time; HTTP-01 and TLS-ALPN-01 answers are copied to every live member before the CA validates (a barrier), never read from the store while serving; each answer has an id per order and is re-applied when republished, a new lease holder withdraws what an earlier holder of the name left, and left-over answers, confirmations, heartbeats and limit windows are removed, and a member copies the answers in the store before its listeners accept (at most 5 s). The directory store removes emptied directories and lists without holding the store's lock. `rdock validate` recommends DNS-01 for clusters. `acme` with `providers.kubernetes` no longer needs `allow_acme` on a control-plane store. Metrics `rdock_cluster_leases_total{result}`, `rdock_cluster_challenge_barriers_total{result}`. New guide: Share certificates across instances.
- **Staged rollout** (H-HA-02, ADR-0031): `control.rollout` (`mode: canary` by default, or `all`; `canary` to name the instance that goes first, otherwise the first online instance by name; `soak` 60 s; `canary_timeout` 2 m). A published revision goes to the canary first and to the other instances once the canary acknowledged it and the soak time passed; a refusal (NACK) or a canary that does not report in time halts the rollout and the others stay on the last revision whose rollout completed. `rdock control rollout status | resume | abandon` and `GET /api/v1/cluster/rollout`, `POST /api/v1/cluster/rollout/resume` (also promotes a soaking revision), `POST /api/v1/cluster/rollout/abandon` (publishes the stable revision again; instances that had the abandoned one go back), operator role, audited; halts and completions are audited as `cluster.rollout.halt` and `cluster.rollout.complete`. Revisions list their rollout outcome. The first revision of a cluster and rollbacks go everywhere at once. `auto_rollback: true` is refused as planned. The revision instances fall back to is never pruned from the history, abandoning a rollout happens under one lock, and rollout audit records are never dropped.
- **Instance view** (F-UI-07, ADR-0031): the dashboard's Cluster page on the control plane (instances with state, serving and target revision, version, last seen, identity expiry and last error; the rollout with resume and abandon); a data plane shows "Not a control plane". `GET /api/v1/cluster/instances` gains `target`, `last_error`, the cluster `name` and the rollout, and its answers are typed in the OpenAPI document.
- **Cluster-scoped limits** (H-HA-04, ADR-0031): `scope: cluster` on `rate_limit` and `quota` (default `instance`) shares each key's budget between the instances of a cluster through `cluster.limits` (`store: cluster` for the control plane's store or the shared directory, or `store: redis` with `redis { url, username, password, ca_file, timeout, key_prefix, allow_plaintext }`; `sync_interval` 1 s; `headroom_percent` 10; `fallback: share | instance`). Instances claim parts of the budget in the background and never wait on the store; the cluster admits at most `L + N × max(c, ⌈L / N⌉)` per key and window, with `c = max(1, ⌈L × headroom_percent / (100 × N)⌉)` (a key new to an instance admits up to `⌈L / N⌉` until its first claim returns, then reconciled; claims are sent 16 at a time). While the store is away each instance admits its share `⌈L / N⌉` (or `L` with `fallback: instance`), logs it and sets `rdock_cluster_limits_store_up` to 0; what it admitted meanwhile is added to the store's count when it returns. Redis is reached with an in-tree RESP client over TLS (`rediss://`; plain `redis://` only to loopback unless `allow_plaintext`), with `AUTH` and the password from a `${file:}` or `${env:}` reference. Limit windows are removed a minute after they ended (by the control plane's clock on its store), members are counted by heartbeats that change rather than by clocks, and Redis membership uses the server's `TIME`. The RESP client drops its connection after any error. The cluster-scoped quota is not counted in the local quota counters, so `GET /api/v1/quotas` and the metering export show instance-scoped quotas only. `in_flight` with `scope: cluster` is refused as planned. Metrics `rdock_cluster_limits_store_up`, `rdock_cluster_limit_claims_total{outcome}`, `rdock_cluster_limits_members`.

#### Admission control, group keys and tenants

- **Group key for limits** (H-LB-04, ADR-0031): `key: group` on `rate_limit`, `quota`, `in_flight` and `bandwidth` counts every consumer by its primary group (the first of its `groups`), so all keys and users of a customer share one count; a consumer without a group is counted on its own, requests without a consumer per client IP. `overrides` apply to the primary group. Only groups that come from the configuration count (configured consumers, a group a middleware assigns, `map_to_consumers`, and token groups listed in the new `jwt.trusted_groups`; never an OIDC provider's); other token groups stay on the consumer for metering and headers, and such a consumer is counted on its own. Works with `scope: instance` and `scope: cluster`. Group quota counters show as `group:<name>` and can be read and reset with `/api/v1/quota/group:<name>`.
- **Admission control** (H-LB-04, ADR-0031): middleware `type: admission` with `mode: aimd` (Netflix's `AIMDLimit`: `latency`, `backoff_percent`) or `mode: gradient` (Envoy's adaptive-concurrency gradient against a measured no-load latency, with Gradient2's smoothing: `tolerance_percent`, `smoothing_percent`, `queue`; the no-load latency is measured at start and then every `interval` (60 s) with `jitter_percent` (15) and a `probe_timeout` (5 s)), `min` 3, `max` 1000, `initial` 20, `shares` (`normal` 90 %, `sheddable` 75 %), `retry_after` 1 s; off unless configured. Routes get `priority_class: critical | normal | sheddable` (default `normal`; unrelated to the matching `priority`): lower classes are refused first with `503` and the new problem type `overloaded`, and higher classes keep a reserve while lower ones drain. The limit learns only from requests that reached a backend (a client abort, rdock's own answers and cache hits are no sample; failed connects and upstream timeouts are drops), a request keeps its place until its response is complete, an upgraded connection gives its place back at `101`, and `critical` and `normal` keep a reserve of at least two. No lock on the request path; metrics `rdock_admission_limit`, `rdock_admission_in_flight`, `rdock_admission_shed_total{class}`; access-log field `admission: shed:<class>`. Settings of the other algorithm, `min > max`, and an `in_flight` with `key: route` beside it are refused.
- **Tenants** (H-SEC-07, ADR-0031): top-level `tenants.<name>` with `prefix` (default `<name>-`), `hosts` (exact names and `*.` wildcards at any depth, never the base or a look-alike; ASCII/A-labels only; no overlap between tenants), `shared` (services, middlewares, cache stores), `backend_networks`, `limits` (`max_body` 16 MiB, `max_routes`, `max_services`, `max_middlewares` 100, `max_tls_names` 20) and `allow_critical` (off: no `priority_class: critical` on a shared `admission`). Users and API tokens gain `tenant` (`rdock users add|set --tenant`, `rdock tokens create --tenant`); a scoped caller reads and writes only the API objects under its prefix, with per-tenant `ETag`s and reports that show only its own diagnostics, and its routes must provably stay inside its claims. Its objects may not read files, call out or run code (`forward_auth`, `agent`, `plugin`, `wasm`, `static`, `oidc`, `cloudflare_access`, `jwt.jwks_url`/`jwks_file`, `basic_auth.users_file`, `errors.file`, `maintenance.file`, `validate.openapi`, upstream TLS files, `${…}` references, Unix-socket, loopback and link-local backends). A tenant's backends may reach only global unicast addresses unless `backend_networks` lists others (exactly those; a cloud metadata address only on its own; listing loopback or link-local warns), enforced on IP literals at validation and on every address a DNS name or SRV record resolves to, each time it resolves, on the data plane (`rdock_backend_addresses_refused_total{service}`); only a middleware's own regular-expression `replacement` may contain `${…}`; names such as `localhost.localdomain` and `ip6-localhost` are refused for tenants. Removing a tenant disables its users and revokes its tokens for good. One tenant's stale API object does not make other writes fail, tenant reports drop `withheld`, and tenant diagnostics do not name or reveal objects outside the tenant. A host claimed by a tenant but routed by a non-API route warns. Authorization fails closed: every admin operation is classified and anything else is refused with `403`; every refusal is audited with the tenant, and audit records carry `tenant`. Tenant-owned listeners and certificates, a tenant label on core metrics and a dashboard tenant view are refused as planned. Without `tenants`, nothing changes.

#### HTTP/3 (experimental)

- **HTTP/3 ingress, experimental** (H-PERF-05, ADR-0032): `listeners.<l>.http3` on `https` listeners (`enabled`, off by default; `advertise` with `advertise_max_age` 1 h and `advertise_port`; `retry: auto | always | never`, `auto` from 100 half-open connections; `max_idle` 30 s; `max_concurrent_streams` 100; `max_header_size` 64 KiB, at most 768 KiB; `max_connections` 1,000 and `max_connections_per_client` 100 per IPv4 address or IPv6 `client_ipv6_prefix` (64); `stream_receive_window` 512 KiB, `receive_window` 1 MiB and `send_window` 1 MiB, a worst case of `max_connections × (2 × receive_window + send_window)` = 3000 MiB that validation warns about above 4 GiB; `congestion: cubic | newreno | bbr`; `gso`), every value bounded. Only in builds made with the cargo feature `http3` (quinn 0.11.12 and h3 0.0.8 on our rustls/ring configuration, with our own QUIC adapter for h3; not in release binaries or images); without it `http3.enabled: true` is refused with a diagnostic. The listener then owns the UDP socket of its address (a `udp` listener there is refused). Each request stream is decoded (our own static-table QPACK decoder) and validated (pseudo-header fields, names, values, connection-specific fields, authority, path, `CONNECT`, `content-length` against the DATA received) before it enters the same Pingora pipeline as HTTP/1 and HTTP/2 as a custom session, so routing, middlewares, the cache, retries and the access log (`proto: "HTTP/3"`) are shared; a malformed request is reset (`H3_MESSAGE_ERROR`, 431 when too large) and never forwarded. `Alt-Svc` on the listener's HTTP/1 and HTTP/2 answers while the QUIC endpoint serves; 0-RTT is off in the TLS configuration; GOAWAY and a drain of at most 10 s on a reload that stops it, shutdown and binary upgrade (GOAWAY announces one past the last accepted request and a request at or past it is refused with `H3_REQUEST_REJECTED`, never forwarded; a draining connection closes only after its responses in flight are acknowledged; the new process answers the previous one's packets with a stateless reset); stateless-reset and Retry-token keys in `<data dir>/quic.key`. Reset floods close the connection (`H3_EXCESSIVE_LOAD`); request bodies need 1 KiB/s after `timeouts.read`. h3 buffers every frame other than DATA whole before decoding it, so rdock reads each frame header first, in its own QUIC adapter that replaces h3-quinn: a HEADERS frame over `max_header_size` + 16 bytes or any other frame over 16 KiB fails before its payload is held (a request stream is reset, the control stream closes the connection, with `H3_EXCESSIVE_LOAD`), the incomplete frames of a connection share a budget of `receive_window`, and a frame that has started must arrive within `timeouts.request_header` (`rdock_http3_connections_closed_total{reason="frame_limit"}`). While the upstream works, a client's `STOP_SENDING` or a lost connection cancels the upstream request at once and counts towards the reset-flood limit. A bodiless request (`GET`, `HEAD`, `OPTIONS`, `DELETE`, `TRACE` without `content-length`) waits for the end of its stream so it is not forwarded with an empty chunked body. A connection counts against its client only once its address is validated; a client that has not proved its address is sent Retry instead of refused when a limit is reached, and `retry: never` still forces Retry once half of `max_connections` are half-open. `quic.key` must belong to rdock's user and not be readable by group or others, or `rdock run` stops with a diagnostic. Metrics `rdock_http3_connections_total`, `rdock_http3_connections`, `rdock_http3_retries_total`, `rdock_http3_connections_closed_total{reason}`, `rdock_http3_malformed_requests_total{reason}`, `rdock_http3_requests_total`. HTTP/3 to backends (`scheme: h3`), 0-RTT, active migration, datagrams, WebTransport, extended CONNECT (WebSocket over HTTP/3, CONNECT-UDP), qlog, PROXY protocol on the QUIC socket and TLS fingerprints of QUIC connections are refused as planned. `rdock version` says whether the build has it. NAT rebinding is not survived: with migration off quinn drops packets from a new address. A fuzz target (`http3_request`) and a non-required CI job `http3` (its curl step passes).

### Changed

#### Upgrading from 0.8.0-alpha.1: changes that affect an existing configuration

- **A second `rdock run` on one data directory is refused** with the holder's pid (`<data dir>/rdock.lock`). Held request bodies spool to `spool/<pid>/`. Run one process per data directory; use `rdock upgrade` to replace the binary.
- **The listen backlog is 4096**, Linux's `net.core.somaxconn` default since 5.4, instead of the standard library's 128. Set `listeners.<l>.socket.backlog` to change it.
- **Numeric host spellings are refused as backend addresses, for everyone**: a host that is not a strict IP literal but whose last label is numeric (decimal, octal or `0x`: `127.1`, `2130706433`, `0x7f.0.0.1`) is refused when the configuration loads, since `getaddrinfo` reads them as IPv4 addresses (127.0.0.1, 169.254.169.254) and no resolver reads them as names (WHATWG URL "ends in a number", read 2026-11-13). Write the address in dotted-quad form.
- **`basic_auth` refuses expensive password hashes**: argon2id above `m=262144` (KiB), `t=10` or `p=8` and bcrypt above cost 14, inline (`users`) at validation and in `users_file` when the middleware is built (also on reload); OWASP's Password Storage Cheat Sheet (read 2026-11-13) recommends at least m=19456/t=2/p=1 and bcrypt 10. At most four verifications run at once process-wide (fewer with fewer CPUs); a request waits up to 1 s for a slot, then gets `503` with `Retry-After: 1` (problem type `overloaded`). Failed checks are still not cached.
- **Group `overrides` count only groups from the configuration**: a group taken from a JWT claim no longer selects an `overrides` entry of `rate_limit` or `quota` (0.8 matched any group of the consumer) unless it is listed in the new `jwt.trusted_groups`, and groups from an OIDC identity provider's claims never do (an OIDC consumer mapped to a configured consumer with `map_to_consumers` keeps that consumer's groups); such a consumer is still counted under its own name.
- **The TLS ClientHello parser is stricter**, also for SNI routing of TCP routes: any duplicate extension type is refused (RFC 8446 §4.2; before, only `server_name` and ALPN) and so are more than 128 extensions.
- **`slow_start` together with `ip_hash`, `header_hash` or `cookie_hash` is refused** (each change of a weight moved keys between backends); 0.8 accepted it.
- **Upstream client certificates are checked against their key** (H-SEC-05): a `services.<s>.tls` certificate and key that do not belong together are refused when the configuration loads (before, the mismatch showed only as failed backend handshakes); a rotation that has written one of the two files keeps the running pair until the other lands. The listeners' `client_auth.ca_files` and the services' `tls.ca_file`, `cert_file` and `key_file` are now watched, and a rotated certificate or CA bundle gets new pooled backend connections.
- **Certificate storage layout** (ADR-0031): certificates are ordered under a lease per name instead of one lock for the whole directory (the directory lock stays, so an earlier version sharing the directory still waits); an order in progress is journalled in `orders/<name>.json`; `meta.json` gains `issuer`, `serial`, `not_before`, `not_after`, `chain_sha256`, `ari` (the chosen renewal time), `issued_by` and `issued_at`; a new certificate is written to `certs/<name>/next/` first, `meta.json` is replaced with compare-and-swap as the commit, and then `cert.pem` and `key.pem` are moved into place; a reader takes the pair that matches `meta.json` and whose key matches the chain, so a store that stops at any point leaves the previous or the new certificate loading (0.8 replaced `cert.pem`, `key.pem` and `meta.json` one after the other with nothing marking the set complete). Requests that share a first name are joined into one certificate with all their names. **A 0.8 directory loads unchanged** and is completed at the next renewal.
- **Priority tiers replace `backup` for SRV priorities**: an SRV target of a higher SRV priority is one tier below its backend (it was `backup` before); `backup: true` is tier 1, and `backup` together with `priority` is refused.
- **Nightly benchmark gate**: CPU time per request from each proxy's cgroup is recorded at every rate and gated at 2.4× NGINX's (new; hosted runners read 1.3× to 2.2×, so a tighter limit failed by the machine drawn, not by the code), and the throughput floor rises from 0.95× to 0.98× NGINX's. This changes CI only.

#### Other changes

- **Routing uses a host index per listener** (issue 181): a request is checked only against the routes for its host (exact names, one-label wildcards) and the routes without a host condition, in the same priority order, so the result is unchanged. CPU per request at 10,000 routes fell from 2.4× to about 1.0× that of one route in a sandbox measurement.
- **Fewer allocations per request** (issue 181): about 12 fewer per plain request and 29 fewer with 20 browser-like headers (forwarded-header cleanup, the client stream's read copy, the request ID, the path, backend selection).
- **Live statistics rings are lazy** (issue 181, ADR-0031): a route's or service's 190 KiB ring is allocated by its first request, so idle routes cost no ring memory, and requests record nothing when neither the admin API nor an error-rate or latency alert can read the rings.
- The minisign verifier moved from `rdock-wasm` to `rdock-credentials` (`rdock_wasm::minisign` still re-exports it).

### Fixed

- **Stopping a listener** (a reload that removes or moves it, shutdown, binary upgrade): connections that have not sent a request yet get up to 2 seconds (never more than the drain) to send their first one before idle connections are closed; before, a connection accepted a moment before the stop could be closed without an answer.
- **Slow start works for backends of weight 1**: weights are compared in thousandths while `slow_start` is set, and the ramp starts at `min_weight_percent` (10 %) of the weight instead of one weight unit; before, a backend of weight 1 (the default) never ramped.

### Security

- Tightened behaviour of released features, each described under Changed: numeric host spellings refused as backends, `basic_auth` hash-cost ceilings and a cap on concurrent verifications, group `overrides` limited to groups from the configuration (or listed in `jwt.trusted_groups`), and the stricter ClientHello parser.

- **Phased middleware pipeline** (F-EXT-01, ADR-0030): middlewares gain the phases `upstream_request` (after the backend is chosen, before the head is sent; once per attempt), `request_body` (the complete body, held by the proxy), `response_body` (each chunk, synchronously, before `compress` and `bandwidth`) and `log` (after the response; read-only, with status, bytes and timings), beside `request` and `response`. A middleware declares the phases it uses, whether it wants a typed per-request state slot, and whether the body should be held; the proxy computes per-route flags once at compile time, so a route that uses none of the new phases does no extra work. Order: list order on the way in (`request`, `upstream_request`, `request_body`), reverse order on the way out (`response`, `response_body`, `log`). `rdock explain` prints each middleware's phases. The context gains the chosen backend and a `consumer` placeholder, which the access log shows as `consumer` once a v0.8 middleware sets it. Groundwork for the cache, plugins and agents.
- **`hold_body` middleware** (F-EXT-01, ADR-0030): `{ type: hold_body, max: 1MiB, timeout: 30s }` holds the request body until it is complete before any of it reaches the backend: in memory up to 64 KiB, then in an unlinked `0600` spool file under `<data dir>/spool/` (emptied at start). A body over `max` (or the route's smaller `max_body`) is refused with `413`, a declared one before the backend is contacted; a body slower than `timeout` gets `408`. The backend connection and the request head already exist while the body is held, so this does not shield backend workers from slow uploads (true pre-buffering waits for Pingora's early-body hook; M-TM-05 stays open). A held body over 64 KiB cannot be replayed by Pingora's retry buffer and is not retried.
- **Directory listings for `static`** (F-WEB-02, ADR-0030): `listing: true` lists a directory that has no index file, as a built-in HTML page or, when `Accept` prefers it, as JSON (`{ "path", "entries": [{ "name", "type", "size", "modified" }], "truncated" }`), with `Vary: Accept`. Off by default and safe when on: names are HTML-escaped and percent-encoded in links, the page carries `Content-Security-Policy: default-src 'none'`, `nosniff` and `Referrer-Policy: no-referrer`, `hidden` and `symlinks` decide what appears (never a name a request would be refused), entries are sorted by name and cut at 10,000 (`truncated`), and the directory is read through the same capability handle as files, on the blocking pool. A directory that exists lists instead of getting the `fallback`; `directory_redirect` also applies to listed directories; the answer has no validator and ignores conditional and range headers. `rdock validate` warns about `listing: true` with `hidden: allow` or `symlinks: all`.
- **UDP routes** (M-L4-04, ADR-0030): `udp` listeners relay datagrams per **session** (one client address and port) to `udp_services`: each session gets its own socket connected to one backend, chosen by the balancer when it starts (`load_balancer.policy`: `round_robin`, `random`, `least_sessions`, `ip_hash`; backend `weight` and `backup`) and kept for its life, and the backend's replies go back to that client only; rdock never sends a datagram that is not a reply on a live session. A session ends after `timeouts.idle` (60 s, Envoy's default) without traffic in either direction, after `responses` replies (NGINX `proxy_responses`; `1` for DNS), when its backend answers ICMP "port unreachable" (which feeds passive health: `health.passive`, on by default), or when its listener is removed (after `lifecycle.drain_timeout`); `requests` detaches a client after that many datagrams (NGINX `proxy_requests`). Sessions are capped by default because UDP sources can be forged: `listeners.<l>.sessions.max` (4,096) and `max_per_client` (64 per client IP), each a number or `unlimited`; datagrams over a cap are dropped and counted, never answered. `udp_routes.<r>` takes `listeners`, an optional `match` of `ClientIP` matchers only (at most one route without `match` per listener), `priority`, `ip_allow`/`ip_deny` middlewares (checked before a session is created) and `enabled`. Optional TCP health probes (`health.tcp_check`) for backends that also listen on TCP. Datagrams up to 64 KiB are relayed whole; one too large for the destination's address family is dropped and counted (`oversize`), never cut. Reloads keep the sockets and sessions of unchanged listeners. Metrics: `rdock_udp_sessions{listener,route}`, `rdock_udp_datagrams_total{route,direction}`, `rdock_udp_bytes_total{route,direction}`, `rdock_udp_dropped_total{listener,reason}`, `rdock_udp_session_ends_total{route,reason}`; one `debug` log line per session when it ends. Docker labels `rdock.udp_routes.*`, `rdock.udp_services.*` and the Traefik subset `traefik.udp.routers.<r>.{entrypoints,service}`, `traefik.udp.services.<s>.loadbalancer.server.port` (other `traefik.udp.*` labels are reported), carried by `rdock migrate traefik`. Not supported: PROXY protocol for datagrams (refused as planned), `SO_REUSEPORT` fan-out, GRO/GSO, and the right reply source address on a wildcard bind of a multi-homed host (bind an explicit address).
- **Gateway API UDPRoute** (W-K8S-01, ADR-0030): `UDP` listeners are accepted (route kind `UDPRoute`; a `UDP` listener shares its port number with TCP-based listeners and conflicts only with another `UDP` one) and UDPRoutes translate like TCPRoutes (attachment, ReferenceGrant, pooled weights; the oldest route of a listener gets its datagrams, all are accepted). The per-Gateway Service keys its ports by protocol and port: TCP and UDP 53 become `tcp-53` and `udp-53` (a mixed-protocol Service), each with its own internal port; Services created earlier keep their `port-<n>` names. `UDPRoute` is claimed in `supportedFeatures` with the nine upstream `GATEWAY-UDP` tests transcribed, and `GATEWAY-UDP` joins the conformance job's profiles; it passes on kind in CI (2026-11-12, commit `43d81de`: core 21 passed, extended 7 passed), so all five profiles pass. The chart's NetworkPolicy allows UDP on the internal port range.
- **HTTP cache** (F-WEB-03, ADR-0030): a `cache` middleware stores a route's responses in a named store under `caches` (`type: memory` with `max_size`, or `type: disk` with `path`, `max_size`, `max_objects`), on pingora-cache's state machine with our own policy and stores in the new crate `rdock-cache`. Safe by default: off unless a route lists it; **no default lifetime** (only `s-maxage`, `max-age` or `Expires`, minus the age the response arrived with, RFC 9111 §4.2.3); `GET` and `HEAD` without a body only; statuses 200, 203, 204, 300, 301, 308, 404, 410; never stored: `no-store`, `private`, `Vary: *`, `Set-Cookie`, and responses to requests that carry `Authorization` unless marked `public`, `s-maxage` or `must-revalidate`; `max_object_size` 64 MiB. Each default has an explicit opposite with its risk documented (`default_ttl` per status, `heuristic_freshness`, `statuses`, `set_cookie: strip`, `authorization: store`, `request_directives: ignore`, `lock.enabled: false`, `tags.keep`, `cache_status: false`). The key frames store, route, scheme, host, forwarded path, query and method class, with `key.query` (`as_sent`, `sorted`, `only`, `ignore`; parameters left out of the key are removed from the forwarded request), `key.headers` and `key.consumer`; override headers such as `X-Original-URL` are removed from requests on caching routes. Added to Pingora's mechanism: the full `304` header update, `Vary` with normalised values, request directives (`no-cache`, `max-age`, `min-fresh`, `max-stale`, `only-if-cached` → `504`), invalidation of the URL and same-host `Location`/`Content-Location` after a successful unsafe method, `stale-if-error` (RFC 5861) on origin errors and 500/502/503/504 within the origin's window capped by `stale_if_error`, and `Cache-Status` (RFC 9211) on every answer of a caching route plus `cache_status` in the access log. Request coalescing is on: one fetch per key, waiters wait at most `lock.timeout` (5 s) and are released to fetch on their own when the fill fails or is not cacheable. Hits still pass every `request`-phase middleware (authentication, IP filters, rate limits); `upstream_request` middlewares do not run on hits; the store holds the origin's representation, so one object serves every `compress` encoding. A route that authenticates (`basic_auth`, `jwt`, `client_cert`, `forward_auth`) and caches is a validation error unless `shared_across_users: true` or `key.consumer: true`; mirrored requests skip the cache. The disk store keeps one file per object (checksummed header with pingora-cache's `CacheMeta`, URL and tags, then the body; temporary name and rename; start-up walk that drops damaged and partial files; LRU by size and count; no `fsync`); a purge cancels fills still in progress. Stores live for the process: adding one applies on reload, changing or removing one is reported as taking effect after a restart. Tags from `Cache-Tag` and `Surrogate-Key`; purges only through the admin API (`POST /api/v1/cache/{store}/purge` by `url`, `prefix`, `tag` or `all`, operator role, audited, rate-limited; `GET /api/v1/cache` for statistics; `rdock cache list|purge`), and **a purge reaches one instance**. Metrics `rdock_cache_requests_total{store,route,status}`, `rdock_cache_objects{store}`, `rdock_cache_bytes{store}`, `rdock_cache_evictions_total{store,reason}`, `rdock_cache_lock_waits_total{store}`, `rdock_cache_dropped_total{store,reason}`. Not supported: background refresh for `stale-while-revalidate` (treated as plain staleness; `background_refresh: true` is refused as planned), a data-plane `PURGE` method, partial reads for waiters, keeping the origin's `Date` on stored responses (Pingora 0.9.1 replaces it on every response; a known defect). The disk-header decoder has a property test and a fuzz target. The public suite `http-tests/cache-tests` (RFC 9111, RFC 9213) runs against the defaults in the `http-cache` CI job, gated by a reviewed allow-list (below). New guide: Cache responses.
- **Targeted cache control, `CDN-Cache-Control`** (F-WEB-03, RFC 9213, ADR-0030): the `cache` middleware's `targeted` (default `[CDN-Cache-Control]`) lists targeted fields in precedence order; the first with a valid, non-empty Structured Field dictionary value replaces `Cache-Control` and `Expires` for this cache, in both directions (`CDN-Cache-Control: no-store`, `private` or `no-cache` beat a fresh `Cache-Control`; `CDN-Cache-Control: max-age=600` stores a response marked `Cache-Control: no-store`). An invalid field, or a known directive with the wrong type, is ignored. `targeted: []` reads `Cache-Control` only; `remove_targeted: true` removes the fields from responses (they are forwarded by default, for a CDN in front).
- **The `http-cache` CI job is gated** (ADR-0030): it fails when a required test of `http-tests/cache-tests` fails that is not on `tests/conformance/http-cache/allowlist.json` (id and reason), and when an allow-listed test passes; optional and check tests and setup, harness and dependency failures are reported only. The suite is pinned to commit `7e2c53785f41eedc57aa73c8cc19a6729eef39ed` and runs on Node.js 24. On commit `c292639` (2026-11-12) the gate passed: 205 tests pass, 2 required tests fail and are allow-listed (`other-date-update`, `other-date-update-expires`: Pingora 0.9.1 rewrites `Date` on every response, which needs an upstream change), 35 optional tests fail, and 4 `Set-Cookie` setup tests fail because rdock does not store `Set-Cookie` by default. Not a required check yet.
- **Terraform and OpenTofu provider** (F-MGMT-02, ADR-0030): source in `clients/terraform` with `reversedock_route`, `reversedock_service` and `reversedock_middleware` resources and data sources, on the admin API's per-object endpoints with `If-Match`, serialised writes and retries on `412` and `429`. The examples in `examples/kubernetes/secrets` and `examples/secrets` are not exercised by CI. A direct `${vault:…}` reference is planned.
- **Native plugins** (F-EXT-02, ADR-0030): `{ type: plugin, name: <registered name>, config: {…} }` runs a Rust plugin compiled into the binary. The new crate `rdock-plugin-api` (its own `0.x` version line; `http`-crate types only, nothing from Pingora) holds the `Plugin` trait with the six phases, `RequestHead`/`ResponseHead` views with bounded changes, `Decision`, typed per-request state, request facts (client address, route, request id, TLS, consumer and groups, chosen backend), and `Factory`/`typed` with `ConfigError`s that `rdock validate` prints under `middlewares.<name>.config`. An unknown name is an error listing the registered ones. A panic in a hook is caught, counted in `rdock_plugin_panics_total{plugin}`, logged and answered with `500` for that request only. Plugins run with the proxy's privileges; the guide says so first.
- **`rdock` as a library** (F-EXT-02, ADR-0030): `rdock::run(registry)` is the whole command line, so a binary with plugins is a `Registry` and one call; every subcommand behaves as in the stock binary, which is the same call with an empty registry. `rdock version` prints the plugin API version and the registered plugins.
- **Plugin SDK** (F-EXT-05, SDK half, ADR-0030): `rdock_plugin_api::testing` runs a plugin through its phases without a proxy; `examples/plugins` holds `header-rewrite`, `ip-blocklist`, a `custom-rdock` binary with an end-to-end test, and a template to copy, all built and tested in CI. The crates are used as git dependencies (not published on crates.io).
- **Agents** (F-EXT-04, ADR-0030): `type: agent` asks an out-of-process service about each request, with `protocol: rdock` (a JSON document and verdict, `schema/agent.v1.json`) or `protocol: forward` (the request replayed; a 2xx allows, anything else goes to the client). The body goes through the held-body mechanism up to `max_body` (default 64 KiB; `on_oversize: reject` gives `413`, `skip` asks without it), so none of it reaches the backend before the verdict. Fails closed by default (`on_error: deny`: 502, 504 on timeout, 503 while the circuit breaker is open), `timeout` 1 s, a breaker (`failures: 5`, `window: 10s`, `open_for: 30s`), an allow-list of headers sent (credentials only when listed) and of headers the agent may set, TLS settings, and metrics `rdock_agent_requests_total`, `rdock_agent_duration_seconds`, `rdock_agent_breaker_open`, `rdock_agent_ignored_headers_total`. `ext_proc`, `ext_authz` and `spop` are refused as planned.
- **WAF example** (F-EXT-04, H-SEC-02, ADR-0030): `examples/waf` runs the CRS project's ModSecurity image (`owasp/modsecurity-crs` 4.30.0, nginx, pinned by digest) as a `forward` agent with Compose; `smoke.sh`, run by the new `waf-example` CI job, proves a clean request passes, attack patterns get `403` and a stopped WAF fails closed.
- Website: Plugins and Agents guides; plugin and agent metrics in the reference.
- **Cloudflare Access** (W-CF-06, ADR-0030): `{ type: cloudflare_access, team, audience }` verifies the JWT Cloudflare Access adds, as a preset over `jwt`: keys from `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs` (cached 10 minutes, refetched at once on an unknown key ID), issuer `https://<team>.cloudflareaccess.com`, RS256 only, token from `Cf-Access-Jwt-Assertion` then the `CF_Authorization` cookie (the header wins). `audience` (one or more AUD tags) is required. The consumer is the user's `email`, or a service token's `common_name` in the group `service-token`. `team` accepts the name or the team domain and is validated; `certs_url` overrides the derived URL for tests and egress proxies.
- **Problem details** (F-GW-04, first half, ADR-0030): `defaults.errors.format` and a route's `errors.format` (`html`, the default and unchanged behaviour; `problem`; `auto`) render every answer rdock produces itself (no route, middleware refusals, 408, 413, 414, 431, 429, 502, 503, 504, agent and plugin failures, the cache's 504) as `application/problem+json` (RFC 9457) with a stable `type` per kind (listed on the new Problem types reference page), `title`, `status`, a generic `detail`, `instance` (`urn:uuid:` and the request ID), `request_id`, `retry_after`, `Content-Language: en` and `Cache-Control: no-store`. A middleware's own body and `errors` pages keep precedence.
- **Consumers and API keys** (F-GW-01, first half, ADR-0030): top-level `consumers.<name>` with `groups`, inline `keys` (`{ id, hash, expires, note }`) and a watched `keys_file` of `id:hash[:expires]` lines; `{ type: api_key }` reads `rdk_<12-char id>_<32-char secret><6-char CRC32>` keys from `Authorization: Bearer` and `X-API-Key` (a query parameter only when named, never a cookie), refuses malformed keys by checksum without a lookup, finds the key by ID in a map compiled per configuration and compares the SHA-256 of the secret in constant time, checks expiry, sets the consumer, removes the key before the request goes upstream (`forward_credential: false`) and sends `X-Consumer-Name`, `X-Consumer-Groups` and `X-Credential-Id`; `anonymous: allow` and `groups` are optional. Keys minted with `POST /api/v1/consumers/{name}/keys` (operator; the key is in that answer only) are kept hashed in the `api` provider and revoked with `DELETE …/keys/{id}`; `rdock consumers` and `rdock keys` (`create`, `revoke`, `hash`, `generate`) do the same from the shell. The access log gains `key_id`; `rdock_consumer_requests_total{consumer,route,status_class}` counts per consumer (capped at 1,000 consumers, then `_other`). `key.consumer` of the cache keys on the consumer. The token-format code shared with admin tokens moved to the new crate `rdock-credentials`; admin tokens are unchanged.
- **Per-consumer limits and quotas** (F-GW-02, ADR-0030): `rate_limit` gains `key: consumer`, `overrides` per group and `headers: draft`; the new `quota` middleware counts requests per consumer per calendar window (`hour`, `day`, `month`, UTC) with group `overrides`, answers `429` with `Retry-After` until the window ends, optionally adds `RateLimit-Policy`/`RateLimit` in the syntax of `draft-ietf-httpapi-ratelimit-headers-11`, and keeps counters in `<data dir>/quota/` (written every `flush_interval` and at shutdown; per instance and approximate). `GET`/`DELETE /api/v1/quota/{consumer}` read and reset them. Counting per consumer without an earlier `api_key` or `cloudflare_access` is a validation error.
- **Usage metering** (F-GW-05, ADR-0030): `observability.metering` sends one event per request with a consumer (or every request with `all_requests`) to a webhook as CloudEvents 1.0 batches (Standard Webhooks signature and bearer token by reference) and/or OTLP/HTTP logs, batched (`max_batch`, `flush_interval`) from a bounded queue (`queue: 10000`) that drops and counts (`rdock_metering_dropped_total`) instead of slowing requests; failed batches are retried with the same event IDs (at least once). No disk spool; not billing-grade.
- Website: guides for API keys and consumers, quotas, usage metering and Cloudflare Access; problem details on the error-pages guide; the Problem types reference; consumer and metering metrics.
- **Request validation** (F-GW-03, ADR-0030): `{ type: validate }` checks path parameters (named groups of `path.regex`), query parameters, headers, cookies and JSON bodies against inline JSON Schema 2020-12, or the operations of an OpenAPI 3.1 document (`openapi`, JSON or YAML, watched; matched by method and path template, `base_path`, `unknown_operations: deny | allow`, default deny with `404`/`405`). Schemas are compiled when the configuration is loaded with `jsonschema` (no default features: no HTTP or file resolver); a schema that does not compile, a `$ref` outside its document, an OpenAPI 3.0 document and parameter styles other than the defaults are diagnostics. Parameter values are converted to the declared type; a repeated scalar parameter fails. Bodies are held up to `max_body` (default 1 MiB, at most 64 MiB; larger `413`), a non-JSON content type is `415`, invalid JSON `400`. Failures answer `400` with the new problem type `validation-failed` and at most `max_errors` (default 5) entries `{ pointer, message }` in `errors`; messages name the failed keyword and the schema's limits, never the value. `formats: true` (default) asserts `format`; `mode: report` logs and counts instead of refusing. Metric `rdock_validation_requests_total{middleware, result}`.
- **Request and response transformation** (F-GW-04, second half, ADR-0030): `{ type: transform }` sets, adds and removes request and response headers, and applies JSON Patch (RFC 6902, implemented in `rdock-model` with RFC 6901 pointers; the appendix A examples are tests) to JSON request bodies (held up to `max_body`, forwarded without the client's `Content-Length`; `on_error: reject` answers `422` with the new problem type `patch-failed`, or `pass`; non-JSON bodies pass unless `on_non_json: reject`) and to JSON response bodies in the synchronous body phase (2xx other than 204/205/206, identity encoding, at most `max_body`; `Content-Length`, `ETag` and digests are dropped). Anything else passes unchanged and is counted in `rdock_transform_skipped_total{middleware, reason}`. The cache stores the backend's response, so a cached answer is patched on every hit, wherever `transform` stands in the list. New problem type `unsupported-media-type` (415); extension members (`errors`) are rendered in problem details and in the pre-v0.8 JSON object.
- **`${vault:<mount>/<path>#<field>}`** (W-OBS-02, ADR-0030): `secrets.vault` (`address`, `ca_file`, `namespace`, `auth.token` as a `${file:}`/`${env:}` reference or `auth.kubernetes` `{ role, mount, token_file }`, `refresh` default 5m, `timeout` default 5s, `allow_private_targets` default true, `insecure_http` opt-in) reads fields of KV version 2 secrets from HashiCorp Vault or OpenBao over raw REST on the existing hyper-rustls client. References are accepted only in secret fields and only from the configuration file; values are read at every load (a reference never read that fails rejects the configuration, like a missing file; `rdock validate` reads them too), read again every `refresh` (a changed value reloads), and a failed read keeps the last value and marks Vault degraded in `rdock status` (`secrets.vault`) and `rdock_vault_refresh_failures_total`. Kubernetes logins are renewed after two thirds of their lease and after a `403`. Values stay in memory: the served configuration, history, last-known-good copy, snapshots, diagnostics and logs keep the reference. A fake KV v2 server in `rdock-testkit` backs the end-to-end tests; the new CI job `openbao` runs one against OpenBao 2.7.2 in dev mode.
- Website: guides for request validation and for transforming requests and responses; the Secrets guide covers `${vault:…}` and lists every secret field; new problem types and metrics in the references.
- **OIDC login** (F-GW-01, ADR-0030): `{ type: oidc, issuer, client_id, client_secret, session: { key } }` is an OpenID Connect relying party for browsers on the ring JWT code `jwt` uses (no new dependency): discovery from `<issuer>/.well-known/openid-configuration` (https, or http to loopback), the authorization code flow with PKCE S256 always on, `state` (constant-time) and `nonce`, the ID-token checks of OpenID Connect Core §3.1.3.7 (`iss`, `aud`, `azp` with several audiences, `exp`, `iat`, `nonce`, `at_hash`, signature with an algorithm both configured and advertised; `none` never, HS* only when listed, keyed with the client secret) and RFC 9207's `iss` on the callback. The session is stateless: a ChaCha20-Poly1305 cookie (keys from HKDF-SHA256, one per purpose and relying party, `v1.` format, random nonce; `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Lax`; split over at most four cookies) holding only `sub`, the consumer, groups, the verified e-mail, the claims to pass on, times and the refresh token; `session.keys` rotates keys, and replicas with the same key share sessions. One encrypted state cookie per login in progress (10 minutes, at most four), post-login targets that are always local paths, redirect URIs built only from the route's `Host` names or `redirect_url`, `401` instead of a redirect for requests that are not page navigations (`unauthenticated: auto | redirect | deny`), refresh 30 s before expiry with refreshes shared by parallel requests, RP-initiated logout at `logout_path`, `claims_to_headers`, `consumer_claim` (default `email`) and `groups_claim` set the request's consumer for `rate_limit`/`quota` with `key: consumer`, the cache key and the access log, `allowed` (`emails`, `domains`, `groups`), `forward_access_token`, `client_secret_basic`/`client_secret_post`, and `allow_private_targets` (off) checked on the address connected to. The provider's configuration and keys are fetched in the background after the first request and kept across reloads, so a reload never waits for it; when it is down, sessions keep working and new logins answer `503` with the new problem type `identity-provider-unavailable`; failed logins answer `401` `login-failed` without echoing the provider's description. `session.secure: false` needs `allow_insecure_cookies: true` and plain-HTTP routes; `same_site: strict` is refused (the login would loop). Metrics `rdock_oidc_logins_total{middleware,result}`, `rdock_oidc_refreshes_total{middleware,result}`, `rdock_oidc_provider_errors_total{middleware,operation}`. A fake provider in `rdock-testkit` drives the end-to-end tests, the new CI job `oidc-dex` logs in against Dex v2.46.1, and the cookie decoder has a fuzz target (`oidc_cookie`). Not supported: server-side sessions and back-channel logout (they need shared state), `id_token_hint` on logout, the userinfo endpoint. New guide: OIDC login.
- **`jwt` sets the consumer** (F-GW-01, ADR-0030): `consumer_claim` (and `groups_claim`) make a claim the request's consumer, so per-consumer limits, quotas and `key.consumer` work with tokens too.
- **WASM plugins, experimental** (F-EXT-03, F-EXT-05 signature half, ADR-0030): `{ type: wasm, path, sha256, trusted_keys }` runs a WebAssembly component for our own WIT world `rdock:plugin/filter@0.1.0` (`on-request` and `on-response` over the request and response heads; no bodies) in a fresh instance per request, on wasmtime 36 (the LTS line that fits the 1.89 MSRV), behind the cargo feature `wasm`, **off by default**: the stock binary and images do not include it, and a configuration with `type: wasm` is refused by `rdock run` (a warning in `rdock validate`) with "this build does not include WASM plugins; build with --features wasm". Before compilation the file must match its `sha256` pin and carry a minisign signature by one of `trusted_keys`, verified on ring's Ed25519 with BLAKE2b-512 for the default prehashed `ED` signatures and also accepting the legacy `Ed`; the trusted comment is checked; `allow_unsigned: true` is the explicit, warned way around the signature. Limits per call: `fuel` (10,000,000), `timeout` (50 ms, epoch interruption), `memory` (16 MiB); no WASI; `capabilities: [log, clock, random]` are granted per middleware and anything else a component imports is refused at load. A failed call (fuel, deadline, memory, trap, an invalid edit such as setting `content-length`) is counted in `rdock_wasm_failures_total{middleware,reason}` and follows `on_error` (`deny`, the default, answers `500`; `allow` passes through). A reload recompiles the module; a refused reload keeps the loaded one. New crate `rdock-wasm`; `rdock version` prints the WASM ABI; example guest `examples/plugins/wasm-header` (`no_std` Rust for `wasm32-wasip2`), tested with the e2e suite in the new, non-required `wasm` CI job. The ABI and keys may change in any release.
- Website: WASM plugins guide (experimental), with the ABI reference and how to sign with minisign; `rdock_wasm_failures_total` in the metrics reference.

- **Pingora 0.9.1 and no tokio cap**: Pingora moves to 0.9.1 (released 2026-11-03), which replaces the zero-capacity `BufStream` that panicked on every accepted connection with tokio 1.54 or newer (tokio#8494, pingora#1059); tokio is no longer capped below 1.54 and resolves to 1.54.1 (MSRV 1.89 kept). The whole test suite, and a new regression test with an HTTP/1.1 and an h2 request through a listener, pass on it. The three `zstd` 0.13 advisory ignores in `deny.toml` are gone with Pingora's move to `zstd` 0.14.3, and the Dependabot ignore for tokio is lifted.
- A request body refused by rdock (`413`, a middleware's answer) and a client that goes away no longer count as failures of the backend for passive health checks.
- `providers.kubernetes` is reshaped (it never shipped): `gateway_class` and the boolean `ingress` give way to `controller_name`, `gateway`, `ingress`, `leader_election` and `allow_acme` (ADR-0029). `gateway.pod_selector` is required while `gateway.enabled`.
- A listener contributed by a provider that cannot be bound (the address is in use) is left out with a diagnostic instead of rejecting the reload; a file listener that cannot bind still rejects it (ADR-0029).

### Fixed
- **HTTP cache, from the first run of `http-tests/cache-tests`** (F-WEB-03, ADR-0030): a response with `Cache-Control: no-cache` next to `max-age`, `s-maxage` or `Expires` was reused without revalidation; `no-cache` (unqualified, any case) now always gives a zero lifetime (RFC 9111 §5.2.2.4), and a `no-cache="…"` that names fields only keeps those fields out. An `Age` with several values (`Age: 7200, 0`, or several lines) was ignored as invalid, so an old response was served as fresh; the first member now counts and a parameter is cut off, while a value that is not delta-seconds is still ignored (RFC 9111 §5.1). Each case has an end-to-end test.
- The admin API document (`GET /api/v1/config/api`) carries exactly the sections it accepts. It used to include empty `tcp_routes` and `tcp_services`, which made every `PUT` and `DELETE` on `/api/v1/{kind}/{name}` answer 422; those endpoints now have an end-to-end test.
- UDP listeners created for a Kubernetes Gateway do not cap sessions per client address: datagrams reach them through the Gateway's Service, so the address seen is the load balancer's or the node's.
- **A removed listener no longer blocks its address** (M-L4-04, ADR-0030): a reload whose new listener needs the address of a listener it removes (another name, or a listener that moves) hands the old listener's socket over instead of failing to bind it. A replaced `udp` listener ends its sessions at once; a replaced TCP listener's connections drain as before. A removed `udp` listener still drains its sessions for `lifecycle.drain_timeout` and keeps its socket meanwhile, but a later reload that needs the port ends that drain and binds it. Before, a Kubernetes Gateway that got the internal port of a UDP Gateway deleted moments earlier could not listen until the next unrelated change (the upstream `UDPRouteParentRefAttachAllListeners` test failed every run on kind).
- **A provider listener left out because its address was in use is retried** (ADR-0029): after 250 ms, 500 ms, 1 s, 2 s and then every 5 s, rdock checks whether the address can be bound and reloads only when it can; it stops once the listener binds or is no longer wanted, and does not repeat the warning on every check. File listeners are unchanged: their bind failure rejects the reload.
- **Gateway listeners that are not serving are not reported `Programmed`** (ADR-0029): while a replica's data plane cannot bind a Gateway's internal port, the listener and the Gateway report `Programmed=False` with reason `Pending` and say why (the leader's view is the one written), and turn `True` once the retry binds it.
- **The Kubernetes provider does not hand out an internal port released moments ago** (ADR-0029): a port a per-Gateway Service let go stays out of new allocations for 30 seconds (longer than a removed listener's drain), unless the port range has no other free port; then the one released longest ago is reused and logged. The leader keeps this in memory; a new leader starts without it, which the two fixes above cover.

### Security
Fixes from the independent security review of v0.8, before any release contained the affected features (ADR-0030, "As implemented" notes):
- **Token consumers** (F-GW-01): an `email` claim names the consumer of `oidc` (and of `jwt` with `consumer_claim: email`) only when `email_verified` is `true` (or absent with the opt-in `unverified_emails`), else `sub` does, so an address a provider did not verify cannot take its owner's quota or cached copies. A consumer named by a token (`oidc`, `jwt`, `cloudflare_access`) is keyed on its issuer for the cache, quotas and rate limits, and gets the groups of a `consumers.<name>` entry only with the new `map_to_consumers: true` (default false); Cloudflare Access service tokens never share a user's identity. Quota counters kept for token consumers before the change start again.
- **Vault references** (W-OBS-02): the refresh task reads only the references of the configuration file, never those of provider or API objects; a `${…}` reference in a secret field of a provider object, and `${vault:…}` in one of an API object, is refused and the object left out.
- **Quotas** (F-GW-02): anonymous clients (IPv6 per /64), token consumers and configured consumers have separate key budgets, so 100,000 spoofed addresses no longer push consumers onto one shared, exhausted counter; overflows are counted in `rdock_quota_overflows_total`. Counter files are `0600` in a `0700` directory.
- **OIDC logout** (F-GW-01): only `GET`, `HEAD` and `POST` from the site itself (`Sec-Fetch-Site: same-origin` or `none`, else a same-origin `Origin` or `Referer`) end the session; other sites get `403`.
- **API consumers** (F-GW-01): keys the admin API minted for a consumer of the file stop working when the file no longer defines it, and the API can no longer give a file consumer groups.
- **`api_key`** (F-GW-01): with `forward_credential: false` every configured header holding a key and the query parameter (name compared decoded) are removed; a second, different key in another location answers `400`.
- **`transform`** (F-GW-04): a JSON Patch fails (`patch-failed`) when the patched document would exceed `max_body`; repeated `copy` operations could grow it exponentially.
- The `agent.max_body` documentation and the agent, validation and WAF guides now state that the request head reaches the backend before a body verdict (Pingora 0.9.1 reads the body after connecting upstream).

## [0.6.0-alpha.1] — v0.6 "Swarm, L4, static"

### Added
- **Docker Swarm provider** (#190, W-SWM-01…03, ADR-0026): `providers.swarm` routes Swarm services from their `deploy.labels` with the Docker provider's translator, so `rdock.*` labels and the Traefik subset work unchanged. Each running task is a backend (`endpoint_mode: tasks`, now the default instead of `vip`): ReverseDock balances, health-checks and drains a task as soon as Swarm starts stopping it (`DesiredState: shutdown` or `remove`). `vip` (or `rdock.swarm.lbswarm` / `traefik.swarm.lbswarm` per service) routes to the service's virtual IP and ignores active health checks and sticky sessions with a warning; a `dnsrr` service in that mode is diagnosed. Swarm sends no task events, so services and tasks are listed every `providers.swarm.poll_interval` (5 s, at least 1 s) and at once on service, node, network, secret and config events; the last routes stay in service while the manager is unreachable. The network is the label (`rdock.network`, `traefik.swarm.network`), then `providers.swarm.network`, then the one the task shares with ReverseDock's own container, never `ingress` and never random. `traefik.docker.network` and `traefik.docker.lbswarm` are accepted on Swarm with a deprecation warning. A missing port label says that Swarm reports no ports. `rdock validate` warns when automatic HTTPS is on with `providers.swarm`, because replicas share no certificates in v0.6. Tasks are read with a small `/tasks` client of our own (Engine API 1.44), because bollard 0.21.1 lacks `NetworksAttachments`. New guide: [Docker Swarm](https://reversedock.oday-bakkour.com/docs/guides/docker-swarm/). Static sites from service labels are limited to `providers.swarm.static_roots` (ADR-0027).
- **Static files** (#191, F-WEB-01, ADR-0026): a `static` middleware serves a directory of ReverseDock's file system (a volume in Docker), so sites and single-page apps need no web server next to the proxy. Strong `ETag`s from modification time and size, `Last-Modified`, every RFC 9110 precondition in its order (304, 412), byte ranges with `If-Range` (206, 416; `max_ranges` up to 16 as `multipart/byteranges`), HEAD, precompressed `.zst`/`.br`/`.gz` sidecars chosen by `Accept-Encoding` with `Vary` on every answer, `index` files and `308` to the trailing slash, a single-page-app `fallback` that leaves asset paths and `fallback_except` prefixes a 404, `Cache-Control` by path prefix, media types with `charset=utf-8` and `nosniff`, and `pass_through` to the route's service for everything else. Safe by default: the root is opened once as a directory handle (cap-std; `openat2` with `RESOLVE_BENEATH` on Linux), the path is decoded once and `..`, `\`, NUL and invalid UTF-8 answer 404, hidden files, symbolic links and directory listings are refused (`hidden: allow`, `symlinks: within_root|all`; listings are planned for v0.8). Files over 1 MiB are streamed in 256 KiB chunks, so `bandwidth`, `compress` and HTTP/2 flow control apply.
- A route needs no `service` when its last middleware answers every request: `static` without `pass_through`, or an enabled `maintenance` without `allow`. `rdock validate` reports a route that needs one.
- Docker labels: `rdock.static.root` ends the container's route with a `static` middleware, and `rdock.middlewares.<name>.type=static` works like any other middleware. Label roots must be inside a directory listed in the new `providers.docker.static_roots` (empty by default), so a container cannot serve ReverseDock's own files.
- **DNS-01 with DigitalOcean, Hetzner and RFC 2136** (#192, W-DNS-03, ADR-0026): `acme.dns_providers` takes `type: digitalocean` (API token with `domain:read`, `domain:create`, `domain:delete`), `type: hetzner` (the Hetzner Cloud API, where Hetzner Console DNS lives; the old `dns.hetzner.com` API is not supported) and `type: rfc2136` (dynamic updates to BIND, Knot, PowerDNS or any primary, signed with TSIG `hmac-sha256` by default over TCP; `hmac-sha384`/`-sha512` accepted, `hmac-sha1` with a warning, `hmac-md5` refused, unsigned updates only with `insecure_unsigned: true`). The zone is found by walking up from the record name unless `zone` is set; a wildcard and its base name get separate values that never remove each other; Hetzner actions are followed until they succeed before the propagation check. API calls take at most 30 s, follow no redirects and retry `429`, `409`, `423` and `5xx` up to five times with jittered backoff that honours `Retry-After` and `RateLimit-Reset`. Their secrets must be `${file:…}`/`${env:…}` references, read again for every call; `rdock validate` refuses literals. Every adapter passes one contract test against a fake of its provider (`rdock-testkit::fake_api`, and an in-process TSIG-verifying DNS server for RFC 2136).
- **PROXY protocol on listeners** (#187, M-L4-03, ADR-0026): `listeners.<l>.proxy_protocol` reads version 1 and 2 headers on `http` and `https` listeners, before the TLS handshake, from `trusted` sources only. The header's address becomes the connection's address (client IP, `ClientIP`, IP filters, rate limits, `X-Forwarded-For`, access log), and the load balancer is logged as `proxy_peer`. Trusted sources must send a header unless `optional: true`; other sources that send one are closed; `LOCAL` headers keep the real address; headers must fit in 16 KiB and arrive within `timeouts.request_header`. Closed connections are counted in `rdock_proxy_protocol_rejected_total{listener,reason}`. Parsed with proxy-header 0.1.3, with a fuzz target and an HAProxy `send-proxy`/`send-proxy-v2` interoperability test.
- **TCP routes** (#189, M-L4-01, M-L4-02, M-L4-03 outbound, ADR-0026): `tcp` listeners in ReverseDock's own accept loop route connections with `HostSNI`, `HostSNIRegexp`, `ALPN` and `ClientIP` rules read from the TLS ClientHello without consuming it. `tls.passthrough` relays TLS untouched (the client sees the backend's certificate), `tls: {}` terminates it with the listener's TLS settings and certificates (automatic ones too) and relays plaintext, and a route without `tls` relays any bytes (``HostSNI(`*`)``). `https` listeners hand ClientHellos a TCP route matches to it and keep serving HTTP otherwise. `starttls: postgres` answers PostgreSQL's `SSLRequest` so clients with the default negotiation reach SNI routes (the request is replayed to passthrough servers); `tcp_services.<s>.proxy_protocol: v1|v2` sends a PROXY header to backends (v2 with ALPN, and after termination the server name and TLS version); `ip_allow`, `ip_deny` and `in_flight` (per client IP) apply before connecting; `tcp_services.<s>.timeouts` sets `connect` (5 s), `idle` (10 min) and `termination_delay` (100 ms). Reloads keep open relays; a removed listener drains for `lifecycle.drain_timeout` and logs how many connections it closed. Metrics: `rdock_tcp_connections{listener,route}`, `rdock_tcp_bytes_total{route,direction}`, `rdock_tcp_rejected_total{listener,reason}`. `rdock validate` refuses termination on a listener without `tls`, ``HostSNI(`*`)`` on an `https` listener and HTTP middlewares on TCP routes, warns about MySQL, SMTP, IMAP and POP3 ports behind routes that need a ClientHello, and no longer needs an HTTP listener for a configuration of TCP routes alone. Tested end to end with PostgreSQL 17 (`sslnegotiation=direct`, `starttls: postgres`, termination). UDP stays planned (v0.8).
- **TCP labels** (#189): `traefik.tcp.routers.<r>.{rule, entrypoints, service, priority, middlewares, tls, tls.passthrough}`, `traefik.tcp.services.<s>.loadbalancer.server.port` and `traefik.tcp.middlewares.<m>.{ipallowlist.sourcerange, inflightconn.amount}`, and the full form `rdock.tcp_routes.<r>.<field>` / `rdock.tcp_services.<s>.<field>`; `tls.certresolver`, `tls.options`, `tls.domains` and `serverstransport` on TCP routers and services are reported. `rdock migrate traefik` carries TCP labels of Compose files over.
- **DNS-01 with Route 53, Google Cloud DNS, Azure DNS and deSEC** (#193, W-DNS-03, ADR-0026): `type: route53` (an access key pair, optionally with an STS `session_token`, signed with AWS Signature Version 4 on ring, no AWS SDK; waits for `GetChange` to report `INSYNC`; standard partition only), `type: google_cloud_dns` (a service account key file exchanged for an access token with an RS256 JWT; each change replaces the TXT record set atomically and is followed until `done`), `type: azure_dns` (exactly one of a client secret, a client certificate signing a PS256 assertion, or a managed identity through the instance metadata service; endpoints fixed per `environment`: `public`, `usgovernment`, `china`; record sets written with `If-Match` etags) and `type: desec` (a token that token policies can limit to the `_acme-challenge` TXT record set; no write when the value is already there). Route 53 and Google skip private zones when looking a zone up. Record sets that hold all values of a name are changed under a per-zone lock, so a wildcard and its base name presented at once keep both values. Access tokens are cached until five minutes before they expire and renewed as soon as the key file or secret changes. Every adapter passes the contract test, which now also checks that a private zone is skipped.

### Changed
- **A failed connection is retried on another backend by default** (ADR-0028): a service without `retries` now behaves as `retries: {}` (connection failures only, up to 2 more attempts, within the retry budget); `retries: { attempts: 0 }` turns it off. A connection that timed out is retried only on a backend not tried yet. In the 3-node Swarm lab this took rolling updates from 85 failed requests in 36,001 to none.
- A connection attempt that would be retried on another backend gives up after `timeouts.connect_attempt` (1 s) instead of the full `timeouts.connect` (5 s), so a stopped backend costs about a second per request instead of five; the last attempt keeps the full timeout (#185, ADR-0026).

### Fixed
- Answers produced by middlewares (maintenance pages, redirects, error pages) now pass through `compress` and `bandwidth` like backend responses; before, a `compress` middleware ahead of a large `maintenance` page could announce a `Content-Encoding` the body did not have. `compress` no longer adds a second `Vary: Accept-Encoding`.

## [0.4.0-alpha.1] — v0.4 "Production reliability"

### Fixed
- **Every response to an HTTP/1 client left as two packets** ([#93](https://github.com/Docker-Hunterpedia/ReverseDock/issues/93)): the header and the body were written separately, because the client connection had no write buffer. It now has one (8 KiB, allocated on the first write), so a header and a typical body leave in one write and one segment, as from NGINX.
- **About 500 requests in flight was the most a container could hold** ([#93](https://github.com/Docker-Hunterpedia/ReverseDock/issues/93)): rdock now raises its soft open-file limit to the hard one at start, as Go programs do; containers often start with a soft limit of 1024 (Docker 29.1 with containerd 2.2). The limit raised, and a warning when it cannot be, are in the log.
- **Throughput collapsed under overload** ([#86](https://github.com/Docker-Hunterpedia/ReverseDock/issues/86), ADR-0023): each listener kept only 128 idle connections to backends, so with more requests in flight every extra request opened and closed its own backend connection. The pool is now 4096 and configurable with `security.limits.upstream_idle_connections` (M-LB-08). At a 40,000 req/s target the benchmark now holds about 14,900 req/s with 0.37 % failures instead of 1,925 req/s with 52 %.

### Changed
- `compress` offers `[zstd, br, gzip]` by default instead of `[gzip]`. Set `algorithms: [gzip]` to keep the old behaviour.

### Added
- **Balancing policies** (M-LB-01, M-LB-02, ADR-0022): `least_requests` and `least_conn` (fewest requests in flight relative to the weight), `p2c` (power of two choices), and consistent hashing of the client IP, a header or a cookie (`ip_hash`, `header_hash`, `cookie_hash`) on a ketama-style ring that every instance computes the same way. Per-backend state is shared across reloads.
- **Sticky sessions** (M-LB-03): `sticky.cookie` pins a client to a backend with an HMAC-SHA256-signed cookie that never contains the backend address; `Secure`, `HttpOnly` and `SameSite=Lax` by default; the key comes from `secret` or `$RDOCK_DATA_DIR/sticky.key`, and `previous_secrets` keeps cookies valid across a key rotation.
- **Health checks** (M-LB-04, M-LB-05, M-LB-07…09, M-L4-05): active probes in the background over HTTP (status, body, method, host, headers), TCP or the gRPC health protocol, with jitter and streak thresholds; passive ejection after `failures` within `window` (connection errors, resets, timeouts and 502/503/504 by default), doubling ejection times up to 5 minutes, a single trial request before a backend returns, and at most `max_ejection_percent` of a pool ejected. When every backend is down the pool fails open by default (`when_all_down`). `slow_start`, `backup` backends, `max_requests` and `max_connections_per_backend`. Metrics `rdock_backend_up` and `rdock_backend_ejections_total`.
- **Retries** (M-LB-06, ADR-0015): `retries.on` takes `connect`, `reset`, `timeout`, `502`, `503` and `504`; each retry goes to a backend the request has not tried yet, after a jittered backoff of up to 25–250 ms; a retry budget keeps retries in flight within `budget_percent` (20) of the requests in flight, with 3 always allowed. Connect failures are retried for every method, everything else only for idempotent ones unless `retry_non_idempotent`; never after the client saw a response or for bodies over 64 KiB. A `503` with `Retry-After` pauses that backend for up to 60 seconds. Metrics `rdock_retries_total` and `rdock_retry_budget_exhausted_total`.
- **Splits, mirroring, gRPC-Web** (M-RT-03, M-RT-04, M-RT-07): `split` services spread requests over other services by weight (smooth round-robin, nested up to 4 levels), switched atomically on reload; the access log names the service that answered. `mirror` sends a copy of `percent` of a route's requests to another service in the background (bodies up to 64 KiB, at most 64 copies in flight per route, metric `rdock_mirror_requests_total`). The `grpc_web` middleware translates binary gRPC-Web from browsers to gRPC and back.
- **Limits** (M-TM-01…04, M-TM-06, M-TM-07): rate limits by `cookie:<name>`; the `in_flight` middleware caps requests in flight per key with an optional queue and deadline (429); `security.limits.max_in_flight` sheds load with 503; the `bandwidth` middleware limits response bytes per second per key; routes take `max_body`. `compress` adds zstd and Brotli, negotiated by `Accept-Encoding` q-values with the configured order breaking ties.
- **Client certificates** (M-TLS-01, W-CF-08): `listeners.<l>.tls.client_auth` with `mode: required` or `optional`, verified against `ca_files` and, with `cloudflare: true`, Cloudflare's built-in origin-pull CA (Authenticated Origin Pulls). The `client_cert` middleware demands a certificate per route, checks its names against `allow` patterns and forwards the identity in Traefik's or Envoy's (XFCC) headers; client-sent copies of those headers are always removed. Services present `tls.cert_file`/`key_file` to backends (upstream mTLS), checked at load.
- **JWT validation** (M-SEC-01): the `jwt` middleware verifies RS/PS/ES/EdDSA/HS tokens with ReverseDock's own verifier on ring, keys from `jwks_url` (background fetch, 10-minute cache, early refresh on an unknown `kid`), `jwks_file` or `hmac_secret`. Algorithms are fixed by the configuration and pinned per key; `exp` is required; `iss` and `aud` are required unless set to `any`; `claims_to_headers` replaces client-sent copies. Limits can count by `claim:<name>`. A new fuzz target covers the verifier.
- **Tracing and observability** (M-OBS-01…03): OpenTelemetry traces over OTLP/HTTP (protobuf, through ReverseDock's own rustls client): a server span per request named `{method} {route}`, a client span per upstream attempt, W3C `traceparent` continued and passed upstream, parent-based ratio sampling, batched export that drops spans rather than slow requests. New metrics `rdock_backend_requests_total` and `rdock_upstream_duration_seconds`. `observability.access_log.sample` logs a share of successful requests and every error.
- **DNS discovery** (M-LB-10): backend names are resolved with hickory and refreshed when their TTL expires (kept between 1 s and 5 min), with the system resolver as a fallback; `srv://_service._proto.name` backends use SRV records, the lowest priority as primaries and higher ones as backups.
- **Ping endpoint** (W-CF-07): `listeners.<l>.ping: /path` answers `200 OK` for any host before routing, for Cloudflare Load Balancing and other monitors.
- **Traefik labels** for v0.4: `healthcheck.mode/status/hostname/method/headers`, `passivehealthcheck.*`, `loadbalancer.strategy`, the `retry` middleware (moved onto the router's service as `retries`), `inFlightReq` and `passTLSClientCert`; `circuitBreaker` is reported with what to use instead. `rdock migrate traefik` translates them too.
- **Chaos suite and benchmarks** (H-ENG-01, H-ENG-02): Toxiproxy-driven tests (a slow backend, resets, an outage and a flapping backend) run in CI; a test shows the retry budget holding an outage to 1.35× the client traffic against 5.9× without it. `benchmarks/` compares ReverseDock with NGINX, HAProxy, Caddy and Traefik under identical configurations and limits with open-model k6 load, with the first published results. A nightly `bench` workflow checks ReverseDock against NGINX for regressions, and `benchmarks/soak/` runs a 24-hour soak with reloads, backend outages and certificate changes under load (H-ENG-03).
- `rdock validate` warns about routes that never match because an earlier route on the same listener has the same rule or matches everything (M-RT-02).

## [0.3.0-alpha.1] — v0.3 "Automatic HTTPS"

### Added
- Guides for [automatic HTTPS](https://reversedock.oday-bakkour.com/docs/guides/automatic-https/), [wildcards and DNS-01](https://reversedock.oday-bakkour.com/docs/guides/dns-challenge/) and [running behind Cloudflare](https://reversedock.oday-bakkour.com/docs/guides/cloudflare/) (Full (strict), Origin CA, Cloudflare Tunnel); Compose examples `deploy/docker/examples/https` and `cloudflare-tunnel`, validated in CI.
- **Automatic certificates** (ADR-0020): routes with `tls: auto` whose hosts no configured certificate covers get a certificate from Let's Encrypt (or `acme.ca`) through HTTP-01, answered on every plain-HTTP listener before routing. One certificate per name, or one per route with `tls.domains`; each with a new ECDSA P-256 key; stored in `$RDOCK_DATA_DIR/acme` (mode 0600, atomic writes, a lock against a second process) and served without a reload; renewed when a third of the lifetime is left; failures retried with backoff from 1 minute to 24 hours. `tlsserver` is ordered when the CA offers it. `acme.ca_root` trusts an internal CA's endpoint. Names public CAs do not certify (`localhost`, `.internal`, private addresses …) are never ordered; they go to the local CA. Tested end to end against Pebble.
- **Local CA and `rdock trust`** (B-TLS-13, ADR-0020): `localhost` and `*.localhost`, names under `.local`, `.internal`, `.home.arpa`, `.test`, `.example` and `.invalid`, and loopback, private and link-local addresses get a certificate from a local CA in `$RDOCK_DATA_DIR/pki` (directory 0700, keys 0600), created on first use: an ECDSA P-256 root valid for 10 years whose name constraints permit only those names and ranges, a 30-day intermediate that signs and is rotated with a third of its life left, and 7-day certificates renewed the same way, served without a reload. `rdock trust` installs the root with the platform tool (macOS `security`, Linux anchors with `update-ca-certificates`, `update-ca-trust` or `trust`, NSS `certutil`; Windows prints the `certutil` command) and `rdock trust --uninstall` removes it; nothing is installed automatically. Single-label names such as `nas` get a warning suggesting `nas.internal` or `nas.home.arpa`.
- **TLS-ALPN-01** (RFC 8737): certificates can also be validated on a TLS listener, without a plain-HTTP port. A handshake offering only `acme-tls/1` gets the validation certificate for its name and is closed without HTTP; no validation certificate is ever served otherwise. `acme.challenges` sets the order of preference, and after a failure the next attempt starts with the next challenge type.
- **Renewal through ARI** (RFC 9773): after issuance, on start and whenever the CA's Retry-After passes, ReverseDock asks the CA for its suggested renewal window and renews at a random time inside it, with `replaces` so Let's Encrypt exempts the order from rate limits. Without ARI it renews with a third of the lifetime left, so 90-, 64-, 45- and 6-day certificates all work. After a failure against Let's Encrypt production, the next attempt proves the setup on staging first. A CA outage never stops serving the stored certificate.
- **Certificate alerts** (B-TLS-12): `rdock status` lists every automatic certificate with its expiry, renewal time, failures and last error; metrics `rdock_cert_renewal_failures_total{name}` and `rdock_acme_orders_total{ca,result}` join `rdock_cert_expiry_timestamp_seconds`; after 3 failures in a row, or with less than 7 days left, a warning is logged and `observability.alerts.webhook` receives the event as JSON (at most once a day per certificate).
- **Cloudflare client IPs** (W-CF-01, W-CF-02): `security.trusted_proxies: [cloudflare]` trusts Cloudflare's edge ranges, fetched from `api.cloudflare.com/client/v4/ips` once a day (kept when the `etag` is unchanged, and when a fetch fails or looks wrong), cached in `$RDOCK_DATA_DIR/cloudflare/ips.json` and backed by a list built into the binary, so startup never waits for the network. Nothing is fetched unless a configuration trusts `cloudflare`. `client_ip_header: cf-connecting-ip` takes the client IP from `CF-Connecting-IP` sent by a trusted peer; with `auto`, a request straight from a Cloudflare address uses `CF-Connecting-IP` and every other trusted proxy `X-Forwarded-For`. From any other peer the header is removed and ignored. `rdock run` no longer refuses these two settings.
- **DNS-01 for any name** (W-DNS-01, W-DNS-02, W-CF-03): wildcards, hosts behind a firewall or a tunnel, or every route with `acme.dns_provider`. Providers: `cloudflare` (token with Zone → DNS → Edit; zone looked up or `zone_id`), `exec` (a program called as `present|cleanup <fqdn> <value>`, never through a shell) and `webhook` (JSON to an HTTPS endpoint). Before validation the record is looked up at the zone's authoritative nameservers, or `acme.dns_resolvers`, for up to `acme.dns_propagation_timeout` (2 minutes); records are removed afterwards. Docker labels: `rdock.tls=dns:<provider>`.
- Configuration for automatic HTTPS (ADR-0020): `acme: false` turns automatic certificates off; `acme.dns_provider` names a default DNS provider for every route; DNS providers `exec` (a program run without a shell) and `webhook` (JSON to an `https://` endpoint) next to `cloudflare`, which gains `zone_id`; `observability.alerts.webhook` for certificate alerts. Webhooks must use `https://` (plain `http://` only for localhost), exec commands must be absolute paths, and tokens should be `${file:…}` references. Public IP-address hosts are flagged unless `acme.profile: shortlived`, and DNS-01 for an IP address is refused.

### Changed
- **Zero-config mode serves HTTPS:** without a configuration file, labelled containers are served on `:443` with automatic certificates, `:80` redirects to HTTPS and answers HTTP-01, and `rdock.tls=off` containers stay on plain HTTP at `:80`.
- **`client_ip_header: cf-connecting-ip` needs `trusted_proxies`, not `cloudflare` specifically**: behind a Cloudflare Tunnel the trusted peer is `cloudflared` on your network.
- **Routes with `tls: off` and no `listeners` attach to the plain-HTTP listeners** instead of `defaults.listeners` (ADR-0021), so a plain route never lands on an HTTPS listener it cannot be served on.
- **`tls: auto` routes now get certificates.** In v0.2 a route asking for automatic HTTPS without a matching certificate was refused ("planned for v0.3"); now ReverseDock orders one from Let's Encrypt production, which accepts its terms of service. Set `acme: false` to keep v0.2's behaviour, or `acme: { staging: true }` to try it first. `ca: buypass` is refused: Buypass stopped issuing certificates on 2025-10-16.

## [0.2.0-alpha.1] — v0.2 "Docker-native"

### Added
- **Extra configuration files** (`providers.file.paths`): files or patterns such as `conf.d/*.yaml` (relative to the main file) add routes, services, middlewares, TCP objects and certificates to the main file. A name defined twice is an error naming both files; other sections belong in the main file. They are watched like the main file, and a file added next to a pattern is loaded without a restart. `rdock validate` reads them too.
- **`rdock migrate traefik`** (F-MGMT-03): turns the Traefik labels of a Compose file, or a Traefik dynamic configuration, into routes, services and middlewares for `rdock.yaml`, through the same translator as the Docker provider. What cannot be migrated is listed at the top of the output. `--expose-by-default` follows Traefik's default for services without `traefik.enable`.
- **Zero-config mode** (B-CFG-11): `rdock run` with no configuration file (none given and none at `/etc/rdock/rdock.yaml`) and a Docker socket at `/var/run/docker.sock` serves labelled containers over HTTP on `:80`; the admin listener keeps its default. Without the socket it exits with a hint. HTTPS joins it in v0.3.
- **The Docker provider** (`providers.docker`, ADR-0018): routes, services and middlewares from container labels, native `rdock.*` and a Traefik v3 subset (64 conformance fixtures in `tests/conformance/traefik-labels`). Containers are opt-in; replicas share a service; unhealthy containers leave the pool. A container Docker is stopping leaves its pool as soon as Docker signals it (the `kill` event), so new requests go to the other replicas while its open requests finish. Changes apply within about a second of the Docker event; if the Docker socket is lost, the last routes stay in service and the provider reconnects. Unix sockets and `tcp://` socket proxies; `rdock status` shows the provider's state. The `docker` cargo feature (on by default) builds it.
- The public website and documentation in `apps/website` (Astro + Starlight, ADR-0017): a landing page and 69 pages of guides, install and migration guides (from Traefik and NGINX), concepts, operations and reference. The configuration and CLI reference are generated from the schema and the binary; every complete configuration in the docs passes `rdock validate --strict` in CI, and "planned for vX.Y" badges are checked against what `rdock` refuses.

### Changed
- A file route that refers to another provider's object (`name@docker`) that does not exist is left out with a warning; the rest of the configuration applies (ADR-0018). The error for a missing service or middleware now reads "`x` does not exist".
- New logo, "Berth": a container moored in an amber dock bay. It replaces the two-arrow mark in the README banner, the website and docs header (with a dark-theme version), and the favicon; the website gains the full web icon set and a manifest. Master files and usage rules are in `docs/assets/logo/`.

### Fixed
- `rdock validate` no longer warns that a route without `Host` needs a host name for automatic HTTPS when `defaults.certificate` serves it.
- The Compose example mounts the config directory instead of the single file (editors replace files on save, which broke reloads), and starts after the backend so its name resolves on the first request.

## [0.1.0-alpha.3] — v0.1 "hello proxy"

### Breaking
Configurations that worked with 0.1.0-alpha.2 may need changes:
- Unknown configuration keys are errors (they were ignored); the error suggests the nearest valid key. Keys starting with `x-` are still ignored, for YAML anchors.
- `redirect.permanent` defaults to `false` (302/307), as in Traefik. Set `permanent: true` for 301/308.
- `security.limits` defaults are 64 KiB of request headers, 100 headers and no body limit; set `max_body_bytes` to limit bodies.
- `rdock validate --strict` turns warnings into errors.

### Added
- **The proxy** (`rdock run`): Pingora 0.9 HTTP engine behind our own listeners (ADR-0012). HTTP/1.1, HTTP/2 over TLS (ALPN), h2c on plain listeners and to backends, WebSocket, server-sent events and gRPC with trailers; backends by IP, DNS name (re-resolved every 10 s) or Unix socket, over HTTP, HTTPS (verified, custom CA, or `verify: false`) or h2c; smooth weighted round-robin and weighted random.
- Routing with the Traefik v3 grammar: priorities, normalised paths (forwarded as normalised), host/path/method/header/query/client-IP matchers; automatic HTTP→HTTPS redirect for HTTPS hosts; branded 404/5xx pages with the request ID (HTML or JSON).
- TLS: manual certificates with SNI (exact, one-label wildcard, `defaults.certificate`), encrypted PKCS#8 keys (`key_password`), `modern` (TLS 1.3) and `intermediate` policies, session tickets, reload when the files change.
- Middlewares: `headers` (with HSTS on HTTPS only), `redirect`, `rewrite`, `strip_prefix`, `add_prefix`, `replace_path`, `basic_auth` (argon2id, bcrypt; Apache MD5 and SHA-1 with a warning), `forward_auth`, `ip_allow`, `ip_deny`, `rate_limit`, `cors`, `compress` (streaming gzip), `errors`, `maintenance`.
- Security: forwarding headers trusted only from `security.trusted_proxies`; header, header-count, target and body limits (431/414/413, chunked bodies counted); HTTP/1.1 without `Host`, bare-LF line endings and unknown `Expect` refused; 10 s request-header deadline; request IDs.
- Operations: reload on file change, `SIGHUP`, `rdock reload` or the admin API, without dropping requests; listener changes without a restart; configuration history and last-known-good copy in `$RDOCK_DATA_DIR/state`, used at start when the file is broken; drain on shutdown (`lifecycle.drain_timeout`); systemd readiness (`Type=notify`).
- Admin listener (`127.0.0.1:2080`): `/healthz`, `/readyz`, `/metrics` (Prometheus), and with a token `/api/v1/status` and `/api/v1/config/reload`; `rdock status`, `rdock reload`, `rdock healthcheck`.
- `${NAME}`, `${env:NAME}` and `${file:/path}` references in the configuration; secret fields stay references (ADR-0016).
- JSON (or text) access log and JSON application logs; Prometheus metrics for requests, latency, upstream errors, connections, TLS handshakes, reloads and certificate expiry.
- Packaging: `Dockerfile` (CMake added), `Dockerfile.release` and multi-arch GHCR images on tags (signed, attested), `deploy/docker` Compose example, `deploy/systemd/rdock.service`.
- Tests: end-to-end suites against the real binary (protocols, middlewares, smuggling vectors, limits, slow clients, reload under load, listener changes, drain, last-known-good, certificate swap); fuzz targets in `tests/fuzz` (differential HTTP/1 framing, rule parser, configuration loader) and a weekly `fuzz` workflow.
- `rdock hash [--user NAME]`: creates an argon2id hash (or a `user:hash` entry) for `basic_auth`, reading the password from stdin.
- Weekly `weekly` workflow: RustSec advisories for both lockfiles, and a tokio canary that tests past the tokio cap.
- ADRs 0012–0016; the v0.1 research notes in `docs/research/`.

### Changed
- `rdock validate` also compiles the configuration and lists settings this version cannot honour yet ("planned for vX.Y"); `rdock run` refuses them.
- Rules: matcher names are case-insensitive, one-argument `Query(k)` matches an empty value, `Host` accepts a trailing dot and unbracketed IPv6, `Method` compares in upper case (Traefik parity).
- Model: new `listeners.*.timeouts`, `routes.*.timeouts`, `defaults.certificate`, `certificates.*.key_password`, `headers.hsts`, `lifecycle.drain_timeout`.
- TLS uses rustls with the ring provider (ADR-0013); tokio is capped below 1.54 until Pingora supports it.

## [0.1.0-alpha.1] — M0 foundations (tagged, not published)

### Added
- Cargo workspace with all crates of the architecture; skeleton crates document their milestone.
- `rdock-rules`: Traefik v3 compatible rule parser (HTTP and TCP matchers, `!`, `&&`, `||`, parentheses, backtick and double-quoted strings), validation, canonical printing and property tests.
- `rdock-model`: configuration types for listeners, routes, services, middlewares, TCP, certificates, ACME, providers, security, admin and observability; typed values (durations, sizes, addresses, networks); semantic validation with paths and hints; JSON Schema (`schema/rdock.v1.json`).
- `rdock-config`: YAML (serde-saphyr, YAML 1.2 booleans) and JSON loading, unknown-key warnings with suggestions, `--strict` mode.
- `rdock validate`, `rdock schema`, `rdock version`.
- CI: rust (fmt, clippy pedantic, nextest, doc), msrv (1.89), cargo-deny, Docker build, Semgrep; release workflow with signed checksums, SBOM and provenance; static non-root Dockerfile.
- ADR-0011 (YAML parser and MSRV).

### Earlier

- Repository governance: contributing guide, code of conduct, security policy, support and governance docs, issue forms, PR template, CODEOWNERS, docs/DCO/PR-title CI checks, protected `main` and release tags.
